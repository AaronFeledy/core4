# Drive Lando through MCP

With Lando installed, configure your MCP client to launch `lando mcp` as a child
process with piped stdin and stdout. Start it in the app you work on most: tools and resources use
that directory's app unless a tool call names another one with `appPath`.
Before connecting, inspect the tools the server will expose without starting the
long-running session:

```sh
lando mcp --list --format=json
```

Check that the catalog includes the tools you intend to expose before connecting
the client. Do not launch serve mode directly in a terminal or add `--format=json`
to it; that format is for the terminating `--list` command.

For example, in GitHub Copilot, add this server to `~/.copilot/mcp-config.json`.
Replace `/home/you/shop` with the absolute path to your app, and make sure
Copilot can find `lando` on its `PATH` (or use the full executable path as
`command`).

```json
{
  "mcpServers": {
    "lando": {
      "type": "stdio",
      "command": "lando",
      "args": ["mcp"],
      "cwd": "/home/you/shop",
      "tools": ["*"]
    }
  }
}
```

Open a Copilot session and check that it lists `app:config:get` among the
`lando` server's tools. If the server doesn't start, check the executable path
and confirm the working directory is an app directory.

The server speaks MCP over newline-delimited JSON-RPC and runs until the client
closes stdin. Closing stdin ends the session: calls still running or waiting are
cancelled and their resources released, and shutdown generates no result for
them, not an error and not a success. A response that was already being written
may still arrive. So if you need a result, keep stdin open until the response
with that request id arrives. You don't need to cancel each outstanding request
before closing. Serve mode writes protocol frames only, not
a Lando command-result envelope for startup or shutdown.

## Initialize the client

Lando negotiates MCP protocol versions `2025-06-18`, `2025-03-26`, and
`2024-11-05`. An `initialize` that offers `2025-06-18` gets `2025-06-18` back.
Write one complete JSON-RPC object followed by a newline for every request or
notification. `\r\n` line endings work too.

If you're writing a client, send this line on stdin:

```json
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"my-agent","version":"1.0.0"}}}
```

Read stdout until the initialization response with `id: 1` arrives. Check its
`result.protocolVersion`, then send the notification and the tool request below,
one line each:

```json
{"jsonrpc":"2.0","method":"notifications/initialized"}
{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"app:config:get","arguments":{"args":{"key":"name"}}}}
```

Keep stdin open until stdout delivers the response with `id: 2`. Check
`result.structuredContent.result.value` for the app name, then close stdin to
send EOF and wait for the child to exit.

Lando ignores empty lines and lines containing only spaces, tabs, or carriage
returns. If a line's text is not valid JSON, Lando replies with one parse error
with `id: null`. Calls already running and requests on later lines continue.
This is a response from the server, not a line to send:

```json
{"jsonrpc":"2.0","id":null,"error":{"code":-32700,"message":"Parse error"}}
```

A line over 1 MiB or one left unfinished for 5 seconds after its first byte
ends the session.

## Call a tool and read its result

With MCP `2025-06-18`, every tool in `tools/list` carries a compact `outputSchema`.
It describes the envelope and the result's first-level fields, required keys,
simple types, and union variants. Nested objects are permissive summaries rather
than complete validation schemas, keeping tool discovery small. When a summary
matches a public schema exactly, its description points to the full schema at
`lando://schemas/{name}`, such as `lando://schemas/ServiceInfo`. Other summaries
have no resource pointer; not every command-specific shape has a public schema.

A `tools/call` result has
`structuredContent` holding the redacted, bounded `CommandResultEnvelope` for the
command, plus the same JSON as a `text` content block for clients that ignore
structured output. `isError` is `true` whenever the envelope is not `ok`, so a
command's own tagged failure (for example `LandofileNotFoundError`) arrives as a
normal tool result you can read.

The compact schema does not shorten the returned data. Results still use the full
command schema for server-side encoding, including tagged errors, validation
issues, warnings, deprecations, and bounded output with `output.truncated`.
MCP envelopes do not include the CLI's optional timing `trace`.

`deprecations` lists each deprecated surface the call used, once per surface
with its notice and the time of first use. For example, an `app:shell` call
that sends `flags.host: true` lists the deprecated `app:shell --host` flag, even
though the call then fails for lack of a terminal. The list belongs to that
call: calls running at the same time and earlier calls in the session never add
to it, and a later call that uses the same surface lists it again. MCP calls
print no deprecation warnings, so read this array to find what to migrate.

Rejections that never reach the command (bad input, `Server busy`) also come
back as a tool result with `isError: true`. Read the same envelope in
`structuredContent` or the first `text` block: `apiVersion` is `"v4"`, `command`
is the called tool id, `ok` is `false`, and `error` is the redacted tagged error,
including its `_tag`, `message`, and `remediation`. `warnings` and `deprecations`
are empty arrays. For `McpToolInputError`, `error.path` identifies the rejected
input. These rejections have no command result or output capture.
A tool outside the effective allowlist is never registered, so calling it gets
the protocol's unknown-tool error, code `-32602`.

A tool's input is the command's own `flags` and `args`, plus `appPath`. Output
selection is not part of it. Every call returns the JSON envelope, so no
command or plugin tool has a `format`, `json`, or `jq` input, and a call that
sends `flags.format` fails with `McpToolInputError` naming `flags.format`. A
tooling task that declares its own `format` flag keeps it as input, because
that flag belongs to the task.

Send integer flags as JSON numbers without a fractional part. For example, the
`app:logs` tool declares `flags.tail` as `integer`:

```json
{"jsonrpc":"2.0","id":4,"method":"tools/call","params":{"name":"app:logs","arguments":{"flags":{"tail":20}}}}
```

`20.5` and `"20"` are rejected with `McpToolInputError` naming `flags.tail`.
For tooling tasks, send declared flags and arguments by name in `flags` and
`args`. Use JSON booleans, including `false`, rather than strings for boolean
flags. Hyphen-leading strings remain values, not new options.

For `app:exec`, send `args.command` as an array of exact arguments. An optional
service name may come first; shell syntax runs only when you explicitly invoke
a shell:

```json
{"jsonrpc":"2.0","id":9,"method":"tools/call","params":{"name":"app:exec","arguments":{"args":{"command":["appserver","--","printf","%s","one argument"]}}}}
```

## Send named tooling inputs

To expose app tooling, inspect the opt-in catalog from the app directory:

```sh
lando mcp --tooling --list --format=json
```

Launch the client session with `lando mcp --tooling` from that same directory.
When the session starts, Lando reads your app's commands, rebuilding the index
if the Landofile, an include, or a script changed since the last run, so the
tool catalog matches the current Landofile. That rebuild plans the app without
starting services or the provider. Each tooling tool's `description` ends with the
sentence `lando <task> --help` prints about what the task runs, such as
``Runs `composer` in appserver.`` or `Runs .lando/scripts/tag.bun.sh on the host.`,
so an agent can tell a database reset from a lint run before calling it.

A `.bun.sh` script can accept sparse named arguments. For example, save this as
`.lando/scripts/tag.bun.sh` before starting the session:

```sh
# ---
# desc: Inspect release inputs
# flags:
#   loud:
#     boolean: true
#     default: true
# args:
#   label:
#     order: 0
#   channel:
#     order: 1
#     default: stable
#     choices: [stable, beta]
# ---
printf '%s\n' "$LANDO_INPUT"
```

After initializing the MCP session, send:

```json
{"jsonrpc":"2.0","id":5,"method":"tools/call","params":{"name":"app:tag","arguments":{"flags":{"loud":false},"args":{"channel":"beta"}}}}
```

Read the tool result's collected output. The script's `LANDO_INPUT` has exactly
`flags` and `args`: `flags.loud` is false, `args.channel` is `beta`, and `label`
is absent. No physical argv is synthesized. An explicit empty string would
remain present; omission alone allows a default. Lando considers only supplied
own properties, so names such as `constructor` do not pick up inherited values.

An argv-only Landofile task cannot represent the same positional gap. It fails
with `ToolingInputError`, whose `field` identifies the absent earlier argument,
rather than silently shifting `beta` into `label`. Required arguments remain
required on both surfaces. For tasks with no declarations, the catalog instead
exposes `args.args` as a string-array passthrough. Do not combine a raw tail with
declared named inputs.

Use `tools/list` as the input contract: choices are JSON Schema `enum`, defaults
retain their string or boolean type, and required members make their containing
`flags` or `args` group required too. The objects are closed with
`additionalProperties: false`. The schema includes `x-lando-input-revision` and
`x-lando-accepts-arguments`. Sensitive flags and arguments expose `writeOnly: true`;
they cannot have defaults or choices. These fields come from the same normalized
declaration used at execution, not prose-only hints. Send only the values you
intend to supply; the authoritative binder applies defaults once.

## Refresh a changed tooling contract

The server retains the revision it advertised and passes it with each tooling
call. Execution checks it against the resolved task after normal task precedence
and late connection-client resolution. Changes to input order, names, aliases,
types, defaults, choices, requiredness, sensitivity, or raw-argument policy reject
the call with `ToolingInputError` before the body runs. Script-body and
description-only edits keep the revision compatible.

After changing metadata, read `lando://diagnostics` and inspect `tools/list`
again. The read reloads the session app's tasks and replaces every changed tool
contract, as described in
[Find out why a tool is missing](#find-out-why-a-tool-is-missing). A session that
doesn't read it keeps the tooling catalog it started with. Reconnecting also
picks up the current commands, so no refresh command is needed. Rejected calls
are not automatically replayed. Review the new declaration before retrying.

If discovery reports `ToolingCommandUnavailableError`, its `reason` is
`missing-cache`, `stale-cache`, or `invalid-cache`. Those appear only in a rare
race where the app changed while Lando was reading it; run the command again.
A name the app does not define is an ordinary `UnknownCommandError`, with the
closest commands in `error.suggestions`, best first, when any are spelled nearby. On the host CLI, every app tooling command and help
rebuilds a missing, stale, or unreadable index before it runs; a rebuild that
fails makes the command fail with the real error, such as
`LandofileValidationError`. `lando help --format=json` exposes
`result.toolingMetadata` with `status` and, after a failed rebuild,
`reason: "rebuild-failed"`, `remediation`, and `error` as `{ _tag, message }`.
Calls from inside a container through the host proxy do not rebuild. Neither
path starts a provider only to repair discovery. You do not need `lando start`
or `lando rebuild` just for that. The same help JSON lists plugin commands as
`result.all[]` rows with `source: "plugin"` and reports plugin discovery in
`result.pluginMetadata`. Plugin commands can be MCP tools too; see
[Expose plugin commands](#expose-plugin-commands).

## Protect sensitive tooling values

Authors mark a flag or argument `sensitive: true`; the existing secret-name
heuristic also applies and cannot be disabled with `sensitive: false`. The
annotation works for an ordinary name such as `note`. Lando redacts supplied
sensitive values before publishing its output, errors, events, or traces,
including invalid, stale, and disabled calls. When authoritative metadata is
unavailable, pre-admission records omit input values rather than guessing which
are safe. Values remain literal, not expressions or secret-provider references.

This does not redact arbitrary files or external logs written by the script,
nor does it protect values your client records before sending them. Test with
fake values, as in [Mark sensitive inputs](../../tooling/bun-shell-scripts/#mark-sensitive-inputs).

## Read streamed command output

To expose your app's tooling tasks, launch the server with `lando mcp --tooling`.
Inspect that catalog first:

```sh
lando mcp --tooling --list --format=json
```

Include `_meta.progressToken` in a `tools/call` request to receive live output.
For example, if your app defines a `report` tooling task:

```json
{"jsonrpc":"2.0","id":8,"method":"tools/call","params":{"name":"app:report","arguments":{},"_meta":{"progressToken":"report-8"}}}
```

Match each `notifications/progress` notification by `params.progressToken`.
Parse `params.message` as JSON to read a text frame with `_tag: "stdout"` or
`"stderr"`, `chunk`, and optional `service` and `source` fields. Append `chunk`
to the matching output stream; it is not a separate command result.

Container output is decoded incrementally as UTF-8. Invalid or incomplete final
byte sequences become replacement characters, so progress notifications are not
a binary transfer channel. Lando buffers continuous output to a newline or 64 KiB
and sends the remaining tail before replying to a call that isn't cancelled.
Log records don't wait for a newline. Lando masks known secrets even when split
between output chunks. A credential shape that wraps onto the next line, such as
a quoted `password=` value, is masked as one value. Lando holds that unfinished
value for at most half a second, then sends the masked line and hides the rest
of the value as it arrives, up to its closing quote or 64 lines.

Wait for the response with the original request id before closing stdin.
Every completed command response includes `structuredContent.output`, even without
a progress token. Its `chunks` array holds redacted stdout and stderr text with
the same optional `service` and `source` fields. Small output is complete. Large
output keeps a bounded tail and sets `truncated: true`; the capture shares a
128 KiB response budget across all channels and may shrink further to fit the
final response. Treat this final capture as authoritative, rather than appending
it to an already displayed live preview.

A nonzero subprocess exit sets `isError: true` and `structuredContent.ok: false`.
The response keeps the typed `result`, including its exit code, alongside the
tagged `error` and captured output. A successfully produced diagnostic report can
instead have `ok: true` while reporting findings; inspect its result fields too.

Without a progress token, only live notifications are omitted. Final output,
status, and diagnostics are still returned. Cancel one unwanted request with
`notifications/cancelled` and its `requestId`; the session stays open for your
other requests. Closing stdin cancels every active call and releases its
provider reads, including idle log followers. Once Lando processes cancellation,
it sends no reply or new progress for that call. It discards buffered output
and any output produced during cleanup. Progress already sent may still arrive,
and cancelling doesn't undo changes the command already made to the app.
Cancelling an exec or tooling call also stops the command inside the container
and everything it started, so a port it held is free for your next call; you
don't need to kill leftover processes yourself.

## Confirm changes to an app

`app:rebuild` asks before it recreates containers. It is not in the default
allowlist; expose it with `--allow app:rebuild` or `mcp.allow`. `app:destroy`
stays forbidden unless you allowlist it explicitly the same way. Plugin commands
follow the same rule: Lando treats a command as destructive when its id ends in
`destroy`, `remove`, `uninstall`, `prune`, `gc`, `reset`, `restore`, `rebuild`,
or `poweroff`, or when the command declares a `yes` flag, so `db:reset` and
`db:import` are never on by default. Once exposed, any of these commands
proceeds without a question when the call sends `flags.yes: true`.

Without `yes`, what happens depends on the client. A client that advertised the
`elicitation` capability in `initialize` gets an `elicitation/create` request
with a `{ confirm: boolean }` form; the message names the tool, the app's
directory, and what the command is about to do. Accept with `confirm: true` and the command runs.
Decline, cancel, answer `confirm: false`, or say nothing for 120 seconds and the
call returns `isError: true` with a `CommandConfirmationError` whose `reason` is
`declined`. A client without elicitation gets the same error with `reason`
`non-interactive`. Elicitation never lifts a deny: a tool outside the effective
allowlist is still unknown to the session.

This request confirms a rebuild. Only send it when you intend to recreate the
app's containers:

```json
{"jsonrpc":"2.0","id":6,"method":"tools/call","params":{"name":"app:rebuild","arguments":{"flags":{"yes":true}}}}
```

Global policy commands are also excluded from the default tools. If you explicitly
allow `meta:global:disable` or `meta:global:reconcile`, the catalog marks them as
destructive because cleanup can remove containers and routes. They preserve named
volumes and refuse known or uncertain consumer disruption unless that call sends
`flags["allow-disruption"]: true`. This acknowledgement is never saved and does
not bypass ownership, dependency, or active-startup protection. These commands
have no `yes` flag or generic confirmation prompt.

## Expose plugin commands

Commands that plugins contribute are MCP tools under the same allowlist as the
built-ins. A bundled plugin command whose manifest sets `mcpAllowed: true`, today
`db:snapshots`, is on by default. Every other plugin command needs an explicit
`mcp.allow` entry or `--allow`, including commands from plugins you install
yourself, even when their manifest declares `mcpAllowed`. Destructive plugin
commands are never on by default and ask for confirmation as described above.

```sh
lando mcp --list --allow db:export --format=json
```

Each plugin tool in that list carries `plugin.name`, `plugin.source` (`bundled`
or `external`), and `destructive`. The `diagnostics` array names plugin commands
the catalog left out and why: a module that failed to load, a descriptor or
alias conflict, or a destructive command that tried to self-allow. A connected
client reads the same records from `lando://diagnostics`. An unknown id
passed to `--allow` that no plugin provides yet stays pending: `--list` reports
it in `diagnostics` with `_tag: "McpPendingAllowance"`, and the tool appears once
an app that provides it is selected, as described in the next section. A malformed
id, or one that can never be an MCP tool, fails with `McpToolInputError` before the
server starts.

A plugin command that runs a process streams its output the same way built-ins
do. With a progress token, `schedule:run` sends the job's output, and `db:import`,
`db:export`, `db:reset`, and `db:seed` send the database client's stderr, as
progress notifications while the call runs. The final response carries the same
output in `structuredContent.output`.

A default allowance covers the bundled plugin that ships the command. If an app
plugin replaces `db:snapshots` with its own implementation, that app's version
needs its own `--allow db:snapshots` entry.

## Drive another app with appPath

One session can work on several apps. Every tool accepts an `appPath` argument
next to `flags` and `args`. Set it to a directory inside the app you want; a
relative path resolves against the directory `lando mcp` was started in. This
call reads the app in `../shop` while the session runs in another app:

```json
{"jsonrpc":"2.0","id":12,"method":"tools/call","params":{"name":"app:config:view","arguments":{"appPath":"../shop"}}}
```

To find paths of known apps, read `lando://apps` and use an entry's `appRoot`
from its `apps` array as `appPath`. That resource lists apps known from applied
state and provider inventory; it does not search your filesystem for every
project. You can also supply the path of a project you already know.

The call uses that app's Landofile and its app plugins under `.lando/plugins`:
their service types, app features, and plugin commands. A plugin command that
both apps define runs the selected app's implementation, so its flags, its
confirmation, and its result follow that app's plugin. Calls without `appPath`
keep using the session app.

The first call that targets an app adds that app's allowed plugin commands to
the catalog. When that adds or changes a tool, the server sends
`notifications/tools/list_changed`. The call's result also includes a second
model-visible `text` block identifying the app by its path and listing added
tools separately from updated tool contracts. The first block remains the
envelope JSON, and `structuredContent` stays the envelope. The notice appears
even if the command fails or its call is rejected after publication. It only
reports contracts published by that call; a later call with no catalog changes
has no notice.

Clients that support tool list updates refresh automatically. If yours does
not, request `tools/list` to read the tools named in the notice. Review changed
contracts before retrying a rejected call.

Commands from installed and app plugins still need an `mcp.allow` or `--allow`
entry. When two apps define the same command id
differently, the tool's input schema lists each version under `anyOf`, and the
app you select decides which version validates your input.

A call can fail on `appPath` with `McpToolInputError` in two cases. If the
selected app has no plugin that provides the command, pick an app that does. If
the selected app's version of the command was not in the catalog when your call
arrived, the server has just published it: list tools again, check the updated
schema, and retry. Lando never runs a command under a contract it has not shown
you.

Lando reads each app's plugin selection on every call. Plugins you install,
link, remove, or edit take effect on the next call, including edits to files
imported by the plugin entry and contributions loaded later. A call already
using the previous code finishes first; calls that need the edited plugin wait
for it before loading the new code. This also applies when several apps share
the plugin. A syntax error makes that plugin's tools return a `PluginLoadError`
that names the plugin and the import error, and planning an app that uses one
of its service types reports the same error. Built-in tools and other plugins'
tools keep working. If the session dropped the broken tool, fix the file and
call `app:config:view` with `appPath` set to that app. Then refresh `tools/list`
before retrying the tool. If files keep changing during loading, finish the edit
and retry the call.

## Find out why a tool is missing

A command you expected can be absent from `tools/list` because Lando could not
build it: a tooling task whose declaration contradicts itself, or a plugin
command whose module fails to load. Read `lando://diagnostics` to see those
commands and what to change:

```json
{"jsonrpc":"2.0","id":8,"method":"resources/read","params":{"uri":"lando://diagnostics"}}
```

The resource is always listed in `resources/list`. Its JSON payload has three
fields:

| Field | What it holds |
| --- | --- |
| `revision` | A number that rises when the published tools or these records change |
| `diagnostics` | One record per unavailable command |
| `omittedDiagnosticCount` | Records left out to keep the payload within 16 KiB |

Every record has `commandId`, `kind` (`tooling` or `plugin`), `_tag`, and
`message`, usually with a `remediation`. A plugin record adds `plugin.name` and
`plugin.source`. A tooling record adds `sourceKind`: `landofile` for a task,
`bun-script` for a `.bun.sh` script. Landofile task declaration failures
(`ToolingCompileError`) also carry `issues` and `omittedIssueCount`, plus
`source` (the file and task) when known and within the disclosure budget.
These are the same fields a failed call reports under `error`.
[Fix an unavailable task](../tooling/flags-and-args.mdx#fix-an-unavailable-task)
explains how to read an `issues` entry.

This record is from an app whose `dup` task gives two flags the same alias. It
is one read of the resource, reindented, with the app directory shortened to
`/home/you/app`:

```json
{
  "commandId": "app:dup",
  "kind": "tooling",
  "_tag": "ToolingCompileError",
  "message": "tooling.dup.flags.note.alias: Flag alias collides with another flag name or alias.",
  "remediation": "Choose an alias that is not used by another flag name or alias.",
  "sourceKind": "landofile",
  "source": {
    "path": "/home/you/app/.lando.yml",
    "task": "dup"
  },
  "issues": [
    {
      "reason": "alias-collision",
      "path": ["tooling", "dup", "flags", "note", "alias"],
      "message": "Flag alias collides with another flag name or alias.",
      "suggestion": "Choose an alias that is not used by another flag name or alias.",
      "source": {
        "file": "/home/you/app/.lando.yml",
        "layer": "canonical",
        "path": ["tooling", "dup", "flags", "note", "alias"]
      },
      "related": [
        {
          "path": ["tooling", "dup", "flags", "name", "alias"],
          "source": {
            "file": "/home/you/app/.lando.yml",
            "layer": "canonical",
            "path": ["tooling", "dup", "flags", "name", "alias"]
          }
        }
      ]
    }
  ],
  "omittedIssueCount": 0
}
```

Reading the resource is also how a running session catches up with your edits.
Each read checks the app's tasks and selected plugin commands again and
republishes the tool catalog from that one snapshot. Fix the file a record
names, read the resource again, and the record is gone and the tool is in
`tools/list`. You don't restart the server or reconnect. The reverse holds too:
break a working task, read the resource, and the tool leaves the list and gains
a record. When a read changes the catalog, the server sends
`notifications/tools/list_changed`.

The session keeps the environment it started with. Editing a source file can
take effect through a resource read, but changing a variable in your shell
does not change a running server's environment. Start a new MCP session when
you need it to use a different environment.

The records cover only commands this session is allowed to expose:

- Tooling records need `lando mcp --tooling`.
- Tasks hidden with `internal: true`, disabled tasks, and ids you deny never
  appear, and they aren't counted in `omittedDiagnosticCount` either.
- A failing plugin command appears when its id is allowed. A command from a
  plugin you installed needs its own `--allow` entry even when it replaces a
  bundled command that is on by default.

The resource describes the app in the directory `lando mcp` was started in and
takes no `appPath`. It reports commands that fail on their own. With
`--tooling`, a Landofile that cannot load at all, for example because of a YAML
syntax error, makes the read fail instead: the JSON-RPC error's `data` carries
the tagged error, such as `LandofileParseError`, and its remediation. Fix the
file and read again.

`lando mcp --list --format=json` prints the same records under
`result.diagnostics`, with `result.omittedDiagnosticCount`, before you connect.

## Read resources and complete schema names

The server also publishes read-only resources. App and diagnostic payloads use
the full matching command result schema, not the compact tool-discovery
projection, and are redacted and bounded the same way tool results are.
Schema resources return full public JSON Schema documents on demand.

| URI | What you get |
| --- | --- |
| `lando://app/config` | Resolved configuration for the app in the server's working directory |
| `lando://app/info` | Services and connections for that app |
| `lando://apps` | Known apps and their services |
| `lando://doctor` | Host-safe diagnostics, no fixes applied |
| `lando://diagnostics` | Commands this session could not publish as tools, and why |
| `lando://schemas/{name}` | A public Lando JSON schema by name |

App-scoped resources resolve the app from the directory `lando mcp` was started
in and fail with the usual tagged errors when there is no app there. The
`lando://schemas/{name}` template supports `completion/complete`, so a client
can tab through the public schema registry instead of guessing names.
Resources have no `appPath`. To read another app, call `app:info` or
`app:config:view` with `appPath` instead.

```json
{"jsonrpc":"2.0","id":7,"method":"completion/complete","params":{"ref":{"type":"ref/resource","uri":"lando://schemas/{name}"},"argument":{"name":"name","value":"CommandResult"}}}
```
