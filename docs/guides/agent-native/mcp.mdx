# Drive Lando through MCP

Configure your MCP client to launch `lando mcp` as a child process with piped
stdin and stdout. For app-scoped tools and resources, start it in the app directory.
Before connecting, inspect the tools the server will expose without starting the
long-running session:

```sh
lando mcp --list --format=json
```

Check that the catalog includes the tools you intend to expose before connecting
the client. Do not launch serve mode directly in a terminal or add `--format=json`
to it; that format is for the terminating `--list` command.

The server speaks MCP over newline-delimited JSON-RPC and runs until the client
closes stdin. Closing stdin ends the session: calls still running or waiting are
cancelled and their resources released, and shutdown generates no result for
them, not an error and not a success. A response that was already being written
may still arrive. So if you need a result, keep stdin open until the response
with that request id arrives. You don't need to cancel each outstanding request
before closing. Serve mode writes protocol frames only, not
a Lando command-result envelope for startup or shutdown.

## Initialize the client

Lando negotiates MCP protocol versions `2025-06-18`, `2025-03-26`, and
`2024-11-05`. An `initialize` that offers `2025-06-18` gets `2025-06-18` back.
Write one complete JSON-RPC object followed by a newline for every request or
notification. An inbound frame over 1 MiB ends the session.

```json
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"my-agent","version":"1.0.0"}}}
```

## Call a tool and read its result

Every tool in `tools/list` carries an `outputSchema`. A `tools/call` result has
`structuredContent` holding the redacted, bounded `CommandResultEnvelope` for the
command, plus the same JSON as a `text` content block for clients that ignore
structured output. `isError` is `true` whenever the envelope is not `ok`, so a
command's own tagged failure (for example `LandofileNotFoundError`) arrives as a
normal tool result you can read.

Rejections that never reach the command (bad input, `Server busy`) also come
back as a tool result with `isError: true`; the
`text` block is the tagged error as JSON and there is no `structuredContent`.
A tool outside the effective allowlist is never registered, so calling it gets
the protocol's unknown-tool error, code `-32602`.

Send integer flags as JSON numbers without a fractional part. For example, the
`app:logs` tool declares `flags.tail` as `integer`:

```json
{"jsonrpc":"2.0","id":4,"method":"tools/call","params":{"name":"app:logs","arguments":{"flags":{"tail":20}}}}
```

`20.5` and `"20"` are rejected with `McpToolInputError` naming `flags.tail`.
For tooling tasks, send declared flags and arguments by name in `flags` and
`args`. Use JSON booleans, including `false`, rather than strings for boolean
flags. Hyphen-leading strings remain values, not new options.

For `app:exec`, send `args.command` as an array of exact arguments. An optional
service name may come first; shell syntax runs only when you explicitly invoke
a shell:

```json
{"jsonrpc":"2.0","id":9,"method":"tools/call","params":{"name":"app:exec","arguments":{"args":{"command":["appserver","--","printf","%s","one argument"]}}}}
```

## Send named tooling inputs

To expose app tooling, refresh its command cache in the app directory, then
inspect the opt-in catalog:

```sh
lando app:cache:refresh
lando mcp --tooling --list --format=json
```

Launch the client session with `lando mcp --tooling` from that same directory.
The refresh rebuilds the full app plan and command index without starting
services. It is explicit, not an automatic metadata-only repair.

A `.bun.sh` script can accept sparse named arguments. For example, save this as
`.lando/scripts/tag.bun.sh` before refreshing:

```sh
# ---
# desc: Inspect release inputs
# flags:
#   loud:
#     boolean: true
#     default: true
# args:
#   label:
#     order: 0
#   channel:
#     order: 1
#     default: stable
#     choices: [stable, beta]
# ---
printf '%s\n' "$LANDO_INPUT"
```

After initializing the MCP session, send:

```json
{"jsonrpc":"2.0","id":5,"method":"tools/call","params":{"name":"app:tag","arguments":{"flags":{"loud":false},"args":{"channel":"beta"}}}}
```

Read the tool result's collected output. The script's `LANDO_INPUT` has exactly
`flags` and `args`: `flags.loud` is false, `args.channel` is `beta`, and `label`
is absent. No physical argv is synthesized. An explicit empty string would
remain present; omission alone allows a default. Lando considers only supplied
own properties, so names such as `constructor` do not pick up inherited values.

An argv-only Landofile task cannot represent the same positional gap. It fails
with `ToolingInputError`, whose `field` identifies the absent earlier argument,
rather than silently shifting `beta` into `label`. Required arguments remain
required on both surfaces. For tasks with no declarations, the catalog instead
exposes `args.args` as a string-array passthrough. Do not combine a raw tail with
declared named inputs.

Use `tools/list` as the input contract: choices are JSON Schema `enum`, defaults
retain their string or boolean type, and required members make their containing
`flags` or `args` group required too. The objects are closed with
`additionalProperties: false`. The schema includes `x-lando-input-revision` and
`x-lando-accepts-arguments`. Sensitive flags and arguments expose `writeOnly: true`;
they cannot have defaults or choices. These fields come from the same normalized
declaration used at execution, not prose-only hints. Send only the values you
intend to supply; the authoritative binder applies defaults once.

## Refresh a changed tooling contract

The server retains the revision it advertised and passes it with each tooling
call. Execution checks it against the resolved task after normal task precedence
and late connection-client resolution. Changes to input order, names, aliases,
types, defaults, choices, requiredness, sensitivity, or raw-argument policy reject
the call with `ToolingInputError` before the body runs. Script-body and
description-only edits keep the revision compatible.

After changing metadata, run `lando app:cache:refresh`, reconnect the client,
and inspect `tools/list` again. A running session does not atomically replace its
catalog after a refresh, and rejected calls are not automatically replayed.
Review the new declaration before retrying.

If discovery reports `ToolingCommandUnavailableError`, inspect its `reason`:
`missing-cache`, `stale-cache`, or `invalid-cache` requires an explicit refresh;
`unknown-command` means a fresh index has no matching command, so check the name
and aliases. `lando help --format=json` exposes `result.toolingMetadata` with
`status` and, when unavailable, `reason` and `remediation`. Neither help nor a
failed lookup repairs metadata by planning or starting a provider. You do not
need `lando start` or `lando rebuild` just to repair discovery. The same help
JSON lists plugin commands as `result.all[]` rows with `source: "plugin"` and
reports plugin discovery in `result.pluginMetadata`; those commands are not
MCP tools, and `lando mcp --allow` accepts built-in ids only.

## Protect sensitive tooling values

Authors mark a flag or argument `sensitive: true`; the existing secret-name
heuristic also applies and cannot be disabled with `sensitive: false`. The
annotation works for an ordinary name such as `note`. Lando redacts supplied
sensitive values before publishing its output, errors, events, or traces,
including invalid, stale, and disabled calls. When authoritative metadata is
unavailable, pre-admission records omit input values rather than guessing which
are safe. Values remain literal, not expressions or secret-provider references.

This does not redact arbitrary files or external logs written by the script,
nor does it protect values your client records before sending them. Test with
fake values, as in [Mark sensitive inputs](../../tooling/bun-shell-scripts/#mark-sensitive-inputs).

## Read streamed command output

To expose your app's tooling tasks, launch the server with `lando mcp --tooling`.
Inspect that catalog first:

```sh
lando mcp --tooling --list --format=json
```

Include `_meta.progressToken` in a `tools/call` request to receive live output.
For example, if your app defines a `report` tooling task:

```json
{"jsonrpc":"2.0","id":8,"method":"tools/call","params":{"name":"app:report","arguments":{},"_meta":{"progressToken":"report-8"}}}
```

Match each `notifications/progress` notification by `params.progressToken`.
Parse `params.message` as JSON to read a text frame with `_tag: "stdout"` or
`"stderr"`, `chunk`, and optional `service` and `source` fields. Append `chunk`
to the matching output stream; it is not a separate command result.

Container output is decoded incrementally as UTF-8. Invalid or incomplete final
byte sequences become replacement characters, so progress notifications are not
a binary transfer channel. Continuous output is buffered to a newline or 64 KiB;
the remaining tail is sent when the command finishes. Log records are delivered
without waiting for a newline. Known secret values are masked even when split
between output chunks.

Wait for the response with the original request id before closing stdin.
Every completed command response includes `structuredContent.output`, even without
a progress token. Its `chunks` array holds redacted stdout and stderr text with
the same optional `service` and `source` fields. Small output is complete. Large
output keeps a bounded tail and sets `truncated: true`; the capture shares a
128 KiB response budget across all channels and may shrink further to fit the
final response. Treat this final capture as authoritative, rather than appending
it to an already displayed live preview.

A nonzero subprocess exit sets `isError: true` and `structuredContent.ok: false`.
The response keeps the typed `result`, including its exit code, alongside the
tagged `error` and captured output. A successfully produced diagnostic report can
instead have `ok: true` while reporting findings; inspect its result fields too.

Without a progress token, only live notifications are omitted. Final output,
status, and diagnostics are still returned. Cancel one unwanted request with
`notifications/cancelled` and its `requestId`; the session stays open for your
other requests. Closing stdin cancels every active call and releases its
provider reads, including idle log followers. Either way, a cancelled call gets
no fabricated result, and a change the command had already applied to the app
stays applied. Progress notifications you already received remain valid.

## Confirm changes to an app

`app:rebuild` asks before it recreates containers. It is not in the default
allowlist; expose it with `--allow app:rebuild` or `mcp.allow`. `app:destroy`
stays forbidden unless you allowlist it explicitly the same way. Once exposed,
either command proceeds without a question when the call sends `flags.yes: true`.

Without `yes`, what happens depends on the client. A client that advertised the
`elicitation` capability in `initialize` gets an `elicitation/create` request
with a `{ confirm: boolean }` form; the message names the tool, the app's
directory, and what the command is about to do. Accept with `confirm: true` and the command runs.
Decline, cancel, answer `confirm: false`, or say nothing for 120 seconds and the
call returns `isError: true` with a `CommandConfirmationError` whose `reason` is
`declined`. A client without elicitation gets the same error with `reason`
`non-interactive`. Elicitation never lifts a deny: a tool outside the effective
allowlist is still unknown to the session.

```json
{"jsonrpc":"2.0","id":6,"method":"tools/call","params":{"name":"app:rebuild","arguments":{"flags":{"yes":true}}}}
```

## Read resources and complete schema names

The server also publishes read-only resources. Each JSON payload reuses the
matching command result schema and is redacted and bounded the same way tool
results are.

| URI | What you get |
| --- | --- |
| `lando://app/config` | Resolved configuration for the app in the server's working directory |
| `lando://app/info` | Services and connections for that app |
| `lando://apps` | Known apps and their services |
| `lando://doctor` | Host-safe diagnostics, no fixes applied |
| `lando://schemas/{name}` | A public Lando JSON schema by name |

App-scoped resources resolve the app from the directory `lando mcp` was started
in and fail with the usual tagged errors when there is no app there. The
`lando://schemas/{name}` template supports `completion/complete`, so a client
can tab through the public schema registry instead of guessing names.

```json
{"jsonrpc":"2.0","id":7,"method":"completion/complete","params":{"ref":{"type":"ref/resource","uri":"lando://schemas/{name}"},"argument":{"name":"name","value":"CommandResult"}}}
```

The two read-only tools are `app:config:get` and `app:config:view`. Both accept
optional `flags.source` (`raw`, `merged`, or `resolved`) and `flags.path`.
The source defaults to `resolved`. Get selects `args.key ?? flags.path`, so
`args.key` is optional but one selector is required. View reads the complete
source unless `flags.path` selects a value. The fixed `lando://app/config`
resource still returns resolved configuration. Umbrella and write-capable ids:
`app:config`, `app:config:set`, `app:config:unset`, `app:config:edit`,
`app:config:validate` are not MCP tools, even through explicit allow
configuration.

Protocol input and output stay bounded. An inbound frame, including one
still being read, is capped at 1 MiB. At most 256 unresolved tool calls are
retained; request 257 gets a tool result with `isError: true` whose text is
a `McpTransportError` reading `Server busy`, and it carries no
`structuredContent`. Each serialized JSON payload is capped at 8 MiB, and a
stdout write that does not finish fails after 5 seconds.
