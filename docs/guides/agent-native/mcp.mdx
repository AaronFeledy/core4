# Drive Lando through MCP

An MCP client starts `lando mcp` as a child process and owns its stdin and stdout
pipes. The server exchanges one JSON-RPC object per line and runs until the client
closes stdin. Keep stdin open until every outstanding request id has answered;
closing early interrupts in-flight tool calls. Serve mode writes protocol frames
only; it does not wrap startup or shutdown in a Lando command-result envelope.

Configure the MCP client to launch `lando mcp` with piped stdin and stdout.
Audit the effective catalog without starting the long-running server with
`lando mcp --list --format=json`. The wire framing is newline-delimited
JSON-RPC: write one complete JSON-RPC object followed by a newline for every
request or notification.

Serve mode rejects a TTY because an MCP client must own both protocol pipes.
It also rejects unavailable descriptors and character devices, and it rejects
command-result machine output. Use `lando mcp --list --format=json` instead
of `lando mcp --format=json`.

The two read-only tools are `app:config:get`, which reads one resolved
configuration key (`args.key` is required), and `app:config:view`, which
reads the complete resolved Landofile. Umbrella and write-capable ids:
`app:config`, `app:config:set`, `app:config:unset`, `app:config:edit`,
`app:config:validate` are not MCP tools, even through explicit allow
configuration.

Protocol input and output stay bounded: a complete inbound frame and a
partial inbound buffer are each capped at 1 MiB. At most 256 unresolved tool
calls are retained; request 257 receives a JSON-RPC `Server busy` error. The
outbound queue, queued bytes, and blocked-write duration are bounded too
(1024 messages / 8 MiB / 5 seconds).
