# Inspect a running app

`lando app:info --format=json` reports every service, its status, and its connections: the addresses you reach from the host and the addresses other services in the app use. You do not need a shell inside a service to read that state:

## The result shape

`app:info --format=json` wraps its result in the same `CommandResultEnvelope`
every non-interactive command emits: `{ "ok": true, "result": <InfoAppResult> }`.
The [`InfoAppResult` schema reference](../../reference/schemas/info-app-result.mdx)
lists every field. The result carries `app` (the app name, matching the
Landofile) and `services`, an array with one entry per service defined in the
Landofile.

Each `services[]` entry names the service and its type and provider, whether
it's primary, its current status, and its connections. It also carries safe
facts from the plan when Lando has them:

```
{ app, service, api, type, provider, primary, status, connections,
  artifact?, user?, workingDirectory?, home?, appMount?, mounts?,
  hostnames?, certs?, health?, logSources?, creds?, providerInfo? }
```

`status` is one of a fixed set of values, safe to branch on directly instead of
parsing prose: `unknown | stopped | starting | running | healthy | unhealthy |
ready | completed | restarting | paused | error`.

`artifact` identifies a selected image as `{ kind: "ref", ref, digest? }`, or
a build as `{ kind: "build", contentHash? }`. It never includes build arguments,
source files, or inline build instructions. `user` and `workingDirectory` are
the planned container user and directory. `home`, `appMount`, and `mounts`
describe planned storage and any mounts the provider observed.

`hostnames` lists the service's planned, deduplicated network aliases. Those
aliases are names other containers can use when the networks are running, not
route URLs or host-file entries.
`certs.state` is `none`, `generated`, or `custom` when the plan records a
certificate source. `health.check`, when present, gives the ongoing probe's
kind and timings without its command or URL. `health.state` is the provider's
reported health status or `unknown` if it hasn't reported one; it is separate
from the service's `status`. These plan fields can be absent on older plans,
and `providerInfo` is reserved for providers that explicitly supply JSON-safe
details. Lando currently omits it.

`connections` is a required array. It includes configured addresses and any host
port bindings the provider observed that don't match a planned publication.
An empty array means Lando has no connection addresses to report, not a missing
field.
Every connection carries:

| Field | Meaning |
| --- | --- |
| `scope` | `app` for an address other services in this app dial, `host` for an address you reach from this machine |
| `source` | `listener` (the service's own port on the app network), `publication` (a port published on the host), or `route` (a router hostname) |
| `protocol` | `http`, `https`, `tcp`, or `udp`. Routes use the router's external scheme; other connections use the declared listener protocol, or `tcp`/`udp` for an unmatched observed host port. Lando never guesses HTTP |
| `host` | Hostname or unbracketed IP address: the service key for `app` scope, `localhost`, a bind address, or a route hostname for `host` scope |
| `endpoint` | The logical listener this connection comes from: `port`, `transport` (`tcp` or `udp`), its sorted `names`, and whether it is marked `primary` |
| `binding` | `assigned` when the address has a port, `pending` when it doesn't have one yet |
| `state` | `active`, `inactive`, or `unknown`. `active` means the service is running and, for a `host` address, Lando saw the port or route actually published. It never means the service is healthy |

An `assigned` connection also carries `port`, a copyable `url` without any
password, and `alternateUrls` for the same address under another scheme. A
`pending` connection has none of those. It's a configured host port that the
provider hasn't assigned, or a route that no router is serving yet. Lando doesn't
invent a port for it, and its `state` is only ever `inactive` or `unknown`. A
`route` connection adds `pathPrefix`, which its `url` keeps.

The demo's Node service listens on `3000`, and the Node type marks that listener
primary, so its `endpoint` is `{ port: 3000, transport: "tcp", names: ["app"],
primary: true }`. Its `app`-scope listener URL is `http://app:3000`, and its
default route is a `host`-scope `route` connection for
`app.in-container-context-demo.lndo.site`. Unix sockets are not listed, and
cross-app `<service>.<app>.internal` aliases are not connections.

Only `host` connections that are `assigned`, `active`, and `http` or `https` on
a non-wildcard hostname are hyperlinked by `lando info`, opened by `lando open`,
or probed by the post-start scanner. `app`-scope addresses are never treated as
clickable from the host.

A stopped service keeps its configured connections with `state: inactive`, so
the addresses stay readable and copyable. `unknown` means Lando could not
observe the binding; it is not a failure and not a promise. No connection `state`
proves the service is ready; use its healthcheck or a protocol probe for that.

When the app has been started, `app:info` describes the plan Lando last applied,
not an edited Landofile you have not started yet. Run `lando start` to apply
edits before reading them back.

`creds` appears only for services that publish database credentials, with
password fields redacted. Build connection strings from the resolved credential
expressions in your Landofile instead of copying them from `app:info`.

The optional `agentEnv` block matches `lando info --deep`: `enabled` reports
the app's forwarding policy, and `forwarded` lists host-present names that
pass the allowlist and value guards, never their values. Service and explicit
command env still take precedence. See [the built-in markers](../tooling/lando-shell.mdx).

CLI invocations load current app configuration. A retained library App handle
instead keeps the plan and Landofile it captured for exec, deep info, and tooling.
This includes the default policy when `agentEnv` is omitted: changing the app to
`agentEnv: false` later does not update the old handle.

To capture the change, resolve the app again with `runtime.app(originalSelector)`
or `resolveApp(originalSelector)`. If the selector is an object, supply the updated
object. Provider status remains live; shallow info does not load a Landofile when
you supply a target.

Automatic forwarding also checks `ConfigService.get("agentEnv")` and the current
`LANDO_AGENT_ENV=0` setting at invocation time. Either can veto forwarding.
The global configuration itself is a snapshot: a CLI command reads it at startup,
while an embedded runtime keeps its initial configuration. A veto does not remove
explicit service or command environment variables, or revoke a running command.

## How context reaches a container

A host script or agent can ask the CLI for structured app state from outside
any container with `lando app:info --format=json`. No shell inside a service
required.

Only the provider-exec surfaces forward host agent-context markers into a
service: `lando exec <service> -- <command>` or `lando shell --service <service>`.
A plain `lando start`'d container gets no such injection. See
[the lando-shell guide](../tooling/lando-shell.mdx) for the exact allowlist
and precedence rules for the forwarded markers; this guide doesn't repeat
them. For the general envelope contract every machine-output command shares
(apiVersion, redaction, and the failure shape), see the
[scripting-with-json guide](../scripting-with-json.mdx); this guide only
covers the `app:info`-specific result fields.

## What changed since Lando 3

In Lando 3, a service process read its own app context from a baked-in
`$LANDO_INFO` environment variable, which could drift from the actual running
state. Lando 4 has no equivalent baked-in env var. `app:info --format=json`
is the supported, authoritative source of app state instead. The upstream
issue tracking `$LANDO_INFO` drift, [lando/lando#2565](https://github.com/lando/lando/issues/2565),
is why v4 makes the CLI itself authoritative for app state rather than a
value frozen into the container at boot.
