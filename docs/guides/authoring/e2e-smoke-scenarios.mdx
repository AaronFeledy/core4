# E2E smoke scenarios

Mark a scenario `layer="e2e"` when the promise it makes only holds against a
real provider. The harness then spawns the compiled `lando` binary instead of
the in-process test provider, so `start` boots containers, `info` reports
what is actually running, and `destroy` tears real resources down.

Use a fixture-owned app and include cleanup: these scenarios create real
provider resources. The `real-provider-loop` scenario in the
[app lifecycle tutorial](/guides/tutorial/app-lifecycle/) starts a two-service
app, checks `lando info` for `running` rows, stops it, and destroys it through
the binary.

## Write one

Set the layer and tag on the scenario, not the guide, unless every scenario
on the page needs a real provider:

```mdx
<Scenario id="real-provider-loop" layer="e2e" timeout={300000} tags={["@smoke"]} render>
  <Step name="start">
    <UseFixture name="app-lifecycle-demo" />
    <Verify command="lando start" expect={{ stdout: { regex: "ready: app-lifecycle-demo" }, stderr: { regex: "complete" } }} />
  </Step>
  <Step name="cleanup">
    <Cleanup />
    <Run command="lando destroy -y --volumes" />
  </Step>
</Scenario>
```

If a live scenario needs more time to pull images or start containers, set
`timeout` on that scenario, in milliseconds. Other scenarios keep the guide's
timeout, which defaults to `60000`.

Rules the generator and linter enforce:

- Put `<Cleanup />` and `lando destroy -y --volumes` (or `--purge`) in the
  same step. The harness runs that step once after the other steps, even if the
  scenario fails or is interrupted. Keep teardown safe to run before the app
  exists. The provider is shared, so a leaked app can break the next run.
- `<Run runtime="library">` cannot appear in an e2e scenario. The binary is
  the only entry point.
- `<Verify event>` has nothing to match. The binary does not stream events
  back to the harness. Assert on stdout, stderr, exit code, or files instead.

## Prove a URL answers

`lando start` checks every routed URL through the proxy after the app is ready.
Read that result from JSON in a hidden step, not from the progress lines it
prints on stderr, which are written for people and change without notice:

```mdx
<Hidden reason="The routed URL answers through the proxy">
  <Step name="route">
    <Verify command="lando start --format=json" expect={{ stdout: { regex: "\"service\":\\s*\"web\",\\s*\"url\":\\s*\"[^\"]+\",\\s*\"verdict\":\\s*\"ready\"" } }} />
  </Step>
</Hidden>
```

A second `lando start` changes nothing on a running app, so the step only
repeats the check.

## Request a page through the router

Use `<Fetch>` when you need to check a specific page, header, or redirect,
rather than the readiness verdict from `lando start`. Run it in an e2e scenario
after `lando start`. The `{{route:web}}` token in the example uses the `web`
service's assigned router URL, including any fallback port. HTTPS requests
verify the router certificate against the CA that `lando setup` installed.

```mdx
<Step name="request-homepage">
  <Fetch url="{{route:web}}/" expect={{ status: 200, headers: { "Content-Type": { regex: "^text/html" } }, body: { regex: "Hello from the router" } }} />
</Step>
```

<Guide>
  <Scenario id="request-router-page" layer="e2e" render>
    <Hidden reason="Start the fixture site for the request example">
      <Step name="start-static-site">
        <UseFixture name="router-page" />
        <Run command="lando start --format=json" />
      </Step>
    </Hidden>
    <Step name="request-homepage">
      <Fetch url="{{route:web}}/" expect={{ status: 200, headers: { "Content-Type": { regex: "^text/html" } }, body: { regex: "Hello from the router" } }} />
    </Step>
    <Hidden reason="Clean up the fixture site after the request example">
      <Step name="destroy-site">
        <Cleanup />
        <Run command="lando destroy -y --volumes --format=json" />
      </Step>
    </Hidden>
  </Scenario>
  <Scenario id="prepare-router-page" render={false} reason="Check the request fixture plans a routed static site without a live provider">
    <Step name="plan-static-site">
      <UseFixture name="router-page" />
      <Verify command="lando app:config:lint --format=json" expect={{ stdout: { regex: "\"valid\":\\s*true" } }} />
    </Step>
  </Scenario>
</Guide>

## Pin a known limitation

When a page tells readers about a limitation or a workaround that an open issue
tracks, add a hidden step that asserts the limitation still holds and name the
issue in its reason. The fix then fails the scenario, and the page gets updated
instead of teaching a workaround nobody needs:

```mdx
<Hidden reason="Tripwire for #1234: the web worker still cannot write uploads">
  <Step name="tripwire">
    <Verify command="lando exec appserver --user www-data -- test -w /app/uploads" expectExit={1} />
  </Step>
</Hidden>
```

## Where it runs

An e2e scenario is `test.skip` unless three things are set: `LANDO_GUIDE_E2E=1`,
`LANDO_SCENARIO_E2E_BINARY` pointing at a compiled binary, and a live provider
socket (either the managed one from `lando setup` or `LANDO_TEST_PODMAN_SOCKET`).

Tag the scenario `@smoke` when it should gate every pull request. The Linux x64
guide-scenario job runs only `@smoke` e2e scenarios. Untagged e2e scenarios
run in the nightly workflow, so a scenario that takes minutes or pulls large
images belongs there.

Run one locally against a binary you built:

```sh
bun run codegen
LANDO_GUIDE_E2E=1 \
LANDO_SCENARIO_E2E_BINARY="$PWD/dist/lando" \
bun run scripts/test-reporters/run-guide-scenarios.ts test/scenarios/generated/guides/app-lifecycle/** --test-name-pattern="\[e2e\]"
```

## What stays out of guides

Guides prove promises a reader can see. Tests that drive a provider through
its library API, inspect containers over the Podman socket, race two
processes, or send signals mid-run verify the model behind the promise. Keep
those as `*.integration.test.ts` under the package that owns the code, for
example `core/test/live/` or `plugins/service-lando/test/`. Add each new
integration suite to a selection in `scripts/test-selections.ts` that a CI job
runs, or `bun run check:test-ownership` fails.
