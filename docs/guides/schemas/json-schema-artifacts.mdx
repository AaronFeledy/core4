# JSON Schema artifacts

Use the public draft 2020-12 artifacts for SDK and command-result validation,
and the draft-07 editor artifacts for authored Landofiles and global config.
The authoring and resolved-runtime views differ, especially around expressions.

Contributors can regenerate the artifact set from the repository root. This
includes schemas, metadata indexes, bundled manifests, editor schemas, and
reference docs:

```sh
bun run scripts/build-schema-snapshot.ts
```

## Public artifacts: draft 2020-12

Every document under `dist/schemas/**` and `dist/command-schemas/**` is a
draft 2020-12 schema (`https://json-schema.org/draft/2020-12/schema`) with
shared definitions under `$defs`. The indexes (`dist/schemas/index.json` and
`dist/command-schemas/index.json`) cover every public SDK registry entry and
every exact canonical command id, while each schema file remains standalone.
The command index also carries `cli:help` (`dist/command-schemas/cli-help.json`),
the result of `lando help --format=json`, so a client can validate the help
catalog and its plugin rows the same way it validates any command result.

Reach for these when you generate types, build a validator, or diff the
contract between releases.

## Editor artifacts: draft-07

Two extra documents exist for editors, because the YAML language server and
most IDE schema stores still speak draft-07:

| File | Validates |
| --- | --- |
| `landofile.schema.json` | `.lando.yml` and its layer files |
| `global-config.schema.json` | the global Lando config file |

Schema snapshot codegen writes these files to `docs/public/schemas/` as
gitignored, derived outputs. `bun run docs:build` regenerates them before
Astro copies them to `/core4/schemas/` on the docs site.

Both are closed objects (an unknown key is an error, matching
`lando app:config:lint`) and carry generated descriptions, so hover text in
your editor reads the same as the schema reference.

`landofile.schema.json` describes the file as authored, not as resolved. At a
boolean, number, list, or object field it accepts the literal type or one
whole-value `{{ ... }}` string, so `primary: "{{ recipe.primary }}"` and
`httpPort: "{{ number(env.PORT) }}"` are valid; `primary: maybe` is not.
That whole value is one interpolation and nothing else. Surrounding text,
including spaces and a trailing newline, is rejected, so
`"  {{ recipe.flag }}  "` fails at a typed field. `{{-` / `-}}` trim markers
inside the braces stay allowed. Text fields take plain or interpolated text.
The expression arm is the pattern `^\{\{-?(?:(?!\{\{|\}\})[\s\S])+?-?\}\}(?![\s\S])`. It
doesn't parse the body, so it can't reject a plan-time scope like
`{{ app.name }}` at a boolean field or a wrong helper type. A valid body that
contains a quoted `}}` or adjacent object-closing braces, for example
`{{ length({a:{b:1}}) }}`, is accepted by the loader and the
[Standard Schema view](./standard-schema.mdx), but this pattern can't match
it. Lint and Standard Schema catch the scope and helper gaps.

`dist/schemas/landofile-shape.json` is the other side: the strict runtime
shape with every expression already resolved. Validate authored YAML against
`landofile.schema.json`; validate `lando app:config --format=json` output
against `landofile-shape.json`.

The docs build publishes the Landofile editor schema at
`https://aaronfeledy.github.io/core4/schemas/landofile.schema.json`. The
SDK exports that URL as `LANDOFILE_EDITOR_SCHEMA_URL` from
`@lando/sdk/schema`, and a test holds the two in agreement, so tooling
imports the constant instead of hard-coding the string:

```ts
import { LANDOFILE_EDITOR_SCHEMA_URL } from "@lando/sdk/schema";
```

New Landofiles written by `lando init` and `lando app:config:translate`
start with a `# yaml-language-server: $schema=<that url>` modeline. Existing
files are never rewritten to add it. To wire the schema into your editor,
see [Validate a Landofile in your editor](../landofile/editor-validation.mdx).

## One contract, two views

The published documents, the editor documents, and the
[Standard Schema views](./standard-schema.mdx) are all projections of the
same Effect Schema contracts that `lando` itself decodes with. The authoring
view (`landofile.schema.json`, `LandofileStandardSchema`,
`LandofileStandardJSONSchema`) checks what you typed and allows expressions
where they're legal. The runtime view (`landofile-shape.json`,
`LandofileShape`) checks resolved values. A parity test loads every guide and
recipe fixture plus curated valid and invalid inputs through each pair and
requires the same accept-or-reject answer, with the pattern-only gaps above
listed by name. This checks agreement within the tested cases without hiding
the editor pattern's limits; use lint or Standard Schema when you need expression
scope and helper-type validation.
