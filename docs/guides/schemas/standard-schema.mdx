# Validate a Landofile with Standard Schema

Use `LandofileStandardSchema` in a host program to validate a parsed `.lando.yml`
object before resolving its expressions. In the example, `input` is that parsed
object, not a YAML string. Read `result.issues` for validation problems or
`result.value` for the accepted authoring shape.

```ts
import { LandofileStandardSchema } from "@lando/sdk/schema/standard";

const result = await LandofileStandardSchema["~standard"].validate(input);
if (result.issues) {
  for (const issue of result.issues) console.error(issue.path, issue.message);
}
```

[Standard Schema](https://standardschema.dev) is the interface form
libraries, routers, and AI SDKs accept instead of asking you which validator
you use. `@lando/sdk/schema/standard` exports Lando's input contracts in that
form, so any tool that takes a Standard Schema can check a Landofile with
Lando's own authoring rules, not a copy of them.

## What the subpath exports

| Export | Validates |
| --- | --- |
| `LandofileStandardSchema` | a parsed `.lando.yml` object, as you wrote it |
| `GlobalConfigStandardSchema` | the global Lando config object |
| `PluginManifestStandardSchema` | a plugin manifest |
| `RecipeManifestStandardSchema` | a recipe manifest |

Each has a `*StandardJSONSchema` sibling (`LandofileStandardJSONSchema` and
so on) implementing Standard JSON Schema V1, for tools that want a JSON
Schema document rather than a validator. Call its `~standard.jsonSchema.input()`
to get the document; the conversion is deferred until you ask.

The subpath is tree-shakeable and imports nothing from the CLI. Unknown keys
are errors and every problem is reported in one pass, the same settings
`lando app:config:lint` runs with.

## Read the result

`validate` resolves to either `{ value }` or `{ issues }`. Each issue has a
`path` array and a `message`, and the paths match the `issues` Lando's own
`LandofileValidationError` reports, so a tool can show the user the same
line whichever side caught it.

## What the Landofile view checks

`LandofileStandardSchema` validates the file as authored, before any
`{{ ... }}` resolves. It does not have your env or recipe options, so it
can't tell you what `{{ env.PORT }}` is worth. It can tell you whether the
expression belongs there:

| Site | Accepts |
| --- | --- |
| text field (`name`, `type`, `environment` values) | plain text, or text with any `{{ ... }}` mixed in |
| boolean, number, list, or object field | the literal type, or one `{{ ... }}` with no text around it |
| any field | nothing else: `primary: maybe` and `httpPort: abc` fail |

At a typed field the expression gets parsed. Whole means one interpolation
and no surrounding text, so `"  {{ recipe.flag }}  "` fails there.
`{{-` / `-}}` inside the braces is still whole. Plan-time scopes (`app`,
`proxy`, `services`) fail there with `Planner scopes require a string site.`
because they only ever fill text. Helpers with a known return type must
match the site, so `name: "{{ number(env.PORT) }}"` fails too. Unknown keys
and reserved map keys fail the same as before.

A success `value` is the authored shape: a plain field comes back as the
literal, and an expression field comes back as a parsed
`AuthoringExpression` (`source`, `expectedType`, `scopes`, parsed
`template`), not the value it will resolve to. Resolve values with
`lando app:config --format=json`; see [Landofile
expressions](../landofile/expressions.mdx#whole-value-expressions-keep-their-type).

`LandofileStandardJSONSchema` describes that same input. Its draft-07
document is the editor schema byte for byte. At a typed field it accepts the
literal or one whole `{{ ... }}`, with `{{-` / `-}}` trim markers allowed
inside the braces. Surrounding text is not whole. JSON Schema can't parse the
expression, so that document doesn't check scopes or helper types. A valid
body that contains a quoted `}}` or adjacent object-closing braces, for
example `{{ length({a:{b:1}}) }}`, is accepted by the loader and by
`LandofileStandardSchema`, but the editor pattern can't match it.

The other three exports (`GlobalConfigStandardSchema`,
`PluginManifestStandardSchema`, `RecipeManifestStandardSchema`) validate
literal values; those files don't carry expressions.

## One contract, two views

The Standard Schema views, the [published JSON Schema
artifacts](./json-schema-artifacts.mdx), and the editor schema all project the
same Effect Schema contracts, from two angles. The authoring view
(`LandofileStandardSchema`, `LandofileStandardJSONSchema`, and the editor
`landofile.schema.json`) accepts expressions where they're legal. The runtime
view (`LandofileShape` and the published `landofile-shape.json`) is strict:
it checks resolved values, which is what `lando start` sees after the
loader has run. A parity test runs every guide and recipe fixture plus curated
valid and invalid inputs through each pair and requires the same answer,
with the JSON Schema gaps above listed by name.
