# Disable shared global services

Use `lando global:disable <service>` to disable a shared service and stop its
containers while retaining named volumes. This manages the global app, not the
Lando CLI. If you only need a temporary stop, use `lando global:stop --service`
instead. Anonymous volumes follow their container, as described in [Keep data across stop, restart, and destroy](../tutorial/app-lifecycle.mdx#keep-data-across-stop-restart-and-destroy).

## Disable a shared service

On the host, preview the effect of disabling Mailpit:

```sh
lando global:disable mailpit --dry-run --format=json
```

The preview changes neither files nor runtime resources. Read `result.impact` for
the selected contributions and plugins, dependency blockers, affected route
hostnames, and the `volumes: retained` policy. `desired` reports the requested
choice; `policyChanges` says whether it would change saved preferences.

Check `validationErrors` and `uncertainties` as well as `dependencyBlockers`. A
successful preview can report problems that would prevent or limit the real
operation. Missing ownership evidence is uncertainty, not permission to delete a
resource. The result reports `dryRun: true` and `policySaved: false`; it doesn't
reserve the state it inspected. The real command checks current state again.

When the proposed change is what you want, disable Mailpit and check the result:

```sh
lando global:disable mailpit
lando global:list --format=json
lando global:status --format=json
```

The `mailpit` entry in the list reports `enabled: false` and `state: disabled`.
Disable saves your choice, stops and removes its owned containers, withdraws its
routes, and regenerates configuration. Other contributions keep their configuration
and active routes. Named volumes remain available for reuse. Check status for any
pending work before treating cleanup as complete.

The argument accepts a contribution id or a plugin package name from
`global:list`. You can pass several ids in one command. A package name disables
that plugin's current and future contributions and clears its individual choices.
For example, `@lando/proxy-traefik` selects the router and its diagnostics service;
disabling that package also makes routed app URLs unavailable. Unknown or ambiguous
names fail before policy changes.

If an enabled service requires one you selected, disable both in the same command,
or select the owning package when it contains both. Lando identifies known
dependents and rejects an incomplete selection before changing policy. It never
silently disables another contribution. Remove an authored dependency before
disabling the contributed service it requires.

The choice persists in `<userConfRoot>/global.config.yml`. Neither automatic
startup nor `lando global:reconcile` re-enables it.
Overrides for that service in any global Landofile layer stay on disk but are
ignored while it is disabled. To re-enable it with those overrides and its retained
named volumes, run:

```sh
lando global:enable mailpit
lando global:list --format=json
```

Check both `enabled: true` and `state: enabled` in the list. A `blocked` or
`unverified` entry needs its reported cause resolved before it can start. Enable
doesn't start containers; start an app that needs
Mailpit, or run `lando global:start --service mailpit` and inspect
`lando global:status --service mailpit --format=json`.

## Finish pending cleanup

An unavailable provider or a broken unrelated contribution cannot prevent Lando
from saving a valid disable choice. Cleanup still needs matching ownership
evidence. After policy is saved, incomplete reconciliation fails with `GlobalPolicyReconciliationError` and reports
`policySaved`, `revision`, `servicesRemoved`, and `pending`. Pending entries identify
work on evidence, containers, routes, or configuration generation. Completed work
stays complete; failure doesn't undo your disabled policy.

Read the desired policy, observed resources, and pending work, then retry after
fixing the reported cause:

```sh
lando global:status --format=json
lando global:reconcile
lando global:status --format=json
```

Reconcile preserves policy and starts no containers. It can finish generating
configuration even when container cleanup is still blocked, or remove a selected
container while another contribution prevents generation. Successful generation
alone doesn't prove cleanup finished. If containers or routes lack matching
applied ownership evidence, Lando leaves their cleanup pending rather than deleting
unverified resources. Status remains available even when the desired Landofile
cannot be validated.

Reconciliation can retry a removed plugin's pending service only while its saved
ownership proof still matches the applied service and that id hasn't become an
authored service. Reused ids or changed ownership remain pending. If you intend to
stop the entire global app instead, `lando global:stop` is the explicit operation;
it also withdraws the whole global route definition while retaining named volumes.
Use that only when stopping the other shared services is acceptable. A route-only
recovery doesn't prove unknown containers were removed.

## Stop one global service

```sh
lando global:stop --service mailpit
lando global:status --service mailpit --format=json
```

That stops Mailpit and removes its container. Status reports it as `stopped` in `result.services[].status`. `--service` (or `-s`) is repeatable: `lando global:stop -s mailpit -s ssh-agent` stops both.

Dependencies aren't stopped for you. Lando leaves named volumes, the shared network, and every service you didn't name alone, so Traefik keeps serving its routes. An unknown name fails before anything stops. A selected stop needs the global app's applied state; if containers outlived it, the command fails and changes nothing.

A stop is temporary. Starting an app that needs a global service can bring it back. To start it yourself:

```sh
lando global:start --service mailpit
```

Mailpit's route needs Traefik, so that also starts Traefik when it's stopped and lists it in `servicesStarted`. Routes follow what runs: services you didn't name keep theirs while they're up, and a stopped service's hostname gets the proxy's 404 page.

## Disable every contributed service

Use `--all` to disable every known plugin's current and future contributions,
including retained policy for plugins that are no longer loaded. This keeps named
volumes and your authored Landofile files. Authored services that aren't current
plugin contributions stay in the configuration. Enable and disable require either
selectors or `--all`; a bare command doesn't change policy, and selectors cannot
be combined with `--all`. Neither command accepts `--yes`.

```sh
lando global:disable --all
lando global:list --format=json
lando global:status --format=json
```

Check that the listed contributions report `enabled: false`, then inspect any
pending cleanup. Re-enable each service or plugin you need with
`lando global:enable <id-or-package>`. Use `lando global:enable --all` only when you
intend to enable every known plugin and reset its individual choices.

## Destroy provider resources

`lando global:destroy` needs `--yes`. Without it the command fails with `GlobalDestroyConfirmationError` and touches nothing. `--yes` is consent.

```sh
lando global:destroy --yes
```

Destroy acts on the provider where the global app actually runs. If multiple providers hold applied global plans, target the unwanted copy explicitly:

```sh
lando global:destroy --provider=lando --yes
```

This reads and cleans up only the selected provider. Named volumes stay unless you pass `--purge`.

To move the global app to another provider, do not destroy it by hand. See [Switch providers](../setup/provider-selection.mdx#switch-providers).

To remove service- and app-scoped named volumes as well as provider resources,
add `--purge`. This deletes their stored data. Volumes declared with
`scope: global` survive this operation:

```sh
lando global:destroy --yes --purge
```

Stop and destroy use the global app's applied state, so an invalid edit to a global Landofile doesn't block cleanup. Fix the config before starting the app again.

If nothing needs removing, both commands report `unchanged`. With `--format=json`, check `result.outcome` for `stopped`, `destroyed`, or `unchanged`; `materialized` only says whether the generated Landofile exists. An unchanged destroy reports `volumesRemoved: false`, even with `--purge`.

## Related commands

```sh
lando global:start
lando global:stop
lando global:status
lando global:config
```

With no `--service`, `global:stop` tears down the whole global app's running provider resources and keeps named volumes. `global:restart` and `global:rebuild` always act on the whole global app. `lando poweroff` stops the global app after your apps unless you pass `--keep-global`. `global:config` prints the effective global Landofile, merged from the generated file and your own layers (YAML or TypeScript, includes resolved), plus the paths behind it.

Each `meta:global:*` command publishes a `global:*` alias.
