# Read the global-app doctor check

Run `lando doctor` on the host to check whether the global app is installed and
read any recorded router watcher failure. You do not need a project app running.

```sh
lando doctor
```

Doctor includes a `global-app` section without bootstrapping a project app. If the provider section degrades, this disk-backed check can still run. In `lando doctor --format=json`, its checks are the `result.checks` entries whose `section` is `global-app`.

This check reads the local generated files under the global root; it doesn't
inspect the provider's containers. Use `lando global:status --format=json` for
runtime observations. See [Where the global app runs](../setup/provider-selection.mdx#where-the-global-app-runs)
for provider placement.

## When it is not installed

The check warns and sets `installed` to `false`. Starting an app that needs Traefik, Mailpit, or the SSH sidecar provisions the global app. To materialize it now:

```sh
lando global:reconcile
lando global:status --format=json
```

## When it is installed

The check passes and reports the generated dist Landofile (`<userDataRoot>/global/.lando.dist.yml`), the overlay (`<userDataRoot>/global/.lando.yml`), the dist file mtime as `lastInstallTimestamp`, materialized service ids, and plugin names that declare `globalServices:`.

If the dist file exists but cannot be read, the check fails and tells you to fix permissions or rerun `lando global:reconcile`. Reconcile preserves saved policy and starts no containers. Use `lando global:status --format=json` to inspect desired policy, observed services, and pending cleanup separately; generated configuration alone isn't proof that a disabled service has stopped.

## Read the router file-watcher check

The router reads its route configuration from a directory Lando mounts into the Traefik container and watches with inotify. If that watch never starts, Traefik keeps running but loads no routes, so every app URL fails without saying why. Lando reads the router's own log once after starting it and records any watcher failure it finds. The `router-file-watcher` check reports that record even when doctor selected a different app provider, because Traefik runs on the host provider, not on whatever the app pinned.

It is a record, not a live probe. The check shows what the last router startup observed, and it stays reported until the next `lando global:restart` or `lando global:rebuild` observes a clean start and refreshes it. If the check still fails after you fixed the host, restart the global router and run doctor again.

Restart and rebuild revalidate a router they actually applied. If the router is
disabled, missing, or cannot be observed running, Lando doesn't probe it or create
ready evidence. Its previous watcher-failure record remains historical evidence;
disabling a service doesn't prove that failure was repaired. Check
`lando global:list --format=json` for policy and
`lando global:status --format=json` for observed state before deciding to restart it.

The watcher runs on the provider runtime host, which is not always the operating system you typed the command on:

| Where you run Lando | Where the watcher runs |
| --- | --- |
| Linux | the local host |
| WSL | the WSL distribution |
| macOS or Windows with the default `lando` provider | the Lando-managed Podman machine |
| Docker or system Podman as the host provider | that runtime's host or VM |

The check sorts failures into `inotify-limit`, `permission`, `disk`, and `other`. The error wording can be misleading: an inotify watch that fails with "no space left on device" usually means the watch budget ran out, not that the disk is full. Doctor reports that as `inotify-limit`. It is a kernel resource, though, and the same error can come from a related limit, so treat it as "watches or a kernel resource", not a verdict on one number. To read the current watch limit on a Linux runtime host:

```sh
cat /proc/sys/fs/inotify/max_user_watches
```

The first remediation is always something you can do without privileges, such as closing other watch-heavy tools and restarting the app. Lando never runs `sysctl` and never restarts system services for you. Raising a kernel limit is listed last and stays the administrator's call.

A watcher that starts but never delivers events, which some virtual filesystems cause, is not detected by this check.

Read the `filesystem-watch` check in the same report for a live CLI-host result. Linux and WSL test one watch allocation. Windows also confirms one file event on the host's temporary filesystem. Neither result looks inside the provider VM or refreshes this router record. See [Check filesystem watches on this host](../subsystems/doctor-walkthrough.mdx#check-filesystem-watches-on-this-host).

## Read the legacy route files check

Each route file in the router's configuration directory is named after a hash of its owner: the app folder for user and global apps, the scratch id for scratch apps. That's what lets a renamed app replace its routes instead of leaving the old hostnames live. Earlier development builds named files after the app instead. The `legacy-route-files` check separates files Lando recognizes as its generated output from files it cannot identify, with `generatedCount` and `unrecognizedCount` and bounded lists of full paths as evidence.

Doctor only reads. Lando removes recognized generated files automatically the next time a routed app starts. To run that cleanup now, run `lando setup` on the host, then check the report:

```sh
lando setup
lando doctor --format=json
```

The migration checks both the encoded app name and the exact generated configuration shape. It preserves every certificate and key file: the route alone cannot prove who owns the bytes currently at those paths. On Windows, Lando reloads the router once for the batch and retains evidence to retry if the reload fails. Start each app whose routes you still need to republish them.

Unrecognized files stay in place and remain a warning. Review those files and manually delete only the ones you no longer need. On Windows, then run `lando global:restart` so Traefik reloads its route configuration. Republish the routes you still need: run `lando start` in a user app, `lando global:start` for global services, or start a scratch app again with its scratch command. An owner-named file without valid route metadata is also unrecognized; `lando start` refuses to overwrite it. The evidence lists can omit paths when large; the counts include every finding.

## Verify

```sh
lando doctor
lando global:status
```
