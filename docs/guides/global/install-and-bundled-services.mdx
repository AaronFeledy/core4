# Install the global app

The global app provides shared services such as Traefik, Mailpit, and the SSH
agent sidecar. Lando provisions it when an app needs those services; use
`lando global:install` if you want to create its configuration ahead of time.

It lives under `<userDataRoot>/global`, not in your current directory. Manage it
with `lando global:*` (aliases of `lando meta:global:*`). The name `global` is
reserved: a project Landofile with `name: global` fails with `AppIdReservedError`
before Lando builds a plan.

## Install the global configuration

Starting an app that needs Traefik, Mailpit, or the SSH sidecar provisions the global app. To create its configuration ahead of time:

```sh
lando global:install
lando global:list --format=json
```

`--yes` is accepted for consistency with `lando setup --yes`. Global install does not prompt.

Install creates configuration without starting containers. The list reports each contribution's `id`, source `plugin`, and saved `enabled` choice. An enabled entry is eligible to start; it doesn't mean a container is running.

Bundled plugins contribute `traefik`, its `traefik-diagnostics` service, `mailpit`, and `ssh-agent` through `globalServices:`. Lando starts the shared services an app needs, including after `lando poweroff` or a reboot. An app with no routes never starts the router, so a database-only or worker app comes up on a host where the router cannot.

## Enable a shared service

Use a contribution id from the list to enable one service, or its plugin package name to enable all of that plugin's global contributions:

```sh
lando global:install mailpit
lando global:list --format=json
```

Check that the `mailpit` entry reports `enabled: true`. For example, `lando global:install @lando/proxy-traefik` enables both the router and its diagnostics service. Unknown names fail without changing enablement; a name that matches a plugin and a different contribution is rejected as ambiguous. Use an unambiguous package name or contribution id from the list.

Lando saves these choices in `<userConfRoot>/global.config.yml`. The first install records each contribution's default. Later installs and plugin updates preserve that saved choice; a newly discovered contribution gets its own default. Running `lando global:install` without an argument reconciles the saved choices and does not re-enable a disabled service. Automatic startup follows the same choices. Use [Disable a shared service](./uninstall-and-purge.mdx#disable-a-shared-service) to turn one off persistently.

Re-enabling restores the service's generated configuration and any overrides you kept in the global Landofile layers. It doesn't start the service. An app that needs it can start it automatically, or you can run:

```sh
lando global:start --service mailpit
lando global:status --service mailpit --format=json
```

Check that the service reports `running` in `result.services[].status` before using it. If install reports an error after saving enablement, fix the reported cause and repeat the same install command to finish generating the configuration.

## Where the global app runs

Traefik, Mailpit, and the ssh-agent sidecar run on the host provider that `lando setup` selected. A Landofile `provider:` never moves them, and routed apps must share that provider. Only `lando setup --provider=<new>` switches an existing global app. See [Where the global app runs](../setup/provider-selection.mdx#where-the-global-app-runs), [Routing needs one provider](../setup/provider-selection.mdx#routing-needs-one-provider), and [Switch providers](../setup/provider-selection.mdx#switch-providers).

## Override a bundled service

After running `lando global:install`, use `lando global:config set` to change a
bundled service. Plugin defaults are in the generated
`<userDataRoot>/global/.lando.dist.yml`; your overrides go in
`<userDataRoot>/global/.lando.yml` and take precedence. For example:

```sh
lando global:config set services.mailpit.environment.MP_MAX_MESSAGES 1000
lando global:config --format=json
lando global:start
```

`lando global:config --format=json` prints the effective merged Landofile under `result.landofile`; before install it reports `materialized: false` with an empty Landofile. Check your new value there before you run `lando global:start` to apply it. Don't edit `.lando.dist.yml`, because Lando regenerates it. The global root takes the same layers an app root does, in YAML or TypeScript form, with `includes:` resolved per layer; a canonical `.lando.ts` is read by `global:config` but not written by `set`, `unset`, or `edit`. See [Read and write global config](../config/global-config.mdx#read-the-effective-global-config) for the full layer order.

## When one global service fails

`lando global:start`, `lando global:restart`, and `lando global:rebuild` start global services that do not depend on each other separately, then wait for each group's readiness. If one fails its healthcheck or exits without an applicable restart policy, the others still start. The command exits non-zero, naming failed and running services.

A failed or interrupted group keeps the services it established, and successful
groups stay running. If any group fails, Lando leaves the previously published
global routes unchanged rather than publishing a partial set. A later start that
succeeds for every selected group publishes the current routes. A failed user-app
start never undoes shared global services.

Exhausted readiness checks fail even supervised services. Restart and rebuild
still revalidate the router after a readiness failure. Diagnose with `lando global:logs -s <service>`, or `lando doctor` for an `inspect-failed` provider observation. Fix the cause, then start that service to converge on its retained resources:

```sh
lando global:start --service ssh-agent
```

To stop one global service without touching the rest, use `lando global:stop --service <name>`. See [Stop one global service](./uninstall-and-purge.mdx#stop-one-global-service).

## Verify

```sh
lando global:status
lando doctor
```
