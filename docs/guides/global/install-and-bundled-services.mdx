# Install the global app

Do not name a project `global`. That id is reserved. A Landofile that resolves to `name: global` fails with `AppIdReservedError` before any plan is built.

The global app lives under `<userDataRoot>/global`. It is not picked up from your cwd. Use `lando global:*` (aliases of `lando meta:global:*`).

## Materialize the stack

Starting an app that needs Traefik, Mailpit, or the SSH sidecar provisions the global app. To materialize it now:

```sh
lando global:install
```

`--yes` is accepted for consistency with `lando setup --yes`. Global install does not prompt.

Bundled plugins contribute `traefik`, `mailpit`, and `ssh-agent` through `globalServices:`. Lando starts Traefik and the SSH agent sidecar when an app start needs them, including after `lando poweroff` or a reboot. You do not start them by hand. An app with no routes never starts the router, so a database-only or worker app comes up on a host where the router cannot.

## Where the global app runs

Traefik, Mailpit, and the ssh-agent sidecar run on the host provider that `lando setup` selected. A Landofile `provider:` never moves them, and routed apps must share that provider. Only `lando setup --provider=<new>` switches an existing global app. See [Where the global app runs](../setup/provider-selection.mdx#where-the-global-app-runs), [Routing needs one provider](../setup/provider-selection.mdx#routing-needs-one-provider), and [Switch providers](../setup/provider-selection.mdx#switch-providers).

## Override a bundled service

Plugin defaults land in the generated `<userDataRoot>/global/.lando.dist.yml`. Your overrides go in the canonical `<userDataRoot>/global/.lando.yml`, which merges on top of the generated file, so your value wins:

```sh
lando global:config set services.mailpit.environment.MP_MAX_MESSAGES 1000
lando global:config --format=json
lando global:start
```

Run this after `lando global:install`. `lando global:config --format=json` prints the effective merged Landofile under `result.landofile`; before install it reports `materialized: false` with an empty Landofile. Check your new value there before you run `lando global:start` to apply it. Don't edit `.lando.dist.yml`, because Lando regenerates it. See [Read and write global config](../config/global-config.mdx) for the full layer order.

## When one global service fails

`lando global:start`, `lando global:restart`, and `lando global:rebuild` start global services that do not depend on each other separately, then wait for each group's readiness. If one fails its healthcheck or exits without an applicable restart policy, the others still start. The command exits non-zero, naming failed and running services. A failed or interrupted group keeps the services it established, and the ones that succeeded stay running. If any group fails, the previously published global routes stay unchanged. Lando does not publish a partial set. A later start that succeeds for every group it selected publishes the current routes. A failed user-app start never undoes shared global services. Exhausted checks fail even supervised services. Restart and rebuild still revalidate the router after a readiness failure. Diagnose with `lando global:logs -s <service>`, or `lando doctor` for an `inspect-failed` provider observation. Fix the cause, then start that service to converge on its retained resources:

```sh
lando global:start --service ssh-agent
```

To stop one global service without touching the rest, use `lando global:stop --service <name>`. See [Stop one global service](./uninstall-and-purge.mdx#stop-one-global-service).

## Verify

```sh
lando global:status
lando doctor
```
