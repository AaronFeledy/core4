# Provider lando windows

## Windows machine lifecycle

Platform-aware Windows provider setup scenarios are gated outside the default generated guide suite.

Run setup on a Windows host.

```sh
lando setup --yes
```

Confirm bindMountPerformance is slow.

```sh
lando doctor
```

## Windows managed machine trust

Managed-machine trust decisions and Windows Hyper-V remediation are exercised by plugins/provider-lando unit tests; the rendered path requires a Windows Podman machine.

Lando-owned machine creation imports the host native CA trust store.

Existing machines get native CA trust sync only when setup state proves Lando created them.

A running Lando-owned machine restarts after trust sync so Podman imports the host CA store at startup.

User-owned machines are left untouched by setup trust remediation (`createdByLando=false`).

Manual Administrator-terminal remediation; Lando never auto-elevates or runs Hyper-V prep for you.

## Windows runtime bundle

Runtime-bundle download paths are exercised by plugins/provider-lando unit tests and the compiled Windows provider integration job.

Pinned manifest carries the URL and SHA-256 for every supported host (`plugins/provider-lando/runtime-bundle-versions.json`).

Idempotent cache path under the per-user state directory.

The managed Windows bundle includes both Podman machine API forwarding helpers.

Tagged failure raised on a SHA-256 mismatch against the pinned checksum manifest; remediation is to retry `lando setup` and, if it fails again, report the release artifact URL and the observed checksum (`ProviderBundleChecksumError`).

## Windows managed API

Compiled Windows setup and named-pipe API reachability run in the provider integration acceptance job.

Lando reaches the managed Podman API over its Windows named pipe, not a Unix socket (`\\.\pipe\podman-lando`).

Setup verifies both basic API reachability and Podman info before reporting success.
