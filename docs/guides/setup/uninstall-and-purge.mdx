# Uninstall and purge

Preview the plan first. `lando uninstall --dry-run` prints owned, user-owned, skipped, and manual-remediation targets without changing the system.

Without `--yes`, Lando refuses destructive execution and tells you to rerun after review. `--yes` is required before any Lando-owned binary or data target is removed.

## Keep data vs purge

Choose one mode after reviewing the dry run. `--keep-data` removes the managed CLI while leaving runtime state available. `--purge` removes Lando-owned runtime resources and the data, cache, and config roots; back up any application data you need before using it. Use `lando uninstall --purge --dry-run` to see the engine connections and resource counts before confirming.

```sh
# Removes the managed CLI while preserving app data, the managed VM,
# runtime services, file-sync tools, global state, and caches
lando uninstall --yes --keep-data

# Removes Lando-owned apps, the managed VM, runtime tools, and data roots
lando uninstall --yes --purge
```

`--keep-data` leaves running apps and their managed VM in place. It also retains the provider setup state, runtime service, host-proxy sessions, and Mutagen tools so those apps can keep using them. The managed CLI binary is removed; keep the retained runtime files until you no longer need the app data.

On host Docker and Podman, `--purge` uses each provider's own engine connection, such as `DOCKER_HOST`, a Unix socket, or a Windows named pipe. It does not look for the `docker` or `podman` command on `PATH`. The plan names each reachable connection and counts the containers, networks, volumes, and built images in scope. It also names connections it could not reach; purge skips those engines.

Lando inspects each container, network, or named volume labeled for this data root before removing it. It stops and removes owned containers first, including their unused anonymous volumes. It then removes private networks, this root's shared bridge if nothing remains attached, and named volumes whose identity still matches. Named volumes and images are never force-deleted. Lando leaves other installations' resources and older resources without a data-root label alone.

Lando also removes images built for this cache root. It removes owned tags by name and keeps images with foreign tags or containers still using them. If in-scope cleanup is incomplete, Lando reports what it removed, kept, or could not delete and stops before removing the installation's files. `--keep-data` leaves images alone.

In private managed `lando` storage, purge also verifies that no containers or local volumes remain before deleting the storage and its images. On macOS and Windows, this whole-storage check and VM removal require a record that this installation created the VM and a match against the current VM. If Lando reused the VM, purge cleans only this data root's resources and keeps the VM.

Only after that check passes, together with the ownership and Windows file-sync guards below, does `--purge` remove the Lando-owned managed VM, runtime service, provider bundle, and file-sync tools. This also removes built-in and residual network configuration inside the verified private installation roots. It does not authorize deletion of unverified networks in system Docker or Podman, or files outside those roots. Purge removes:

- User data root (`~/.local/share/lando` or `$LANDO_USER_DATA_ROOT`)
- User cache root (`~/.cache/lando` or `$LANDO_USER_CACHE_ROOT`), including the remote source store that [`lando sources:gc`](../cli/sources-gc.mdx) otherwise trims
- User config root (`~/.config/lando` or `$LANDO_USER_CONF_ROOT`)

On Windows, Podman keeps network definitions in the Windows host config outside its managed VM. Removing the VM does not remove those definitions. Current definitions have no Lando ownership label, so the purge plan reports them for manual review. Check `$env:APPDATA\containers\networks` after purge, and leave any entry whose ownership you cannot verify. Lando does not delete those files.

On Windows, purge also refuses when accelerated file-sync state is active, unreadable, or still has helpers or sync volumes. Run `lando stop` for the affected app to flush pending file changes, then `lando destroy --volumes` only after backing up any database or other volume data you need. That destroy deletes the app’s data volumes as well as verified sync resources. Resolve any reported sync errors before retrying purge.

You can still stop or destroy apps yourself first. Purge no longer depends on it:

```sh
# Stop all apps before uninstalling, if you prefer a tidy shutdown
lando poweroff

# Then purge Lando
lando uninstall --yes --purge
```

A binary outside Lando's managed bin directory is never removed automatically. The plan prints exact manual removal steps for it instead.

## Socket proxy helper ownership

On Linux and WSL, `lando setup` can install a systemd socket proxy so Traefik can serve ports 80 and 443. The proxy plugin owns that helper's uninstall step, `socket-proxy-helper`. Uninstall removes the helper (its units under `/etc/systemd/system/` and the polkit rule) only when this install's data root installed it. The units carry the owner root's path, and Lando compares it to the data root you are uninstalling.

`--keep-data` keeps this install's helper in place, because it serves the apps keep-data leaves running. `--purge` removes it before deleting the data root. If that removal fails, purge keeps the data root and writes the resumable report so you can fix the cause and rerun.

Removal runs under `flock` from util-linux. Without it, the step reports `Install flock (util-linux), then rerun lando uninstall. No helper artifacts were changed.`

Helpers this install did not install are never removed:

- A helper installed by another Lando install that still exists is `user-owned`. The plan names that install's data root and leaves the helper running.
- Files at those paths with no Lando marker are also `user-owned`; Lando never touches them.
- A helper whose owner cannot be verified (the owner root is gone, the units carry Lando's marker but no owner stamp, or the files disagree with each other) is a `manual` step. The plan prints the exact commands:

```sh
sudo systemctl disable --now lando-proxy-http.socket lando-proxy-https.socket lando-proxy-http.service lando-proxy-https.service
sudo rm -f /etc/systemd/system/lando-proxy-http.socket /etc/systemd/system/lando-proxy-http.service /etc/systemd/system/lando-proxy-https.socket /etc/systemd/system/lando-proxy-https.service /etc/polkit-1/rules.d/10-lando-proxy.rules
sudo systemctl daemon-reload
```

Review who owns those units before you run them. If you would rather hand the helper to this install than remove it, run `lando setup` instead; see [Use the Traefik proxy](../subsystems/proxy-traefik.mdx).

## Review systemd cgroup delegation

Lando leaves `/etc/systemd/system/user@.service.d/delegate.conf` in place. Setup does not record which installation wrote that system-wide drop-in. If no other installation or program needs it, remove it on the host and reload systemd:

```sh
sudo rm -- /etc/systemd/system/user@.service.d/delegate.conf
sudo systemctl daemon-reload
```

## Review lingering

If you let `lando setup` enable lingering, uninstall leaves it enabled, because other user services may rely on it. If nothing else needs a user manager running while you are logged out, disable it:

```sh
loginctl disable-linger $USER
```

## Remove the local CA

Uninstall leaves the local CA that `lando setup` created in place and trusted, in both `--keep-data` and `--purge`. Every Lando installation on this machine shares that CA, and so does `mkcert` if you use it directly, so uninstalling one installation can't tell whether anything else still needs it.

The plan lists the CA as a manual step in both modes, with what you need to remove it from the trust stores Lando knows about: its fingerprint, the directory that holds it and its private key, and one command for each of those stores on this machine that may hold it. That covers the system trust store (on Windows and under WSL, both your user store and, if the CA was added for all users, the machine store), browser certificate databases, Homebrew's CA bundle, and the Java keystore older Lando setups wrote when `JAVA_HOME` is set. If you added the CA anywhere else by hand, such as a browser's own certificate settings, remove it there too. The commands use your operating system's tools, not Lando, so they still work after `--purge` removes Lando. Preview them with:

```sh
lando uninstall --purge --dry-run
```

Run them after you've uninstalled every Lando installation that uses the CA. Then delete the directory the step names, unless another tool uses it.

## Shell profile entries

`lando setup` can write a `# >>> LANDO4 shellenv >>>` block to your POSIX shell profile. Each block exports the `LANDO_USER_DATA_ROOT` it was written for. `--purge` strips only the block written for the data root you are uninstalling. Blocks for other installs stay, and the plan names their data roots as `user-owned`. A block whose data root is missing or unreadable is a `manual` step: remove it by hand if it belongs to this install. `--keep-data` leaves every block in place.

## Private runtime directory

On Linux, the managed `lando` runtime keeps its rootless Podman state (the pause process, user namespace handles, and temporary files) in a private directory under `/run/user/<uid>/`, named `lando-<id>` where the id is derived from this data root's runtime path. It lives outside the data root, so removing the data root alone would leave it behind. `--purge` stops this root's Podman pause process and removes that private directory after the runtime directory is gone. It never touches another data root's private runtime directory or pause process. `--keep-data` leaves both in place so retained apps keep working.

## Resume a failed uninstall

A failed confirmed uninstall writes a resumable report of completed, failed, skipped, and manual steps. The report lands at `<userDataRoot>/uninstall/report.json`, or under a private tmpdir if purge already removed the data root. After you fix the failure, rerun the same `--keep-data` or `--purge` command to resume.

In JSON output and the report, each step's `status` keeps its planning classification: `owned`, `user-owned`, `skipped`, or `manual`. Execution adds an `outcome` of `completed`, `skipped`, `manual`, or `failed`. Only failed outcomes carry an `error`; `detail` explains a manual outcome or why a target was preserved. Dry-run plans have no outcome.

For example, a data root classified as `owned` stays `owned` if removal is deferred. Its outcome is `manual` while the install record still needs cleanup, or `failed` if a host-maintainer step prevents safe removal. If the install record is removed later in the same run and nothing blocks deletion, the data root's outcome becomes `completed`.
