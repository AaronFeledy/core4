# Pick a container provider

Run `lando setup`, then `lando doctor`. The default provider is `lando` (Lando-managed Podman). It does not need system Docker or Podman.

On Intel Macs (`darwin-x64`), managed `lando` fail-closes. Run setup with Docker Desktop. That is the live path on that host, not a Linux-only fallback.

On Linux, if default setup fails, switch to system Docker. That is the supported fallback, not an advanced preference.

## Run setup with Docker

You need working Docker Desktop on Intel Mac, or working system Docker on Linux.

1. Run setup with Docker:

```sh
lando setup --provider=docker
```

Or set the provider for this shell:

```sh
LANDO_PROVIDER=docker lando setup
```

2. Verify:

```sh
lando doctor
```

After a successful `lando setup --provider=docker`, setup writes `defaultProviderId: docker` to your config. Later `lando doctor`, `lando start`, and bare `lando setup` stay on Docker. You do not need to repeat the flag. An interactive provider choice persists the same way. A failed config write fails setup.

`LANDO_PROVIDER=docker lando setup` does not persist. If you only set the env, keep it for later commands.

`lando setup` and `lando setup --yes` with no `--provider` keep the `defaultProviderId` already in your config. Setup prompts for a provider only when nothing chose one. `--yes` consents to confirmation and privileged host changes. It does not switch providers. To return to the default, run `lando setup --provider=lando`.

System `podman` is also opt-in with `--provider=podman`. It needs an existing Podman install. Setup fails with remediation if that runtime is missing. It does not install Docker or Podman for you.

## Override the provider

Setup (`lando setup`, including `--yes`) uses:

```
--provider > LANDO_PROVIDER > user-config defaultProviderId > interactive prompt > capability default (lando)
```

The router, ssh-agent sidecar, and other global services run on the provider setup selected, and every later command keeps them there.

App commands (`lando start`, `lando doctor`) use:

```
--provider > Landofile provider: > LANDO_PROVIDER > user-config defaultProviderId > capability default (lando)
```

Force Docker for one command:

```sh
lando start --provider=docker
```

Or for one shell:

```sh
LANDO_PROVIDER=docker lando start
```

A Landofile `provider:` or a one-off `--provider` selects only that app's desired provider. It never moves an existing app. If another provider already holds the app's applied plan, start, rebuild, and restart fail with `AppPlacementError` before changing resources. Stop, destroy, info, and logs follow the existing realization even after the default changes. From the app directory, run `lando destroy --provider=lando --yes` before starting on Docker. Data volumes stay on the old provider; they are not copied.

If older starts left copies on two providers, retire the unwanted copy with `lando destroy --provider=<id> --yes`. Without that explicit selection, ambiguous cleanup fails closed. The router and other global services stay on the host provider: `LANDO_PROVIDER`, else `defaultProviderId`, else `lando`.

## Switch providers while the global app is running

Lando never moves the global app on its own. If the router already runs on one provider and you change the host provider (for example `lando setup --provider=docker` after it started on `lando`), `lando global:install`, `global:start`, `global:restart`, `global:rebuild`, and any `lando start` that publishes routes fail with `AppPlacementError`.

1. Stop the apps that use the router:

```sh
lando stop
```

2. Destroy the global app. The command targets the provider where the global app actually runs:

```sh
lando global:destroy --yes
```

3. Retry the command that failed. The global app comes up on the new provider.

Or switch back to the provider that still holds it. If `LANDO_PROVIDER` picked the new provider, unset it first, or every later command picks it again:

```sh
unset LANDO_PROVIDER
lando setup --provider=lando
```

`lando global:stop`, `global:destroy`, `global:status`, `global:info`, and `global:logs` always act on the provider where the global app actually runs, so they keep working while the mismatch exists.

## Resolve a provider conflict

If `lando doctor` reports a conflict between the managed Lando runtime and system Podman, pick one provider explicitly:

```sh
lando setup --provider=lando
```

or, when you already have system Docker:

```sh
lando setup --provider=docker
```

or, when you already have system Podman:

```sh
lando setup --provider=podman
```

## Verify with lando doctor

```sh
lando doctor
lando --version
```

Doctor should name the provider you selected. After `lando setup --provider=docker`, bare `lando doctor` should report Docker.
