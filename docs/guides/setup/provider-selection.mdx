# Provider selection

## Provider selection precedence

App commands (`lando start`, `lando doctor`, the planner) pick a provider from the highest-priority input available, in this order:

```
--provider > Landofile provider: > LANDO_PROVIDER > ~/.lando/config.yml defaultProviderId > capability default (lando)
```

`lando setup` and `lando setup --yes` do **not** honor leftover `defaultProviderId`. A last-used `docker` or `podman` value in user config does not pick Docker for first-time setup. Setup precedence is:

```
--provider > LANDO_PROVIDER > capability default (lando)
```

Pass `--provider` on this invocation, or set `LANDO_PROVIDER` for this invocation, to override the Lando-managed default. `--yes` consents to confirmation and privileged host changes; it does not switch providers.

Force a specific provider for the current command:

```sh
lando setup --provider=podman
```

Or override the active provider for a single shell:

```sh
LANDO_PROVIDER=docker lando start
```

## CI managed lando default

linux-x64 provider-integration CI selects the lando capability default through lando setup instead of exporting LANDO_TEST_PODMAN_SOCKET.

CI provider-integration-linux-x64 runs dist/lando setup --yes --provider=lando and resolves the managed socket from Paths for contract and integration suites.

Local rehearsal may still point live tests at a manual socket when the managed runtime is unavailable.

```sh
LANDO_TEST_PODMAN_SOCKET
```

## Lando podman socket conflict

Reported in the provider-conflict check context (`provider-lando-podman-socket`).

provider-lando records its bound Podman socket here when set up (`$LANDO_DATA_DIR/providers/provider-lando/setup-state.json`).

Pick one provider explicitly to resolve the ambiguity.

```sh
lando setup --provider=podman or lando setup --provider=lando
```

## Lando managed runtime paths

provider-lando installs verified runtime bundle binaries in Lando's private runtime bin directory (`$LANDO_DATA_DIR/runtime/bin`).

provider-lando resolves the managed Podman socket from Paths instead of a system Podman location (`$LANDO_DATA_DIR/runtime/run/podman.sock`).

Setup state records the installed runtime version and runtimeBinDir for doctor and later provider resolution (`$LANDO_DATA_DIR/providers/provider-lando/setup-state.json`).

Runtime bundle extraction fails closed before install when gzip or zip inflation exceeds the default decompressed-size cap; tests may override the cap with this environment variable.

```sh
LANDO_RUNTIME_BUNDLE_MAX_DECOMPRESSED_BYTES
```

provider-lando ships managed runtime bundles only for hosts supported by Podman 6; Intel macOS (darwin-x64) fails setup with remediation instead of downloading a bundle.

## Provider data plane capabilities

provider-lando advertises native volume snapshots through the managed runtime data plane.

provider-docker and provider-podman advertise copy-mode volume snapshots over their Docker-compatible APIs.

All bundled providers advertise native service file copy for host↔container byte movement.

All bundled providers advertise image artifact import and export when their runtime API is available (`enabled`).

Bundled providers only advertise service log source following when the host injects log-file access; generic provider contracts still use runtime logs when that capability is false.
