# Choose a provider

The default provider is `lando`: a managed Podman runtime that does not use your system Docker.

```sh
lando setup
lando doctor
```

`lando setup --yes` consents to automatic host prerequisites. It does not switch providers. Leftover `defaultProviderId` in `~/.lando/config.yml` does not pick Docker or system Podman for setup.

`--provider=docker` or `--provider=podman` requires that system runtime to already be installed. Setup will not install it for you.

## If default setup fails

Fix the host problem first (`lando doctor`, then the command it prints).

If the managed runtime still cannot install and you already have working system Docker, use Docker as the supported Linux fallback:

```sh
lando setup --provider=docker
```

Or for one command:

```sh
LANDO_PROVIDER=docker lando start
```

This is a fallback, not the default.

## Who wins

App commands (`lando start`, `lando doctor`, the planner):

```
--provider > Landofile provider: > LANDO_PROVIDER > ~/.lando/config.yml defaultProviderId > capability default (lando)
```

`lando setup` and `lando setup --yes`:

```
--provider > LANDO_PROVIDER > capability default (lando)
```

Pass `--provider` on this invocation, or set `LANDO_PROVIDER` for this invocation, to override the managed default.

```sh
lando setup --provider=podman
LANDO_PROVIDER=docker lando start
```

## Socket conflict

If doctor reports a Podman socket conflict (`provider-lando-podman-socket`), pick one provider:

```sh
lando setup --provider=lando
```

or

```sh
lando setup --provider=podman
```

provider-lando records its bound socket in `$LANDO_DATA_DIR/providers/provider-lando/setup-state.json` and resolves the managed socket from Paths (`$LANDO_DATA_DIR/runtime/run/podman.sock`), not a system Podman location.

## Verify

```sh
lando doctor
```

## Contributor and CI notes

These are not the first-time user path.

Doctor prints NDJSON on every selected-provider check.

linux-x64 provider-integration CI selects the `lando` capability default through `lando setup` instead of exporting `LANDO_TEST_PODMAN_SOCKET`. The `provider-integration-linux-x64` job runs `dist/lando setup --yes --provider=lando` and resolves the managed socket from Paths.

Local rehearsal may still point live tests at a manual socket when the managed runtime is unavailable:

```sh
LANDO_TEST_PODMAN_SOCKET
```

provider-lando installs verified runtime bundle binaries in `$LANDO_DATA_DIR/runtime/bin`. Setup state records the installed runtime version and `runtimeBinDir` for doctor.

Runtime bundle extraction fails closed when gzip or zip inflation exceeds the default decompressed-size cap. Tests may override the cap with `LANDO_RUNTIME_BUNDLE_MAX_DECOMPRESSED_BYTES`.

provider-lando ships managed runtime bundles only for hosts supported by Podman 6. Intel macOS (`darwin-x64`) fails setup with remediation instead of downloading a bundle.

provider-lando advertises native volume snapshots through the managed runtime data plane. provider-docker and provider-podman advertise copy-mode volume snapshots over their Docker-compatible APIs. All bundled providers advertise native service file copy. Image import/export is advertised when the runtime API is `enabled`. Log-file following is advertised only when the host injects log-file access.
