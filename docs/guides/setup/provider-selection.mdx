# Pick a container provider

Choose a provider for your host, then run setup and verify it with `lando doctor`. The default provider is `lando` (Lando-managed Podman), which does not need system Docker or Podman.

On an Intel Mac (`darwin-x64`), install and start Docker Desktop, then run `lando setup --provider=docker`. The managed `lando` provider is not supported on that host. On other supported hosts, start with `lando setup`.

On Linux, if default setup fails, switch to system Docker. That is the supported fallback, not an advanced preference.

After setup succeeds, run `lando doctor` and check that it names the provider you selected.

## Run setup with Docker or Podman

You need working Docker Desktop on Intel Mac, or working system Docker on Linux. System Podman is also opt-in and needs an existing rootless Podman install.

1. Run setup with the provider you have:

```sh
lando setup --provider=docker
```

or:

```sh
lando setup --provider=podman
```

2. Verify:

```sh
lando doctor
```

Doctor should name the provider you selected. Setup fails with remediation if that system runtime is missing. It does not install Docker or Podman for you. To return to the default, run `lando setup --provider=lando`.

## How setup chooses a provider

`lando setup` (including `--yes`) picks the first of:

```
--provider > LANDO_PROVIDER > user-config defaultProviderId > interactive prompt > capability default (lando)
```

Setup prompts for a provider only when nothing else chose one. `--yes` consents to confirmation and privileged host changes. It does not switch providers, and it skips the prompt. `--no-interactive` and `--skip-provider` skip the prompt too.

## What persists

After a successful `lando setup --provider=docker`, setup writes `defaultProviderId: docker` to your config when it differs from what is already there. Later `lando doctor`, `lando start`, and bare `lando setup` stay on Docker. You do not need to repeat the flag. An interactive provider choice persists the same way. A failed config write fails setup.

`lando setup` and `lando setup --yes` with no `--provider` keep the `defaultProviderId` already in your config. Setup never changes it on its own.

`LANDO_PROVIDER` never persists. See the next section.

Read or edit the value directly with `lando config get defaultProviderId`, `lando config set defaultProviderId <id>`, and `lando config unset defaultProviderId`. Setting it by hand does not move the global app; use [Switch providers](#switch-providers) for that.

## Override the provider for one command

`LANDO_PROVIDER` selects a provider for that command or shell only:

```sh
LANDO_PROVIDER=docker lando start
```

```sh
export LANDO_PROVIDER=docker
lando start
```

`LANDO_PROVIDER=docker lando setup` does not persist. If the global app already lives on another provider, setup refuses with `AppPlacementError` before changing anything. Run `lando setup --provider=docker` to switch persistently, or unset `LANDO_PROVIDER` to keep the existing provider. If you only set the env, keep it set for later commands, or they fall back to your config.

On `lando setup` and `lando doctor`, `--provider` wins over `LANDO_PROVIDER` for that command.

## How an app chooses its provider

`lando start` creates an app on the first of:

```
Landofile provider: > LANDO_PROVIDER > user-config defaultProviderId > capability default (lando)
```

A Landofile `provider:` pins that app's desired provider, ahead of the environment and host default. It never moves an existing app. If another provider already holds the app's applied plan, start, rebuild, and restart fail with `AppPlacementError` before changing resources. Stop, destroy, info, and logs follow the existing realization even after the default changes. See [Recover an app left on another provider](#recover-an-app-left-on-another-provider).

Placement failures report `code: AppPlacementError` at the top level for start, setup, and global lifecycle commands. Machine output keeps the app identity, both provider ids, and the recovery commands in the same failure rather than hiding them inside a proxy or global-service cause.

## Where the global app runs

The router, ssh-agent sidecar, Mailpit, and other global services run on the host provider: `LANDO_PROVIDER`, else `defaultProviderId`, else `lando`. Setup places them on the provider it selected, and every later command keeps them there. A Landofile `provider:` selects only that app's provider; it never moves the global app.

Only setup moves the global app. Start, restart, rebuild, and doctor never relocate it. `lando global:stop`, `global:destroy`, `global:status`, `global:info`, and `global:logs` always act on the provider where the global app actually runs, so they keep working while a mismatch exists.

Cross-provider apps cannot reach same-runtime features such as Mailpit SMTP over `mailpit.global.internal` or the ssh-agent runtime volume. SSH forwarding still uses its host relay across providers.

## Routing needs one provider

Routes require the app and the router to use the same provider. If they differ and the router is enabled with nonempty routes (including generated defaults), planning fails with `RouteProviderMismatchError` before resources change. Lando never publishes host ports to bridge providers.

Pick one:

- Run `lando setup --provider=<app provider>` so the global app and router move there. See [Switch providers](#switch-providers).
- Remove `provider:` from the Landofile so the app follows the host provider.
- Keep the app where it is: set `router.enabled: false` and connect through explicitly published host ports. Setting each service's `routes: []` also suppresses its routes.

## Switch providers

Use setup for a deliberate switch. Nothing else moves global services. Export any data you need on the new provider before switching: setup does not copy data volumes, and they remain on the old provider. The poweroff command below also removes scratch apps and their disposable data unless you pass `--keep-scratch`.

1. Stop apps before switching:

```sh
lando poweroff --yes
```

2. Run setup on the new provider:

```sh
lando setup --provider=docker --yes --no-interactive
```

Setup refuses with `AppPlacementError` and lists running apps, including scratch apps, that use routes or require global services on the old provider. Stop those apps (a scratch app with `lando scratch:destroy <id> --keep-volumes --yes`) and retry. Once none are running, setup retires the old global containers and applied state, keeps its volumes and router dynamic configuration, and starts global services on the selected provider.

3. Read setup's list of user apps still applied on the old provider. From each app directory, retire the old realization and start on the new provider:

```sh
lando destroy --provider=lando --yes
lando start
lando info --format=json
```

Plain `lando start` uses the new persisted provider unless the Landofile has a `provider:` pin. Update or remove that pin to move the app. Data volumes stay on the old provider. Setup does not copy their contents. Export data before switching if the new realization needs it.

To switch back instead, unset `LANDO_PROVIDER` first if it picked the new provider, or every later command picks it again:

```sh
unset LANDO_PROVIDER
lando setup --provider=lando
```

## Recover an app left on another provider

Changing the default never moves an applied app or copies its data. Export any data you need before retiring the old copy. When `lando start` fails with `AppPlacementError`, run the following from the app directory, replacing `lando` in `--provider=lando` with the old provider named by the error:

```sh
lando destroy --provider=lando --yes
lando start
```

Data volumes stay on the old provider; they are not copied.

If older starts left copies on two providers, retire the unwanted copy with `lando destroy --provider=<id> --yes`. Without that explicit selection, ambiguous cleanup fails closed. The global app has the same escape hatch: `lando global:destroy --provider=<id> --yes`.

## Resolve a provider conflict

If `lando doctor` reports a conflict between the managed Lando runtime and system Podman, pick one provider explicitly:

```sh
lando setup --provider=lando
```

or, when you already have system Docker:

```sh
lando setup --provider=docker
```

or, when you already have system Podman:

```sh
lando setup --provider=podman
```

## Verify with lando doctor

```sh
lando doctor
lando --version
```

Doctor should name the provider you selected. After `lando setup --provider=docker`, bare `lando doctor` should report Docker.
