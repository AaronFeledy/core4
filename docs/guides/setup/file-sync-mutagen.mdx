# Accelerate Windows project files with Mutagen

Run `lando setup` to install the file-sync tools for Windows with the managed `lando` provider. Lando starts and manages the sync sessions for your app. If you'd rather keep a plain bind mount, set `appMount.accelerate: false` on the service or `defaultFileSyncEngine: passthrough` in global config; both are supported and reversible.

## Install the sync tools

```sh
lando setup
lando doctor
```

Setup installs checksum-verified Mutagen binaries and a private Docker command-line client. Lando uses that client to reach its managed Podman machine. You don't need to install or start Docker Desktop.

The `file-sync` doctor check verifies that the installed tools and session client are available. The separate `filesystem-watch` check creates a temporary Windows file and verifies that a native watcher receives its event. That watch check covers the host temporary directory; it does not test every project directory or a container watcher.

Setup installs the selected engine only when the provider reports slow bind mounts and an installed engine supports the host and provider. With automatic selection on a native Linux provider, with no compatible engine, or when global config selects `passthrough`, setup does no file-sync work and doctor does not require a sync engine.

## Start the app

If you set a service’s `user`, use a numeric UID and GID on Windows, such as `1000:1000`. Lando uses that identity for synced files. Named service users cannot be resolved before the container starts; use the numeric identity from your image.

From your project directory:

```sh
lando start
lando info --format=json
```

Edit a project file on Windows and check the change through the app's URL or tooling. Files written inside the synced project paths return to Windows too. Lando completes the initial sync before it starts the app's services. That first scan can take several minutes for a large project; later starts reuse the session and its history. Only the project app mount is accelerated; extra bind mounts, including config files, keep their ordinary mount behavior.

Read `result.fileSync.applied` for the recorded mount policy, not proof that the sync daemon is healthy. If start reports a missing tool, unavailable engine, or failed sync-target preparation, follow its remediation and retry. A planned accelerated start fails rather than silently switching to ordinary binds.

## Keep an app mount as an ordinary bind

Acceleration is automatic, not forced. To keep one service's app mount as a plain bind on a slow provider, set `accelerate: false` on its `appMount` block. `target` stays required:

```yaml
services:
  app:
    type: "node:22"
    primary: true
    appMount:
      target: /app
      accelerate: false
```

Lando then mounts the project directory directly and creates no sync session. Excluded directories such as `node_modules` still get their own service-owned overlays. Unshadowed files and `.git` become visible through the bind. A fresh app needs no sync engine; an already accelerated app still needs its previous engine to finish the safe switch described below. Omitting `accelerate`, or writing `true`, permits automatic acceleration and never forces it: a native Linux provider stays an ordinary bind either way.

A Landofile cannot name a sync engine. Engine choice belongs to the host, through global config.

## Choose an engine for every app

Global config decides which engine accelerates app mounts on this machine:

```sh
lando config set defaultFileSyncEngine passthrough
lando config get defaultFileSyncEngine --format=json
```

```yaml
defaultFileSyncEngine: passthrough
```

`passthrough` is a reserved policy, not an engine: app mounts on this host use ordinary binds instead of creating sync sessions. Existing accelerated apps first drain through their recorded engine. Unset the key to return to automatic selection. See [Read and write global config](../config/global-config.mdx) for how `config.yml`, drop-ins, and `LANDO_CONFIG__DEFAULT_FILE_SYNC_ENGINE` layer.

When an app mount may accelerate on a slow provider, Lando first checks which installed engines support the host platform, the provider's sync-target capabilities, `two-way-safe` synchronization, and exclusion patterns. A plugin's default preference does not grant support. Lando then chooses:

- The engine id in `defaultFileSyncEngine`, if it is installed and eligible. An unknown or unsupported named choice fails with a selection error and remediation; naming an engine never bypasses support checks.
- Otherwise, the one eligible engine whose plugin metadata nominates it for this host platform and bind-mount performance. Multiple matching defaults fail until you choose an eligible engine explicitly.
- Otherwise, the sole eligible engine. Multiple eligible engines with no unique default also fail instead of choosing by load order.

If automatic selection finds no eligible engine, the app uses ordinary binds and `lando info --format=json` reports `no-compatible-engine`. You do not need a file-sync workaround in your Landofile or global config for macOS or Docker Desktop. Ordinary binds still support directory overlays, but do not filter excluded files or `.git` out of the host tree.

Once Lando plans acceleration, engine loading, setup, availability, capability, and sync-target failures are errors with remediation, not reasons to downgrade to ordinary binds. This applies to new apps too. Changing an existing accelerated app to ordinary binds still requires the safe transition below; automatic selection cannot bypass unreturned edits.

## Inspect the project-file policy

From the app directory, refresh the desired plan and read its policy without starting services:

```sh
lando app:cache:refresh
lando info --format=json
```

Under `result.fileSync`, `planned` describes the desired policy and `applied`, when present, describes the recorded applied plan. `pendingChange: true` means those two policy snapshots differ. If there is no applied evidence, `applied` is absent and `pendingChange` is false; that does not mean the app is running or the desired plan has been applied.

Each snapshot has a `mode` and a `reason`, with `engineId` shown once for the app when accelerated. Its `services` list distinguishes accelerated app mounts, ordinary binds, and services with no app mount (`absent`). Reasons include `native-provider`, `service-opt-out`, `global-passthrough`, and `no-compatible-engine`. A mixed app can have an engine selected while an opted-out service stays ordinary.

For each service, `exclusions.kind` distinguishes transport filtering (`transport-patterns`) from directory overlays (`directory-overlays`). `patterns` lists transport filters, `overlays` lists derived volume paths, and `hostBackedIncludes` lists the host and container paths kept by explicit includes. A historical plan without recorded reasons reports `unknown`; Lando does not guess from today's config. This policy view does not load a sync engine, query its sessions, or check daemon health. Use `lando doctor` and an actual file edit to check operation.

## Exclude generated files

Add patterns under the service's app mount:

```yaml
services:
  app:
    type: "node:22"
    primary: true
    appMount:
      target: /app
      excludes:
        - dist
```

The defaults already exclude `node_modules`, `vendor`, `.git`, and `tmp`. See [Exclude paths from file sync](./file-sync-excludes.mdx) for includes and per-service overrides.

After you change `excludes`, `includes`, or what is mounted under the app mount, the next `lando start` tells you the sync settings changed, syncs pending changes back to your project, removes the old session, and creates a new one with the new settings. Named data volumes stay. The new session starts with a full initial scan. If that start is interrupted, the next `lando start` picks up where it stopped.

## Switch between accelerated and ordinary mounts

Changing `accelerate`, changing `defaultFileSyncEngine`, or installing a plugin that changes automatic selection takes effect on the next `lando start`. Lando treats a changed selection like a changed sync setting. The transition runs in this order:

Lando first checks that the previously applied app state is fully yours and reads the engine id recorded with it. It stops the app's writers, then uses that recorded engine, not the new one, to flush pending container-side edits back to your project and remove the old sessions and sync targets.

After that, Lando retires the old applied state without removing named data or cache volumes and without running authored destroy steps. It applies the new plan: an ordinary bind with no session, or a fresh session under the new engine that populates from your project.

Start refuses the switch and leaves everything in place when it can't do that safely: an unresolved file conflict, a session whose history is gone, an engine it can't reach, applied state it doesn't recognize, a failed flush, or an unfinished accelerated start recorded for a different plan. Fix the reported problem, or restore the previous settings, then run `lando start` again. An interrupted switch resumes from where it stopped.

## Stop and resume the app

```sh
lando stop
lando start
```

Stopping pauses the app's sessions and retains their history. Starting resumes them, including changes made while the app was stopped. Lando uses two-way safe sync: if both sides change the same file incompatibly, it reports a conflict instead of choosing one version silently.

`lando destroy` removes the app's sync sessions and disposable sync caches after syncing pending changes in included paths back to the project. Resolve reported sync errors before retrying destroy. The normal destroy rules for application data volumes still apply.

## Finish an interrupted start

```sh
lando start
```

If a start fails or you press Ctrl-C at any point, valid sync sessions, their targets, and every container Lando already created stay where they are, even if some containers already ran and wrote to the targets. The next `lando start` finishes any unfinished accelerated-start attempt with the same sessions and their history and reuses the containers that match the plan. `lando restart` and `lando rebuild` finish an unfinished attempt first, then continue with their explicit stop/recreate work. Lando never reseeds an existing target from your project. `lando doctor` lists an unfinished attempt until provider apply completes. `lando stop` and `lando destroy` work on it like any other app, with one exception: destroy refuses when a sync target may hold app writes and its session is gone, until you restore that session's history in Mutagen. See [Finish an interrupted accelerated start](../subsystems/doctor-walkthrough.mdx#finish-an-interrupted-accelerated-start).

## Resolve a file conflict

If start reports a conflict, keep the session and inspect the affected paths:

```sh
lando start --format=json
```

The error names the session, relative file paths, verified Mutagen and Docker tools, isolated session data, and helper container. Use those exact tools and settings when inspecting it. The Windows project is one copy; the helper's `/sync` directory is the other.

Stop anything writing to the affected project files, then use the reported Mutagen CLI and isolated session data to pause that exact session. For a conflict between two regular files, copy both versions to a backup folder outside the project before changing either one. Compare or merge the backups, then put the chosen contents in both locations. Keep the helper file owned by the service's numeric UID and GID. Once both copies agree, retry:

```sh
lando start
lando info
```

Directory, deletion, and symbolic-link conflicts need a decision about which content to keep; see [Mutagen's conflict resolution guide](https://mutagen.io/documentation/synchronization#conflict-resolution). Keep your backups until the app starts and the files match. Do not reset or terminate Lando's session or remove its cache to bypass a conflict: that can discard the history or the container's unreturned edits.

## Check whether your host can accelerate

The bundled Mutagen transport supports native Windows with the managed `lando` provider's prepared sync volumes. A Windows host alone is not sufficient: an external runtime socket does not provide that managed target lifecycle. On macOS or Docker Desktop, the bundled engine is ineligible, so automatic selection keeps ordinary binds without extra configuration. Native Linux providers, including rootless Podman and Docker Engine, also use ordinary binds.

An explicit engine id is still validated when host policy is evaluated, even on a native provider. Clear an unsupported named choice with `lando config unset defaultFileSyncEngine`, then read the effective value with `lando config get defaultFileSyncEngine --format=json`. If a drop-in or environment override supplies it, remove it there instead. A valid explicit choice does not force a native provider to accelerate.

`lando setup --skip-file-sync` skips engine selection and installation for that setup run, including when the configured engine is missing or ambiguous. It does not remove existing tools, select ordinary mounts, or change your provider. Later app planning still follows the configured policy.

Lint the opt-out before you start, then refresh the plan and inspect its mount layout. These commands do not install Mutagen or boot a sync session.
