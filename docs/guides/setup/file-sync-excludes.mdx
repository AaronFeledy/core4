# Exclude paths from the app mount and other binds

A service's app mount shows your whole project unless something excludes a path. A service's excludes are the ones its service type declares plus the ones you write. An excluded directory is an empty volume that belongs to the service, so what the service writes there stays in the service, not on your host. The same Landofile produces the same mounts on Linux, macOS, and Windows.

| Service type | Excluded by the service type |
| --- | --- |
| Node, including a Node service on your own image | `node_modules`, plus `<packageRoot>/node_modules` when `packageRoot` is a nested directory. Nothing with Yarn Plug'n'Play. |
| Ruby | `.bundle` and `vendor/bundle` |
| Python | `__pycache__` and `.venv` |
| PHP, `compose`, static, nginx, Apache, Tomcat, .NET, Go, `lando` | Nothing |

Composer's `vendor/` is project content. It's part of the app mount, so Composer installs into your project directory. Your editor, PHPStan or Psalm, and coding agents read the same packages PHP does, and every service that mounts the app shares them: `appserver`, a queue worker, a scheduler. `tmp/` is ordinary project content too.

On macOS and Windows, accelerated file sync leaves each excluded directory out of synchronization and copies the rest of the project, `vendor/` included. Its one fixed ignore is `.git`; see [Keep Git metadata available](#keep-git-metadata-available).

## Add your own excludes

Add per-service patterns under `services.<name>.appMount.excludes` in your Landofile. Your patterns are appended after the service type's. Duplicates are removed.

If a path must stay on the host even though the service type excludes it, add it to `services.<name>.appMount.includes`. An include that names the exclude, such as `node_modules` on a Node service, keeps all of that directory on the host. A deeper path, such as `node_modules/@acme/ui`, keeps only that directory on the host while the rest of `node_modules/` stays in the service. Includes are literal paths relative to the mount: an absolute path, `..`, or a glob character fails `lando app:config:lint`.

```yaml
services:
  app:
    type: "node:22"
    primary: true
    appMount:
      target: /app
      excludes:
        - dist
        - coverage
      includes:
        - node_modules
```

This service owns `dist` and `coverage` and uses the `node_modules` in your project directory.

From the app directory, run `lando app:config:lint --format=json`, then `lando start` to apply the changed mounts. Check the affected path inside the service; the [verification commands below](#verify) distinguish a fresh overlay from a host-backed directory.

To give one service its own `vendor`, exclude it there:

```yaml
services:
  app:
    type: "php:8.4"
    primary: true
    appMount:
      target: /app
      excludes:
        - vendor
```

That service's `vendor` starts empty and is invisible to your host and to other services, so run its dependency install inside it.

Lando 3's `!vendor` spelling is not accepted; `includes` is the one way to keep a path. The Lando 3 translator rewrites `!vendor` and deeper entries like `!vendor/acme` into `includes` for you.

An authored `appMount` block needs `target`, the container path of the app mount. `/app` keeps the default. A different path moves the mount, and on Lando service types the working directory, `LANDO_APP_ROOT`, `LANDO_PROJECT_MOUNT`, and a relative `webroot` follow it. When you only move the mount, write `appMount: /site`; it means the same as a block with just `target: /site`. Use the block form when you need `excludes`, `includes`, `readOnly`, or `accelerate`. The path must be absolute.

`accelerate: false` keeps the app mount as an ordinary bind, with no sync session, where Lando would otherwise accelerate it. Excluded directories still get the same overlays; files that have no overlay, including `.git`, remain visible through the bind. Omitting it, or `accelerate: true`, lets Lando accelerate the mount automatically where the host supports it. A Landofile never names a sync engine; see [Accelerate Windows project files with Mutagen](./file-sync-mutagen.mdx#keep-an-app-mount-as-an-ordinary-bind).

Set `appMount: false` when a service does not use your app's code. Lando mounts no app source and sets no `LANDO_APP_ROOT`, `LANDO_PROJECT_MOUNT`, or `LANDO_WEBROOT`. The container starts in the image's own working directory unless you set `working_dir`. On webroot-serving types (`php`, `nginx`, `apache`, `static`, `tomcat`), a relative or omitted `webroot` fails planning: set an absolute container path or remove `appMount: false`. A [Tomcat](../services/tomcat.mdx) service on a custom `image:` or `build.context` is the exception: leave `webroot` out, because nothing would use it. An absolute `webroot` such as `/var/www/html` serves content the image provides. Data stores already skip the app mount. An authored `mounts:` entry whose target is the app mount path replaces Lando's app mount instead.

## Mount a host directory inside an excluded one

Lando mounts every path a service gets from the shallowest to the deepest, so a deeper path always shows through the one above it. To put a host directory inside an excluded directory, mount it at its own path:

```yaml
services:
  app:
    type: "node:22"
    primary: true
    mounts:
      - source: ./packages/ui
        target: /app/node_modules/@acme/ui
```

`/app/node_modules` stays the service's own volume, and `/app/node_modules/@acme/ui` is your host's `packages/ui`. A mount at exactly an excluded path, such as `target: /app/node_modules`, replaces that overlay instead of nesting inside it.

Each path takes one mount. Two entries from `mounts:`, `storage:`, and `tmpfs:` at the same path fail `lando app:config:lint`, which names both. A Compose `volumes:` entry or `configs:` grant at a path that `mounts:`, `storage:`, or `tmpfs:` already uses is dropped in their favor; two Compose entries at one path fail lint, as they would in Compose.

## Exclude paths from other bind mounts

A host bind under `mounts:` takes the same `excludes` and `includes` as the app mount. Service types declare excludes only for the app mount, so list every path you want the service to own:

```yaml
services:
  tools:
    type: "node:22"
    appMount: false
    mounts:
      - source: ./tools
        target: /tools
        excludes:
          - node_modules
```

`/tools/node_modules` becomes a volume that belongs to the `tools` service. `excludes` and `includes` work only on host binds; on a `volume` or `tmpfs` mount, lint fails.

## Keep a framework directory on the host

To keep a directory on the host that the service type excludes, such as Ruby's `vendor/bundle`, name it in `includes`. Merged order is the service type's excludes, then yours. Stock Python uses an app-scoped dependency environment for `.venv` instead of an exclude shadow. Compatible services share it. Adding `appMount.includes: [.venv]` opts out and exposes the host tree, which may not run in the container. See [Python services](../services/python.mdx).

Excludes create volume overlays at literal paths relative to the mount target; they do not create overlays for nested directories with the same name. Add `backend/.venv` to give that path its own overlay. With accelerated sync, Mutagen treats a name without `/`, such as `.venv`, as an ignore at every directory depth, so nested venvs are excluded from synchronization even without their own overlay. Use literal paths rather than globs for predictable behavior across mount modes.

## Choose between a directory overlay and a shared volume

An excluded directory gets an empty volume overlay, one per service, so two services never share an excluded directory. When a second service needs the same `node_modules/`, include it on both.

On the managed `lando` provider and on `podman`, a fresh overlay volume belongs to the service's process user the first time it is mounted, unless the image already has a directory at that path; then the volume takes that directory's owner. A service that runs as a non-root user, such as `user: node` or a `type: compose` service with `user: "1001"`, can write to its `node_modules` without a `chown` step.

A volume you mount yourself inside the app mount works the same way, so `storage: [/app/node_modules]` and `excludes: [node_modules]` give the same result. Use `storage` when you want to name the volume or share it across services with `scope: app`. A `tmpfs` mount at the same path, under `mounts:` or the service's `tmpfs:` list, is the throwaway version: it replaces the overlay with an in-memory directory that starts empty every time the container starts.

An overlay can only cover a directory. When an excluded path is a file on the host, Lando skips the overlay and the file remains visible through an ordinary bind. Every accelerated file-sync session leaves it out, along with every other path mounted beneath the app mount, including nested binds, because the engine receives the derived exclusion patterns.

Overlays and sync exclusions are two different things. Overlays decide what the container sees at each directory. Exclusion patterns decide what the engine copies. Every eligible accelerated engine must support exclusion patterns and `two-way-safe` synchronization; Lando does not substitute overlays for transport filtering. If automatic selection finds no compatible engine, it uses ordinary binds with directory overlays instead. Those binds do not hide excluded files or `.git`. An explicitly named incompatible engine fails selection rather than weakening exclusions.

## When a directory moves back to the app mount

When a service will see app-mount contents where it had its own volume, the next `lando start`, `lando restart`, or `lando rebuild` warns once. That happens after you remove an entry from `excludes` or add one to `includes`. It also happens once after an upgrade for an app that an earlier Lando release started with `vendor` or `tmp` volumes it no longer creates.

The warning names the service, the path (such as `/app/vendor`), and the volume. Lando leaves that volume untouched and does not copy its contents to your project, so the directory holds whatever your host has there.

If the service has no `build.app` steps, the warning also tells you to rerun the dependency install, such as `lando composer install`. A service with `build.app` steps gets no such advice: Lando replaces its container, and the steps run again against the app mount.

## Keep Git metadata available

Accelerated app mounts exclude `.git` from sync by default. On ordinary bind mounts, whether from a provider that needs no acceleration, an opt-out, or no compatible engine, Lando does not hide `.git`, so the container sees the directory. `git status`, `git log`, and anything that shells out to git work at `/app` there. If you need `.git` with Mutagen, `includes: [.git]` turns the exclusion off; synchronizing a large repository can be slow.

In a `git worktree`, `.git` is a one-line file that points at the main checkout's `.git` directory. On Linux, Lando mounts that directory into the container at the same path, so git works in the worktree too. Inside the container, `git worktree list` shows the worktree as `prunable` because the container can't see the worktree folder at its host path, and a plain `git worktree prune` there drops the worktree's entry. Prune from the host. `git gc` is safe: it only prunes worktrees idle for months. A checkout that is itself a git submodule is different: its git config pins the working tree to the host path, so git stays a host-side tool there.

## Verify

After you change excludes, start so the mounts update:

```sh
lando start
lando doctor
```

Then check what the container sees:

```sh
lando exec app -- ls -A /app/node_modules
lando exec app -- git -C /app status --short
```

The first prints nothing on a fresh service. The second works with an ordinary app mount; with Mutagen and the default `.git` exclusion, it fails with `not a git repository`.

To see the planned layout without starting anything, refresh the plan and read `lando info --format=json`:

```sh
lando app:cache:refresh
lando info --format=json
```

Each entry under `services[].mounts` has a `type` (`bind`, `volume`, or `tmpfs`) and a `target`, listed shallowest first, plus a `provenance` that says why it is there: `authored` for your Landofile, `service` for the service type, `derived` for an excluded directory's volume or a nested include. Before `lando start`, its `observation` is `unknown`.

In the same JSON result, `fileSync.planned.services[]` explains each service's project-file policy. An ordinary app mount reports `exclusions.kind: directory-overlays`, an empty `patterns` array, and the derived overlay paths in `overlays`. An accelerated app mount reports `transport-patterns` and its exact planned filters. `hostBackedIncludes` records both exact includes, such as `node_modules`, and nested ones, such as `vendor/acme/sdk`, with their host `source` and container `target`.

Compare `fileSync.planned` with `fileSync.applied` when applied evidence exists. `pendingChange` reports whether those snapshots differ, not whether synchronization is healthy. Older plans without recorded policy reasons report `unknown`. See [Inspect the project-file policy](./file-sync-mutagen.mdx#inspect-the-project-file-policy).

Lint the excludes before you start. The check reads the Landofile. It does not boot a sync session.
