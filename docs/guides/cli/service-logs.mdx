# Read service logs

```sh
lando logs --service appserver
```

That prints a snapshot for the service, merging console output with any declared file sources. File-source lines carry their source id (`appserver stderr [myapp-error]: line`). Console lines omit a source label (`appserver stdout: line`).

Declare extra in-container log files on the service that owns them:

```yaml
services:
  myapp:
    logs:
      - path: /var/log/myapp/error.log
        stream: stderr
        label: myapp error log
```

A user-declared source needs a `path`. You can also set `id`, `label`, `stream`, and timestamp behavior. The implicit container stdout/stderr source is always available. Use `--source console` to select that combined stream.

Lando-built images can redirect daemon log files through stdout/stderr. Bring-your-own images and logs that cannot redirect are followed by the active runtime provider. You do not run `tail -F` yourself.

## Filter and follow

Select one declared source id, or select the combined stdout/stderr stream with `console`:

```sh
lando logs --service appserver --source myapp-error
```

`--follow` backfills the source tail, then streams new lines until you interrupt:

```sh
lando logs --service appserver --source myapp-error --follow
```

`--tail` applies per source, not as one total across merged sources:

```sh
lando logs --service appserver --tail 50
```

`--since` accepts durations such as `30s`, `15m`, `2h`, `7d`, or an RFC3339 timestamp:

```sh
lando logs --service appserver --since 15m
```

## When a source is missing

A provider that cannot stream service logs fails before planning with a tagged capability error and a fix. Follow sources from container files need the `serviceLogSources` capability. Redirect sources still work without it because they flow through the console stream.

Selecting a redirected source selects that console stream. Other stdout and stderr from the same container can appear with it because the runtime cannot separate the original file after redirection. Use a `follow` source when you need file-specific output and the provider supports it.

A required follow source fails up front when the provider cannot follow service files. A non-required unavailable follow source is marked unavailable and skipped. An undeclared `--source` fails and lists the known source ids, including `console`.

Without `--follow`, a file source emits a bounded snapshot and reaches EOF. Followers survive common log rotation (rename+create and copytruncate) and keep per-source order. Interrupting `lando logs` releases every follower. Lines are redacted once before they reach the CLI.

## Read a start-failure log tail

When the provider cannot apply a service, Lando tries to capture its console logs before rollback removes newly created containers. Captured output appears in the failure report, including in non-interactive runs. The snapshot keeps the last 50 lines within 4,000 characters; an oversized line keeps its end.

After apply succeeds, `lando start`, `lando restart`, and `lando rebuild` wait for services to stay running and pass their enabled healthchecks. Longer waits show per-service readiness progress. Selected-service operations follow the same rule. An unsupervised exited service or exhausted check fails non-zero with `ServiceNotReadyError`, naming the service and reason, with the stopped container's exit code and log tail when available. Running containers do not report an exit code. Lando retains the applied app, routes, and volumes so you can inspect the failure:

```sh
lando logs -s appserver --tail 50
lando info
```

Fix the service and run `lando start` again. For a healthcheck failure, correct the command or relax the timing in `healthcheck:`; set `healthcheck: { disable: true }` only when you want running-state checks without a health probe. Post-start steps run only after readiness succeeds. URL-scan warnings do not fail start.

With authored `restart: always` or `unless-stopped`, an exit or observed restart delegates recovery to the container engine. `on-failure` does that only for a non-zero exit; exit 0 remains a readiness failure. Start warns with the reason, available exit code, a short redacted log tail, and app-specific logs remediation, then reports `restarting`. Exhausted healthchecks still fail, and completion jobs must exit 0 regardless of restart policy. Pressing Ctrl-C during user-app readiness leaves the applied app running while the command exits as interrupted.

An inspection failure uses reason `inspect-failed`, not a stopped-container verdict. Run `lando doctor` to diagnose the provider. For global services, use `lando global:logs -s <service>` and retry `lando global:start`. Scratch acquisition also waits for readiness, but failure or interruption cleans up unless `--keep-on-failure` was passed. Inspect a retained scratch by its id, not with user-app `lando start`.

A blocked dependency gate captures the dependency that failed the gate, not the service that was waiting on it. `--format=json` puts the same snapshot on `error.logTail` (`service`, `lines`, `truncated`, and optional `exitCode` / `timedOut`). Gate metadata reports the last healthcheck or completion exit code and whether the healthcheck timed out.

Known secrets and credential patterns are redacted before truncation. Unregistered secrets, such as passwords generated inside a container, can still appear. Empty logs, capture failures, and the four-second capture timeout omit the tail without replacing the original start error. Starts interrupted before capture skip it.
