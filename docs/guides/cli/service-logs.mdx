# Service logs

Declare extra in-container log files under `services.<name>.logs`, the
service that owns them:

```yaml
services:
  myapp:
    logs:
      - path: /var/log/myapp/error.log
        stream: stderr
        label: myapp error log
```

A user-declared source needs a `path`; `id`, `label`, `stream`, and
timestamp behavior can be tuned when needed. Landofile-declared sources
resolve to provider-owned follow sources — user config doesn't choose the
collection architecture. The implicit container stdout/stderr source is
always available and is selected with `--source console` when you want only
engine logs.

Service types can declare redirect sources for Lando-built images so daemon
log files flow through stdout/stderr with no runtime follower. BYO images
and non-redirectable logs are followed by the active runtime provider inside
`RuntimeProvider.logs`. Core doesn't shell out to `tail -F`; the provider
owns file access, rotation handling, framing, and follower cleanup.

## The `lando logs` CLI

Show a finite snapshot for the selected service, merging console and
available declared sources with source labels:

```sh
lando logs --service appserver
```

File-source lines are labeled with their source id so interleaved output
stays attributable (`appserver stderr [myapp-error]: line`); console lines
omit a source label since absence of source means the implicit console
source (`appserver stdout: line`).

`--source` restricts output to one declared source id, or to `console` for
container stdout/stderr:

```sh
lando logs --service appserver --source myapp-error
```

`--follow` backfills the source tail and then streams appended lines until
interrupted:

```sh
lando logs --service appserver --source myapp-error --follow
```

`--tail` applies per source, not as a single global total across merged
sources:

```sh
lando logs --service appserver --tail 50
```

`--since` accepts durations such as `30s`, `15m`, `2h`, `7d`, or an RFC3339
timestamp:

```sh
lando logs --service appserver --since 15m
```

## Capability degradation

A provider that can't stream service logs fails before planning with a
tagged capability error and remediation. A provider must advertise
`serviceLogSources` before follow sources can be read from container files;
redirect sources remain available without it, since they flow through the
existing console stream.

A required follow source fails up front when the provider can't follow
service files. A non-required unavailable follow source is surfaced as
unavailable and skipped instead of being silently dropped. Requesting an
undeclared `--source` fails with the known source ids, including `console`.

## Following, rotation, and redaction

Without `--follow`, a file source emits a bounded snapshot and reaches EOF
instead of waiting for a missing future file. Provider followers survive
common log rotation patterns (rename+create and copytruncate) while
preserving per-source order. Redaction and rendering happen after provider
framing as complete UTF-8 lines, so multibyte characters and partial final
lines are handled consistently. Interrupting `lando logs` releases every
provider follower through the logs stream scope.

Providers and library callers see the raw `LogChunk` stream; the on-disk
service file stays under the app's control. CLI rendering, stream frames,
events, and transcripts pass lines through `RedactionService` exactly once.
Machine-readable output preserves the source id on `StreamFrame.source` so
agents can distinguish console, redirect, and followed file lines.
