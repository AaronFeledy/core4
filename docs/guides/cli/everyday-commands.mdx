# Run the everyday CLI loop

Run these commands from an app directory with a Landofile after completing `lando setup`. Start the app, inspect its services and connection details, then run commands inside it.

```sh
lando start
lando info
```

Use the URLs and connection details from `lando info` to reach your services. When you finish working, use `lando stop` to stop the app while keeping its named volumes. Use `lando destroy` only when you want to remove its containers and networks.

## Everyday commands

| Command | What it does |
| --- | --- |
| `lando start` | Start this app and apply changed container create configuration. Unchanged containers and named volumes stay. Alias of `app:start`. |
| `lando info` | Print services, URLs, and connection details. Alias of `app:info`. |
| `lando exec -- <cmd>` | Run a one-off command in the primary service; `-s` / `--service` selects another service. Alias of `app:exec`. |
| `lando logs` | Stream service logs. Alias of `app:logs`. |
| `lando stop` | Stop this app. Keeps named volumes. Alias of `app:stop`. |
| `lando restart` | Stop then start. Alias of `app:restart`. Pass `-s` / `--service` to bounce one service. |
| `lando rebuild` | Force an image pull, cache refresh, and app-build rerun, then recreate containers. Asks first. Alias of `app:rebuild`. |
| `lando destroy -y` | Remove this app's containers and networks. Named volumes stay unless you pass `--volumes` or `--purge`. Alias of `app:destroy`. |
| `lando doctor` | Report setup, provider, proxy, and cert health. Alias of `meta:doctor`. |
| `lando poweroff -y` | Stop every Lando app on this host. Alias of `apps:poweroff`. |
| `lando list` | List apps on this host. Alias of `apps:list`. |
| `lando share` | Start a public tunnel. Use `--target` for a non-primary service or extra port. Alias of `app:share`. |

## Fix a mistyped command

When a command does not exist, Lando names the closest one it knows: built-in commands, this app's tooling tasks and scripts, and plugin commands.

```sh
lando strat
```

```text
Unknown command "strat".
  ↳ Did you mean `lando start`?
code: UnknownCommandError
commandId: cli:unknown-command
commandToken: strat
suggestions: start
```

The command exits `2`, like any other way of calling Lando wrong, so scripts can tell a typo from a command that ran and failed. Command ids use colons; only a few groups such as `scratch`, `global`, and `app config` also accept spaces. `lando meta version` suggests `lando meta:version` or its alias `lando version`. With `--format=json`, `error.suggestions` lists up to three spellings, best first. When nothing is spelled close, the remediation points at `lando help --all`.

## Work inside a service

```sh
lando exec -- node --version
lando exec db -- psql --version
lando logs --service app --follow
```

`lando ssh` opens a login shell in the primary running service. It starts bash when available, or sh otherwise. See [Open a shell in a service](./ssh.mdx).

## Stop, restart, rebuild

```sh
lando stop
lando start
lando restart
lando rebuild
```

Bare `restart` stops then starts the app, removing and recreating its containers and reusing local images. It is not an in-place process restart. `lando start` applies a changed image, command, environment, user, working directory, mount, label, healthcheck, or other container create setting, and keeps unchanged containers and named volumes. `rebuild` re-pulls the images your services reference so updated tags take effect, then reruns the build even when the build key did not change. If the registry can't be reached, Lando warns and rebuilds from the local copies. A service's `pull_policy` takes precedence: `never` is never pulled, and a failed pull of an `always` service fails the command; see [Control when the image is pulled](../services/compose-passthrough.mdx#control-when-the-image-is-pulled). Only an image that was never pulled needs network access; build steps that download packages still need it too. `start` does not take `-y`.

All of these keep named volumes and drop a removed container's anonymous volumes. For what counts as retained storage, how to declare it, and how to read `services[].mounts` in `lando info --format=json`, see [Keep data across stop, restart, and destroy](../tutorial/app-lifecycle.mdx#keep-data-across-stop-restart-and-destroy).

The `stopped:` and `destroyed:` lines repeat how the runtime said each container ended, such as `app (exit 143)` after SIGTERM, and `--format=json` carries the same facts under `result.shutdownObservations`. Lando reports the code; it does not decide whether the stop was clean. Exit `0` is not proof your app finished its cleanup, and `137` alone is not proof Lando killed it. Only an explicit `OOMKilled` report or a failed inspection adds a warning. See [Read what stop reports](../tutorial/app-lifecycle.mdx#read-what-stop-reports).

## Recover from a failed start

```sh
lando info
lando logs -s <service>
lando start
```

A failed or interrupted `lando start` keeps what it built: created containers (started or not), networks, volumes, published routes, agent relays, and file-sync sessions. Creating a container is not the same as it being ready. After the error, the human report prints one warning that starts with `Start did not complete. Resources were left in place.` It lists `Running`, `created/stopped`, and `unverified` services, and says agent forwarding and file sync remain active where established. It tells you to inspect `lando info` and `lando logs`, fix the reported error, then run `lando start`. A service Lando could not observe within one second is unverified, never stopped. A failure before any app resource changed says `Start did not complete. No app resources changed.` instead of that inventory. JSON and YAML output don't carry the warning; use `lando info --format=json`.

Fix the reported error, then run `lando start`. It converges rather than starting over: containers that match the plan are started as they are, only a container whose create config changed is recreated, an unfinished accelerated file-sync attempt resumes with its sessions, and healthy agent relays and host-proxy workers are reused. SSH and GPG forwarding stay enabled from the failed attempt until `lando stop` or `lando destroy`. Init steps and lifecycle hooks run again on every invocation, so write them to tolerate a rerun. `lando restart` and `lando rebuild` still stop first. If the start that follows fails, that failure does not remove routes.

If you'd rather shut the half-started app down, `lando stop` does that and `lando destroy` removes it; add `--volumes` to drop data volumes too.

`lando restart --service redis` (or `-s`, repeatable) restarts only those named services in place. Other services keep running and keep their host ports. Lando does not pull in dependencies. If a selected container is missing, or would have to be recreated for published-port, bind-source, network, or create-config drift, or because it has no `dev.lando.create-config` label, the command refuses with `ServiceRestartWouldRecreateError`. Create-config drift and a missing label use reason `config`. The error tells you to run `lando rebuild -s <name>`.

`lando rebuild -s <name>` recreates the named services and the services they depend on. They rejoin the host proxy the running app already uses, so `lando` and `open` inside a rebuilt `type: lando` service still reach your host, and the services you did not rebuild keep working. Running `lando start` again reuses that session, socket, and credentials while the proxy is healthy and your Lando roots, provider, and Lando install are unchanged. Every call runs a fresh host Lando process that reads current global config and installed plugins, so those changes need no proxy restart. The worker retains the host environment from the start that launched it. See [host callbacks](../subsystems/host-open.mdx) for output, cancellation, and URL-scheme policy.

If another process takes a selected service's host port after it stops, restart fails and leaves that service down. Check `lando info`, free the port or run `lando rebuild -s <name>`, then check `lando info` again.

Start, restart, and rebuild wait for every affected service's effective readiness before reporting success or running post-start steps. Authored `readiness:` controls the lifecycle gate; `healthcheck:` controls ongoing native health independently. Omitted readiness preserves a type's contributed check, such as MongoDB's stronger protocol ping, otherwise it falls back to native health. `readiness: false` blocks that fallback; `healthcheck: false` disables only native monitoring. Longer waits show readiness progress. The summary reports `ready` after a command gate passes, `running` without one, and `completed` for a successful `service_completed_successfully` dependency target. Readiness probes immediately; the start period is a grace period for failures, not a mandatory sleep. `lando info` observes state and configuration without rerunning probes or proving the last readiness gate.

An unsupervised service that exits fails the command non-zero with `ServiceNotReadyError`. Exhausted readiness fails every service, even one with a restart policy. Nothing is removed: diagnose with `lando logs -s <service>` and `lando info`, fix the service or its effective readiness configuration, then run `lando start` again. With `restart: always` or `unless-stopped`, an exit or observed restart produces a warning and a `restarting` row. `on-failure` does that only for a non-zero exit; exit 0 still fails readiness. Completion jobs must exit 0 regardless of restart policy.

If the provider cannot inspect a service, the reason is `inspect-failed`: run `lando doctor` to restore the provider. That failure never counts as a supervised restart. Global services use `lando global:logs -s <service>` and `lando global:start`; failed groups keep their established resources and published routes, while independent ready groups stay applied. Scratch start and `lando run` also wait for readiness, but failed or interrupted acquisition cleans up unless you passed `scratch:start --keep-on-failure`. URL-scan warnings still do not fail start.

Pressing Ctrl-C at any point stops the start, cancels in-flight healthchecks and build steps, and leaves everything already established in place. The command still exits as interrupted.


## Fix an image pull failure

Read the engine reason after the HTTP status in the pull error. A blocked registry,
missing image tag, or registry connection failure needs a registry or network fix,
not a runtime reinstall. Check the image reference and the container engine's
registry policy, then retry once registry access works.

For authentication failures, follow the error's credential remediation. Stale
credentials can affect public images too. Clear the affected registry's stale
credentials with the engine's logout command or remove its stale `auths` entry,
then authenticate again if the registry requires it.

Use `lando start --format=json` to inspect the tagged error and remediation.
Already-pulled images can still work without registry access; see
[Work offline](../config/offline-dev.mdx).

## Wait for another command to finish

`start`, `stop`, `restart`, `rebuild`, and `destroy` take a per-app advisory lock so two processes cannot apply provider state at the same time. A second command waits and prints that another Lando command holds the app lock. After two minutes it fails. Set `LANDO_APP_LOCK_TIMEOUT_MS` (milliseconds) to wait longer or shorter.

Read-only commands (`info`, `logs`, `app:config:lint`) do not take the lock.

Lando reclaims a lock left by a killed command without printing a wait message. You don't need to delete the lock file.

User apps share a mutation lock by canonical (realpath) app root, so changing `name:` in the same folder does not bypass a running command's lock. Scratch apps use their id plus canonical root because they can share a user app's folder. If you move the app directory while a mutate is running, a command against the new path sees a different key and does not wait on the first lock.

A mutating command that shells out to another `lando` mutate on the same app reuses the lock it already holds. It does not deadlock.

## Tear down

`destroy` deletes this app's containers and networks. Named volumes stay unless you pass `--volumes` or `--purge`.
Run it again with `--volumes` when you want those named volumes gone; Lando removes them from what the provider
still holds, and reports `unchanged` when there is nothing left to remove.

Snapshots stay with plain `destroy` and `--volumes`. **`--purge` also deletes this folder's catalogued snapshots and their provider-stored data**, even when an earlier destroy left only ownership inventory. Selection uses the volume owner's canonical app root, not the app name, so another worktree's snapshots stay untouched. Native data is removed through the provider that recorded each snapshot; a failed deletion leaves its catalog entry available for retry.

```sh
lando destroy -y
```

`-y` skips the confirmation prompt.

`pre-destroy` fires before anything is removed, and `post-destroy` only after everything, leftovers included, is gone. When Lando finds no trace of the app, destroy reports `unchanged` and fires neither.

If you've deleted or moved app folders before tearing them down, inspect their
leftovers with `lando apps:gc`. `lando apps:gc --prune` asks once before cleaning
up all reported roots. The prompt lists observed containers and volumes for each
root, marks which categories are kept or deleted, and includes the completed
start-journal sweep. Before the prompt, Lando starts any idle runtime that holds
reported resources, so the prompt lists its containers and volumes; reporting
without `--prune` never starts a runtime. Snapshots are not inventoried in this
preview. Lando revalidates roots and ownership before
deleting anything; changed evidence is retained for another review.
If the report says Lando cannot remove a provider's file-sync copies of a deleted
app yet, run `lando apps:gc --prune` without `--volumes`. It removes everything
else selected by your flags and keeps data volumes, file-sync copies, and their
ownership journals. Requesting `--volumes` fails that root before deletion.
Otherwise, add `--volumes` to delete data volumes and file-sync copies
of app files; add `--purge-caches` to delete caches. Data you keep by leaving off
`--volumes` is listed in the result. A failed root doesn't prevent the others from
being cleaned up, but makes the command exit nonzero.

```sh
lando apps:gc
lando apps:gc --prune --volumes
```

`lando doctor` points missing-folder findings at this command. To clean up just
one root, use its old path:
`--root` refuses folders that still exist; run `lando destroy` from inside those
folders instead. `--volumes` deletes the app's retained data, so use it only when
you no longer need that data.

```sh
lando destroy --root <path> --volumes
```

`poweroff` reaches beyond this app. Run it only when you mean to stop every app. `--keep-global` leaves shared host services such as the proxy up. `--keep-scratch` leaves scratch apps up. The next `lando start` brings back the global services that app uses, including Traefik and the SSH agent sidecar.

When the managed runtime is positively identified as idle, `lando stop` finishes the app's host-side cleanup without starting it and reports that the runtime is idle and nothing was running. Its `:host` event steps still run; steps that would run in a service container are skipped with a notice. `lando destroy` starts or repairs the managed runtime holding the app's resources before checking and removing them, including when status is unknown after a crash, `wsl --terminate`, or an upgrade. `lando destroy --root` and `lando apps:gc --prune` prepare it the same way. If preparation fails, cleanup reports that error. Normal data-retention rules still apply.

On macOS and Windows, an absent API and a managed machine inspected as stopped establish idle. On Linux and WSL, Lando's shutdown receipt establishes idle after a quiescent `poweroff` or when it comes from an earlier boot, provided the API is absent and no managed processes match. Each runtime launch invalidates that evidence first. Without valid receipt evidence, `lando list` reports `unknown` and stop fails closed; process observations alone cannot prove workloads stopped. Observation and stop never launch the runtime.

To stop everything Lando is running:

```sh
lando list
lando poweroff -y
```

`lando list` keeps known apps in the inventory after they stop. Its status comes
from runtime discovery, not the saved plan:

| Status | Meaning |
| --- | --- |
| `active` | At least one container for this app is running. This does not mean every service is healthy. |
| `stopped` | The app's provider answered discovery with no running containers, or an absent endpoint and stopped managed machine establish idle on macOS or Windows. |
| `unknown` | Lando could not observe the provider or establish that it runs no workloads. Read failures and an unresponsive live runtime remain unknown. |

Use `lando list --format=json` for the same `status` on each entry in `result.apps`.
`--status` keeps only matching rows after that one discovery pass. Repeat it to
keep more than one value: `lando list --status=active --status=stopped`.
`--path` matches an existing directory and apps beneath it, resolving relative
paths against your current directory (the session directory in MCP). Use `.`,
`./drupal`, `~/projects`, or an absolute path; symlinks work too. A bare word
like `drupal` matches root substrings even if that folder exists. Nonexistent
paths also fall back to substring matching.
The same `--status` and `--path` filters apply to the table, JSON, and MCP
results. `running` is not a status; the command rejects it. A `--status` or
`--path` filter that matches nothing prints `No Lando apps match the filters.`

The service list includes saved service names; it is not a list of running services.
The table adds `(stale)` when the recorded root no longer exists; JSON reports
that separately as `stale: true`.
Pruning also requires the provider to confirm that no matching containers or
volumes remain through a successful resource listing. An idle runtime proves nothing is running, but can still hold stopped containers and volumes; it never authorizes pruning. Remove those exact stale records with:

```sh
lando list --prune
```

Pruning removes only the applied-plan and directory-cache records reported by
the command. Missing or unreadable provider state is not enough evidence to
delete a record.
The `Pruned N` line ignores `--status` and `--path`; it counts every pruned
record, not the filtered table.

## Jump to an app folder

Add this function to your bash, dash, or zsh configuration, then run
`lando_cd myapp`. It checks for a single nonempty root before changing folders.

```sh
lando_cd() {
  _lando_cd_root=$(command lando list --jq ".result.apps[] | select(.appName==\"$1\") | .appRoot") || {
    _lando_cd_status=$?
    echo "lando list --jq failed for $1" >&2
    return $_lando_cd_status
  }
  [ -n "$_lando_cd_root" ] && [ "$_lando_cd_root" != "null" ] || { echo "no app root for $1" >&2; return 1; }
  case "$_lando_cd_root" in
    *'
'*)
      echo "multiple apps named $1" >&2
      echo "disambiguate with lando list --path" >&2
      return 1
      ;;
  esac
  cd -- "$_lando_cd_root"
}
```

Use a name without quotes or backslashes, which have special meaning in jq.
For duplicate names, pass the folder you already know to `lando list --path`.
Container-only discoveries may have no saved root.
