# Open a shell in a service

Run `lando ssh` from your app directory to open a login shell in the primary running service:

```sh
lando ssh
```

Lando starts `bash -l` if bash is on the container's `PATH`; otherwise, it starts `sh -l`. It runs the shell through `app:exec` and allocates a TTY when your stdin is a terminal.

Commands you type in that shell run inside the service, not on your host.

## Keep the service `PATH`

Distribution login profiles, such as `/etc/profile` on Debian and Alpine, reset `PATH`. Lando puts it back: a login shell starts from the `PATH` the service runs with, which is the image's `PATH` or your `environment.PATH`, then appends any directories the profiles added that it doesn't already list. `go` in the stock Go image and `bundle` in the stock Ruby image work in `lando ssh` the same way they do in `lando exec`. Files that run later, such as your `~/.bash_profile`, can still put directories in front.

This holds for every login shell in the service: `lando ssh`, `lando shell --service`, and a `bash -l` or `sh -l` you start yourself. Take this Alpine service with its own `PATH`:

```yaml
services:
  tools:
    type: compose
    image: alpine:3.20
    command: sleep infinity
    environment:
      PATH: /opt/tools/bin:/usr/local/bin:/usr/bin:/bin
```

A login shell keeps that `PATH` first, then adds the directories Alpine's profile wanted:

```sh
lando ssh --service tools -- sh -lc 'printenv PATH'
```

```text
/opt/tools/bin:/usr/local/bin:/usr/bin:/bin:/usr/local/sbin:/usr/sbin:/sbin
```

Lando does this with a small read-only file it mounts at `/etc/profile.d/zz-lando-service-path.sh`, which runs the current version of the script from Lando's helper directory. An updated Lando reaches running services at their next login, without recreating them. If your service binds its own `/etc/profile.d` or `/etc`, Lando keeps your mount and leaves the file out, so login shells use whatever `PATH` the image's profiles set.

## Pick a service or user

The primary service is the default target.

```sh
lando ssh --service db
lando ssh --user www-data
```

Pass a command instead of the default shell:

```sh
lando ssh -- ls -la
lando ssh --service db -- sh -c 'echo $HOSTNAME'
```

Lando reads its own flags (`--service`, `--user`, `--no-history`) before the command. Everything after `--` goes to the command unchanged. Without `--`, the command starts at the first word that is not one of those flags, and every token from there on is the command's, including flags such as `--help` and `--format`: `lando ssh ls --help` shows `ls` help, while `lando ssh --help` shows Lando's. An unknown flag in front of the command fails with `UnknownCliFlagError` before anything runs, so the Lando 3 spelling `lando ssh -c "echo hi"` tells you to put the command after `--` instead.

To leave shell and common client history off disk for one session, pass `--no-history`. See [Keep shell and client history across rebuilds](../tooling/lando-shell.mdx#keep-shell-and-client-history-across-rebuilds).

Pipe a script in, and the shell runs it without a terminal, then exits at the end of the input:

```sh
lando ssh < setup.sh
```

Interrupting a non-terminal `lando ssh -- <command>` with `SIGINT` or `SIGTERM` stops the command inside the service and everything it started, then exits `130` or `143`. See [Interrupt a command](./exec.mdx#interrupt-a-command).

## SSH identities

By default the bundled SSH-agent sidecar loads keys from the host `~/.ssh` directory (`id_rsa`, `id_ed25519`, and the other `ssh-add` defaults). Passphrase-protected keys are skipped. Every service sees the agent at `SSH_AUTH_SOCK=/run/lando/ssh-agent/agent.sock`.

To use your own agent instead (1Password, YubiKey, gpg-agent), set `sshAgent.sidecar: false` in the Landofile or global config. The host agent is forwarded through a per-app relay and signs on the host. See [Use your host SSH agent](../subsystems/ssh-host-agent.mdx).

`lando ssh --sidecar` and `lando ssh --subsystem` are not supported.

A Landofile `keys:` list is not a canonical key.

## Host keys

When SSH agent forwarding is active, your services trust the hosts in your host `~/.ssh/known_hosts`. If that path is a regular file, Lando binds it read-only at `/etc/ssh/ssh_known_hosts` in each eligible service, in both sidecar and host-agent modes. Git and Composer can use those trusted hosts without a host-key prompt, including in non-interactive runs and services with `home: false`. OpenSSH also checks the service user's own known hosts, so you can still add hosts there. Lando never copies or rewrites your host file.

If you create or replace the host file after the app started, run `lando start` from your app directory. Lando recreates the affected service to mount the current file, including after an atomic replacement by `ssh-keygen -R` or a symlink retarget. Appending entries to the existing file keeps the same bind and does not require a restart. If the file disappears or becomes inaccessible, the next start omits the bind. The host file must be readable by the service user; OpenSSH creates it with mode `0644`.

If your service mounts its own `/etc/ssh/ssh_known_hosts` or an ancestor directory such as `/etc/ssh`, `/etc`, or `/`, Lando keeps your mount instead. SSH host-key verification remains enabled.
