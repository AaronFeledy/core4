# Run the Drupal CMS recipe

Create a local Drupal CMS site with PHP and MariaDB. Run these commands from your host terminal:

```sh
lando init --recipe drupal-cms --name=drupal-cms-demo --yes
cd drupal-cms-demo
lando start
```

Init writes `.lando.yml` and `.lando/php/drupal-cms.ini` in `drupal-cms-demo/`. `--yes` keeps PHP 8.4, Apache, MariaDB 11.4, Composer 2, and webroot `web`.

If something else owns 80 or 443, Lando falls back to the next free port, starting with `:8080` / `:8443`. `lando info` shows the URL it picked.

## Install Drupal CMS

The first `lando start` downloads Drupal CMS 2, project-local Drush, and the PHP lint tools. Install the site with the starter recipe:

```sh
lando drupal-cms-install
```

`lando drupal-cms-install` runs project-local Drush with the recipe's database credentials. Drush prints the admin username and a generated password when install finishes. The generated PHP ini sets a 512M memory limit for Drush and web requests.

To scaffold and install in `docroot/` instead of `web/`, pass `--answer=webroot=docroot` to `lando init`. For a new scaffold, use one directory name, not a nested path.

On Windows with accelerated project files, the install command gives the web server ownership of Drupal's public files so uploads and image styles work. To check access with webroot `docroot`:

{/* lando-lint: not-e2e Windows accelerated-files ownership check; CI does not run Mutagen install-time chown */}
```sh
lando exec --user www-data appserver -- test -w /app/docroot/sites/default/files
```

Then confirm the day-to-day tools:

```sh
lando drush --version
lando drush status
lando composer --version
lando mariadb -e 'SELECT 1 AS ok;'
```

Open the site with `lando open`, or print its URL with `lando open --print`. The front page and `/user/login` should both render with HTTP 200. On the default Apache stack, confirm that from inside `appserver`, independent of the proxy:

```sh
lando exec appserver -- curl --fail --silent --show-error --max-time 30 --output /dev/null --write-out '%{http_code}' http://127.0.0.1/
lando exec appserver -- curl --fail --silent --show-error --max-time 30 --output /dev/null --write-out '%{http_code}' http://127.0.0.1/user/login
```

Each prints `200`. Anything else means Drupal didn't render the page, so check `lando logs -s appserver`.

## See what the recipe writes

| Piece | What you get |
| --- | --- |
| `appserver` | `php:8.4`, `framework: drupal`, webroot `web`, Composer `2`, Apache on port `80`, depends on `database`, `.lando/php/drupal-cms.ini` at 512M, Git installed at build for the pinned SVG Image source |
| `database` | `type: mariadb:11.4` |
| Tooling | `lando drush`, `lando composer`, `lando phpcs`, `lando phpcbf`, `lando phpstan`, and `lando drupal-cms-install` on `appserver`, plus `lando mariadb` from the database service |

Routes use `{{ app.name }}.{{ proxy.defaultDomain }}` on HTTP and HTTPS. Pass `--answer=php=8.5`, `--answer=webserver=nginx`, `--answer=database=mysql:8.0`, or `--answer=database=postgres:16` when you want those instead.

Nginx answers add an `edge` service in front of `appserver` (`via: fpm`). Both webserver choices set `uploadDirs: [sites/*/files]` on the service serving PHP to keep code out of Drupal's uploads. For `mysql:8.0`, use `lando mysql` instead of `lando mariadb`. For `postgres:16`, use `lando psql` instead of `lando mariadb`.

Scaffold creates Drupal CMS in a private staging directory. Git is installed automatically in `appserver`. A first-priority package repository pins the upstream SVG Image security patch from [merge request 65](https://git.drupalcode.org/project/svg_image/-/merge_requests/65) at commit `c788b1e2f2be29f62c9812b2b0558472afa61d6d`. The declared `3.x-dev` build uses the fixed `enshrined/svg-sanitize` 1.0 release; it does not claim to be a tagged SVG Image release or disable security checks.

It also requires the `drupal_cms_starter` recipe that install uses, since `drupal/cms` no longer pulls it in. The scaffold verifies the package metadata and actual checkout, audits before and after installation, and runs Drupal's native hooks, including recipe unpacking. It keeps the pin in `composer.json` and `composer.lock` and checks again after the hooks. Any mismatch, audit failure, or install failure stops before anything reaches your app. Successful files are promoted without overwriting user content. Interrupted copies resume when you run `lando start` again; a completed site is left alone on later starts.

## Connect Drupal to the database

`lando drupal-cms-install` writes these into `<webroot>/sites/default/settings.php`, or `web/sites/default/settings.php` with the default webroot. Use the same values when you bring an existing project's settings. They cover MariaDB and `mysql:8.0` answers:

| Setting | Value |
| --- | --- |
| Host | `database` |
| Database | App name (here `drupal-cms-demo`) |
| User | `lando` |
| Password | `lando` |
| Port | `3306` |

Use the service key `database`, not `127.0.0.1` or `localhost`. Root password is generated; you don't need it for the site user.

For Postgres answers, host `database`, port `5432`, user `lando`, database the app name. The password is derived per app; `lando psql` opens a session without it.

## Log in and clear caches with Drush

```sh
lando drush user:login --no-browser
lando drush cache:rebuild
lando drush updatedb -y
lando drush config:export -y
```

`user:login` prints a one-time login link for the admin account. `lando drush` builds links from the current app URL, including a nondefault proxy port. To pin another URL, set `DRUSH_OPTIONS_URI` under `services.appserver.environment` and run `lando start`, or pass Drush `--uri` on one command.

`drush` is a wrapper task, so every flag after `lando drush` goes to Drush, including ones Lando also has, such as `--format`, `--debug`, and `--verbose`:

```sh
lando drush status --format=json
```

Drush gets `status --format=json` and prints its own JSON. Lando's flags go before the task name: `lando --format=json drush status` returns Lando's result envelope instead.

## Lint PHP

The first start installs Drupal Coder and PHPStan with its Drupal extension and writes `phpcs.xml.dist` and `phpstan.neon.dist` to the app root, so `lando phpcs`, `lando phpcbf`, and `lando phpstan` work as soon as start finishes. They check your code under `web/modules`, `web/themes`, and `web/profiles` and skip Drupal CMS's `contrib` directories. The tasks, config files, and defaults are the same as on the Drupal recipe; see [Lint PHP on the Drupal recipe](./drupal-workflow.mdx#lint-php).

## Import, export, and snapshot the database

`db:import` executes the dump's SQL in `database`; the dump determines which existing data is changed or replaced. Lando snapshots the volume first, and import asks before it runs. `--yes` answers for you:

```sh
lando db:export dump.sql.gz
lando db:import dump.sql.gz --yes
lando drush cache:rebuild
```

A `.gz` name gzips on export and gunzips on import. The recipe has one database service, so you don't need `--service`.

Take your own snapshot before a risky update, then roll back to it:

```sh
lando db:snapshot --label before-update
lando db:restore before-update --yes
```

`db:restore` takes the label or the id `lando db:snapshots` lists. Lando stops the database while it copies the volume, then starts it again.

## Change PHP settings

Edit `.lando/php/drupal-cms.ini`. It's mounted read-only into `appserver`, so a restart picks it up without a rebuild:

```ini
memory_limit = 1G
upload_max_filesize = 64M
post_max_size = 64M
```

```sh
lando restart
lando exec appserver -- php -r 'echo ini_get("memory_limit"), PHP_EOL;'
```

## Debug with Xdebug

Add `xdebug: true` under `services.appserver` in `.lando.yml`, then start:

```yaml
services:
  appserver:
    xdebug: true
```

```sh
lando start
lando xdebug status
```

Xdebug connects to your IDE on port `9003`. Map `/app` in the container to your project root. `lando xdebug on` and `lando xdebug off` toggle it without another rebuild.

## Capture outgoing mail

Add a Mailpit service next to `appserver`, then start and send a test message:

```yaml
services:
  inbox:
    type: mailpit
```

```sh
lando start
lando exec appserver -- php -r 'mail("you@example.test", "Mailpit check", "Hello from Drupal CMS");'
lando info
```

Start installs `msmtp` in `appserver` and points PHP's `sendmail_path` at `inbox`, so mail Drupal sends through PHP lands there. Open the `inbox` URL that `lando info` prints.

## Read logs and open a shell

```sh
lando logs -s appserver -f
lando logs -s database --tail 50
lando shell -s appserver
lando exec appserver -- php -v
```

`lando shell -s appserver` opens a login shell in the container. `lando exec` runs one command and exits.

## Compile theme assets

A contrib or custom theme with a Node-based build can use a Node sidecar;
no PHP extension provides npm. Add `node` next to `appserver`, point `lando npm` at the theme
with tooling `dir:`, then `lando npm install` and the theme's build script. See
[Compile PHP theme assets with Node](../services/node-theme-assets.mdx).

## Destroy the app

```sh
lando destroy -y
```

That removes containers and networks. Volumes stay unless you pass `--volumes` or `--purge`.
