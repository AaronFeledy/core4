# Run Symfony Messenger workers

Run `messenger:consume` in its own `worker` service next to the Symfony recipe's `appserver`, with Postgres as the queue. A container restart policy brings the consumer back after `messenger:stop-workers` or a crash.

This builds on [Run the Symfony recipe](./symfony-workflow.mdx). Run the commands from your host terminal. The app name below is `symfony-messenger`.

## Add a worker to the Symfony recipe

```sh
lando init --recipe symfony --name=symfony-messenger --yes
cd symfony-messenger
```

Init writes the service and tooling definitions, plus a `recipe:` block recording the selected options. Keep that block: `{{ recipe.php }}` reads its PHP option, which defaults to `8.4`.

Before the first start, merge these changes into `.lando.yml`. Add the `appMount` block to the existing `appserver` service and add the new `worker` service:

```yaml
services:
  appserver:
    appMount:
      target: /app
      includes:
        - vendor
  worker:
    type: "php:{{ recipe.php }}"
    via: cli
    framework: symfony
    command: "php bin/console messenger:consume async --time-limit=3600 -vv"
    restart: unless-stopped
    environment:
      DATABASE_URL: "postgresql://{{ url.encodeComponent(services.database.creds.user) }}:{{ url.encodeComponent(services.database.creds.password) }}@database:{{ services.database.port }}/{{ url.encodeComponent(services.database.creds.database) }}?serverVersion=16&charset=utf8"
    appMount:
      target: /app
      includes:
        - vendor
    dependsOn:
      database:
        condition: service_healthy
```

Each service keeps its own `vendor` directory unless you include it. These `includes` entries cancel that default exclusion, so both services use the project directory's `vendor`. `lando composer` runs inside `appserver`, not on your host; its files are visible to both services through the shared app mount. The worker gets the same `DATABASE_URL` the recipe gives `appserver`, built from the database's resolved credentials. `--time-limit=3600` asks the consumer to exit after an hour, once its current work finishes, and `unless-stopped` starts a fresh one.

Check the config and start the app:

```sh
lando app:config:lint
lando start
```

There's no `bin/console` yet, so the worker exits. Lando reports this supervised exit as a warning and a `restarting` worker row rather than failing start. An exhausted healthcheck still fails start regardless of restart policy. The restart policy keeps retrying; the consumer can run once Symfony, its dependencies, and the transport configuration are installed. Check `lando logs -s worker` while it retries.

## Install Symfony and Messenger

Install the skeleton as [Run the Symfony recipe](./symfony-workflow.mdx) shows, including moving `tmp-app` into the app root while keeping `.lando.yml`. The current stable skeleton selects Symfony 8.1 and requires PHP 8.4 or newer, matching this recipe's default. The command class below uses invokable commands and `#[Argument]`, available since Symfony 7.3.

From the app root, add Messenger with its Doctrine transport. The ORM pack supplies DoctrineBundle and the default database connection that the minimal skeleton lacks:

```sh
lando composer require symfony/messenger symfony/doctrine-messenger symfony/orm-pack --no-interaction
```

The Flex recipe writes `MESSENGER_TRANSPORT_DSN=doctrine://default?auto_setup=0` to `.env`, so messages go to a table in the recipe's Postgres database. The recipe's `cache` Redis service isn't used here: stock PHP services don't include the `redis` extension Symfony's Redis transport needs, and Doctrine runs on the `pdo_pgsql` driver they already ship.

Save this as `config/packages/messenger.yaml`:

```yaml nolint
framework:
    messenger:
        failure_transport: failed

        transports:
            async:
                dsn: '%env(MESSENGER_TRANSPORT_DSN)%'
                retry_strategy:
                    max_retries: 1
            failed: 'doctrine://default?queue_name=failed'

        routing:
            App\Message\SendPing: async
```

Create the queue tables:

```sh
lando console messenger:setup-transports
```

Check that it reports both `async` and `failed` as set up. They use different queues in the same `messenger_messages` table. With `auto_setup=0`, a worker polling before setup can report `relation "messenger_messages" does not exist` and restart. After setup, check the latest `lando logs -s worker` entries for `Consuming messages from transport "async"` without recurring database errors; an older banner alone doesn't prove the worker is healthy.

## Dispatch a message and watch it run

Create the source directories from the app root, then save the files below:

```sh
mkdir -p src/Message src/MessageHandler src/Command
```

Save this as `src/Message/SendPing.php`:

```php
<?php

namespace App\Message;

final class SendPing
{
    public function __construct(public readonly string $text) {}
}
```

Save this as `src/MessageHandler/SendPingHandler.php`:

```php
<?php

namespace App\MessageHandler;

use App\Message\SendPing;
use Psr\Log\LoggerInterface;
use Symfony\Component\Messenger\Attribute\AsMessageHandler;

#[AsMessageHandler]
final class SendPingHandler
{
    public function __construct(private LoggerInterface $logger) {}

    public function __invoke(SendPing $message): void
    {
        if ($message->text === 'boom') {
            throw new \RuntimeException('ping exploded');
        }

        $this->logger->warning('ping handled: {text}', ['text' => $message->text]);
    }
}
```

Save this as `src/Command/PingCommand.php` so you can queue a message from the console:

```php
<?php

namespace App\Command;

use App\Message\SendPing;
use Symfony\Component\Console\Attribute\Argument;
use Symfony\Component\Console\Attribute\AsCommand;
use Symfony\Component\Console\Command\Command;
use Symfony\Component\Messenger\MessageBusInterface;

#[AsCommand(name: 'app:ping', description: 'Queue a SendPing message.')]
final class PingCommand
{
    public function __construct(private MessageBusInterface $bus) {}

    public function __invoke(#[Argument] string $text): int
    {
        $this->bus->dispatch(new SendPing($text));

        return Command::SUCCESS;
    }
}
```

The minimal skeleton's logger writes to stderr without requiring Monolog. The worker's `-vv` sets Console's `SHELL_VERBOSITY` to `2`, enabling the warning from this handler and Messenger's info-level success message.

The worker loaded the old code when it started. Tell it to stop, then wait for the restart. `messenger:stop-workers` signals through Symfony's app cache. Both services mount the same project at `/app`, including `var/`, which Lando doesn't exclude by default, so they share the default filesystem cache:

```sh
lando console messenger:stop-workers
lando logs -s worker --follow
```

Wait for a new `Consuming messages from transport "async"` entry, then press Ctrl-C. Now dispatch:

```sh
lando console app:ping 'hello from console'
lando logs -s worker --follow
```

Wait for `ping handled: hello from console` and `handled successfully`, then press Ctrl-C. Dispatch queues the message without waiting for the worker to handle it.

## Read and clear failed messages

```sh
lando console app:ping boom
lando logs -s worker --follow
```

Wait for `Removing from transport after 1 retries`, then press Ctrl-C and list the failure:

```sh
lando console messenger:failed:show
```

Check that the table lists `App\Message\SendPing` with `ping exploded` and an `Id`. To retry it after fixing the handler and restarting the worker, use `lando console messenger:failed:retry MESSAGE_ID --force`, replacing `MESSAGE_ID` with that id. The bare retry command prompts interactively; specifying the id and `--force` also works without an interactive terminal.

Alternatively, delete this deliberately failing message. Replace `MESSAGE_ID` below with its id. This deletes the stored message:

```sh
lando console messenger:failed:remove MESSAGE_ID --force
lando console messenger:stats
```

Check that both `async` and `failed` show a count of `0`.

## Fix the usual failures

| You see | Fix |
| --- | --- |
| `Could not open input file: bin/console` in the worker log | Symfony isn't installed yet. Install it; the worker restarts on its own. |
| `relation "messenger_messages" does not exist` | Run `lando console messenger:setup-transports`. |
| The worker runs old handler code | Run `lando console messenger:stop-workers` and wait for the new `Consuming messages` entry. |
| `worker` stays `stopped` after `messenger:stop-workers` | The service has no `restart: unless-stopped`. Add it and run `lando start`. |
| Class not found in the worker but fine in `lando console` | The worker isn't sharing `vendor`. Add `includes: [vendor]` to both services' `appMount` and run `lando start`. |

## Tear down

This removes containers and networks. Volumes, including the queue tables, stay unless you pass `--volumes` or `--purge`; those flags delete data. `--purge` also deletes the app's database snapshots. The shared project files remain on your host.

```sh
lando destroy -y
```
