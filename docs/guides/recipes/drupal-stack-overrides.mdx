# Drupal stack overrides

The `drupal` recipe's prompt surface is narrow: an app name, a PHP version
prompt that only offers `8.3`, and a database prompt that only offers
`mariadb` or `postgres`. These overrides below are not recipe prompts —
they are ordinary Landofile edits you make to the generated `.lando.yml`
after `lando init`, then apply with `lando rebuild -y`.

## What the recipe actually generates

`lando init --recipe drupal` writes a fixed shape: an Apache-backed
`appserver` on `php:8.3`, webroot `/app/web`, `allowOverride: true`, a
`database` service, and `drush`/`composer` tooling tasks that call
project-local `vendor/bin/drush` and `composer`.

## Running two database services side by side

Nothing pins the app to one database service name. Author a second,
explicit database service — say a legacy `database-legacy` on `mysql`
alongside the default `mariadb` `database` — and add it to the
appserver's `dependsOn`. This is a manual second-service Landofile, not a

## Drush URI and a moved webroot

The generated `drush` tooling task calls project-local `vendor/bin/drush`
with no `DRUSH_OPTIONS_URI` set. Add it under
`services.appserver.environment`, and if you also move the webroot away
from the default `/app/web` (say to `/app/docroot`), Drush's project-local
path in `tooling.drush.cmds` doesn't need to change — `vendor/bin/drush`
lives at the Composer project root, not under the webroot:

## Bind-mounting custom PHP and database config

There's no recipe shorthand for a custom `php.ini` or database config
file, and the default `provider-lando` can't realize Compose `configs:`.
Bind-mount host config files with `volumes:` instead — one entry on
`appserver` for PHP, one on `database` for MariaDB:

  </Scenario>

Applying any of these edits to a running app still needs `lando rebuild -y`
to recreate the affected containers — none of that requires live Drupal or
database traffic to prove the Landofile is correct, so every scenario
above stops at lint and inspect.
