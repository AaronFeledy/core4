# LAMP stack variants

The `lamp` recipe's prompt surface is narrow: an app name and a PHP version
prompt that only offers `8.2` or `8.3`, defaulting to `8.3`. There is no
prompt for database engine, database version, Composer version, or
webroot. The variants below are not recipe prompts — they are ordinary
Landofile edits you make to the generated `.lando.yml` after `lando init`,
then apply with `lando rebuild -y`.

## What the recipe actually generates

`lando init --recipe lamp` writes a fixed shape: an Apache-backed
`appserver` on `php:8.3` (or `8.2` if chosen), `framework: none`, port
`80`, a `database` service pinned to `type: mariadb` with no version, and
`composer`/`php` tooling tasks that call the project-local binaries
directly.

## Replacing MariaDB with MySQL

Nothing pins the `database` service's type. Swap `type: mariadb` for
`type: mysql` and pin an exact tag with `image:` — for example
`mysql:8.4` — where the recipe prompt offers neither a database choice
nor a version option at all. This is the same Landofile-edit-plus-rebuild
mechanism the [switching-databases](../services/switching-databases.mdx)
guide walks in detail, including the data-migration caveat that a rebuild
does not carry old data into the new engine.

## Replacing MariaDB with PostgreSQL

Swap `type: mariadb` for `type: postgres` the same way, again pinning a
version with `image:` — here `postgres:15`. The default PHP image already
compiles the `pdo_pgsql` extension, so nothing else on the `appserver`
side needs to change for the Postgres driver to be available.

## Running two database services side by side

Nothing pins the app to one database service name either. Author a
second, explicit database service — say a legacy `database-legacy` on
`mysql` alongside the default `mariadb` `database` — and add it to the
appserver's `dependsOn`. This is a manual second-service Landofile, not a
recipe multi-database prompt.

## Bind-mounting custom PHP and database config

There's no recipe shorthand for a custom `php.ini` or database config
file, and the default `provider-lando` can't realize Compose `configs:`.
Bind-mount host config files with `volumes:` instead — one entry on
`appserver` targeting the PHP `conf.d` drop-in directory, one on
`database` targeting the MariaDB image's own `conf.d` directory, the same
upstream-image convention the php-customization guide uses for the PHP
side alone.

## Matching PHP, Composer, and database tooling aliases

The recipe already generates `composer` and `php` tooling tasks against
`appserver`. Add a matching client alias against whichever `database`
service type you land on — `mariadb`, `mysql`, or `psql` — so
`lando <alias>` opens the right client without the reader having to
remember the container's service name:

| Database type | Client alias |
| --- | --- |
| `mariadb` | `lando mariadb` |
| `mysql` | `lando mysql` |
| `postgres` | `lando psql` |

Interactive client sessions are covered in each engine's own service guide
CLI section.

Applying any of these edits to a running app still needs `lando rebuild
-y` to recreate the affected containers — none of that requires a live
database connection or PHP request to prove the Landofile is correct, so
every scenario below stops at lint and inspect.
