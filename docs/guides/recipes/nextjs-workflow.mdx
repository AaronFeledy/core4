# Run the Next.js recipe

Create a Next.js environment with Postgres, then scaffold and run the application inside `web`. Run these commands from your host terminal.

```sh
lando init --recipe nextjs --name=nextjs-demo --yes
cd nextjs-demo
lando start
```

`--yes` skips prompts. Defaults are Node lts, Postgres, and `NEXTAUTH_PROVIDER: none`. First start builds `web` and `database`. If host ports 80 or 443 are already taken, `lando info` URLs may use fallback ports such as `:8080` and `:8443`.

## Scaffold Next.js, then run it

With the app running, generate a fresh Next.js project into the app root:

```sh
lando nextjs-scaffold
```

That runs `create-next-app@16.4.0` inside `web`, generates in a temp directory, then copies the result into the app root without overwriting `.lando.yml` or anything else you already have. It finishes with `npm install` in `/app`. Dependencies live in the service's `node_modules` volume, mounted at `/app/node_modules`, not in your host tree. You can work in the app root once the scaffold completes.

The generated project is the empty TypeScript App Router template: ESLint on, Tailwind off, no `src/` directory, `@/*` import alias, Turbopack.

Confirm tooling:

```sh
lando next --version
lando npm --version
```

Start the development server:

```sh
lando next dev
```

Next listens on all interfaces by default, and the recipe sets `PORT=3000`. The `Local: http://localhost:3000` line in Next's output is a display URL, not a loopback-only bind. The command stays in the foreground; `lando start` brings up the services but doesn't launch Next. Open the URL `lando info` prints while the development server is running.

### Already have a Next.js project?

Skip the scaffold and use the package manager your project declares. If
`package.json` declares none, or declares npm, install and run with the recipe
tooling:

```sh
lando npm install
lando next dev
```

### Projects that use Yarn or pnpm

The scaffold installs with npm. A project you checked out may declare Yarn or
pnpm instead. Declare the exact release once in `package.json`, for example
`"packageManager": "pnpm@9.15.0"`. The `web` service installs that release
when Lando builds its image on `lando start`, and the commands follow it. You
don't declare it again in the Landofile, and you don't run Corepack.

| `package.json` declares | Install | Run Next |
| --- | --- | --- |
| npm, or nothing | `lando npm install` | `lando next dev` |
| pnpm | `lando pnpm install` | `lando next dev` |
| Yarn | `lando yarn install` | `lando next dev` |

For pnpm, start the app and check the release:

```sh
lando start
lando pnpm --version
```

That prints the pinned version and needs no network. Then install
dependencies, which does need the network, and start the development server:

```sh
lando pnpm install
lando next dev
```

`lando next` runs the `next` binary your project installed, through the
project's own manager: `pnpm exec`, `yarn run`, or `npm exec`. It never
downloads Next for you, so run the install first. For Yarn Plug'n'Play, see
[how Lando handles the linker and dependency directory](../services/node.mdx#use-yarn-plugnplay).

In a pnpm project there is no `lando npm`, and in a Yarn project there is
neither `lando npm` nor `lando pnpm`. See
[Use your project's package manager](../services/node.mdx#use-your-projects-package-manager).

### When the scaffold refuses or fails

- Any existing `package.json` in the app root stops the scaffold before it generates anything. That includes a second run. Install with your project's package manager instead, as described above.
- If a generated top-level file collides with one you already have, the command stops and names the first conflicting path. Nothing is copied. Move or remove yours, then run it again.
- If `npm install` fails, the generated sources stay. Fix the npm error, then run `lando npm install`. Don't scaffold again.

Prefer Node 22, no database, or NextAuth at init?

```sh
lando init --recipe nextjs --name=nextjs-alt --yes \
  --answer=node=22 \
  --answer=database=none \
  --answer=auth=nextauth
cd nextjs-alt
```

## See what the recipe writes

Init writes `.lando.yml` only and downloads nothing. The Next.js app itself comes from `lando nextjs-scaffold` after start, or from the project you already have.

| Piece | What you get |
| --- | --- |
| `web` | `node:lts` (or `node:22` when you pass `--answer=node=22`), port `3000`, `NEXTAUTH_PROVIDER` set from the auth answer |
| `database` | `type: postgres` by default; `mariadb` with `--answer=database=mariadb`; omitted with `--answer=database=none` |
| Tooling | `lando next` and `lando nextjs-scaffold` on `web`. The `web` service adds `lando npm` and `lando npx`, or the Yarn or pnpm commands when `package.json` declares one of those |

Routes use `{{ app.name }}.{{ proxy.defaultDomain }}` on HTTP and HTTPS. Auth answers (`none`, `nextauth`, `clerk`) only set the `NEXTAUTH_PROVIDER` env hint. Install and configure the helper yourself.

## Talk to Postgres

Default recipe Postgres uses the app network hostname `database`:

| Setting | Value |
| --- | --- |
| Host | `database` |
| Port | `5432` |
| Database | app name (here `nextjs-demo`) |
| User | `lando` |
| Password | generated when omitted; read it with `{{ services.database.creds.password }}` |

The recipe doesn't set a connection URL on `web`. Add one under `web.environment` and Lando fills the credentials from `database`:

```yaml
services:
  web:
    environment:
      DATABASE_URL: "postgresql://{{ services.database.creds.user }}:{{ services.database.creds.password }}@database:5432/{{ services.database.creds.database }}"
```

Then `lando start`. Read `process.env.DATABASE_URL` in your app code, so the password never lands in a committed file. `lando info` redacts it. See [Plan-time service credentials](../landofile/expressions.mdx#plan-time-service-credentials).

Query it with the `psql` tooling. It logs in with the service credentials, so you never type the password:

```sh
lando psql -c 'SELECT version();'
```

## Destroy without surprises

```sh
lando destroy -y
```

That removes containers and networks. Volumes stay unless you pass `--volumes` or `--purge`.
