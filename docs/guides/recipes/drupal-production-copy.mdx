# Copy a production Drupal database into Lando

A production database carries real users' email addresses and password hashes, plus whatever your own modules store. Keep the raw dump out of your project, import it with `lando db:import`, and scrub it with `lando drush sql:sanitize` before you run updates, log in, or share it.

This page starts from a site on the Drupal recipe, such as the one [Run the Drupal recipe](./drupal-workflow.mdx) builds, on Drupal 10 or 11. Run the `lando` commands from the app directory on your host.

## Get a dump

When your team has a vetted export that was sanitized before it left production, use it instead of a raw dump. Copy it to a private directory as the next section shows, and still run the scrub and check steps.

Without one, dump the database on the production server from the site's project root:

```sh
umask 077
vendor/bin/drush sql:dump --gzip --structure-tables-list='cache,cache_*,sessions,watchdog' --result-file=/tmp/prod.sql
```

`umask 077` makes the dump readable only by your server user. `--gzip` compresses it and adds `.gz` to the name, so Drush writes `/tmp/prod.sql.gz`. `--structure-tables-list` keeps the table definitions for caches, sessions, and the log but skips their rows, which you don't need locally.

## Copy the raw dump to a private directory

On your host, make a temporary directory outside your project, copy the dump into it, and delete the server copy right away:

```sh
dump_dir=$(mktemp -d)
scp prod.example.com:/tmp/prod.sql.gz "$dump_dir/" && ssh prod.example.com rm /tmp/prod.sql.gz
```

Replace `prod.example.com` with your server's SSH host. `mktemp -d` creates a directory only your user can open, under your system's temp directory, so the dump never lands in the checkout, in git, or in the `/app` mount the containers see. The host copy and import commands need a POSIX shell in the same terminal session so `$dump_dir` stays set.

## Catch outgoing mail first

Add a Mailpit service before the import, so mail Drupal sends through PHP lands in a local inbox:

```sh
lando app:config:set services.inbox '{"type":"mailpit"}' --type json
lando start
```

Start points PHP's `sendmail_path` in `appserver` at `inbox`. See [Capture outgoing mail](./drupal-workflow.mdx#capture-outgoing-mail) for the inbox URL.

## Snapshot, then import

Take a snapshot of your local database, then import the dump by its absolute path:

```sh
lando db:snapshot --label before-prod
lando db:import "$dump_dir/prod.sql.gz" --yes && rm -rf "$dump_dir"
```

`db:import` reads the file from your host, gunzips it, and runs it in the recipe's `database` service. A Drush dump drops and recreates every table it contains, so your local content in those tables is replaced. `--yes` answers the confirmation prompt. Delete the directory as soon as the import succeeds. The database now holds the data, so the raw file has no further use.

## Point mail and cron at local settings

The copy also brings production settings that live in the database. Switch those first, before `sql:sanitize`, `updatedb`, or a login runs Drupal code that could mail a real user or call a production service:

```sh
lando drush config:get system.mail interface.default
lando drush config:set system.mail interface.default php_mail --yes
lando drush config:set automated_cron.settings interval 0 --yes
```

`config:get` shows the mail plugin production used. Anything other than `php_mail`, such as `symfony_mailer` with an SMTP server in `mailer_dsn`, can send through a real mail server. Automated Cron skips its run when `interval` is `0`. Check your own modules' settings for production API keys, endpoints, and accounts the same way, and switch them to test values or turn them off.

## Scrub user emails and passwords

```sh
lando drush sql:sanitize --yes
lando drush sql:query "SELECT uid, mail FROM users_field_data"
```

Drush lists the operations before it runs them. By default it replaces every user's email with `user+<uid>@localhost.localdomain` and every password with the same random one, so no production password works. The query shows the new addresses, for example `user+1@localhost.localdomain` for the first account.

## Check what Drush doesn't scrub

`sql:sanitize` only cleans user data that Drush and your installed modules tell it about. A table your own code creates keeps its rows. For example, a table of contact form leads:

```sh
lando drush sql:query "SELECT COUNT(*) FROM app_leads"
lando drush sql:query "TRUNCATE app_leads"
```

Replace `app_leads` with your own tables, and clear or mask every one that holds personal data.

## Update, then log in

```sh
lando drush updatedb --yes
lando drush cache:rebuild
lando drush user:login --name=admin
```

`updatedb` runs any database updates your local code has that production hasn't applied yet. It prints `No pending updates.` when the two match.

Nobody knows the new password, so `user:login` prints a one-time login link instead. It starts with your app's URL, including the fallback port, such as `:8443`, when Lando picked one, followed by `/user/reset/1/`. Open it in your browser to land on the admin account's edit page. Replace `admin` with the production admin's user name.

## Share the scrubbed copy

Export the database only after the scrub and checks:

```sh
lando db:export drupal-scrubbed.sql.gz
```

The file lands in your app directory. Keep it out of git and send it the same way you'd send any other private file.

## Go back to your local database

```sh
lando db:restore before-prod --yes
```

`db:restore` brings back the snapshot you took before the import. Lando stops the database while it copies the volume, then starts it again. Labels don't have to be unique, so if you've run this page before, the restore fails with `SnapshotAmbiguousError` and lists the matching ids, newest first. Pass the newest id instead of the label.

Like every restore, `db:restore` first saves a recovery snapshot of the database you're leaving, which now holds the scrubbed copy. `lando db:snapshots` lists it with recovery reason `restore`. Lando keeps the newest three recovery snapshots for each database, so later imports, resets, and restores push it out.
