# Copy a production Drupal database into Lando

Debugging with real content beats guessing, but a production database also carries real users' email addresses and password hashes. Dump it with Drush on the server, import it with `lando db:import`, then scrub it with `lando drush sql:sanitize` before you do anything else.

This page starts from a site on the Drupal recipe, such as the one [Run the Drupal recipe](./drupal-workflow.mdx) builds. Run the `lando` commands from the app directory on your host.

## Dump the production database

On the production server, run the site's own Drush from its project root:

```sh
vendor/bin/drush sql:dump --gzip --structure-tables-list='cache,cache_*,sessions,watchdog' --result-file=/tmp/prod.sql
```

`--gzip` compresses the dump and adds `.gz` to the name, so Drush writes `/tmp/prod.sql.gz`. `--structure-tables-list` keeps the table definitions for caches, sessions, and the log but skips their rows, which you don't need locally and which makes the dump smaller.

Copy `/tmp/prod.sql.gz` from the server into your app directory, next to `.lando.yml`, then delete it from the server's `/tmp`.

## Snapshot, then import

Take a snapshot of your local database first, so you can go back to it:

```sh
lando db:snapshot --label before-prod
lando db:import prod.sql.gz --yes
```

`db:import` gunzips the `.gz` file and runs it in the recipe's `database` service. A Drush dump drops and recreates every table it contains, so your local content in those tables is replaced. `--yes` answers the confirmation prompt.

Bring the schema up to your local code and clear caches:

```sh
lando drush updatedb --yes
lando drush cache:rebuild
```

`updatedb` runs any database updates your local code has that production hasn't applied yet. It prints `No pending updates.` when the two match.

## Scrub user emails and passwords

```sh
lando drush sql:sanitize --yes
lando drush sql:query "SELECT uid, mail FROM users_field_data"
```

Drush lists the operations before it runs them. By default it replaces every user's email with `user+<uid>@localhost.localdomain` and every password with the same random one, so no real address gets mail from your local site and no production password works. The query shows the new addresses, for example `user+1@localhost.localdomain` for the first account.

`sql:sanitize` only knows about user data that Drush and your installed modules tell it about. A table your own code creates, such as a list of contact form leads, keeps its rows, so clear it yourself before you share the database.

## Log in after sanitizing

Nobody knows the new password, so log in with a one-time link:

```sh
lando drush user:login --name=admin
```

Drush prints a `/user/reset/1/...` link on your app's URL, including the fallback port, such as `:8443`, when Lando picked one. Open it in your browser to land on the admin account's edit page. Replace `admin` with the production admin's user name.

## Go back to your local database

```sh
lando db:restore before-prod --yes
```

`db:restore` brings back the snapshot you took before the import. Lando stops the database while it copies the volume, then starts it again.
