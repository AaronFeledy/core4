# Write a recipe and init from a remote source

A recipe is a `recipe.yml` with metadata and an ordinary Landofile-shaped `config`. Lando compiles it into the app's `.lando.yml` and derives every digest and producer identity itself; you never write a snapshot, an expression tree, or a hash. The same file initializes from a local directory and from git, a tarball, npm, or the registry:

```sh
lando init --source=git --url=<git-url> --yes
```

Replace `<git-url>` with the repository URL. `--yes` accepts the remaining prompts. A remote tree is read as YAML only: `recipe.ts` is never evaluated from a clone, download, or package, so publish `recipe.yml` for anything you install remotely. See [Init from a remote recipe](../cli/init-from-remote.mdx) for the flags each source takes.

Three steps get a recipe from an idea to a running app: write it, validate it, init from it.

## Write recipe.yml

Save these three files in a directory named `tool-runner`. The directory basename must equal `id`.

`recipe.yml` declares one BusyBox service and two auxiliary files:

```yaml
id: tool-runner
title: Tool Runner
description: One disposable BusyBox service for running one-off commands.
version: 1.0.0
config:
  runtime: 4
  services:
    tools:
      type: lando
      image: busybox:1.37
      command: sleep infinity
files:
  - src: README.tmpl
    dest: README.md
    template: true
  - src: banner.txt
    dest: banner.txt
```

`README.tmpl`:

```text
# {{ app.name }}

Run `lando start`, then `lando exec tools -- busybox --help`.
```

`banner.txt`:

```text
Static files are copied byte for byte, so {{ app.name }} stays literal here.
```

`config` is the Landofile Lando writes, minus `name:` and the `recipe:` provenance block it adds. `lando init` asks for the app name itself, so a recipe never declares a `name` option. `files` lists files next to `recipe.yml`: a static file is copied byte for byte, and a `template: true` file is decoded as strict UTF-8 with only `{{ app.name }}` replaced. Lando computes each file's digest at init time, so edit `README.tmpl` freely.

The recipe parser is restricted to block YAML: use block mappings and block sequences, never inline `{ ... }` or `[ ... ]`. Leave `options:` out when the recipe has none.

## Validate before you push

From the parent directory:

```sh
lando meta recipes validate ./tool-runner --format=json
```

`readiness` is `ready` and `preview.landofile` shows the `.lando.yml` prepared with default option answers, an app name derived from the current directory, and the current directory as the destination. `preview.outputs` lists every prepared file's destination, mode, byte count, and digest. Inspection and init share the same preparation, but init with a different name, answers, or destination produces a different preview. Validation is read-only: it creates no directories and contacts no provider. `lando meta recipes describe ./tool-runner` reports the same fields with the recipe metadata.

`historyEligible` is `true` for this YAML recipe because every resolved source is declarative and can produce inert declarative history without evaluating recipe code. It does not promise external published versions or installed migration edges. A local YAML recipe that inherits from any evaluated `recipe.ts` reports `false`; remote trees and their ancestry remain YAML-only.

A `recipe.yml` without `config:`, or whose `config` isn't a valid Landofile shape, fails with `RecipeManifestValidationError`. Init runs the same compilation first, so an invalid recipe fails before anything is written.

## Init from a local directory

A local directory goes through the same compilation as a remote one, so test a recipe before publishing it. With the three files saved in `tool-runner/`:

```sh
lando init --recipe=./tool-runner --name=demo-app --yes
```

Init creates `demo-app/` in the current directory with `.lando.yml`, `README.md`, and `banner.txt`. Verify from inside the new app directory with `lando app:config --format=json`.

`README.md` came from `README.tmpl` with `{{ app.name }}` replaced. `banner.txt` is static, so its `{{ app.name }}` text is still there. `.lando.yml` is your `config` plus `name:` and a `recipe:` block recording the chosen options and the producer identity Lando computed from the recipe content.

## Add a typed option

Declare each option once under `options:` with a closed `type`, an optional typed `default`, and an optional `prompt`. Lando derives the init question from the type. An option without a default is required, and `lando init --no-interactive` fails for it with `InteractionRequiredError` instead of writing anything. Put conditional config under `variants:`; each `when` is an expression over `options` that Lando evaluates at init time.

```yaml
id: tool-runner-worker
title: Tool Runner with optional worker
description: One BusyBox service plus an optional worker service.
version: 1.0.0
options:
  worker:
    type:
      kind: boolean
    default: false
    prompt:
      message: Add a worker service?
config:
  runtime: 4
  services:
    tools:
      type: lando
      image: busybox:1.37
      command: sleep infinity
variants:
  - when: "{{ options.worker }}"
    config:
      services:
        worker:
          type: lando
          image: busybox:1.37
          command: sleep infinity
```

Answer it on the command line with `--answer worker=true`, or let `--yes` take the default. Option types are `string`, `number`, `boolean`, `enum`, `array`, and `optional`; reference a chosen value inside `config` as `{{ recipe.<option> }}`.

## Fail fast before a clone

The git source without a url exits `1` with `RecipeSourceError` kind `missing-url`:

```sh
lando init --source=git --yes --no-interactive
```

A tarball source needs a url. A registry source needs an id. Any other source value is `unsupported-source`.

`--path=packages/my-recipe` selects a subdirectory. Absolute paths and `..` escapes fail with `subpath-invalid` before cloning. A valid `--path` without `recipe.yml` at its top level is `subpath-missing`.

## How git caching works

Append `@ref` to the URL to pick a tag, branch, or full 40-character commit SHA. Without it, Lando uses the repository's default branch.

```sh
lando init --source=git --url=https://github.com/acme/lando-recipes.git@v2.1.0 --path=drupal
```

A recipe's `extends:` takes the same suffix, such as `extends: github:acme/lando-recipes/drupal@v2.1.0`.

Lando fetches exactly that ref, shallow and without tags, and caches the files under the Lando user data root at `<userDataRoot>/recipe-cache/git/<commitSha>/`. A full commit SHA that's already cached is reused without touching the network. A branch, tag, or the default branch is fetched again on every init so you get its current commit. If that fetch fails for a reason other than authentication and an earlier init cached the same URL and ref, `lando init --source=git` warns and uses the cached commit. An `extends:` parent on a branch or tag has no such fallback and fails instead.

Interactive git prompts are off (`GIT_TERMINAL_PROMPT=0`). Auth failures fail fast as `RecipeSourceError` kind `auth`. A ref that isn't a valid tag, branch, or full commit SHA fails before Lando runs git.
