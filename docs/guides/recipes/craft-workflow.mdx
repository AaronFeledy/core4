# Run a Craft CMS site on the LAMP recipe

Craft CMS 5 needs Composer, a `web/` webroot, and working `.htaccess` rewrites. The LAMP recipe plus one service key and a `lando craft` tool covers all three. Run these commands from your host terminal.

```sh
lando init --recipe lamp --name=craft-demo --answer=webroot=web --yes
cd craft-demo
```

The named init creates `craft-demo/` and writes only `.lando.yml` there. `--answer=webroot=web` points Apache at the directory Craft serves. `--yes` keeps PHP 8.4, MariaDB 11.4, and Composer 2. Craft 5 needs PHP 8.2 or newer, so don't pass `--answer=php=8.1`.

## Add the Craft pieces

Merge these keys into the generated `.lando.yml`. Keep its `recipe:` block: `webroot`, `type`, and `composer` read their values from it.

```yaml
services:
  appserver:
    allowOverride: true
tooling:
  craft:
    service: appserver
    user: www-data
    cmds:
      - php craft
    description: Run the Craft CLI inside the appserver service.
    wrapper: true
```

- `allowOverride: true` lets Apache read the `web/.htaccess` Craft ships, so control panel and front-end URLs rewrite to `index.php`.
- `lando craft` runs the CLI as `www-data`, the user Apache runs as. Caches and logs it writes stay writable by the site. `wrapper: true` hands every argument to Craft, as the recipe's `lando php` and `lando composer` do, so Lando doesn't keep flags such as `--verbose` for itself.

Check the file, then start the app:

```sh
lando app:config:lint
lando start
```

If something else owns 80 or 443, `lando info` shows the fallback port it picked, usually `:8080` / `:8443`.

## Install Craft

Run the commands in this section from a POSIX shell on your host (WSL on Windows). The password step also needs `openssl`.

`create-project` wants an empty directory, and the app root already holds `.lando.yml`. Install into `tmp-app`, then copy it into the root:

```sh
lando composer create-project craftcms/craft tmp-app "^5" --no-scripts
lando exec appserver -- sh -c 'cp -a tmp-app/. . && rm -r tmp-app && mv composer.json.default composer.json && cp .env.example.dev .env'
```

`--no-scripts` stops Composer from starting Craft's interactive installer inside `tmp-app`. The copy command finishes the rest of that script: it swaps in the project's own `composer.json` and creates `.env` from the dev example. `vendor/` lives in a service volume, so it stays empty on the host while PHP sees the packages inside the container. See [Exclude paths from the app mount](../setup/file-sync-excludes.mdx).

Save the database connection to `.env`:

```sh
lando php craft setup/db-creds \
  --driver=mysql \
  --server=database \
  --port=3306 \
  --user=lando \
  --password=lando \
  --database=craft-demo \
  --interactive=0
```

`--database` matches the app name (here `craft-demo`). Use the service key `database`, not `127.0.0.1` or `localhost`.

`--site-url` in the next command takes the full HTTPS URL `lando info` prints. On a fallback port the URL includes the port, for example `https://craft-demo.lndo.site:8443/`. Install saves it to `.env` as `PRIMARY_SITE_URL`, so you can change it there later.

Generate the admin password, then install. The password stays out of shell history, but it's on the command line, so process lists can see it while install runs.

```sh
CRAFT_ADMIN_PASSWORD="$(openssl rand -base64 18)"
printf 'Save this Craft admin password: %s\n' "$CRAFT_ADMIN_PASSWORD"
lando php craft install \
  --email=admin@example.com \
  --username=admin \
  --password="$CRAFT_ADMIN_PASSWORD" \
  --site-name='Craft Demo' \
  --site-url=https://craft-demo.lndo.site/ \
  --language=en \
  --interactive=0
unset CRAFT_ADMIN_PASSWORD
```

Setup and install run through `lando php` instead of `lando craft` because they write `.env` in the app root, and `www-data` can't write there. Both print Craft's warning that its commands shouldn't run as root. That's expected for these two. On the default provider, container root writes the app mount as your host user, so `.env` stays yours.

Give the web user the paths Craft writes to:

```sh
lando exec appserver -- touch /app/config/license.key
lando exec appserver -- chown -R www-data:www-data \
  /app/storage /app/config/project /app/config/license.key /app/web/cpresources
```

Until Craft can write `config/license.key`, every page is a 503 that says `/app/config isn't writable by PHP`. The other three hold logs and caches, the project config the control panel saves, and published control panel assets. Don't chown all of `/app` or all of `config/`. That reowns your code and `config/general.php`, so your editor and host `lando` commands lose write access.

On a Linux host you can still read those four paths, but your own user can no longer write to them. Craft and `lando craft` do the writing there. To change a file yourself, run your command inside the service with `lando exec appserver -- ...`.

## Check the tools and the site

```sh
lando craft help
lando mariadb -e 'SELECT username, email FROM users;'
```

`lando craft help` prints `Welcome to Craft CMS version` with the installed 5.x version, then lists the CLI commands. Craft has no `--help` or `--version` flag, so use `lando craft help <command>` for one command's options. The query's output includes `admin`.

Open the HTTPS URL `lando info` prints. A fresh install serves "Welcome to Craft CMS". Add `/admin` to the URL for the control panel and sign in as `admin` with the password you saved.

From here on, run Craft commands through `lando craft`, for example `lando craft clear-caches/all`. A Craft command run through `lando php` runs as root and can leave files in `storage/` that the site can't write.

## Add a plugin

Composer still runs as root and writes `composer.json` and `vendor/`. Install the plugin into Craft as `www-data`, so the project config it saves stays writable:

```sh
lando composer require craftcms/ckeditor
lando craft plugin/install ckeditor
lando craft plugin/list
```

`plugin/list` shows `ckeditor` as installed and enabled.

## See what you built

| Piece | What you get |
| --- | --- |
| `appserver` | `php:8.4`, Apache on port `80`, webroot `web`, `.htaccess` on, depends on `database` |
| `database` | `type: mariadb:11.4` |
| Tooling | `lando craft` as `www-data`, `lando composer` and `lando php` on `appserver`, plus `lando mariadb` from the database service |

Routes use `{{ app.name }}.{{ proxy.defaultDomain }}` on HTTP and HTTPS. On the `--answer=database=mysql:8.0` path, use `lando mysql` instead of `lando mariadb`.

## Connect Craft to MariaDB

| Setting | Value |
| --- | --- |
| Host | `database` |
| Database | app name (here `craft-demo`) |
| User | `lando` |
| Password | `lando` |
| Port | `3306` |
| Driver | `mysql` |

Setup saved these in `.env` as `CRAFT_DB_*`. Craft's MySQL driver talks to MariaDB on the LAMP recipe.

## Export and import the database

Import runs the dump's SQL, which can change or replace existing data. Export first if you need to keep it.

```sh
lando db:export craft.sql.gz
lando db:import craft.sql.gz --yes
lando craft clear-caches/all
```

The app has one database service, so neither command needs `--service`. `.gz` dumps compress and decompress on the way through. Importing into a non-empty database asks first, and `--yes` skips the prompt. Clear the caches after an import so Craft stops serving pages built from the old data.

Take a snapshot before you add a plugin or update Craft. Run the second command only to roll back:

```sh
lando db:snapshot --label before-update
lando db:restore before-update --yes
```

`db:restore` takes the label or the id `lando db:snapshots` lists. It asks before it replaces data, and `--yes` skips the prompt. Clear the caches after a restore too.

[Import and export app databases](../tooling/db-import-export.mdx) covers the other dump formats and the recovery snapshot `db:import` takes.

## Destroy the app

On a Linux host, your own user can't delete the files Craft wrote as `www-data`. If you plan to remove the project directory too, give those paths back to yourself while the app is still running:

```sh
lando exec appserver -- sh -c 'chown -R "$(stat -c %u:%g .lando.yml)" /app'
lando destroy -y
```

The first command reowns `/app` to whoever owns `.lando.yml`, which is you. `destroy` removes containers and networks. Volumes stay unless you pass `--volumes` or `--purge`.
