# Run the Hugo recipe

```sh
lando init --recipe hugo --name=hugo-demo --yes
cd hugo-demo
lando start
```

`--yes` skips prompts. Hugo declares no recipe options, so the only prompt is the app name. The first start builds the `builder` image with a pinned official Hugo extended binary and brings up `hugo server`. No package install, no parking, no second edit of `.lando.yml`.

## See what the recipe writes

Init writes `.lando.yml` and a small starter site: a Hugo config, a content archetype, and layouts that render the home page plus any content you add. That's enough for `hugo server` to have something to serve on the first start.

| Piece | What you get |
| --- | --- |
| `builder` | `node:lts` with Hugo extended baked in, port `1313`, command `hugo server --bind 0.0.0.0 --port 1313` |
| `web` | `static:nginx` serving `public/` from the app mounted at `/app`, one route on both schemes |
| Tooling | `lando hugo` (the bundled binary) and `lando npm` on `builder` |

`builder` is the day-to-day browse target while Hugo serves. `web` is the nginx sidecar on the app hostname. Routes use `{{ app.name }}.{{ proxy.defaultDomain }}` on HTTP and HTTPS.

## Check the toolchain

```sh
lando hugo version
lando npm --version
```

`lando hugo version` reports the extended build the recipe pins in `builder.build.artifact` of your Landofile. That pin is part of your app, not something Lando swaps underneath you; change it there if you need a different release. `lando npm` is there for themes and asset pipelines that need Node, not for installing Hugo.

## Find your URLs

```sh
lando info
```

Open the **builder** URL `lando info` prints (for example `https://builder.hugo-demo.lndo.site`). That's the Hugo development server with live reload. If host ports 80 or 443 are already taken, the URL may use a fallback port such as `:8443`.

The app hostname URL (the **web** entry, for example `https://hugo-demo.lndo.site`) is nginx serving `public/`. Hugo 0.167.0's server writes its output to disk by default, so `web` has pages as soon as `hugo server` finishes its first render.

## Add content

```sh
lando hugo new content posts/hello.md
```

The starter archetype writes `draft = false`, so the post publishes as soon as you save and shows up on the `builder` URL. Want to keep something out of the build while you work on it? Set `draft = true` in its front matter; `hugo server` and `hugo build` skip drafts unless you pass `-D`.

## Build explicitly

```sh
lando hugo build
```

That runs a one-shot build into `public/`. `web` ships with `webroot: /app/public`, so there's nothing to configure. The running `hugo server` writes to the same directory on every change, so don't expect `hugo build` output to stay untouched while you keep editing; stop the server or build elsewhere if you need a frozen copy.

## Builder versus web

Two URLs, two jobs:

| URL | Process | Use it for |
| --- | --- | --- |
| `builder` | `hugo server` | Editing. Live reload on save |
| `web` | nginx on `public/` | Seeing the same output served as plain static files, no Hugo in the request path |

## Destroy without surprises

```sh
lando destroy -y
```

That removes containers and networks. Volumes stay unless you pass `--volumes` or `--purge`.
