# Open a Lando shell

From your app directory in an interactive terminal, open a shell on the host with the app’s Lando environment. This command does not enter a container:

```sh
lando shell
```

With no `--service` flag, that opens a host shell scoped to the app root. The host shell gets the app-scoped Lando environment (`LANDO_APP_NAME`, `LANDO_APP_ROOT`). `--host` is deprecated. Host mode is already the default, so `lando shell --host` is redundant.

## Open a shell in a service

Start the app first, then select the service explicitly. Replace `appserver` with your service name:

```sh
lando shell --service appserver
```

Lando starts `bash -l` if bash is on the container's `PATH`; otherwise, it starts `sh -l`.

Use the `--service` flag, not a positional argument. `lando shell appserver` fails with `Unexpected argument: appserver` instead of opening a host shell.

## Forward agent-context env

`lando exec` and `lando shell --service` copy host agent-context markers into the target service. Only this allowlist is forwarded:

```text
CLAUDECODE, CLAUDE_CODE, CLAUDE_CODE_IS_COWORK, CURSOR_AGENT,
OPENCODE, OPENCODE_CLIENT, COPILOT_CLI, GEMINI_CLI,
CODEX_SANDBOX, CODEX_CI, AUGMENT_AGENT, ANTIGRAVITY_AGENT,
PI_CODING_AGENT, CLINE_ACTIVE, GOOSE_TERMINAL, OPENCLAW_SHELL,
GROK_AGENT, AI_AGENT, AGENT, CI
```

`GROK_AGENT` is forwarded only when its host value is exactly `1`. A definition name or path is dropped.

Forwarded markers are the lowest-precedence layer. Configured service env and explicit command env always win.

Set app `agentEnv: false`, global `agentEnv.enabled: false`, or `LANDO_AGENT_ENV=0` to veto automatic forwarding. Global policy is read through `ConfigService.get` at invocation time from the runtime's config snapshot: fresh for each CLI command, fixed for the life of an embedded runtime. Vetoes do not scrub explicit service or command env or revoke a running command.

Ordinary CLI commands discover current app configuration. An embedded App handle instead retains its captured Landofile for exec, deep info, and tooling. It does not observe a later app `agentEnv: false` edit. Re-resolve with `runtime.app(originalSelector)` or `resolveApp(originalSelector)` after edits; update an object selector too. The current process `LANDO_AGENT_ENV=0` remains an immediate veto for subsequent handle invocations.

## Drive an interactive service shell

While a service shell is interactive: stdin is attached, stdout and stderr stream back, terminal resize (`SIGWINCH`) updates the running shell, and Ctrl-C cancels the exec stream.

PTY allocation and host-terminal detection are separate. `lando exec`, `lando ssh`, and service tooling borrow attached stdout facts such as `TERM`, `COLORTERM`, width, and height only when stdout is a real terminal. Redirected output and MCP calls do not gain terminal identity from a stream sink. An explicit PTY request still allocates a provider PTY through a pipe, using provider-safe size defaults without inventing `TERM` or `COLORTERM`.

## Use host-mode REPL

Host mode reads one line at a time and evaluates it as a Bun Shell template. Bun Shell supports pipes, redirection, globs, command substitution, and shell builtins across Linux, macOS, and Windows. It is not your Bash or zsh session and does not load your login-shell configuration. See the [Bun Shell syntax reference](https://bun.com/docs/runtime/shell) for its supported language. A blank line re-prompts without evaluating anything.

Each line starts in the app root with `$PWD` identifying that directory, not the directory you launched Lando from. Lando resolves symbolic links before execution. An explicitly configured `PWD` overrides this default, even when it is empty.

Lines run independently. A `cd` or variable assignment affects only that line; it does not change the next prompt's directory or environment. Put dependent commands on one line or save them in a [project script](./bun-shell-scripts.mdx).

`lando` in a line runs Lando. `bun` uses your host Bun on `PATH`, or Lando's embedded Bun if none is installed. You don't need a separate Bun installation.

A `${secret:<id>}` or `${secret:<scheme>://path}` reference (for example `${secret:DB_PASSWORD}` from `LANDO_SECRET_DB_PASSWORD`, or `${secret:op://Vault/Item/field}` from 1Password) resolves only when that line runs, through the same routed secret stores as `lando start`. The REPL never preloads secrets into the environment. Resolved secret values are redacted before they reach stdout, stderr, lifecycle events, or history.

Host-mode history persists per accepted line to a per-app history file under the user cache root. `--no-history` disables history for the session. History is bounded, and every line is redacted before it is appended, so a line that resolved a secret never lands on disk raw.

Every accepted line publishes `pre-shell-exec` before it runs and `post-shell-exec` with its exit code after. Subscribers receive the redacted command text, cwd, and output, not the raw line.

Ctrl+C aborts only the currently running line. The REPL prompt returns. An interrupted line reports exit status 130.

Ctrl+D at an empty prompt ends the REPL with the exit status of the last executed line. Typing `exit` does the same. `exit <code>` ends it with that status. On both paths, the REPL restores the terminal before `lando shell` returns.

The JSON result for a completed shell session contains `mode` (`host` or
`service`), `app`, `shell`, `cwd`, and `exitCode`. Service mode also includes
`service`; host mode omits it. Selecting JSON does not make the shell
non-interactive. Use `lando shell --json` to list the result keys without
opening a session, or `lando exec` to run a command without a terminal.

`lando shell --no-interactive`, a non-TTY stdin/stdout, or a redirected invocation never opens the REPL. The command fails fast with tagged `ShellRequiresTtyError` instead of hanging. The error points at the scriptable equivalent:

```sh
lando exec <service> -- <command>
```
