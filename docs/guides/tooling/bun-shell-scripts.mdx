# Add project commands with Bun Shell scripts

Drop a `.bun.sh` file into `.lando/scripts/` and it becomes a `lando` command. The script runs on your host through Bun Shell, from the app root, with your normal `PATH`. No Landofile entry, no Makefile, and no Bun install on your side: Lando runs it with the Bun it already ships. Any app with a `.lando.yml` works, even one with no services.

In an app with `.lando.yml`, create `.lando/scripts/` and make sure `src/index.html` exists. This example deletes and recreates `dist/` on your host every time it runs, so use it only when that directory contains disposable build output. Save the script as `.lando/scripts/build.bun.sh`:

```sh
# ---
# desc: Build dist/ from src/ on the host
# ---
rm -rf dist
mkdir -p dist
cp src/index.html dist/index.html
echo "built dist/ from src/"
```

From the app directory, refresh the command cache once, then run the script:

```sh
lando app:cache:refresh
lando build
lando bun -e 'console.log(await Bun.file("dist/index.html").text())'
```

The script prints `built dist/ from src/` and `lando build` exits with the script's own exit code. The final command reads the copied HTML; check that it matches `src/index.html`.

## Write the front matter

Every script opens with a front-matter block. It sits on the first lines of the file (an optional `#!/usr/bin/env bun` shebang may come first), starts and ends with `# ---`, and prefixes each line with `# `.

| Key | What it does |
| --- | --- |
| `desc`, `description`, or `summary` | Help text for the command |
| `service` | Where the script runs. Only `:host`, which is also the default |
| `flags` | Named options with aliases, defaults, choices, required values, and boolean switches |
| `args` | Named positional arguments with ordering, defaults, choices, and required values |
| `arguments` | Set `false` to reject positional arguments; do not combine it with declared `args` |
| `disabled` | `true` hides the command and refuses execution; omitted or `false` keeps it enabled |

Use indented YAML mappings for `flags` and `args`, as in the next example. Front matter uses the same restricted YAML parser as a Landofile, not a separate shell-comment syntax. Quote strings containing YAML punctuation; inside a single-quoted value, double an apostrophe, as in `# desc: 'Print the team''s greeting'`.

Other tooling features are not script metadata. Keys such as `aliases`, `engine`, `bootstrap`, `sources`, and `run` refuse with `NotImplementedError` and name the field. Unknown keys, malformed YAML, conflicting input declarations, or a file with no block refuse with `BunShellScriptFrontMatterError`. An empty file refuses with `BunShellScriptEmptyError`.

Missing or malformed front matter makes `lando app:cache:refresh` fail before it writes the command cache. Fix the reported script and refresh again.

## Declare flags and read inputs by name

Declare inputs when you want help text, defaults, and validation before the script runs. Save this as `.lando/scripts/greet.bun.sh` in the same app:

```sh
# ---
# description: Greet a target environment
# flags:
#   name:
#     alias: n
#     default: world
#   loud:
#     boolean: true
#     default: false
# args:
#   target:
#     order: 0
#     required: true
#     choices: [dev, prod]
#   label:
#     order: 1
#     default: latest
# ---
printf 'Hello %s: target=%s label=%s loud=%s\n' "$LANDO_FLAG_NAME" "$LANDO_ARG_TARGET" "$LANDO_ARG_LABEL" "$LANDO_FLAG_LOUD"
```

Refresh the metadata, check the help, then call it from the app directory:

```sh
lando app:cache:refresh
lando greet --help
lando greet dev
lando greet prod release -n team --loud
```

The first call prints a greeting for `world` with `target=dev`, `label=latest`, and `loud=false`. The second uses `team`, `prod`, `release`, and `loud=true`. This example prints the switch's value; it does not change the greeting's case. `lando greet` without a target, or `lando greet staging`, fails with `ToolingInputError` before running the body. Supply `dev` or `prod` to recover.

For a structured description of this script, run `lando help app:greet --format=json` from the same app. Read `result.target.input` for its flags, arguments, and declaration revision. Unknown targets and unavailable metadata return a tagged failure instead of an unrelated command catalog.

The nested declarations follow the [tooling flag and argument rules](../flags-and-args/): flags accept `alias`, `boolean`, `choices`, `default`, `required`, `description`, and `sensitive: true`; arguments accept `order`, `choices`, `default`, `required`, `description`, and `sensitive: true`. Use `required: true` or a `default`, not both. Boolean flags accept `--loud`, `--loud=true`, or `--loud=false`; explicit false overrides a true default. Lando does not generate `--no-loud`, and `--loud false` does not set the flag to false. Booleans cannot have choices.

Flags and defaults are literal values, not expressions or secret lookups. Sensitive inputs cannot declare defaults or choices, because metadata is retained in command caches and exposed through help and catalogs.

Use the named environment variables rather than counting `$1` positions when you declare inputs:

| Read inside the script | Value |
| --- | --- |
| `LANDO_FLAG_NAME` | Resolved `name` flag, including its default |
| `LANDO_ARG_TARGET` | Resolved `target` positional argument |
| `LANDO_FLAG_LOUD` | The string `true` or `false` when the boolean has a value |
| `LANDO_INPUT` | `ToolingInputValues` JSON with exactly `flags` and `args` |

Lando replaces every character outside ASCII letters, digits, and `_` with `_`, then uppercases the result. For example, `output-dir` becomes `LANDO_FLAG_OUTPUT_DIR`. Two names in the same group cannot produce the same suffix: `output-dir` and `output_dir` together fail with `BunShellScriptFrontMatterError`. Rename one and refresh. A flag and an argument may share a suffix because their prefixes differ.

An optional input with no supplied value or default has an empty-string environment variable and is omitted from its JSON map. A boolean with no default is also absent until supplied; declare `default: false` if you need an explicit false value. `LANDO_INPUT` contains data only, not IO handles or the full command invocation. Lando replaces inherited `LANDO_INPUT` and clears inherited `LANDO_FLAG_*` and `LANDO_ARG_*` values before setting the current inputs, so stale values cannot leak into the script.

Named input preserves the difference between omission, an empty string, and boolean false. MCP and library callers can supply a later optional argument by name while leaving an earlier optional argument absent. Scripts read those maps directly; Lando does not create command-line tokens from them. An argv-only Landofile task instead rejects an interior positional gap before execution.

For a CLI call, `$1` through `$9` retain the original physical tokens after Lando's global-option handling, not a reordered or default-filled list. In `lando greet prod release -n team --loud`, `$1` is `prod`. Defaults exist in the named inputs, not in those numeric parameters. Prefer named environment variables or `LANDO_INPUT` for declared inputs so the script also works for named-map callers. Without declarations, the JSON maps are empty; see [Pass arguments](#pass-arguments) for raw CLI tokens.

## Mark sensitive inputs

Add `sensitive: true` to any flag or argument that may carry a private value, even if its name is innocuous. Save this as `.lando/scripts/show-note.bun.sh`:

```sh
# ---
# desc: Demonstrate protected input
# flags:
#   note:
#     sensitive: true
#     required: true
# ---
printf '%s\n' "$LANDO_FLAG_NOTE"
```

Refresh and test with a fake value, never a real credential:

```sh
lando app:cache:refresh
lando show-note --note=guide-canary-note --format=json
```

Check that the collected output contains `[redacted]`, not the fake value. Lando protects supplied sensitive values in its output, errors, events, and traces, including invalid, stale, or disabled calls. Names recognized by Lando's existing secret-name rules are sensitive too; there is no `sensitive: false` opt-out. Remove any `default` or `choices` from a sensitive declaration if metadata validation refuses it.

This protection covers Lando's observable output, not arbitrary files or external logs your script writes. The script still receives the literal value. Do not write it to a file or pass it to an external logger and expect Lando to redact that destination.

## Disable a script without deleting it

Add `# disabled: true` inside the script's front-matter block, then run `lando app:cache:refresh`. Check `lando --help`: the script is absent from the app command list. Calling it directly, including with `--help`, fails with `ToolingDisabledError` before environment resolution, task progress, or the body runs. To restore it, remove `disabled` or set it to `false`, then refresh again.

Disabled scripts are also absent from the MCP tooling catalog. Enabled scripts and their declared inputs use the existing tooling discovery path when you opt in with `lando mcp --tooling`; this does not bypass command-cache requirements. See [Drive Lando through MCP](../../agent-native/mcp/).

A running MCP session retains the revision of the input declaration it advertised. Changes to names, aliases, order, types, defaults, choices, requiredness, sensitivity, or raw-argument policy make old calls fail with `ToolingInputError` before the body runs. Refresh the command cache and reconnect the client to load the new catalog, then decide whether to retry. Lando does not reload that session's catalog or replay the failed call automatically. Description-only changes and script-body edits keep the input revision compatible, although front-matter edits still require a cache refresh for discovery.

## Refresh when the shape changes

The first run in a fresh clone needs one `lando app:cache:refresh`. This explicitly rebuilds the full app plan and command index without starting services; it is not a metadata-only refresh. You do not need to start or rebuild services just to repair command discovery. After that:

| You changed | Run |
| --- | --- |
| A script body | Nothing. The next call runs the new body |
| A new script file | Direct invocation can find it with an otherwise fresh cache; refresh to update command listings |
| A script's front matter, including declaration order | `lando app:cache:refresh` |
| The Landofile | `lando app:cache:refresh` |

Unavailable command metadata produces `ToolingCommandUnavailableError`. Its `reason` tells you what to repair:

| `reason` | Next action |
| --- | --- |
| `missing-cache` | Run `lando app:cache:refresh` in this app |
| `stale-cache` | Refresh after the Landofile or script metadata changed |
| `invalid-cache` | Refresh to replace an index this Lando version cannot decode |
| `unknown-command` | Check the name and alias; a fresh index has no matching command |

The error also carries `commandId`, `tool`, and `remediation`, with `staleReason` and `sourcePath` when available. Help does not run a planner, start a provider, or silently fall back to live discovery to repair this state. To inspect it, run:

```sh
lando help --format=json
```

Read `result.toolingMetadata.status`: `fresh`, `not-app`, or `unavailable`. An unavailable result includes the recovery reason and remediation instead of stale tooling declarations. Human help shows the same recovery guidance. After refreshing successfully, inspect help again before retrying the command.

For a newly added script with declared inputs, `lando <name> --help` can show those inputs before an inventory refresh, provided the existing cache is otherwise fresh. Scripts without input declarations receive `--help` as a raw argument. If any declared flag is named `help` or aliased to `h`, Lando leaves both help spellings to the script's input parser instead of showing its own help.

## List your commands

Run `lando --help` inside the app after refreshing. Enabled scripts show up under `THIS APP` with their description, next to any Landofile tooling:

```sh
lando --help
```

`lando help --all` prints the same list after every built-in command.

## Pass arguments

Without `flags` or `args` declarations, arguments after the command name pass through unchanged and are available as `$1` through `$9`. Save this as `.lando/scripts/stamp.bun.sh`:

```sh
# ---
# desc: Write a version stamp into dist/
# ---
echo "$1" > dist/version.txt
echo "stamped dist/version.txt with $1"
```

Stamp the build with the current commit:

```sh
lando stamp "$(git rev-parse --short HEAD)"
```

Your own shell runs `git` before Lando sees the line, so the script receives the short SHA. Check `dist/version.txt` for that same value.

Bun Shell does not expand `$@` or `$#`. They come through as literal text, so name each argument you need with `$1`, `$2`, and so on.

Lando reads its own global flags, such as `--format` and `--verbose`, anywhere on the line. Put `--` in front when the script should get them instead:

```sh
lando stamp -- --format=json
```

## Feed a script stdin

Pipe or redirect into the command and the script reads it to the end. Save this as `.lando/scripts/count.bun.sh`:

```sh
# ---
# desc: Count the lines on stdin
# ---
wc -l
```

```sh
printf 'a\nb\nc\n' | lando count
lando count < src/index.html
```

The first prints `3`. Commands inside the script share that input, so a `seed` script can take `lando seed < dump.sql` and hand the dump to whatever client it runs.

Run it from a terminal with nothing piped in and the script inherits your keyboard. Lando retires its task-tree consumer before starting it. stdout and stderr still stream through the byte sink, with registered values masked even when a write splits a secret. The script does not write around that redaction boundary.

Ctrl+C (`SIGINT`) cancels the active command with exit status `130`; `SIGTERM` uses `143`. An interruption-only failure is `CommandInterruptedError`, with the signal when known, rather than internal Effect interruption text. Lando releases scoped resources; if execution or cleanup also failed, those failures remain visible rather than being replaced by a cancellation message. Cancellation does not undo files or other effects the script already produced. Inspect those effects before running the command again.

With `--format=json`, `--format=yaml`, or `--renderer=json`, piped input still arrives but the keyboard does not. A script that waits for typed input reads end of input instead of hanging an automated caller.

## Capture output as JSON or YAML

Add `--format=json` or `--format=yaml` and Lando collects the script instead of streaming it. You get one envelope on stdout with the script's output and exit code under `result`:

```sh
lando stamp abc1234 --format=json
lando stamp abc1234 --format=yaml
```

| Key | What it holds |
| --- | --- |
| `result.stdout` | Everything the script wrote to stdout |
| `result.stderr` | Everything it wrote to stderr |
| `result.exitCode` | The script's exit code |

A script that exits nonzero still gets its output collected, and `lando` exits with that same code. The envelope's `ok` only says Lando ran the script, so branch on `result.exitCode`, not on `ok`. Without a format flag, output streams to your terminal as it happens. Both formats run the script with Lando's embedded Bun, so a host with no Bun installed works the same.

The envelope, `--json=<key>`, and `--jq` work the way they do for every other command. See [Script Lando with JSON](../../scripting-with-json/) for the full contract.

## Group commands in folders

Subfolders become namespaces. `.lando/scripts/env/init.bun.sh` is `app:env:init`:

```sh
# ---
# desc: Create .env from .env.example if it is missing
# ---
if test -f .env; then
  echo ".env already exists, leaving it alone"
else
  cp .env.example .env
  echo "created .env"
fi
```

```sh
lando app:env:init
```

The first run prints `created .env`. Run it again and it prints `.env already exists, leaving it alone`. Names with a colon always take the `app:` prefix. Top-level scripts answer to both `lando build` and `lando app:build`.

Lando lowercases each path segment, turns anything outside `a-z`, `0-9`, `_`, and `-` into `-`, collapses repeated `-` into one, and trims `-` from both ends.

`lando app:cache:refresh` rejects a script whose canonical command or active top-level name collides with a built-in command. You get `CommandAliasConflictError`, and the invalid command cache is not written. For example, `info.bun.sh` collides with `app:info`, while `version.bun.sh` collides with the default `version` alias. Rename the script and refresh again. Disabling or remapping aliases does not free a built-in canonical id such as `app:info`.

Folders do not claim bare namespaced aliases. `.lando/scripts/db/seed.bun.sh` registers `app:db:seed`, so run `lando app:db:seed`, not `lando db:seed`. A plugin command named `db:seed` does not collide with that script. A folder path that produces an existing canonical id, such as `.lando/scripts/cache/refresh.bun.sh` producing `app:cache:refresh`, still fails.

## Use Bun Shell and your host tools

Bun Shell supports pipes, redirection, `$(...)`, `&&`, `||`, environment variables, and `if ... then ... fi`. It is a separate shell language, not Bash, zsh, or a promise of full POSIX shell compatibility. Use the [Bun Shell syntax reference](https://bun.com/docs/runtime/shell) when writing scripts. Commands can use shell builtins or executables found on your host `PATH`. Host tools such as `git`, `curl`, and your package managers must be available in that environment.

Scripts always run from the app root, even when you call them from a subdirectory. Relative paths such as `src/` and `dist/` mean the same thing everywhere in the repo.

Lando resolves the working directory before starting a command, so relative paths and `$PWD` refer to the same directory, including through symbolic links. An explicitly configured `PWD` overrides this default, even when it is empty. Host tooling commands use the same rule. If the working directory is missing, inaccessible, or not a directory, the command does not start; fix the reported directory and rerun it.

## Smoke test the running site

Host scripts can poke the app through its public URL. Save this as `.lando/scripts/smoke.bun.sh`:

```sh
# ---
# desc: Fetch a URL from the running site and fail loudly
# ---
curl -sf "$1"
```

Start the app and pass the `web` URL from `lando info`. Lando adds a port such as `:8443` when 443 was taken:

```sh
lando start
lando info
lando smoke https://web.scripts-demo.lndo.site/version.txt
```

That prints the stamped SHA. Ask for a path that does not exist and `curl -f` exits `22`, so `lando smoke` exits `22` too. You can use that exit code in a git hook.

## Call `lando` from a script

A script can run `lando` like any other host command, so one file can bring the app up and work inside it. Save this as `.lando/scripts/peek.bun.sh`:

```sh
# ---
# desc: Start the app and print the stamp web serves
# ---
lando start
lando exec web -- cat /app/dist/version.txt
```

```sh
lando peek
```

That starts the app, then prints the stamped SHA from inside `web`. The app and its URL stay up after the script exits, the same as a `lando start` you type yourself.

`lando` in a script is the `lando` on your `PATH`. If your `PATH` has none, it is the Lando that started the script, so `./lando peek` from a download folder works too. Call it by name: a path such as `./bin/lando` inside the script runs as Bun instead of Lando.

Package scripts you run with `lando bun run` follow the same rule: `lando` in them runs Lando, and `bun` runs the Bun Lando ships. A nested `lando bun` is refused.

## Run service work from the Landofile

Scripts run on your host. Setting `service: web` in front matter refuses with `NotImplementedError` and points you at a Landofile tooling task. Commands that belong inside a service go in the Landofile:

```yaml
name: scripts-demo
services:
  web:
    type: static
    webroot: dist
tooling:
  curl:
    service: web
    cmd:
      - sh
      - -c
      - 'curl -sf "http://localhost:80/$1"'
      - curl
```

```sh
lando curl version.txt
```

That curl runs inside `web` against nginx on port `80`. If a Landofile task and a script share a name, the Landofile task wins. Drop a `curl.bun.sh` next to that Landofile and `lando curl` still runs in `web`.

## Declare a host task in the Landofile

A one-liner does not need its own file. Set `service: ":host"` on a Landofile task: no services required, no Bun install, and the task's exit code becomes `lando`'s exit code. Host output streams as the command writes it, value-only redacted and byte-exact, the same sink container tooling uses. Task progress stays on stderr, so `lando <task> > out.txt` captures only the command's output. A string `cmd` uses Bun Shell. A list is argv, and arguments you pass on the line are appended to it:

```yaml
name: host-task-demo
tooling:
  greet:
    description: Say hello from the host
    service: ":host"
    cmd: echo "hello from a host task"
  stamp:
    description: Print a version stamp
    service: ":host"
    cmd: ["printf", "stamped %s\n"]
```

```sh
lando app:cache:refresh
lando greet
lando stamp abc1234
```

`lando greet` prints `hello from a host task`, and `lando stamp abc1234` prints `stamped abc1234`. Add `--format=json` and the text lands in `result.stdout`, same envelope as a script. Reach for a `.bun.sh` file when the body outgrows one line, or when you want `if`, pipes, and `$(...)` without quoting a shell string inside YAML.
