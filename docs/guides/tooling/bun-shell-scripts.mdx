# Add project commands with Bun Shell scripts

Drop a `.bun.sh` file into `.lando/scripts/` and it becomes a `lando` command. The script runs on your host through Bun Shell, from the app root, with your normal `PATH`. No Landofile entry, no Makefile, and no Bun install on your side: Lando runs it with the Bun it already ships. Any app with a `.lando.yml` works, even one with no services.

In an app with `.lando.yml`, create `.lando/scripts/` and make sure `src/index.html` exists. This example deletes and recreates `dist/` on your host every time it runs, so use it only when that directory contains disposable build output. Save the script as `.lando/scripts/build.bun.sh`:

```sh
# ---
# desc: Build dist/ from src/ on the host
# ---
rm -rf dist
mkdir -p dist
cp src/index.html dist/index.html
echo "built dist/ from src/"
```

From the app directory, run the script. Lando notices the new file and reads your app's commands before it runs:

```sh
lando build
lando bun -e 'console.log(await Bun.file("dist/index.html").text())'
```

The script prints `built dist/ from src/` and `lando build` exits with the script's own exit code. The final command reads the copied HTML; check that it matches `src/index.html`.

## Write the front matter

Every script opens with a front-matter block. It sits on the first lines of the file (an optional `#!/usr/bin/env bun` shebang may come first), starts and ends with `# ---`, and prefixes each line with `# `.

| Key | What it does |
| --- | --- |
| `desc`, `description`, or `summary` | Help text for the command |
| `service` | Where the script runs. Only `:host`, which is also the default |
| `flags` | Named options with aliases, defaults, choices, required values, and boolean switches |
| `args` | Named positional arguments with ordering, defaults, choices, and required values |
| `arguments` | Set `false` to reject positional arguments; do not combine it with declared `args` |
| `disabled` | `true` hides the command and refuses execution; omitted or `false` keeps it enabled |

Use indented YAML mappings for `flags` and `args`, as in the next example. Front matter uses the same restricted YAML parser as a Landofile, not a separate shell-comment syntax. Quote strings containing YAML punctuation; inside a single-quoted value, double an apostrophe, as in `# desc: 'Print the team''s greeting'`.

Other tooling features are not script metadata. Keys such as `aliases`, `engine`, `bootstrap`, `sources`, and `run` refuse with `NotImplementedError` and name the field. Unknown keys, malformed YAML, conflicting input declarations, or a file with no block refuse with `BunShellScriptFrontMatterError`. An empty file refuses with `BunShellScriptEmptyError`.

Missing or malformed front matter makes the next command fail while Lando reads your app's commands, before anything runs. Fix the reported script and run the command again. `lando app:cache:refresh` reports the same error if you want to check every script at once.

## Declare flags and read inputs by name

Declare inputs when you want help text, defaults, and validation before the script runs. Save this as `.lando/scripts/greet.bun.sh` in the same app:

```sh
# ---
# description: Greet a target environment
# flags:
#   name:
#     alias: n
#     default: world
#   loud:
#     boolean: true
#     default: false
# args:
#   target:
#     order: 0
#     required: true
#     choices: [dev, prod]
#   label:
#     order: 1
#     default: latest
# ---
printf 'Hello %s: target=%s label=%s loud=%s\n' "$LANDO_FLAG_NAME" "$LANDO_ARG_TARGET" "$LANDO_ARG_LABEL" "$LANDO_FLAG_LOUD"
```

Check the help, then call it from the app directory:

```sh
lando greet --help
lando greet dev
lando greet prod release -n team --loud
```

The first call prints a greeting for `world` with `target=dev`, `label=latest`, and `loud=false`. The second uses `team`, `prod`, `release`, and `loud=true`. This example prints the switch's value; it does not change the greeting's case. `lando greet` without a target, or `lando greet staging`, fails with `ToolingInputError` before running the body. Supply `dev` or `prod` to recover.

For a structured description of this script, run `lando help app:greet --format=json` from the same app. Read `result.target.input` for its flags, arguments, and declaration revision. Unknown targets and unavailable metadata return a tagged failure instead of an unrelated command catalog.

The nested declarations follow the [tooling flag and argument rules](../flags-and-args/): flags accept `alias`, `boolean`, `choices`, `default`, `required`, `description`, and `sensitive: true`; arguments accept `order`, `choices`, `default`, `required`, `description`, and `sensitive: true`. Use `required: true` or a `default`, not both. Boolean flags accept `--loud`, `--loud=true`, or `--loud=false`; explicit false overrides a true default. Lando does not generate `--no-loud`, and `--loud false` does not set the flag to false. Booleans cannot have choices.

Flags and defaults are literal values, not expressions or secret lookups. Sensitive inputs cannot declare defaults or choices, because metadata is retained in command caches and exposed through help and catalogs.

Use the named environment variables rather than counting `$1` positions when you declare inputs:

| Read inside the script | Value |
| --- | --- |
| `LANDO_FLAG_NAME` | Resolved `name` flag, including its default |
| `LANDO_ARG_TARGET` | Resolved `target` positional argument |
| `LANDO_FLAG_LOUD` | The string `true` or `false` when the boolean has a value |
| `LANDO_INPUT` | `ToolingInputValues` JSON with exactly `flags` and `args` |

Lando replaces every character outside ASCII letters, digits, and `_` with `_`, then uppercases the result. For example, `output-dir` becomes `LANDO_FLAG_OUTPUT_DIR`. Two names in the same group cannot produce the same suffix: `output-dir` and `output_dir` together fail with `BunShellScriptFrontMatterError`. Rename one and run the command again. A flag and an argument may share a suffix because their prefixes differ.

An optional input with no supplied value or default has an empty-string environment variable and is omitted from its JSON map. A boolean with no default is also absent until supplied; declare `default: false` if you need an explicit false value. `LANDO_INPUT` contains data only, not IO handles or the full command invocation. Lando replaces inherited `LANDO_INPUT` and clears inherited `LANDO_FLAG_*` and `LANDO_ARG_*` values before setting the current inputs, so stale values cannot leak into the script.

Named input preserves the difference between omission, an empty string, and boolean false. MCP and library callers can supply a later optional argument by name while leaving an earlier optional argument absent. Scripts read those maps directly; Lando does not create command-line tokens from them. An argv-only Landofile task instead rejects an interior positional gap before execution.

For a CLI call, `$1` through `$9` retain the original physical tokens after Lando's global-option handling, not a reordered or default-filled list. In `lando greet prod release -n team --loud`, `$1` is `prod`. Defaults exist in the named inputs, not in those numeric parameters. Prefer named environment variables or `LANDO_INPUT` for declared inputs so the script also works for named-map callers. Without declarations, the JSON maps are empty; see [Pass arguments](#pass-arguments) for raw CLI tokens.

## Mark sensitive inputs

Add `sensitive: true` to any flag or argument that may carry a private value, even if its name is innocuous. Save this as `.lando/scripts/show-note.bun.sh`:

```sh
# ---
# desc: Demonstrate protected input
# flags:
#   note:
#     sensitive: true
#     required: true
# ---
printf '%s\n' "$LANDO_FLAG_NOTE"
```

Test with a fake value, never a real credential:

```sh
lando show-note --note=guide-canary-note --format=json
```

Check that the collected output contains `[redacted]`, not the fake value. Lando protects supplied sensitive values in its output, errors, events, and traces, including invalid, stale, or disabled calls. Names recognized by Lando's existing secret-name rules are sensitive too; there is no `sensitive: false` opt-out. Remove any `default` or `choices` from a sensitive declaration if metadata validation refuses it.

This protection covers Lando's observable output, not arbitrary files or external logs your script writes. The script still receives the literal value. Do not write it to a file or pass it to an external logger and expect Lando to redact that destination.

## Disable a script without deleting it

Add `# disabled: true` inside the script's front-matter block. Check `lando --help`: the script is absent from the app command list. Calling it directly, including with `--help`, fails with `ToolingDisabledError` before environment resolution, task progress, or the body runs. To restore it, remove `disabled` or set it to `false`. Both changes take effect on the next invocation.

Disabled scripts are also absent from the MCP tooling catalog. Enabled scripts and their declared inputs use the existing tooling discovery path when you opt in with `lando mcp --tooling`; the server reads your app's commands when the session starts. See [Drive Lando through MCP](../../agent-native/mcp/).

A running MCP session retains the revision of the input declaration it advertised. Changes to names, aliases, order, types, defaults, choices, requiredness, sensitivity, or raw-argument policy make old calls fail with `ToolingInputError` before the body runs. Reconnect the client to load the new catalog, then decide whether to retry. Lando does not reload that session's catalog or replay the failed call automatically. Description-only changes and script-body edits keep the input revision compatible.

## Change a script and run it again

Lando keeps your app's command index current on the host CLI. Any app tooling command or script, `lando --help`, `lando help`, `lando help <task>`, and `lando <task> --help` rebuild it first when it is missing, unreadable, or out of date. You never run `lando app:cache:refresh` just to make a command appear or pick up new metadata, and you never start or rebuild services for that:

| You changed | What happens |
| --- | --- |
| A script body | The next call runs the new body; no rebuild |
| A new or removed script file | The next call or help picks it up |
| A script's front matter, including declaration order | The next call or help picks it up |
| The Landofile, an include, or a file it loads | The next call or help picks it up |
| Lando itself (an upgrade) | The next call or help rebuilds for the new version |

A fast rebuild prints nothing. In a terminal, one that takes longer than about half a second prints one line naming the cause, such as `Updating this app's commands (scripts changed)...`. The rebuild plans the Landofile the same way `lando app:cache:refresh` does, including fetching and pinning includes, without starting services or the provider. Built-in commands such as `lando start` never trigger it, and neither do `lando` calls from inside a container through the host proxy.

If the rebuild fails because of broken YAML, invalid config, a bad tooling definition, or malformed script front matter, the command fails with that error: `LandofileParseError`, `LandofileValidationError`, `BunShellScriptFrontMatterError`, and so on, as `error._tag` in `--format=json`. Fix it and run the command again; Lando does not cache the failure.

Unavailable command metadata produces `ToolingCommandUnavailableError`. Its `reason` tells you what to do:

| `reason` | Next action |
| --- | --- |
| `unknown-command` | Check the name and aliases with `lando help`; the app has no matching command |
| `missing-cache`, `stale-cache`, `invalid-cache` | The app changed while Lando was reading it. Run the command again |

The error also carries `commandId`, `tool`, and `remediation`, with `staleReason` and `sourcePath` when available. Help does not start a provider or fall back to live discovery. To inspect status, run:

```sh
lando help --format=json
```

Read `result.toolingMetadata.status`: `fresh`, `not-app`, or `unavailable`. After a failed rebuild, `status` is `unavailable` with `reason: "rebuild-failed"`, a `remediation`, and the underlying `error` as `{ _tag, message }`; human help prints `This app's commands are unavailable:` with the same message while still listing built-in and plugin commands. Fix the reported problem and run help again. `toolingMetadata` covers only scripts and Landofile tooling; plugin commands report through the separate `result.pluginMetadata` and don't depend on this cache.

For a newly added script with declared inputs, `lando <name> --help` shows those inputs right away. Scripts without input declarations receive `--help` as a raw argument. If any declared flag is named `help` or aliased to `h`, Lando leaves both help spellings to the script's input parser instead of showing its own help.

## List your commands

Run `lando --help` inside the app. Enabled scripts show up under `THIS APP` with their description, next to any Landofile tooling:

```sh
lando --help
```

`lando help --all` prints the same list after every built-in and plugin command. In `--format=json`, your scripts are the `all[]` rows with `source: "tooling"`; plugin commands carry `source: "plugin"`.

## Pass arguments

Without `flags` or `args` declarations, arguments after the command name pass through unchanged and are available as `$1` through `$9`. Save this as `.lando/scripts/stamp.bun.sh`:

```sh
# ---
# desc: Write a version stamp into dist/
# ---
echo "$1" > dist/version.txt
echo "stamped dist/version.txt with $1"
```

Stamp the build with the current commit:

```sh
lando stamp "$(git rev-parse --short HEAD)"
```

Your own shell runs `git` before Lando sees the line, so the script receives the short SHA. Check `dist/version.txt` for that same value.

Bun Shell does not expand `$@` or `$#`, so name each argument you need with `$1`, `$2`, and so on. A script that uses `$@`, `$#`, or another form Bun Shell can't run fails before it starts; see [Write host commands in Bun Shell syntax](#write-host-commands-in-bun-shell-syntax).

Lando reads its own global flags, such as `--format` and `--verbose`, anywhere on the line. Put `--` in front when the script should get them instead:

```sh
lando stamp -- --format=json
```

## Feed a script stdin

Pipe or redirect into the command and the script reads it to the end. Save this as `.lando/scripts/count.bun.sh`:

```sh
# ---
# desc: Count the lines on stdin
# ---
wc -l
```

```sh
printf 'a\nb\nc\n' | lando count
lando count < src/index.html
```

The first prints `3`. Commands inside the script share that input, so a `seed` script can take `lando seed < dump.sql` and hand the dump to whatever client it runs.

Run it from a terminal with nothing piped in and the script inherits your keyboard. Lando retires its task-tree consumer before starting it. stdout and stderr still stream through the byte sink, with registered values masked even when a write splits a secret. The script does not write around that redaction boundary.

Ctrl+C (`SIGINT`) cancels the active command with exit status `130`; `SIGTERM` uses `143`, and closing the terminal (`SIGHUP`) uses `129`. A Lando started with that signal ignored, such as under `nohup`, keeps ignoring it. An interruption-only failure is `CommandInterruptedError`, with the signal when known, rather than internal Effect interruption text. Lando releases scoped resources; if execution or cleanup also failed, those failures remain visible rather than being replaced by a cancellation message. Cancellation does not undo files or other effects the script already produced. Inspect those effects before running the command again.

With `--format=json`, `--format=yaml`, or `--renderer=json`, piped input still arrives but the keyboard does not. A script that waits for typed input reads end of input instead of hanging an automated caller.

## Capture output as JSON or YAML

Add `--format=json` or `--format=yaml` and Lando collects the script instead of streaming it. You get one envelope on stdout with the script's output and exit code under `result`:

Captured `result.stdout` and `result.stderr` are present even for empty output. A result returned through a live sink omits both fields because the sink already received the bytes; MCP carries them in `output.chunks` instead.

```sh
lando stamp abc1234 --format=json
lando stamp abc1234 --format=yaml
```

| Key | What it holds |
| --- | --- |
| `result.stdout` | Everything the script wrote to stdout |
| `result.stderr` | Everything it wrote to stderr |
| `result.exitCode` | The script's exit code |

A script that exits nonzero still gets its output collected, and `lando` exits with that same code. With `--format=json` or `--format=yaml`, the envelope sets `ok: false`, keeps the script payload under `result` (including `result.exitCode`), and adds a tagged `LandoCommandError`. Branch on `result.exitCode` when you care about the script's status; use `ok` and `error._tag` when you care about the command outcome. Without a format flag, output streams to your terminal as it happens. Both formats run the script with the Bun that Lando ships, so a host with no separate Bun install works the same.

The envelope, `--json=<key>`, and `--jq` work the way they do for every other command. See [Script Lando with JSON](../../scripting-with-json/) for the full contract.

## Group commands in folders

Subfolders become namespaces. `.lando/scripts/env/init.bun.sh` is `app:env:init`:

```sh
# ---
# desc: Create .env from .env.example if it is missing
# ---
if test -f .env; then
  echo ".env already exists, leaving it alone"
else
  cp .env.example .env
  echo "created .env"
fi
```

```sh
lando app:env:init
```

The first run prints `created .env`. Run it again and it prints `.env already exists, leaving it alone`. Names with a colon always take the `app:` prefix. Top-level scripts answer to both `lando build` and `lando app:build`.

Lando lowercases each path segment, turns anything outside `a-z`, `0-9`, `_`, and `-` into `-`, collapses repeated `-` into one, and trims `-` from both ends.

A script whose canonical command or active top-level name collides with a built-in command fails the rebuild with `CommandAliasConflictError`, and the invalid command index is not written. For example, `info.bun.sh` collides with `app:info`, while `version.bun.sh` collides with the default `version` alias. Rename the script and run your command again. Disabling or remapping aliases does not free a built-in canonical id such as `app:info`.

Folders do not claim bare namespaced aliases. `.lando/scripts/db/seed.bun.sh` registers `app:db:seed`, so run `lando app:db:seed`, not `lando db:seed`. A plugin command named `db:seed` does not collide with that script. A folder path that produces an existing canonical id, such as `.lando/scripts/cache/refresh.bun.sh` producing `app:cache:refresh`, still fails.

## Use Bun Shell and your host tools

Bun Shell supports pipes, redirection, `$(...)`, `&&`, `||`, environment variables, and `if ... then ... fi`. It is a separate shell language, not Bash, zsh, or a promise of full POSIX shell compatibility. Use the [Bun Shell syntax reference](https://bun.com/docs/runtime/shell) when writing scripts. Commands can use shell builtins or executables found on your host `PATH`. Host tools such as `git`, `curl`, and your package managers must be available in that environment.

### Write host commands in Bun Shell syntax

Every host command uses the same Bun Shell on Linux, macOS, and Windows: `.bun.sh` scripts, `service: ":host"` tooling and event steps, host readiness probes, and `lando shell` lines. A few everyday POSIX forms either fail in Bun Shell or silently mean something else. Write the Bun Shell form instead:

| POSIX habit | Write in a host command |
| --- | --- |
| `${NAME}` | `$NAME`, or `"$NAME"` when a letter, digit, or `_` follows it |
| `${NAME:-default}` | `$NAME`, with the default set in the task's `env:` |
| `echo oops >&2` | `echo oops 1>&2` |
| `cmd > out.log 2>&1` | `cmd &> out.log`, or `&>>` to append |
| `cmd 2>&-` | `cmd 2>/dev/null` to discard the output |
| `$?` | `cmd && echo ok \|\| echo failed` |
| `$@`, `$#`, `$*` | `$1` through `$9` in a script. A `:host` task appends the arguments you pass to its command |
| `$((1 + 2))` | `$(bun -e "console.log(1 + 2)")` |
| `cat <<EOF` here-documents | `printf` or `echo` piped into the command, or a file |
| `for`, `while`, `case`, or a function | A script you run by path; see [Run sh or bash when you need them](#run-sh-or-bash-when-you-need-them) |
| `set -e` | Commands chained with `&&` |
| `command -v NAME`, `type`, `hash` | `which NAME` |
| `source .env`, `. .env` | Values set in the task's `env:` |
| `:` | `true` |
| `{ a; b; }`, `! cmd` | `( a; b )`, `cmd \|\| other` |
| `( a; b ) > out.log` | `( a > out.log; b >> out.log )`, so the second command appends instead of truncating |
| A word broken across lines with `\` | The word on one line |

Lando also rejects `<<<` here-strings, a quote that's never closed, descriptor duplication other than `1>&2` and `2>&1`, such as `3>&1`, and the other builtins Bun Shell lacks, such as `eval`, `exec`, `read`, `trap`, and `shift`. Bun Shell reports those as missing commands and keeps running the rest of the line, so Lando stops first. Text you mean literally still works: `'${NAME}'` and `\${NAME}` aren't flagged.

Lando looks for these forms before running anything, so a host command doesn't quietly pass `${NAME}` through as text or stop with Bun Shell's bare `Redirection with no file` error. Each diagnostic names the form, its column, and the fix:

- `lando app:config:lint` reports a `landofile.host-shell` error for each one in a `:host` tooling or event step and in a host readiness command. In a Landofile, an unescaped `${NAME}` already fails to load (`landofile.load`), so the form lint reports there is the escaped `$${NAME}`, which would reach Bun Shell as `${NAME}`.
- A `:host` step in a lifecycle event such as `pre-start`, or a host readiness command, also stops `lando start` before it changes anything. `lando stop` and `lando destroy` still tear the app down but skip the Landofile's events, as they do whenever the Landofile can't be planned.
- A host tooling task fails with `ToolingCompileError` when you run it, before any of its steps start. A broken task you never run doesn't block the rest of the app, but `lando app:cache:refresh` warns about it (`LANDO_HOST_SHELL_SYNTAX` in `--format=json` output) so you hear about it before you need it.
- A `.bun.sh` script fails with `ToolingCompileError` before it starts, with the line and column. Scripts may use `$1` through `$9`.
- `lando shell` prints the problem for that line and, when the fix is mechanical, offers the corrected line at the next prompt for you to run or edit.

Run lint after you edit a host command:

```sh
lando app:config:lint
```

Container commands are different. They run through the service's own `sh -c`, so `${NAME}` works there, and you write it as `$${NAME}` in a Landofile so Lando passes it through. See [Landofile expressions](../landofile/expressions.mdx#keep-var-and--as-text).

A few differences depend on values or files, so Lando can't see them in the command. Bun Shell keeps a variable's value as one argument instead of splitting it at spaces and doesn't expand patterns inside it, expands `*` patterns you write but leaves `?` and `[...]` as written, and its `echo` prints backslashes as written and treats `-e` as an option. A `*` matches the same files `sh` would, but Bun Shell lists them in directory order instead of sorting them. Like bash, it expands `{a,b}`. Quote your variables, match files with `*`, name the files in order when order matters, such as migrations you pipe to a database, and use `printf` when you need escapes.

#### Run sh or bash when you need them

Loops, functions, and `set -e` belong in a script file that its own shell runs. Call the script from the task, and Lando appends the arguments you pass:

```yaml
tooling:
  seed:
    service: ":host"
    cmd: bash ./scripts/seed.sh
```

`lando seed db/one.sql db/two.sql` runs `bash ./scripts/seed.sh 'db/one.sql' 'db/two.sql'`, so the script reads them as `$1`, `$2`, and `"$@"` like any bash script. This needs `bash` on the host, which macOS and Linux have and Windows does not. For a task that must also run on Windows, write the logic as a Bun program and use `cmd: bun ./scripts/seed.ts`; Lando uses the Bun it ships when your host has none.

Scripts always run from the app root, even when you call them from a subdirectory. Relative paths such as `src/` and `dist/` mean the same thing everywhere in the repo.

Lando resolves the working directory before starting a command, so relative paths and `$PWD` refer to the same directory, including through symbolic links. An explicitly configured `PWD` overrides this default, even when it is empty. Host tooling commands use the same rule. If the working directory is missing, inaccessible, or not a directory, the command does not start; fix the reported directory and rerun it.

## Smoke test the running site

Host scripts can poke the app through its public URL. Save this as `.lando/scripts/smoke.bun.sh`:

```sh
# ---
# desc: Fetch a URL from the running site and fail loudly
# ---
curl -sf "$1"
```

Start the app and pass the `web` URL from `lando info`. Lando adds a port such as `:8443` when 443 was taken:

```sh
lando start
lando info
lando smoke https://web.scripts-demo.lndo.site/version.txt
```

That prints the stamped SHA. Ask for a path that does not exist and `curl -f` exits `22`, so `lando smoke` exits `22` too. You can use that exit code in a git hook.

## Call `lando` from a script

A script can run `lando` like any other host command, so one file can bring the app up and work inside it. Save this as `.lando/scripts/peek.bun.sh`:

```sh
# ---
# desc: Start the app and print the stamp web serves
# ---
lando start
lando exec web -- cat /app/dist/version.txt
```

```sh
lando peek
```

That starts the app, then prints the stamped SHA from inside `web`. The app and its URL stay up after the script exits, the same as a `lando start` you type yourself.

`lando` in a script is the `lando` on your `PATH`. If your `PATH` has none, it is the Lando that started the script, so `./lando peek` from a download folder works too. Call it by name. A path-qualified binary such as `./bin/lando` inside the script still runs as Bun instead of Lando: Bun Shell file mode exports Lando's embedded-Bun switches (`BUN_BE_BUN` and related flags) and has no `unset` for them. That upstream shell limitation also applies to other Bun-compiled CLIs the script starts by path. Prefer the bare `lando` name for nested Lando calls.

Package scripts you run with `lando bun run` follow the same rule: `lando` in them runs Lando, and `bun` runs the Bun the Lando executable provides. A nested `lando bun` inside one of those scripts fails with `BunSelfReentryError` before another Bun child starts; call `bun` directly instead. How `lando bun` reports its child's exit and output is in [Script Lando with JSON](../../scripting-with-json/#capture-bun-backed-commands).

## Run service work from the Landofile

Scripts run on your host. Setting `service: web` in front matter refuses with `NotImplementedError` and points you at a Landofile tooling task. Commands that belong inside a service go in the Landofile:

```yaml
name: scripts-demo
services:
  web:
    type: static
    webroot: dist
tooling:
  curl:
    service: web
    cmd:
      - sh
      - -c
      - 'curl -sf "http://localhost:80/$1"'
      - curl
```

```sh
lando curl version.txt
```

That curl runs inside `web` against nginx on port `80`. If a Landofile task and a script share a name, the Landofile task wins. Drop a `curl.bun.sh` next to that Landofile and `lando curl` still runs in `web`.

## Declare a host task in the Landofile

A one-liner does not need its own file. Set `service: ":host"` on a Landofile task: no services required, no Bun install, and the task's exit code becomes `lando`'s exit code. Host output streams as the command writes it, value-only redacted and byte-exact, the same sink container tooling uses. Task progress stays on stderr, so `lando <task> > out.txt` captures only the command's output. A string `cmd` uses Bun Shell, written in [Bun Shell syntax](#write-host-commands-in-bun-shell-syntax). A list runs as exact arguments with no shell, and the arguments you pass on the line are appended to it:

```yaml
name: host-task-demo
tooling:
  greet:
    description: Say hello from the host
    service: ":host"
    cmd: echo "hello from a host task"
  stamp:
    description: Print a version stamp
    service: ":host"
    cmd: ["printf", "stamped %s\n"]
```

```sh
lando greet
lando stamp abc1234
```

`lando greet` prints `hello from a host task`, and `lando stamp abc1234` prints `stamped abc1234`. Add `--format=json` and the text lands in `result.stdout`, same envelope as a script. Reach for a `.bun.sh` file when the body outgrows one line, or when you want `if`, pipes, and `$(...)` without quoting a shell string inside YAML.
