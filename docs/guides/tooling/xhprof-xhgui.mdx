# Profile PHP requests with XHProf and XHGui

Install the XHProf extension in your PHP service, send each web request's profile to an XHGui service, and read the call graph in your browser.

You need Lando 4 with a ready provider. The default provider is `lando` (managed Podman). Run the host commands from a new app directory for this demo. In an existing app, merge the services, mount, and tooling into your Landofile rather than replacing it.

Use this only for local development. Profiles can contain query parameters, selected server fields, and PHP environment values. This example uses demo database credentials and leaves XHGui's UI and upload endpoint unauthenticated. Don't expose it through a public tunnel or profile requests carrying real credentials or customer data.

## Configure PHP, XHGui, and Postgres

Save this as `.lando.yml` in your app directory:

```yaml
name: xhprof-demo
services:
  app:
    type: "php:8.3"
    primary: true
    build:
      artifact:
        - "pecl install xhprof"
        - "docker-php-ext-enable xhprof"
    mounts:
      - source: "./xhprof.ini"
        target: "/usr/local/etc/php/conf.d/zz-xhprof.ini"
        readOnly: true
  xhgui:
    type: compose
    image: xhgui/xhgui:0.23
    appMount: false
    environment:
      XHGUI_SAVE_HANDLER: pdo
      XHGUI_PDO_DSN: "pgsql:host=profiles;dbname=xhgui"
      XHGUI_PDO_USER: xhgui
      XHGUI_PDO_PASS: xhgui
    endpoints:
      - _tag: internal
        name: ui
        protocol: http
        port: 80
    dependsOn:
      profiles:
        condition: service_healthy
  profiles:
    type: postgres
    creds:
      user: xhgui
      password: xhgui
      database: xhgui
tooling:
  composer:
    service: app
    cmd: [composer]
    dir: /app
```

- `app` runs PHP 8.3 under Apache. The two `build.artifact` steps compile and enable XHProf when Lando builds the image, and the mount drops a PHP ini file into the image's `conf.d` directory.
- `xhgui` runs the upstream XHGui image, which serves its UI on port 80. `appMount: false` keeps your source out of it, and Lando plans no home store for a Landofile-supplied image. Keep the explicit HTTP `ui` endpoint so Lando can proxy port 80 and give the UI its own `*.lndo.site` URL.
- `profiles` is the Postgres store. XHGui creates its `results` and `watches` tables on first use. `dependsOn` holds XHGui until the Postgres healthcheck passes.
- `composer` runs Composer inside `app`. The PHP service ships Composer, so there is nothing else to install.

Save this as `xhprof.ini` next to the Landofile:

```ini
auto_prepend_file = /app/xhgui-header.php
```

Save this as `xhgui-header.php` next to the Landofile:

```php
<?php
$autoload = '/app/vendor/perftools/php-profiler/autoload.php';
if (PHP_SAPI === 'cli' || !is_file($autoload)) {
    return;
}
require_once $autoload;

try {
    $profiler = new \Xhgui\Profiler\Profiler([
        'save.handler' => \Xhgui\Profiler\Profiler::SAVER_UPLOAD,
        'save.handler.upload' => ['url' => 'http://xhgui/run/import'],
    ]);
    $profiler->start();
} catch (\Throwable $e) {
    error_log('xhgui: ' . $e->getMessage());
}
```

PHP runs this file before every script. It skips the CLI, so `lando composer` and other commands aren't profiled, and it does nothing until the profiler package is installed. Web requests upload their profile to `http://xhgui/run/import` when they finish; `xhgui` is the service key on the app network.

Save this as `index.php` so there is something worth measuring:

```php
<?php
function fib(int $n): int
{
    return $n < 2 ? $n : fib($n - 1) + fib($n - 2);
}

echo 'fib(25) = ' . fib(25) . "\n";
```

## Start and install the profiler

```sh
lando start
lando exec app -- php -m
lando composer require perftools/php-profiler
```

Check that `xhprof` and `curl` appear in the module list. The profiler uses PHP's cURL extension to upload runs. Composer writes `composer.json` and `composer.lock` to your app directory; commit both so the next `lando composer install` gets the same profiler release. The `vendor` directory stays inside the `app` service, not on your host.

## Profile a request

Run `lando info` and open the `app` URL in your browser. The page prints `fib(25) = 75025`.

Open the `xhgui` URL from `lando info`. Check that the run list shows a run for `/`, then open it and check that its function table lists `fib`. Every page load adds a run, so reload a few times to compare.

If no run appears, check that `xhprof` and `curl` are in `lando exec app -- php -m` and that `lando exec app -- ls /app/vendor/perftools/php-profiler` lists the package. Check `lando logs -s app` for `xhgui:` setup errors.

The profiler suppresses upload exceptions during shutdown, so an empty app log doesn't prove that a profile was saved. Check `lando logs -s xhgui` and `lando logs -s profiles` for import or database errors. After correcting an error, reload the app page and look for a new run containing `fib`.

## Large profiles disappear without an error

A request that calls many distinct functions can produce a profile of several megabytes. The upstream XHGui image limits uploads in two places: its nginx site config sets `client_max_body_size 5M`, and its PHP config keeps the default `post_max_size = 8M` and `memory_limit = 128M`. When an upload is too large, nginx or XHGui rejects it. Because the profiler suppresses upload exceptions, the page still loads normally, no run appears, and the app log stays empty. `upload_max_filesize` doesn't apply, because the profiler sends a raw JSON body rather than a file upload.

To reproduce it, save this as `big.php` next to the Landofile. It defines and calls `n` small functions, so `n=120000` produces a profile of about 10 MB:

```php
<?php
ini_set('memory_limit', '1G');
$n = (int) ($_GET['n'] ?? 20000);
for ($i = 0; $i < $n; $i++) {
    eval("function profile_padding_function_$i() { return $i; }");
    ("profile_padding_function_$i")();
}
echo "called $n functions\n";
```

Request it from inside `app`, then read the XHGui log:

```sh
lando exec app -- curl -s "http://localhost/big.php?n=120000"
lando logs -s xhgui
```

Check that the log shows `client intended to send too large body` and a `413` for `POST /run/import`. That proves nginx rejected the upload before XHGui saw it.

To raise the limits, copy the image's nginx site config to your app directory:

```sh
lando exec xhgui -- cat /etc/nginx/http.d/default.conf > xhgui-nginx.conf
```

In `xhgui-nginx.conf`, change `client_max_body_size 5M;` to `client_max_body_size 100M;`. Save this as `xhgui-php.ini` next to the Landofile:

```ini
post_max_size = 100M
memory_limit = -1
```

XHGui decodes the whole profile in memory, so a large profile needs far more memory than its upload size. `-1` removes the limit; use this only for local profiling. Mount both files into the `xhgui` service:

```yaml
services:
  xhgui:
    type: compose
    image: xhgui/xhgui:0.23
    appMount: false
    mounts:
      - source: "./xhgui-nginx.conf"
        target: "/etc/nginx/http.d/default.conf"
        readOnly: true
      - source: "./xhgui-php.ini"
        target: "/etc/php83/conf.d/zz-xhgui.ini"
        readOnly: true
```

Keep the rest of the `xhgui` service as it was. The profiler gives each upload 3 seconds by default, so a large profile can also time out. Raise `timeout` in `xhgui-header.php`:

```php
        'save.handler.upload' => [
            'url' => 'http://xhgui/run/import',
            'timeout' => 30,
        ],
```

Restart and repeat the request:

```sh
lando restart
lando exec xhgui -- grep client_max_body_size /etc/nginx/http.d/default.conf
lando exec xhgui -- php-fpm -i
lando exec app -- curl -s "http://localhost/big.php?n=120000"
lando logs -s xhgui
```

Check that `client_max_body_size` reads `100M` and that `php-fpm -i` reports `post_max_size => 100M` and `memory_limit => -1`. That proves XHGui loaded both files. Check that the log now shows a `200` for `POST /run/import`, then open the `xhgui` URL and check that the run list shows `/big.php?n=120000`. That proves the large profile was saved.

## Keep or remove the profiles

`lando destroy -y` removes the app's containers and networks but keeps its named volumes: the `profiles` data store and the `vendor` shadow, so saved runs and the installed profiler are still there after the next start:

```sh
lando destroy -y
```

Add `--volumes` only when you want to delete the app's named volumes, including every saved profile. Your source files stay on the host.
