# Install Composer dependencies on start

[Composer on PHP](composer-php.mdx) covers routing a `composer` tooling task. This guide makes `composer install` part of the build so you do not run it by hand after every `lando start`.

Put it under `build.app`. It runs every time the app starts or rebuilds, after the project code is mounted:

```yaml
name: php-composer-workflows-demo
services:
  appserver:
    type: "php:8.3"
    primary: true
    build:
      app:
        - "composer install --no-interaction --no-progress --no-dev"
tooling:
  composer:
    service: appserver
    cmd:
      - sh
      - -c
      - composer "$@"
      - composer
```

`build.app` runs after the code is mounted, so `composer install` sees `composer.json` and writes `vendor/` into the project. The flags keep it non-interactive, quiet, and production-mode.

## Install global tools in the image

Put the tools on `composer.packages` and Lando bakes them into the image for you:

```yaml
services:
  appserver:
    type: "php:8.3"
    composer:
      version: "2"
      packages:
        squizlabs/php_codesniffer: "^3.10"
        phpstan/phpstan: "^1.11"
```

The object form is additive. `composer: "2"` and `composer: false` keep working, and `composer: { version: "2" }` with no packages plans exactly like the string form.

Packages install with `composer global require` into `/usr/local/composer`, with the generated binary proxies written to `/usr/local/bin`, so `phpcs` and `phpstan` are callable by name without editing `PATH`. The Composer home is left world readable so a non-root service user can run them too.

Lando normalizes the map before it reaches the build: package names and version constraints are validated at plan time, and the packages are installed in sorted order. Reordering the YAML does not rebuild the image; adding, removing, or re-pinning a package does, because the normalized list is part of the image build key.

Names must be lowercase `vendor/name`, and constraints are ordinary Composer constraints such as `^13.0`, `13.0.0`, or `>=1.0,<2.0`. Anything else fails at plan time, before any container work, with the offending package named.

A custom `image:` skips the Lando-managed Composer install but still installs your packages, so bring an image that already ships `composer`.

If you would rather script it yourself, a `build.artifact` step also runs while the image is baked, before project code is mounted:

```sh
composer global require squizlabs/php_codesniffer
```

## Re-run after composer.json changes

The first `lando start` (and every `lando rebuild`) re-runs the `build.app` composer install, downloading packages not already in the Composer cache volume. After you change `composer.json`:

```sh
lando rebuild -y
```

## Pick a Composer version

Stock PHP services install checksum-pinned Composer `2.10.2`. Set `composer:` on the PHP service to track that major channel, pin an exact release, or skip the install:

```yaml
services:
  appserver:
    type: php:8.5
    composer: "2"          # default; the 2.10.2 channel
    # composer: "2.10.2"   # optional exact pin on that channel
    # composer: false      # skip Composer entirely
```

Exact pin `2.7.7` is valid on PHP 8.1 through 8.4 and fails at plan time on PHP 8.5+.

Unknown versions fail at plan time with remediation. Changing `composer:` rebuilds the artifact layer because the selected pin is part of the image build key.
