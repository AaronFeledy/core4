# Set tooling defaults and command aliases

Use `toolingDefaults` when most commands run in the same service, directory, or environment. Each task inherits those values, then its own `service`, `dir`, `env`, and `vars` win where they overlap.

```yaml
toolingDefaults:
  service: web
  dir: /app
  env:
    APP_ENV: development
  vars:
    MODE: default

tooling:
  build:
    cmd: bun run build
  lint:
    service: worker
    dir: /app/tools
    env:
      APP_ENV: ci
    cmd: bun run lint
```

Here, `build` uses every default. `lint` targets `worker`, runs from `/app/tools`, and replaces `APP_ENV`, while still inheriting `MODE`. A task's `dir` is the working directory inside its target service. Lando does not resolve it against the host app directory.

## Read precedence

Task-local values win first. Values from included tooling fragments come next. App-wide `toolingDefaults` fill whatever remains.

## Remap a command

Use `commandAliases.custom` to give a canonical command an app-specific shortcut. The canonical id stays put, so scripts can keep using it.

```yaml
tooling:
  greet:
    service: web
    cmd: echo hello

commandAliases:
  custom:
    hi: app:greet
```

Run `lando app:cache:refresh` after changing aliases. Then both forms resolve to the same command:

```sh
lando hi
lando app:greet
```

Set `enabled: false` to suppress every top-level alias in this app, or add tokens under `disabled` to remove only those shortcuts. Canonical ids remain available.
