# Set tooling defaults and command aliases

Add `toolingDefaults` to your `.lando.yml` when most commands run in the same service, directory, or environment. The fragment below assumes your app defines `web` and `worker` services with the shown directories and Bun package scripts. Each task inherits those values, then its own `service`, `dir`, `env`, and `vars` win where they overlap.

```yaml
toolingDefaults:
  service: web
  dir: /app
  env:
    APP_ENV: development
  vars:
    MODE: default

tooling:
  build:
    cmd: bun run build
  lint:
    service: worker
    dir: /app/tools
    env:
      APP_ENV: ci
    cmd: bun run lint
```

Save the Landofile, run `lando app:cache:refresh` from the app directory, and start the services before executing the tasks.

Here, `build` uses every default. `lint` targets `worker`, runs from `/app/tools`, and replaces `APP_ENV`, while still inheriting `MODE`. A task's `dir` is the working directory inside its target service. Lando does not resolve it against the host app directory.

## Read precedence

Task-local values win first. Values from included tooling fragments come next. App-wide `toolingDefaults` fill whatever remains.

## Remap a command

Use `commandAliases.custom` to give a canonical command an app-specific shortcut. The canonical id stays put, so scripts can keep using it.

A remap can't free `run`, `scratch`, or a `scratch:*` name for a tooling task. Those belong to scratch apps, and `lando app:config:lint` and `lando start` reject a task named after one.

```yaml
tooling:
  greet:
    service: web
    cmd: echo hello

commandAliases:
  custom:
    hi: app:greet
```

Run `lando app:cache:refresh` after changing aliases. Then both forms resolve to the same command:

```sh
lando hi
lando app:greet
```

Set `enabled: false` to suppress every top-level alias in this app, or add tokens under `disabled` to remove only those shortcuts. Canonical ids remain available.

The target can also be a plugin command id. With the bundled `@lando/sql` plugin, this makes `lando dump` run `db:export`, and `lando help --format=json` then lists `db:export` with `typeable: "dump"`:

```yaml
commandAliases:
  custom:
    dump: db:export
```

## Plugin aliases

A plugin can ship its own shortcuts in its manifest: colon-form `aliases` such as `db:dump`, or a `topLevelAlias` such as `export`. Both route to the plugin command without any Landofile change. A plugin alias loses to anything Lando already owns: a built-in command or alias, a core help topic such as `recipes`, a reserved token, or a tooling task in the current app. Lando drops the colliding alias, keeps the command reachable by its id, and lists the conflict in `lando help --format=json` under `result.pluginMetadata.diagnostics`; `lando help --all` lists the conflicts under `Plugin command conflicts`. When two plugins claim the same alias, the one found first in discovery precedence wins. A plugin can't shadow a built-in command, and installing one never makes `lando app:cache:refresh` fail.
