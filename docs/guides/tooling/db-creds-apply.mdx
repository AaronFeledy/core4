# Keep database credentials in sync

Edit `creds` in your Landofile and run `lando start` from your app directory. For catalog PostgreSQL, MySQL, MariaDB, MongoDB, and SQL Server services, Lando applies the new credentials to the running database without dropping or renaming existing users or databases. If your application keeps its own connection settings, update those separately.

## Change a PostgreSQL password and check your data

If you already have data, change only `creds.password`, run `lando start`, and check that your app can still read a known row. To try that sequence without touching your app, save this `.lando.yml` in a new directory. Use the example password only in this throwaway app.

```yaml
name: db-creds-apply-pg
services:
  db:
    type: postgres
    creds:
      database: credential_demo
      password: pg-fixture-pass-one
  client:
    type: compose
    image: docker.io/library/postgres:16
    appMount: false
    home: false
    depends_on:
      db:
        condition: service_healthy
    environment:
      PGUSER: "{{ services.db.creds.user }}"
      PGPASSWORD: "{{ services.db.creds.password }}"
      PGCONNECT_TIMEOUT: "5"
    entrypoint: [/bin/sh, -c]
    command:
      - |
        psql -X -w -h db -d credential_demo -tAc 'SELECT 2616;' >/tmp/boot-select 2>&1
        printf 'boot-select status=%s\n' "$?" >>/tmp/boot-select
        exec sleep infinity
```

The `client` service stands in for your app. It waits for `db` to be healthy, runs one query when it boots, and saves the output and exit status in `/tmp/boot-select`.

Start the app, read the result of that boot query, and add a marker row before you change the password:

```sh
lando start --format=json
lando exec client -- cat /tmp/boot-select
lando psql -c "CREATE TABLE creds_marker(id int PRIMARY KEY); INSERT INTO creds_marker(id) VALUES (2457);"
```

Set `services.db.creds.password` to `pg-fixture-pass-two` in `.lando.yml`, leaving the database name unchanged. Then run:

```sh
lando start --format=json
lando exec client -- cat /tmp/boot-select
lando psql -tAc "SELECT id FROM creds_marker WHERE id = 2457;"
lando db:export marker.sql --format=json
lando start --format=json
```

Both times, `/tmp/boot-select` holds `2616` and `boot-select status=0`. The password edit replaces `client`, and its one query at boot already uses the new password. The first start after the edit reports one `credentialChanges` entry for `db` with `changedMembers: ["password"]`. The `creds_marker` query returns `2457`, and `marker.sql` contains the row. The last start omits `credentialChanges`: Lando skips credential work for an unchanged service that's already running. Without `--format=json`, look for the start message that names the service and the credential fields that changed, not their values.

## Point `creds.database` at the right data

Changing the name does not move any data. If Lando creates an empty database on existing storage, it warns with `LANDO_DATABASE_CREATED_ON_EXISTING_STORAGE` and lists other databases it found. To use the old data, set `creds.database` back to the original name and run `lando start`. If you meant to use a new database, [import or restore a backup](./db-import-export.mdx) into it. In MongoDB a name-only edit doesn't create an empty database or report a `database` change. MongoDB creates the database on the first write.

## Start services that wait on the database

A service that requires a Lando-managed catalog database with `condition: service_healthy` waits for two checks. The usual readiness probe runs first. Then Lando verifies or applies the database's `creds` before it starts or replaces the waiting service. Its first connection at boot can use the configured user, password, and database, as `client` does in the example above.

If credential preparation fails for a required dependency, the error names the database and the service that was waiting. That check stops Lando from starting or replacing the waiting service at this point. It doesn't undo any work already done by the command. With `required: false`, a credential refusal doesn't block the waiting service.

If the error says a write may have taken effect, inspect the database before you try again. Fix the issue named in the error, then retry the same command with the same service selection. Don't delete the database volume to retry.

Lando doesn't restart a waiting service that's already running and isn't being replaced. If no required edge blocks the command, it can finish with a warning even when Lando couldn't verify or apply the database credentials.

## Check credentials for a custom image or launcher

When Lando starts or replaces a typed database service it can't manage, or its connection settings change, Lando checks the configured login without changing the database. `LANDO_DATABASE_CREDENTIALS_REJECTED` means the server rejected the login. Restore the previous credentials or update the account in your image. For `LANDO_DATABASE_MISSING`, restore the previous database name or make the configured database accessible in your image. `lando db:creds:apply` does not manage custom images or launchers. Follow [custom-image opt-in support](https://github.com/AaronFeledy/core4/issues/2619) for updates.

## Preview and apply a repair if start can't authenticate

If you get `LANDO_DATABASE_ADMIN_SEED_UNAVAILABLE`, Lando couldn't read or create its private administrator seed. For MySQL, MariaDB, MongoDB, and SQL Server, Lando skips adopting `lando_admin` and still tries the previous or desired administrator credentials. Check ownership and permissions on `db-admin/key.v1` in your Lando data directory, or restore the original seed from backup. Don't replace an existing seed.

If you get `LANDO_DATABASE_CREDENTIAL_CONVERGENCE_FAILED`, Lando couldn't verify or apply the credentials. This can happen if you restored a volume from another machine or changed the administrator password outside Lando. `lando db:creds:apply` needs a running catalog database already recorded for this app. The desired and applied database must agree on the provider, image, launcher, and owned storage. A failed start does not establish those prerequisites. If they hold, preview the repair and check the listed changes before applying them:

```sh
lando db:creds:apply --service db --format=json
lando db:creds:apply --service db --yes --format=json
```

Replace `db` with your service name, or omit `--service` if there's only one database service. The first command is read-only and reports `planned` or `already-matched`. The second applies the changes and reports `applied` if any were needed. If the result includes `next`, run that command to refresh Lando-managed container settings, then check that your app can read its data. Applying credentials doesn't update an open client session or rewrite app-owned config files.

If the known administrator logins fail, enter the **current** administrator password at the masked prompt. For PostgreSQL or MongoDB, pass `--admin-user <login>` if you're using a different existing administrator login. To supply the password non-interactively, pipe it to either command and add the `-` argument. Lando reads it only if its known administrator paths fail. Keep the password out of command arguments and shell history.

Lando uses its own `lando_admin` account for routine changes. If the warning says that account exists but Lando can't verify it, restore the original private key at `db-admin/key.v1` in your Lando data root if you still have it. Otherwise ask a database administrator to resolve the account conflict. Lando won't take over a user account with that name. Run `db:creds:apply` directly from a terminal, not from an MCP client or a Landofile event step.
