# Run a git worktree as its own Lando app

Give each `git worktree` its own app name, URL, and database, then copy the main checkout's data into it with one command. A feature branch, a hotfix, and a coding agent can each run a copy of the same repo at once. You need Lando 4 with a ready provider. The default provider is `lando` (managed Podman).

The commands below use `shop` as the main checkout and `shop-feature` as the worktree, side by side in one parent folder. This is the main checkout's `.lando.yml`:

```yaml
name: shop
services:
  web:
    type: php:8.4
    primary: true
    environment:
      DB_HOST: database
      DB_NAME: "{{ services.database.creds.database }}"
  database:
    type: postgres
```

Ignore the per-checkout file once, in the main checkout's `.gitignore`. Every worktree shares it:

```text
.lando.local.yml
```

Keep the main app running. The worktree copies its database straight from the running containers, so there is no dump file to manage.

## Add the worktree

```sh
git worktree add ../shop-feature -b feature
cd ../shop-feature
```

The worktree has the same `.lando.yml`, so it also claims `name: shop`. Start it like that and Lando stops with a `VolumeOperationError` that says the two apps share an app name. Two checkouts don't get to fight over one database.

## Rename the worktree in `.lando.local.yml`

Save this as `.lando.local.yml` in the worktree. The committed Landofile stays untouched:

```yaml
name: shop-feature
```

The new name gives the worktree its own containers, volumes, database, and hostname. That's the only change a worktree needs. In a worktree, `.git` is a one-line file that points at the main checkout's `.git` directory; on Linux, Lando mounts that directory into the container at the same path, so `git` works at `/app` like it does in the main checkout. See [Exclude paths from the app mount](../setup/file-sync-excludes.mdx#git).

Check the layer took:

```sh
lando app:config --format=json
```

`result.app` reads `shop-feature`.

## Start the worktree

```sh
lando start
lando info
```

The worktree serves at `web.shop-feature.lndo.site` while the main checkout keeps `web.shop.lndo.site`. Both run at the same time. Open the URLs `lando info` prints.

The database name defaults to the app name, so the worktree's database is `shop-feature`. `DB_NAME` comes from the resolved credentials, so it follows along:

```sh
lando exec web -- printenv DB_NAME
```

That prints `shop-feature` here and `shop` in the main checkout. Build connection settings from `{{ services.database.creds.* }}` and nothing in your code has to know which checkout it's in.

## Seed the worktree's database

Copy the main checkout's database into the worktree, then count rows in a table you know is there. This sample's database has a `products` table:

```sh
lando db:seed --from-app shop
lando psql -tAc 'SELECT count(*) FROM products;'
```

`--from-app` names a running app by its id, the `name` in its Landofile. Lando streams a logical dump out of that app's database container, through a checked temp file in its own scratch space, and into this one. Nothing lands in either checkout, and credentials never hit the command line. `--from-path ../shop` picks the source by folder instead, and `--from-service` picks the database service when the source has more than one. Both apps need the same database type.

`db:seed` only loads into a database Lando freshly created that nothing has written to yet. No prompt, no `--yes`. Seed once. A second `db:seed` fails with `SqlSeedStateError`. Snapshot the seeded database so you can get back to it without the main checkout:

```sh
lando db:snapshot --label seeded
```

To reseed, delete the worktree's volumes, start fresh, and seed from that snapshot. This throws away the worktree's database:

```sh
lando destroy -y --volumes
lando start
lando db:seed --snapshot seeded
```

## Snapshot before risky work

Take a snapshot before a migration, list it, and roll back when the migration eats a table:

```sh
lando db:snapshot --label before-migration
lando db:snapshots
lando db:restore before-migration --yes
```

`db:restore` takes a label or the id `db:snapshots` prints first in each entry. Reused a label? Restore fails with `SnapshotAmbiguousError` and lists the matching ids, newest first. Pass one of those.

Snapshots belong to the checkout that took them. To see what the main checkout has saved, list its snapshots from the worktree:

```sh
lando db:snapshots --from-app shop
```

For snapshots, `--from-app` only matches checkouts of the same Git repository, and `--from-path ../shop` selects the main checkout by folder instead. Listing is as far as it goes: passing one of those ids to `db:restore` or `db:seed --snapshot` in the worktree fails with `SqlRecoveryUnavailableError`, because a snapshot is a physical copy of another checkout's database. Move data between checkouts with `db:seed --from-app`, or with `db:export` and `db:seed <file>` when the source isn't running.

## Remove the worktree

Destroy the app before you delete its folder. `--volumes` deletes the worktree's database; drop it to keep the data:

```sh
lando destroy -y --volumes
cd ../shop
git worktree remove ../shop-feature
```

Deleted the folder first? `lando doctor` reports `missing-app-root` for it and prints the cleanup command with the old path:

```sh
lando destroy --root /path/to/shop-feature -y --volumes
```
