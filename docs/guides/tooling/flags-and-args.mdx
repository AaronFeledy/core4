# Declare flags and args on a tooling task

Add `flags:` and `args:` to a task in your `.lando.yml` when you want Lando to validate input before the command runs. The following fragment assumes your app has a service named `web`. Declared input shows up in `lando <task> --help`, gets checked against choices and requiredness, and is available to the task by name.

```yaml
tooling:
  greet:
    description: Greet a target environment
    service: web
    flags:
      name:
        alias: n
        description: Who to greet
        default: world
      loud:
        boolean: true
        description: Shout the greeting
    args:
      target:
        order: 0
        required: true
        choices: [dev, prod]
        description: Environment to greet
    cmd: echo greeting
```

Save the file and run `lando app:cache:refresh` from the app directory. Check `lando greet --help` for the declared flags and argument, then start `web` before running these examples. The task below validates the inputs but always runs `echo greeting`; it does not interpolate them into the greeting:

```sh
lando greet dev -n team
lando greet prod --loud
```

Host `.bun.sh` scripts support the same nested input declarations in their comment front matter. Use `LANDO_FLAG_<NAME>` and `LANDO_ARG_<NAME>` inside those scripts to read the resolved values. See [Declare flags and read inputs by name](../bun-shell-scripts/#declare-flags-and-read-inputs-by-name) for a working host example; service-targeted scripts still require a Landofile task.

## Declare flags

Each key under `flags:` is one `--flag`. Every option is optional; an empty object still declares the flag.

| Key | What it does |
| --- | --- |
| `alias` | Short form, so `-n` means `--name` |
| `default` | Value used when the flag isn't passed |
| `choices` | Allowed values; anything else is rejected |
| `required` | Fails the run when the flag is missing and there's no default |
| `boolean` | Boolean input: `--flag` means `true`; `--flag=true` and `--flag=false` set it explicitly |
| `description` | Help text for `lando <task> --help` |
| `sensitive` | `true` protects supplied values in Lando output, errors, events, and traces |

A `boolean` flag can't take `choices` or a string `default`. Explicit false overrides a true default, both on the CLI and in named JSON input. For example, to default `loud` to true in the task above, use:

```yaml
flags:
  loud:
    boolean: true
    default: true
```

After refreshing the command cache, `lando greet dev --loud=false` binds `loud` to false. `--loud` and `--loud=true` bind it to true; repeated flags use the last occurrence. Lando does not generate `--no-loud`. The space-separated spelling `--loud false` sets `loud` to true and leaves `false` as a positional token, not a boolean value.

For a command that accepts only argv, Lando forwards value flags as `--name=value`, true as `--name`, and false by omitting the positive switch. This is a forwarding rule, not a promise to turn off the child program's own default. Lando does not invent a downstream negation flag. A `.bun.sh` script receives the actual boolean through `LANDO_INPUT` and `LANDO_FLAG_LOUD`, so it can implement either branch directly.

MCP, structured event, and library calls keep declared inputs as named maps until an execution adapter needs argv. Defaults and validation run once against the resolved task, after normal task precedence and late connection-client resolution. Omitted values, empty strings, and false are distinct; a supplied false or empty string is not replaced by a default.

Retained callers carry the discovered input revision. Changes to names, aliases, order, types, defaults, choices, requiredness, sensitivity, or raw-argument policy cause `ToolingInputError` before execution. Refresh command metadata and reconnect the MCP client, or resolve the event's command again, before retrying. Description and body changes do not change the input revision. There is no automatic catalog reload or replay.

## Declare arguments

Positional input goes under `args:`. `order` fixes the position, starting at `0`, and Lando reads positionals in that order no matter how you list the keys in YAML.

```yaml
args:
  target:
    order: 0
    required: true
    choices: [dev, prod]
  label:
    order: 1
    default: latest
```

`choices`, `default`, `required`, `description`, and `sensitive` behave the same as they do for flags. A few layout rules apply on top:

- Either every arg declares `order` or none do. Leave them all out and the order follows the YAML key order; mix the two and the Landofile is rejected.
- Two args can't share an `order`. Gaps are fine: `0` and `5` work, `0` and `0` don't.
- A required arg can't come after an optional one.

Named arguments retain their names; order matters when reading or producing argv. A trailing optional argument can be left off. For an argv-only task, an absent argument before a later value creates a gap that argv cannot represent. Lando refuses that projection with `ToolingInputError` rather than moving the later value into the wrong slot. A later default can create the same gap:

```yaml
tooling:
  tag:
    description: Tag a release
    service: web
    args:
      label:
        order: 0
        description: Release label
      channel:
        order: 1
        default: stable
        description: Release channel
    cmd: echo tagging
```

`lando tag v1` runs with `channel=stable`, and `lando tag v1 beta` runs with `channel=beta`. Plain `lando tag` fails: `channel` picks up `stable` from its default while `label` has nothing, and the error names `label` in its `field`. Supply the label, give it a default, or remove the later default if omission is intended.

A `.bun.sh` script is map-capable instead: MCP can send only `args.channel` and the script receives that value in `LANDO_ARG_CHANNEL` while `label` stays absent from `LANDO_INPUT.args`. No positional gap is compacted and no argv is synthesized. Required arguments still must be supplied. See [Drive Lando through MCP](../../agent-native/mcp/).

## Protect sensitive values

Set `sensitive: true` on a flag or argument, including one named `note` or another name that does not suggest a credential. The existing secret-name heuristic also marks inputs sensitive; `sensitive: false` is not an opt-out. Lando rejects defaults and choices on effectively sensitive declarations so credential literals cannot enter cached metadata or catalogs. The declaration exposes sensitivity safely, including `writeOnly: true` in MCP's input schema.

Values remain literal: this annotation does not enable expressions or secret-provider lookup. Lando redacts supplied sensitive values before its output, errors, events, or traces become observable, including invalid, stale, and disabled calls. It cannot protect arbitrary files or external logs written by your command. Use the [fake-value script example](../bun-shell-scripts/#mark-sensitive-inputs) to verify the boundary without exposing a real credential.

## Forward undeclared input

Declaring input is opt-in. A task with no `flags:` or `args:` forwards everything you type straight to the command, unparsed:

```yaml
tooling:
  npm:
    service: web
    cmd: npm
```

`lando npm install --save-dev vitest` hands `install --save-dev vitest` to `npm` untouched. Add `flags:` only when you want Lando to check the input first. Raw tails are for undeclared passthrough, not a way to fill gaps in named arguments. Do not mix declared named input with a raw tail; Lando rejects the ambiguous call. Prefer named maps for declared MCP, event, and library inputs.

## Pick the service from a flag

Set `service: ":<flag-name>"` and the task runs in whichever service the flag names. Lando resolves the target from the validated value, so `choices` and `default` apply before anything runs.

```yaml
tooling:
  deploy:
    description: Run against a chosen service
    flags:
      service:
        alias: s
        choices: [web, worker]
        default: web
    service: ":service"
    cmd: echo deploying
```

`lando deploy -s worker` runs in `worker`. Plain `lando deploy` falls back to `web`. Leave out `default` and skip the flag, or name a service that isn't in the app, and the run fails before any command starts.

## Turn a task off

Set a task to `false` to drop an inherited or service-type task of the same name:

```yaml
tooling:
  legacy: false
  old-build: false
```

Both spellings replace the inherited definition wholesale. The task disappears from `lando --help` and the MCP tooling catalog. Calling it directly fails with `ToolingDisabledError`, even when a stale command cache still lists it.

Use `disabled: true` inside an object when you want to keep your authored command and metadata in the Landofile but refuse to run it:

```yaml
tooling:
  legacy:
    description: Retired task
    disabled: true
    service: web
    cmd: echo legacy
```

This object can merge with an object task from a lower config layer. An authored task always replaces a service-type task of the same name, so this does not preserve a service type's definition. Deleting the key lets an inherited task return; use `false` when it must stay off.

For a `.bun.sh` script, put `# disabled: true` inside its front-matter block and refresh the command cache. It is hidden from listings, help, and the MCP tooling catalog, and direct calls fail with `ToolingDisabledError` without running the body.
