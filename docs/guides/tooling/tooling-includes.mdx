# Tooling includes

Tooling fragments load through the canonical `includes:` surface with `kind: tooling`. The
`toolingIncludes:` shorthand resolves through the same machinery, so both spellings produce the
same commands wherever both are accepted. Inside a tooling fragment only the `toolingIncludes:`
spelling nests further fragments; a bare `includes:` key in a fragment fails closed with a tagged
`LandofileIncludeError`.

```yaml
name: tooling-includes-demo
runtime: 4
includes:
  - source: ./docs/.lando.tasks.yml
    kind: tooling
    namespace: docs
    aliases: [documentation]
    excludes: [publish]
    vars:
      DOCS_PORT: 4321
toolingIncludes:
  api:
    file: ./api/.lando.tasks.yml
    internal: true
services:
  web:
    type: node
    primary: true
tooling:
  build:
    service: web
    cmd: bun run build
```

## The resolution contract

Included tasks register beneath the include namespace inside the task's command namespace:
`app:<namespace>:<task>`. `flatten: true` registers included tasks without the namespace prefix.
`internal: true` marks every task the include contributes as internal, so it stays out of command
listings while remaining callable. `aliases: [documentation]` aliases the include namespace at the
same command-namespace level, and `excludes: [publish]` removes tasks from the include before
flattening or namespace registration.

Include-level `vars: { DOCS_PORT: 4321 }` apply to every included task unless the task defines the
same var. `optional: true` suppresses missing-fragment errors instead of failing the load. Fragments
that include each other fail closed with a tagged `ToolingIncludeCycleError`.
