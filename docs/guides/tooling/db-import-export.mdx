# Import and export app databases

Use `lando db:import` and `lando db:export` for dump files. Use `lando db:snapshot` and `lando db:restore` for volume snapshots. Use `lando db:reset` when you want an empty database. Use `lando db:seed` to fill a database Lando freshly created from a dump, a snapshot, or another running app.

A single database service needs no `--service` flag. Two or more database services require `--service <name>`.

```sh
lando db:export dump.sql.gz
lando db:export dump.sql.zst
lando db:import dump.sql.gz --yes
lando db:import dump.sql.zst --yes
```

`.gz` and `.zst` compress and decompress on the host process. The default export name stays `<service>.sql.gz` when you omit a path. Import trusts magic bytes, so a gzip or zstd dump still decompresses if the suffix is missing. Host compression stages the uncompressed dump in a temp file, so a huge dump pays disk twice. Credentials stay in the service environment, not on argv.

## Dump files

`db:export` writes `<service>.sql.gz` in the current directory when you are inside the app, otherwise the app root. Relative paths resolve the same way.

```sh
lando db:export backups/app.sql.gz --service database
lando db:export backups/app.sql.zst --service database
lando db:import backups/app.sql.gz --service database --yes
lando db:import backups/app.sql.zst --service database --yes
```

MySQL, MariaDB, Postgres, and MongoDB stream through the client. SQL Server uses `sqlcmd` backup and restore files.

## Stream a dump through stdout or stdin

Pass `-` as the dump path. `db:export -` writes the dump on stdout and the checksum on stderr. `db:import - --yes` reads stdin. `-` does not skip confirmation: stdin is the dump, so you still pass `--yes`. Empty stdin (`</dev/null`) fails.

```sh
lando db:export - > dump.sql
lando db:export - | gzip > dump.sql.gz
lando db:import - --yes < dump.sql
```

Export to stdout is uncompressed. There is no `--compression` flag, and `/dev/stdout` has no suffix, so pipe through `gzip` or `zstd` when you want a compressed file. Named pipes and process substitution stay pipes for an uncompressed dump: Lando writes in place instead of renaming a temp file onto them.

A compressed export to a named pipe such as `dump.sql.gz` still stages the uncompressed dump in the host temp directory, then compresses onto the pipe. Imports from stdin or a named pipe always stage in that temp directory so retries can reread the dump and SQL Server restore can seek. Staging has no size cap and no free-space check.

```sh
lando db:export /dev/stdout | gzip > dump.sql.gz
mkfifo dump.fifo
lando db:export dump.fifo
```

`db:export -` refuses a terminal so a binary dump does not land in your shell. Redirect stdout, or pass `--force-tty` if you really want the dump in this terminal.

## Snapshots

Snapshots land in Lando's snapshot store, not next to your dump files. Lando briefly stops a running database before copying or restoring its volume, then starts it and waits until it accepts a SQL command. A database that was already stopped stays stopped.

```sh
lando db:snapshot --label before-change
lando db:snapshots
lando db:restore before-change --yes
```

`db:restore` takes a label or the id `db:snapshots` prints. Labels don't have to be unique. A label on more than one snapshot fails with `SnapshotAmbiguousError` and lists the matching ids, newest first, so pass one of those. A name that matches nothing fails with `SnapshotNotFoundError`.

A snapshot restores only into the database volume that took it. Snapshots from another app or checkout don't restore, even when they show up in `db:snapshots --from-app`; move that data with `db:export` and `db:seed <file>`.

## Seed a fresh database

`db:seed` loads a dump file or one of this app's snapshots into a database Lando freshly created that nothing has written to yet. It never prompts, because there is nothing to replace. That makes a snapshot a fast reset point that survives `--volumes`. This throws away the current database:

```sh
lando destroy -y --volumes
lando start
lando db:seed --snapshot before-change
```

`db:seed` also copies straight from another running Lando app of the same database type. `--from-app` takes the source app's id (its Landofile `name`), `--from-path` takes its folder, and `--from-service` picks the source's database service when it has more than one. Lando streams the dump between the two containers through a checked temp file in its own scratch space; nothing lands in your checkout and credentials stay off the command line:

```sh
lando db:seed --from-app shop
lando db:seed --from-path ../shop --from-service database
```

A dump file works from anywhere on the host, including outside the app root. Seed once: a second `db:seed`, or a seed into a database that already has tables, fails with `SqlSeedStateError`. Use `db:import` to load data into a database that's already in use.

If another service fails after Lando creates the database volume, fix that error and run `lando start` again. You can still use `db:seed` while the database stays fresh and empty. A volume Lando didn't create, or whose creation it couldn't record, isn't eligible.

```sh
lando db:seed ../shared/baseline.sql.gz
```

Snapshots survive `lando destroy` and `lando destroy --volumes`. Use `lando destroy --purge` to delete this folder's snapshots, including their provider-stored snapshot data. Snapshots from another folder or Git worktree stay put, even when the apps share a name.

Lando labels native snapshot data so it can find leftovers after an interrupted snapshot write. `lando doctor` reports unindexed images older than one hour; `lando snapshots:gc --prune` removes them. Run `lando snapshots:gc` without `--prune` to inspect them first. Stopped runtimes stay stopped.

Before `db:import`, `db:reset`, or `db:restore` changes your data, Lando takes an automatic recovery snapshot. After a successful operation, Lando keeps the newest 3 recovery snapshots per database automatically, including the one just taken. Failed operations leave every recovery snapshot in place and report the snapshot ID you can restore. Retention stays within this app folder and database; another Git worktree's snapshots stay put.

`lando db:snapshots:prune` handles manual snapshots created by `db:snapshot`, not automatic recovery snapshots. It keeps the newest 3 manual snapshots by default. Removing a snapshot frees its provider storage, not just its entry in the snapshot list. If automatic retention warns that cleanup failed, your database operation still succeeded; older recovery snapshots may remain until a later successful operation retries cleanup.

## Confirm destructive work

`db:import` into a non-empty database and every `db:reset` ask first. `--yes` skips the prompt. Non-interactive runs without `--yes` fail with `SqlConfirmRequiredError` and list the steps.

```sh
lando db:reset --yes
```
