# Import and export app databases

Use `lando db:import` and `lando db:export` for dump files. Use `lando db:snapshot` and `lando db:restore` for volume snapshots. Use `lando db:reset` when you want an empty database. Use `lando db:seed` to fill a database Lando freshly created from a dump, a snapshot, or another running app.

`lando help db` lists every database command with a one-line summary, and `lando db:export --help` shows one command's flags. Run dump commands from your app directory with the database service running. A single database service needs no `--service` flag; with two or more, pass `--service <name>` to select the target. Over [MCP](../../agent-native/mcp/), agents can list snapshots with `db:snapshots` by default and need an explicit `--allow` for every other `db:*` command. The examples below cover server databases. For file-backed SQLite databases declared with `sqlite.path`, see [Use SQLite with db commands](./sqlite-database.mdx).

Export a backup before importing into a database that contains data. Import can change or delete existing data, and `--yes` skips confirmation. The examples show gzip and zstd alternatives; choose one rather than importing the same dump twice.

```sh
lando db:export dump.sql.gz
lando db:export dump.sql.zst
lando db:import dump.sql.gz --yes
lando db:import dump.sql.zst --yes
```

`.gz` and `.zst` compress and decompress on the host process. The default export name stays `<service>.sql.gz` when you omit a path. Import trusts magic bytes, so a gzip or zstd dump still decompresses if the suffix is missing. A compressed server-database export stages the uncompressed dump beside the destination, so that directory needs write access and room for both files. Lando creates missing destination directories and removes its staging files when the export finishes or fails. Compressed imports stage in Lando's cache directory instead. Credentials stay in the service environment, not on argv.

## Export or import a dump

`db:export` writes `<service>.sql.gz` in the current directory when you are inside the app, otherwise the app root. Relative paths resolve the same way.

```sh
lando db:export backups/app.sql.gz --service database
lando db:export backups/app.sql.zst --service database
lando db:import backups/app.sql.gz --service database --yes
lando db:import backups/app.sql.zst --service database --yes
```

Before an import or seed changes anything, Lando reads the whole dump. An empty dump fails with `SqlDumpIncompleteError`, and so does a dump that a dump tool stopped writing partway: a mysqldump or mariadb-dump dump without its final `-- Dump completed` line, a pg_dump dump without its `-- PostgreSQL database dump complete` comment, or a mongodump archive in which a collection never finished. Lando checks for the marker of the target database's own dump tool, so a MySQL dump is checked when you import into MySQL or MariaDB, not when you import it into Postgres. The database and its seed eligibility stay as they were, and no recovery snapshot is taken. SQL you wrote yourself and SQL Server `.bak` files have no such marker, so they aren't checked for truncation.

This check catches a dump tool that stopped early. It can't prove the dump is valid: a dump edited by hand, or one whose ending was faked, gets past it, and the database client still reports errors in the statements themselves.

MySQL, MariaDB, and Postgres execute the dump through the client without automatically resetting the database first; what changes depends on the dump statements. MongoDB restores its archive without automatically dropping collections. SQL Server uses `sqlcmd` backup and restore files, and its restore replaces the target database.

Postgres exports include `DROP IF EXISTS` statements for the objects in the dump,
so importing a Lando export recreates those objects and their saved data. Objects
absent from the dump are not automatically removed. Source ownership and grants
are omitted; the restoring user owns the recreated objects. Postgres imports stop
at the first SQL error instead of reporting partial work as success. Earlier
statements may already have changed data, so use the reported recovery snapshot
if needed.

For SQL Server, use a `.bak` path to make the file type clear:

```sh
lando db:export backups/app.bak --service database
lando db:import backups/app.bak --service database --yes
```

Lando prepares a server-readable backup directory, completes `BACKUP DATABASE`,
then copies the backup to your host. Import uploads the backup before running
`RESTORE DATABASE` from `master`. A failed backup stops before copying a stale
file. Export never creates a missing database; the
[catalog service startup](../services/mssql.mdx) owns default database creation.

## Stream a dump through stdout or stdin

Pass `-` instead of a file name to send a dump through your shell. Run these on the host from the app directory, in a POSIX shell such as bash or zsh:

```sh
lando db:export - > dump.sql
lando db:export - --compression=zstd | ssh backup-host 'cat > app.sql.zst'
```

`db:export -` writes the dump to stdout byte for byte, and progress stays on stderr. SQL Server writes its `.bak` backup the same way. The stream is uncompressed unless you pass `--compression=gzip` or `--compression=zstd`, which compresses on the host, so you don't need `gzip` or `zstd` installed; `--compression-level` tunes it. A file export takes its compression from the `.gz` or `.zst` suffix instead, so `--compression` with a file name is refused.

Lando refuses to write a dump to a terminal, so redirect or pipe stdout. To feed a named pipe, redirect into it, as in `lando db:export - > /tmp/dump.fifo`. A file export into an existing pipe or directory is refused before the dump starts, because the export would replace it.

A dump that fails partway has already sent part of its bytes downstream, and Lando exits non-zero. In a pipeline, check the export's exit status before trusting the output, for example with `set -o pipefail` in bash. If the reader closes early, as `| head` does, Lando stops the dump and exits with status 141.

Scripts and agents that need the structured result can still ask for it. With `-`, `--format=json`, `--format=yaml`, `--json=<keys>`, and `--jq` write the result to stderr, because stdout carries the dump:

```sh
set -o pipefail
lando db:export - --format=json 2> result.json | gzip > dump.sql.gz
```

`result.json` ends with one result envelope: `"ok": true` on success, or `"ok": false` and the tagged error on failure, including failures before the dump starts. With the default renderer the envelope is usually all stderr holds, but a diagnostic or `--debug` output can come before it, so read the last line for JSON or the last document for YAML.

To import from stdin, pass `-` and `--yes`. Lando can't ask for confirmation because stdin carries the dump:

```sh
lando db:import - --yes < dump.sql
```

Lando saves stdin to a private file in its cache directory, decompressing gzip or zstd input as it goes, then imports it exactly like a dump file: the same checks run, a recovery snapshot is taken first, and failures report the same errors. That disk needs room for the uncompressed dump; the file is removed when the import finishes. A compressed dump file is staged the same way. [Find where Lando keeps files](../config/global-config.mdx#find-where-lando-keeps-files) lists the cache directory for your platform. If the program feeding stdin dies partway, the dump it sent ends early, and the import fails before it changes anything; see [Export or import a dump](#export-or-import-a-dump). `lando db:seed - < dump.sql` reads stdin the same way and needs no `--yes`, because seed only fills a fresh, empty database.

`-` works only when you run the `lando` CLI yourself. An MCP tool call that passes `-` is rejected before the command runs, and event commands fail with `CommandStdioError`, because neither has a stdin or stdout to give the dump. Pass a file path there. Scripts and agents can find the dash form in `lando help db:export --format=json`, where the `file` argument carries `"stdio": "stdout"` (`"stdin"` for `db:import` and `db:seed`).

### Stream a dump on Windows

Command Prompt passes dump bytes through unchanged, so the same commands work there:

```bat
lando db:export - > dump.sql
lando db:import - --yes < dump.sql
```

Windows PowerShell 5.1 re-encodes a native command's output and input as text, which corrupts a dump. From PowerShell, hand the redirection to Command Prompt:

```powershell
cmd /d /c "lando db:export - > dump.sql"
cmd /d /c "lando db:import - --yes < dump.sql"
```

On Windows, Lando can't stop an export while the program reading it has stopped reading but is still running. Ctrl+C usually stops that program too; if it doesn't, close it and Lando exits.

## Inspect a failed database command

Request JSON when you need structured diagnostics:

```sh
lando db:export backups/app.sql.gz --service database --format=json
```

Failed service-command transfers report `DataTransferError`; failed SQL actions
report `SqlCommandFailedError`. When the command supplied them, `exitCode` and
`stderrTail` preserve its exit status and redacted stderr. The tail is limited to
8 KiB, including its truncation marker. Oversized unfinished lines may be
suppressed. A provider failure without an exit status does not invent one.
When the container runtime itself failed, for example because it stopped
responding, `error.cause` holds that failure with its own `_tag`, message, and
`remediation`, and `error.remediation` starts with what the runtime says to do.
Database payloads and stdout are never included in these command failures.

Host filesystem failures during a transfer report `DataTransferError` for both
compressed and plain dumps. Their `error.cause` is a `FileIoError` with the failed `path`, an
`operation` of `read`, `stage`, or `persist`, and a `reason` you can use in a script.
The remediation matches that operation: an unreadable source needs read access,
while staging and output files need a writable location.

The reason distinguishes permissions (`permission-denied`), a read-only
filesystem (`read-only`), exhausted storage (`no-space`), account quota
(`quota-exceeded`), a missing path (`not-found`), and an invalid path
(`invalid-path`). Storage includes filesystem space and available inodes. Other
I/O failures use `io` or `unknown`. Use the reported path and remediation to
identify what needs to change.

`SqlDumpCompressionError` means the compression or decompression itself failed,
such as corrupt gzip or zstd input. A staging-directory failure stops the export
before the database dump starts. Compression and output writes can fail after
the dump has finished; an existing destination still stays unchanged. Initial
checks for a missing or unreadable import file happen before the database probe
and use `SqlDumpNotFoundError`.

`lando db:*` commands mask only the target database's credential password or
root password in their output and errors, following the same rules as other
commands: a secret-store or generated password is masked wherever it appears,
and a password you wrote as a literal in a committed YAML layer is masked only
where it stands alone as a whole token. The database user, database name, host,
port, and file paths stay readable, including paths that contain `lando`. See
[What gets masked, and where](../config/secret-stores.mdx#what-gets-masked-and-where).

A failed export leaves an existing host destination unchanged. After a snapshot
is captured, failures during database resume, readiness, import, reset, or restore
report `recoverySnapshotId` with recovery guidance. Command failures keep their
tag and diagnostics. A manual snapshot also remains available when restarting
the database fails; that failure reports the captured snapshot instead of losing
its handle. Failures outside command execution may use a different error tag.
Snapshot capture and restore failures caused by the runtime carry it under
`error.cause` the same way. Fix the reported problem before retrying. Restore
the snapshot only if recovery is needed. A failed capture never invents a
snapshot ID.

Import and seed stop with the same diagnostics if their emptiness query fails.
`--yes` skips confirmation, not a failed database check.

## Take and restore a snapshot

Snapshots land in Lando's snapshot store, not next to your dump files. Lando briefly stops a running database before copying or restoring its volume, then starts it and waits until it accepts a SQL command. A database that was already stopped stays stopped.

Each snapshot has an owner recorded from the source volume's physical identity, not just the app name. Lando keeps its catalog entry at `<userDataRoot>/snapshots/<owner-key>/<store>/<id>.json`, with a copy-mode archive beside it or a reference to a native image on the recording provider. There is no separate index. If Lando cannot prove the volume's identity, capture fails before copying data. `db:snapshot` can adopt a legacy database volume after verifying its mounted target.

Take and list the snapshot first. Run `db:restore` only when you intend to replace the current database with the saved state; it is not part of taking a backup.

```sh
lando db:snapshot --label before-change
lando db:snapshots
lando db:restore before-change --yes
```

`db:restore` takes a label or the id `db:snapshots` prints. Both ids and labels resolve only within the current app, owner, and database store. Labels don't have to be unique. A label on more than one snapshot in that scope fails with `SnapshotAmbiguousError` and lists the matching ids, newest first, so pass one of those. A name that matches nothing in that scope fails with `SnapshotNotFoundError`.

A snapshot restores only into the database volume that took it, with matching owner, service, database family, version, and image. Snapshots from another app or checkout don't restore, even when they show up in `db:snapshots --from-app`. Native snapshots also cannot restore through another provider. Move data across providers with `db:export` on the source, then `db:import` or `db:seed <file>` on the destination.

## Seed a fresh database

`db:seed` loads a dump file or one of this app's snapshots into a database Lando freshly created that nothing has written to yet. It never prompts, because there is nothing to replace. That makes a snapshot a fast reset point that survives `--volumes`. This throws away the current database:

```sh
lando destroy -y --volumes
lando start
lando db:seed --snapshot before-change
```

`db:seed` also copies straight from another running Lando app of the same database type on the selected provider. The apps can have different owners. `--from-app` takes the source app's id (its Landofile `name`), `--from-path` takes its folder, and `--from-service` picks the source's database service when it has more than one. Lando streams the dump between the two containers through a checked temp file in its own scratch space; nothing lands in your checkout and credentials stay off the command line:

```sh
lando db:seed --from-app shop
lando db:seed --from-path ../shop --from-service database
```

A dump file works from anywhere on the host, including outside the app root. Seed once: a second `db:seed`, or a seed into a database that already has tables, fails with `SqlSeedStateError`, and its remediation says which case you hit. Lando checks this before it reads the dump file or stdin, so a refused seed of a large dump returns right away. Use `db:import` to load data into a database that's already in use.

If another service fails after Lando creates the database volume, fix that error and run `lando start` again. You can still use `db:seed` while the database stays fresh and empty. A volume Lando didn't create, or whose creation it couldn't record, isn't eligible.

```sh
lando db:seed ../shared/baseline.sql.gz
```

Snapshots survive `lando destroy` and `lando destroy --volumes`. **`lando destroy --purge` deletes this folder's data volumes and catalogued snapshots**, including native data through each snapshot's recording provider. Purge may start a stopped runtime to remove those snapshots. It works even when only ownership inventory remains after an earlier destroy. Snapshots from another folder or Git worktree stay put, even when the apps share a name.

Lando labels native snapshot data so it can find leftovers after a hard process kill before the catalog entry was saved. `lando doctor` reports uncatalogued images after a one-hour grace period. Inspect them with `lando snapshots:gc` first; **`lando snapshots:gc --prune` deletes eligible images**. GC never starts or repairs a runtime. It skips stopped runtimes during discovery; if a runtime stops after the removal recheck, the provider is reported as failed and that deletion is not counted as removed.

Doctor's filesystem-only `legacy-snapshot-catalogs` check lists the count and paths of catalogs written by older development builds. Those snapshots are no longer listed or restorable, but the catalogs still protect their referenced provider images from `lando snapshots:gc`. An unreadable legacy catalog blocks GC rather than risking those images. **Deleting a legacy catalog directory releases that protection so GC can reclaim its images.** Keep the directory if you still need those images. After deleting it, run `lando snapshots:gc` to review eligible images and `lando doctor` to check the remaining catalogs.

Before `db:import`, `db:reset`, or `db:restore` changes your data, Lando takes an automatic recovery snapshot. After a successful operation, Lando keeps the newest 3 recovery snapshots per database automatically, including the one just taken. Failed operations leave every recovery snapshot in place and report the snapshot ID you can restore. Retention stays within this app folder and database; another Git worktree's snapshots stay put.

`lando db:snapshots:prune` handles manual snapshots created by `db:snapshot`, not automatic recovery snapshots. It keeps the newest 3 manual snapshots by default. Prune and purge delete native data through the recording provider before removing the catalog entry. If deletion fails, the snapshot stays listed so you can retry. If automatic retention warns that cleanup failed, your database operation still succeeded; older recovery snapshots may remain until a later successful operation retries cleanup.
