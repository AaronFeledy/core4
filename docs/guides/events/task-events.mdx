# Run steps before and after a tooling task

Use `pre-<task>` and `post-<task>` under `events:` to run steps before and after
a public tooling task. Lando runs these steps when someone calls `lando <task>`.

Save the following as `.lando.yml` in an example app directory. The `build` task
and its event steps run on the host because they use `service: ":host"`.

```yaml
name: task-events-demo
services:
  web:
    type: "node:22"
    primary: true
tooling:
  build:
    service: ":host"
    cmds:
      - cmd: echo "build step one"
      - cmd: echo "build step two"
events:
  pre-build:
    - cmd: echo "before build"
      service: ":host"
  post-build:
    - cmd: echo "after build"
      service: ":host"
```

From that directory, refresh the command cache after adding the task, then run it:

```sh
lando app:cache:refresh
lando build
```

Check that the messages appear in this order: `before build`, `build step one`,
`build step two`, then `after build`. Lando runs `pre-build`, the task's own steps,
and `post-build` in that fixed order.

Each `events.<name>` step list replaces its inherited list across Landofile layers, just like tooling `cmds`. A step's `service` is an execution target, not a merge identity. Set `[]` to clear inherited steps. See [Override a list in a local layer](../landofile/your-landofile.mdx#override-a-list-in-a-local-layer).

Only tasks that show up in `lando --help` get brackets. Tasks pulled in with `internal: true` from a tooling include stay callable but do not grow `pre-` or `post-` names.

Service types bring tasks of their own, and those get brackets too. Add a `mysql:8.0` service and you can hook `pre-mysql` without writing the `mysql` task yourself:

```yaml
services:
  database:
    type: "mysql:8.0"
events:
  pre-mysql:
    - cmd: echo "before the mysql task"
      service: ":host"
```

## What happens on failure

A failed step affects the remaining steps as follows:

| Failure | Result |
| --- | --- |
| A `pre-<task>` step exits non-zero | The task body never starts. The run fails. |
| The task body exits non-zero | `post-<task>` is skipped. The body's exit code is the command's exit code. |
| A `post-<task>` step exits non-zero | The run fails with `LandofileEventStepFailedError`. |

That last row is worth a second look. A `post-` failure is not a warning. The body already ran, but the operation still fails with a tagged error that carries the redacted tail of the step's output. Treat `post-<task>` steps as part of the task, because from the caller's point of view they are.

## Reuse a task inside an event

Two step forms call another task. They are not interchangeable.

```yaml
events:
  pre-build:
    - task: lint
    - command: app:lint
```

`task: lint` is an inline invocation. Lando runs `lint`'s steps right there and does not fire `pre-lint` or `post-lint`.

`command: app:lint` re-enters the top-level command path, exactly as if you had typed `lando lint`. That fires `pre-lint` and `post-lint` too.

Pass declared inputs by name. Positional `order` controls the argument sequence,
not the order of keys in your Landofile:

```yaml
tooling:
  compare:
    service: ":host"
    cmd: ["printf", "%s\n"]
    args:
      destination:
        order: 2
      source:
        order: 1
events:
  pre-build:
    - command: app:compare
      args:
        destination: after.txt
        source: "-before.txt"
```

The equivalent CLI call is `lando compare -- -before.txt after.txt`. Lando adds
the positional delimiter for named event and MCP inputs, so a leading hyphen
stays part of the value. Tasks without declared flags or args keep raw arguments
unchanged.

Because `command:` re-enters, a `pre-build` step that runs `command: app:build` is a loop. Lando rejects it with `LandofileEventLifecycleReentryError` before anything runs. Nesting is also capped at 16 active event frames; exceeding that limit produces
`LandofileEventInvocationDepthError`. Use `task:` when you want to reuse another
task's steps without firing its own events.

## Restart is bracketed too

`lando restart` fires `pre-restart`, then the full `stop` and `start` event trees exactly as they run on their own, then `post-restart`. Hook `pre-restart` for work that should happen once per restart instead of once per stop and once per start.

## Unknown event names

Lando checks every key under `events:` against the full valid set: the twelve lifecycle names (`pre-init`, `post-init`, `pre-start`, `post-start`, `pre-stop`, `post-stop`, `pre-restart`, `post-restart`, `pre-rebuild`, `post-rebuild`, `pre-destroy`, `post-destroy`), the four remote sync hooks (`post-pull`, `post-push`, `post-switch`, `post-code-sync`), plus `pre-<task>` and `post-<task>` for each non-internal tooling task. A key outside that set fails `lando start` with a `LandofileValidationError` that names every unknown key, alongside anything else wrong in the Landofile.

The remote sync hooks are reserved whether or not you have a remote connector installed, so a hook you write now keeps working once you add one. Until then, nothing fires them. A tooling task can't take a name whose brackets would land on a reserved event: a task called `start` would bind `pre-start`, and one called `pull` would bind `post-pull`. Lint and `lando start` reject it as a `landofile.tooling` issue and tell you to rename it.

`lando app:config:lint`, `lando doctor --app`, and `lando start` build that set the same way, from the same tasks: your Landofile, every config layer, every include, and every service type. Lint and doctor get there without touching a container runtime, so a name that lints clean is a name `lando start` will run. Lint reports each bad key as a `landofile.event` finding at `events.<name>`, the same issue `lando start` fails on. If a service type can't resolve, lint and doctor report that failure and skip the event check instead of blaming your event key.

```sh
lando app:config:lint
```

Typo'd `pre-buidl`? Lint and `lando start` both ask `Did you mean "pre-build"?`. A key nowhere near a valid name gets the full list instead.
