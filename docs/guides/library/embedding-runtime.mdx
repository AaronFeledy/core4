# Embedding the Lando runtime

Embedding hosts have two complementary surfaces. The **App handle** is the preferred
app lifecycle path: `openLandoRuntime()` retains one scoped runtime, `runtime.app()`
resolves a root-bound `App` handle, and `app.start()`, `app.info()`, and `app.stop()`
drive the app while Effect scopes clean everything up when the host scope closes.
Layer-native hosts that compose their own Effect program keep using
`makeLandoRuntime()` directly. Both surfaces share the same bootstrap: logging is
silent, the renderer is JSON, plugin discovery is explicit-only, telemetry is
disabled unless opted in, and signal handlers are not installed by runtime
construction.

## App lifecycle with `openLandoRuntime`

Reach for the App handle whenever you want to start, inspect, and stop a project the
way the CLI does. `openLandoRuntime()` acquires the runtime once in the caller's
`Scope`; `runtime.app(selector?)` resolves a branded `App` handle whose one-shot
methods (`info`, `exec`, `tooling`, `config.lint`) need no further services and whose
live-resource methods (`start`, `logs`, `events.subscribe`) stay bound to the
retained runtime scope. A no-selector `runtime.app()` resolves the project at the
runtime's construction working directory, and the handle stays bound to that root
even if the host later changes its process working directory.

The handle retains its resolved plan and captured Landofile. `exec`, deep `info`, and handle-bound tooling reuse that object, including when `agentEnv` is omitted. A later file edit does not refresh the handle. Re-resolve with `runtime.app(originalSelector)` or layer-native `resolveApp(originalSelector)` to capture edits; supply an updated object when the selector contains a Landofile shape. Ordinary CLI invocations still discover fresh configuration.

That is a privacy boundary: an existing handle does not observe a later app `agentEnv: false` edit. Invocation-time `ConfigService.get("agentEnv")` and the current `LANDO_AGENT_ENV=0` emergency veto still disable automatic forwarding. Global config is a snapshot taken when the runtime was built, so a later `config.yml` edit is not seen until you build a new runtime. Vetoes do not remove explicit service or command env and do not revoke commands already running. Provider status remains live, including shallow `info`, which does not load a Landofile for a supplied target.

```ts
import { Effect } from "effect";
import { openLandoRuntime } from "@lando/core";

const program = Effect.gen(function* () {
  const runtime = yield* openLandoRuntime({ cwd: process.cwd() });
  const app = yield* runtime.app();
  yield* app.start();
  const info = yield* app.info();
  yield* app.stop();
  return info;
});

// Closing the scope tears down any start-state resources the handle is holding.
const info = await Effect.runPromise(Effect.scoped(program));
```

`app.start()` keeps start-state resources (such as file-sync sessions) alive on a
managed scope between calls; `app.stop()`, `app.restart()`, `app.destroy()`, and
runtime-scope close each tear that scope down exactly once. A failed or
interrupted `app.start()` keeps the current managed scope while the runtime
scope remains open. It also leaves containers and published routes in place.
Call `app.start()` again to converge, or `app.stop()` / `app.destroy()` to
shut down or remove the app. Use
`app.start({ detached: true })` when you want the started resources to outlive the
runtime scope, matching the CLI's detached semantics.

Service startup also honors each Landofile `depends_on` condition: `service_started`
waits for the dependency to start, `service_healthy` waits for its healthcheck, and
`service_completed_successfully` waits for a zero exit code. An optional dependency
declared with `required: false` does not block the remaining services when it is absent
or fails.

## Layer-native hosts with `makeLandoRuntime`

Hosts that build their own Effect program provide `makeLandoRuntime()` as a `Layer`
and resolve service tags directly. This is the right surface when you need a service
that the App handle does not expose, or when you are composing Lando services into a
larger Effect application. `makeLandoRuntime()` is scoped, option-validated,
idempotent, and CLI-bootstrap-equivalent; repeated runtimes stay isolated from each
other.

Pass Effect service overrides through `plugins.layers`; each layer is built once and
its services take precedence over matching services from the generated bootstrap.
Pass already-loaded plugin descriptors through `plugins.manifests` when the runtime
must register contributions such as providers or certificate authorities without
enabling filesystem discovery or external imports. Each resolved entry pairs one
validated manifest with its matching plugin module, and bootstrap rejects identity or
capability mismatches instead of silently loading a partial plugin.

Hosts that only need Lando's root and derived-path catalog before constructing a
runtime can import `resolveLandoRoots()`, `makeLandoPaths()`, and
`normalizeHostPlatform()` from `@lando/core/paths`. That subpath is the stable,
Effect-free, OCLIF-free path primitive for pre-bootstrap code such as editor
integrations, installers, and test harness setup.

## Supply global config

Global config resolves once, while the runtime layer builds. The layers are the
same as the CLI's, plus one for you: built-in defaults, then `config.yml`, then
`config.d/*.yml`, then environment (`LANDO_CONFIG__*`, aliases, root vars), then
the host `config` option. `config` accepts any `GlobalConfig` field, not only
roots:

```ts
import { makeLandoRuntime } from "@lando/core";

const runtime = makeLandoRuntime({
  bootstrap: "minimal",
  config: {
    userDataRoot: "/srv/lando/data",
    router: { httpPort: 8123 },
    appEnv: { TEAM: "platform" },
  },
});
```

`configSources` turns the user and environment layers off for hermetic hosts.
`{ user: false }` skips `config.yml` and `config.d`; `{ env: false }` skips
`LANDO_CONFIG__*`, aliases, `LANDO_USER_*` root vars, `LANDO_PROVIDER`, and the
proxy and CA variables (`HTTPS_PROXY`, `NO_PROXY`, `LANDO_NETWORK_CA_CERTS`)
the HTTP client would otherwise read. Platform defaults still come from `HOME`
or `APPDATA`, so set the roots in `config` when you want full isolation:

```ts
const hermetic = makeLandoRuntime({
  bootstrap: "minimal",
  configSources: { user: false, env: false },
  config: { userConfRoot: "/tmp/host/conf", userDataRoot: "/tmp/host/data", userCacheRoot: "/tmp/host/cache" },
});
```

The merged result is validated once. An invalid value from any layer fails the
layer build with a `ConfigError` whose `issues[]` carry `path`, `message`,
`suggestion`, and `source`. A bad host value reports `source: { layer: "host", path }`
and a suggestion naming the option to fix. The error keeps its own tag; it is not
wrapped in `LandoRuntimeBootstrapError`.

Once built, `ConfigService.load` and `ConfigService.get` never fail. They return
the snapshot the runtime was built with, and the runtime's `StateStore`, plugin
trust store, and HTTP egress use that snapshot's roots and environment rather
than `process.env`. Two runtimes in one process never share a snapshot. To pick
up a changed `config.yml` or environment, build a new runtime.

## Running arbitrary effects and command operations

A retained runtime also exposes `runtime.run(effect)`, which provides the retained
context to any Effect program without re-acquiring the bootstrap layer:

```ts
import { CacheService } from "@lando/core";

await Effect.runPromise(
  Effect.scoped(
    openLandoRuntime({ cwd: process.cwd() }).pipe(
      Effect.flatMap((runtime) =>
        runtime.run(CacheService.pipe(Effect.flatMap((cache) => cache.read("key")))),
      ),
    ),
  ),
);
```

For command-shaped dispatch, `@lando/core/cli` exposes the programmatic `runCli`
entry point, while the lower-level Effect operations behind built-in commands remain
available from `@lando/core/cli/operations` (for example `startApp`, `infoApp`, and
`stopApp`). These are building blocks for hosts that want command parity without
OCLIF. They return typed results rather than rendered text, but they are not the
preferred app lifecycle API. Prefer the `App` handle for lifecycle work and reach
for the raw operations only when you need command-level dispatch.
