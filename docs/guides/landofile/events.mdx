# Run tasks at app lifecycle events

Use `events:` to run a command or tooling task before or after an app lifecycle operation. Add the steps to your Landofile. This example runs a host command before start and a tooling task inside `web` after start:

```yaml
name: events-demo
services:
  web:
    type: "node:22"
    primary: true
events:
  pre-start:
    - cmd: echo "Preparing the app"
      service: ":host"
  post-start:
    - task: warm-cache
tooling:
  warm-cache:
    service: web
    cmd: echo "Cache ready"
```

Run the commands from the app directory:

```sh
lando app:config:lint
lando start
```

After the app starts, the `warm-cache` task runs inside `web`. In this example it prints `Cache ready`. Replace its `cmd` with the work your app needs.

A plain-string step runs inside a service by default. Before start, that service may not exist yet, so use `service: ":host"` for `pre-start` shell commands. Use `pre-stop` for work that needs a running service, and `service: ":host"` for shell work after stop.

Host commands use Lando's embedded Bun Shell, not Bash, zsh, or the container's shell. They use the same language as [host tooling and project scripts](../tooling/bun-shell-scripts.mdx#use-bun-shell-and-your-host-tools).

App mutations hold a process-owned lock. A hook that launches a child `lando`
cannot lend it the running command's lock for the same app. Recognized parent
ownership causes an immediate refusal; other contention uses the normal bounded
wait. Run that mutation separately after the parent operation finishes. Nested
in-process `command:` steps and SDK calls keep their normal admission and event
recursion checks.

## Available events

You can attach tasks to `pre-init`, `post-init`, `pre-start`, `post-start`, `pre-stop`, `post-stop`, `pre-restart`, `post-restart`, `pre-rebuild`, `post-rebuild`, `pre-destroy`, and `post-destroy`. Steps run in declaration order. `lando restart` fires `pre-restart`, then the stop and start event trees, then `post-restart`.

Every non-internal tooling task also gets `pre-<task>` and `post-<task>`. See [Run steps before and after a tooling task](../events/task-events.mdx).

## Handle a failed step

A failed `pre-*` step prevents the lifecycle operation from running. If the operation itself fails, its `post-*` steps do not run.

A failed `post-start` or `post-stop` step produces a warning with the step's redacted output tail, but does not fail the completed operation. Other `post-*` failures fail the command with `LandofileEventStepFailedError` and a redacted output tail. Event output uses Lando's normal secret redaction.

## Change stop and destroy hooks

`lando stop` and `lando destroy` use the Landofile at the recorded app root to find the steps to run. They do not take hooks from an old saved plan or a different Landofile in your working directory. A `pre-destroy` step added after `lando start` therefore runs on the next `lando destroy`, without a restart.

If that root has no Landofile, Lando prints an info notice and skips the Landofile and host-event steps. If the Landofile cannot load, or describes a different app, app root, or provider, Lando prints a warning and skips those steps. This also applies when you target an app with `--root`. The operation can still stop or destroy the recorded app, subject to the data-removal check below. Ownership checks and recovery of an unfinished start still fail when Lando cannot establish that cleanup is safe.

**Check backup hooks before removing data.** If a Landofile is present but unusable, a `pre-destroy` backup step might not run. With `lando destroy --volumes`, `--purge`, or `--purge-caches`, Lando asks before proceeding without those steps. Fix the Landofile to run them. Pass `--yes` only if you intend to remove data without them. A non-interactive run without `--yes` fails with `LandofileEventsSkippedError` before changing the app. This extra confirmation does not apply when the root has no Landofile.

For scripts, inspect the result of `lando stop --format=json` or `lando destroy --format=json`. When the operation tears down an app whose steps could have run, [`landofileEvents`](../../reference/schemas/landofile-events-outcome.mdx) contains:

- `{ status: "ran" }` when Lando could use the Landofile's event plan.
- `{ status: "skipped", reason }` when it could not.

`ran` describes how the event plan was sourced, not whether every step succeeded. Steps may still warn or be skipped under the rules on this page. The field can be absent for a no-op or cleanup without an applied app.

Cleaning up leftovers, such as orphaned containers, ownership records, or snapshots after the app is gone, skips your steps. Destroy still publishes the plugin lifecycle events; a destroy that fails partway does not publish `post-destroy`.

If you embed Lando, an existing library `App` handle keeps the Landofile snapshot it was resolved from. Resolve a new handle to pick up edited project hooks. Host-wide hooks use the host-configuration snapshot held by the runtime.

## Run the same steps on every app

Edit `<userConfRoot>/config.yml` to run steps for every user app. The shared global app and scratch apps are excluded. `hostEvents` is separate from the file's `events` delivery policy.

```yaml
hostEvents:
  pre-start:
    - cmd: echo starting
      service: ":host"
  post-start:
    - cmd: echo ready
      service: web
```

Steps accept a string, `{cmd, service?}`, or `{command}`. A string or omitted `service` uses the app's primary; `service: ":host"` runs on the host. Other fields are rejected. Host events support pre/post `start`, `stop`, `restart`, `rebuild`, and `destroy`, not init or tooling events.

Container steps are allowed except in `pre-start`, `post-stop`, and `post-destroy`. Use `:host` or `{command}` there. A `command` step names a Lando command without flags or args; lifecycle commands such as `start`, `app:start`, and `poweroff` are rejected to prevent re-entry. Quote the whole YAML value when a shell command contains quotes or `#`, for example `cmd: 'echo "ready # now"'`.

Host steps run before project steps, each in declaration order. Lando drops a host copy when the project has the same step for that event: `"x"` matches `{cmd: x}`, an omitted service is the primary, and `:host` remains distinct. Project steps with conditions or other execution modifiers do not suppress an unconditional host step. There is no per-app opt-out.

Missing or stopped services skip the host step with an info notice, including created, dead, or paused containers. `:host` steps do not need a running service. Other failures follow the project-event rules above.

Only `:host` children of host events receive `LANDO_HOST_EVENT=1`. A nested `lando` that sees it skips host events with a notice; project events still run.

Run `lando config validate` after editing. `lando config --format=json` shows the key; `lando app config --format=json` reports each host step as `active`, `skipped` (with a reason), or `deduped` from the resolved Landofile. This status does not inspect running containers. `lando app config explain` stays a canonical-file recipe report, not an effective event view.
