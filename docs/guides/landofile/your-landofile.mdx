# Write a Landofile

A Landofile describes your app’s services, tooling, and routes. After completing `lando setup`, create an app directory and save the following as `.lando.yml` in it. For an existing app, merge the relevant entries into its Landofile instead of replacing it:

```yaml
name: your-landofile-demo
services:
  app:
    type: "node:22"
    primary: true
  db:
    type: postgres
tooling:
  node:
    service: app
    cmd: node
  psql:
    service: db
    cmd: psql
```

From the directory containing `.lando.yml`, start the app and inspect its services. Lando starts Traefik for you; you do not start it by hand.

```sh
lando start
lando info
```

`lando info` prints URLs and connection details for the configured services. This example supplies a Node environment and Postgres; add your application code and startup command to make Node serve your application.

MySQL and Postgres already wait on their own probe. To wait on your app, set `healthcheck:` on the service. See [Make start wait for your app](../services/wait-for-your-app.mdx).

## Add a hostname

Most apps skip `routes:`. Default hostnames look like `app.your-landofile-demo.lndo.site`. Authored routes replace the default hostname, so list every name you want:

```yaml
services:
  app:
    type: "node:22"
    primary: true
    routes:
      - hostname: app.your-landofile-demo.lndo.site
        scheme: both
```

Top-level `proxy:` is the other spelling: a map of service name to the same route list. Set `routes: []` to give a service no hostname at all.

## Stop discovery at a directory

Run app commands from your app directory or any directory below it. Lando checks
the current directory, then up to 64 parents, and uses the first directory with
any Landofile layer. It never combines layers from different directories.

To keep a workspace from picking up a Landofile above it, put an empty
`.lando.stop` file at the workspace boundary:

```sh
touch .lando.stop
lando app:config --format=json
```

Lando still checks that directory for a Landofile before stopping. Its own
Landofile wins, and apps nested below it work normally. With no Landofile below
or at the boundary, the command reports `LandofileNotFoundError`, the searched
range, and the marker location. Run `lando init` to create an app, or move/remove
the marker if you meant to use a parent app. Without a marker, discovery stops at
the filesystem root or the 64-parent limit.

## Write maps as block YAML

Indent every map, and put a value that contains `#` in YAML quotes:

```yaml
services:
  app:
    type: "node:22"
    primary: true
    environment:
      DEMO: "echo # hi"
```

Here `#` sits inside the YAML quotes, so it stays part of the value: `DEMO` is `echo # hi`. Outside YAML quotes, a `#` after whitespace starts a comment, and shell-style quotes inside a plain scalar do not change that: `DEMO: echo "# hi"` leaves `DEMO` holding only `echo "`.

A one-line `{key: value}` flow mapping is not accepted anywhere in a Landofile, including when its only `#` is inside quotes:

```yaml nolint
services:
  app:
    environment:
      DEMO: {key: "echo # hi"}
```

```sh
lando app:config --format=json
```

That fails with `LandofileParseError`, the line number, and a remediation showing the block rewrite. Lando does not read the braces as text and does not cut the value at the `#`. `lando app:config:lint --format=json` reports the same problem as a `valid: false` violation with the line, so you can check a file before you start the app.

## Override a list in a local layer

Put machine-local changes in `.lando.local.yml`. Layers load from low to high precedence: `.lando.base.yml`, `.lando.dist.yml`, `.lando.upstream.yml`, `.lando.yml`, `.lando.local.yml`, then `.lando.user.yml`.

Each layer accepts YAML (`.yml`) or TypeScript (`.ts`), not both: Landofile loads fail with `LandofileFormConflictError` naming both files and telling you to remove one. `stop` and `destroy` can still tear down from applied state, skipping Landofile hooks with the conflict reason; a never-started app reports `unchanged`.

Maps deep-merge and scalars use the later value. Collection rules come from each field's schema, not the properties of its entries. Included Landofiles follow the same rules.

These are authored values: Lando merges before interpreting shorthand or adding defaults. A local `appMount: /site` replaces an inherited app-mount object, including its `excludes`. Changing `environment` or `labels` between a list and a map also replaces the earlier value. Use maps when you want individual keys to merge. Only literal `healthcheck: false` discards an inherited probe before later layers; disabled object spellings still participate in ordinary map merging.

Inspect the effective result with `lando app:config --format=json`. A bad local value carries its effective `issues[].path` plus `issues[].source` with the original file, layer, and authored path. The error's `remediation` is separate from those locations. Source coordinates appear only when the parser actually recorded them.

Compare individual layers with `lando app:config --source raw --format=json`, or inspect their authored composition with `--source merged`. Both can show values that effective validation rejects. See [Inspect each stage of your Landofile](./config-views.mdx).

`lando app:config set` and `unset` change the canonical YAML source, not the merged result. Before saving, Lando validates that partial authored candidate and the effective stack with the candidate substituted at canonical precedence. `set` and `unset` allow unchanged validation problems elsewhere while you repair one key; a write is rejected if it introduces a problem or leaves the written key or a descendant invalid. Lando still needs to read the layer stack, so unreadable files or malformed YAML in another layer block the operation. `edit` can repair malformed YAML and saves your exact buffer, including template directives. `--dry-run` performs the same validation without writing; an unchanged unset creates no file. Set/unset don't rewrite templated or TypeScript sources.

- Routes match by scheme, case-insensitive hostname, and path prefix in either shorthand or object spelling. Omitted scheme means HTTPS and omitted path means `/`. A `both` route participates in both scheme identities; an HTTPS-only overlay leaves its HTTP route alone. Backends and filters are not route identity.
- `dependsOn` matches by service, in list, map, or object-entry form. Logs match by `id`, which defaults to the path basename.
- Route filters match by `name`, otherwise by `type`. Named filters never match unnamed ones. Changing a matched filter's type replaces that entry.
- Endpoints and ports match by exact, case-sensitive `name` only when every entry on both sides is named. Otherwise the list replaces.
- Every other list replaces, including scalar arrays, tooling `cmds`, event step lists, and opaque extension arrays. A step's `service` is where it runs, not a merge identity.

Route identities with template expressions match by their literal text, including case. Untouched `both` entries stay authored; matching one of their schemes splits only that entry.

An explicitly empty array (`[]`) clears any inherited list. Omit a key to leave its inherited value alone. To replace a value whole or delete a key, use `!override` or `!reset` ([below](#replace-or-remove-a-value-with-override-and-reset)). See the generated [Landofile schema reference](../../reference/schemas/landofile-shape.mdx#layer-merge-rules) for per-field rules.

For example, start with this `.lando.yml`:

```yaml
name: empty-routes-overlay
services:
  web:
    type: "node:22"
    routes:
      - hostname: web.example.test
tooling:
  test:
    cmds:
      - service: web
        cmd: echo base-first
      - service: web
        cmd: echo base-second
```

Clear the inherited routes and replace the tooling steps in `.lando.local.yml`:

```yaml
services:
  web:
    routes: []
tooling:
  test:
    cmds:
      - service: web
        cmd: echo local-only
```

Inspect the merged config without starting containers:

```sh
lando app:config --format=json
```

`services.web.routes` is now `[]`, not the inherited object route. `tooling.test.cmds` contains only `echo local-only`; neither base step remains. Event step lists replace the same way. To add a route rather than clear the list, set a distinct path such as `{hostname: web.example.test, pathPrefix: /api}`; the inherited root route stays, even if it was a shorthand string.

## Replace or remove a value with `!override` and `!reset`

A higher layer has four moves at any mapping key:

| You write | Result |
| --- | --- |
| A plain value | Merges. Maps deep-merge, lists follow their schema rule, scalars win. |
| `[]` | Clears the inherited list. The key stays, holding an empty list. |
| `!override` and a value | Replaces the inherited value whole. No deep merge, no list identity matching. |
| `!reset` | Deletes the key, as if no lower layer ever set it. |

Say `.lando.yml` sets two routes and a `DEBUG` variable:

```yaml
name: merge-directives
services:
  web:
    type: nginx
    environment:
      APP_ENV: dev
      DEBUG: "true"
    routes:
      - web.a.test
      - web.b.test
```

Drop `DEBUG` and swap in one local hostname from `.lando.local.yml`:

```yaml
services:
  web:
    environment:
      DEBUG: !reset
    routes: !override
      - web.local.test
```

```sh
lando app:config --format=json
```

`services.web.routes` is exactly `["web.local.test"]`, and `environment` holds only `APP_ENV`. A plain `routes:` list would have merged by hostname and kept both inherited routes. The directives themselves never show up in `app:config`, plans, or containers; layer merging consumes them.

A `.lando.*.ts` layer uses the same operations through helpers:

```ts
import { defineLandofile, override, reset } from "@lando/sdk";

export default defineLandofile({
  services: {
    web: {
      environment: { DEBUG: reset() },
      routes: override(["web.local.test"]),
    },
  },
});
```

Where they go:

- On a mapping key: `services.web: !reset`, `environment.DEBUG: !reset`, or a key inside a list item, such as `filters: !override []` inside a route object.
- Not at the document root, not directly on a list item (`- !reset`), and not on a field that identifies a list entry: route `hostname`, `scheme`, and `pathPrefix`, dependency `service`, filter `name` and `type`, endpoint and port `name`, log `id` and `path`. To drop one entry from such a list, `!override` the whole list.
- Inside sequence entries only when the schema declares a keyed collection. Non-keyed sequences, such as tooling `cmds`, event steps, and mounts, do not accept directives inside their entries.
- Not inside dependency-map entries or on security CA aliases (`cas`, `certificate-authority`, or `certificate-authorities`). CA directives use canonical `ca`.
- `!reset` ignores a scalar or empty payload, so the Compose spelling `!reset []` works too. `!override` needs a value: a bare `!override` with nothing indented below it fails.
- `routes: !reset` deletes the key, so generated default hostnames come back. `routes: []` keeps the key and gives the service no hostname at all.
- `!reset` on a key no lower layer set does nothing. A later plain value puts a reset key back.

Run `lando app:config:lint` to check directive placement before you start the app.

## Reach for other keys

| Key | What it does |
| --- | --- |
| `events:` | Tasks at start, stop, rebuild, and destroy. |
| `includes:` | Pull in Landofile or tooling fragments. |
| `env_file:` | Shared `KEY=VALUE` files for every service. |
| `environment:` | Per-service env. There is no top-level `env:` key. |
