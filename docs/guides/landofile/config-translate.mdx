# Translate a config into a v4 Landofile

Preview a conversion without changing files. From the app directory, run:

```sh
lando app:config:translate
```

Lando detects the source files, picks a translator, and prints the canonical v4 Landofile it would produce. Nothing is written. No `.lando.yml.canonical` appears next to your file.

The bundled `lando4` translator ships with Lando, so a v4 Landofile round-trips out of the box. Other translators come from plugins.

## Preview the result

```sh
lando app:config:translate
lando app:config:translate --format=json
```

The default output is the translated YAML. When a single layer is produced, you get the bare Landofile. When several layers are produced, each block is labeled with a `# <path>` comment for the file it belongs to.

If the translator reports diagnostics, YAML comments after the converted Landofile summarize the counts and explain the changes in impact order. You can still parse the preview as YAML. Read the blocking and review diagnostics before deciding to write.

`--format=json` prints the structured preview: `inputPath`, `translator`, `target`, `files`, `content`, `targets` (one `layer`, `path`, `content` per declared layer), `diagnostics`, and `deletions`.

## Write the files

Review the preview and its diagnostics before writing. The next command replaces the declared v4 Landofile layers and can remove source files listed in `deletions`; Lando backs up each replaced or removed file before changing it.

```sh
lando app:config:translate --write
```

`--write` replaces the declared v4 Landofile layer files through the managed-file transaction. Before any file changes, Lando keeps an immutable backup beside each replaced file, named `<file>.bak.<sha256>` after the digest of the bytes it replaces. There is no plain `.lando.yml.bak`.

The human write summary lists each written path and removed source. It ends with counts of written files, removed files, and backups, each backup location, counts of `needs-review` and `dropped` diagnostics, and a reminder to lint. These status lines are YAML comments, not part of the saved Landofile. The saved files contain the converted configuration, without the diagnostic comments.

From the app directory, check the written configuration before starting the app:

```sh
lando app:config:lint
```

Resolve any lint errors and review the translation diagnostics before running `lando start`. A successful write confirms the files were saved, not that the app behaves the same as before.

Only the `lando4` target may write. Any other `--to` target is preview-only, and pairing it with `--write` fails with `Target <id> is preview-only.`

## Read the diagnostics

Human diagnostics start with an ASCII summary counting each kind present. Blocking diagnostics come first, followed by changes that need review, omitted values, equivalent rewrites, and generated values. Each diagnostic shows its glyph, bracketed kind, message, and `source:path` location. Use the kind to distinguish the two meanings of `~`:

| Glyph | Kind | Effect |
| --- | --- | --- |
| `!` | unsupported | Blocks encoding and `--write` |
| `~` | non-portable | Blocks `--write` |
| `?` | needs-review | Converted, but needs your review |
| `-` | dropped | Omitted from the converted configuration |
| `~` | rewritten | Equivalent behavior with a different spelling |
| `+` | generated | Added by the translator |

Blocking, review, and dropped diagnostics include the translator's remediation when available. Sibling fields share one line listing their leaf keys only when their kind, source, parent path, message, and remediation are identical. The summary counts diagnostics before grouping, not displayed lines.

Diagnostics are redacted on both human and machine surfaces. JSON preserves the individual diagnostic entries and their original order; human grouping does not change the structured result.

An `unsupported` diagnostic empties the preview content and refuses to write. A `non-portable` diagnostic still previews but refuses to write. A refused human write shows the same grouped diagnostics with remediation before the tagged `ConfigTranslateError`. No files are changed. Resolve the blockers, preview again, and retry `--write`. JSON failures keep the structured error rather than the human diagnostic comments.

## Translate one layer

```sh
lando app:config:translate --file .lando.local.yml
lando app:config:translate --file .lando.local.yml --write
```

`--file <path>` scopes the conversion to one layer. Lando reads the lower layers as context, but writes only the selected layer's dependency closure. It fails closed in two cases:

- A lower layer is not already valid v4. Convert the base first.
- A target file already exists and was not selected. The error names it: `Cannot modify unselected source <path>.` Add `--file <path>` to include it.

`--file` is repeatable. Paths must sit inside the app root and stay under 1 MiB.

## Pick a translator or target

```sh
lando app:config:translate --list
lando app:config:translate --detect
lando app:config:translate --from lando4
lando app:config:translate --to lando4
```

| Flag | Does |
| --- | --- |
| `--list` | Prints registered translators: id, input kinds, summary |
| `--detect` | Reports which translators match the discovered files, with confidence, without translating |
| `--from <id>` | Forces a translator instead of autodetecting |
| `--to <id>` | Picks the target encoder. Default `lando4`, the only one that may write |
| `--format` | `yaml` (default), `table`, or `json` |

A `--to` target without an encoder fails with `Invalid --to target "<id>": an encoder is required.` and lists the ids you can choose from.

## Preserve Lando 3 Compose arguments

```sh
lando app:config:translate --from lando3
```

Scalar `command` and `entrypoint` values in Lando 3 Compose fields become argument lists, not shell scripts. This applies to nested `services` fields on `type: compose` and `type: lando`, and to Compose `overrides` on typed services. For example, `command: --port 8080` becomes `["--port", "8080"]`, so both arguments reach the image's entrypoint.

Quotes keep an argument together: `sh -c "echo a b"` becomes `["sh", "-c", "echo a b"]`. Existing argument lists stay unchanged. A `~` diagnostic explains each scalar rewrite. Unmatched quotes or other unrepresentable syntax produce an `unsupported` diagnostic instead of guessing how to run the service. Fix the source or supply an explicit argument list before writing.

Compose stops reading a scalar at an unquoted `;`, `&`, `|`, `<`, or `>`, so `echo a && echo b` only ever ran `echo a`. Translation keeps that argument list and adds a `?` diagnostic. If you wanted the whole script, write `["sh", "-c", "echo a && echo b"]` instead.

API-4 `type: l337` services in a Lando 3 file also pass these fields to Compose, so their scalar values become argument lists. API-4 `type: lando` services split a single-line `command` or `entrypoint` the way Lando 3 did: on whitespace, with quotes grouping words and no shell operators. A multi-line value stays a script. Catalog-owned top-level commands, such as a Node service's shell script, keep their existing behavior. In a native v4 Landofile, a string `command` on `type: compose` splits into argv the same way; a string `command` on any other service type still means a shell script. Translation makes the distinction explicit.

## Write your own translator

Plugin authors register a translator through the `ConfigTranslator` SDK service tag. Each declares a stable `id`, a `summary`, supported input kinds, and `detect`/`translate` hooks. Optionally it declares `encode`, which is what makes an id a valid `--to` target. Core reads bounded document snapshots once; detection returns matches with source ids and confidence instead of re-reading files.

The selected translator sees the whole ordered document set and returns outputs by target layer. Core validates each fragment against the authoring schema before merging, then hands the merged context and each fragment to the encoder. Duplicate translator ids fail with `ConfigTranslatorConflictError` before any translator runs.

Library consumers get the same parse and emit helpers through `@lando/core/landofile` without going through the CLI.
