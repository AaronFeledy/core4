# Translate a config into a Landofile

```sh
lando app:config:translate
```

Run that from an app directory. Registered translators turn the discovered `.lando.yml` into a canonical v4 Landofile.

By default the canonical Landofile is written next to the input as `.lando.yml.canonical`, leaving the original untouched. `--format json` prints the structured result (paths plus diagnostics). `text` is the default human-readable summary.

Overwrite the input in place with `--write`. Lando keeps the original as `.lando.yml.bak` first:

```sh
lando app:config:translate --write
```

With zero translators registered, the command exits non-zero before touching any file, with `ConfigTranslateNoTranslatorsError`. Concrete translators ship as plugins:

```sh
lando plugin:add <translator-plugin>
```

## Know how translators resolve

Plugin authors contribute a translator through the `ConfigTranslator` SDK service tag. Each declares a stable `id`, a user-facing `summary`, supported input kinds, and `detect`/`translate` hooks. Core reads bounded document snapshots once. Detection receives those snapshots and returns matches with source identities and confidence, not instructions to read files again.

Core invokes one selected translator for the whole ordered document set. The translator returns outputs by target layer, with an authoring wire fragment and source identities for each output. Core validates the fragments before merging them, including expression syntax and expected value types. Diagnostics stay ordered by input document, source span, then key path. Duplicate translator ids fail with `ConfigTranslatorConflictError` before any translator runs.

Library and embedding consumers can use the same parse/emit helpers through `@lando/core/landofile` when they need this serializer without invoking the CLI.
