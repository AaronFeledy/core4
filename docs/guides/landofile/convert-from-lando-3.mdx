# Convert a Lando 3 app to Lando 4

Use the Lando 4 executable from the app directory to preview the conversion first. The first command below prints proposed Landofile layers and diagnostics without writing. Review them before running the second command: `--write` replaces those files and can remove obsolete layers, with backups for rollback.

Until you write, your saved Lando 3 executable can still use the original files. After writing, restore the backups before running that app with Lando 3 again. Conversion does not adopt Lando 3 containers or volumes.

```sh
lando app:config:translate --from lando3
lando app:config:translate --from lando3 --write
```

Lando 4 never translates a Lando 3 file on the fly. Every `lando` app command loads v4 only, so conversion is a step you take once, on purpose, and can undo.

## Write with backups

```sh
lando app:config:translate --from lando3 --write
lando app:config:lint
```

`--write` commits every layer through one managed-file transaction. Before any byte moves, each file it will replace or remove gets an immutable backup beside it named `<file>.bak.<sha256>`, where the digest is the SHA-256 of the original bytes. The write summary lists `written`, `backups`, and `removed`.

Three guarantees come with that transaction:

- Interrupted mid-write? The next `lando` app command in that directory recovers the transaction or refuses to load until it is resolved. It never loads a half-converted app.
- Edited a file between preview and `--write`? The write fails and the originals stay untouched. Run the preview again.
- Want Lando 3 back? Copy each `.bak.<sha256>` file over its original name and delete `.lando.dist.yml` if the conversion created it. Lando 4 does not adopt Lando 3 containers or volumes, so the Lando 3 app is exactly where you left it.

After the write, `lando app:config:lint` reports the result valid, and `lando start` runs it as an ordinary Lando 4 app. Review every `needs-review` diagnostic before that first start.

## Detect or say so

```sh
lando app:config:translate --detect --format=json
```

`--detect` reports which translator matches your files without translating. A file with unambiguous Lando 3 spellings (`recipe:` plus `config:`, `portforward`, `overrides`, `api: 3`, a `.lando.recipe.yml` layer) matches `lando3` with `exact` confidence, and a bare `lando app:config:translate` picks it for you.

A Lando 3 file that is also valid v4 shape (a `name`, a couple of services with only `type`) is not auto-detected as Lando 3. Detection reports `lando4` instead, and the default run round-trips the file as v4. Pass `--from lando3` explicitly when you know where the file came from.

## Preview the layers

```sh
lando app:config:translate --from lando3
lando app:config:translate --from lando3 --format=json
```

The YAML output labels each block with a `# <path>` comment. The JSON preview carries `targets` (one `layer`, `path`, `content` per file), `diagnostics`, and `deletions`.

Each Lando 3 layer converts to the v4 layer of the same name:

| Lando 3 file | Lando 4 file |
| --- | --- |
| `.lando.base.yml` | `.lando.base.yml` |
| `.lando.dist.yml` | `.lando.dist.yml` |
| `.lando.upstream.yml` | `.lando.upstream.yml` |
| `.lando.yml` | `.lando.yml` |
| `.lando.local.yml` | `.lando.local.yml` |
| `.lando.user.yml` | `.lando.user.yml` |
| `.lando.recipe.yml` | folded into `.lando.dist.yml`, then removed |

`.lando.recipe.yml` has no v4 counterpart. Its recipe and config land in `.lando.dist.yml`, and the preview lists the file under `deletions` with the reason. `--write` removes it in the same transaction that writes the others, with a backup like every other replaced file.

### Recipes

A Lando 3 `recipe:` with its `config:` map becomes the matching bundled Lando 4 recipe with `options`:

| Lando 3 recipe | Lando 4 recipe |
| --- | --- |
| `drupal10`, `drupal11` | `drupal` (with `drupal: "10"` or `"11"` pinned) |
| `wordpress` | `wordpress` |
| `lamp` | `lamp` |
| `lemp` | `lemp` |
| `laravel` | `laravel` |
| `symfony` | `symfony` |
| `backdrop` | `backdrop` |
| `joomla` | `joomla` |
| `mean` | `mean` |

`config` keys the Lando 4 recipe has no option for are reported as `dropped`, once each, with a remediation telling you where to set the value by hand. Values the option does not accept, such as a PHP version the recipe no longer ships or a `webroot` with spaces, stop the conversion with a `ConfigTranslateError` that names the accepted shape.

Relative Lando 3 webroots carry over unchanged: `webroot: web` stays `web`. Lando 4 resolves that path against the service's app mount, `/app` unless an authored `appMount` path such as `appMount: /site` moves it, when planning the service. Omit `webroot` or use `.` for the app root. Absolute container paths remain available for a specific layout; relative paths that escape the app mount are rejected during planning.

For Tomcat, conversion sets Lando 4 `webroot` to `<webroot>/webapps/ROOT` (`webapps/ROOT` when Lando 3 used the default), matching the path Lando 3 served at `/`. It reports that other webapps or WAR files under `webapps/` are not deployed.

Hosting-platform recipes (`pantheon`, `platformsh`, `lagoon`, `acquia`), `drupal7` through `drupal9`, and any recipe Lando 4 does not bundle are rejected. The preview is empty, `--write` refuses, and your files do not change. Keep those apps on Lando 3 or replace the recipe with explicit v4 services first.

### Removals convert to `!reset` and `!override`

A Lando 3 higher layer that removes something becomes a native Lando 4 directive in the converted layer. The lower layers keep what they set, so every layer still means what it meant before.

- A removed key or service becomes `!reset`. A `portforward: false` in `.lando.local.yml` over `portforward: true` in `.lando.yml` converts to `ports: !reset` in `.lando.local.yml`.
- A list that loses, reorders, or rewrites an entry the merge cannot express becomes `!override` with the full list. An emptied list stays `[]`.
- A change that cannot stand alone in its layer, such as a single recipe option, becomes `!override` on the nearest key that can.

```yaml
# .lando.local.yml after conversion
services:
  cache:
    ports: !reset
```

See [Replace or remove a value with `!override` and `!reset`](./your-landofile.mdx#replace-or-remove-a-value-with-override-and-reset) for how layers consume them.

## Read the diagnostics

| Kind | Meaning | Blocks `--write` |
| --- | --- | --- |
| `generated` | Lando 4 produced this from a recipe or a default | No |
| `rewritten` | Same intent, new spelling (`portforward` became `ports`) | No |
| `dropped` | No Lando 4 equivalent; set it by hand if you still need it | No |
| `needs-review` | Converted, but look at it before you start the app | No |
| `non-portable` | Previews, but will not write | Yes |
| `unsupported` | Cannot be expressed; empties the preview | Yes |

Each diagnostic carries `sourceId`, `keyPath`, `message`, and `remediation`. Preview and `--write` emit the same list, so what you reviewed is what lands.

Lando 3 removed tooling tasks whose values weren't mappings. The converter keeps `false` unchanged, without a diagnostic. Every other non-mapping task value, including `disabled`, becomes `false` with a `rewritten` note. That includes a command-looking string: conversion keeps the task disabled rather than turning it into a runnable Lando 4 string task.

Two families of `needs-review` come from your commands rather than your keys. Any string that mentions `LANDO_INFO`, `LANDO_MOUNT`, `settings.lando.php`, or `wp-config` gets a review note: Lando 4 sets typed `LANDO_DB_*` and `LANDO_SERVICE_*` variables and never adds a `LANDO_INFO` alias, so a settings file that parses it needs your eyes. Any string that calls `lando <verb>` gets a reminder to verify that `lando --version` reports Lando 4 before running it; conversion does not change your PATH.

A third family covers service homes. Lando 3 kept a home directory for every service it built from its own catalog. Lando 4 keeps one only when the service type knows where the planned user's home is, so the converter checks each converted service against the Lando 4 catalog and adds a `needs-review` note only when that check fails. When Lando 4 won't keep the home, the note says `Lando 3 kept this service's home, but Lando 4 won't keep it automatically: its image comes from the Landofile.` and its remediation is `Set services.<name>.home.path to keep a home.` When the converter can't tell, it says `Lando 3 kept this service's home; Lando 4 can't confirm it will keep it automatically (<reason>).` and points you at the `home` row in `lando info` after the first start. Raw Lando 3 Compose services get no note, because Lando 3 never kept their home. See [Keep a service home across rebuilds](../services/home-and-host.mdx) for what `lando info` reports.

`lando pull`, `lando push`, and `lando share` are `unsupported`. Lando 4 does not emulate hoster sync. Remove the command, move the workflow to `lando remote:add` and dataset `pull`/`push`, or keep that app on Lando 3.

## What converts and what doesn't

Nothing falls through silently. When a key has both a supported form and a rejected form, the rejected form blocks `--write`.

| Lando 3 input | Result | Blocks `--write` |
| --- | --- | --- |
| A bundled recipe from the table above, with its `config:` | The matching Lando 4 recipe with `options` | No |
| A service type and version Lando 4 ships (`php:8.3`, `mariadb:11.4`, `redis:7`) | The same service | No |
| Supported `portforward`, override fields, `build_as_root`, `build`, `run_as_root`, `run`, `proxy` routes, `tooling`, `events`, and text `!load` / `!import` | Native Lando 4 keys, with a `rewritten` or `generated` note | No |
| `moreHttpPorts`, `plugins`, `pluginDirs`, tooling `level`, `usage`, `examples`, and `interactive` | `dropped`, with where to set it by hand | No |
| `keys` | `dropped`. Lando 4 has no key list: the SSH agent sidecar loads your default `~/.ssh` keys, and hardware-backed or 1Password keys use [host agent forwarding](../subsystems/ssh-host-agent.mdx) with `sshAgent: { sidecar: false }` | No |
| A version Lando 4 doesn't ship (PHP 7.4, Node 18, MariaDB 10.6, Postgres 14, Solr 8) | `unsupported`, naming the versions you can pick | Yes |
| Compose `tty`, `stdin_open`, `links`, `network_mode`, or `container_name`; image build `ssh`; Varnish with several backends; Elasticsearch or OpenSearch `plugins` | `unsupported` | Yes |
| `lando pull`, `lando push`, or `lando share` in a command | `unsupported` | Yes |
| Hosting-platform recipes, `drupal7` through `drupal9`, and unbundled recipes | Rejected with `ConfigTranslateError` | Yes |

The versions that convert are exactly the ones listed in [Service type versions](../../reference/service-types.mdx). Lando 4 never builds an image for a version it doesn't ship. Bump the version in your Lando 3 file first, check the app still works on Lando 3, then convert.

## Convert one layer

```sh
lando app:config:translate --from lando3 --file .lando.local.yml
lando app:config:translate --from lando3 --file .lando.local.yml --write
```

`--file <layer>` writes only that layer. The lower layers are read as v4 context. Lando refuses, before writing anything, when doing the job right would need edits to a layer you did not select. The most common case is a `.lando.yml` that is still Lando 3: the error tells you to convert it first or run the full conversion without `--file`.

This is the fix for a shared repo where `.lando.yml` was converted upstream and only your `.lando.local.yml` is still Lando 3.

## Load before you convert

Lando 4 refuses Lando 3 files with a tagged error instead of guessing:

| Situation | Error | Remediation it prints |
| --- | --- | --- |
| `.lando.yml` is Lando 3 | `Lando3LandofileDetected` | `lando app:config:translate --from lando3 --write` |
| `.lando.yml` is v4, another layer is Lando 3 | `LandofileDialectMixError` | `lando app:config:translate --from lando3 --file <layer> --write` |

Every `lando` app command (`info`, `start`, `exec`, `app:config:lint`) fails the same way until you convert. Your saved Lando 3 executable can still use the original files before conversion, or after you restore the backups.
