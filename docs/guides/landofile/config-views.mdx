# Inspect each stage of your Landofile

Run `lando app:config --source raw --format=json` from your app directory to see what each layer authored.

## Compare raw, merged, and resolved values

```sh
lando app:config --source raw --format=json
lando app:config --source merged --format=json
lando app:config --source resolved --format=json
```

Raw lists layers from low to high precedence. Each entry carries its `layer`, `file`, `form`, and parsed `document`. YAML templates render and TypeScript runs in its sandbox, but includes and load helpers don't run. Merge directives use JSON envelopes; literal maps that resemble those envelopes are escaped.

Merged shows the authored composition, including included fragments and canonical service aliases. Expressions stay authored. Defaults and tooling contributions haven't been assembled yet.

Resolved is the default. It shows the canonical configuration after expression materialization and validation. Raw and merged still work when a later runtime-schema check would reject the configuration. A syntax error can still stop raw; a broken include can stop merged.

## Select inside a document

```sh
lando app:config get services.web.environment --source merged --format=json
lando app:config get --source raw --path 'services.web.ports[0]' --format=json
```

Raw applies the selector independently to every layer. A layer that doesn't contain the path stays in the array without `document`. Raw get returns that array if any layer matches; if none match, `value` is absent. Merged and resolved return the selected `value`. Null is a value, not a missing path. An unindexed array stays an array. Missing human output is empty.

## Choose YAML output

```sh
lando app:config --format=yaml
lando app:config --source merged --format=yaml
```

Only the full resolved view emits a bare Landofile. Raw, merged, selected values, and get use normal YAML result envelopes. Literal secrets are redacted before emission, including values in shadowed layers. Inspection doesn't read secret stores or env files to discover more secrets.

The read-only MCP `app:config:view` and `app:config:get` tools accept `source` and `path`; get also accepts an optional `key`. The fixed `lando://app/config` resource remains resolved.

## Repair one key without fixing the whole file

```sh
# Fix one service's type while other problems remain in .lando.yml
lando app:config set services.web.type node:22 --format=json
# Drop a misspelled key
lando app:config unset services.web.typ --format=json
lando app:config validate --format=json
```

`set` and `unset` reject a write with `LandofileWriteValidationError` only if
it introduces a problem or leaves the written key or a descendant invalid.
Problems already present elsewhere, identified by the same path and message,
don't block the write. The command reports the remaining issues and their fixes
once, as a text warning or a `LANDO_CONFIG_PREEXISTING_ISSUES` warning in the
JSON envelope. Comments stay in the file. Inferred values use the first
interpretation that meets this rule. `edit` still validates the whole edited
configuration before saving. Add `--dry-run` to any of the three to run that
validation without writing; a change the file already holds reports
`(no change)`. For the preview, no-op, and lockfile rules, see
[Set, unset, and edit from the CLI](./your-landofile.mdx#set-unset-and-edit-from-the-cli).
