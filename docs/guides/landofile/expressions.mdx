# Landofile expressions

Load-time `{{ recipe.<option> }}` and `{{ env.* }}` sites resolve when Lando reads the Landofile. Plan-time `{{ app.* }}` and `{{ proxy.* }}` sites resolve when Lando builds the plan, in route hostnames, `environment:` values, service config, and tooling commands. `${...}` shell params stay blocked.

A whole-file template, includes, and env overlays still exist for the jobs expressions don't cover.

```yaml
template: handlebars
```

If you came here for `${VARS}` magic in volumes or tooling, that path is still not up.

## Load-time recipe and env

Recipe Landofiles keep values like `php:{{ recipe.php }}`. Lando fills those from that same file's merged `recipe.options`. It does not look up a recipe plugin or run recipe code.

`{{ default(env.LANDO_NODE_VERSION, 'lts') }}` reads the host environment. A missing variable fails closed unless the expression supplies a `default()`.

A missing recipe option, or an unset env var with no default, is a Landofile validation error that names the YAML path.

The `recipe:` block itself is provenance. Lando does not rewrite expressions inside it.

## Plan-time app and proxy

`app.name` and `app.slug` both resolve to the app slug: lowercase, with every run of non-alphanumerics turned into `-`, so `My App` becomes `my-app`. That is the same value route hostnames and default database names use. `proxy.defaultDomain` comes from global config and defaults to `lndo.site`.

Route hostnames, `environment:` values, service config such as `database:`, tooling `cmd` / `cmds`, and `x-` extension values all resolve at plan time:

```yaml
name: Expressions Demo
services:
  app:
    type: "node:22"
    primary: true
    environment:
      APP_HOST: "{{ app.name }}.{{ proxy.defaultDomain }}"
      APP_LABEL: "{{ default(env.LANDO_EXPRESSIONS_UNSET, 'dflt') }}-{{ app.name }}"
  database:
    type: "mariadb:11.4"
    database: "{{ app.slug }}"
tooling:
  whoami:
    service: app
    cmds:
      - "echo {{ app.name }}"
```

Recipes write their primary route the same way:

```yaml
routes:
  - hostname: "{{ app.name }}.{{ proxy.defaultDomain }}"
    scheme: both
```

Change `proxy.defaultDomain` once and every recipe URL that uses the expression follows, without editing Landofiles. Services with no authored `routes:` still get `<service>.<app>.lndo.site`.

A site that mixes scopes, like `APP_LABEL` above, is left alone by the loader and resolves at plan time.

`lando app:config` echoes the Landofile as you wrote it, so it never shows resolved values. `lando app:cache:refresh` builds the plan and fails when an expression can't resolve. `lando info` shows the resolved `database:` value in the database credentials:

```sh
lando app:cache:refresh
lando info --format=json
```

For the Landofile above, the database name comes back as `expressions-demo`.

## Plan-time service credentials

`{{ services.<name>.creds.* }}` reads another service's resolved database credentials: `.user`, `.password`, `.database`, and `.rootPassword`. Use it wherever plan-time sites already work: `environment:` values, service config, tooling `cmd` / `cmds`, and `x-` values.

```yaml
name: Creds Demo
services:
  web:
    type: "node:22"
    primary: true
    environment:
      DATABASE_URL: "postgresql://{{ services.database.creds.user }}:{{ services.database.creds.password }}@database:5432/{{ services.database.creds.database }}"
  database:
    type: "postgres:16"
```

`web` starts with a working `DATABASE_URL`. No copying the generated password out of `lando info`, no second place for it to go stale.

Lando resolves `database` first and `web` after it, whatever order the Landofile lists them in, so the values are the ones the database actually uses, including an authored `creds:` block on `database`. That ordering is what lets a service's own `creds:` read another service: a replica can set `password: "{{ services.primary.creds.password }}"`. Mixed sites like `"{{ app.name }}:{{ services.database.creds.user }}"` are fine.

Only services whose type publishes credentials have `creds`: `postgres`, `mariadb`, `mysql`, `mongodb`, and `redis` when it sets a `password:`. Reading `creds` from a service with none, or from a service name that is not in the Landofile, fails the plan with `ConfigExpressionError` and `Expression resolved to a missing value.` Lint names the site, for example `["services", "web", "environment", "DATABASE_URL"]`:

```sh
lando app:config:lint --format=json
lando app:cache:refresh
```

Two limits. A service cannot read its own `services.<name>.creds`, and two services cannot each read the other's; both fail the plan as a cycle, because credentials exist only after the service resolves. And values that arrive through `env_file:` are never interpolated, so put the expression in `environment:`.

The password still redacts in `lando info` and in logs, because the database service carries the same value under `POSTGRES_PASSWORD` / `LANDO_DB_PASSWORD`.

## Find a bad expression

A plan-time expression that points at nothing, like `{{ app.nope }}`, fails with `ConfigExpressionError` and the message `Expression resolved to a missing value.` The `lando app:cache:refresh` error does not say where. Run lint to get the YAML path:

```sh
lando app:config:lint --format=json
```

That returns `valid: false` and a violation whose `path` walks to the bad site, for example `["tooling", "probe", "cmds", 0]`.

## When expressions are not enough

Need to template the whole file, not single values? Use `template: handlebars` or `template: mustache`, then write ordinary YAML. See [Template engines](./template-engines.mdx).

Share fragments across apps with `includes:`. See [Includes and the lockfile](./includes-and-lockfile.mdx).

Override config from the environment with `LANDO_CONFIG__` or `env_file:`. See [Env overrides](./env-overrides.mdx).

`${VARS}` in volumes or tooling is still not up. Lando rejects it with `NotImplementedError` naming the file. `load()` and `import()` stay on their own file-IO path.
