# Include Landofile fragments

Use `includes:` in your `.lando.yml` to share service or tooling configuration without copying it into every app. For a complete local example, follow [Opt into a user profile](#opt-into-a-user-profile), then inspect the result with `lando app:config --format=json` from the app directory.

Put fragments under `includes:`. `kind: landofile` (the default,
whole-file fragments) and `compose` fragments resolve per file before the
layer merge, while `tooling` fragments resolve after it; see the
[Include tooling from another file](../tooling/tooling-includes.mdx) for the tooling namespace,
flatten, aliases, excludes, and vars contract. Included Landofile fragments
use native YAML anchors, aliases, and merge keys (`&node-service`,
`*node-service`, `<<:`); explicit mapping keys override merged defaults
before the fragment is layered into the app.

Fragments can use [`!override` and `!reset`](./your-landofile.mdx#replace-or-remove-a-value-with-override-and-reset).
They apply at the including file's layer, in order: a fragment's own nested
includes, then the fragment's inline keys, then the including file's inline
keys. So a fragment in `.lando.local.yml` can `!reset` a variable that
`.lando.yml` set. Overriding or resetting `includes:` in a higher layer does
not undo what a lower layer's includes already applied.

The Landofile parser preserves
encoded map order for round trips and fails closed on invalid map keys or
non-serializable values before lockfile state is written. Command-index
cache fingerprints include the resolved local include bytes, so changing a
local fragment invalidates cached app commands even after the merged
Landofile shape has dropped includes.

A fragment is a slice of one app, not an app of its own. It can't declare
top-level `name:`, `runtime:`, or `recipe:`; Lando rejects the include with
`LandofileIncludeError` naming the fragment. Expressions inside a fragment,
`{{ recipe.<option> }}` and `{{ env.* }}`, resolve against the including
app's merged recipe options and the host environment, with the same typed
whole-value results as the app's own layers. See
[Landofile expressions](./expressions.mdx#whole-value-expressions-keep-their-type).

Fragments do not need to be complete runtime values. A fragment can set only
`build.args` while the app supplies `build.context`. Lando composes the authored
maps first, resolves recipe/env expressions, assembles tooling, and validates
the effective Landofile once. Shorthand forms and defaults apply after that
composition, not separately inside each fragment.

Remote git and npm includes are pinned in `.lando.lock.yml` by resolved
revision and SHA-256 content hash; local includes are not locked. See
[Pin a remote include](#pin-a-remote-include).

A whole Compose file can be included too, with Compose's own top-level
`include:` key rather than `includes:`. Its services become `type: compose`
services of your app, and relative paths inside a local compose file resolve
from that file's directory. See
[Fold the stack into your app](../config/networks.mdx#fold-the-stack-into-your-app).

## Opt into a user profile

Put reusable YAML fragments in the `includes` directory below your Lando user
configuration root. For example, save this as `includes/php-corp.yml`:

```yaml
services:
  appserver:
    environment:
      COMPANY_REGION: local
      API_TOKEN: '${secret:CORP_API_TOKEN}'
```

Review a profile before including it: opting in trusts its build and tooling commands, not just its environment values. Select it explicitly in each consuming app's Landofile:

```yaml
includes:
  - user:php-corp.yml
```

Inspect the merged config without starting containers:

```sh
lando app:config --format=json
```

The structured result includes a `sources` inventory of logical source IDs and
SHA-256 hashes, not profile contents or host paths. A `${secret:...}` reference
authored as a whole service `environment` value in a profile is a reference in
the merged config and in the plan, the same as one written in `.lando.yml`. A bare id such as
`CORP_API_TOKEN` resolves from `LANDO_SECRET_CORP_API_TOKEN` through the default
`env` store; an `op://Vault/Item/field` reference resolves through the bundled
1Password store. Lando reads the store only when it creates the container or
runs a tooling command that needs the value; `lando app:config` shows the
reference as a typed descriptor and never reads a store. Don't interpolate
secrets into build arguments or scripts. See
[secret stores](../config/secret-stores.mdx).

No profile is loaded automatically. Opting in trusts its build and tooling
commands, not just its environment values. Profiles must use `.yml` or `.yaml`;
TypeScript, file-access expressions, remote nested includes, absolute sources and
paths escaping the user includes root are rejected.

Nested relative includes resolve from the declaring profile's directory, while
nested `user:` includes start at the user includes root. Build `context` and
`env_file` paths still resolve from the consuming app root. Include order, array
merge rules and project overrides work as they do for local fragments. Profiles
cannot declare `name`, `runtime`, or `recipe`, and cannot override reserved
runtime environment identity.

User profiles are not lockfile entries. Their content hashes participate in cache
freshness. The separate `toolingIncludes:` shorthand does not accept `user:`.

## Pin a remote include

Set `version:` to the tag, branch, or full 40-character commit SHA you want:

```yaml
includes:
  - source: github:acme/lando-shared
    path: fragments/php.yml
    version: v1.2.0
```

`github:acme/lando-shared/fragments/php.yml@v1.2.0` is the same include as
one string. Git sources can also be `https://`, `git+https://`, `ssh://`,
`git+ssh://`, or `git@host:owner/repo.git` URLs with the fragment in `path:`;
put `@ref` after the URL. For an npm include, `version:` is a version or
range, such as `version: ^1.2.0` on `source: npm:@acme/lando-fragments`.
Leave `version:` off and the include pins whatever the default branch or
latest release is when Lando first resolves it; `lando app:includes:update`
moves it forward.

The first load resolves the include and adds an entry to `.lando.lock.yml`:
the `source` (repository or package plus fragment path), the `version` you
asked for (omitted when you didn't pin one), the `resolved` commit SHA or
package version, and the fragment's SHA-256 `checksum`. Lando checks an npm
package against the registry's integrity hash or shasum before unpacking it,
and refuses a package the registry publishes neither for. Commit the
lockfile.

After that, loads use the lockfile instead of the network. Lando reads the
pinned revision from the include cache under your user cache root and checks
its checksum before parsing it, so `lando start`, `lando app:config`, and
tooling keep working offline. On a machine without the cache, Lando fetches
exactly the pinned commit or package version. A branch that moves upstream
doesn't change your app until you run `lando app:includes:update`.

Change `version:` and the next load fetches the new version and replaces that
include's lockfile entry. Review and commit the lockfile change with the
Landofile change. In CI, run `lando app:includes:verify`; it fails when the
committed lockfile doesn't pin what the Landofile asks for.

`lando app:config set`, `unset`, and `edit` never write the lockfile, with or
without `--dry-run`. They may fetch a new or re-versioned include into the
include cache to validate the candidate, but the pin arrives with the next
ordinary load, after the whole effective config loads successfully. See
[Set, unset, and edit from the CLI](./your-landofile.mdx#set-unset-and-edit-from-the-cli).

A cached fragment whose bytes no longer match its checksum fails closed with
`LandofileLockMismatchError`. If `.lando.lock.yml` can't be decoded, for
example after a merge conflict, Lando fails with `LandofileParseError`
instead of dropping your pins. Restore the file from version control or
remove it, then run `lando app:includes:update`.

A remote fragment can include files beside it with relative paths:

```yaml
# fragments/php.yml in acme/lando-shared
includes:
  - ./php-extensions.yml
```

`./php-extensions.yml` comes from the same commit or package version as
`php.yml` and gets its own lockfile entry, so it's pinned and checked the
same way. A relative path that climbs out of the repository or package fails
with `LandofileIncludeError`.

Any include that can't be read, fetched, or that cycles back on itself fails
the same way. `LandofileIncludeError` carries the `path` of the entry,
`["includes", <index>]`, and the `file` that declares it, so a nested failure
names `php.yml` rather than your root Landofile. `lando app:config:lint`
reports the same thing as a `landofile.load` violation at that path with
`source.file` set to the declaring file.

## Refresh and check the lockfile

```sh
# Re-resolve every remote include from its source, recompute SHA-256
# checksums, rewrite .lando.lock.yml only when something changed, and prune
# stale lock entries
lando app:includes:update

# Refresh only named sources, merging them into the existing lockfile
# without pruning other sources; unknown sources fail closed listing the
# known sources
lando app:includes:update SOURCE...

# Rebuild entries from the lockfile and the include cache only; a missing
# lock entry or cached copy fails closed and tells you to rerun
# app:includes:update with network access
lando app:includes:update --no-network

# Report whether a refresh would change the lockfile, such as a branch
# that moved upstream, without writing; sets exit code 1 when it would
lando app:includes:update --check

# Check that the lockfile pins every remote include at its requested
# version and that the pinned content matches; reads the include cache, so
# it runs offline once includes are cached
lando app:includes:verify
```

`app:includes:verify` reports `{ ok, entries, mismatches }` in text and JSON
output. An entry is `ok` when the lockfile pins it at the requested version
and the content matches, `mismatch` when the version or content differs,
`missing` when the lockfile has no entry for it, and `stale` when a lockfile
entry matches no include. Non-`ok` results set exit code 1.
`app:includes:update` reports
`{ lockfilePath, entries, removed, drift, wrote, checkMode, noNetwork, requestedSources }`
in text and JSON output. Each of `entries` carries the `source`, pinned
`version`, `resolved` revision, `checksum`, and an `added`, `updated`, or
`unchanged` status. The rest lists removed stale sources and says whether
drift exists, whether the lockfile was written, whether `--check` or
`--no-network` was used, and which sources were requested.

## Parser limits

The published Landofile parser rejects oversized input with
`LandofileParseError` before include or lockfile state is processed.
Inputs are capped at 1 MiB of UTF-8. Deep block indentation and inline-array
nesting fail closed with `LandofileParseError` instead of recursing
indefinitely, at 64 nested levels. Nested YAML aliases fail with
`LandofileParseError` when their resolved graph exceeds the parser's
bounded expansion or alias-depth budget.
