# Lint a Landofile

```sh
lando app:config:lint
```

That validates every retained root and include fragment against its authoring schema, validates the effective composition, checks that every key under `events:` names an event Lando can actually run, resolves every service type, and then runs the same resolved-Landofile validation stage that `lando start` and `lando app:cache:refresh` run before they plan. No doctor checks, no provider probes, no container runtime. A clean Landofile exits `0`.

Lint resolves `{{ recipe.<option> }}` and `{{ env.* }}` expressions the same way `lando start` does, before validation, so a whole-value expression like `primary: "{{ recipe.flag }}"` or `httpPort: "{{ number(default(env.PORT, '8080')) }}"` lints as the boolean or number it resolves to. An unset env var with no `default()` is a violation at that path, reported against the layer file that wrote it. Planner-owned expressions (`app.*`, `proxy.*`, `services.<name>.creds.*`) evaluate too, so a route hostname built from `{{ app.name }}` is checked as the string it becomes. See [Landofile expressions](./expressions.mdx#whole-value-expressions-keep-their-type).

Lint retains each acquired source once. It can report a bad lower fragment even when a higher layer masks the value and the effective configuration is valid. Fragment and effective findings stay separate; identical paths in different files aren't collapsed. Event checks reuse the resolved snapshot instead of loading or evaluating TypeScript again.

## What lint catches

Lint collects the findings from every check in one run, so you fix the whole list instead of replaying start after each edit.

| Rule | What it checks | Example path |
| --- | --- | --- |
| `landofile.validation` | Unknown keys, wrong literal types, missing required fields | `services.web.imgae` |
| `landofile.compose-rejection` | Compose keys Lando rejects | `services.web.deploy.replicas` |
| `landofile.expression` | Unresolvable `{{ }}` sites, type mismatches after evaluation | `tooling.t.cmd` |
| `landofile.service` | Service-type configuration: native port vars, reserved ports, unsupported versions, storage scopes, duplicate log source ids, `appMount`, `webroot` on a type without support | `services.db.environment.PGPORT` |
| `landofile.hostname` | Each `services.<name>.hostnames:` entry is a plain DNS name after evaluation | `services.web.hostnames[0]` |
| `landofile.route` | `hostname`, `pathPrefix`, and shorthand in `routes:` after evaluation | `services.web.routes[1].pathPrefix` |
| `landofile.healthcheck` | Authored `kind: http` or `kind: tcp` | `services.web.healthcheck.kind` |
| `landofile.load` | An include that cannot be read, fetched, or that cycles | `includes[1]` |

A service-type finding is reported at the field that is wrong, with the remediation in `suggestion`. A postgres service with `environment.PGPORT: "5433"` gets `PGPORT is 5433, but the service listens on 5432.` at `["services", "db", "environment", "PGPORT"]` and the suggestion `Set port: 5433 instead; Lando sets PGPORT from port:.` When a service's type fails to resolve, lint still reports every other service. Services that read its `creds.*` are skipped until you fix it, so you don't get a cascade of follow-on errors.

An include failure points at the entry that declared it: `path` is `["includes", <index>]` and `source.file` is the file holding that list, so a fragment that fails inside a nested include names the fragment and the layer that pulled it in, not your root Landofile.

## What only planning catches

`lando start` and `lando app:cache:refresh` run the same validation stage and fail with one `LandofileValidationError` listing the same issues: same `path`, `message`, `suggestion`, and `source`. Planning then goes further than lint can without a provider or an assembled plan:

- provider capability checks and anything resolved from capabilities
- feature application
- route-to-endpoint resolution and route conflicts (`RouteInputError`)
- `dependsOn` checks

A Landofile that lints clean can still fail there.

## Print JSON

```sh
lando app:config:lint --format=json
```

JSON output is a stable `ConfigLintResult` for editor integrations:

```
{ app, file, valid, violations: [{ rule, severity, path, message, scope, source: { file, layer, path }, suggestion?, line?, column? }] }
```

Each finding extends `ValidationIssue` with a stable `rule` and a `severity` of `error` or `warning`. `valid` means there are no error-severity findings; warnings alone leave it true. `path` is an array of keys and indexes, `["services", "web", "ports", 0, "target"]`, so a consumer walks it without splitting on dots or guessing whether `0` was a key or an index. `message` says what is wrong. `suggestion`, when present, says how to fix it.

`scope` is `fragment` or `effective`. `source.path` is the original authored path, so `working_dir` can be the source of an effective `workingDirectory` finding. Coordinates come only from retained source content; transformed templates and TypeScript don't get guessed YAML coordinates.

This shape is frozen by the schema artifact-set gate. `--format` defaults to `text`. Pass `--format=json` for machine output.

## Read schema violations

Text output prints the path, severity, rule identifier, and message for each finding.

An unknown key gets a `suggestion` naming the closest allowed key, as long as the typo is within two edits. `imgae` suggests `image`. A key nowhere near anything valid gets a plain unknown-key message instead. Unknown keys are schema-only violations, never a `NotImplementedError`.

## Read rejected Compose keys

A rejected Compose key keeps its full authored path, for example `["services", "web", "deploy", "replicas"]`. The `suggestion` comes from the pinned Compose disposition matrix instead of a generic unknown-key message.

## Fix healthcheck warnings

`healthcheck.bare-compose-marker` means a bare argv list starts with `CMD`, `CMD-SHELL`, or `NONE`. Bare lists execute literally, including that first item. Remove the marker, or move the list under `test:` in a block YAML healthcheck object.

`healthcheck.mixed-dialects` means different sources contributed surviving Lando-only and Compose-only healthcheck fields. Lando fields still win. Pick one dialect across layers rather than relying on that precedence. Discarded lower fields and shared `retries` or `disable` fields alone do not trigger the warning.

## Read unknown event names

Lint resolves your tooling the same way `lando start` does: your Landofile, every config layer, every include, and every service type. So a task a service type contributes, such as `mysql` on a `mysql:8.0` service, makes `pre-mysql` and `post-mysql` valid here too. An event key outside that set exits non-zero with `LandofileUnknownEventError` and lists every name you could have used.

When Lando cannot resolve your services at all, lint reports that resolution failure. It does not call your event key unknown on the strength of a set it could not finish building.

## Run it from doctor

`lando doctor --app` runs the same lint as part of the combined doctor report, under the `app-config-lint` check name. Both commands call the same pass, so they never disagree about which events exist.

## Validate as you type

Your editor can catch the structural problems (unknown keys, wrong literal types, an expression where none belongs) before you run anything; lint still owns resolving expressions. See [Validate a Landofile in your editor](./editor-validation.mdx) for the one-line modeline.
