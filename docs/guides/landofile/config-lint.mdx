# Lint a Landofile

Check your Landofile before starting containers. From the app directory, run:

```sh
lando app:config:lint
```

Lint checks each retained root and include fragment against its authoring schema, then validates their effective composition and resolves every service type. It runs the same resolved-Landofile validation stage as `lando start` and `lando app:cache:refresh`, including event names and conflicts between tooling names and built-in commands.

When every load failure is a local problem with a known destination (a failed `load()` or other load-time expression, an unset env expression, a bad env list entry, or an invalid `lando:` range), lint still runs those effective and resolve checks on what loaded. Services and fields blocked by the load failure stay unavailable, so you see the load finding next to independent problems in other services. A missing include, a failed root layer, a failed tooling include, a lockfile problem, or a blocked app name stops effective and resolve checks until load is clean, because the missing content could change any of their answers. `lando start` stays strict either way.

When that earlier work finds no errors on a successfully loaded Landofile, lint runs the same final planning path `lando start` uses. That pass uses the selected provider's offline capability declaration. It applies features, builds default routes, checks route conflicts and `depends_on`, and computes certificate plans. It does not construct a provider, contact a container runtime, issue certificates through a CA, or read or write the plan cache. When the provider has no offline declaration, lint skips final planning and adds one `landofile.capability` warning that those checks run at `lando start`. Final planning never runs while load still failed.

It does not run doctor checks, probe a live provider, or start a container runtime. Every output format exits `1` when lint finds errors and `0` when it does not. JSON and YAML still return a successful report with `ok: true`: inspect `result.valid` and the violations list. Successful report generation is not itself a clean-lint verdict.

Lint does not save configuration, publish include pins, or recover interrupted file updates. It may fetch remote includes into Lando's cache while checking them. If a managed-file update is unfinished or blocked, lint reports a `landofile.load` finding with recovery guidance instead of changing its files or recovery records.

Lint resolves `{{ recipe.<option> }}` and `{{ env.* }}` expressions the same way `lando start` does, before validation, so a whole-value expression like `primary: "{{ recipe.flag }}"` or `httpPort: "{{ number(default(env.PORT, '8080')) }}"` lints as the boolean or number it resolves to. An unset env var with no `default()` is a violation at that path, reported against the layer file that wrote it. Planner-owned expressions (`app.*`, `proxy.*`, `services.<name>.creds.*`) evaluate too, so a route hostname built from `{{ app.name }}` is checked as the string it becomes. See [Landofile expressions](./expressions.mdx#whole-value-expressions-keep-their-type).

Lint retains each acquired source once. It can report a bad lower fragment even when a higher layer masks the value and the effective configuration is valid. A value that's wrong in its own file and in the composed app is one finding listing both scopes, unless composition moves it to a different path, such as a later position in a merged list. Identical paths in different files stay separate findings. Event and tooling checks reuse the resolved snapshot instead of loading or evaluating TypeScript again.

For example, `tooling.old-build: disabled` is one finding at fragment and effective scope: "`disabled` is not a command; use false to disable a task". Set `tooling.old-build: false` to disable it. To keep the command and its metadata, set `disabled: true` inside the task object instead.

## What lint catches

Lint reports every independent load failure in one run: broken layers, load expressions, includes, tooling includes, recipe/env expressions, and `lando:` ranges. It skips the failed entries and continues with what loaded, retaining fragment findings from those files. Checks that depend on a failed entry are skipped instead of producing follow-on errors.

When the only load failures are local and isolable, effective configuration and service checks still run. A failed `{{ load('./missing-payload.txt') }}` under `services.other.environment.FOO` and `type: no-such-type` under `services.web` produce both findings in one JSON report: a `landofile.load` finding at the FOO path and a `landofile.service` finding at `services.web.type`. Lint reports nothing else about the blocked `other` service. A missing include still stops effective checks, so restore the fragment and lint again.

Lint also reports the first planning-time expression failure in each independently failing service. For example, if a BusyBox service with no planned port and a PHP service using `via: cli` both read `{{ service.port }}`, one lint run reports two `landofile.expression` findings and exits `1`. Lint skips checks that need facts from those services and reports those omissions as `resolve` / `unavailable`. An expression failure outside the service checks can still stop the remaining resolve checks, but it won't hide findings already collected. Operational planning, including `lando start` and `lando app:cache:refresh`, stops at the first expression failure.

Every finding carries a stable `rule` id. The full list of registered ids, the stages that emit them, their severities, and example paths lives in the [config lint rule reference](../../reference/config-lint-rules.mdx). Use that page when you need the complete inventory or a deep link such as [`landofile.hostname`](../../reference/config-lint-rules.mdx#landofile-hostname) or [`env-file.read`](../../reference/config-lint-rules.mdx#env-file-read).

A service-type finding is reported at the field that is wrong, with the remediation in `suggestion`. A postgres service with `environment.PGPORT: "5433"` gets `PGPORT is 5433, but the service listens on 5432.` at `["services", "db", "environment", "PGPORT"]` and the suggestion `Set port: 5433 instead; Lando sets PGPORT from port:.` When a service's type fails to resolve, lint still reports every other service. Services that read its `creds.*` are skipped until you fix it, so you don't get a cascade of follow-on errors.

An include failure points at the entry that declared it: `path` is `["includes", <index>]` and `source.file` is the file holding that list, so a fragment that fails inside a nested include names the fragment and the layer that pulled it in, not your root Landofile. Tooling includes work the same way. A `kind: tooling` entry reports `["includes", <index>]`, and a `toolingIncludes:` entry reports `["toolingIncludes", <namespace>]`, with the file and layer that declared it.

An invalid value within an include declaration points at that value. For example, include-level vars accept only literal strings, numbers, or booleans. Writing `toolingIncludes.frag.vars.WHO: { sh: echo inc }` produces a `landofile.validation` finding at `toolingIncludes.frag.vars.WHO`, with the declaring file and its YAML coordinates. Lint skips the invalid entry and continues checking the entries that can load.

Env-file findings point to the configuration entry that declared the file. Their messages name the resolved env-file path and, for syntax and literal warnings, its line number. Warnings stay in `violations` with `severity: "warning"`; they leave `valid` true when no errors exist. Env-file values are never interpolated. See [Quote env file values](./env-overrides.mdx#quote-env-file-values) for quoting rules and fixes.

## What only start still catches

When the resolve pass completes with no errors on a successfully loaded Landofile and the selected provider declares offline capabilities, lint runs the same final planning path as `lando start` and `lando app:cache:refresh`. Shared findings keep the same `rule`, `path`, `message`, `suggestion`, and `source`. The exception is `landofile.host-shell`: planning fails only for host steps of lifecycle events such as `pre-start` and for host readiness, so a broken host tooling task you never run doesn't stop `lando start`. Tooling declaration findings and computed var findings under `landofile.tooling` are lint-only too: planning doesn't fail on them, and only the affected task refuses to run.

A Landofile that still has load findings never reaches final planning, even when resolve already reported independent service findings next to them. Final planning still needs offline capabilities on a clean load. Without them, lint skips that stage and leaves these checks for start:

- feature application
- automatic route selection and route conflicts (`RouteInputError`)
- `depends_on` checks
- capability checks that need a live provider or an offline declaration the provider does not publish

Even after a clean lint with offline capabilities, start can still fail on work lint never does:

- whether an external network exists on the engine
- provider construction, runtime contact, and image inspection
- certificate authority issuance

A Landofile that lints clean can still fail there.

## Fix a route's HTTP endpoint

A numeric route declares the HTTP listener and the hostname together. No separate
`endpoints:` entry is required when the selector is the container port that serves
HTTP:

```yaml
services:
  web:
    type: compose
    image: nginx:alpine
    routes:
      - web.lndo.site:80
```

Use endpoint-only authoring when you want the default HTTPS hostname, a named
reusable listener, or an HTTPS backend. Write `https:N` (or a `kind` object with
`protocol: https`) when the process speaks TLS on that port; the route's public
scheme does not upgrade an implied HTTP listener. A string selector, an omitted
selector, and a generated default route never declare a listener. Keep an explicit
`endpoints:` entry when a named or unselected listener is missing and no numeric
route covers it. A raw Compose image, `ports:`, `expose:`, or a TCP endpoint's
`appProtocol: http` still does not prove HTTP on its own.

Lint checks authored routes against service and app features' endpoint declarations
during resolve, including listeners numeric routes declare. After a clean resolve
with offline provider capabilities, final planning applies those features and builds
the same default routes start would, still without issuing certificates or reading
or writing a plan cache. An explicit `endpoints:` list replaces type and app-feature
declarations and synthesis from `ports:` and `expose:`; it does not suppress numeric
route declarations. `endpoints: []` clears those contributions. With multiple HTTP listeners,
select one by name or port in the route, or mark one listener `primary: true`. A
primary TCP listener does not hide the service's only HTTP listener.

A numeric route can still use an existing HTTP(S) listener on the same port as
an independent UDP listener. Without an HTTP(S) listener, known TCP or UDP at the
selected port causes a protocol conflict, even if `endpoints: []` cleared a listener
from the service type or a feature. Change the route to the actual HTTP(S) port,
or declare `http:N` or `https:N` if the backend speaks that protocol. A Compose UDP
publication alone does not block an implied HTTP listener. A missing named or
unselected listener, an unmatched alias, or ambiguous selection is an indexed
`landofile.route` finding. Start and cache refresh reject the same entries. Lint
also rejects a top-level `proxy:` route whose target service is not declared.
Correct the proxy key or declare the target under `services:`.
It cannot check bindings whose service or endpoint declarations are unavailable; it
reports the underlying failure instead. It does not contact the service to prove
that the declared listener is serving HTTP.

## Print JSON

```sh
lando app:config:lint --format=json
```

JSON output is a stable `ConfigLintResult` for editor integrations:

```
{
  app, file, valid,
  violations: [{ rule, reason?, severity, path, message, scopes?, source?, suggestion?, related?, line?, column? }],
  skipped?: [{ stage, reason, path?, source?: { file, layer, path }, message }]
}
```

Each finding extends `ValidationIssue` with a stable `rule` and a `severity` of `error` or `warning`. `valid` means there are no error-severity findings; warnings alone leave it true. `path` is an array of keys and indexes, `["services", "web", "ports", 0, "target"]`, so a consumer walks it without splitting on dots or guessing whether `0` was a key or an index. `message` says what is wrong. `suggestion`, when present, says how to fix it. A `landofile.load` finding also carries `reason`, a stable id for the cause: the failing issue's own rule, such as `unsupported-secret-reference` or `unsupported-expression`, or the failure's error tag, such as `LandofileIncludeError`. A [tooling declaration finding](#read-tooling-declaration-findings) carries one too, such as `alias-collision`. Match on `reason` instead of parsing `message`. `related`, when present, lists the other declarations that explain a conflict. It holds locations only, never the values written there.

`skipped` lists checks lint couldn't run. Match on `stage` and `reason`, not on `message`. A missing include can skip effective and resolve checks (`effective` / `load-failure`). An isolated failure can skip checks on one entry (`resolve` / `unavailable`). If an expression error stops the resolve pass, lint reports the expression finding and records the remaining resolve checks as skipped (`resolve` / `earlier-errors`). Follow `path` to the effective value and `source`, when present, to the authored failure. Final planning can be skipped because of `earlier-errors`, a `diagnostic-document`, or `capabilities-undeclared`. An absent or empty list means lint recorded no omissions. Skips don't change `valid`.

Text output prints `suggestion` under `fix:` and lists omissions under **Not checked** after the findings.

`scopes` lists `fragment`, `effective`, or both: `fragment` means the file is wrong on its own, `effective` means the composed app is. `source.path` is the original authored path, so an authored path stays the finding path after canonical re-encode. Coordinates come only from retained source content; transformed templates and TypeScript don't get guessed YAML coordinates.

This shape is frozen by the schema artifact-set gate. `--format` defaults to `text`. Pass `--format=json` for machine output.

## Read schema violations

Text output prints each finding's path, severity, rule, and message, then where it came from: the file, line, and column, the layer, and the scope. A typo in `.lando.local.yml` reads like this:

```
/tmp/demo-app/.lando.local.yml: 1 config lint finding.
  services.web.imagee: error [landofile.validation] Expected no excess property
    at /tmp/demo-app/.lando.local.yml:3:5 (local layer; fragment and effective)
    fix: Did you mean "image"?
```

That file is wrong on its own (`fragment`) and it breaks the composed app (`effective`), so it's one finding with both scopes. JSON reports it once, with `"scopes": ["fragment", "effective"]`. When the effective path differs from what you wrote, the location line adds `authored as <path>`.

A key that is not a plain identifier prints in quoted brackets, so an environment variable named `x.dotted` reads `services.web.environment["x.dotted"]` rather than looking like two nested keys. JSON keeps the array, `["services", "web", "environment", "x.dotted"]`. Numeric indexes print as `[0]`; a string key `"0"` prints as `["0"]`. That printed path is the same selector `lando app:config get`, `set`, `unset`, and `describe` accept, so you can paste it into a command. Quote the whole selector in the shell when it contains brackets. See [Select inside a document](./config-views.mdx#select-inside-a-document) and [Set, unset, and edit from the CLI](./your-landofile.mdx#set-unset-and-edit-from-the-cli).

Wrong values name the expected shape, not an internal schema name. For example,
`services.web: nginx` needs an object. A filter with `kind: stripPrefix` and
`prefix: 5` reports the prefix's wrong type once, with both scopes. It does not
report errors for other filter kinds you didn't choose.

A malformed endpoint scalar is an indexed finding. For example,
`endpoints: [tcp:9000, http:65536]` fails at `["services", "web", "endpoints", 1]`
with a message that names the accepted `protocol:port` or `name=protocol:port`
form (and `kind` objects). The `source.path` keeps the authored index.

An unknown key gets a `suggestion` naming the closest allowed key, as long as the typo is within two edits. `imgae` suggests `image`. A key nowhere near anything valid gets a plain unknown-key message instead. Unknown keys are schema-only violations, never a `NotImplementedError`.

A removed spelling such as `workingDirectory` or `dockerfileInline` is one `landofile.validation` finding with `reason: "key.renamed"`. The `suggestion` names the canonical key (`working_dir`, `dockerfile_inline`). Match on `reason` rather than the message.

If your service has `environment: [FOO]`, lint reports `environment.bare-entry` at `services.web.environment[0]` (for a service named `web`). To pass `FOO` from your host, use the suggested entry `"FOO={{ env.FOO }}"` and set `FOO` before running Lando. For a literal value, write `FOO=value`; `FOO=` passes an empty string. When scripting against lint JSON, match `rule` and `reason` rather than the message. The [rule reference](../../reference/config-lint-rules.mdx#reasons-within-a-rule) lists the documented reasons.

## Read rejected Compose keys

A rejected Compose key keeps its full authored path, for example `["services", "web", "deploy", "replicas"]`. The `suggestion` comes from the pinned Compose disposition matrix instead of a generic unknown-key message.

## Fix healthcheck warnings

[`healthcheck.bare-compose-marker`](../../reference/config-lint-rules.mdx#healthcheck-bare-compose-marker) means a bare argv list starts with `CMD`, `CMD-SHELL`, or `NONE`. Bare lists execute literally, including that first item. Remove the marker, or move the list under `test:` in a block YAML healthcheck object.

[`healthcheck.mixed-dialects`](../../reference/config-lint-rules.mdx#healthcheck-mixed-dialects) reports conflicting Lando and Compose fields. It is an error when both fields come from the same source. For example, keep `command:` and change `interval: 1s` to `intervalSeconds: 1`. When the fields come from different sources, lint warns and Lando fields take precedence. Fields discarded during layering and shared `retries` do not trigger the rule.

The same checks apply independently to `readiness`, using [`readiness.bare-compose-marker`](../../reference/config-lint-rules.mdx#readiness-bare-compose-marker) and [`readiness.mixed-dialects`](../../reference/config-lint-rules.mdx#readiness-mixed-dialects). Native `healthcheck` cannot select a host target or an explicit probe user; move that command to `readiness` instead of changing monitoring through execution metadata. Use `lando app:cache:refresh --format=json` to validate the effective plan without starting services. See [Make start wait for your app](../services/wait-for-your-app.mdx) for defaults and disabling either policy.

## Fix a Landofile router bind

[`router.bind-address-global-only`](../../reference/config-lint-rules.mdx#router-bind-address-global-only) means the Landofile set `router.bindAddress`. That key is installation-wide: set it in `config.yml` or `LANDO_ROUTER_BIND_ADDRESS`, then run `lando start`. The Landofile value is ignored so one app cannot widen the shared listener. The Landofile stays valid.

## Read unknown event names

Lint resolves your tooling the same way `lando start` does: your Landofile, every config layer, every include, and every service type. So a task a service type contributes, such as `mysql` on a `mysql:8.0` service, makes `pre-mysql` and `post-mysql` valid here too. An event key outside that set is a `landofile.event` finding at `["events", "<name>"]`, reported alongside every other finding. Its `suggestion` names the closest valid event when you're within two edits, and lists every name you could have used when you aren't. `lando start` fails on the same keys with the same suggestions.

When a service type fails to resolve, lint reports that failure and skips the event check. That service's tasks are missing from the set, so lint doesn't call your event key unknown on the strength of a set it couldn't finish building.

## Read reserved tooling names

`run`, `scratch`, and every `scratch:*` name belong to scratch apps. A tooling task with one of those names is a `landofile.tooling` finding at `["tooling", "<name>"]`, whether it comes from your Landofile, a tooling include namespaced `scratch`, or a service type. The same rule covers a task whose brackets would land on a reserved event: a task named `start` would bind `pre-start`, and one named `pull` would bind the `post-pull` sync hook. `lando start` rejects the same tasks, and `commandAliases.custom` can't hand those names to a task. A task you wrote points `source` at your `tooling:` entry; rename it. A service type's task points `source` at that service's `type`; drop it by setting `tooling.<name>: false`.

```yaml
tooling:
  run: false
```

## Read script findings

Lint also checks every `.lando/scripts/**/*.bun.sh` script in the app, and it does so even when the Landofile itself fails to load, so one pass shows you every script Lando can't turn into a command. Two rules cover scripts:

- [`script.front-matter`](../../reference/config-lint-rules.mdx#script-front-matter): a missing or malformed `# ---` block (with the YAML line and column), an unknown or unsupported key at its key path, `wrapper`, an empty file, a file name that cannot become a command, two scripts that produce the same command id, or a `service` other than `:host`.
- [`script.host-shell`](../../reference/config-lint-rules.mdx#script-host-shell): a body form Bun Shell rejects, such as `${HOME}`, with its line and column. Lint checks the body only for enabled scripts that no Landofile task of the same name shadows.

With a script that has no front matter, one that sets `wrapper: true`, and one whose body uses `${HOME}`, lint prints:

```
/tmp/lint-scripts-demo/.lando.yml: 3 config lint findings.
  .lando/scripts/bad.bun.sh: error [script.front-matter] .bun.sh script at /tmp/lint-scripts-demo/.lando/scripts/bad.bun.sh is missing the front-matter block.
    at /tmp/lint-scripts-demo/.lando/scripts/bad.bun.sh (script layer)
    fix: Wrap the front-matter in `# ---` markers, prefix every line with `# `, and use only service, desc, description, summary, flags, args, arguments, disabled.
  .lando/scripts/wrapped.bun.sh: error [script.front-matter] Expected no excess property
    at /tmp/lint-scripts-demo/.lando/scripts/wrapped.bun.sh:3:3, authored as wrapper (script layer)
    fix: Wrap the front-matter in `# ---` markers, prefix every line with `# `, and use only service, desc, description, summary, flags, args, arguments, disabled.
  .lando/scripts/greet.bun.sh: error [script.host-shell] Bun Shell does not expand ${HOME}.
    at /tmp/lint-scripts-demo/.lando/scripts/greet.bun.sh:5:6 (script layer)
    fix: Write $HOME, or "$HOME" when a letter, digit, or underscore follows it.
```

The location names the script by its path relative to the app. In JSON, each script finding carries `source: { "layer": "script", "file": <absolute path>, "path": <front-matter key path> }`, with `line` and `column` when lint knows them; `path` is the key inside the front matter, such as `["wrapper"]`, or `[]` for a problem with the whole file. A broken script doesn't stop `lando start` or your other commands. Only that script's own command and help fail, and `lando start`, `lando restart`, `lando rebuild`, and `lando app:cache:refresh` warn with `LANDO_SCRIPT_INVALID`. Run lint, fix what it names, and run the script again. See [Add project commands with Bun Shell scripts](../tooling/bun-shell-scripts.mdx#write-the-front-matter) for the front-matter keys.

## Read tooling declaration findings

A task can pass the schema and still contradict itself. Lint reports each of these as a `landofile.tooling` finding at the key that is wrong, with the file, line, and column that wrote it:

- two flags that share an `alias`, or an alias that repeats a flag name
- a `default` outside its `choices`, a `required` input with a `default`, or a boolean flag with `choices`
- args that mix ordered and unordered declarations, repeat an `order`, or put a required arg after an optional one
- a `wrapper: true` task with more than one command, declared flags or args, or `arguments: false`
- an `env` key named `LANDO` or starting with `LANDO_`
- a `service: ":<flag>"` selector whose flag the task doesn't declare

One run lists every affected task, not only the first. Fix them in any order.

Each finding has a `reason` that names the rule, such as `alias-collision`, `default-outside-choices`, `argument-order-duplicate`, `wrapper-command-count`, `reserved-env`, or `service-flag`, and a `suggestion` written for that rule. Two flags sharing `-n` read like this:

```
  tooling.broken.flags.note.alias: error [landofile.tooling] Flag alias collides with another flag name or alias.
    at /tmp/malformed-task/.lando.yml:14:9 (canonical layer; effective)
    fix: Choose an alias that is not used by another flag name or alias.
```

`source` names where the value was written, which isn't always your root Landofile. It can be an include or tooling include fragment, an override layer such as `.lando.local.yml`, `toolingDefaults` when the task inherited the value from there, or the service's `type` when a service type contributed the task.

Lint skips disabled tasks, whether you wrote `tooling.<name>: false` or `disabled: true`, because Lando refuses them before it reads their declarations. It does check tasks hidden by `internal: true` on a tooling include. Those stay callable, so their mistakes still matter.

These findings are lint-only. A malformed task doesn't stop unrelated tasks or `lando start` unless a lifecycle hook calls it. Lando lists it as unavailable, and it fails with `ToolingCompileError` when you run it or ask for its help. That error carries the same findings in `error.issues`. See [Fix an unavailable task](../tooling/flags-and-args.mdx#fix-an-unavailable-task) for what a call, a hook, and an MCP client see.

## Read computed var findings

A task var written as `{ sh: <command> }` is computed when the task runs. Two positions cannot read such a value: another var's definition and the task-level `service`, `user`, and `dir`. Lint reports a read from one of those positions as a `landofile.tooling` finding at the var or field that reads it, with the same message `lando <task>` fails with (`ToolingCompileError`):

```
  tooling.badref.vars.LABEL: error [landofile.tooling] Dynamic tooling vars cannot be read by var definitions or task-level service, user, or dir.
    at /tmp/lint-dynamic-vars-demo/.lando.yml:9:7 (canonical layer; effective)
    fix: Use a literal or invocation input in this field; read shell-computed vars in commands or step overrides.
```

When the task runs on the host (`service: ":host"`), its `vars.<name>.sh` is a host Bun Shell command, so `landofile.host-shell` checks it at `tooling.<task>.vars.<name>.sh` the same way it checks `cmd`. A `{ default: ... }` or `{ prompt: ... }` var is not a var form; it fails the load with `NotImplementedError`, which lint reports as `landofile.load`. See [Compute a value with a shell command](../tooling/flags-and-args.mdx#compute-a-value-with-a-shell-command).

Lint reports every refused tooling key once, with `reason: "NotImplementedError"`, its authored path, and the loader's remediation. For example, `tooling.build.vars.D.default` points at the `default` key and tells you to write the value directly. Refused task fields such as `deps` and `sources`, unsupported flag or arg fields, and event-step `platforms` receive the same treatment. These findings replace the generic unknown-key message for those keys.

A command that reads an invocation scope Lando doesn't provide yet (`service`, `sources`, `generates`, `checksum`, or `timestamp`) is reported the same way: one `landofile.load` finding per read, at the command or field that reads it, with its line and column. A read in `tooling.stamp.cmd` and a `deps` key on another task are two findings with two paths. Lint doesn't add a copy without a path.

Unlike a malformed declaration, a refused key or scope still fails the load. `lando start`, `lando app:cache:refresh`, and every task stop with `NotImplementedError` naming the first refused path until you remove it.

## Run it from doctor

`lando doctor --app` runs the same lint, including the local-isolable load path and final planning after a clean earlier pass, as part of the combined doctor report under the `app-config-lint` check name. Both commands call the same pass, so they never disagree about which events exist, which load findings appear next to independent service findings, or which final-planning findings appear.

A passing app-config check doesn't mean every check ran. Look for `app-config` entries in the doctor report's `skipped` list to see which checks weren't run.
