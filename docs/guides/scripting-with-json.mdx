# Script Lando with JSON

Use `lando version --format=json` or `lando version -j` to run the command and read its full `CommandResultEnvelope`. Start scripts with the exit status and `ok` field, then read `result` or `error` as appropriate.

Bare `lando version --json` is different: it lists selectable result keys as a JSON array without running the command body:

```sh
lando version --json
```

Every non-interactive command accepts `--format json` and emits one envelope
on stdout. `--format=json` is equivalent. `-j` is the single-character
shorthand for that full envelope. Bare `--json` lists keys. `--json=key`
projects that key inside `result`. `--jq` prints a raw jq selection.

On success the envelope wraps the command's typed result under `result` with
`ok: true`. On failure it carries the tagged error JSON under `error` with
`ok: false`. A process that finishes unsuccessfully also retains its typed
`result`, so failure does not discard its exit code and diagnostics. A global `apiVersion: "v4"` identifies the wire contract, and
the redaction service runs before emission so secrets never appear in
machine output.

Failures that include a service identify it in `error.service`; scripts don't
need to parse that name from the human message. Other JSON-safe error fields stay
structured too. Raw causes, stacks, and redaction-token lists are not emitted.

Streaming commands such as `app:logs` and `app:exec` emit `StreamFrame`
frames under `--format json`: `stdout` and `stderr` frames carry output,
`event` frames carry progress and lifecycle events as they happen, and a
single result frame comes last. `lando start --format=json` and
`lando rebuild --format=json` stream their events the same way, so a script
sees each service's progress while the command runs. If the reader falls far
enough behind that Lando drops events instead of stalling, the result frame's
`envelope.warnings` carries `LANDO_EVENT_FRAMES_DROPPED` with the count.
Source and compiled `--format json` are identical because both use the same
native registry and dispatcher.

## Capture project script output

Project scripts from `.lando/scripts/*.bun.sh` emit the same envelope. With
`--format=json` or `--format=yaml`, `result` carries the script's `stdout`,
`stderr`, and `exitCode`, and Lando exits with the script's own code. A nonzero
script exit sets `ok: false`, retains `result`, and includes a tagged `error`.
Writing those scripts is covered in
[Add project commands with Bun Shell scripts](../tooling/bun-shell-scripts/).

Diagnostic reports are different from failed processes. A completed lint report
can have `ok: true`, `result.valid: false`, and shell exit status 1. Check the
report's fields as well as `ok`. JSON and YAML preserve that exit status, just
like text output.

After adding the `stamp.bun.sh` example from that guide to your app, run these commands from its directory:

```sh
lando app:cache:refresh
lando stamp abc1234 --format=json
```

## List keys with --json

Bare `--json` after a command id lists the keys you can project. The command
does not run, so `lando app:config --json` never needs a successful view of
secrets. Space-form `--json echo` does not steal `echo`. Use `--json=key`
for a single key.

## Project a key

`--json=app` still emits the envelope. `ok` stays `true` and `result`
contains only that key.

## Select with --jq

`--jq .ok` prints the raw scalar `true`. Do not combine bare `--json` with
`--jq`. An unknown key exits nonzero.

## Read anything as YAML

`--format=yaml` is the envelope again, serialized as YAML. Any command that
does not print a document of its own emits the same `CommandResultEnvelope`
it emits for `--format=json`. Parse either one and you hold the same model.

```sh
lando app:info --format=yaml
```

```yaml
apiVersion: v4
command: app:info
ok: true
result:
  app: demo
  services:
    - service: appserver
      status: running
warnings: []
deprecations: []
```

The controls carry over unchanged. Redaction runs first. `--json=<key>`
projects inside `result`. Warnings land in `warnings`. A closed pipe exits
`141`. A failure is a YAML envelope on stdout with `ok: false` and the tagged
`error`, and the command keeps its non-zero exit code. Streaming commands
such as `app:logs` and `app:exec` emit only the terminal envelope under
`yaml`; per-frame streaming stays a JSON concern.

Plugin `message.warn` events also land in `warnings` for JSON and YAML
results, whether the command succeeds or fails. Each uses the code
`LANDO_MESSAGE_WARN` and puts the event body in `message`, with secrets
redacted. Existing coded warnings keep their own codes and remediation.
For JSON streams, read warnings from the terminal result frame's
`envelope.warnings`; YAML streaming commands put them in the terminal
envelope document. Human warning output is unchanged.

`--jq` output is jq's output, whatever the format. `--format=yaml --jq .ok`
prints `true`, byte for byte what `--format=json --jq .ok` prints. Do not
expect a YAML document from a jq selection.

Two commands print a product document instead of the envelope, and only on
success:

- `lando app:config --format=yaml` (the bare `view` verb) prints the
  Landofile. `lando app:config get ... --format=yaml` and the write verbs
  emit the envelope.
- `lando app:config:translate --format=yaml` (the default preview) prints the
  translated v4 Landofile. `--list`, `--detect`, and `--write` emit the
  envelope.

Pass `--jq` or `--json=<key>` to either of those and you get the envelope,
because those controls select inside it.

## Read config as YAML

`lando app:config --format=yaml` is the export exception described above: on
success it prints the Landofile itself as YAML, not the envelope. What comes
out parses back into the same document Lando held. Values YAML would
otherwise reinterpret get quoted on the way out: the redaction sentinel
`[redacted]`, strings that look like booleans (`yes`, `off`, `true`),
strings that look like numbers (`8080`, `1e3`), strings that look like
`null` (`~`, `null`), values containing `: `, and values that start with an
indicator character such as `*`, `&`, `!`, `%`, `@`, `` ` ``, `|`, or `>`. Parse the
output with any YAML 1.2 loader and you get strings where Lando had strings.

```sh
lando app:config --format=yaml > .lando.exported.yml
```

## Pipe into a consumer that exits early

Machine output survives a closed pipe. When the reader stops early, Lando
ends output silently and exits with the conventional terminated-pipeline
status `141`. No stack trace, no partial envelope on stderr.

```sh
lando app:config --format=json | head -n 1
lando app:config --format=json | jq -e .ok
```

Stdout and stderr are handled independently because you can redirect them
separately. A consumer that closes stdout does not silence diagnostics headed
for stderr, and a closed stderr does not truncate the envelope on stdout.
Grab the Lando exit status from `PIPESTATUS` in bash or `pipestatus` in zsh;
the pipeline's own status is whatever the last consumer returned.

## Ask only for a format the command produces

`--format` offers `text`, `json`, and `yaml` on every command. Those three are
universal: `text` is the command's human rendering, and `json` and `yaml` are
the same result envelope.

Two more values exist, and a command offers them only when it produces them.
`table` is a human rendering that the list, config, and recipe commands emit.
`ndjson` is the per-check stream `lando doctor` emits. Ask a command for a
format it does not produce and it fails with `RendererSelectionError` naming
the formats it does support, rather than quietly printing its text form at
exit 0:

```sh
lando version --format=table
# RendererSelectionError
# meta:version does not support result format "table". Allowed: text, json, yaml.
```

`lando <command> --help` names the same list in its global-flags footer, and
the generated command reference carries it too, so a program never has to
guess.

## Envelope contract

The full-envelope aliases are `--format json`, `--format=json`, `-j`, and
`--format yaml` (or `--format=yaml`) for the same envelope as YAML.
The failure envelope has the shape `{ "ok": false, "error": <tagged-error> }`.
A failing command keeps its non-zero exit code alongside the envelope so
scripts can branch on both. The tagged error exposes a machine `_tag` plus
a required `message` and nonblank `remediation`, so an agent can react to the failure class without
scraping prose.

If rollback, cleanup, or another step also fails, `error` still describes the
primary failure and determines the exit code. `error.additionalErrors` contains
the other failures in cause order, each with its own `_tag`, `message`, required
`role`, required `remediation`, and JSON-safe fields. `role` is `rollback` for
undoing partial work, `cleanup` for release or bookkeeping, or `peer` for a
sibling step. The array is absent when there are no
additional failures, and its entries never contain another `additionalErrors`.
Interruptions are not additional errors. MCP results use the same projection.
Reason annotations select the first operation failure, not whichever failure
happens to appear first. Human reports show the primary message and remediation
first, followed by `Rollback also failed (<tag>)`, `Cleanup also failed (<tag>)`,
or `Also failed (<tag>)`. Each block includes its own remediation and distinct
diagnostic fields, without stack traces or repeated command context.

An unexpected Lando defect returns `LandoInternalError` and exits `1`, including
failures during routing, startup, formatting, or cleanup. A known error that was
raised as a defect keeps its own tag and remediation. Its remediation tells
you how to collect diagnostics and report the problem. Normal reports contain
no stack traces. Rerun with `--debug --trace` to collect redacted diagnostic
records on stderr and invocation timings. Redirect stderr to a file if you need
to attach those records to a bug report. Runtime worker logs are separate files
under the report's `logsDir`; debug records are not automatically saved there.
Review diagnostics for secrets before sharing them.

A failed `lando start` does not undo established app resources, so its
envelope does not carry app-wide `rollback` entries. Other commands still
can: role `rollback` means that command tried to undo partial work.
Acquisition-local cleanup can still fail and show up with role `cleanup`.
Whatever start established stays in place. The human report adds one warning
after the error. It lists running, created/stopped, and unverified services,
and says agent forwarding and file sync stay active where they were
established. That warning is not in the JSON or YAML envelope. Call
`lando info --format=json` to see what is there, then `lando start` again
to converge.

The error also keeps its remaining JSON-safe fields directly under `error`.
For example, `ConfigExpressionError` carries `error.path` (a dotted string),
`error.expression`, and `error.filePath`; `ConfigError` carries `error.path`
and, for a global config that fails validation, `error.issues` and
`error.remediation` (see below).
JSON, YAML, terminal result frames, and MCP envelopes preserve the same fields
with the same secret redaction. `cause`, `stack`, and private redaction metadata
are excluded. Fields containing class instances, unsupported values, cycles,
or nesting beyond 32 levels are omitted whole rather than partly serialized.
Plain error reports show scalar fields and scalar arrays after their existing
diagnostic details; use the envelope for nested objects.

## Read validation issues

A Landofile that fails validation produces a `LandofileValidationError`
envelope at exit `1` from `lando app:config`, `lando start`, and
`lando app:cache:refresh`, and the error carries every problem under
`error.issues`. Each issue is `{ path, message, suggestion?, source? }`. `path` is an
array of keys and indexes, never a dotted string, so a script indexes into
the parsed Landofile with it directly. `suggestion` is present when Lando has
a concrete fix, such as the closest allowed key for a typo:

```sh
lando app:config --format=json | jq ".error.issues[0]"
```

For a service that spells `image` as `imgae`, that first issue has `path`
`["services", "web", "imgae"]` and a `suggestion` naming `image`.

Three independent mistakes produce three issues in one run. Branch on
`error._tag`, then loop `error.issues`; do not parse `error.message`, which
is the human rendering of the same list. `lando app:config:lint
--format=json` reports the same issues as `violations` inside an `ok: true`
result with `valid: false`, which suits editors that want the list without a
failing exit. Lint and planning run one shared validation stage, so a
service-type finding such as `["services", "db", "environment", "PGPORT"]`
or a bad route hostname shows up with the same `path`, `message`,
`suggestion`, and `source` in both envelopes. `lando app:config` stops
earlier: it echoes the resolved Landofile and reports schema and
expression issues, not service-type or route findings.

A global config that fails validation in any layer (`config.yml`, a
`config.d/*.yml` drop-in, a `LANDO_CONFIG__*` or alias env var, or an
embedding host's `config` option) produces a `ConfigError` envelope at exit
`1` from every command that needs config, including `lando info`, `lando
start`, and the resolved `lando config` views. Lando resolves config once at
startup, so the error arrives before the command body runs. `lando config
validate` checks the same layers and fails with the same `ConfigError`.
`lando doctor` reports it inside its report under `result.globalConfig.error`
and lists config-dependent sections under `result.skipped`.

The error carries `error.path` (the `config.yml` location),
`error.remediation`, and `error.issues`. Each issue is
`{ path, message, suggestion, source }`. `suggestion` is the exact fix for
that value. `source` names the layer that supplied it:

| `source.layer` | Other fields | Fix shape |
| --- | --- | --- |
| `config-file` | `file`, `path` | `` Run `lando config unset <key>` or `lando config set <key> <value>`. `` |
| `config-drop-in` | `file`, `path` | `Edit <file>.` |
| `env` | `variable`, `path` | `Unset <variable> or set it to a valid value.` |
| `host` | `path` | `` Fix the `<key>` host config option. `` |

Landofile issues keep their `{ file, layer, path }` source. Branch on
`source.layer` to pick the fix; do not parse `error.message`, which prefixes
the first issue with `Invalid config file <path>` or `Invalid global
configuration (<sources>)` depending on which layers failed:

```sh
lando config --format=json | jq ".error | {path, issues, remediation}"
```

`message` on each issue says what the schema expected (`Expected a value
between 1 and 65535`, `Expected string | null`, `Expected one of lando, json,
plain, verbose.`) and never repeats the rejected input, so the envelope is
safe to log. An invalid `renderer` or `logLevel` in a config layer is reported
the same way; the command falls back to the default renderer and log level to
print it. `notify.commands` entries that match no canonical command id are
issues too, with the closest id in `suggestion`.

A `config.yml` with broken YAML syntax also fails with `ConfigError`, but
without `error.issues`, because there is no decoded tree to report paths into.
`error.message` is `Invalid YAML in config file <path>: <detail>`, where the
detail is a location such as `Unsupported YAML value at line 2, column 13` or
`Malformed YAML at line 1, column 1`, never the offending text. `--source raw`
fails with the same message.

`lando config set` and `unset` reject a candidate only when it introduces an
issue (a new path/message pair) or leaves the written key or a descendant
invalid. Rejections use `LandofileWriteValidationError` and `error.issues`,
without changing the file. Unchanged issues elsewhere don't block the write;
the successful envelope carries one `LANDO_CONFIG_PREEXISTING_ISSUES` warning
naming every remaining issue and its fix. `app:config` and `global:config`
set/unset use the same rule. `telemetry off` applies it to `telemetry.enabled`.
`config edit` still validates the whole edited file.

A problem in another layer does not block the write. Once the candidate file
is valid, the successful envelope carries a warning
with code `LANDO_CONFIG_OTHER_SOURCE_INVALID`, whose `message` and
`remediation` name the source and the fix. Unknown-key typos surface once per
command as warning code `LANDO_MESSAGE_WARN` from every command, `lando
config` and `lando doctor` included. Text mode prints warnings once.

The generated command reference lists every public command and documents the
universal `--format json` flag once in its machine-readable output section.
