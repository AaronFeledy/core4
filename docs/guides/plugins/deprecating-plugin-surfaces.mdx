# Deprecate plugin surfaces

Add a `deprecated` notice to a plugin manifest to tell callers when a surface
was deprecated and what to use instead. The `DeprecationNotice` shape is shared
by whole plugins and individual contributions; the fields below control its
message, severity, and removal schedule.

`nolint` on the fence: this is a plugin manifest, not a Landofile, so Landofile schema checks do not apply.

```yaml nolint
name: "@acme/lando-plugin-demo"
version: 0.1.0
api: 4
requires:
  "@lando/core": "^4.0.0"
deprecated:
  since: "4.1.0"
  removeIn: "5.0.0"
  severity: warn
  replacement: "@acme/lando-plugin-next"
  note: "Use the next plugin for this contribution."
```

Set `since` to the deprecation release and use `note` to explain the migration.
Check the `removeIn` rules below before choosing a removal release.

## Fields

| Field | Rule |
| --- | --- |
| `since` | Semver `major.minor.patch`. Required. |
| `note` | Required string. |
| `removeIn` | Optional semver `major.minor.patch`, strictly later than `since`. |
| `severity` | `info`, `warn`, or `error`. Default `warn`. `error` still records use, then fails. |
| `replacement` | Optional string. |
| `docsUrl` | Optional absolute `http:` or `https:` URL. |
| `ticket` | Optional string. |

These schema rules apply to app, plugin, and recipe authors in their own
version space. A later patch release is a valid removal schedule.

Lando's own surfaces follow a separate release gate policy: removal must target
a future major or minor release with patch `0`, and `removeIn` is required after
12 months. Follow that policy for your plugins when you want to give callers
the same migration window.

## Other surfaces

Contribution refs can carry the same notice:

```yaml
contributes:
  globalServices:
    - id: mailpit
      deprecated:
        since: "4.1.0"
        removeIn: "5.0.0"
        note: "Use the bundled mail service instead."
  serviceTypes:
    - id: legacy-php
      deprecated:
        since: "4.1.0"
        note: "Switch callers to php."
```

`globalServices`, `proxyServices`, `setup.flags`, the string-or-object contribution lists (`serviceTypes`, `renderers`), and the command descriptors under `commands` register through the same notice type. A command descriptor can also deprecate one alias: write the alias as an object with `name` and `deprecated` instead of a bare token.

## Verify

Keep the notice on `plugin.yaml` / `landoPlugin`. Schema decoding rejects a
`removeIn` that is the same release as `since` or earlier. Choose a later version
to resolve that error.
