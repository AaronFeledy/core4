# Scaffold a plugin

Run `lando meta:plugin:new` to create a plugin checkout. From the directory that
will contain it, use the example below to create `./demo` with the package name
`@acme/lando-plugin-demo` and contribution namespace `acme`. Choose an empty or
new destination; Lando rejects a non-empty directory and does not overwrite it.

```sh
lando meta:plugin:new @acme/lando-plugin-demo ./demo \
  --template bare --cspace acme \
  --description Demo-plugin --no-interactive
```

For a non-interactive run, supply every required value as shown above.
`--no-interactive` does not choose a package name for you. After the command
succeeds, check `demo/package.json` and `demo/src/index.ts` before adapting the
plugin. The template is built into the CLI, not read from files on disk.

## Pick a template

`--template` is one of: `service-type`, `provider`, `tooling-engine`, `template-engine`, `route-filter`, `config-translator`, `recipe`, `bare`.

`service-type`, `provider`, and `template-engine` seed `contributes` with a `<cspace>-example` id. The rest stay bare.

## What lands

| Path | Why it is there |
| --- | --- |
| `package.json` | `landoPlugin.api: 4`, `requires["@lando/core"]: "^4.0.0"`, scripts for `meta:plugin:test` / `build` / `link` |
| `plugin.yaml` | Same manifest, YAML form |
| `src/config.ts` | Effect Schema options (`enabled` defaults true) |
| `src/service.ts` | `Greeter` service with a static Effect layer and a traced method |
| `src/index.ts` | Decoded `PluginManifest`, config, and `definePlugin` wired to the service layer |
| `test/plugin.test.ts` | Manifest assertions and a greeting executed through Effect |
| `tsconfig.json`, `README.md` | Strict TypeScript and a one-page README |

The default destination, if you omit it, is the package basename with a leading `lando-plugin-` stripped to `plugin-`.

## Adapt the service

You get the same small service in every template. Replace its greeting with your plugin's behavior. Keep the `Context.Service` class, static `layer`, and `Greeter.of` construction. Use `Effect.fn` for traced service methods. When Lando loads your plugin, it supplies its own `@lando/sdk` and `effect` to the module, so the installed copy shares Lando's service tags and schemas; a local install of those two packages is for editor types only, while every other dependency must ship in the plugin's `node_modules`.

```ts
import { Context, Effect, Layer } from "effect";

export class Greeter extends Context.Service<Greeter, {
  readonly greet: (name: string) => Effect.Effect<string>;
}>()("@acme/lando-plugin-demo/Greeter") {
  static readonly layer = Layer.effect(this, Effect.gen(function* () {
    return Greeter.of({
      greet: Effect.fn("Greeter.greet")(function* (name: string) {
        return `Hello, ${name}!`;
      }),
    });
  }));
}
```

Your package name prefixes the service id. `src/index.ts` exports `plugin = definePlugin({ name: PLUGIN_NAME, manifest, layer: services })`, where `services` is `Greeter.layer`. The generated test provides that layer before calling `greet`. Your package pins Effect 4 and TypeScript 7.

## Use `dataName` for persisted defaults

`ServiceTypeInput` and `ServiceFeatureContext` carry both `appName` and optional
`dataName`. `appName` is the current Landofile name. `dataName` is the name this
folder's persisted data was first created under. When `dataName` is absent, it
matches `appName`.

Derive databases, generated passwords, bucket names, and other values that live
inside named volumes from `dataName` (or fall back to `appName` when it is
absent). Use `appName` for runtime identity that should follow a rename:
container-facing labels you surface only in the current process, diagnostics that
name the running app, and similar non-persisted strings.

`ServiceFeatureContext.serviceStoreName(role)` already names a store from the
folder's data identity. Do not rebuild that name from the current `appName`, or a
rename will point a new empty volume at services that still hold data under the
old name.

## Supply the service image

If your plugin contributes a service type, its `resolve` method chooses the base,
normalized configuration, and features. Every planned service needs an artifact:
the container image reference or build definition that Lando can pull or build.
You can let the app author supply `image:` or a Compose `build:` block. Core turns
those into an artifact even when your type requests no artifact-setting feature.
A versioned type's published image tag works the same way.

To supply an image from your plugin, request a feature whose `apply` callback calls
`ctx.setArtifact({ kind: "ref", ref: "nginx:alpine" })`. A feature's artifact wins
over the `image:` fallback; an authored Compose `build:` replaces it. Lando
`build.artifact` scripts only add steps and still need a base image or build.

If none of these supplies an artifact, planning fails before provider work with
`LandofileValidationError` at `services.<name>.type`. The message names the service,
type, and contributing plugin when known. Set `image:` or Compose `build:` in the
Landofile, or fix your type's requested features, then rerun `lando start`.

## Declare a feature's endpoints

Put listener declarations in `declareEndpoints`, not `apply`. Config lint runs
declarations without applying features, probing a provider, issuing certificates,
or building a plan. Keep the callback deterministic and resource-free. It receives
immutable service facts and the original decoded feature configuration, before
planning substitutes certificate or SSH delivery configuration.

Use an optional `validateEffective` callback for cross-field checks and explicit
service-field support. Lando calls it once for each prepared feature occurrence
after inheritance, before endpoint declaration and app-plan cache lookup. It
receives the same immutable facts and original decoded feature configuration as
declaration, not an application draft. Do not run `apply`, inspect images, resolve
secrets, or acquire filesystem, network, or provider resources to validate.

On success, return a `ServiceFeatureValidationResult` with `handledServiceFields`
for the fields the feature actually consumes, currently `webroot` and
`consolePort`. A property with the same name in feature configuration is not a
support declaration. Claim `webroot` only when this feature really uses the root
for server configuration or supported context; conditional mount-dependent
features must not claim it when that context is absent.

Reject expected invalid input through `ServiceFeatureError.issues`. Paths are
relative to the service configuration, such as `["port"]`; include a useful
`suggestion`. Core prefixes the service path and preserves structured findings
for lint and machine output. Do not encode a path into prose or report an
internal feature-config field as an authored Landofile field unless they really
correspond. Validation still runs when the author supplies `endpoints: []`.

```ts
import { Effect } from "effect";
import type { ServiceFeatureDefinition } from "@lando/sdk/services";

export const webFeature: ServiceFeatureDefinition = {
  id: "acme.web",
  priority: 600,
  declareEndpoints: () => Effect.succeed([
    { _tag: "internal", name: "browser", protocol: "http", port: 8080 },
  ]),
  apply: (ctx) => Effect.sync(() => {
    ctx.setCommand(["my-server", "--port", "8080"]);
  }),
};
```

For an app feature, return endpoint lists keyed by selected service name. The same
`activatedBy` and `selectors` logic chooses services for declarations and application.
Declaration contexts have no mutation methods; application contexts cannot add endpoints.

If an app feature needs a fact established by a service type, return it in
`ServiceTypeResolution.metadata`. Both declaration and application expose
that record as the optional, read-only `AppFeatureServiceView.resolutionMetadata`.
Use a namespaced key owned by your plugin and validate its value before relying
on it. These are service-type-produced facts, not authored `x-*` fields,
provider observations, or the final artifact after mutable feature application.
Keep private implementation keys private rather than making them Landofile
options. A missing fact is not permission to reconstruct it from a later image
reference that may have changed.

```ts
import { Effect } from "effect";
import type { AppFeatureDefinition } from "@lando/sdk/services";

export const adminListeners: AppFeatureDefinition = {
  id: "acme.admin-listeners",
  priority: 700,
  selectors: { names: ["web"] },
  declareEndpoints: (ctx) => Effect.succeed(Object.fromEntries(
    ctx.selected.map((service) => [service.serviceName, [
      { _tag: "internal", name: "admin", protocol: "http", port: 9000 },
    ]]),
  )),
  apply: (ctx) => Effect.sync(() => {
    ctx.forEachSelected((service) => service.addEnv("ADMIN_PORT", "9000"));
  }),
};
```

Declarations compose in stable feature-priority order, service features before app
features. Authored `endpoints:` overrides the contributions, including an empty
list. `ports:` adds publication facets without turning a TCP-only listener into HTTP.

## Renderer plugins

`@lando/renderer-lando` is the bundled example. It declares:

```yaml
contributes:
  renderers:
    - lando
```

That key is `contributes.renderers`. Core still owns plain, JSON, and verbose fallbacks.

## Certificate authority plugins

`@lando/ca-mkcert` is the bundled example. Declare yours under
`contributes.certificateAuthorities` and implement the four members of
`CertificateAuthority` from `@lando/sdk/services`:

| Member | What it does |
| --- | --- |
| `id` | The id from your manifest. |
| `setup(options)` | Installs what you need and creates your root. After it succeeds, `root` must work. Honor `skipTrustInstall` by leaving the host trust store alone. |
| `root` | Yields `{ certificate }`, the PEM of the root that signs your leaves. Fail with a `CaError` and a remediation when setup hasn't run or there is no root yet. |
| `issueCert(spec)` | Issues a leaf for `spec.cn` and `spec.sans` and returns PEM values: `{ certificate, privateKey, root: { certificate } }`, with `privateKey` wrapped in `Redacted`. |

Return values, not file paths, and keep no copy of what you issue. Lando and the
router store their own copies and decide when to ask again, so `issueCert` issues
fresh material on every call and doesn't need to remember earlier requests. If
your tool has to write files, use a private temporary directory and remove it
when issuance completes, fails, or is interrupted.

Keep `root` and `issueCert` in agreement. Lando checks every pair you return
against the root that came with it, and refuses to use one that doesn't cover the
requested names, doesn't match its key, is outside its validity window, or isn't
signed by that root. On later starts it checks the stored pair against `root`, so
an authority that reports one root and signs with another gets asked for a new
certificate on every start.

Run `runCaContract` from `@lando/sdk/test` against your authority in your own
tests. It checks setup, `root`, the shape of what `issueCert` returns, and that
the issued pair verifies against both the root it came with and `root` read
afterwards. To make the same judgment yourself, call `certificatePairIsCurrent`
from `@lando/sdk/certificates` with the requested names, the current root, and
`LEAF_RENEWAL_MARGIN_MS` as `renewalMarginMs`. That constant is the shared 30-day
policy for service and router leaves; the verifier caps it at one third of the
leaf's lifetime. The Traefik router reads `root` once per HTTPS route apply,
including warm reuse, so keep that read free of setup and issuance work. It
repairs its saved issuer independently of valid leaves and reloads served-pair
replacements itself. HTTP-only publication and withdrawal need no authority.
These are apply-time checks, not background renewal.

For tests that only need certificate-shaped
input, `@lando/sdk/test` exports `TEST_CERTIFICATES`, a set of throwaway PEM
fixtures you must never trust, and `makeTestCertificateAuthority`, which returns
one fixed leaf whatever names you request.

## Declare a router's shared services

Declare your router under `contributes.routerServices`. If it needs services in
the global app, list their contribution ids in `requires.globalServices`. The
router id and its service ids can differ. For example, this entry declares a
router named `acme-router` that needs a global service named `acme-gateway`:

```yaml
contributes:
  routerServices:
    - id: acme-router
      module: ./src/router.ts
      requires:
        globalServices:
          - acme-gateway
      defaultFor:
        platform:
          - linux
```

Contribute `acme-gateway` under `globalServices` too, or depend on a plugin that
contributes it. Omit `requires` or use an empty `globalServices` list when the
router works without the global app. The bundled Traefik router declares
`requires.globalServices: [traefik]`.

Users select an installed router with `defaultRouterService` in `config.yml`.
Without that choice, Lando selects one matching `defaultFor.platform` for the
host family, then a sole installed router. When no router can be chosen, the
plan records none and Lando keeps working without one: `lando info`, `lando
logs`, `lando exec`, `lando stop`, `lando destroy`, and apps with no routes all
run. Only work that needs the router fails, and it fails before Lando changes
anything. `lando start`, `lando restart`, and `lando rebuild` on an app with
routes report why no router was selected and how to fix it before running hooks,
building images, or stopping a service, so a running app stays running. The same
goes for `lando global:start`, `global:restart`, and `global:rebuild` when the
global services they start have routes. The router step of `lando setup` reports
the same reason.
A `defaultRouterService` that names an uninstalled router reads `Router
service <id> is not installed` when other routers are installed; with none
installed Lando says no router is selected, and an ambiguous choice says so.
For a mistyped id, set `defaultRouterService` to an installed router id or
remove the setting, then re-run the command.

Teardown still cleans up routes. With no router selected, `lando stop` on an
idle runtime, `lando destroy`, `lando poweroff`, and `lando global:stop` or
`global:destroy` ask every installed router to remove the routes, so your
router's `removeRoutes` can run even when it isn't the selected one. Lando
builds your router for that only when a withdrawal runs, never at startup, so
it must be able to remove routes while its proxy is stopped. If every installed
router removes them, teardown finishes without a warning. Otherwise the routes
step reads `Routes not withdrawn`, Lando warns and carries on: the warning says
`no router is available` when none is installed, or `an installed router could
not remove them` with that router's error and fix.
Planning reads these manifest declarations without constructing your router or
running its module.

Lando records the selection in the app plan and invalidates cached plans when
it changes. At start, Lando ensures the selected router's declared services
alongside any services required by app features. Disabled routing and apps
without routes add no router requirements; feature requirements still apply.
Check the planned `router.id` and `requires.globalServices` when testing your
plugin, including a start with only its declared global services available.

## Contribute commands

Describe each command under `contributes.commands` in the manifest. Every entry
is an object with an `id` and a `summary`; `hidden`, `aliases`, `topLevelAlias`,
`mcpAllowed`, and `deprecated` are optional. The bundled `@lando/sql` plugin is
the shape to copy. This entry also gives `db:export` the shortcut `db:dump`:

```yaml
contributes:
  commands:
    - id: db:export
      summary: Export a database dump from a service.
      aliases: [db:dump]
```

Lando reads help, routing, aliases, and MCP eligibility from this manifest
without running any plugin code, so the summary you write here is the one
`lando help` shows. The command module may omit its own `summary`; if it sets
one, it must match the manifest or the command fails validation when it runs.
`aliases` take the colon form. `topLevelAlias: true` also registers the id
without its first namespace segment (`db:export` as `export`); give it a token or
a list of tokens to choose the bare names yourself. An alias that collides with
a built-in command, a core help topic, a reserved word, or the current app's
tooling is dropped while the id keeps working, and `lando help --format=json`
reports the conflict in `result.pluginMetadata.diagnostics`.

Then give `definePlugin` a `commands` map from the same ids to lazy loaders
that resolve an `ExecutableCommandSpec` from `@lando/sdk/plugins`:

```ts
export const plugin = definePlugin({
  name: manifest.name,
  manifest,
  commands: new Map([
    ["db:export", () => import("./commands/export.ts").then((module) => module.spec)],
  ]),
});
```

Once the plugin is installed or linked, its commands appear in `lando help --all`
next to the built-ins, `lando help <namespace>` (here, `lando help db`) lists
them under the manifest `description`, and the root `lando --help` adds that
topic to its MORE section. In `lando help --format=json`, each plugin row carries
`source: "plugin"` plus the `plugin` name and its `provenance`. Lando loads the
module only when someone runs the command or asks for its `--help`, so a module
that fails to load still appears in listings; the load error surfaces at that
point, naming the problem.

`lando <command> --help` and `lando help <command> --format=json` both list the
flags and positional arguments the module declares. JSON help puts them under
`result.target.input`, with each input's type, description, choices, and whether
it's required.

### Accept `-` for stdin or stdout

A command that moves a data payload, like a dump, can let users pass `-` to use
their shell's stdin or stdout. Declare it on the positional argument:

```ts
args: {
  file: { type: "string", description: "Destination dump file.", stdio: "stdout" },
},
```

When someone runs the command with `-` for that argument, the CLI hands your
`run` a byte stream in `input.stdio`: `input.stdio.stdout` writes bytes to stdout
exactly as given, and `input.stdio.stdin` is a stream you can read once. Write
nothing else to stdout. Lando refuses `-` before your code runs when that stream
is a terminal, and with `--format=json` it writes the result envelope to stderr
so stdout stays yours. MCP rejects `-` for the argument, and event invocations
get no stream, so when `input.stdio` lacks the stream you asked for, fail with
`CommandStdioError` (reason `unavailable`) and suggest a file path. Help appends
"Use - to write to stdout." (or "read from stdin") to the argument's
description, so leave it out of your own. Each stream can be claimed by one
argument, which can't be `multiple`.
