# Put lando on PATH and run setup

The [POSIX](./posix-installer.mdx) and [Windows](./windows-installer.mdx) installers do this for you. Use this page when you downloaded a binary from a [GitHub release](./github-releases.mdx) by hand.

After you download and verify the platform-qualified binary, put it on PATH as `lando`. These commands preserve an existing executable in a unique backup before installing. For Linux x64, run these commands from the download directory. On another Linux or macOS architecture, replace `lando-linux-x64` with the asset you downloaded before running them:

```sh
(
  set -eu
  chmod +x lando-linux-x64
  mkdir -p "$HOME/.local/bin"
  if [ -e "$HOME/.local/bin/lando" ] || [ -L "$HOME/.local/bin/lando" ]; then
    landoBackup=$(mktemp "$HOME/.local/bin/lando.bak.XXXXXX")
    mv "$HOME/.local/bin/lando" "$landoBackup"
  fi
  mv -n lando-linux-x64 "$HOME/.local/bin/lando"
  test ! -e lando-linux-x64
) &&
export PATH="$HOME/.local/bin:$PATH" &&
command -v lando &&
lando --version
```

Replace `lando-linux-x64` with the asset you downloaded on Linux or macOS. Add `$HOME/.local/bin` to your shell profile's PATH to keep `lando` available in new terminals.

On Windows, name the downloaded asset `lando.exe`, then move it into a directory on PATH. The commands below back up an existing `lando.exe` in that directory before installing the new binary. In PowerShell from the download directory, use the following commands. On ARM64 Windows, replace `lando-windows-x64.exe` with `lando-windows-arm64.exe` first:

```powershell
Rename-Item .\lando-windows-x64.exe lando.exe
$landoInstallDir = "$env:LOCALAPPDATA\Programs\Lando"
New-Item -ItemType Directory -Force $landoInstallDir | Out-Null
$landoExe = Join-Path $landoInstallDir 'lando.exe'
if (Test-Path -LiteralPath $landoExe) {
  Move-Item -LiteralPath $landoExe -Destination "$landoExe.bak.$(Get-Date -Format yyyyMMddHHmmss)"
}
Move-Item .\lando.exe $landoExe
$env:PATH = "$env:LOCALAPPDATA\Programs\Lando;$env:PATH"
Get-Command lando | Select-Object -ExpandProperty Source
lando --version
```

Use `lando-windows-arm64.exe` on ARM64 Windows. `Get-Command` should point to the `lando.exe` you just moved. If it points to an older installation, correct your PATH or remove an older `lando` alias from your PowerShell profile before continuing. To keep this directory first on PATH in new PowerShell sessions, append the PATH entry to your profile. These commands create the profile if it is missing and preserve any existing content:

```powershell
New-Item -ItemType Directory -Force -Path (Split-Path -Parent $PROFILE) | Out-Null
if (-not (Test-Path -LiteralPath $PROFILE)) { New-Item -ItemType File -Path $PROFILE | Out-Null }
$landoProfilePath = @'
$landoBin = Join-Path $env:LOCALAPPDATA 'Programs\Lando'
if (($env:PATH -split [IO.Path]::PathSeparator)[0] -ne $landoBin) {
  $env:PATH = $landoBin + [IO.Path]::PathSeparator + $env:PATH
}
'@
Add-Content -LiteralPath $PROFILE -Value $landoProfilePath
```

Run these once for each profile where you want Lando. The current session already has the PATH entry from the earlier command.

Run setup in your terminal and follow the prompts. Choose the recommended Lando-managed runtime on supported hosts; Docker is not required. On an Intel Mac (`darwin-x64`), install and start Docker Desktop first, then choose Docker when setup asks. Setup does not install Docker for you:

```sh
lando setup
lando doctor
```

The default provider is `lando` (managed Podman). Check `lando doctor` for provider and host health. If setup reports a missing host prerequisite, follow its remediation and rerun setup. If the managed runtime still cannot install and you have working system Docker:

```sh
lando setup --provider=docker
```

`--yes` consents to confirmation and privileged host changes. It does not switch providers. See [Pick a container provider](../setup/provider-selection.mdx).

## Preview what setup changes

`--dry-run` shows the host changes setup would make, the exact commands it would run, and whether sudo would need your password. It changes nothing: it never prompts, downloads nothing, and writes no configuration:

```sh
lando setup --dry-run
```

Pass the flags you plan to use, such as `lando setup --dry-run --yes --enable-linger`, to see what that run would do. With `--format=json`, `result.changes` lists each change with the `approval` saying what a real run with those flags in the same terminal would do with it: `approved` (applies it without asking), `will-ask` (asks you), `will-skip` (skips a recommended change and warns), `blocked` (stops before changing anything, because a required change has no approval), or `not-offered` (cannot offer it, such as a change only a terminal run without `--yes` asks about). `approvedBy` lists the flags that approve the change in a run that cannot ask, such as `--yes` or `--enable-linger`; it is empty for a change only a terminal can approve. `result.elevation.state` says how a real run would get administrator access, for example `will-prompt` in a terminal or `required` when the run cannot ask.

The preview lists the provider's changes and, on Linux, the router's port helper. `--format=json` shows the helper's exact install script; the text view summarizes the script by its size and digest. Trusting the local CA is still decided when setup reaches it, so the preview names it in `result.notices` instead.

## When setup needs administrator access

Run `lando setup` as yourself, never with `sudo`. A few steps change the system, and setup asks for administrator access itself before the first one runs:

- installing the `uidmap` package and adding subordinate user and group IDs for your account on Linux
- letting your systemd user manager delegate cgroup controllers, and enabling lingering when no user manager runs for you
- trusting Lando's local certificate authority in the system trust store
- installing the helper that serves ports 80 and 443 on Linux

Before setup changes anything, it plans the provider's and the router's host changes and asks you once to approve them, listing each one. Lingering gets its own question (see below). Then setup tells you what it needs, and `sudo` asks for your password with its own prompt. It asks once per run, however many steps change the system: setup keeps sudo's credentials fresh while it works (a long runtime download does not outlast them) and tells sudo to forget them when it finishes, unless you already had them from your own `sudo -v`. Progress keeps rendering after the prompt. Lando never asks for or sees the password. If you run `sudo lando ...` against your own Lando files, Lando refuses and asks you to rerun without `sudo`, because files it wrote as root would break your later runs.

Without a terminal (`--no-interactive`, a CI job, or an agent), setup cannot prompt. Before it changes anything, it stops with `PrivilegeCredentialsRequiredError` unless one of these is true:

- you ran `sudo -v` in the same terminal shortly before, so sudo still has your credentials
- `SUDO_ASKPASS` names a program that prints the password
- sudo needs no password for your user, as on hosted CI runners

Trusting the local CA runs mkcert, which asks sudo itself, so without a terminal that step needs passwordless sudo (or `--skip-install-ca` and trusting the CA yourself). `SUDO_ASKPASS` and a `sudo -v` from another shell do not reach it.

```sh
sudo -v
lando setup --yes --no-interactive
```

`--no-interactive` on its own approves no privileged change; add `--yes` for that. Enabling lingering keeps a systemd user manager running after you log out and after a reboot, so `--yes` does not approve it either. Setup asks about it separately in a terminal; in automation, pass `--enable-linger`. Without it, setup skips lingering and says how to enable it later. If your session also has no `/run/user/<uid>` directory, as on a host you reach only through `su` or a service account, the managed runtime cannot start until lingering is enabled, and setup stops with that remediation.

Setup writes the PATH block to your shell profile as you, never as root. It picks `LANDO_SHELL_PROFILE` when set, otherwise the profile for your `$SHELL`. If it cannot write that file, setup fails with `ShellProfileIntegrationError` naming the path, and leaves the file alone.

`lando shellenv` prints a profile snippet for the current shell. Use `--shell=powershell` in PowerShell or `--shell=posix` in a POSIX shell. A manually installed compiled binary adds its own directory when there is no install record. An installer-managed copy uses the verified directory from its install record. The profile commands above keep your chosen directory first on PATH.
