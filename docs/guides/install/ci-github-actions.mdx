# Run Lando in GitHub Actions

> **Alpha status:** There is no live `get.lando.dev` installer and no `releases/latest` v4 binary. Do not curl `https://github.com/lando/core/releases/latest/download/lando-linux-x64`. That is not this product. See [Alpha install and bug reports](../../alpha-install-and-bug-reports.md).

CI can run Lando on `ubuntu-latest` if you first put the Linux x64 `v4.0.0-dev.N` binary on PATH. Pin a specific prerelease tag from [AaronFeledy/core4 releases](https://github.com/AaronFeledy/core4/releases). Download the `lando-linux-x64` asset and `SHA256SUMS`, verify the checksum, and [put the binary on PATH as `lando`](./path-and-setup.mdx). Run the following from the checked-out app directory containing its Landofile:

```sh
lando --version
lando setup --yes --no-interactive
lando start --no-interactive
lando app:config --format=json
lando poweroff -y
```

`--yes` consents. It does not pick a provider. The default provider is `lando` (managed Podman). Pin `--provider=lando` only if you want that explicit. If managed setup fails and the runner already has system Docker:

```sh
lando setup --provider=docker --yes --no-interactive
```

`--no-interactive` fails instead of waiting for a TTY when required input is missing. `poweroff` does not prompt; it accepts `-y` but does not require it. Provider rules live in [Pick a container provider](../setup/provider-selection.mdx).

Do not scrape human text. Assert on JSON (`ok: true`) from `--format=json`.

The committed runtime-bundle manifest points to published assets. Host prerequisites can still block setup; follow its remediation before starting the app. A successful configuration read verifies the Landofile, not service readiness.

For a minimal Node app, save this as `.lando.yml` in the checked-out app directory before running the commands above:

```yaml
name: ci-github-actions-demo
services:
  app:
    type: "node:22"
    primary: true
```
