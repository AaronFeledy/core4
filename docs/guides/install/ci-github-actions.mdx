# Run Lando in GitHub Actions

CI can run Lando on `ubuntu-latest` once the Linux x64 binary is on PATH. The shortest path is the installer without its setup prompt:

```sh
curl -fsSL https://get.lando.dev/install.sh | LANDO_INSTALL_SKIP_SETUP=1 sh
eval "$("$HOME/.local/share/lando/bin/lando" shellenv)"
```

To pin an exact version instead, pick a release tag from [AaronFeledy/core4 releases](https://github.com/AaronFeledy/core4/releases), download its `lando-linux-x64` asset and `SHA256SUMS`, verify the checksum, and [put the binary on PATH as `lando`](./path-and-setup.mdx). Then run the following from the checked-out app directory containing its Landofile:

```sh
lando --version
lando setup --yes --no-interactive
lando start
lando app:config --format=json
lando poweroff -y
```

`--yes` consents. It does not pick a provider. The default provider is `lando` (managed Podman). Pin `--provider=lando` only if you want that explicit. If managed setup fails and the runner already has system Docker:

```sh
lando setup --provider=docker --yes --no-interactive
```

`--no-interactive` makes setup fail instead of waiting for a TTY when required input is missing. Setup runs privileged steps through `sudo` and cannot type a password in CI. Hosted Ubuntu runners have passwordless `sudo`, so it works there. On a self-hosted runner, give the job passwordless `sudo` or provision the prerequisites first; otherwise Lando's own elevated steps stop with `PrivilegeCredentialsRequiredError` before they change anything. `SUDO_ASKPASS` can satisfy every one of them, including trusting the local CA. A runner with no systemd user manager runs containers without `deploy.resources` limits unless you add `--enable-linger`, which keeps lingering enabled for the runner account. When the runner's session has neither `/run/user/<uid>` nor `XDG_RUNTIME_DIR`, as when the job runs under `su` or a service account, the managed runtime cannot start without lingering: `--enable-linger` is required, and without it setup stops with `HostChangeConsentRequiredError` before it changes anything. `start` and `poweroff` do not prompt; `poweroff` accepts `-y` but does not require it. `poweroff` stops each app at its recorded root and keeps the global app and managed runtime running when any app fails, so the job reports the failing app instead of tearing down the runtime first. Provider rules live in [Pick a container provider](../setup/provider-selection.mdx).

To see what setup would change on the runner before it changes anything, run `lando setup --dry-run --yes --no-interactive --format=json` first. Each entry in `result.changes` is a host change with its exact commands and what a run with these flags does with it; an entry that is `blocked` or `will-skip` lists in `approvedBy` the flags (such as `--enable-linger`) that would approve it.

Do not scrape human text. Assert on JSON (`ok: true`) from `--format=json`.

The committed runtime-bundle manifest points to published assets. Host prerequisites can still block setup; follow its remediation before starting the app. A successful configuration read verifies the Landofile, not service readiness.

For a minimal Node app, save this as `.lando.yml` in the checked-out app directory before running the commands above:

```yaml
name: ci-github-actions-demo
services:
  app:
    type: "node:22"
    primary: true
```
