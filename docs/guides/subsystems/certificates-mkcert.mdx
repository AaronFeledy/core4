## Author service leaf certificates

A service's own leaf TLS certificate is configured with `certs:`. It is a separate surface from
`security.ca:`, which adds trusted certificate authorities; a service may declare both.

Issue a certificate from the active certificate authority:

```yaml
services:
  appserver:
    certs: true
```

Disable issuance for a service:

```yaml
services:
  appserver:
    certs: false
```

Supply a custom certificate path:

```yaml
services:
  appserver:
    certs: ./certs/appserver.crt
```

Supply an explicit certificate and key pair:

```yaml
services:
  appserver:
    certs:
      cert: ./certs/appserver.crt
      key: ./certs/appserver.key
```

The object form requires both `cert` and `key`. Any other shape — a number, a list of paths, an
incomplete object, or an unknown field beside `cert` and `key` — fails validation with a
`services.<name>.certs` correction before planning.

## Service certificate environment and SAN coverage

Planning a `type: lando` service composes the `lando.certs` feature, which mounts the resolved
certificate material read-only inside the service and publishes its in-container paths. The
[`lando.boot` scaffold](../services/lando-boot-scaffold.mdx) emits the provider-neutral,
artifact-phase intent for the shared `/etc/lando/certs` directory; `lando.certs` does not own that
directory and only mounts leaf files beneath it:

```text
LANDO_SERVICE_CERT=/etc/lando/certs/leaf/<service>.crt
LANDO_SERVICE_KEY=/etc/lando/certs/leaf/<service>.key
```

`LANDO_SERVICE_KEY` is set only when key material is available, so a custom certificate supplied as
a bare path publishes `LANDO_SERVICE_CERT` alone. `certs: false` — and any service that does not
author `certs` — leaves both variables unset and adds no mounts. Services on the `l337` base never
compose `lando.certs`, so `certs:` on a raw Compose service is inert.

With `certs: true` the planner asks the active certificate authority to issue a leaf for the
service's internal alias. The certificate's subject alternative names cover, in order:

- the service name (`<service>`)
- the internal alias (`<service>.<app>.internal`)
- every entry in the service's `hostnames:`
- every proxied hostname from the service's `routes:` and from the top-level `proxy:` block
- `localhost` and `127.0.0.1`

Custom certificate and key paths are resolved against the app root, must stay inside it, and must be
readable; an escaping or missing path fails with a `services.<name>.certs` correction before any
container work starts. Requesting `certs: true` with no certificate authority available fails with
remediation naming `lando setup`.

## Select the active certificate authority

The CLI combines bundled, system, user, and app plugin contributions into one selection graph. The
bundled `@lando/ca-mkcert` contribution declares itself the default on macOS, Linux, and Windows, so
it is selected when no higher selection tier replaces it. `lando setup` and `certs: true` resolve
through that same selected authority.

Library runtimes start without bundled or discovered plugins. An embedding host may contribute an
authority through `plugins.layers` or `plugins.manifests`, or opt into selected discovery sources.
To replace mkcert with another platform default, enable the replacement and disable
`@lando/ca-mkcert` in the runtime plugin policy; `disable` is applied after all sources are merged.

If no authority remains, setup reports that an authority plugin must be enabled or installed, and
`certs: true` fails before container work with the same remediation. If multiple authorities match
the platform default, selection fails with the candidate plugin names and asks the operator to
disable all but one instead of choosing silently.

## Install the certificate authority

`lando setup` provisions the pinned mkcert binary through `Downloader`, so corporate `network.ca`
and `network.proxy` settings apply to that fetch, then installs the local root CA into the host
trust stores. When the unelevated install fails on a host that needs elevation, the install is
retried through `PrivilegeService` with the same `CAROOT`, and a still-failing install reports the
underlying mkcert output plus how to retry or skip.

Run `lando setup --skip-install-ca` to provision mkcert without writing to any host trust store;
embedding hosts pass `skipTrustInstall: true` to `CertificateAuthority.setup` for the same effect.
Issuing a certificate before setup fails with remediation naming `lando setup`, and hosts with no
published mkcert build fail with remediation instead of a partial install.

Installing the root CA into the host trust store is also what makes browsers trust the
[Traefik reverse proxy's HTTPS certificates](./proxy-traefik.mdx): without that host trust step, a
browser shows a certificate warning even though the proxy is issuing valid certificates from the
same authority.
