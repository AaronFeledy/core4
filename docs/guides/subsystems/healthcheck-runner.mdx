# How the healthcheck runner gates readiness

`HealthcheckRunner` gates startup readiness by probing a service before its
post-start subscribers run. This contributor reference describes accepted input,
probe timing, and failure retention. For app configuration, use
[Make start wait for your app](../services/wait-for-your-app.mdx).

Service `healthcheck:` configures native ongoing container health; `readiness:` configures the engine's lifecycle gate. Both accept `false`, a non-empty shell string, literal argv, or a command/timing object. Compose `CMD`, `CMD-SHELL`, and `NONE` markers only mean something in an object's `test` list. The object accepts `kind`, `command`, `intervalSeconds`, `timeoutSeconds`, `retries`, and `startPeriodSeconds`; Compose spellings `test`, `disable`, `interval`, `timeout`, and `start_period` also decode. The schema accepts HTTP/TCP intent, but the shipped runner is command-only. `start_interval` / `startInterval` are preserved duration strings for extensions, not a separate lifecycle scheduler.

Execution metadata `target: service | host` and `user: ContainerUser` survives either dialect without selecting one. Native `healthcheck` rejects host targets and any explicit probe user with `HealthcheckTargetUnsupportedError` before action, with remediation to move the probe to `readiness`. Explicit `target: service` is a native no-op. Readiness accepts a service user without changing the main process identity; host readiness cannot select a container user.

Literal `false` reads back as `false` in `lando app:config`. Disabled objects (`disable: true`, `test: [NONE]`, `kind: none`) retain normalized settings and execution metadata as `kind: none` when any remain; an otherwise empty disabled object becomes `false`. Executable fields are dropped, but malformed commands, retries, or durations still fail validation, and disabling cannot hide unsupported native execution metadata. Lando fields take precedence over Compose fields, so `command:` wins over `disable: true`. Only literal `false` replaces the lower probe wholesale during composition; disabled objects merge as ordinary mappings and inherited siblings remain subject to validation.

```yaml
services:
  db:
    type: mysql
    healthcheck: false
    readiness: mysqladmin ping
  cache:
    type: redis
    healthcheck: redis-cli ping
    readiness: false
```

The engine owns readiness attempt execution. Service execution uses the selected `RuntimeProvider.exec`: strings use `sh -c`, argv stays exact, and an explicit `user` selects only the probe's container identity. Host execution uses `ShellRunner` with Bun Shell for strings or `ProcessRunner` for exact argv, with the CLI machine's current identity and the app root as cwd. It is not the provider VM or a sandbox. `kind: none` skips the command gate, not process-running or completion supervision. Authored HTTP/TCP kinds fail planning with `LandofileValidationError` before provider actions; use a command probe instead.

The runner probes immediately, including during `startPeriodSeconds`. Failed probes during that period do not consume retries; probes run at one-second intervals or `intervalSeconds` when shorter. The first passing probe returns immediately. After the start period, the runner permits `retries` attempts (at least one) at `intervalSeconds`, with `timeoutSeconds` per attempt.

Start, restart, rebuild, and global-service start wait for effective readiness before post-start subscribers run. The barrier, `service_healthy` dependencies, and app-build gates use the same policy. Disabling readiness does not relax a healthy dependency: its target must still have enabled command readiness, or planning fails. Language runtimes add no default checks; authors provide `readiness:` when needed.

## Separate startup readiness from ongoing health

Service-type contributors use `ServiceFeatureContext.setHealthcheck` for ongoing native health and may use `setReadiness` for a stronger startup probe. Both accept `HealthcheckPlan`. `effectiveReadiness(service)` selects `readiness` when present, otherwise `healthcheck`; only `healthcheck` becomes the provider's periodic native check. MongoDB uses this split to run a protocol ping during startup without launching a MongoDB shell every ten seconds afterwards.

An authored `healthcheck:` overrides only native health; authored `readiness:` overrides only lifecycle readiness. Omitted readiness preserves a contributed default, otherwise it falls back to effective native health. `readiness: false` stores explicit `kind: none` to block fallback. `healthcheck: false` disables native health, including inherited image checks, without disabling explicit or contributed readiness. `ServicePlan.readinessSource` records `authored` or `contributed`; fallback and historical unknown provenance are derived during inspection.

The engine supplies an invocation-scoped `executeReadinessAttempt` delegate to provider apply for both service and host attempts, bound to that plan, cancellation signal, and selected provider execution. Providers retain resource ownership, container creation, the start/dependency graph, and partial-apply persistence. Direct apply without the delegate can execute service readiness but refuses host readiness before mutation. Moving the full start scheduler into the engine is deferred until provider-neutral lifecycle primitives and partial-apply ownership are designed; the delegate is not a second scheduler.

Authored `readiness.target` lowers to `HealthcheckPlan.executionTarget`; it is distinct from the persisted optional listener `HealthcheckPlan.target: EndpointRef`. Host readiness with a user, listener, or no own authored/composed command fails planning with `HealthcheckTargetUnsupportedError`. Host probes inherit neither a type's command nor its container identity/listener. Plan refresh (`lando app:cache:refresh --format=json`) exercises validation without provider mutation.

Host probes use the general SDK private capture mode: no command/output events or live output sink, unchanged stdin and exit semantics, and a hard 1 MiB limit per stdout/stderr channel. Capture plus inherited output is invalid before child creation. Overflow uses the runner's tagged error and terminates/reaps the child without exposing raw captured causes. Host probe commands/output never enter public failure evidence. Host readiness must not depend on app routes or dependents behind its own gate; use an independently produced host prerequisite.

Lando 3 API-4 and raw-service conversion maps every supported top-level `healthcheck` form, including strings, argv, objects, and `false`, to `readiness`. Nested Compose healthchecks remain native. Legacy catalog-service input that ignored healthcheck still ignores it and emits a diagnostic. A converted container user never means host impersonation.

A type-owned command probe can carry `target: EndpointRef` for one of its declared listeners. Port and transport identify the listener. The shared compiler supplies `LANDO_PROBE_HOST` and `LANDO_PROBE_PORT` from managed network intent: the service alias on a private bridge, or its canonical qualified alias on a shared-only network. It never discovers an interface address or falls back to loopback. Invalid listeners, unavailable topology, and reserved or overridden service DNS fail planning before provider action. Custom untargeted commands receive no injected target.

Direct runner calls with a targeted probe must pass the full app plan as the fourth argument: `runner.run(probe, appPlan.id, serviceName, appPlan)`. Provider create requests, Compose output, dependency gates, and the engine runner share the compiler, so their target and command cannot drift independently.

## Distinguish inspection from a successful gate

`ServiceInfo.health` describes native monitoring and provider-observed health. Explicit native `none` is `not-monitored`; missing evidence is neutral `unknown`. `ServiceInfo.readiness.state` is `disabled`, `not-configured`, or `not-observed`; source is `authored`, `contributed`, `healthcheck`, `unknown`, or `none`. Safe metadata includes execution target, identity source, listener, timing, command presence, and configuration pointer, never raw commands. Info performs no probes, extra inspection calls, or durable writes to invent readiness evidence.

Start's `ready` result remains a real observed gate success for that invocation. Info does not retain or imply that proof. Durable last-readiness proof is deferred: it needs start-generation and probe identity, provenance, interruption/failure invalidation, and orphan handling before it can be truthful.

An unsupervised exited service fails with `ServiceNotReadyError`; applied user-app resources stay available for diagnosis. `restart: always` or `unless-stopped` permits an exit or observed restart to yield a warning and `restarting`; `on-failure` permits that only with a non-zero exit code. Exhausted startup probes remain fatal for every service. A `service_completed_successfully` dependency target skips probes and must exit 0 regardless of restart policy. Successful rows report `ready`, `running` without a check, or `completed` for verified jobs. Restart policies never relax dependency gates during provider apply.

Provider inspection failures use `inspect-failed` and prescribe `lando doctor`, never a successful restart warning. Service diagnosis uses `lando logs -s <service>` and `lando start` for user apps, or `lando global:logs -s <service>` and `lando global:start` for global services. Scratch acquisition runs the same checks, but failure or interruption follows scratch cleanup and `--keep-on-failure`, not user-app retention.

Non-instant readiness waits publish task-tree progress. Interruption at any phase, the barrier included, cancels in-flight probes and keeps the applied app, routes, volumes, sessions, journal, and managed scopes while the interruption propagates; the next `lando start` converges on them.

This is not a user how-to. To make start wait for your app, see [Make start wait for your app](../services/wait-for-your-app.mdx). For a running app, use [everyday commands](../cli/everyday-commands.mdx) and [lando doctor](./doctor-walkthrough.mdx).
