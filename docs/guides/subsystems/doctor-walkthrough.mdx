# Run lando doctor

After `lando setup`, run `lando doctor` on the host to check the provider, proxy,
certificates, and related setup state. Read the suggested action for each failing
section; a failure does not prevent the remaining checks from running.

```sh
lando doctor
```

Doctor checks the provider setup persisted, or the one `LANDO_PROVIDER` names for this command. See [Pick a container provider](../setup/provider-selection.mdx#what-persists).

## Read the report

Doctor runs one section at a time under the same live task list `lando start` paints: `✓` for a clean section, `!` when it passed with warnings, `✗` when a check failed or doctor could not run the section. The text report shows non-passing checks, skipped sections with their reasons, and any failures of doctor's own checks. Deprecation findings stay visible when requested. Passing checks, including a valid global config, stay out of the default report, whether you read it in a terminal or pipe it to a file.

Repeated findings from the same contributor with the same check name and status appear as one entry with a count and up to three identifying paths or IDs. Long resource lists show a few items and the number left out. Identical remediation appears once; when the remedies differ, the report gives the number of variants and any command they share. The next steps collect distinct commands, with at most one per check name.

To see every record, including passing checks, full context, provider capabilities, and every remediation variant:

```sh
lando doctor --all
```

For a structured report containing every record regardless of `--all`, run:

```sh
lando doctor --format=json
```

A check passes only after doctor inspects it. Loading a healthcheck runner or an
endpoint scanner does not prove either one works against your provider. Doctor
reports `healthcheck` and `scanner` as `SKIPPED`, with a reason, because it does
not run service probes or scan app endpoints. `lando start` runs those checks
against the app's selected provider; rebuild also runs service readiness gates.
`--fix` does not turn an uninspected check into a pass.

On macOS and Windows, an absent API endpoint and a managed machine inspected as stopped establish idle. Doctor reports `idle (starts on demand)` and passes `selected-provider` and `runtime-service` without asking you to run setup. It skips container exec probes, container event history, router and SSH sidecar readiness, host-proxy reachability, and app listeners on that idle provider. Host SSH and GPG agent checks, host-proxy directory privacy, and saved-state checks still run. Neither doctor nor `--fix` starts an idle runtime.

On Linux and WSL, Lando's shutdown receipt establishes idle after a quiescent `lando poweroff`, or when the receipt comes from an earlier boot, provided the API is absent and no managed processes match. Each launch invalidates the receipt before starting the service. Doctor passes `selected-provider` for idle, and `lando list` reports apps as `stopped`. Without valid receipt evidence, runtime state remains unknown; process observations alone cannot prove workloads stopped. HTTP, protocol, permission, and timeout failures remain failures rather than becoming idle.

To remove an app while runtime state is unknown, use `lando destroy`. It starts or repairs the managed runtime holding that app's resources, then checks the live inventory before cleanup. This also works after a crash, `wsl --terminate`, or the first poweroff after an upgrade without shutdown evidence. `lando destroy --root` and `lando apps:gc --prune` prepare owning runtimes the same way; if preparation fails, cleanup reports that failure. Doctor, other observation commands, and `lando stop` never launch the runtime.

JSON reports keep these entries in the report's `skipped` array, separate from
`subsystems.checks`. The library `doctorReport()` skips the subsystem section
when neither runtime subsystem services nor a host DNS resolver were supplied.

The `host-dns` check resolves `lando-doctor-probe.<proxy.defaultDomain>` through
your host DNS resolver, independently of the host-proxy worker. It passes only when
the answer is nonempty and every address matches the expected loopback address.
Its context contains DNS observations, not RPC service status.
An unavailable resolver produces a `SKIPPED` entry with a reason.

Selecting a certificate authority does not verify its installation or host trust.
Doctor reports `certs` as `SKIPPED` when selection succeeds but no read-only trust
inspection is available. Certificate selection errors still appear as findings.

| Check | What to do |
| --- | --- |
| global-config | Your global config does not decode. Doctor prints the `ConfigError` and its fix, marks `provider`, `subsystems`, `network-trust`, `certificate-authority`, `global-app`, and `mcp` as `SKIPPED` (plus `app-config`, `app-version-constraints`, and `deprecations` under `--app` or `--deprecations`), still runs config-independent checks such as `filesystem-watch`, and exits `1`. Run `lando config validate`, repair with `lando config set`, `unset`, or `edit`, then rerun doctor. See [Repair an invalid global config](../config/global-config.mdx#repair-an-invalid-global-config). |
| selected-provider | Idle passes without repair. For a failure, follow its cause-specific remediation; a missing runtime bundle needs `lando setup`, while a provider API or process-inspection failure names the access or runtime problem. |
| runtime-service | Idle passes. Descendants of Lando's verified service process belong to it, including its rootless child. Only positively identified unowned processes receive termination advice. |
| host-proxy-transport | Reachability is skipped on an idle runtime. The separate `host-proxy-privacy` check still reports host run-directory privacy; its pass does not claim reachability. If the runtime is up but the app's worker isn't running, `lando start` in that app restarts it. Ownership or privacy remediation appears only when those checks fail. |
| provider-bootstrap | Global config passed, but doctor could not build the provider runtime. Read this self check's failure and suggested repair. Doctor marks `provider`, `router`, `ssh`, `healthcheck`, `scanner`, `certificate-authority`, `missing-app-roots`, and `orphaned-volume-snapshots` as `SKIPPED`, plus requested `app-config` and `deprecations`. It does not invent router, SSH, or certificate warnings or suggest `--fix` for checks it never ran. Host DNS (`host-dns`), filesystem watches, network trust, MCP, global-app files, accelerated-start journals, legacy snapshot catalogs, and requested app version constraints still get checked. Doctor exits `1`; repair the bootstrap failure, then rerun it. |
| host-dns | Host DNS did not resolve the probe hostname to loopback. Check connectivity and DNS-rebinding protection on your resolver, or add a local DNS rule for your configured domain. `lando setup` and `doctor --fix` do not write host DNS. See [Check host DNS](./host-dns.mdx). |
| proxy | Run `lando setup`, then start an app so Traefik can route. You do not start Traefik by hand. |
| legacy-route-files | Lando removes recognized generated files automatically on the next routed app start; run `lando setup` to clean them up now. The check reports generated and unrecognized counts with bounded evidence lists. Review and manually delete only unrecognized files you no longer need (on Windows, then run `lando global:restart`), then republish needed routes with each owning app's start command. See [Read the legacy route files check](../global/doctor-walkthrough.mdx#read-the-legacy-route-files-check). |
| preferred-host-ports | Something else owns 80 or 443. Read the selected fallback ports with `lando info`. Stop the holder or choose free router ports in `config.yml`, then run `lando setup`. |
| certs | Run `lando setup` to install and trust the local CA. |
| setup readiness | Rerun `lando setup` to resume the first failed step. |
| filesystem-watch | Read the stage and errno. Windows can also report a missing file event after the watcher opens. On Linux or WSL, close unnecessary watchers first when allocation fails. See [Check filesystem watches on this host](#check-filesystem-watches-on-this-host). |
| accelerated-start | An accelerated file-sync start didn't finish and its app folder still exists. In that folder, run `lando start` to finish it. `lando stop` and `lando destroy` also work when the attempt's sessions and sync targets still check out as yours. |
| missing-app-root | Move the folder back to keep using the app, or run the `lando apps:gc --prune` command doctor gives you. It adds `--volumes` only when Lando can remove the recorded file-sync copies. Without `--volumes`, data and file-sync copies are kept. Add `--purge-caches` when doctor lists caches. |
| missing-app-root-scan | Lando could not read app state to look for missing app folders. Fix the reported problem, then rerun `lando doctor`. |
| orphaned-volume-snapshots | Inspect uncatalogued native images past the one-hour grace period with `lando snapshots:gc`. `lando snapshots:gc --prune` deletes eligible images after rechecking catalog references. GC never starts or repairs a runtime, including during removal. |
| legacy-snapshot-catalogs | Review the reported count and catalog paths. These catalogs came from a development build. Their snapshots are no longer listed or restorable, but their referenced provider images stay protected from GC. Deleting a catalog directory releases that protection so GC can reclaim the images. |

If doctor names a host prerequisite, fix it and rerun `lando setup`. If the managed runtime still cannot install and you have working system Docker, run `lando setup --provider=docker`. See [Pick a container provider](../setup/provider-selection.mdx).

**`lando snapshots:gc --prune` deletes eligible native images.** It does not prune your catalogued manual or recovery snapshots; use the [database snapshot commands](../tooling/db-import-export.mdx) for those.

GC skips stopped runtimes during discovery. If a runtime stops after the removal recheck, GC reports that provider as failed and does not count the failed deletion as removed. It never starts or repairs the runtime. `lando destroy --purge` may start a stopped runtime to remove catalogued snapshots.

The `legacy-snapshot-catalogs` check reads the filesystem only. It finds old `index.bin` catalogs outside the owner-keyed directories, even when no runtime is running. An unreadable legacy catalog blocks GC rather than risking its images. **Deleting a legacy catalog directory releases its image protection.** Keep it if you still need those images; otherwise delete the reported catalog's containing directory, then run `lando snapshots:gc` to review the newly eligible images. Run `lando doctor` again to check the remaining catalogs.

## Finish an interrupted accelerated start

```sh
lando doctor --format=json
```

An `accelerated-start` warning means provider apply did not finish successfully; some app containers may already have run and written to the sync targets. The check lists the app ID, app root, phase, attempt ID, provider, file-sync engine, recorded sessions and volumes, and the journal path. It scans every app, even without `--app`. An attempt whose folder is gone appears in that root's `missing-app-root` finding instead. `doctor --fix` reports these records; it doesn't start or destroy apps for you.

Change to the reported app root and run:

```sh
lando start
lando info
```

That finishes the attempt with its existing sync sessions and history. `lando restart` and `lando rebuild` finish it first too, then do their own work.

`lando stop` and `lando destroy` work from any phase, as long as the attempt's sessions and sync targets still check out as this app's and nothing you wrote could be lost. Stop pauses the sessions and keeps the attempt for the next start. Destroy syncs each session's pending changes back to the project, then discards the attempt's sync sessions and sync targets. **`--volumes` still means your app's data volumes**; leave it off to keep that data.

Start refuses to finish an attempt in three cases:

| Refusal | What to restore |
| --- | --- |
| The provider, file-sync engine, or mount settings changed since the attempt | Put the recorded provider, engine, and mount settings back, then run `lando start`. |
| A sync session is missing after the app may have written to its target | Restore that session's synchronization history in the file-sync engine, then run `lando start`. `lando stop` still stops the app's writers. `lando destroy` refuses until the history is back, because the target may hold the only copy of what the app wrote. Lando leaves the target alone. |
| The engine lists a session Lando didn't record for this app | Lando leaves that session untouched. Inspect it, and clear it only once you know what owns it. |

Keep the journal file. It's what tells the next command which sessions and volumes belong to the attempt.
Once the attempt finishes or its targets have been disposed of, Lando removes the
journal. Old completed journal documents are swept by `lando apps:gc --prune`.

## Clean up an app whose folder is gone

```sh
lando doctor --format=json
```

A `missing-app-root` warning lists resources recorded against an app folder that
no longer exists. If you moved the folder and want to keep using the app, move
it back to the reported path instead of cleaning up its resources.

Inspect all missing roots from any host directory:

```sh
lando apps:gc
```

Report mode never starts a runtime. An unobserved provider with recorded state is listed explicitly;
its containers and volumes may be missing from the report. Failures to read state
are reported even when Lando cannot establish what that provider holds.

If the report says Lando cannot remove a provider's file-sync copies of a deleted
app yet, run `lando apps:gc --prune` without `--volumes`. Lando cleans up everything
else selected by your flags and keeps data volumes, file-sync copies, and their
ownership journals. Those copies keep appearing in doctor. Requesting `--volumes`
for that root fails before deletion and tells you to rerun without it. This includes
prepared file-sync targets on the bundled Windows provider.

For roots whose copies can be removed, **`--volumes` deletes data volumes and file-sync copies of app files, which may
hold the only surviving copy.** Drop that flag to keep them. When you're ready
to discard the reported apps, run:

```sh
lando apps:gc --prune --volumes
```

Lando asks once, listing the roots and what it deletes or keeps. Add
`--purge-caches` to delete cache volumes, or `--purge` to delete data and
catalogued snapshots too. Scripts must pass `--yes` to confirm. Before it asks,
pruning starts the managed runtime that holds the reported resources when it is
idle or its status is unknown, the same way `lando destroy` does, so the
confirmation lists what will actually be removed. Each root is checked again under its app lock; a folder that reappears or
changed evidence is retained. Roots discovered after confirmation are reported
without being pruned. Data you keep by leaving off `--volumes` is listed in the
result and isn't a failure; a root whose cleanup fails doesn't stop the others,
but makes the command exit nonzero. A journal file Lando can't read is reported
and left in place.

For an unfinished accelerated start, Lando verifies the recorded identity and
terminates its engine-listed sessions without syncing back into the missing
folder. Without `--volumes`, file-sync targets and their owning journal stay
and keep being reported. A target that cannot be verified, or an unavailable
engine, leaves the targets and journal in place with a reported failure.

To target only one missing root, `lando destroy --root <path> --volumes` remains
available; replace `<path>` with that root and quote it if needed.
`lando doctor --fix` never cleans up these resources. Check again after cleanup:

```sh
lando doctor --format=json
```

## Check filesystem watches on this host

```sh
lando doctor --format=json
```

On Linux and WSL, the `filesystem-watch` check creates one temporary directory, allocates one non-recursive watch, then closes the watch and deletes the directory. It reads configured inotify limits for watches, instances, and queued events where the host lets it; limits it cannot read show as unavailable. On Windows, the check watches a temporary directory, creates a file there, and confirms that the file event arrives before cleaning up. It does not read Linux inotify limits. On macOS and other hosts, the check reports that it does not apply.

This is a point-in-time check on the machine where you typed the command. Linux and WSL success proves one watch could be allocated; it does not prove event delivery. Windows success proves one event arrived on the CLI host's temporary filesystem. Neither result inspects an app directory, shared mount, provider runtime, or VM, and neither proves spare capacity. Doctor does not total up which processes hold Linux watches: shared file descriptors, user namespaces, and process visibility make an exact count unreliable, and rootless containers can draw from the same per-user budget as your host tooling.

On Linux and WSL, use the failure stage and errno to decide what to inspect:

| Where it failed | What it means |
| --- | --- |
| `ENOSPC` allocating the watch | The inotify watch budget, or a related kernel resource, is exhausted. This is not evidence of a full disk. |
| `ENOSPC` creating the temporary directory | Storage ran out: blocks or inodes on the temp filesystem. |
| `EMFILE` allocating the watch | Either the per-process file-descriptor limit or the inotify instance limit. Doctor cannot tell which. |
| `EMFILE` creating the temporary directory | The per-process file-descriptor limit, not the inotify instance limit. |
| `ENFILE` | The system-wide file-descriptor limit. |
| `EACCES` or `EPERM` | Doctor was not allowed to create the directory or the watch. |
| Unsupported | The host or filesystem does not support inotify watches here. |
| Anything else | Reported as unknown, with the error attached. |

On Windows, `stage: delivery` with `ETIMEDOUT` means the watcher opened but the temporary-file event did not arrive. Check the Windows temporary filesystem and security software, then rerun doctor. A `setup` or `watch` failure carries its own errno; fix temporary-directory access or close unused watch tasks before retrying.

For Linux watch-resource failures, close unnecessary watchers first: extra editors, file-sync daemons, test runners in watch mode. Then rerun doctor. Address storage or permission failures on the reported filesystem instead. If a limit itself is the problem, raising it is an administrator change on the affected host or VM. `lando doctor --fix` never writes sysctl config, raises limits, or kills processes.

The router has its own, separate watcher record. That one reports what the Traefik container observed on the provider runtime host, and a clean `filesystem-watch` result does not clear it. See [Read the router file-watcher check](../global/doctor-walkthrough.mdx#read-the-router-file-watcher-check).

## Check the current app

```sh
lando doctor --app
```

That adds Landofile lint (the same pass as
[`lando app:config:lint`](../landofile/config-lint.mdx), including its offline
final-planning stage), version-constraint checks, and a point-in-time TCP
listener check for this app. A missing or invalid Landofile shows up as its own
section. The rest of the report still runs.

### Check the app's TCP listeners

Run from the app directory after starting it:

```sh
lando doctor --app --all
```

Doctor uses the last applied plan and its provider, even if you've since changed
the Landofile's provider or port. For each running service with an expected TCP
listener, it reads the container's network-namespace listener tables. It does
not run your readiness command or scan URLs. Each read is limited to two seconds
and 128 KiB, with at most four reads at once and an overall section deadline.

| Result | Meaning and next action |
| --- | --- |
| `pass`, `listening` | A non-loopback binding exists on the planned port. This does not prove that the application is ready or that a particular process owns the socket. |
| `warn`, `loopback-only` | Only loopback bindings were found on that port. Bind the server to `0.0.0.0` so other services can reach it. |
| `warn`, `not-listening` | No binding was found on that port at this instant. If the app is still starting, rerun `lando doctor --app`; otherwise follow the action line. |
| `skipped` | There is no applied plan, the service isn't running, no expected TCP listener is recorded, or the observation is unavailable. An unreadable table or expired budget is not evidence of an absent listener. |

A not-listening finding for planned port `8080` reads:

```text
finding: No TCP listener was observed on planned port 8080 at this instant. If the application is still starting, rerun `lando doctor --app`.
```

The action also names what your application, command, or custom image must
configure when it owns that listener. `--fix` does not change your server's
configuration. Without `--app`, doctor does not perform this listener check.
JSON keeps observations in `result.appListeners.checks`, with string context fields
`service`, `port`, `listenerState`, `finding`, and `bindings`, plus `solutions`.
Unavailable observations go in the report's `skipped` array.

## Machine-readable output

```sh
lando doctor --format=json
lando doctor --format=yaml
```

Use those formats in scripts. Both wrap the report in the standard result envelope under `result`, so `ok` and the tagged `error` are always there to branch on. Doctor redacts secrets, certificate bodies, and proxy URLs.

## Verify

```sh
lando doctor
lando --version
```

Doctor should name the provider you selected.
