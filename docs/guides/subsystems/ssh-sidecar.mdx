# SSH sidecar

This page is a contributor dump for `SshService` and the default SSH-agent delivery path. It stays off the user nav. To forward a 1Password, YubiKey, or gpg-agent instead, see [Use your host SSH agent](./ssh-host-agent.mdx).

The Landofile knob is top-level `sshAgent`. Leaving it out is the same as this:

```yaml
name: myapp
sshAgent:
  sidecar: true
```

`sidecar: true` selects the Lando-managed `ssh-agent` global service. It runs `ssh-agent` and loads your `~/.ssh` keys through `ssh-add` when the global app starts. The managed `lando` provider hosts it even when the app itself runs on Docker or user-owned Podman. `sidecar: false` switches the app to host mode; that page is linked above. There is no per-service `sshAgent` key.

Lando starts the sidecar with the global app when a start needs it. You do not start an SSH agent by hand.

## What lands in the container

Every `type: lando` service gets the `lando.ssh-agent` feature (priority 1200) in both modes. It bind-mounts a relay directory and sets:

```sh
SSH_AUTH_SOCK=/run/lando/ssh-agent/agent.sock
```

The mount is the directory, not the socket. A per-app relay owns that directory and streams raw agent bytes between `agent.sock` and the upstream (here, the sidecar socket under the user data root). Replacing the relay socket never recreates the container. The sidecar's own socket is never bound directly into a service.

The planner records only the eligible services and the selected mode under the plan extension `@lando/core/ssh-agent` (`{ mode: "sidecar" | "host" }`). The relay directory and the `SSH_AUTH_SOCK` mount are a start-time overlay applied by start, restart, and rebuild; they never enter the plan cache. The relay is scope-owned: kept after a successful apply, closed on stop or destroy.

## When the sidecar is missing

Sidecar mode is best-effort. If the provider does not advertise `agentSocket`, the sidecar is not installed or not running, or the relay or bridge fails to come up, `lando start` still succeeds. Lando publishes a warning naming the reason and the remediation and starts the app without the `SSH_AUTH_SOCK` overlay. `lando doctor` reports the `ssh` check as degraded with `lando setup` or `lando doctor --fix` as remediation.

Host mode does the opposite and fails closed. That difference is deliberate: nobody opts into the sidecar, so it must never block a start; everyone who opts into host forwarding wants to know when it is not working.

## Security

The sidecar is a Lando-managed `ssh-agent` container. At global-app start it runs `ssh-add` against a read-only bind of your `~/.ssh`, so every default key it can load without a passphrase ends up unencrypted in that agent's memory for as long as the global app runs. Passphrase-protected keys are skipped. Hardware-backed keys and 1Password keys never load here; they need [host mode](./ssh-host-agent.mdx), which keeps signing on the host.

Any `type: lando` service in any running app can request signatures from the sidecar. The relay socket on the host is mode `0666` inside a per-user `0700` run directory, so other accounts on the machine cannot reach it. On Windows the bridge into the Podman machine uses a loopback TCP broker without a token; another local account on that host could connect to it while an app runs.

This is not a user how-to. For a shell inside a service, see [Open a shell in a service](../cli/ssh.mdx).
