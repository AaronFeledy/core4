# Deliver the sidecar SSH agent inside the runtime

The default SSH sidecar delivers its socket through a runtime volume when the app uses the managed `lando` provider. This contributor explanation covers `SshService` and delivery. To forward a 1Password, YubiKey, or gpg-agent instead, see [Use your host SSH agent](./ssh-host-agent.mdx).

The Landofile knob is top-level `sshAgent`. Leaving it out is the same as this:

```yaml
name: myapp
sshAgent:
  sidecar: true
```

`sidecar: true` selects the Lando-managed `ssh-agent` global service. It runs `ssh-agent` and loads your `~/.ssh` keys through `ssh-add` when the global app starts. The managed `lando` provider hosts it even when the app itself runs on Docker or user-owned Podman. `sidecar: false` switches the app to host mode; that page is linked above. There is no per-service `sshAgent` key.

That `~/.ssh` resolves against your current host home when the global app is planned, so a changed home reaches the next plan without manual cleanup. A sidecar that is already running keeps its old bind until `lando global:rebuild`.

Lando starts the sidecar when a start needs it. You do not start an SSH agent by hand. `lando start`, `lando restart`, and `lando rebuild` check the sidecar's agent first. If it does not answer, whether after `lando poweroff`, a reboot, or a crash, Lando starts the sidecar and waits up to about 30 seconds for the agent under a "Start SSH agent sidecar" progress step. A sidecar that is already running costs nothing extra. Forwarding comes back after a poweroff or reboot without `lando setup` or `lando global:start`.

## What lands in the container

Every `type: lando` service gets the `lando.ssh-agent` feature (priority 1200) in both modes. Its start-time overlay mounts a socket directory read-only and sets:

```sh
SSH_AUTH_SOCK=/run/lando/ssh-agent/agent.sock
```

On the managed provider, the plugin publishes `runtimeVolume: "lando-ssh-agent"` through `SshService.getAgentSocket`. The global service declares `storage: [{ store: "lando-ssh-agent", target: "/run/lando/ssh-agent", scope: "app" }]`. The planner preserves that native name and puts the store on the global plan, never on consuming app plans. Apps mount the volume directly: no host socket probe, detached relay worker, or VM bridge. Readiness checks the global service on the managed provider and runs `ssh-add -l` inside it; an empty but reachable agent is ready.

The sidecar publishes `agent.sock` at the volume root with mode `0666` and a traversable directory. A socat listener connects to the private agent socket as the agent's owner, allowing non-root service users through OpenSSH's peer-UID check. This local forwarding stays inside the runtime on Linux, macOS, and Windows.

Apps on Docker or user-owned Podman keep the host-relay path. A second sidecar listener preserves `<userDataRoot>/ssh/ssh-agent.sock`; the per-app worker probes and relays it through the selected provider's existing delivery mechanism. A plugin without `runtimeVolume` also uses that path. Cross-provider delivery still depends on the host being able to connect to the sidecar's host-facing socket.

The planner records only the eligible services and the selected mode under the plan extension `@lando/core/ssh-agent` (`{ mode: "sidecar" | "host" }`). The mount and `SSH_AUTH_SOCK` are a start-time overlay applied by start, restart, and rebuild; they never enter the plan cache. Runtime-volume sessions need no per-app cleanup. App stop, destroy, and volume pruning leave the globally owned store alone. Global destroy or uninstall may remove it. Host-relay sessions retain their existing cleanup on stop or destroy.

## When the sidecar is missing

Sidecar mode is best-effort. If the provider does not advertise `agentSocket`, no sidecar service is installed, the sidecar cannot start or its agent never answers within the wait, or a required relay or bridge fails, `lando start` still succeeds. Lando publishes a warning that names the cause and starts the app without the `SSH_AUTH_SOCK` overlay. The fix depends on the cause:

- The sidecar could not start: fix the cause, then run `lando restart`. `lando global:logs --service ssh-agent` shows the sidecar's output.
- It stopped, or its agent did not answer within the wait: run `lando global:logs --service ssh-agent` to see why, fix the cause, then run `lando restart`.
- No SSH agent sidecar service is installed: install and select the bundled SSH agent plugin, then restart the app.

Every later start retries on its own. `lando doctor` reports `runtime-volume` delivery and the volume name on the managed provider, using in-runtime readiness rather than host socket reachability. A failed check reports degraded with `lando setup` or `lando doctor --fix` as remediation.

Setup and the global app follow the same rule. If the sidecar cannot start, `lando setup` prints a warning with the cause, finishes its other steps, and records the `shell` step as unavailable. `lando doctor` keeps reporting that setup record until the next `lando setup` run, even after an app start brings the sidecar up. `lando doctor --fix` can restart the sidecar and waits for its agent before reporting the `ssh` check recovered or failed, but it does not rewrite the setup record. `lando global:start`, `lando global:restart`, and `lando global:rebuild` start global services that do not depend on each other separately, so a broken sidecar does not stop Traefik or the other global services from starting. Those commands still exit non-zero and name the service that failed.

Host mode does the opposite and fails closed. That difference is deliberate: nobody opts into the sidecar, so it must never block setup or a start; everyone who opts into host forwarding wants to know when it is not working.

## Security

The sidecar is a Lando-managed `ssh-agent` container. At global-app start it runs `ssh-add` against a read-only bind of your `~/.ssh`, so every default key it can load without a passphrase ends up unencrypted in that agent's memory for as long as the global app runs. Passphrase-protected keys are skipped. Hardware-backed keys and 1Password keys never load here; they need [host mode](./ssh-host-agent.mdx), which keeps signing on the host.

Any opted-in service can request signatures from the shared sidecar. A read-only socket-volume mount prevents filesystem changes, not signing requests. The host-facing listener is mode `0666` inside the private `0700` SSH directory. The host relay uses a mode `0666` socket inside a per-user `0700` run directory. Managed-provider sidecar delivery does not open a host TCP broker. Host mode and cross-provider delivery retain their existing transport restrictions.

This is not a user how-to. For a shell inside a service, see [Open a shell in a service](../cli/ssh.mdx).
