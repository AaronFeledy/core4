# Add Apache

Add `type: apache` under `services` in `.lando.yml`. Lando pulls `httpd:2.4-alpine` and listens on `80`:

```yaml
name: apache-demo
services:
  web:
    type: apache
```

Your repository is mounted at `/app`. The default `webroot` is `.`, resolving to `/app` for `APACHE_DOCUMENT_ROOT`. Start it. Lando wires the service into the proxy:

## Open the URL

The proxy derives an HTTPS hostname from the service's HTTP endpoint without a `proxy:` block. You'll get something like `web.<app>.lndo.site`.

A stock service serves native HTTPS too. When a route needs HTTPS and Lando owns Apache, Lando declares both a plain listener and an HTTPS listener on `443` (`8443` when your plain `port:` is already `443`), loads the image's SSL modules during the build, and serves a generated certificate on the TLS listener. The HTTPS listener is not primary and is not published; `routes:` and `lando info` still describe the public URL. An HTTPS route prefers that listener; an HTTP route, or an explicit `endpoint:` naming the plain listener, keeps plain HTTP. A request for a directory without its trailing slash redirects to the same scheme, host, and port the browser used, with the slash added.

Hidden paths, meaning any path segment that starts with `.` such as `/.git/config` or `/.env`, get a 403, so your repository's dotfiles stay private even though the app root is the default webroot. `/.well-known/` stays served.

Set `webroot:` to an app-relative path when Apache should serve a subdirectory. Lando resolves it against `/app`, writes the absolute path into Apache's generated config, and exposes that resolved absolute path as `LANDO_WEBROOT` and `APACHE_DOCUMENT_ROOT`. Omit it or use `.` for the app root. An absolute container path is allowed when you need a very specific location outside the usual app layout:

```yaml
services:
  web:
    type: apache
    webroot: public
```

An explicit `environment.APACHE_DOCUMENT_ROOT` still wins for custom setups. If you replace `command:` or `entrypoint:`, your launcher owns the Apache config too, and Lando generates no TLS listener or certificate request.

## Serve HTTPS from Apache

A plain `type: apache` service with an HTTPS route gets a generated certificate and a TLS listener. Lando asks for the certificate because the route needs it, so the service needs no `certs:` key and adds no certificate-authority dependency to an HTTP-only service or an app with the router disabled. An explicit `certs: true` keeps its usual meaning and configures the TLS listener even without a route; `certs: false` or custom certificate material keeps plain Apache, with the router terminating TLS.

The service's parent process runs as root by default and reads the certificate key before workers drop privileges. If you set `user:` to a non-root account, Lando keeps that account and the plain listener, because it will not weaken the key file's permissions or hand host material to a container user. HTTPS routes then terminate at the router and reach Apache as plain HTTP.

## Run as a non-root user

Set `user: www-data` to run Apache as the image's `www-data` account. Lando hands its directives to `httpd-foreground` as `-c` arguments and points the PID file at `/tmp/lando-httpd.pid`, so nothing gets written into the image's root-owned config tree at start:

```yaml
services:
  web:
    type: apache
    user: www-data
```

On the default `lando` provider, this non-root configuration also needs a port of 1024 or above: the process cannot bind the image's default port `80`. Set `port:` to 1024 or above and Apache listens there instead. Lando passes `Listen <port>` as a `-c` directive and drops the image's `Listen 80` from `httpd.conf` during the build, so the daemon binds only the port you picked:

```yaml
services:
  web:
    type: apache
    user: www-data
    port: 8080
```

Leave `port:` out and nothing changes: same launcher, same image, no extra
build step. If you set your own `command:` or `entrypoint:`, Lando never
appends `Listen` or other flags, and it does not generate the launcher or touch
the image config. Match Apache to `port:` yourself. Point `image:` at something
other than `httpd:2.4-alpine` and Lando still generates the start command, but
it does not emit `Listen` or edit `httpd.conf`. That image owns its own
listener.
If startup fails with an authored `command:` or `entrypoint:`, Lando includes
a hint naming `Listen <port>` with your planned port number.

## Pin a version

Set `image:` when `httpd:2.4-alpine` isn't the version you want. For example, a Debian-based image:

```yaml
services:
  web:
    type: apache
    image: httpd:2.4
```
