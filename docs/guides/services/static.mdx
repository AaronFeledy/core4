# Serve a static site

Add `type: static` under `services` in `.lando.yml`. That defaults to the nginx variant. Lando pulls `nginx:1.30-alpine` and listens on `80`. The webroot defaults to `.`, resolving to the app root at `/app`, and the app source is mounted read-only. The server can't mutate your repository:

```yaml
name: static-demo
services:
  web:
    type: static
    webroot: dist
tooling:
  curl:
    service: web
    cmd:
      - sh
      - -c
      - 'test -n "$1" || set -- ""; curl -sf -- "http://localhost:80/$1"'
      - curl
```


Before starting this example, build your site into `dist/` so that `dist/index.html` exists. The configuration serves generated files, not your source templates.

## Read missing paths and directories

On a matched host with default `static:nginx`:

- Missing file → **`404 · Lando web server`** / "Page not found"
- Directory without an index → **`403 · Lando web server`** / "Access denied"
- Hidden path, any segment starting with `.` such as `/.git/config` or `/.env` → **`403 · Lando web server`**. `/.well-known/` stays served.

Wrong hostname? You get the proxy page (`404 · Lando proxy`) instead. See [Use the Traefik proxy](../subsystems/proxy-traefik.mdx).

## Serve a subdirectory

Set `webroot` to a path relative to the app mount at `/app`, just as you do for nginx, Apache, and PHP services. The example uses `webroot: dist` to serve the build output directory. Inside the container, `LANDO_WEBROOT` is always the resolved absolute path, here `/app/dist`. Omit `webroot` or use `.` to serve the app root. Use an absolute value such as `webroot: /srv/site` only when you need a very specific container path outside the usual app layout; make sure that directory exists in the container. Relative paths that escape `/app`, such as `../srv`, are rejected.

## Serve with Caddy

Prefer Caddy? Set `type: static:caddy`. Its default image is `caddy:2-alpine`:

```yaml
services:
  web:
    type: static:caddy
```

Lando generates a Caddyfile during the image build and starts `caddy run --config /usr/share/lando/caddy/Caddyfile --adapter caddyfile`. The site listens on plain HTTP only: automatic HTTPS and the admin API are off, so the router or a published host port owns TLS. Caddy serves the same shared 403 and 404 pages as the nginx variants, and it returns 403 for hidden path segments such as `/.git/config` and `/.env`. Only a segment named exactly `.well-known` is exempt, so `/.well-known/acme-challenge/token` stays reachable. Caddy answers a directory URL without its trailing slash with a relative 308, so the browser keeps the proxy's scheme, host, and port. `port:` moves the baked site address, the endpoint, and the healthcheck together.

## Run as a non-root user

Set `user: nginx` to run the default `static:nginx` server as the image's own `nginx` account. Lando writes its whole nginx configuration to `/tmp/lando-nginx.conf`, points the PID file and temp directories at `/tmp` too, and starts the daemon with `nginx -c /tmp/lando-nginx.conf`, so nothing gets written into the image's root-owned config tree at start:

```yaml
services:
  web:
    type: static
    user: nginx
    port: 8080
```

Lando plans no home store for the `nginx` account, whose home on this image is
its cache directory; set `home.path:` when you want a directory to survive a
rebuild. `port:` moves the listen port itself, not just Lando's endpoint,
because Lando templates it into the generated config. A non-root process can't
bind below 1024 on the default `lando` provider, so pick something at or above
`1024`.

If you set your own `command:`, Lando preserves it instead of generating the
launcher. Include the nginx `listen <port>;` directive with your planned port.
Lando never appends it to your command. If startup fails, Lando includes a hint
naming that setting. An authored `entrypoint:` alone still receives Lando's
generated nginx command.

`static:caddy` reads its baked Caddyfile at start and writes nothing, so it also
works under a non-root `user:`. It still listens on `80` by default, so the same
port rule applies. An authored `command:` or `entrypoint:`, a different `image:`
reference, or a replacement `build:` takes over server configuration instead:
Lando bakes no Caddyfile for that service, so your configuration must serve the
planned port.

## Pin a version

Set `image:` to pin a specific nginx version. The generated nginx launcher still
applies:

```yaml
services:
  web:
    type: static
    image: nginx:1.27-alpine
```

Caddy's generated configuration is baked for the bundled `caddy:2-alpine` image.
Writing a different `image:` reference, including a pinned Caddy tag, a
replacement `build:`, or an authored `command:` or `entrypoint:` means you own
the server configuration. Lando then bakes no Caddyfile and runs no generated
launcher:

```yaml
services:
  web:
    type: static:caddy
    image: caddy:2.8-alpine
    command: ["caddy", "run", "--config", "/etc/caddy/Caddyfile", "--adapter", "caddyfile"]
```
