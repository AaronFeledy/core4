# Add Python

Add `type: python:3.12` to your primary service in `.lando.yml`. Python has no bare `type: python` alias, so pin a version. Lando supports `python:3.12`. The default image is `python:3.12-slim`. Your repo mounts read-write at `/app`.

```yaml
name: python-demo
services:
  app:
    type: "python:3.12"
    primary: true
```

Add `framework:` when you want FastAPI, Django, or Flask defaults for port and env. Keep-alive still runs until you set `command:` or serve with `lando exec`.

Python publishes its port endpoint but has no default healthcheck or readiness probe, including for authored worker commands. Add `readiness:` when you want start to wait for application readiness; use `healthcheck:` separately for native ongoing monitoring. Without an effective readiness command, Lando checks that the process stays running. The slim image has no `curl`, so probe with Python itself in argv form. This example serves the app directory with Python's built-in HTTP server:

```yaml
services:
  app:
    type: "python:3.12"
    primary: true
    port: 8000
    command: [python, -m, http.server, "{{ service.port }}"]
    readiness: [python, -c, "import urllib.request; urllib.request.urlopen('http://localhost:{{ service.port }}/')"]
```

For an existing FastAPI project, save this complete service and tooling configuration in `.lando.yml`:

```yaml
name: python-fastapi
services:
  app:
    type: "python:3.12"
    framework: fastapi
    primary: true
    port: 8000
tooling:
  pip:
    service: app
    cmd: pip
  uv:
    service: app
    cmd: uv
  python:
    service: app
    cmd: python
```

The `django` preset sets `DJANGO_SETTINGS_MODULE=config.settings`, and `flask` sets `FLASK_APP=app`. Without a framework, the service stays plain Python.

## Pass `port:` to your Python server

Lando derives the port variables from the internal HTTP endpoint, and an explicit `port:` replaces the framework default. See the [Python listener reference](../../reference/service-listeners.mdx#python) for each framework's variables, default port, and host defaults.

Gunicorn reads `PORT` and binds `0.0.0.0`; Uvicorn CLI reads `UVICORN_*`, and `flask run` reads `FLASK_RUN_*`.

Port variables are not independent overrides. If an authored value is malformed or differs from the planned port, planning fails at `services.app.environment.<VAR>`. This includes inherited `appEnv` and env-file values. Set `port:` instead. Host variables are ordinary defaults: your authored host value wins, but a loopback address makes the server unreachable through the proxy.

FastAPI CLI does not read `UVICORN_*`. `fastapi run main.py` binds all interfaces and reads `PORT`; `fastapi dev main.py --host 0.0.0.0` still needs its host argument. Django reads neither the port nor the host from these variables, and Python's built-in `http.server` also needs its port argument. In an authored launcher, use the [port expression](../landofile/expressions.mdx#your-services-own-port) for the value, as in the `http.server` example above.

Python does not interpret `webroot:`. An explicit root fails planning unless
a composed plugin feature declares and handles it. Set `workingDirectory:`
to move the process, and configure static-file paths in your application or a
separate webserver.

Start it:

```sh
lando start
lando info
```

If host ports 80 or 443 are taken, `lando info` shows fallback ports such as `:8080` and `:8443`.

## Run tools in your project's environment

On the stock Python service, put `:python-local` before a project tool in your Landofile. For a uv project with `pytest` in its dependencies or default dependency group, add this task:

```yaml
tooling:
  pytest:
    service: app
    cmd: [":python-local", "pytest"]
    wrapper: true
```

From your app directory, run `lando start` and then `lando pytest -q`. The launcher searches for `pyproject.toml` from the command's working directory up to the app mount root, or up to the filesystem root when the command runs outside the mount. When it finds one, it runs the command through `uv run --` in that working directory, so uv creates and syncs the project environment first. Plain `uv run` can create or update `uv.lock`, from tooling and service commands alike. To reject a missing or stale lockfile instead, run `lando exec app -- uv run --locked -- pytest -q`.

### Install from `requirements.txt`

On a fresh clone, run `lando start` from the app directory. Stock Python prepares an active virtual environment at `/app/.venv` (or `.venv` under your app mount) and installs `requirements.txt` before the Python services start. Without that file, Lando still prepares the environment. For `pyproject.toml` projects, use `:python-local` as above; the prepare job does not sync those projects.

Run `lando restart` after changing dependencies while the app is running. A `lando start` that keeps every consumer running leaves the environment alone. Unchanged inputs need no package index access. Local `-r` and `-c` files inside the app are tracked, but changes to the contents of editable or local packages aren't. Installation is additive; removing a line doesn't uninstall the package. Use `pip freeze --local` to record only project-installed packages.

Services such as `web` and `worker` share one environment when their Python toolchain and image build, app mount source and target, user, and platform match. A change to those inputs can select a fresh store. Ad-hoc installs survive restarts, rebuilds, and a plain `lando destroy` as long as the environment stays compatible. Lando repairs an invalid venv before installing requirements again; ad-hoc packages aren't restored in that case.

`lando start` and `lando info` show `python-env` as a completed job, with a suffix on each job name if the app has multiple Python environments. If installation fails, the services that use it cannot start. Run `lando logs -s python-env` (or use the suffixed job name), fix `requirements.txt`, and retry `lando start`.

A custom image, replacement `build.context`, `appMount: false`, an app mount target containing `:`, or any authored mount at the venv path skips both preparation and activation. An authored named volume is yours to populate and activate. `appMount.includes: [.venv]` also opts out and exposes the host tree, which may not run in the container. Scratch apps skip dependency environment preparation.

Login shells keep the service's `PATH`, including an authored `environment.PATH` that leaves the venv off it. The prepare job uses a shared uv download cache; `uv` commands you run yourself use uv's normal cache in the service home.

Without a project manifest, `:python-local` uses the app-root `.venv` if it has an executable interpreter, and otherwise runs the command directly. An unreadable manifest or a broken interpreter link fails rather than falling back. Lando has no command to reset just the dependency environment. `lando destroy --volumes` also deletes other app volumes, such as databases.

## Serve FastAPI

Declare `fastapi` and `uvicorn` as project dependencies in `pyproject.toml`, and put `main.py` with an ASGI object named `app` in your app root. Set `command` in the Landofile so Lando starts Uvicorn through the project environment:

```yaml
services:
  app:
    type: "python:3.12"
    framework: fastapi
    primary: true
    port: 8000
    command: [":python-local", "uvicorn", "main:app", "--host", "0.0.0.0", "--port", "{{ service.port }}"]
```

```sh
lando start
lando info
```

Open the URL `lando info` prints. A tiny `main.py` that returns JSON is enough to prove the route.

## Django and Flask

Same service type. Swap the framework and start the server you run through the project environment:

```yaml
services:
  app:
    type: "python:3.12"
    framework: django
    primary: true
    command: [":python-local", "python", "manage.py", "runserver", "0.0.0.0:{{ service.port }}"]
```

```yaml
services:
  app:
    type: "python:3.12"
    framework: flask
    primary: true
    command: [":python-local", "flask", "run"]
```

The `flask` preset sets `FLASK_RUN_HOST=0.0.0.0` and `FLASK_RUN_PORT` from `port:`, so `flask run` binds where Lando routes traffic. To pass the bind address explicitly to Gunicorn, use `[":python-local", "gunicorn", "--bind", "0.0.0.0:{{ service.port }}", "app:app"]`.

## Pin an image

Slim is the default. Use the full image when wheels need build tools. A custom `image:` or a Dockerfile selected by `build.context` owns its toolchain. Only the stock image gets Lando's `uv` install and `:python-local`; on a replacement image, invoke the tools your image provides directly:

```yaml
services:
  app:
    type: "python:3.12"
    image: python:3.12
```
