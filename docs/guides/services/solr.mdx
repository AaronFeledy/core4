# Add Solr

Add `type: solr` under `services` in `.lando.yml`. That resolves to `solr:9`. Lando pulls it and listens on `8983`:

```yaml
name: solr-demo
services:
  search:
    type: solr
```

## Precreate cores

List cores under `services.search` to have Solr precreate them on boot, before the foreground server starts:

```yaml
services:
  search:
    type: solr
    cores: [default, products]
```

`precreate-core` runs for each declared core before `solr-foreground`, so every core exists before the server accepts queries. When you declare cores, Lando selects user-managed (standalone) mode on Solr versions that offer it, including Solr 10. Older images keep their standalone default.

A core name has to name exactly one directory under `/var/solr/data`. Use letters, numbers, dots, underscores, and dashes. `.` and `..` are reserved, and `/` and `\` are rejected, so no core can precreate or overlay config outside its own directory. Dots inside a name are fine: `a.b` and `a...b` both work. `lando app:config:lint` reports a bad name at `["services", "search", "cores", 0]`, and `lando start` refuses it while it plans the app, before it builds the startup command and before it starts a provider. The error names the offending entry:

```
services.search.cores[0]: "../escape" is not a usable Solr core directory name. Use letters, numbers, dots, underscores, and dashes. "." and ".." are reserved, and "/" and "\" are not allowed. Rename the core to a plain directory name.
```

### Run Solr as another user

`precreate-core` writes into `/var/solr`, and that path is a named volume. The container runs as whatever `user:` you set, so the planned user has to own that tree or the first start dies on a permission error before Solr ever listens.

The image ships `/var/solr` owned by `solr` (uid `8983`), so `user: solr`, `user: "8983"`, `user: root`, and no `user:` at all just work. Nothing changes for those.

For any other user, Lando prepares the tree in the image before the volume exists: one root build step creates `/var/solr` and chowns it to your user. A container runtime seeds a fresh named volume from the image directory at that path, ownership included, so your user owns the data tree from the first start.

```yaml
services:
  search:
    type: solr
    user: "10001"
    cores: [default, products]
```

Two things to know:

- It only applies to a **new** volume. A volume created by an earlier start keeps the ownership it already has. Purging that volume deletes its Solr data. Back up anything you need before using `lando destroy` with volume purge to create a fresh volume with the new ownership.
- Lando has to know your user exists in the image. A numeric uid always works, because a uid can always be given ownership, even when you supply your own `image:` or `build:`. A name the `solr` type doesn't declare (`solr` and `root` are the only two) is refused. A named `user:` on a service that supplies its own `image:` or `build:` is refused too, because that image is no longer the one the type described. The refusal is a `DataTreeOwnershipCapabilityError` that names the service, the data tree (`/var/solr`), and the Landofile option to change. Fix it with a numeric uid, or use `root`.

## Hit the admin API

Run a request inside the service after start to confirm the HTTP surface is reachable:

```sh
lando exec search -- curl -sf http://localhost:8983/solr/admin/info/system
```

That's the same endpoint the built-in healthcheck curls (`curl -sf http://localhost:8983/solr/admin/info/system`) before Lando reports `post-start`.

## Ship your own core config

Set `config.dir` to an app-relative directory that holds your `solrconfig.xml`, `managed-schema`, and friends:

```yaml
services:
  search:
    type: solr
    cores: [default, products]
    config:
      dir: ./config/solr
```

Lando mounts that directory read-only at `/etc/lando/solr/conf` inside the container. When the service starts, it copies the contents into `/var/solr/data/<core>/conf` for each core you declared, so `default` and `products` above both get the same config.

The path has to stay inside the app root. Absolute paths, paths that climb out of the app root, and symlinks that point outside it are rejected when Lando plans the app, before anything starts.

That copy is an overlay, not a replace. `cp -a` lays your files over whatever `precreate-core` just wrote into `/var/solr/data/<core>/conf`, so anything you ship wins and anything you leave out keeps the stock file. It runs on every start, so an edited file lands on the next `lando start`. If the copy fails, the container exits instead of serving a half-configured core.

Lando identifies that directory by its contents, not by where it sits. Move the directory and the service keeps its build key. Change a file inside it and the service rebuilds. An empty directory is a legal overlay and hashes to one fixed identity, so two empty directories in different places give the same build key, and the first file you add changes it.

The copy runs as the planned `user:`, so the same ownership rule as [precreating cores](#run-solr-as-another-user) applies: your user has to own `/var/solr`, and Lando arranges that for a numeric uid on a fresh volume. The overlay side has its own requirement. The host directory is bind-mounted read-only, and a non-root user still has to be able to read it. A `0700` directory on the host is not readable by uid `10001` inside the container, and the copy fails. `0755` works.

If you also set `command:` on the service, yours wins. Your command owns core
creation, config copying, Solr's listen port, and startup mode. Lando never
appends `-p` or other flags to a command you wrote. An authored `entrypoint:`
still receives Lando's Solr command, port included.

## Change the port

Set `port:` to move the HTTP listener, healthcheck, and endpoint together:

```yaml
services:
  search:
    type: solr
    port: 8984
```

Lando starts Solr with `-p 8984`, including when it precreates cores. Other
services connect to `search:8984`. If you author `command:`, pass `-p 8984`
yourself.
If startup fails with an authored command, Lando includes a hint naming
`-p 8984`.

Apply the change with `lando rebuild`, then check the admin API on the planned
port:

```sh
lando exec search -- curl -sf http://localhost:8984/solr/admin/info/system
```

## Keep the stop listener valid

Solr also opens a loopback-only Jetty stop listener. Its default port is
`7983`, derived from the HTTP port minus `1000`. Moving `port:` also moves
that listener, so `7983` is not a fixed reservation for HTTP.

With Lando's launcher, `port:` must be above `1000` unless you set a valid
`STOP_PORT`. A primary port below `1000` disables Jetty's stop monitor; at
exactly `1000`, Jetty chooses an ephemeral stop port. HTTP can still start in
both cases, but Solr's stop client rejects the nonpositive configured port,
so graceful shutdown is unreliable. Lando rejects this configuration during
planning at `services.<name>.port` rather than selecting a stop port for you.

If you need a low HTTP port, set `STOP_PORT` to a distinct integer from `1`
to `65535`:

```yaml
services:
  search:
    type: solr
    port: 1000
    environment:
      STOP_PORT: "18000"
```

This fixes the stop-port derivation; it does not grant permission to bind a
privileged HTTP port. The stop listener cannot share the HTTP port. An authored
`command:` owns its own stop-listener configuration, so these launcher checks
do not apply to it.

Validate with `lando app:cache:refresh --format=json` before start.

## Pin a version

Set `image:` when the default `solr:9` line is not the tag you want:

```yaml
services:
  search:
    type: solr
    image: solr:9.6
```

Because you supply the image, Lando plans no home store for the service. See [home and host mounts](../home-and-host/) if you want to keep one with `home.path`.

For Solr 10 with standalone cores, declare the cores directly:

```yaml
services:
  search:
    type: solr
    image: solr:10
    cores: [default, products]
```

Start the app and check that both cores loaded:

```sh
lando start
lando exec search -- curl -sf 'http://localhost:8983/solr/admin/cores?action=STATUS&wt=json'
```

The response's `status` object should contain `default` and `products`, with an empty `initFailures` object. No custom startup command is needed. `config.dir` works with this configuration too.

Without a `cores:` list, Lando keeps the image's default startup mode. Solr 10 starts in SolrCloud mode; use collections rather than standalone cores in that mode. See [Add Solr 10](../solr10/).
