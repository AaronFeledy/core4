# Add Solr

Put `type: solr` in your services block. That resolves to `solr:9`. Lando pulls it and listens on `8983`:

```yaml
name: solr-demo
services:
  search:
    type: solr
```

## Precreate cores

List cores under `services.search` to have Solr precreate them on boot, before the foreground server starts:

```yaml
services:
  search:
    type: solr
    cores: [default, products]
```

`precreate-core` runs for each declared core before `solr-foreground`, so every core exists before the server accepts queries.

A core name has to name exactly one directory under `/var/solr/data`. Use letters, numbers, dots, underscores, and dashes. `.` and `..` are reserved, and `/` and `\` are rejected, so no core can precreate or overlay config outside its own directory. Dots inside a name are fine: `a.b` and `a...b` both work. Lando refuses a bad name while it plans the app, before it builds the startup command and before it starts a provider, and the error names the offending entry:

```
services.search.cores[0] "../escape" is not a usable Solr core directory name. Use letters, numbers, dots, underscores, and dashes. "." and ".." are reserved, and "/" and "\" are not allowed. Rename the core to a plain directory name.
```

### Run Solr as another user

`precreate-core` writes into `/var/solr`, and that path is a named volume. The container runs as whatever `user:` you set, so the planned user has to own that tree or the first start dies on a permission error before Solr ever listens.

The image ships `/var/solr` owned by `solr` (uid `8983`), so `user: solr`, `user: "8983"`, `user: root`, and no `user:` at all just work. Nothing changes for those.

For any other user, Lando prepares the tree in the image before the volume exists: one root build step creates `/var/solr` and chowns it to your user. A container runtime seeds a fresh named volume from the image directory at that path, ownership included, so your user owns the data tree from the first start.

```yaml
services:
  search:
    type: solr
    user: "10001"
    cores: [default, products]
```

Two things to know:

- It only applies to a **new** volume. A volume created by an earlier start keeps the ownership it already has. Remove the volume (`lando destroy` with volume purge) to get a fresh one that is seeded again.
- Lando has to know your user exists in the image. A numeric uid always works, because a uid can always be given ownership, even when you supply your own `image:` or `build:`. A name the `solr` type doesn't declare (`solr` and `root` are the only two) is refused. A named `user:` on a service that supplies its own `image:` or `build:` is refused too, because that image is no longer the one the type described. The refusal is a `DataTreeOwnershipCapabilityError` that names the service, the data tree (`/var/solr`), and the Landofile option to change. Fix it with a numeric uid, or use `root`.

## Hit the admin API

Expose a tooling alias that curls the Solr admin API after start to confirm the HTTP surface is reachable:

```sh
lando solr-cli /solr/admin/info/system
```

That's the same endpoint the built-in healthcheck curls (`curl -sf http://localhost:8983/solr/admin/info/system`) before Lando reports `post-start`.

## Ship your own core config

Set `config.dir` to an app-relative directory that holds your `solrconfig.xml`, `managed-schema`, and friends:

```yaml
services:
  search:
    type: solr
    cores: [default, products]
    config:
      dir: ./config/solr
```

Lando mounts that directory read-only at `/etc/lando/solr/conf` inside the container. When the service starts, it copies the contents into `/var/solr/data/<core>/conf` for each core you declared, so `default` and `products` above both get the same config.

The path has to stay inside the app root. Absolute paths, paths that climb out of the app root, and symlinks that point outside it are rejected when Lando plans the app, before anything starts.

That copy is an overlay, not a replace. `cp -a` lays your files over whatever `precreate-core` just wrote into `/var/solr/data/<core>/conf`, so anything you ship wins and anything you leave out keeps the stock file. It runs on every start, so an edited file lands on the next `lando start`. If the copy fails, the container exits instead of serving a half-configured core.

Lando identifies that directory by its contents, not by where it sits. Move the directory and the service keeps its build key. Change a file inside it and the service rebuilds. An empty directory is a legal overlay and hashes to one fixed identity, so two empty directories in different places give the same build key, and the first file you add changes it.

The copy runs as the planned `user:`, so the same ownership rule as [precreating cores](#run-solr-as-another-user) applies: your user has to own `/var/solr`, and Lando arranges that for a numeric uid on a fresh volume. The overlay side has its own requirement. The host directory is bind-mounted read-only, and a non-root user still has to be able to read it. A `0700` directory on the host is not readable by uid `10001` inside the container, and the copy fails. `0755` works.

If you also set `command:` on the service, yours wins. Lando won't copy that config into each core unless your command does it.

## Pin a version

Set `image:` when `solr:9` isn't the version you want:

```yaml
services:
  search:
    type: solr
    image: solr:9.6
```
