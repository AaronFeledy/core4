# Add Node.js

Put `type: node` on the primary service to use the Node version your project
already declares. Lando reads `.nvmrc` first, then checks `package.json`
`engines.node` when it exists. Your repository is bind-mounted read-write at
`/app` by default, which is also the working directory; set `appMount: /site`
to move both:

```yaml
name: node-demo
services:
  app:
    type: node
    primary: true
```

Save the configuration as `.lando.yml`, then create `.nvmrc` beside it with this version constraint:

```text
22.11.0
```

That `.nvmrc` resolves to `node:22.11.0`. A major pin such as `22`, `24`, or
`26` selects that image channel. LTS codenames work the same way: `jod` or
`lts/jod` resolve to `node:22`, and `krypton` or `lts/krypton` resolve to
`node:24`. Lando does not define a codename alias for Node 26. The `lts` and
`lts/*` selectors resolve to `node:24`, not the floating `node:lts` Docker tag.

If `package.json` also declares `engines.node`, that range must allow the
version selected by `.nvmrc`. For a major or minor pin, it must allow the
entire selected channel, not just one release in it. Conflicting constraints
fail before Lando starts any containers.

Without `.nvmrc`, Lando chooses a complete supported major allowed by
`engines.node`. It prefers Node 24 when the range allows it; otherwise, it
chooses the highest compatible supported major.

## Run the app

The default Node keep-alive process holds the container open and exits cleanly on
SIGTERM or SIGINT. Declare an `npm` tooling alias targeting `app` before using the commands below; the Node service does not add that alias automatically. See [Run TypeScript on a Node service](./node-typescript.mdx) for a complete tooling block. Then install dependencies and start your server:

```sh
# Declare an npm tooling alias to install dependencies inside the service
lando npm install

# Run your server via a tooling alias; bind it to 3000 to be reached at the app URL
lando npm start

# Or run a one-off process directly
lando exec app -- node server.js
```

## Pass `port:` to your app

Lando uses the same port for the internal HTTP endpoint and the process environment:

| Variable | Value | Who reads it |
| --- | --- | --- |
| `PORT` | `port:`, default `3000` | Next.js, Nuxt, Remix, or your own code via `process.env.PORT` |

Your server must listen on an interface reachable from other containers, such as `0.0.0.0`.

Set `port:` to change both the endpoint and `PORT`:

```yaml
services:
  app:
    type: "node:22"
    port: 5173
    command: node server.mjs
```

An authored `environment.PORT` must be a literal integer equal to the planned port. A different or malformed value fails planning at `services.app.environment.PORT`, including values inherited from `appEnv` or env files. Set `port:` instead of overriding `PORT`.

Vite does not read `PORT`. For `port: 5173`, use `vite --host 0.0.0.0 --port 5173` in your npm script, or set the equivalent Vite configuration. Keep that port aligned when you change the Landofile.

Node has no default healthcheck or readiness probe, even with an authored `command:`. A command might be a server, an asset watcher, or a queue worker. Add `readiness:` when you want start to wait for application readiness; otherwise Lando checks that the process stays running. Use `healthcheck:` separately for ongoing native monitoring. A command string is enough, and the official `node` image ships `curl`:

```yaml
services:
  app:
    type: node
    primary: true
    command: ["node", "server.js"]
    readiness: curl -fsS http://localhost:3000/
```

## Stop cleanly

`lando stop` sends SIGTERM to the container and waits for the stop grace period before it kills the process. A Node service runs under a small init process by default, so your command does not become PID 1, where the kernel ignores a signal nobody handles. Init forwards the stop signal to the process it started and reaps orphaned children, so an unhandled SIGTERM ends Node right away instead of waiting out the grace period. Handle SIGTERM in your app when it should finish in-flight requests before it exits.

Init forwards the signal only to the process it started. A string `command:` runs under `sh -c`, and that shell receives the signal instead of your server; `npm start` and similar wrappers decide for themselves whether to pass it on. Write the command as a list, such as `["node", "server.mjs"]`, or `exec` your server from the shell, so the signal reaches it directly. You don't need `tini` or `dumb-init` in the image for this; Lando already runs init in front of your command.

The default follows the service's Lando base, not its image name, so it also applies when you set a custom `image:` on a Node service. Set `init: false` when your image supplies its own init or its process must run as PID 1; that process then owns signal handling and child reaping, and Lando no longer needs an init helper for that service:

```yaml
services:
  app:
    type: "node:22"
    init: false
    command: ["node", "server.mjs"]
```

`init` accepts the booleans `true` and `false`. It also accepts quoted strings such as `"true"`, `"false"`, `"on"`, `"off"`, `"yes"`, `"no"`, `"1"`, and `"0"`, ignoring letter case. Other values fail planning before Lando starts a container.

After a stop, the `stopped:` line repeats the exit code the runtime reported beside each service, such as `app (exit 143)` for a server that ended on SIGTERM, and `lando stop --format=json` carries the same facts under `result.shutdownObservations`. Those are runtime facts, not proof that your handler finished its work; [Read what stop reports](../tutorial/app-lifecycle.mdx#read-what-stop-reports) explains each value and its limits.

## Install global npm packages

Tools your whole image needs go on `globals`, a map of package name to version specifier:

```yaml
services:
  app:
    type: "node:22"
    globals:
      yarn: "1.22.4"
      gulp-cli: "latest"
```

They install with `npm install -g` while the image is baked, so `gulp` is on `PATH` without an extra `lando npm install -g` every rebuild.

Official Node 26 images do not include Yarn or Corepack. If your project
needs Yarn 1, add `globals: { yarn: "1.22.22" }` to the Node service. You can
install pnpm through `globals` too, using the version your project needs.
Official Node 22 and Node 24 images include Yarn 1, but not pnpm. See the
[Node image's package-manager notes](https://github.com/nodejs/docker-node#yarn-v1-classic-bundling) and
[Corepack installation guidance](https://github.com/nodejs/corepack#default-installs).

Lando normalizes the map first: names and version specifiers are validated at plan time, and packages install in sorted order. Reordering the YAML does not rebuild the image. Adding, removing, or re-pinning a package does, on the next `lando start`, because the normalized list is part of the image build key.

Specifiers are ordinary npm spellings such as `1.22.4`, `^17.0.0`, `>=5 <6`, or a dist-tag like `latest`. Anything else fails at plan time, before any container work, naming the package that broke.

`globals` applies to a custom `image:` too, so the image you bring needs `npm`.

## Read a nested package

Set `packageRoot` when the Node package lives below the app root. This changes
only where Lando reads `.nvmrc` and `package.json`. It does not change mounts or
the container working directory.

```yaml
services:
  app:
    type: node
    packageRoot: apps/web
```

The directory must exist inside the app root. Lando rejects absolute paths,
parent traversal, and symbolic links for inference inputs.

For a PHP app whose theme lives under the webroot, add a Node sidecar and set
tooling `dir:`. See [Compile PHP theme assets with Node](./node-theme-assets.mdx).

## Pin the service type

Use an explicit type when the Landofile, rather than project files, should own
the version. Lando supports `node:lts`, `node:22`, `node:24`, and `node:26`.
`type: node:lts` selects `node:24`. Lando controls that alias; a change to the
upstream `node:lts` Docker tag does not change your selected major version.

```yaml
services:
  app:
    type: node:lts
```

```yaml
services:
  app:
    type: "node:24"
    image: node:24-bookworm
```

Custom `image:` values work with explicit Node types. Don't combine `image:`
with bare `type: node`; inference must choose the image without a second source
of truth.
