# Add Node.js

Put `type: node` on the primary service to use the Node version your project
already declares. Lando reads `.nvmrc` first, then checks `package.json`
`engines.node` when it exists. Your repository is bind-mounted read-write at
`/app` by default, which is also the working directory; set `appMount: /site`
to move both:

```yaml
name: node-demo
services:
  app:
    type: node
    primary: true
```

Save the configuration as `.lando.yml`, then create `.nvmrc` beside it with this version constraint:

```text
22.11.0
```

That `.nvmrc` resolves to `node:22.11.0`. A major pin such as `22`, `24`, or
`26` selects that image channel. LTS codenames work the same way: `jod` or
`lts/jod` resolve to `node:22`, `krypton` or `lts/krypton` resolve to
`node:24`, and `lithium` or `lts/lithium` resolve to `node:26`.

The `lts` and `lts/*` selectors resolve to `node:26`, the current LTS line,
which is also what nvm installs for `lts/*`. As in nvm, `lts/-1` and `lts/-2`
step back one and two LTS lines, to `node:24` and `node:22`. Lando pins these
selectors to a major rather than the floating `node:lts` Docker tag, so a new
Node LTS release doesn't change your selected major version until a Lando
release moves the alias. If your project uses Yarn or pnpm, see
[Use your project's package manager](#use-your-projects-package-manager).

If `package.json` also declares `engines.node`, that range must allow the
version selected by `.nvmrc`. For a major or minor pin, it must allow the
entire selected channel, not just one release in it. Conflicting constraints
fail before Lando starts any containers, and the error names the `.nvmrc` or
`package.json` to fix.

Without `.nvmrc`, Lando chooses a complete supported major allowed by
`engines.node`. It prefers Node 26, the current LTS, when the range allows it;
otherwise, it chooses the highest compatible supported major. For example,
`>=22` selects `node:26`, and `^24` selects `node:24`.

## Run the app

Without `command:`, the default Node keep-alive holds the container open but
doesn't start your server. If nothing is listening on your Node port, `lando
start` reports an `expected` URL check without warning or retrying. The route
stays available for when you start serving. Add `command:` to start the server
automatically, or use the `lando npm` and `lando npx` commands the Node service
adds. Run these from the app directory on your host:

```sh
# Install dependencies inside the service
lando npm install

# Run your server; bind it to 3000 to be reached at the app URL
lando npm start

# Or run a one-off process directly
lando exec app -- node server.js
```

A project that declares Yarn or pnpm gets `lando yarn`, or `lando pnpm` and
`lando pnpx`, instead. See
[Run your package manager from the host](#run-your-package-manager-from-the-host).

## Pass `port:` to your app

Lando derives `PORT` from `port:` for the internal HTTP endpoint; see the [service listener reference](../../reference/service-listeners.mdx#node) for defaults and variables. Next.js, Nuxt, and Remix read `PORT`, and your own server can read `process.env.PORT`.

Your server must listen on an interface reachable from other containers, such as `0.0.0.0`.

Set `port:` to change both the endpoint and `PORT`:

```yaml
services:
  app:
    type: "node:22"
    port: 5173
    command: node server.mjs
```

An authored `environment.PORT` must be a literal integer equal to the planned port. A different or malformed value fails planning at `services.app.environment.PORT`, including values inherited from `appEnv` or env files. Set `port:` instead of overriding `PORT`.

Vite does not read `PORT`. For `port: 5173`, use `vite --host 0.0.0.0 --port 5173` in your npm script, or set the equivalent Vite configuration. Keep that port aligned when you change the Landofile.

Node has no default healthcheck or readiness probe, even with an authored `command:`. A command might be a server, an asset watcher, or a queue worker. Add `readiness:` when you want start to wait for application readiness; otherwise Lando checks that the process stays running. Use `healthcheck:` separately for ongoing native monitoring. A command string is enough, and the official `node` image ships `curl`:

```yaml
services:
  app:
    type: node
    primary: true
    command: ["node", "server.js"]
    readiness: curl -fsS http://localhost:3000/
```

## Stop cleanly

`lando stop` sends SIGTERM to the container and waits for the stop grace period before it kills the process. A Node service runs under a small init process by default, so your command does not become PID 1, where the kernel ignores a signal nobody handles. Init forwards the stop signal to the process it started and reaps orphaned children, so an unhandled SIGTERM ends Node right away instead of waiting out the grace period. Handle SIGTERM in your app when it should finish in-flight requests before it exits.

Init forwards the signal only to the process it started. A string `command:` runs under `sh -c`, and that shell receives the signal instead of your server; `npm start` and similar wrappers decide for themselves whether to pass it on. Write the command as a list, such as `["node", "server.mjs"]`, or `exec` your server from the shell, so the signal reaches it directly. You don't need `tini` or `dumb-init` in the image for this; Lando already runs init in front of your command.

The default follows the service's Lando base, not its image name, so it also applies when you set a custom `image:` on a Node service. Set `init: false` when your image supplies its own init or its process must run as PID 1; that process then owns signal handling and child reaping, and Lando no longer needs an init helper for that service:

```yaml
services:
  app:
    type: "node:22"
    init: false
    command: ["node", "server.mjs"]
```

`init` accepts the booleans `true` and `false`. It also accepts quoted strings such as `"true"`, `"false"`, `"on"`, `"off"`, `"yes"`, `"no"`, `"1"`, and `"0"`, ignoring letter case. Other values fail planning before Lando starts a container.

After a stop, the `stopped:` line repeats the exit code the runtime reported beside each service, such as `app (exit 143)` for a server that ended on SIGTERM, and `lando stop --format=json` carries the same facts under `result.shutdownObservations`. Those are runtime facts, not proof that your handler finished its work; [Read what stop reports](../tutorial/app-lifecycle.mdx#read-what-stop-reports) explains each value and its limits.

## Use your project's package manager

Declare the exact Yarn or pnpm release once in `package.json`. Every bundled
Node type (`node`, `node:lts`, `node:22`, `node:24`, and `node:26`) installs
that release into the service image when Lando builds it, and adds the
matching `lando` command. You don't need a `globals` entry, a tooling block,
or Corepack.

This Landofile pins the Node version and runs the service as the non-root
`node` user:

```yaml
name: my-app
services:
  app:
    type: node:lts
    primary: true
    user: node
```

Put the package manager in the `package.json` beside it:

```json
{
  "name": "my-app",
  "private": true,
  "packageManager": "yarn@4.18.1"
}
```

Start the app, then run Yarn the way you would on your host, with `lando` in
front. Run these from the app directory on your host:

```sh
lando start
lando yarn --version
lando yarn install
```

`lando yarn --version` prints `4.18.1`. Those last two commands check
different things. The first proves the manager itself: it's already in the
image, so it runs under any service `user:` and needs no network. The second
downloads your dependencies, which still needs network access.

If your project uses `devEngines` instead, Lando reads that field too. This
`package.json` gives you pnpm 9.15.0 with the same Landofile:

```json
{
  "name": "my-app",
  "private": true,
  "devEngines": {
    "packageManager": {
      "name": "pnpm",
      "version": "9.15.0"
    }
  }
}
```

```sh
lando pnpm --version
```

That prints `9.15.0`.

### Use Yarn Plug'n'Play

Pin a supported Yarn Berry release in `package.json`, for example
`"packageManager": "yarn@4.5.3"`. With the default Plug'n'Play (PnP) linker or
`nodeLinker: pnp`, Lando leaves `/app/node_modules` in the app bind instead of
mounting a volume there. That path is your host directory, so
`lando yarn install` can delete an existing host `node_modules`. Lando does not
change how `.yarn/` is mounted.

Lando reads `nodeLinker` from `.yarnrc.yml` at `packageRoot` and, for a nested
package, at the app root; the nearest one wins. It ignores other ancestor configs
and `YARN_NODE_LINKER`, so set the linker in one of those two files to keep the
mount plan in step with Yarn. Yarn Classic and Berry with
`nodeLinker: node-modules` or `nodeLinker: pnpm` keep the default volume.
Explicit `appMount.excludes` and `appMount.includes` take precedence over this default.

After changing linkers, run `lando start` for the whole app to apply the new
mount plan, then run `lando yarn install` if your service does not install on start.

### Run your package manager from the host

A bundled Node service adds tooling commands for the manager its
`package.json` selects:

| `package.json` declares | Commands |
| --- | --- |
| pnpm | `lando pnpm`, `lando pnpx` |
| Yarn | `lando yarn` |
| npm, or no package manager | `lando npm`, `lando npx` |
| Bun | none |

Each command runs inside that service and passes everything after its name to
the manager, so `lando pnpm add -D vitest` runs `pnpm add -D vitest`. To check
what a command runs without starting anything:

```sh
lando help pnpm --format=json
```

The `result.target.runs` entry names the service and the program.

The list follows `package.json`. Change the manager there and the next `lando`
command you run shows the new set, with no refresh step. A custom `image:` or
replacement Compose build gets no commands, because that image owns its
toolchain.

Your Landofile wins over these commands. Define `tooling.npm` yourself to
change the service, `dir:`, or command, or set a name to `false` to turn it
off:

```yaml
tooling:
  npx: false
```

#### Apps with more than one Node service

Lando adds a command only when exactly one bundled Node service claims that
name. Two npm services both claim `npm` and `npx`, so neither gets them. A pnpm
service beside a Yarn service keeps `lando pnpm`, `lando pnpx`, and
`lando yarn`, because no name collides.

When names collide, say which service you mean in the Landofile:

```yaml
services:
  web:
    type: node:lts
    primary: true
  worker:
    type: node:lts
tooling:
  npm:
    service: web
    cmd: [npm]
    wrapper: true
  worker-npm:
    service: worker
    cmd: [npm]
    wrapper: true
```

`lando exec worker -- npm install` also works without any tooling.

### Run a binary your project installed

Tools such as `vite`, `next`, or `eslint` live in your project's
`node_modules`, and each package manager runs them its own way. Start an
argv-list tooling `cmd` with `:node-local` and Lando uses the manager the
service selected:

```yaml
tooling:
  vite:
    service: app
    cmd: [":node-local", "vite"]
    wrapper: true
```

`lando vite build` then runs `pnpm exec vite build`, `yarn run vite build`, or
`npm exec --no -- vite build`. A Bun declaration and a project with no
declaration both use the npm form. None of them downloads a missing package,
so install your dependencies first. `:node-local` works on every Node
service, including one with a custom `image:`.

### Install dependencies, then start your server

A service `command` can install before it serves. Start an argv-list
`command` with `:node-install-run` and name a `package.json` script:

```yaml
services:
  app:
    type: node:lts
    primary: true
    command: [":node-install-run", "start"]
```

Each time the container's process starts, Lando runs the selected manager's
install (`npm install`, `pnpm install`, or `yarn install`) and then runs the
`start` script through that same manager. Extra items after the script name
reach the script as arguments. If the install fails, the script never starts, and
`lando logs --service app` shows the manager's error. When the service stops,
Lando sends the stop signal to every process the script started, not just the
manager, and waits for them to exit, so your server's shutdown handler runs.

`:node-install-run` exists only on a bundled Node type whose `package.json`
declares npm, pnpm, Yarn, or no package manager. A service with a custom
`image:` or replacement build, or a project that declares Bun, doesn't get
it, and planning fails at `services.app.command` if you use it there. Write
that service's own install and start command instead.

Both markers are launchers.
[Run a command through the project's toolchain](../tooling/flags-and-args.mdx#run-a-command-through-the-projects-toolchain)
covers where a marker is recognized and how a bad one fails.

### Where the release comes from

Lando downloads the Yarn or pnpm release on your host, not inside the image
build. The download goes through Lando's own HTTP client, so it uses the npm
registry, proxy, and certificate authorities you configured for Lando. Behind
a corporate proxy, set those up once as described in
[Trust a corporate CA and proxy](../config/corporate-network-trust.mdx).

Lando verifies the release against the registry's integrity value before it
copies anything into the image. Verified releases stay in Lando's source
cache, so the registry is contacted once per release:

| Situation | Needs the registry? |
| --- | --- |
| First build with a release | Yes |
| Rebuild with that release already cached | No |
| Start an app whose image is already built | No |
| `lando yarn install`, `lando pnpm install` | Yes, for your dependencies |

Lando doesn't install or run Corepack for any of this.

Three limits apply:

- Yarn 2.0.0 through 2.4.0 fail planning. Upgrade to 2.4.1 or later, or bring
  your own image as described in [Pin the service type](#pin-the-service-type).
- Global installs through the manager Lando installed, such as `pnpm add -g`
  and `yarn global add`, aren't supported. Put image-wide tools in
  [`globals`](#install-global-npm-packages).
- Yarn Classic before 1.22.21 can still refuse to run in a project whose
  `package.json` names a different manager.

### Pin an exact version

Only the Yarn or pnpm declaration that wins must name one exact release, such
as `yarn@4.18.1` or `pnpm@9.15.0`.
[Know which declaration wins](#know-which-declaration-wins) explains how Lando
picks it. An integrity suffix is fine: with `pnpm@9.15.0+sha512.<hex>`, the
download is also checked against that hash. For pnpm and Yarn 1, the hash
covers the release tarball from the npm registry. For Yarn 2 and later, it
covers the release's `bin/yarn.js`. A release that doesn't match fails the
build.

In the winning declaration, ranges such as `^9`, tags such as `latest`, a `v`
prefix, and URLs fail planning before any container starts. The error names
the file and the field to fix. Because the cause is a project file, the
message leads with that file, for example `package.json has invalid values`,
or `apps/web/package.json has invalid values` for a nested package. It doesn't
blame the Landofile.

### Know which declaration wins

Lando reads `package.json` in the service's
[`packageRoot`](#read-a-nested-package) first, then the one at the app root.
The first file that declares a manager wins, so a monorepo can declare it once
at the root. Inside one file, top-level `packageManager` wins.

When one file has both fields, `devEngines.packageManager` stops being a pin
and becomes a compatibility check on the top-level one. Its `version` can be
left out, or it can be a range that admits the pinned release:

```json
{
  "packageManager": "pnpm@9.15.0",
  "devEngines": {
    "packageManager": {
      "name": "pnpm",
      "version": "^9"
    }
  }
}
```

A different manager name, or a range that excludes the pin, fails planning.
Set `onFail` to `warn` or `ignore` on that `devEngines` entry and Lando accepts
the mismatch. It doesn't print a warning.

Lando opens both files before it picks one. An app-root `package.json` that is
unreadable, too large, a symbolic link, or not a regular file fails planning
even when the nested file would win. A readable one that loses is never parsed
for a manager.

Two manager names get no install. They still end the search, so Lando doesn't
fall back to the app root:

- `npm`: the service keeps the npm that ships with the Node image.
- `bun`: the Node service doesn't provision Bun. Lando accepts the declaration
  and installs nothing for it.

### Change the version

Edit the pin in `package.json` and run `lando start`. Lando rebuilds the image
with the new release. Editing other `package.json` fields, such as `scripts`,
doesn't rebuild it.

Until you run `lando start`, the running service still has the release it was
built with. `lando exec` and tooling commands notice the difference, print a
warning, and then run your command anyway:

```text
Service app was built with pnpm@9.15.0, but package.json now selects pnpm@10.19.0. Run `lando start` to rebuild it.
```

Adding a pin, removing one, and changing its manager, version, or integrity
hash all count. With `--format=json`, the same warning is in the envelope's
`warnings` array with code `LANDO_NODE_PACKAGE_MANAGER_STALE`, the service
name under `context.service`, and the built and declared releases under
`context.built` and `context.declared`.

Lando publishes its own `yarn` or `pnpm` launcher in the service for the
manager you selected, and that launcher always runs the release Lando planned.
It turns off pnpm's switch to the version a project asks for, and it ignores a
vendored Yarn `yarnPath`. `yarn set version`, `corepack`, `npx corepack`, and
binaries inside your project are separate entry points that the launcher
doesn't control, so change versions through `package.json` and `lando start`.

## Install global npm packages

Tools your whole image needs go on `globals`, a map of package name to version specifier:

```yaml
services:
  app:
    type: "node:22"
    globals:
      gulp-cli: "latest"
```

They install with `npm install -g` while the image is baked, so `gulp` is on `PATH` after every rebuild without a manual install.

Lando normalizes the map first: names and version specifiers are validated at plan time, and packages install in sorted order. Reordering the YAML does not rebuild the image. Adding, removing, or re-pinning a package does, on the next `lando start`, because the normalized list is part of the image build key.

Specifiers are ordinary npm spellings such as `1.22.4`, `^17.0.0`, `>=5 <6`, or a dist-tag like `latest`. Anything else fails at plan time, before any container work, naming the package that broke.

Keep Yarn and pnpm out of `globals` on a bundled Node type. The pin in
`package.json` already
[installs the manager](#use-your-projects-package-manager). A `globals.yarn`
or `globals.pnpm` entry with the same version as that pin is redundant, and
Lando skips it without a message. A different version fails planning with
`Landofile has invalid values`. That error points at
`services.<name>.globals.<manager>` in the Landofile, because removing the
entry is the fix. Keep the pin in `package.json`.

`globals` applies to a custom `image:` too, so the image you bring needs `npm`.
Lando installs no package manager and adds no tooling commands for a custom
image, so `globals` is where Yarn or pnpm goes there. See [Pin the service type](#pin-the-service-type).

## Read a nested package

Set `packageRoot` when the Node package lives below the app root. It defaults
to `.` and selects where Lando looks for `package.json` and `.yarnrc.yml`.
It does not move the app mount or change the container working directory.

```yaml
services:
  app:
    type: node
    packageRoot: apps/web
```

With bare `type: node`, Lando infers the Node version from `.nvmrc` and
`engines.node` in that directory. `packageRoot` works with explicit types too.
There it only chooses where Lando looks for the package manager:

```yaml
services:
  app:
    type: "node:22"
    packageRoot: apps/web
```

Either way, Lando reads `apps/web/package.json` for the package manager first,
then the app-root `package.json`.

`packageRoot` must be a directory inside the app root. Lando rejects absolute
paths, paths that escape the app root, and symbolic links for these project
files.

`lando npm` and the other package-manager commands start in the directory
that matches where you ran them, not in `packageRoot`. Run them from
`apps/web` on your host, or define the command with a `dir:`.

For a PHP app whose theme lives under the webroot, add a Node sidecar and set
tooling `dir:`. See [Compile PHP theme assets with Node](./node-theme-assets.mdx).

## Pin the service type

Use an explicit type when the Landofile, rather than project files, should own
the version. Lando supports `node:lts`, `node:22`, `node:24`, and `node:26`.
`type: node:lts` selects `node:26`. Lando controls that alias; a change to the
upstream `node:lts` Docker tag does not change your selected major version.

```yaml
services:
  app:
    type: node:lts
```

Project files never change an explicit version. `type: "node:22"` stays on
Node 22 even when `.nvmrc` or `engines.node` asks for something else. Lando
still reads `package.json` for the
[package manager](#use-your-projects-package-manager).

Custom `image:` values work with explicit Node types:

```yaml
services:
  app:
    type: "node:24"
    image: node:24-bookworm
```

A custom `image:`, or a Compose `build.context` that replaces the image, owns
its own toolchain. Lando reads no Node project files for that service,
installs no package manager into it, and adds no `lando npm`, `lando yarn`, or
`lando pnpm`. Bake Yarn or pnpm into the image, or add it through
[`globals`](#install-global-npm-packages), then declare the tooling you want
in the Landofile.

Bare `type: node` can't be combined with `image:` or a replacement Compose
build, and planning fails if you try. Use an explicit Node type with a custom
image or replacement Compose build, and remove `packageRoot`; Lando rejects it
when your build owns the toolchain.
