# Add Node.js

Put `type: node:22` on the primary service. Node has no bare `type: node` alias, so pin a version.
Lando currently supports `node:lts` and `node:22`, and derives the default
image (`node:22`) from the version you pin. Your repository is bind-mounted
read-write at `/app`, which is also the working directory:

```yaml
name: node-demo
services:
  app:
    type: "node:22"
    primary: true
```

## Run the app

The default keep-alive command holds the container open so you can install
dependencies and start your server via tooling:

```sh
# Declare an npm tooling alias to install dependencies inside the service
lando npm install

# Run your server via a tooling alias; bind it to 3000 to be reached at the app URL
lando npm start

# Or run a one-off process directly
lando exec app -- node server.js
```

The default HTTP port the service exposes is `3000`.

## Install global npm packages

Tools your whole image needs go on `globals`, a map of package name to version specifier:

```yaml
services:
  app:
    type: "node:22"
    globals:
      yarn: "1.22.4"
      gulp-cli: "latest"
```

They install with `npm install -g` while the image is baked, so `gulp` is on `PATH` without an extra `lando npm install -g` every rebuild.

Lando normalizes the map first: names and version specifiers are validated at plan time, and packages install in sorted order. Reordering the YAML does not rebuild the image; adding, removing, or re-pinning a package does, because the normalized list is part of the image build key.

Specifiers are ordinary npm spellings such as `1.22.4`, `^17.0.0`, `>=5 <6`, or a dist-tag like `latest`. Anything else fails at plan time, before any container work, naming the package that broke.

`globals` applies to a custom `image:` too, so the image you bring needs `npm`.

## Pin a version

Pin a different supported Node version, or set `image:` to use a custom
Node base image:

```yaml
services:
  app:
    type: node:lts
```

```yaml
services:
  app:
    type: "node:22"
    image: node:22-bookworm
```
