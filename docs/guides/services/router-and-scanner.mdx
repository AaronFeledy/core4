# Turn the router off and tune the post-start URL scanner

Lando starts a shared router for every app that has routes and, once the app is up, probes each published HTTP and HTTPS URL to make sure something answers. You can configure these behaviors separately. Turn the router off when you only want host ports, and tune or disable the scanner per service when the default probe doesn't fit.

```yaml
name: router-and-scanner-demo
router:
  enabled: false
services:
  web:
    type: "nginx"
    primary: true
    scanner:
      path: /healthz
proxy:
  web:
    - web.router-and-scanner-demo.lndo.site
```

Save the example in `.lando.yml`, then run these commands from the app directory:

```sh
lando app:config:lint
lando start
lando info
```

With `router.enabled: false`, the Host connections `lando info` prints for `web` are the host ports it publishes, and its App Network address, `http://web:80`, is still listed for other services in the app. The `web.router-and-scanner-demo.lndo.site` route stays in the Landofile and still appears as a route connection, marked inactive and not published, with no hyperlink. Lando does not publish it while the router is off.

## Turn the router off

```yaml
router:
  enabled: false
```

When the router is off, Lando skips two things at start: it doesn't launch the shared router, and it doesn't hand the app's routes to it. Everything else runs as usual. Services still get their host ports, `lando ssh` and `lando exec` still work, and `lando info` still prints the host ports and App Network addresses that exist. What you lose is the `*.lndo.site` hostnames: their route connections stay listed so you can see what is configured, but they are inactive and nobody serves them.

`lando open` and `lando share` follow the same rule. Neither hands you a hostname nobody serves: they reach for a published host port instead, and when there is nothing left to reach, `lando open` says the router is off rather than telling you to declare the route you already declared.

The routes you declared in `services.<name>.routes` or top-level `proxy:` aren't deleted or rewritten. They're simply never published. Set `enabled: true` (or remove the key) and the next `lando start` publishes them again.

The rest of the `router:` block works the same whether or not you touch `enabled`:

| Key | What it does |
| --- | --- |
| `enabled` | Start the shared router and publish this app's routes. Default `true`. |
| `bindAddress` | Host address the router listens on. Global-only (`config.yml` or `LANDO_ROUTER_BIND_ADDRESS`); a Landofile value is ignored and lint warns. |
| `httpPort` | Host port for plain HTTP. |
| `httpsPort` | Host port for HTTPS. |
| `httpFallbacks` | Extra HTTP ports to try when `httpPort` is taken. |
| `httpsFallbacks` | Extra HTTPS ports to try when `httpsPort` is taken. |

## Use the route's scheme on fallback ports

```sh
lando info
```

Open the complete URL it prints, including a fallback port such as `:8443`.
Shorthand routes and object routes without `scheme` publish **HTTPS only**.
An HTTP request to that hostname on the HTTP listener (for example `:8080`)
receives the diagnostic HTTP 404 when no HTTP route matches. That is expected,
not a broken backend. Use the HTTPS URL, or explicitly set `scheme: http` or
`scheme: both` if the app should accept plain HTTP. Lando does not implicitly
redirect an HTTPS-only route from HTTP.

```yaml
services:
  web:
    type: nginx
    routes:
      - hostname: web.example.lndo.site
        scheme: both
```

The HTTP and HTTPS listeners may use different fallback ports. Neither port
changes the selected backend endpoint. See [route identity and ordering](../proxy/route-shorthand.mdx#choose-which-overlapping-route-wins)
when the same host serves several backends or paths.

## Resolve `router.enabled`

The value resolves through normal config precedence. Last one wins:

- Built-in default: `true`.
- Your global config: `router.enabled`.
- The app's Landofile: `router.enabled`.

So a global `router.enabled: false` turns the router off for every app on the machine, and a single app can opt back in with `router.enabled: true` in its own Landofile. The reverse works too: leave the global default alone and disable the router for the one app that doesn't want it.

You don't need any of that for an app with no routes. A database-only, worker, or build app never starts the router, and its `lando start` only withdraws routes it published earlier.

## Tune the scanner per service

Once the app is up, `lando start` checks every HTTP and HTTPS URL each service publishes before returning. Rows say what your app or web server returned. Your app's own answer isn't a Lando warning; only Lando-side problems enter command warnings. A failed check doesn't fail `lando start`. Cancelling during the check still interrupts start and closes its in-flight requests.

The app check has its own progress tree, with one row per URL. Each row spins while
its probe runs and shows the attempt number and reason while retrying. Settled
rows show the HTTP status or failure reason. A `•` row is your app's own answer,
not a Lando warning. A `!` row with `unreachable` identifies a Lando-side problem;
a web-server error row says what the web server returned without adding a command warning.
The tree finishes with the number of URLs that answered, or counts of errors and unreachable URLs.
Full `lando restart` and `lando rebuild` show the same scan progress. Services with
`scanner: false` get no scan row, and an app with no scan targets gets no empty tree.

The scanner skips `tcp://`, `udp://`, and database connections; `lando info` still lists them. A Compose port mapping such as `9080:9080` describes the transport, not the application protocol, so Lando reports it as `tcp` rather than guessing HTTP. If you know that port serves HTTP, declare it with `protocol: http` in an explicit `endpoints:` entry so the scanner and `lando open` pick it up, or check it directly:

```sh
curl --fail http://localhost:9080/
```

Without an endpoint-specific default, the probe hits `/` and accepts any 2xx.
Service features can supply different paths for different HTTP listeners: for
example, MinIO's API uses `/minio/health/live` while its console uses `/`. This
avoids treating a normal unauthenticated S3 root response as a failed health
probe. The scanner does not accept `401` or `403` globally.

Explicit global settings override endpoint defaults, and explicit service
settings override global values. Setting `path: /` or `okCodes: []` is an
override too, not an omitted value. The default retry budget remains two retries
after the first attempt, with a 20-second deadline per URL. Change those settings
under `services.<name>.scanner`:

```yaml
services:
  app:
    type: "node:22"
    primary: true
    scanner:
      path: /healthz
      okCodes: [200, 204]
      retries: 1
      timeout: 2000
```

| Key | Default | What it does |
| --- | --- | --- |
| `path` | Endpoint default, otherwise `/` | Explicit path used for every scanned HTTP listener in this service. A route's own `pathPrefix` stays in front of it. |
| `okCodes` | Endpoint default, otherwise none | Extra HTTP statuses to accept beyond 2xx. An explicit empty list clears endpoint/global extras. |
| `retries` | `2` | Retries after the first attempt, so the default is three tries. |
| `timeout` | `20000` | Deadline in milliseconds for the whole probe of one URL, retries included. |

Every key is optional. Set only the one you need. A `retries` below `0` fails lint before anything starts, so you find out at `lando app:config:lint` rather than after a start.

Run `lando start`, then `lando info` to check the published URLs after changing these settings.

The scanner sends GET requests but reads only response status and headers. It doesn't download the body, so a large download or an endless response doesn't hold up a probe after the headers arrive. At most four URLs are probed at once; extra URLs wait their turn. The timeout budget starts when a URL's probe starts, not while it's queued. Each attempt has a five-second ceiling, capped by the URL's remaining overall budget. Deadline warnings report the measured elapsed time, including retries and waits, rather than repeating the configured timeout.

Loopback targets (`localhost`, IPv4 loopback addresses, and `::1`) connect directly instead of going through an outbound HTTP proxy. Other targets follow the normal proxy and `NO_PROXY` settings, with the same custom CA trust. A `*.lndo.site` name isn't a blanket proxy bypass: configure `NO_PROXY` for local route names if your proxy shouldn't receive them.

If a probe fails, the message Lando prints has already been through redaction, so a URL with credentials in it won't leak them into your terminal or logs.

When the router can't reach a service, or the connection fails, a warning can include the service's observed TCP bindings and configuration advice:

```text
Lando could not reach http://app.example.test/: the router could not reach app. No TCP listener observed on 3000; observed ports: none. Make app listen on 3000. Your application owns this listener. Lando sets `PORT` to 3000; make its server listen on 0.0.0.0:3000.
```

Lando reads that evidence once per service per scan, only when the failed URL targets the service's expected listener. A missing router route, an app or web-server response, or a ready URL doesn't trigger the read. Secondary listeners don't inherit evidence for a different port. If the socket table can't be read, the warning keeps its original reachability message without guessing. These findings remain warnings, not a new startup gate; structured start results include the evidence in the affected `checks` entries as `listener`. See [Inspect a failed start](./wait-for-your-app.mdx#inspect-a-failed-start) for the listener findings and ownership advice.

## Turn scanning off

Skip one service:

```yaml
services:
  web:
    type: "nginx"
    scanner: false
```

Skip every service on this machine by setting the same key in your global config:

```yaml
scanner: false
```

Global `scanner: false` disables scanning for every service. A service object or
an endpoint default cannot opt back in while that global switch is off. Remove
the global `false` to resume scanning, then use service-level `scanner: false`
for individual exceptions. This keeps an app's configuration from silently
re-enabling requests you disabled for the whole machine.
