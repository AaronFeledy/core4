# Keep a service home across rebuilds and reach your host

A service's home directory is where tools drop their caches and credentials: `~/.npm`, `~/.composer`, `~/.ssh`, shell history. Lando puts that directory on a persistent store so a rebuild does not throw it away. Home persistence is on by default whenever Lando knows where the planned user's home is. When it doesn't, for example because you supplied the image yourself, Lando plans no home store and moves on; set `home.path` if you want one anyway.

```yaml
name: home-and-host-demo
services:
  app:
    type: "node:22"
    primary: true
    user: node
  cache:
    type: compose
    image: redis:7-alpine
    home: false
```

Save the example in `.lando.yml`, then run these commands from its directory:

```sh
lando app:config:lint
lando start
```

The `app` service gets a persistent home because `node:22` ships a known image and Lando knows the `node` user lives in `/home/node`. The `cache` service supplies its own image, so Lando would plan no home store for it anyway; `home: false` says so on purpose, because a Redis container has no home worth keeping.

## Check what Lando keeps

`lando info` shows the plan, so it answers the question before the app has ever started. Run it from the app directory:

```sh
lando info
lando info --format=json
```

In the human view, the retained home mount is labeled `(home)` next to the other stores, for example `/root (home), /data (store)`. A service whose home Lando can't place gets a `home` row instead, such as `not kept automatically · image comes from your Landofile · set services.web.home.path to keep one`. The other two reasons read `<type> doesn't declare image users` and `<type> doesn't know where <user>'s home is`.

In JSON, each entry under `services[]` carries a `home` object with one of four states:

| `state` | Meaning | Extra fields |
| --- | --- | --- |
| `persisted` | Lando generated a home store | `target`, `store`, `user` |
| `authored` | You already mount something at the home path, so Lando generates nothing | `target`, `mount` (`volume`, `bind`, or `tmpfs`) |
| `disabled` | `home: false` | none |
| `unknown` | Lando can't place the home | `reason` (`custom-image`, `no-identity`, `undeclared-user`), `user` when known |

## When Lando knows where home is

Catalog service types declare the users inside the image they ship and where each of those users lives. Lando picks the home for whichever user the service actually runs as, which is the one you set with `services.<name>.user`, or the image's own default when you set nothing.

| Your service | What happens |
| --- | --- |
| `type: "node:22"` | Home persists at `/home/node` or `/root`, depending on `user:` |
| `type: "php:8.3"` | Home persists at `/root`. With `user: www-data`, home persists at `/var/www` |
| `type: apache` with `user: www-data` | Home persists at `/home/www-data` |
| `type: nginx` or `type: static` with `user: nginx` | No home store; that account's home is nginx's cache directory. Root keeps `/root` |
| `type: compose` | No home store; set `home.path` to keep one |
| `type: "node:22"` with a different `image:` | No home store; set `home.path` to keep one |
| A catalog type with a `user:` it does not document | No home store; set `home.path` to keep one |
| Anything with `home: false` | No automatic home store; storage and mounts you declare still apply |

The php image ships `/var/www` owned by root. Lando creates it for `www-data` in a root build step, so the fresh volume starts owned by `www-data` and the account can write to it from the first start.

### One volume per user

The store belongs to that one service in that one app, and to the user it was planned for. Its name is `lando-<app>-<service>-home-<user>-<8-hex digest>`; only an explicit `home.path` on a service with no known user drops the user part and gets `lando-<app>-<service>-home`. Planning the app again reuses the volume instead of stacking a second copy.

Changing `user:` changes the home. The new user gets a fresh, empty volume, and the previous user's volume stays in place with its contents, so switching back finds everything where it was. Nothing is copied between them.

When a service stops keeping its home, for example because you added your own `image:`, the next `lando start`, `lando rebuild`, or `lando restart` warns once:

```text
Service web will no longer keep its home at /home/node: its image now comes from your Landofile.
Lando leaves lando-<app>-web-home-node-<digest> untouched. To mount it at its previous location, set storage: [{ store: "<that volume>", target: "/home/node" }] under services.web in your Landofile.
```

When the home moved instead, say after a `user:` change, the warning names both volumes: `Service web will use home volume <new volume> at <target> (previously <old volume> at <old target>).` You get no warning for `home: false` or when you mount something at the home path yourself.

To reattach the old volume, declare it as storage with the name from the warning:

```yaml
services:
  web:
    type: "node:22"
    image: my-org/web:dev
    user: node
    storage:
      - store: lando-<app>-web-home-node-<digest>
        target: /home/node
```

To get rid of it instead, `lando destroy --volumes` removes the app's volumes, old homes included.

## When Lando doesn't know where home is

The moment you supply the image yourself, whether through `type: compose`, an `image:` other than the one the service type ships, or a Compose `build:` with a `context`, the service type's metadata stops describing your container. Lando will not guess a path and mount a volume over it, so it plans no home store for that service. That alone never fails planning; caches and credentials inside that home just don't survive a rebuild unless you declare storage for them.

Image references compare canonically, so repeating the image a versioned type already ships is not a custom image. With `type: "mariadb:11.4"`, both `image: mariadb:11.4` and `image: docker.io/library/mariadb:11.4` keep catalog behavior, home included. Without a version in `type:`, any `image:` counts as your own.

The same thing happens when a catalog service runs as a user the image does not document, for example `user: lando-nonexistent` on `type: apache`, and for nginx's `nginx` account, whose home is its cache directory. On nginx and static, root still keeps `/root`. `lando info` tells you which case you hit; see [Check what Lando keeps](#check-what-lando-keeps).

To keep a home Lando can't infer, name the path yourself:

```yaml
services:
  web:
    type: compose
    image: traefik/whoami:v1.10
    home:
      path: /home/whoami
```

`home.path` is right when your image does have a real user whose home you want to keep, and you know the path. `home: false` goes the other way: it turns persistence off for a service Lando would otherwise persist, which fits anything stateless such as a router, a mail catcher, or a cache.

```yaml
services:
  cache:
    type: redis
    home: false
```

## Already mounting something there?

If you already declared storage that lands on the same directory, Lando leaves it alone. Your entry keeps its own store name, scope, and ownership, and nothing is generated on top of it.

Lando normalizes every container destination to one POSIX path before comparing it, so `/home/node`, `/home/node/`, `/home//node`, and `/home/./other/../node` are all the same destination, not four. Two rules follow from that:

- A destination must be absolute. `app/data`, `.`, and `..` are refused, because Lando will not resolve a mount against a working directory it does not control.
- A destination cannot be the filesystem root. `/`, and anything that reduces to it like `/a/..`, is refused: container engines reject a mount over `/`, so Lando refuses it up front instead of promising a mount the provider will throw out.

A colon is fine in a destination. `/srv/a:b` is a legal POSIX path, so Lando keeps it and switches that mount to the provider's long syntax, because the short `source:target:mode` spelling has nowhere to put the extra colon. Authoring a colon destination as a Compose short volume string is the one place it cannot work; write it as a mount or storage object instead.

Home contents stay out of build keys. Filling up `~/.npm` will not trigger a rebuild.

## Reach your host from inside a service

Containers get `host.lando.internal` pointing at your host machine, plus `LANDO_HOST_IP` holding that name so your code does not have to hardcode it. Use it for a service you run outside Lando:

```sh
lando ssh -s app -c 'curl -sf http://host.lando.internal:5000/'
lando ssh -s app -c 'echo $LANDO_HOST_IP'
```

Both exist only when your provider says it can reach the host. A provider that cannot is not an error: you simply get neither the alias nor the variable, so check for `LANDO_HOST_IP` rather than assuming it.

Debuggers use a separate alias, `debugger.lando.internal`, which follows global `debugger.host` and defaults to the same gateway. Leave `host.lando.internal` alone when the IDE needs a different address. See [Debug PHP with Xdebug in PhpStorm](../tooling/xdebug-phpstorm.mdx).

If the request is refused, see [Reach host services and sibling stacks](../subsystems/host-services.mdx) for the bind address and `extra_hosts` names.
