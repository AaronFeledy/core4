# Keep a service home across rebuilds and reach your host

A service's home directory is where tools drop their caches and credentials: `~/.npm`, `~/.composer`, `~/.ssh`, shell history. Lando puts that directory on a persistent store so a rebuild does not throw it away. You get this without asking for it, as long as Lando knows where home actually is.

```yaml
name: home-and-host-demo
services:
  app:
    type: "node:22"
    primary: true
    user: node
  cache:
    type: compose
    image: redis:7-alpine
    home: false
```

Check it, then start:

```sh
lando app:config:lint
lando start
```

The `app` service gets a persistent home because `node:22` ships a known image and Lando knows the `node` user lives in `/home/node`. The `cache` service says `home: false` because a Redis container has no home worth keeping.

## When Lando knows where home is

Catalog service types declare the users inside the image they ship and where each of those users lives. Lando picks the home for whichever user the service actually runs as, which is the one you set with `services.<name>.user`, or the image's own default when you set nothing.

| Your service | What happens |
| --- | --- |
| `type: "node:22"` | Home persists at `/home/node` or `/root`, depending on `user:` |
| `type: "php:8.3"` | Home persists at `/root` |
| `type: compose` | Refused, because the image comes from your Landofile |
| `type: "node:22"` with your own `image:` | Refused, for the same reason |
| Anything with `home: false` | Nothing persists, nothing is refused |

The store is scoped to that one service in that one app, and it is created once. Planning the app again reuses it instead of stacking a second copy.

## When Lando refuses

The moment you supply the image yourself, whether through `image:` or a Compose `build:` with a `context`, the service type's metadata stops describing your container. Lando will not guess a path and mount a volume over it, so it stops before touching the provider:

```
Service web persists its home directory, but its image is supplied by the
Landofile, so Lando does not know which user runs it or where that user's
home is.
```

The error is `HomePathCapabilityError` and it names both ways out. Pick one:

```yaml
services:
  web:
    type: compose
    image: traefik/whoami:v1.10
    home: false
```

```yaml
services:
  web:
    type: compose
    image: traefik/whoami:v1.10
    home:
      path: /home/whoami
```

`home: false` is right for anything stateless: a router, a mail catcher, a cache. `home.path` is right when your image does have a real user whose home you want to keep, and you know the path.

You get the same refusal when you run a catalog service as a user the image does not document, for example `user: www-data` on a type that only declares `root`. Same two fixes.

## Already mounting something there?

If you already declared storage that lands on the same directory, Lando leaves it alone. Your entry keeps its own store name, scope, and ownership, and nothing is generated on top of it. A trailing slash does not fool it either, so `/home/node` and `/home/node/` are one destination, not two.

Home contents stay out of build keys. Filling up `~/.npm` will not trigger a rebuild.

## Reach your host from inside a service

Containers get `host.lando.internal` pointing at your host machine, plus `LANDO_HOST_IP` holding that name so your code does not have to hardcode it. Use it for a debugger listening on your laptop, or a service you run outside Lando:

```sh
lando ssh -s app -c 'curl -sf http://host.lando.internal:5000/'
lando ssh -s app -c 'echo $LANDO_HOST_IP'
```

Both exist only when your provider says it can reach the host. A provider that cannot is not an error: you simply get neither the alias nor the variable, so check for `LANDO_HOST_IP` rather than assuming it.
