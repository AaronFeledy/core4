# Run scheduled jobs

Add a `schedule:` list to a service and Lando runs those commands on a timer for as long as the app is up. You don't install cron in your image or keep a loop running in a terminal.

Run the commands on this page from the app directory on your host.

## Add jobs to a service

Put `schedule:` under the service whose code and tools the jobs need. Save this as `.lando.yml`:

```yaml
name: schedule-demo
services:
  appserver:
    type: "node:22"
    primary: true
    environment:
      TZ: "America/Chicago"
    schedule:
      - name: heartbeat
        every: "@every 5m"
        run: "echo heartbeat from $(hostname)"
      - name: report
        every: "0 6 * * 1-5"
        run: ["node", "--version"]
```

Each job takes these keys:

| Key | What to write |
| --- | --- |
| `name` | A name unique within the service. Start with a letter, then use letters, digits, `_`, or `-`. |
| `every` | When the job runs. See the forms below. |
| `run` | The command. A string runs through `sh -c`, so pipes and `$(...)` work. A list runs as written, with no shell. |
| `user` | Optional. The container user the job runs as. See [Choose the user](#choose-the-user). |

`every` accepts three forms:

- A 5-field cron expression, such as `"0 6 * * 1-5"` for 06:00 on weekdays.
- A named schedule: `@hourly`, `@daily`, `@midnight`, `@weekly`, `@monthly`, `@yearly`, or `@annually`.
- `@every <duration>` with a step that lines up with the clock: seconds or minutes that divide 60, or hours that divide 24. `@every 30s`, `@every 5m`, and `@every 6h` are valid.

Quote `every` values. A bare `@` or `*` at the start of a YAML value isn't a plain string.

A job starts in the service's working directory, the directory the service's own process starts in. Lando service types such as `php:*` and `node:*` start in the app mount, `/app`. A `type: compose` service uses its image's `WORKDIR`.

Keep secrets out of `run`. Lando writes job commands into the image it builds for the jobs, so a secret reference such as `${secret:API_TOKEN}` in `run` fails loading with `LandofileValidationError`. Bind the secret in the service's `environment` and read it as `$API_TOKEN` in a string `run`:

```yaml
services:
  appserver:
    environment:
      API_TOKEN: "${secret:API_TOKEN}"
    schedule:
      - name: sync
        every: "@hourly"
        run: 'curl -fsS -H "Authorization: Bearer $API_TOKEN" https://api.example.com/sync'
```

A list `run` has no shell, so the program has to read the variable from its environment itself.

`schedule:` belongs to a service. There is no top-level `schedule:` key.

Start the app:

```sh
lando start
```

The first start after you add a schedule takes longer, because Lando builds the scheduler into an image for the jobs. That build downloads the scheduler once and checks its SHA-256 before installing it. Nothing is downloaded when containers start.

`lando info` now lists a second service, `appserver-schedule`. That's the sidecar that runs the jobs.

## Run a job now

Don't wait for the clock while you're writing a job. Run it once by name:

```sh
lando schedule:run report
```

The job runs in the sidecar that schedules it, here `appserver-schedule`. A manual run is the same execution as a timed one: same container user, same working directory, same environment.

That means the app has to be started with the schedule applied. After you add a job, or change `user:` so the set of sidecars changes, run `lando restart` first. Otherwise the command fails with `PlanReplanRequiredError`. Its message names the job and the missing sidecar, and its remediation is to run `lando restart`.

Output prints when the job finishes, not line by line while it runs. The exit code of `lando schedule:run` is the job's exit code. With `--format=json`, a job that exits nonzero returns `"ok": false` and still includes `result`, with the job's `service`, `name`, `exitCode`, `stdout`, and `stderr`.

A name that no service uses fails with `ScheduleJobNotFoundError`, which lists the jobs you can run:

If two services use the same job name, the command fails with `ScheduleJobAmbiguousError`. Pass `--service` with the service the job is declared on, not the sidecar's name:

```sh
lando schedule:run report --service appserver
```

## Read a job's output

Timed runs write their output to the sidecar's log:

```sh
lando logs --service appserver-schedule
```

The sidecar is an ordinary service, so `lando exec appserver-schedule -- sh` opens a shell in it too. It is never the app's primary service.

## Choose the user

A job without `user:` runs as the service itself does: the service's `user:` if you set one, otherwise the image's default user. Add `user:` when one job needs a different account:

```yaml
services:
  appserver:
    schedule:
      - name: heartbeat
        every: "@every 5m"
        run: "echo heartbeat from $(hostname)"
      - name: report
        every: "0 6 * * 1-5"
        run: ["node", "--version"]
        user: node
```

`user` takes a name, a uid, `name:group`, or `uid:gid`. Lando runs that job in a sidecar whose container user is that user.

Lando groups a service's jobs by user and runs one sidecar per group. Most services have one group, so one sidecar. In the example above there are two:

- `appserver-schedule` runs `heartbeat`. The first job in the list decides which group gets the plain name.
- `appserver-schedule-node` runs `report`. Other groups add the user, lowercased, with any other character turned into `-`. A later group of jobs without `user:` is named `appserver-schedule-default`.

The first job's user owns the plain `appserver-schedule` name, so reordering jobs that use different users can rename the sidecars.

Read a job's log from the sidecar that runs it.

## Set the timezone

Jobs use the service's `TZ`, and `lando schedule:list` reports times in the same zone. Without `TZ`, jobs run on UTC. There is no app-wide timezone key; see [Set the timezone](./timezone.mdx).

A zone name such as `America/Chicago` needs the image's timezone database. Debian-based images ship it. When the image has no data for the zone, `lando start` or `lando restart` fails while it builds the sidecar's image. The error is one line that names the service, the `TZ` value, and the fix: install the timezone database in the service's `build.artifact`, or remove `TZ`. On Alpine:

```yaml
services:
  appserver:
    environment:
      TZ: "America/Chicago"
    build:
      artifact:
        - run: apk add --no-cache tzdata
          user: root
```

Lando never swaps in UTC for a zone name it can't load, so `lando schedule:list` and the timer agree.

## Know what the sidecar shares

The sidecar is a copy of the parent service that runs the scheduler instead of your server. It has the same image and image build steps, the same mounts and volumes, the same environment, and the same networks. A job sees the files the service sees, including dependency directories such as `vendor` and `node_modules`, and reaches `database` or `cache` by the same hostnames. It starts after the parent.

Some things stay with the parent only:

- Published ports, routes, hostnames, and network aliases. Nothing can reach the sidecar by URL.
- Healthchecks and certificates.
- The parent's server process and its app build steps (`build.app`). Those run once, in the parent.

The image needs a shell. An image without one, such as a distroless image, can't carry scheduled jobs, and Lando says so when it plans the app.

## Change or remove jobs

Edit `schedule:`, then run `lando start` or `lando restart`. Lando rebuilds only the small layer that holds the job table. You don't need `lando rebuild`.

Whole-app `start`, `stop`, `restart`, `rebuild`, and `destroy` include the sidecar. A command scoped to the parent leaves the sidecar alone, so `lando restart --service appserver` doesn't apply a schedule edit. Name both, or run the whole-app command:

```sh
lando restart --service appserver --service appserver-schedule
```

Delete the `schedule:` list and the next whole-app `start`, `restart`, or `rebuild` removes the sidecar. The result reports it under removed services.

When Landofile layers both set `schedule:` on a service, the higher layer's list replaces the lower one. Jobs don't merge by name. `schedule: []` in a higher layer clears the list.

## Plan for overlap and missed runs

Runs of one job can overlap. If `heartbeat` takes seven minutes, the next run still starts on time. A job that must not run twice at once has to lock itself, for example with `flock`.

Missed runs aren't replayed. After your laptop sleeps or the app stops, the next run is the next scheduled time.

`@every` follows the clock, not the moment the app started. At 12:02, `@every 5m` next runs at 12:05.

## Fix a rejected schedule

Lando checks `schedule:` whenever it loads the Landofile. An `@every` step that doesn't line up with the clock, such as `@every 7m` or `@every 1h30m`, fails with `LandofileValidationError` at the job's `every` path, and the message tells you to use a 5-field cron expression instead:
