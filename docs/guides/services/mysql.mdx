# Add MySQL

Add `type: mysql` under `services` in `.lando.yml`. Lando pulls `mysql:8.0` and listens on `3306`:

```yaml
name: mysql-demo
services:
  db:
    type: mysql
```

Set a member under `creds:` when you want an explicit value. A member you leave out keeps its default. By default, the username, password, and root password are `lando`, and the database is named after the app. `lando info` prints those published defaults. `creds.user` is the database username. Container `user:` is not.

```yaml
services:
  db:
    type: mysql
    creds:
      database: shop
      rootPassword: secret
```

Start it. Lando puts the database on the app network:

## Connect from another service

Other services use the service name as the hostname. Here that's `db`. Defaults:

| Setting | Value |
| --- | --- |
| Host | `db` |
| Database | the folder's data name (here `mysql-demo`, the name this folder's data was first created under); override with `creds.database` under `services.db` |
| User | `lando` |
| Password | `lando` |
| Root password | `lando`; `LANDO_DB_ROOT_PASSWORD` inside the service, and `lando info` prints it |

From inside the app network the connection URL is:

```
mysql://lando:lando@db:3306/mysql-demo
```

That URL uses the default port. If you set `port:`, use that port in your application's connection URL too.

## Open the client

The `mysql` type ships the client task. After start:

```sh
lando mysql --version
```

The readiness probe pings the server without requiring a working application login. See [Recover when credentials don't match](#recover-when-credentials-dont-match).

The generated client supplies its password for each invocation. Lando scopes the client-only `MYSQL_PWD` variable to client and healthcheck processes, not the database server's initialization environment.

Import a dump with `lando db:import`. See [Import and export app databases](../tooling/db-import-export.mdx). You can also pipe a plain SQL file directly into the client. This executes the dump's statements against the database, so back up any data you need first:

```sh
lando mysql < dump.sql
```

## Add server config

Set `config.server` to an app-relative file when you need to tune the server:

```yaml
services:
  db:
    type: mysql
    config:
      server: ./config/my.cnf
```

Lando mounts that file read-only at `/etc/mysql/my.cnf`. MySQL reads it directly on startup, after the image's `/etc/my.cnf`, without relying on that file's include directives. It has to be a regular file, not a directory.

Lando's generated launcher gives the planned port, `port:` or the default, precedence over a port line in your config file. If you replace the launcher, see [Change the port](#change-the-port).

To add daemon flags without replacing Lando's launcher, use
[`extraArgs:`](./extra-args.mdx):

```yaml
services:
  db:
    type: mysql
    extraArgs:
      - --max-connections=77
```

Lando keeps the planned port and any `config.server` handling, then appends
your list. Set `port:` or `config.server` rather than passing `--port`, `-P`,
or `--defaults-*`. `--datadir` is also reserved: keep the default data directory
or use `command:` for a custom launcher. With `config.server`, Lando still
reads the database version from `/var/lib/mysql`, the default data directory.
Custom images and Compose builds reject `extraArgs:`.

The path has to stay inside the app root. Absolute paths, paths that climb out of the app root, and symlinks that point outside it are rejected when Lando plans the app, before anything starts.

## Change the port

Set `port:` to move the daemon's listener, healthcheck, endpoint, and Lando's own clients together:

```yaml
services:
  db:
    type: mysql
    port: 3307
```

Other services now connect to `db:3307`. Lando sets `MYSQL_TCP_PORT` for the server and in-container clients, and publishes the same value as `LANDO_DB_PORT`. `lando mysql` and `lando db:*` commands use that planned port.

An authored `MYSQL_TCP_PORT` must match the planned port, or planning fails; `lando app:config:lint` reports the mismatch at `services.<name>.environment.MYSQL_TCP_PORT`. If you replace `command:` or `entrypoint:` and the option file sets another port, pass `--port={{ service.port }}` in your launcher. The [port expression](../landofile/expressions.mdx#your-services-own-port) supplies the value; you supply the flag.

Port `33060` fails during planning. MySQL's X Protocol listener already binds it, so a server listening there can't start.

Apply the change with `lando rebuild`, then check the running server:

```sh
lando mysql -N -e 'SELECT @@port'
```

## Recover when credentials don't match

After editing `creds`, run `lando start`. Lando applies the settings to the catalog server without dropping or renaming existing users or databases. For these updates, Lando connects over the container's Unix socket as `lando_admin`, an account restricted to `localhost`. Its password is derived from a private key and the volume identity. Lando never prints it.

If start warns that it couldn't update the credentials, follow [Keep database credentials in sync](../tooling/db-creds-apply.mdx) to preview and apply a repair with `lando db:creds:apply`. If Lando needs a fallback password, supply the current root password, not the new one.

`LANDO_DATABASE_ADMIN_SEED_UNAVAILABLE` means Lando skipped adopting `lando_admin` and tried the previous or desired root password instead. See [how to restore access to the seed](../tooling/db-creds-apply.mdx).

## Pin a version

Choose a managed series in `type:`. Lando supports MySQL 8.0, 8.4 LTS, and 9.7 LTS. An unversioned `mysql` service stays on 8.0.

```yaml
services:
  db:
    type: "mysql:8.4"
```

Use unversioned `type: mysql` for an image outside the catalog. Lando can [check the configured login](../tooling/db-creds-apply.mdx#check-credentials-for-a-custom-image-or-launcher), but it doesn't apply credential changes to that image. A versioned type can only use its catalog image.

Each MySQL service keeps its data in its own `lando-<data-name>--<service>--mysql-data` volume, independent of the server version. The data-name slug stays fixed when you rename the app.

Oracle MySQL clients installed into PHP services use Oracle's signed Bookworm APT repository on amd64 and SHA256-pinned Oracle EL9 RPM payloads on Linux arm64 for all three series (8.0, 8.4, and 9.7). The arm64 support policy covers default `caching_sha2_password` authentication, not LDAP/SASL plugins. Live arm64 build, connection, and dump/restore verification is still pending. See [Customize PHP](./php-customization.mdx).

## Change versions

To move from MySQL 8.0 to 8.4 on the existing data volume, run these commands from the app directory:

```sh
lando stop
lando app:config:set services.db.type mysql:8.4
lando start
lando mysql -N -e 'SELECT VERSION()'
```

Lando saves a restore point before upgrading and prints its ID. If you run `lando start --format=json` for the upgrade, the ID is `dataVersionChanges[0].restorePoint` in the final result. The version query should report 8.4. Check that your app can still read its data.

Pass `--no-snapshot` to start without saving a restore point only if you have another backup or accept upgrading without one. Automatic retention leaves [upgrade restore points](../tooling/db-import-export.mdx#restore-points-before-version-upgrades) in place. Use `lando db:snapshots:prune --recovery` to remove them explicitly.

## Go back to the old version

List the restore points for `db` and note the ID of the `upgrade` point for 8.0:

```sh
lando db:snapshots --service db
```

Pin the old series and restore the point. Replace `<id>` with the ID from the list. Restoring replaces your current database files, including changes made since the upgrade.

```sh
lando app:config:set services.db.type mysql:8.0
lando db:restore <id> --service db
lando start
lando mysql -N -e 'SELECT VERSION()'
```

Check that the server reports 8.0 and that your app can read the recovered data. To keep the upgraded data instead, restore `type: mysql:8.4` or your previous `image:` without running `db:restore`.

MySQL may not leave a readable version record. If the point is listed as unverified, add `--any-series` to `db:restore` only if you independently know the series of the saved data. If you start on the old series before restoring, Lando refuses a downgrade it can verify and names a matching verified point if one exists. Otherwise, the server's own downgrade refusal can appear under `ServiceNotReadyError`.

If you have no restore point, use a verified export taken before the upgrade. To make one before changing versions, run `lando db:export before-upgrade.sql.gz --service db` while 8.0 still runs. Importing an export made on 8.4 into 8.0 isn't guaranteed to work. **Back up other services first:** `--volumes` deletes every service's data in the app. Run `lando destroy -y --volumes`, `lando start` on 8.0, then `lando db:import before-upgrade.sql.gz --service db --yes`.
