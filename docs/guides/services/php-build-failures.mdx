# Recover from a failed PHP build

A failed PHP build stops startup and reports the command that failed. Read that command's output, fix the script or its dependencies, then rerun `lando start`.

`build.app` defines shell commands for the app phase of a service build. Each entry executes as `sh -c "<command>"`, in order, after Lando's own PHP prerequisite steps. A `composer install`
that fails on a bad `composer.json`, a missing PHP extension a package
requires, or a stray `exit 1` all fail a build step the same way: the step
exits non-zero, and Lando stops instead of starting a half-built app.

## Recover from a failing build step

Fix the failing command in `build.app`. Most often that means fixing the underlying script itself, not the Landofile. Then rerun `lando start`. It reuses the containers from the failed attempt, reruns the failed step, and only recreates a container whose config changed.
Editing a `build.app` entry changes that step's content-hash build key, so
the next `lando start` reruns it. A `build.artifact` edit changes the image
key the same way, so start rebuilds that image too. `lando rebuild` is the
forced rerun when the command text is unchanged and only bind-mounted inputs
changed, or when you want a forced pull.

## The build plan captures the exact failing command

Every `build.app` entry reaches the app's build plan verbatim, whether or not it will actually succeed. Planning never runs a build step. It just records the command to run later. This means a successful plan check does not prove that `composer install --no-dev`, or any other build command, will succeed when executed.

## What a failing build step looks like

On a real provider (not the in-memory test double), a failing app-phase
step becomes a tagged `BuildStepFailedError` carrying the step, its exit
code, and its transcript path. Every step failure in the app build phase
is collected into one tagged `BuildPhaseFailedError` with a `failures`
array, not just the first one. A step that depends on a failed step is
marked blocked and reported as its own failure, so Lando never silently
skips work downstream of a broken step.

Every app-phase step writes its stdout/stderr to a per-step transcript
file under the user data root, named by the step's content-hash build key:

```text
<userDataRoot>/builds/<appId>/app/<service>/<buildKey>.log
```

Scratch apps get the same layout under an extra `scratch/` segment. While
the step runs, its stdout/stderr lines also stream live as `task-detail`
events, so `lando start` shows the failing command's own output, not just
its exit code.

On a `BuildPhaseFailedError`, `lando start` stops there and leaves what
it already applied in place: containers, routes, volumes, and any build
steps that did finish. The CLI exits non-zero, reports the tagged error
with its list of `BuildStepFailedError` entries, and prints one warning
naming which services are running, created/stopped, or unverified. Nothing is
removed. `lando stop` shuts the app down if you want it quiet while you
fix the script.

## Prove the plan

The happy-build fixture runs a successful `build.app` entry through start
and destroy. The failing-build fixture proves the broken command reaches
the resolved plan without executing it on the test provider:

<Guide>
  <Scenario id="app-build-step-succeeds" render>
    <Step name="scaffold">
      <UseFixture name="happy-build" />
    </Step>
    <Step name="start">
      <Run command="lando start" />
      <Verify event="post-start" />
    </Step>
    <Step name="cleanup">
      <Cleanup />
      <Run command="lando destroy -y" />
    </Step>
  </Scenario>

  <Scenario id="failing-build-reaches-plan" render>
    <Step name="scaffold">
      <UseFixture name="failing-build" />
    </Step>
    <Step name="confirm-plan">
      <Run command="lando app:config --format=json" />
      <Verify command="lando app:config --format=json" expect={{ stdout: { regex: "composer install --no-dev" } }} />
      <Verify command="lando app:config --format=json" expect={{ stdout: { regex: "exit 1" } }} />
    </Step>
  </Scenario>
