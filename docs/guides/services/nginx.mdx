# Add nginx

Add `type: nginx` under `services` in `.lando.yml`. Lando pulls `nginx:1.30-alpine` and listens on `80`. Your repository is mounted at `/app` and served as the document root:

```yaml
name: nginx-demo
services:
  web:
    type: nginx
```

## Open the URL

Lando derives an HTTPS hostname from the nginx service's HTTP endpoint, such as `web.<app>.lndo.site`. Use the URL reported by `lando info`, including any fallback port. You only need a `proxy:` block to customize hostnames.

Redirects nginx sends on its own, such as adding the trailing slash to a directory URL, are relative. The browser stays on the HTTPS URL and port it used.

Hidden paths, meaning any path segment that starts with `.` such as `/.git/config` or `/.env`, get Lando's 403 page, so your repository's dotfiles stay private even though the app root is the default webroot. `/.well-known/` stays served.

## Serve files only you can read

On Linux providers that support [project-user mapping](./file-ownership.mdx), the stock nginx launcher maps its `nginx` workers to your host user. The workers can read files you own in a private checkout without changing the files' owner or permissions. The master still starts as root and the listener port stays the same. This also applies when nginx serves files in front of PHP-FPM.

Run `lando info --format=json` from your app directory and check `projectUser` for the `web` service. When it names `nginx`, user commands such as `lando exec` use that account by default too. Lando doesn't persist `/var/cache/nginx` as a home. If the provider can't map the worker, `projectUserExplanation` tells you why; the service may not be able to read private files.

An existing container keeps its applied command identity until you run `lando start` to apply the new plan. If that switches your default commands from root to `nginx`, see [Recover an old nginx root home](./home-and-host.mdx#recover-an-old-nginx-root-home) before removing any volumes.

On an engine that renumbers image accounts, the default worker keeps its container identity if your host UID or GID is `0`. Lando never renumbers the worker to either zero ID.

Set `projectUser: false` on the service to opt out. If you supply your own `command:` or `entrypoint:`, Lando doesn't assume your launcher uses the stock worker. If you supply a different image or a replacement build, it doesn't assume that image has the stock account or IDs.

## Mount your project read-only

`type: nginx` mounts your project read-write by default, regardless of whether it serves static files or sends PHP requests to a backend. On a provider that maps the project user, commands in the nginx service can write to the mounted files that your host user can write. [The `static` and `static:nginx` types](./static.mdx) mount the project read-only by default.

To make only the nginx service's project mount read-only, add `appMount` to its block in `.lando.yml`. Keep `target: /app` to leave the mount and relative webroot in their usual places:

```yaml
services:
  web:
    type: nginx
    appMount:
      target: /app
      readOnly: true
```

From the app directory, run `lando app:config:lint`, then `lando start` to apply the change. In `lando info --format=json`, check that the `web` service's `/app` mount has `readOnly: true`. This doesn't make mounts on other services read-only. Configure those on the services that use them.

## Pair nginx with PHP

nginx is commonly paired with a `php-fpm` service: nginx serves static
files and proxies dynamic requests to the app service over the per-app
network.

```yaml
services:
  web:
    type: nginx
    backend: app
  app:
    type: "php:8.3"
    via: fpm
```

The generated FastCGI configuration passes `HTTPS=on` to PHP when the browser reached the proxy over HTTPS, so PHP apps build `https://` URLs; see [Get HTTPS URLs through the proxy](./php.mdx#get-https-urls-through-the-proxy). It runs PHP only for lowercase `.php` names and answers `.PHP` and other case variants with Lando's 403 page, so a case-insensitive app mount on macOS or Windows can't serve PHP source.

FastCGI also receives `REQUEST_SCHEME` and `SERVER_PORT`, so `$_SERVER` agrees with `HTTPS`, and `SERVER_NAME` is the requested host, so frameworks that compare the `Host` header with it accept routed requests. The router supplies the public value through `X-Forwarded-Proto` and `X-Forwarded-Port`; a valid forwarded port from `1` to `65535` is used as-is, while a missing, malformed, comma-separated, or out-of-range value falls back to `443` for `https`, `80` for `http`, or nginx's own listener port when the scheme is unknown. A direct request to the container without forwarded headers reports nginx's own scheme and listener port. The router replaces client-supplied `X-Forwarded-*` headers, so a browser cannot spoof these values through the proxy.

## Stop PHP in upload directories

Set `uploadDirs:` on the nginx service in front of PHP-FPM, not on the FPM service. Lando's generated PHP location blocks execution from these webroot-relative directories:

```yaml
services:
  web:
    type: nginx
    backend: app
    uploadDirs:
      - sites/*/files
      - uploads
  app:
    type: "php:8.3"
    via: fpm
```

The nginx service needs a non-empty `backend` and Lando's generated launcher, with no authored `command:` or `entrypoint:`. See [Keep PHP out of upload directories](./php.mdx#keep-php-out-of-upload-directories) for syntax, recipe defaults, Apache support, and how to check or clear the setting.

## Serve a subdirectory

Set `webroot:` to a path relative to the app mount at `/app`. For example, `public` serves `/app/public`. Omit it or use `.` to serve the app root. An absolute container path is allowed when you need a very specific location outside the usual app layout. Inside the container, `LANDO_WEBROOT` is always the resolved absolute path. Set `port:` to move nginx's listener, endpoint, and healthcheck together:

```yaml
services:
  web:
    type: nginx
    webroot: public
    port: 8080
```

## Run as a non-root user

Set `user: nginx` only if you want to run the master itself as the image's `nginx` account, with or without a PHP backend. This isn't needed for the default worker mapping. Lando writes its whole nginx configuration to `/tmp/lando-nginx.conf`, points the PID file and temp directories at `/tmp` too, and starts the daemon with `nginx -c /tmp/lando-nginx.conf`, so nothing gets written into the image's root-owned config tree at start:

```yaml
services:
  web:
    type: nginx
    user: nginx
    port: 8080
```

Lando plans no home store for the `nginx` account, whose home on this image is its cache directory; set `home.path:` when you want a directory to survive a rebuild. A non-root process can't bind below 1024 on the default `lando` provider, so pick something at or above `1024`.

If you set your own `command:` or `entrypoint:`, your startup owns nginx's
configuration. Lando never appends listen directives or flags to an authored
launcher, and it does not generate a config or remove the image's default site.
Match the daemon to `port:` yourself.
If startup fails with this override, Lando includes a hint naming the required
`listen <port>;` directive with your planned port number.

## Pin a version

Set `image:` when `nginx:1.30-alpine` isn't the version you want:

```yaml
services:
  web:
    type: nginx
    image: nginx:1.27-alpine
```
