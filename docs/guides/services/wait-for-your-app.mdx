# Make start wait for your app

Add `readiness:` so `lando start` waits until the app answers, not only until the process is running. Keep `healthcheck:` for the container runtime's ongoing health monitoring; the two settings are independent.

```yaml
name: myapp
services:
  app:
    type: "node:22"
    command:
      - node
      - server.mjs
    healthcheck: curl -fsS http://localhost:3000/health
    readiness: curl -fsS http://localhost:3000/ready
```

This edits an app that already serves HTTP on port 3000 with `/health` and `/ready` endpoints. Use paths your app actually implements. `server.mjs` has to listen there and exit on SIGTERM. `type: "node:22"` is the Node 22 image, which includes `curl`, and Lando sets `PORT=3000`. Point the probes at that port.

```sh
lando start
lando app:config --format=json
```

Start waits for the readiness command to exit successfully. If its attempts run out, start reports a readiness failure. `app:config --format=json` shows both normalized authored policies; `lando info --format=json` inspects runtime state without running either probe.

Writing `healthcheck:` replaces only native health. Writing `readiness:` replaces only lifecycle readiness. If you omit readiness, Lando keeps a service type's contributed readiness, such as MongoDB's stronger protocol check. When there is no contributed readiness, Lando falls back to the effective native healthcheck. Node has neither default, so author a readiness command for an application-level gate.

## Write the probe as a string or a list

A string runs through `sh -c` inside the service by default. The shell splits `curl -fsS http://localhost:3000/`. Host probes use Bun Shell instead, as described below.

A list is literal argv. Lando runs those strings as the program and its arguments, with no shell. Compose markers such as `CMD`, `CMD-SHELL`, and `NONE` belong in an object's `test` list, not in bare argv. A bare list that starts with one stays literal, so the probe tries to run a program called `CMD-SHELL`. `lando app:config:lint` flags that as `readiness.bare-compose-marker` (or `healthcheck.bare-compose-marker` under native health) and the Landofile stays valid. See [Lint a Landofile](../landofile/config-lint.mdx#fix-healthcheck-warnings).

```yaml
services:
  app:
    type: "node:22"
    command:
      - node
      - server.mjs
    readiness:
      - curl
      - -fsS
      - http://localhost:3000/
```

Write the service `command:` as a list too, `[node, server.mjs]`. The service runs under Lando's init process, which forwards SIGTERM to the process it started; a string command puts `sh -c` in that position, and the shell does not pass the signal on to your server. Handle SIGTERM in the app so it finishes in-flight work before it exits. See [Stop cleanly](./node.mdx#stop-cleanly) for the `init` option.

## Set timing on an object

Use an object when you need an interval, a timeout, retries, or a start period. Keep `kind: command`.

```yaml
services:
  app:
    type: "node:22"
    command:
      - node
      - server.mjs
    readiness:
      kind: command
      command:
        - curl
        - -fsS
        - http://localhost:3000/
      intervalSeconds: 7
      timeoutSeconds: 4
      retries: 9
      startPeriodSeconds: 15
```

`retries` is how many probes one start attempts after the start period. It isn't a count of `lando start` reruns. Failed probes during `startPeriodSeconds` don't use up those retries. The first success ends the wait.

Compose spellings work on the same object. Markers belong in `test`, not in a bare list:

```yaml
services:
  app:
    type: "node:22"
    readiness:
      test:
        - CMD
        - curl
        - -fsS
        - http://localhost:3000/
      interval: 5s
      timeout: 3s
      retries: 6
      start_period: 20s
```

`CMD` becomes an argv command. `CMD-SHELL` takes one shell string. `NONE` shows up as `false`. A duration such as `5s` becomes seconds. `lando app:config --format=json` prints that stored object, not the spelling you typed.

Use one dialect per probe. If you wrote `command:` with `interval: 1s` or `timeout: 1s` in the same Landofile, `lando app:config:lint` and `lando start` report the conflicting keys. Keep `command:` and replace those durations with `intervalSeconds: 1` and `timeoutSeconds: 1`. To keep the Compose durations instead, use `test:` with a `CMD` or `CMD-SHELL` marker in place of `command:`. Run `lando app:config:lint` again to check the edit.

If the two dialects come from different files or layers, lint warns with `readiness.mixed-dialects` (or `healthcheck.mixed-dialects`). The Lando command and timing fields still take precedence in that case. Match the lower layer's dialect when overriding individual fields, or use `!override` to replace the whole probe. The shared `target`, `user`, and `retries` fields work with either dialect.

Both keys accept `false`, a command string, argv, or a command, HTTP, or TCP object with timing settings. Use `lando app:cache:refresh --format=json` to validate the plan without starting services.

## Probe HTTP or TCP without curl

Use `kind: http` when the service answers HTTP and the image doesn't include `curl`. Lando's mounted helper sends one GET from inside the service to an absolute `http://` or `https://` URL. Status codes 200 through 399 count as success without following redirects. The probe doesn't read the response body or verify TLS certificates. It checks readiness, not trust.

```yaml
services:
  web:
    type: compose
    image: docker.io/library/busybox:1.37
    command:
      - sh
      - -c
      - echo ok >/tmp/index.html && exec httpd -f -p 8080 -h /tmp
    readiness:
      kind: http
      url: http://127.0.0.1:8080/
```

Use `kind: tcp` to dial a port. Lando connects through the service's managed network name, the same host catalog TCP probes use, never loopback discovery or an interface address. Supply `port:` (1 to 65535), or let a service type attach a listener `target`.

```yaml
services:
  cache:
    type: compose
    image: docker.io/library/busybox:1.37
    command: [nc, -l, -p, "6379"]
    readiness:
      kind: tcp
      port: 6379
```

You can use either kind under `healthcheck:` for ongoing monitoring, with the same timing fields as a command probe (`intervalSeconds`, `timeoutSeconds`, `retries`, `startPeriodSeconds`). Neither needs a shell or network tools in the image. `target: host` fails planning with `HealthcheckTargetUnsupportedError`; use a command under `readiness:` for host-side execution or when you need to check a response body.

Validate the plan, then start:

```sh
lando app:cache:refresh --format=json
lando start --format=json
```

`app:config --format=json` shows the normalized `kind`, `url`, and `port` on each service. `app:cache:refresh` runs the planner and records the plan without starting containers. Start waits until each probe succeeds.

## Run the probe as a container user

Set `readiness.user` when the startup command must run as a particular container identity. In your existing Node app's `.lando.yml`, run its readiness request as UID and GID 1000:

```yaml
services:
  app:
    type: "node:22"
    command: [node, server.mjs]
    readiness:
      target: service
      user: "1000:1000"
      command: [curl, -fsS, http://localhost:3000/ready]
```

Run these commands from the app directory on your host:

```sh
lando app:config --format=json
lando start
```

The config should retain `target: service` and `user: "1000:1000"`. A successful readiness check means the HTTP request succeeded under that identity, not merely that an identity comparison passed. The user must be valid for the image: accepted forms are a username, numeric UID, or either followed by `:group` or `:GID`. This selects the probe's identity, not the main service process's user. Omitting `target` also means `service`.

Lando waits for readiness during start, restart, rebuild, `service_healthy` dependency gates, and app-build gates. Selecting a probe user does not enable or disable native health monitoring. Any explicit `user` under `healthcheck`, even the service's usual user, fails before action with `HealthcheckTargetUnsupportedError`. Move that probe to `readiness`; keep a separate native healthcheck if you want periodic monitoring.

## Wait for a file on the host

Use `target: host` when a prerequisite is available on the machine running the CLI, rather than inside the container. Create an empty `.ready` file beside `.lando.yml` before starting, then use this configuration in your existing app:

```yaml
services:
  app:
    type: "node:22"
    command: [node, server.mjs]
    readiness:
      target: host
      command: test -f .ready
      intervalSeconds: 1
      retries: 10
```

From that app directory, validate the plan and start the app:

```sh
lando app:cache:refresh --format=json
lando start
```

Plan refresh validates the configuration without starting services. Start then waits until `.ready` exists. A missing file exhausts the configured attempts; create it and retry start. If another host process creates the file, launch that process before start and ensure it can finish without waiting for this app's routes or dependent services. Those may not exist until after the readiness gate, so probing an app URL here can make startup wait on itself.

For that host example, the normalized `readiness` configuration value is below. This is a configuration fragment, not runtime health or a captured info result; omitted timing fields receive defaults during planning.

```json
{
  "target": "host",
  "kind": "command",
  "command": "test -f .ready",
  "intervalSeconds": 1,
  "retries": 10
}
```

Host probes run with the CLI process's current identity and the app root as their working directory, not in a provider VM or a sandbox. They don't receive secrets bound in the service `environment` or any other Lando secret binding. Only use commands you trust. The string above uses Bun Shell's file test, not your interactive login shell. Write it in [Bun Shell syntax](../tooling/bun-shell-scripts.mdx#write-host-commands-in-bun-shell-syntax): `$NAME` rather than `${NAME}`, and `1>&2` rather than `>&2`. Planning rejects the other forms with `LandofileValidationError`, and `lando app:config:lint` reports them as `landofile.host-shell`. A list passes the program and arguments exactly without shell expansion. For example, `command: [test, -f, .ready]` needs a `test` executable on the CLI machine instead of a shell builtin.

Host readiness runs at the same lifecycle gates, never as permanent host monitoring. Supply its own command through `command` or Compose `test`; it cannot borrow a type's default command, container user, or listener. Do not set `user` on it. Invalid host readiness fails planning with `HealthcheckTargetUnsupportedError` before changing containers. `target: host` under native `healthcheck` also fails with remediation to move the probe to `readiness`; `target: service` is accepted there as a no-op. Neither execution target changes native monitoring policy.

Private capture prevents live streaming and process/shell execution events; it does not make the configured command confidential. Redacted lifecycle plan metadata can include the command, and failures can include bounded, redacted stderr or command context. Keep secrets out of the command text. Bind the secret in the service `environment` and read it as `$NAME` in a string probe command, which runs under a shell inside the service. A `${secret:...}` reference written in the command itself fails loading with `LandofileValidationError`. `lando info` omits raw commands entirely.

## Turn the probe off

Choose which policy to disable. `healthcheck: false` turns off native monitoring, including an inherited image healthcheck, but keeps explicit or contributed readiness. `readiness: false` disables the lifecycle command gate and prevents fallback to native health; it does not disable native monitoring. Process-running and job-completion supervision continue. A `service_healthy` dependency still requires an enabled readiness probe; disabling it does not relax the dependency gate and the plan is rejected.

Put the override in `.lando.local.yml` when only this machine should skip that policy. Literal `false` replaces its base value instead of merging with it. Disable both keys only if you intend to keep process supervision without either command policy. For [MongoDB](./mongodb.mdx#what-ready-checks-and-what-it-doesnt), native health off alone still preserves the stronger startup check.

Object spellings such as `disable: true`, `test: [NONE]`, or `kind: none` are not that barrier. They merge into an inherited object like any other mapping. A bad `interval` or an empty `command` can still fail validation when the probe is off. If you layer `disable: true` over a Lando `command`, the inherited command wins and the probe stays on. Use literal `false` when you mean off.

```yaml
services:
  app:
    healthcheck: false
    readiness: false
```

## Inspect a failed start

If a `service_healthy` dependency exits and the runtime confirms it won't restart, Lando stops retrying that gate. The same exit report applies when a `service_completed_successfully` job finishes nonzero. `ServiceStartError` names the blocked service and the dependency. With `--format=json`, `error.details.dependencyExit` reports the dependency's state and its process exit code when available, even if the container logged nothing.

If the dependency is missing, replaced, or unverified just after start, the gate can fail before the probe runs. If the runtime discovers the change while watching for an exit, the readiness probe keeps its original retry budget. If those attempts fail, `error.details.dependencyUnavailable` gives the reason (`missing`, `replaced`, or `unverified`). Lando leaves out logs and listener advice because those would describe a container it couldn't verify. Check the provider with `lando doctor`, then retry start.

A oneshot that exits 7 while `web` waits on `init:completed` fails like this:

```text
Dependency init exited with code 7. Service web could not start because dependency gate init:completed was not satisfied.
```

```json
{
  "dependencyExit": {
    "service": "init",
    "gate": "init:completed",
    "status": "exited",
    "exitCode": 7
  }
}
```

Start, restart, and rebuild normally wait for effective readiness. If it exhausts its attempts, the command fails with `ServiceNotReadyError` and retains the applied app, routes, and volumes. When a restart policy allows recovery, an exit or observed restart can instead produce a warning and a `restarting` result before the probe passes.

When the failing check targets a TCP port, Lando looks at the ports the service is actually listening on and leads the error with what it found:

- **No listener on the expected port.** For example, `no TCP listener observed on 6380; observed ports: 6379` means the daemon came up on a different port. Make it listen on 6380, or set `port: 6379` if that's the port it uses.
- **Loopback only.** The daemon listens on `127.0.0.1`, so other services can't reach it. Bind it to `0.0.0.0`.
- **Port is bound.** Something listens on the expected port, but the check still failed. The error's `lastStatus` shows the check's last output.

The same report can appear when a `service_healthy` dependency or an app-build step waits on a service that never becomes healthy. If the provider verifies a terminal dependency exit, Lando reports the exit and skips both the listener check and its configuration advice. With `--format=json`, a listener report appears on `error.listener` (`port`, `state`, and the observed `listening` addresses). The observation covers the container's network namespace, which pod siblings can share, so it shows which ports are bound, not which process bound them. If Lando can't read the container's socket table, the error leaves the report out rather than guess.

For a missing or loopback-only listener, the first remediation line gives one diagnostic action. When the service type records who must configure that port, a second line gives that owner's configuration advice. Your application may need to use Lando's port variables, or your custom image may need a daemon setting. If you set the listener with a flag in a Landofile launcher, pass the value with [`{{ service.port }}`](../landofile/expressions.mdx#your-services-own-port). You can reuse it in a container probe command that checks the same port. For an application-owned Node listener on port 3000 with no observed listeners, those lines read:

```text
Make app listen on 3000.
Make your server listen on 0.0.0.0:3000; your application owns this listener and Lando sets `PORT` to 3000.
```

This configuration advice is separate from socket evidence. It appears only for the matching port, not when that port is already bound. If socket evidence is unavailable after a readiness probe fails or times out, the ownership advice can still supply the action. A failed `service_healthy` gate uses the dependency's advice, never the service waiting on it. Create and container-start failures don't append listener advice.

Lando's built-in TCP checks connect through the service's network name, the same way other services reach it, so a daemon bound only to loopback fails them. They need `bash` or `nc` in the image; a custom image with neither fails with a message saying so, and you can replace the check with your own `healthcheck:` or `readiness:`.

```sh
lando app:config --format=json
lando logs -s app
```

`-s` is `--service`. Fix the app or the probe, then retry start:

```sh
lando start
```

An exhausted readiness probe stays fatal even if the service has a restart policy. To skip the readiness gate and keep process supervision, set `readiness: false`.

## Inspect configuration without claiming readiness

Run `lando info --format=json` for a running app. Each service entry in the result separates `health` from `readiness`. Native `health` reports provider-observed `healthy`, `starting`, or `unhealthy`; explicitly disabled native health is `not-monitored`, and missing evidence is `unknown`, not a failure.

The readiness `state` is `disabled`, `not-configured`, or `not-observed`. Its `source` is `authored`, `contributed`, `healthcheck` (fallback), `unknown` (historical provenance unavailable), or `none`. The metadata includes execution `target`, `userSource`, `listener`, timings, command presence, and a configuration pointer, not the raw command. A listener identifies the container endpoint a type-owned probe checks; it is not the host/service execution target.

When present, the service's `listenerAuthority` records who must configure its planned listener and which setting to use. It is configuration advice, not proof that the port is open.

Info never executes probes or reports a durable last-readiness proof. `not-observed` means configured but not proved by this inspection, even after a successful start. The `ready` result returned by start is the observed gate success for that invocation; a running container or healthy native check is not a substitute.
