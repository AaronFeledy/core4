# Make start wait for your app

Add `readiness:` so `lando start` waits until the app answers, not only until the process is running. Keep `healthcheck:` for the container runtime's ongoing health monitoring; the two settings are independent.

```yaml
name: myapp
services:
  app:
    type: "node:22"
    command:
      - node
      - server.mjs
    healthcheck: curl -fsS http://localhost:3000/health
    readiness: curl -fsS http://localhost:3000/ready
```

This edits an app that already serves HTTP on port 3000 with `/health` and `/ready` endpoints. Use paths your app actually implements. `server.mjs` has to listen there and exit on SIGTERM. `type: "node:22"` is the Node 22 image, which includes `curl`, and Lando sets `PORT=3000`. Point the probes at that port.

```sh
lando start
lando app:config --format=json
```

Start waits for the readiness command to exit successfully. If its attempts run out, start reports a readiness failure. `app:config --format=json` shows both normalized authored policies; `lando info --format=json` inspects runtime state without running either probe.

Writing `healthcheck:` replaces only native health. Writing `readiness:` replaces only lifecycle readiness. If you omit readiness, Lando keeps a service type's contributed readiness, such as MongoDB's stronger protocol check. When there is no contributed readiness, Lando falls back to the effective native healthcheck. Node has neither default, so author a readiness command for an application-level gate.

## Write the probe as a string or a list

A string runs through `sh -c` inside the service by default. The shell splits `curl -fsS http://localhost:3000/`. Host probes use Bun Shell instead, as described below.

A list is literal argv. Lando runs those strings as the program and its arguments, with no shell. Compose markers such as `CMD`, `CMD-SHELL`, and `NONE` belong in an object's `test` list, not in bare argv. A bare list that starts with one stays literal, so the probe tries to run a program called `CMD-SHELL`. `lando app:config:lint` flags that as `readiness.bare-compose-marker` (or `healthcheck.bare-compose-marker` under native health) and the Landofile stays valid. See [Lint a Landofile](../landofile/config-lint.mdx#fix-healthcheck-warnings).

```yaml
services:
  app:
    type: "node:22"
    command:
      - node
      - server.mjs
    readiness:
      - curl
      - -fsS
      - http://localhost:3000/
```

Write the service `command:` as a list too, `[node, server.mjs]`. The service runs under Lando's init process, which forwards SIGTERM to the process it started; a string command puts `sh -c` in that position, and the shell does not pass the signal on to your server. Handle SIGTERM in the app so it finishes in-flight work before it exits. See [Stop cleanly](./node.mdx#stop-cleanly) for the `init` option.

## Set timing on an object

Use an object when you need an interval, a timeout, retries, or a start period. Keep `kind: command`.

```yaml
services:
  app:
    type: "node:22"
    command:
      - node
      - server.mjs
    readiness:
      kind: command
      command:
        - curl
        - -fsS
        - http://localhost:3000/
      intervalSeconds: 7
      timeoutSeconds: 4
      retries: 9
      startPeriodSeconds: 15
```

`retries` is how many probes one start attempts after the start period. It isn't a count of `lando start` reruns. Failed probes during `startPeriodSeconds` don't use up those retries. The first success ends the wait.

Compose spellings work on the same object. Markers belong in `test`, not in a bare list:

```yaml
services:
  app:
    type: "node:22"
    readiness:
      test:
        - CMD
        - curl
        - -fsS
        - http://localhost:3000/
      interval: 5s
      timeout: 3s
      retries: 6
      start_period: 20s
```

`CMD` becomes an argv command. `CMD-SHELL` takes one shell string. `NONE` shows up as `false`. A duration such as `5s` becomes seconds. `lando app:config --format=json` prints that stored object, not the spelling you typed.

Pick one dialect and keep it across layers. When the merged object holds a Lando field such as `command` or `intervalSeconds`, Lando reads only the Lando command/timing fields and ignores `test`, `interval`, `timeout`, and `start_period`. If one layer wrote the Lando side and another wrote the Compose side, `lando app:config:lint` warns with `readiness.mixed-dialects` (or `healthcheck.mixed-dialects` under native health) so you can see which timing survived. The shared `target` and `user` fields work with either dialect; neither makes an otherwise Compose object mixed-dialect.

Both keys accept `false`, a command string, argv, or a command/timing object. Probe HTTP through a command such as `curl`; the bundled runner does not execute `kind: http` or `kind: tcp`. Unsupported kinds fail planning with `LandofileValidationError` before Lando touches a container. Use `lando app:cache:refresh --format=json` to validate the plan without starting services.

## Run the probe as a container user

Set `readiness.user` when the startup command must run as a particular container identity. In your existing Node app's `.lando.yml`, run its readiness request as UID and GID 1000:

```yaml
services:
  app:
    type: "node:22"
    command: [node, server.mjs]
    readiness:
      target: service
      user: "1000:1000"
      command: [curl, -fsS, http://localhost:3000/ready]
```

Run these commands from the app directory on your host:

```sh
lando app:config --format=json
lando start
```

The config should retain `target: service` and `user: "1000:1000"`. A successful readiness check means the HTTP request succeeded under that identity, not merely that an identity comparison passed. The user must be valid for the image: accepted forms are a username, numeric UID, or either followed by `:group` or `:GID`. This selects the probe's identity, not the main service process's user. Omitting `target` also means `service`.

Lando waits for readiness during start, restart, rebuild, `service_healthy` dependency gates, and app-build gates. Selecting a probe user does not enable or disable native health monitoring. Any explicit `user` under `healthcheck`, even the service's usual user, fails before action with `HealthcheckTargetUnsupportedError`. Move that probe to `readiness`; keep a separate native healthcheck if you want periodic monitoring.

## Wait for a file on the host

Use `target: host` when a prerequisite is available on the machine running the CLI, rather than inside the container. Create an empty `.ready` file beside `.lando.yml` before starting, then use this configuration in your existing app:

```yaml
services:
  app:
    type: "node:22"
    command: [node, server.mjs]
    readiness:
      target: host
      command: test -f .ready
      intervalSeconds: 1
      retries: 10
```

From that app directory, validate the plan and start the app:

```sh
lando app:cache:refresh --format=json
lando start
```

Plan refresh validates the configuration without starting services. Start then waits until `.ready` exists. A missing file exhausts the configured attempts; create it and retry start. If another host process creates the file, launch that process before start and ensure it can finish without waiting for this app's routes or dependent services. Those may not exist until after the readiness gate, so probing an app URL here can make startup wait on itself.

For that host example, the normalized `readiness` configuration value is below. This is a configuration fragment, not runtime health or a captured info result; omitted timing fields receive defaults during planning.

```json
{
  "target": "host",
  "kind": "command",
  "command": "test -f .ready",
  "intervalSeconds": 1,
  "retries": 10
}
```

Host probes run with the CLI process's current identity and the app root as their working directory, not in a provider VM or a sandbox. Only use commands you trust. The string above uses Bun Shell's file test, not your interactive login shell. A list passes the program and arguments exactly without shell expansion. For example, `command: [test, -f, .ready]` needs a `test` executable on the CLI machine instead of a shell builtin.

Host readiness runs at the same lifecycle gates, never as permanent host monitoring. Supply its own command through `command` or Compose `test`; it cannot borrow a type's default command, container user, or listener. Do not set `user` on it. Invalid host readiness fails planning with `HealthcheckTargetUnsupportedError` before changing containers. `target: host` under native `healthcheck` also fails with remediation to move the probe to `readiness`; `target: service` is accepted there as a no-op. Neither execution target changes native monitoring policy.

Private capture prevents live streaming and process/shell execution events; it does not make the configured command confidential. Redacted lifecycle plan metadata can include the command, and failures can include bounded, redacted stderr or command context. Keep secrets in supported secret references rather than literal command text. `lando info` omits raw commands entirely.

## Turn the probe off

Choose which policy to disable. `healthcheck: false` turns off native monitoring, including an inherited image healthcheck, but keeps explicit or contributed readiness. `readiness: false` disables the lifecycle command gate and prevents fallback to native health; it does not disable native monitoring. Process-running and job-completion supervision continue. A `service_healthy` dependency still requires enabled command readiness; disabling it does not relax the dependency gate and the plan is rejected.

Put the override in `.lando.local.yml` when only this machine should skip that policy. Literal `false` replaces its base value instead of merging with it. Disable both keys only if you intend to keep process supervision without either command policy. For [MongoDB](./mongodb.mdx#what-ready-checks-and-what-it-doesnt), native health off alone still preserves the stronger startup check.

Object spellings such as `disable: true`, `test: [NONE]`, or `kind: none` are not that barrier. They merge into an inherited object like any other mapping, and Lando still validates every sibling you wrote next to them: a bad `interval` or an empty `command` fails even though the probe is off. If the merged object keeps a Lando field such as `command`, `disable: true` loses to it and the probe stays on. Reach for literal `false` when you mean off.

```yaml
services:
  app:
    healthcheck: false
    readiness: false
```

## Inspect a failed start

Start, restart, and rebuild normally wait for effective readiness. If it exhausts its attempts, the command fails with `ServiceNotReadyError` and retains the applied app, routes, and volumes. When a restart policy allows recovery, an exit or observed restart can instead produce a warning and a `restarting` result before the probe passes.

```sh
lando app:config --format=json
lando logs -s app
```

`-s` is `--service`. Fix the app or the probe, then retry start:

```sh
lando start
```

An exhausted readiness probe stays fatal even if the service has a restart policy. To skip that command gate and keep process supervision, set `readiness: false`.

## Inspect configuration without claiming readiness

Run `lando info --format=json` for a running app. Each service entry in the result separates `health` from `readiness`. Native `health` reports provider-observed `healthy`, `starting`, or `unhealthy`; explicitly disabled native health is `not-monitored`, and missing evidence is `unknown`, not a failure.

The readiness `state` is `disabled`, `not-configured`, or `not-observed`. Its `source` is `authored`, `contributed`, `healthcheck` (fallback), `unknown` (historical provenance unavailable), or `none`. The metadata includes execution `target`, `userSource`, `listener`, timings, command presence, and a configuration pointer, not the raw command. A listener identifies the container endpoint a type-owned probe checks; it is not the host/service execution target.

Info never executes probes or reports a durable last-readiness proof. `not-observed` means configured but not proved by this inspection, even after a successful start. The `ready` result returned by start is the observed gate success for that invocation; a running container or healthy native check is not a substitute.
