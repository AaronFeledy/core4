# Make start wait for your app

Add `healthcheck:` so `lando start` waits until the app answers, not only until the process is running.

```yaml
name: myapp
services:
  app:
    type: "node:22"
    command:
      - node
      - server.mjs
    healthcheck: curl -fsS http://localhost:3000/
```

This edits an app that already serves HTTP on port 3000. `server.mjs` has to listen there and exit on SIGTERM. `type: "node:22"` is the Node 22 image, which includes `curl`, and Lando sets `PORT=3000`. Point the probe at that port.

```sh
lando start
lando app:config --format=json
```

Start waits for the probe to exit successfully. If its attempts run out, start reports a readiness failure. `app:config --format=json` shows the effective healthcheck configuration.

## Write the probe as a string or a list

A string runs through `sh -c`. The shell splits `curl -fsS http://localhost:3000/`.

A list is literal argv. Lando runs those strings as the program and its arguments, with no shell. Compose markers such as `CMD`, `CMD-SHELL`, and `NONE` belong in an object's `test` list, not in bare argv. A bare list that starts with one stays literal, so the probe tries to run a program called `CMD-SHELL`. `lando app:config:lint` flags that as the warning `healthcheck.bare-compose-marker` and the Landofile stays valid. See [Lint a Landofile](../landofile/config-lint.mdx#fix-healthcheck-warnings).

```yaml
services:
  app:
    type: "node:22"
    command:
      - node
      - server.mjs
    healthcheck:
      - curl
      - -fsS
      - http://localhost:3000/
```

Write the service `command:` as a list too, `[node, server.mjs]`, so the server receives SIGTERM directly rather than through `sh -lc`. Handle SIGTERM in the app so it stops before the runtime's timeout.

## Set timing on an object

Use an object when you need an interval, a timeout, retries, or a start period. Keep `kind: command`.

```yaml
services:
  app:
    type: "node:22"
    command:
      - node
      - server.mjs
    healthcheck:
      kind: command
      command:
        - curl
        - -fsS
        - http://localhost:3000/
      intervalSeconds: 7
      timeoutSeconds: 4
      retries: 9
      startPeriodSeconds: 15
```

`retries` is how many probes one start attempts after the start period. It isn't a count of `lando start` reruns. Failed probes during `startPeriodSeconds` don't use up those retries. The first success ends the wait.

Compose spellings work on the same object. Markers belong in `test`, not in a bare list:

```yaml
services:
  app:
    type: "node:22"
    healthcheck:
      test:
        - CMD
        - curl
        - -fsS
        - http://localhost:3000/
      interval: 5s
      timeout: 3s
      retries: 6
      start_period: 20s
```

`CMD` becomes an argv command. `CMD-SHELL` takes one shell string. `NONE` shows up as `false`. A duration such as `5s` becomes seconds. `lando app:config --format=json` prints that stored object, not the spelling you typed.

Pick one dialect and keep it across layers. When the merged object holds a Lando field such as `command` or `intervalSeconds`, Lando reads only the Lando fields and ignores `test`, `interval`, `timeout`, and `start_period`. If one layer wrote the Lando side and another wrote the Compose side, `lando app:config:lint` warns with `healthcheck.mixed-dialects` so you can see which timing survived.

Probe HTTP through a command such as `curl`. The bundled runner executes commands inside the service; it does not execute `kind: http` or `kind: tcp` checks. Authoring either kind fails planning with `LandofileValidationError` at `services.<name>.healthcheck.kind`, before Lando touches a container, with every offending service listed in one error. `lando app:config:lint` reports the same finding as a `landofile.healthcheck` violation, and `lando app:cache:refresh` runs the planning step on its own; `lando start` fails at the same point.

## Turn the probe off

`healthcheck: false` drops the probe. That includes one you wrote and a service type's default, such as MySQL's `mysqladmin ping`. Running-state checks remain in place; start no longer waits for an application probe.

Put the override in `.lando.local.yml` when only this machine should skip the probe. `false` replaces the base value. It doesn't merge with it. A later layer that sets an object doesn't bring the old probe back. It starts from the service type's default, or from nothing when the type has none.

Object spellings such as `disable: true`, `test: [NONE]`, or `kind: none` are not that barrier. They merge into an inherited object like any other mapping, and Lando still validates every sibling you wrote next to them: a bad `interval` or an empty `command` fails even though the probe is off. If the merged object keeps a Lando field such as `command`, `disable: true` loses to it and the probe stays on. Reach for literal `false` when you mean off.

```yaml
services:
  app:
    healthcheck: false
```

## Inspect a failed start

Start, restart, and rebuild normally wait for enabled probes. If a healthcheck exhausts its attempts, the command fails with `ServiceNotReadyError` and retains the applied app, routes, and volumes. When a restart policy allows recovery, an exit or observed restart can instead produce a warning and a `restarting` result before the probe passes.

```sh
lando app:config --format=json
lando logs -s app
```

`-s` is `--service`. Fix the app or the probe, then retry start:

```sh
lando start
```

An exhausted healthcheck stays fatal even if the service has a restart policy. To skip the probe and keep only the process-running check, set `healthcheck: false`.
