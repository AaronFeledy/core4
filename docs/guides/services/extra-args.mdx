# Append flags with extraArgs

Use `extraArgs:` when you want one more daemon flag and still want Lando's launcher. Lando keeps the port, persistence, password, and config-file flags it already owns, then appends your argv list. Replace the whole launcher with `command:` only when you need a different process.

```yaml
name: redis-extra-args
services:
  cache:
    type: redis
    port: 6380
    extraArgs:
      - --maxmemory
      - 10mb
```

`extraArgs:` is an argv list only. Each element is a text site: the same expression rules as a `command:` list element, including `{{ service.port }}` and numeric rendering. A higher Landofile layer replaces the whole list. An empty list clears it.

Save that Landofile, then check the plan without starting containers:

```sh
lando app:config:lint --format=json
lando app:cache:refresh --format=json
```

Lint must report `"valid": true`. Refresh must exit 0. The planned command keeps Lando's Redis flags and ends with your args, for example `redis-server --appendonly yes --port 6380 --maxmemory 10mb`.

## Supported types

These catalog types accept a non-empty `extraArgs:` list on a Lando-owned launcher:

| Type | What Lando still owns | Typical extra args |
| --- | --- | --- |
| `redis` | port, `persist:`, `creds.password` | `--maxmemory`, `--maxmemory-policy` |
| `valkey` | port, append-only persistence | same style as Redis |
| `memcached` | port | `-m`, `-c` |
| `minio` | API and console bind addresses | server flags after the image entrypoint |
| `postgres` | planned port, `config.server`, `-D`, `-c data_directory=...` | `-c max_connections=200` |
| `mysql` | planned port, `config.server`, `--datadir` | `--max-connections=77` |
| `mariadb` | planned port, `config.server`, `--datadir` | `--max-connections=77` |
| `mongodb` | planned port, `config.server` | `--wiredTigerCacheSizeGB`, `0.5` |

The catalog database launchers preserve the image entrypoint, pin the planned port, and keep any `config.server` flag. MariaDB's launcher also [refuses a downgrade](./mariadb.mdx#go-back-to-the-old-version) before the server starts. Custom images and Compose builds of these types reject `extraArgs:`.

Everything else rejects a non-empty list at `services.<name>.extraArgs` with a located `LandofileValidationError` and type-specific remediation. That includes Solr, Varnish, nginx, Apache, PHP, language runtimes, raw `lando` and `compose`, and image-default env-configured types such as Elasticsearch, RabbitMQ, and Mailpit.

## Keep Lando's launcher

Leave `command:` and `entrypoint:` unset. Lando owns the process argv, pins the planned port, and appends `extraArgs:` after its own flags. Shell-wrapped launchers (Redis with a password, MinIO's `sh -c` entrypoint) pass your tokens as positional parameters so a shell never re-parses them.

Do not put a listener flag Lando already owns in `extraArgs:` (`--port` for Redis or Valkey, `-p` for Memcached, `--address` for MinIO, `-c port=` for Postgres, and the matching MySQL, MariaDB, and MongoDB port flags). Set `port:` instead. Lint and planning name the offending index.

## When to use command instead

Author `command:` when you replace the process entirely. Then you own every flag, including the port. Use `{{ service.port }}` so the listener stays tied to `port:`:

```yaml
services:
  cache:
    type: redis
    port: 6380
    command: [redis-server, --port, "{{ service.port }}", --maxmemory, 10mb]
```

See [Your service's own port](../landofile/expressions.mdx#your-services-own-port). Redis rejects `command:` together with managed `creds.password` or `persist:`; put those flags in `command:` yourself, or stay on `extraArgs:` and keep Lando's launcher.

A non-empty `extraArgs:` with any effective authored `command:` or `entrypoint:` fails at `services.<name>.extraArgs` with remediation to put the flags in `command:`.
