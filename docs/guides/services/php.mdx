# Add PHP

Add `type: php:8.3` under `services` in `.lando.yml` to serve PHP with Apache on port `80`. PHP needs a minor version; there is no bare `type: php` alias. In your PHP project root, save:

```yaml
name: php-demo
services:
  app:
    type: "php:8.3"
    primary: true
```

Put an `index.php` in that directory, then run from the host:

```sh
lando app:config:lint --format=json
lando start
lando info
```

Open the app URL from `lando info` and check that your page loads. If startup
fails, inspect `lando logs -s app`. Your project is mounted read-write at `/app`.

## Pick a serving mode

`via:` picks the image variant and process shape:

| `via:` | Image | What you get |
| --- | --- | --- |
| `apache` (default) | `php:<version>-apache-bookworm` | Apache + mod_php on port `80`. `webroot:` and `allowOverride:` apply. |
| `fpm` | `php:<version>-fpm-bookworm` | PHP-FPM on port `9000`. Front it with `nginx` and `backend:`. `allowOverride:` is rejected. |
| `cli` | `php:<version>-cli-bookworm` | Idle worker for tooling and `command:`. No web server, no HTTP route. |

Lando enables `mod_rewrite` while building stock Apache services. Set
`allowOverride: true` if your app uses `.htaccess` rewrite rules; it defaults to
`false`. PHP framework recipes such as Laravel and Backdrop already set it.
Custom images, `build.context`, and authored `command:` or `entrypoint:` values own their Apache
configuration, including module setup. After upgrading Lando, run `lando start`
to apply the updated default build key to existing apps.

Pair FPM with nginx by naming the PHP service on `backend:`. The nginx service
generates a FastCGI upstream pointing at that service on port `9000`:

```yaml
name: php-fpm-nginx
services:
  appserver:
    type: "php:8.3"
    via: fpm
    primary: true
  edge:
    type: nginx
    backend: appserver
```

## Run as a non-root user

To run stock Apache PHP as the image's `www-data` account, save this as
`.lando.yml` in your PHP project root. Use port `8080` for a portable non-root
listener: permission to bind ports below `1024` depends on runtime policy.
Put an `index.php` in that directory for Apache to serve:

```yaml
name: php-nonroot
services:
  appserver:
    type: php:8.3
    user: www-data
    port: 8080
```

Lando keeps `www-data`'s home at `/var/www`, the directory the account's
passwd entry points at. The image ships it owned by root, so Lando prepares it
for `www-data` during the image build. The fresh home volume starts owned by
`www-data`, and Composer and shell caches there survive a rebuild. Run
`lando info` to see the mount labeled `(home)`; see
[Keep a service home across rebuilds](./home-and-host.mdx) for volume naming
and what happens when you change `user:`.

From that directory on your host, start the app and find its URL:

```sh
lando start
lando info
lando logs -s appserver
```

Open the appserver URL from `lando info` and check that your page loads. Apache
access and error logs remain available through `lando logs`; you don't need
to make `/var/log/apache2` writable or add your own log redirection.

Lando passes Apache's serving directives at launch without writing into
root-owned configuration files. It prepares the error pages and removes the
stock default site and extra access-log configuration during the image build.
Access logs go to container stdout and error logs to container stderr. An
authored `port:` also changes Apache's listener, not just Lando's endpoint;
choose `1024` or above for portable non-root use.

If logs show a bind permission error, check `port:` first. Omitting it keeps
Apache on `80`; the logging setup does not grant permission to bind low ports.
Before start hooks and builds, Lando warns with
`LANDO_NONROOT_LOW_PORT_UNVERIFIED` when a declared user other than explicit
root/UID 0 has a planned container port below `1024`. For a named user, the
warning is conditional on that name resolving to a non-root UID. It does not
probe permissions, reject the app, or change the port. A provider name alone
does not establish whether the bind will succeed.

If you set your own `command:` or `entrypoint:`, use a custom `image:`, or
provide `build.context`, you own the serving and logging configuration instead.
Lando never appends `Listen`, pool, or other listen flags to an authored
launcher; match the daemon to `port:` yourself. See
[Replace the image](./php-customization.mdx#replace-the-image).
For an authored command, entrypoint, custom image, or replacement build, a startup failure includes a hint naming
Apache's `Listen <port>` or PHP-FPM's `listen = <port>` with the planned port.
`via: cli` has no listener and no listener hint.

`via: fpm` works the same way with a different file. Lando writes its pool
override to `/tmp/lando-php-fpm.conf` and starts the daemon with
`php-fpm -y /tmp/lando-php-fpm.conf`, so the image's `php-fpm.d` tree is never
touched:

```yaml
services:
  appserver:
    type: php:8.3
    via: fpm
    user: www-data
```

FPM listens on `9000`, so there's no privileged port to worry about. Under a
non-root user php-fpm logs that the pool's `user` and `group` directives are
ignored. That's a notice, not a failure; the pool already runs as the account
you set.

Generated Apache services expose `access` on stdout and `error`
on stderr. Generated FPM services expose `access` and `error`,
both on the same stderr pipe. These names select pipes, not individual writers.
See [Read service logs](../cli/service-logs.mdx#select-a-php-console-alias).

## Set the webroot yourself

`framework: wordpress` installs pinned, checksum-verified WP-CLI on stock PHP images, sets `WP_CLI_ALLOW_ROOT=1` for tooling, and writes `conf.d/50-lando-wordpress.ini` with `memory_limit = 512M` for CLI and web PHP alike; a later drop-in such as `zz-custom.ini` overrides it. No framework name switches the served webroot for Drupal, Laravel, Symfony, or WordPress. Omit `webroot:` or use `.` to serve the app root at `/app`. To serve a framework public directory, set `webroot: public`, or put nginx in front with `via: fpm`. Relative paths resolve against `/app`; `LANDO_WEBROOT` inside the container is always the resolved absolute path. An absolute value such as `webroot: /srv/site` is allowed when you need a very specific container path outside the usual app layout. For a custom `php.ini`, use a read-only mount or a Compose `configs:` grant. See [Customize PHP](./php-customization.mdx#mount-a-custom-phpini) for both forms.

## Run Composer

Declare a Composer tooling alias targeting your PHP service before running this command. PHP recipes normally include it; a hand-written service needs its own tooling entry:

```sh
lando composer install
```

Stock PHP services install a checksum-pinned Composer 2 release (`2.10.2`).
Set `composer:` on the service to pick a different pinned version, skip the install entirely, or use the object form to also bake global Composer packages into the image. See [PHP Composer workflows](../tooling/php-composer-workflows.mdx).

A `php` alias runs the CLI inside the service:

```sh
lando php -v
```

## Pin a version

Pin one of `8.1`, `8.2`, `8.3`, `8.4`, `8.5`, or `8.6` under `type`.
Versions 8.1 through 8.5 use Bookworm tags for the selected serving mode;
8.6 uses the official `8.6-rc` Bookworm tags until GA:

```yaml
services:
  app:
    type: php:8.2
```

`image:` or a Compose build with `build.context` replaces Lando's stock image
setup. You supply the tools, extensions, and serving configuration; see
[Replace the image](./php-customization.mdx#replace-the-image). Additive
`build.artifact` and `build.app` steps alone keep the stock PHP setup.
