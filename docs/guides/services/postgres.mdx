# Add PostgreSQL

Put `type: postgres` in your services block. Lando pulls `postgres:16` and listens on `5432`:

```yaml
name: postgres-demo
services:
  db:
    type: postgres
```

Without a `creds:` block, Lando generates the password. Do not assume it is `lando`. To choose explicit credentials, provide `user`, `database`, and `password` together:

```yaml
services:
  db:
    type: postgres
    creds:
      user: lando
      database: postgres-demo
      password: local-development-only
```

For a private password, use `password: '${secret:DB_PASSWORD}'` and set its [secret store](../config/secret-stores.mdx) value before starting the app. The server, the `psql` task, and `lando db:*` all receive that same resolved value.

Start it. Lando puts the database on the app network:

## Connect from another service

Other services use the service name as the hostname. Here that's `db`. Defaults:

| Setting | Value |
| --- | --- |
| Host | `db` |
| Database | the app name (`postgres-demo`); override with `database:` under `services.db` |
| User | `lando` |
| Password | generated when omitted; read it with `{{ services.db.creds.password }}` |

Hand the consuming service a URL built from `db`'s resolved credentials and port:

```yaml
services:
  web:
    type: "node:22"
    environment:
      DATABASE_URL: "postgresql://{{ services.db.creds.user }}:{{ url.encodeComponent(services.db.creds.password) }}@db:{{ services.db.port }}/{{ services.db.creds.database }}"
  db:
    type: postgres
```

`web` gets the real password, and it follows an authored `creds:` block. Don't hardcode it. `{{ services.db.port }}` is `5432` here and follows `port:` when you set one. `url.encodeComponent()` percent-encodes the password for the URL, which matters once you author one with `@` or `/` in it. `lando info` redacts the password, so it's no place to copy it from. A password authored as a `${secret:...}` reference travels through this URL as a reference and resolves when `web` is created. See [Plan-time service credentials](../landofile/expressions.mdx#plan-time-service-credentials).

## Open the client

The `postgres` type ships the `psql` client task. `lando start` returns only after Postgres accepts TCP connections, so the client works as soon as start finishes, even on a fresh volume that is still running its first-boot setup:

```sh
lando psql
```

That's a live session: type queries, page through long results, `\q` to leave. Need one answer, not a session? Pass `-c`:

```sh
lando psql -c 'SELECT version();'
```

Import a dump with `lando db:import`. See [Import and export app databases](../tooling/db-import-export.mdx). Or pipe a plain SQL file straight into the client:

```sh
lando psql < dump.sql
```

Piped input skips the live session: `psql` runs the file, reaches its end, and exits.

## Use your own postgresql.conf

Set `config.server` to an app-relative file when the stock config isn't enough:

```yaml
services:
  db:
    type: postgres
    config:
      server: ./config/postgresql.conf
```

Lando mounts that file read-only at `/etc/lando/postgresql.conf` and starts the server with `-c config_file=/etc/lando/postgresql.conf`. It has to be a regular file, not a directory.

Lando's planned port, `port:` or the default, beats a port line in your config file.

The path has to stay inside the app root. Absolute paths, paths that climb out of the app root, and symlinks that point outside it are rejected when Lando plans the app, before anything starts.

If you also set `command:` or `entrypoint:` on the service, yours wins. Lando won't append the `-c config_file=...` flag to a command you wrote yourself, so pass it in your own command if you still want the file loaded.

## Change the port

Set `port:` when something else needs `5432`. Lando moves the server's listener, healthcheck, endpoint, and its own clients together:

```yaml
services:
  db:
    type: postgres
    port: 5433
```

Other services then connect to `db:5433`, and a `{{ services.db.port }}` expression in their config follows along. Lando sets `PGPORT` from `port:`. An authored `PGPORT` must match the planned port, or planning fails; `lando app:config:lint` reports the mismatch at `services.db.environment.PGPORT` with the `port:` value to set. With `config.server`, Lando pins `port:` or the default on its command line.

The service also exposes `LANDO_DB_PORT=5433`. The `psql` task and `lando db:*` commands pass the planned port explicitly, including for local socket connections. If you author `command:` or `entrypoint:`, you own the daemon's flags; make your launcher honor the planned port, including when you load a config file yourself.

Apply the change with `lando rebuild`, then check the running listener:

```sh
lando psql -c 'SHOW port;'
```

## Pin a version

Put the major in `type:` when `16` isn't the one you want. Lando ships Postgres 15, 16, 17, and 18:

```yaml
services:
  db:
    type: postgres:18
```

Any other version fails when Lando plans the app, before anything starts. Every major, 18 included, keeps its data in the `<app>-postgresql-data` volume.

Changing the major doesn't upgrade an existing database. Postgres refuses to start on files from another major, so the `lando start` that applies the change fails with the server's own error. Move the data through a dump:

1. Export it while the old major still runs: `lando db:export dump.sql.gz`
2. Delete the old data volume: `lando destroy -y --volumes`
3. Change `type:` to the new major, then start: `lando start`
4. Load the dump: `lando db:import dump.sql.gz --yes`

For vector search on Postgres 18, [use a pgvector image](./postgres-pgvector.mdx).
