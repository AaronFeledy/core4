# Add PostgreSQL

Add `type: postgres` under `services` in `.lando.yml`. Lando pulls `postgres:16` and listens on `5432`:

```yaml
name: postgres-demo
services:
  db:
    type: postgres
```

Without a `creds:` block, the password is `lando`. `lando info` prints that published default. To choose your own, set it under `creds:`. One member is enough. `user` and `database` keep their defaults when you leave them out:

```yaml
services:
  db:
    type: postgres
    creds:
      password: local-development-only
```

`creds.password` is the superuser password, so Postgres takes no `creds.rootPassword`.

For a private password, use `password: '${secret:DB_PASSWORD}'` and set its [secret store](../config/secret-stores.mdx) value before starting the app. The server, the `psql` task, and `lando db:*` all receive that same resolved value.

Start it. Lando puts the database on the app network:

## Connect from another service

Other services use the service name as the hostname. Here that's `db`. Defaults:

| Setting | Value |
| --- | --- |
| Host | `db` |
| Database | the folder's data name (here `postgres-demo`, the name this folder's data was first created under); override with `creds.database` under `services.db` |
| User | `lando` |
| Password | `lando`; `lando info` prints it, and another service reads `{{ services.db.creds.password }}` |

Hand the consuming service a URL built from `db`'s resolved credentials and port:

```yaml
services:
  web:
    type: "node:22"
    environment:
      DATABASE_URL: "postgresql://{{ services.db.creds.user }}:{{ url.encodeComponent(services.db.creds.password) }}@db:{{ services.db.port }}/{{ services.db.creds.database }}"
  db:
    type: postgres
```

`web` gets the real password, and it follows an authored `creds:` block. Don't hardcode it. `{{ services.db.port }}` is `5432` here and follows `port:` when you set one. `url.encodeComponent()` percent-encodes the password for the URL, which matters once you author one with `@` or `/` in it. `lando info` prints this published default, so you can copy it from there. An authored password that is not a published default stays `[redacted]`. A password authored as a `${secret:...}` reference travels through this URL as a reference and resolves when `web` is created. See [Plan-time service credentials](../landofile/expressions.mdx#plan-time-service-credentials).

## Open the client

The `postgres` type ships the `psql` client task. `lando start` returns only after Postgres accepts TCP connections, so the client works as soon as start finishes, even on a fresh volume that is still running its first-boot setup:

```sh
lando psql
```

The `pg_isready` probe checks whether the server accepts connections, not whether your credentials work. See [Recover when credentials don't match](#recover-when-credentials-dont-match).

That's a live session: type queries, page through long results, `\q` to leave. Need one answer, not a session? Pass `-c`:

```sh
lando psql -c 'SELECT version();'
```

Import a dump with `lando db:import`. See [Import and export app databases](../tooling/db-import-export.mdx). You can also pipe a plain SQL file into the client. This executes the dump's statements against the database, so back up data you need before running it:

```sh
lando psql < dump.sql
```

Piped input skips the live session: `psql` runs the file, reaches its end, and exits.

## Use your own postgresql.conf

Set `config.server` to an app-relative file when the stock config isn't enough:

```yaml
services:
  db:
    type: postgres
    config:
      server: ./config/postgresql.conf
```

Lando mounts that file read-only at `/etc/lando/postgresql.conf` and starts the server with `-c config_file=/etc/lando/postgresql.conf`. It has to be a regular file, not a directory.

Lando's planned port, `port:` or the default, beats a port line in your config file.

The path has to stay inside the app root. Absolute paths, paths that climb out of the app root, and symlinks that point outside it are rejected when Lando plans the app, before anything starts.

To add daemon flags without replacing Lando's launcher, use
[`extraArgs:`](./extra-args.mdx):

```yaml
services:
  db:
    type: postgres
    extraArgs:
      - -c
      - max_connections=200
```

Lando keeps the planned port and any `config.server` flag, then appends your
list. Do not put `-p`, `-c port=...`, or `-c config_file=...` in `extraArgs:`;
set `port:` or `config.server` instead. Custom images and Compose builds reject
the key.

If you also set `command:` or `entrypoint:` on the service, yours wins. Lando won't append the `-c config_file=...` flag to a command you wrote yourself, so pass it in your own command if you still want the file loaded.

## Change the port

Set `port:` when something else needs `5432`. Lando moves the server's listener, healthcheck, endpoint, and its own clients together:

```yaml
services:
  db:
    type: postgres
    port: 5433
```

Other services then connect to `db:5433`, and a `{{ services.db.port }}` expression in their config follows along. Lando sets `PGPORT` from `port:`. An authored `PGPORT` must match the planned port, or planning fails; `lando app:config:lint` reports the mismatch at `services.db.environment.PGPORT` with the `port:` value to set. With `config.server`, Lando pins `port:` or the default on its command line.

The service also exposes `LANDO_DB_PORT=5433`. The `psql` task and `lando db:*` commands pass the planned port explicitly, including for local socket connections. If you replace `command:` or `entrypoint:`, pass `-p "{{ service.port }}"` to `postgres`, including when you load your own config file. The [port expression](../landofile/expressions.mdx#your-services-own-port) supplies the value, not the flag.

Apply the change with `lando rebuild`, then check the running listener:

```sh
lando psql -c 'SHOW port;'
```

## Recover when credentials don't match

After editing `creds`, run `lando start`. Lando applies the settings to the catalog server without dropping or renaming existing roles or databases. For these updates, Lando uses a `lando_admin` superuser role with no password over the container's trusted Unix socket. Lando refuses to use this role if the server trusts connections from beyond loopback.

If start warns that it couldn't update the credentials, follow [Keep database credentials in sync](../tooling/db-creds-apply.mdx) to preview and apply a repair with `lando db:creds:apply`.

## Pin a version

Put the major in `type:` when `16` isn't the one you want. Lando ships Postgres 15, 16, 17, and 18:

```yaml
services:
  db:
    type: postgres:18
```

Any other version fails when Lando plans the app, before anything starts. Every major, 18 included, keeps its data in the service's own `lando-<data-name>--<service>--postgresql-data` volume. That name follows the folder's data name across renames.

For vector search on Postgres 18, [use a pgvector image](./postgres-pgvector.mdx).

## Change versions

PostgreSQL can't open an existing data directory from a different major. If you change `postgres:16` to `postgres:17` while 16 is still running, `lando start --format=json` reports `ServiceDataVersionError` with `dataVersion.direction: "upgrade"` and leaves 16 running. If the old server was stopped, the native refusal reports the same versions under `ServiceNotReadyError`.

To move the data, export it and restore it on the new major. Before deleting volumes, verify the export and back up other services: volume deletion removes every service's data in the app.

1. Export it while the old major still runs: `lando db:export dump.sql.gz --service db`
2. Delete the old data volume: `lando destroy -y --volumes`
3. Change `type:` to the new major, then start: `lando start`
4. Load the dump: `lando db:import dump.sql.gz --service db --yes`
