# Add SQL Server

Use an amd64 host or a provider with architecture emulation; otherwise planning fails before the container starts. This service uses the Developer edition and sets `ACCEPT_EULA=Y`, so review the upstream license terms before starting it.

Add `type: mssql` under `services` in `.lando.yml`. That shorthand is the 2022 image. It listens on `1433`, keeps data in `/var/opt/mssql`, and ships `sqlcmd` tooling:

```yaml
name: mssql-demo
services:
  database:
    type: mssql
```

Start the service and check the database:

```sh
lando start
lando sqlcmd -d master -Q "SELECT name, state_desc FROM sys.databases"
lando logs --service database
```

On the selected catalog image, Lando starts SQL Server, waits for it to accept
connections, and creates the resolved `creds.database` if it doesn't exist. The
default name is the folder's data name (the name this folder's data was first created under). Every start checks again without dropping or
replacing an existing database. Initialization failure fails startup. The
healthcheck connects to `master` and checks that the target database is online
and accessible, including after a restart. It never creates a database or keeps
a target connection open.

When Lando creates the database, its startup logs include a
`lando.database.created` record naming that database. A warm startup reuses the
database without emitting another creation record.

A custom `image:`, `build:`, `command:`, or `entrypoint:` owns initialization
instead. An explicit `image:` equal to the selected catalog image still gets
Lando's launcher unless you override the build or process. Your custom startup
must make the configured database available before the read-only healthcheck can
pass.

## Pick a version

Use `mssql:2022` when you want the default major written out. Choose `mssql:2019` for the previous line:

```yaml
services:
  database:
    type: mssql:2019
```

## Set credentials

Set a member under `creds:` when you need an explicit value. A member you leave out keeps its default. `rootPassword` becomes `SA_PASSWORD` inside the container. The login is `sa`. Lando sets `ACCEPT_EULA=Y` and `MSSQL_PID=Developer` on the image. Omit `rootPassword` and the password is `Landolando1`. `lando info` prints that published default. SQL Server rejects `lando`, so this default is longer and mixes case and a digit.

Use `sa`; another `creds.user` fails planning rather than creating a separate login.
`creds.password`, `creds.rootPassword`, and any authored native password aliases
must agree. Secret references must name the same reference, without reading the
secret during planning. The launcher and generated clients read the password from
the runtime environment, not a password argument.

Replace `ReplaceMe!2026` with a private password before using this example. SQL Server requires at least eight characters and characters from at least three categories: uppercase letters, lowercase letters, digits, and symbols. See [Microsoft's container password requirements](https://learn.microsoft.com/sql/linux/install-upgrade/quickstart-install-docker). Alternatively, omit `rootPassword` and use `Landolando1`.

```yaml
services:
  database:
    type: mssql
    creds:
      rootPassword: "ReplaceMe!2026"
      database: LANDO_DB
```

Another service reads the resolved `sa` password from its own environment:

```yaml
services:
  web:
    type: "node:22"
    environment:
      DB_HOST: database
      DB_USER: sa
      DB_PASSWORD: "{{ services.database.creds.rootPassword }}"
```

See [Plan-time service credentials](../landofile/expressions.mdx#plan-time-service-credentials).

`lando start` signs in with the configured administrator password when it started or recreated the database container, or when the planned connection changed since the last apply, and warns when the running server rejects it. An unchanged running database is checked by `lando doctor --app`, `lando restart`, and `lando rebuild`. See [Recover when credentials don't match](#recover-when-credentials-dont-match).

The type ships the `sqlcmd` client task. After start:

```sh
lando sqlcmd -Q "SELECT @@VERSION"
```

## Change the port

Set `port:` to move the daemon's listener, healthcheck, endpoint, and Lando's own clients together:

```yaml
services:
  database:
    type: mssql
    port: 14330
```

Other services connect to `database` on port `14330`; SQL Server tools write that as `database,14330`. Lando sets `MSSQL_TCP_PORT` for the server and exposes the same value as `LANDO_DB_PORT`. The `sqlcmd` task and `lando db:*` commands pass `-S localhost,14330`.

Ports `135`, `1431`, and `1434` fail during planning. SQL Server reserves `135` for its MSDTC RPC endpoint mapper, `1431` for an internal loopback connection, and `1434` for its dedicated admin connection.

Lando sets `MSSQL_TCP_PORT` from `port:`. An authored `MSSQL_TCP_PORT` must match the planned port, or planning fails; `lando app:config:lint` reports the mismatch at `services.<name>.environment.MSSQL_TCP_PORT`. An authored `command:` or `entrypoint:` owns the daemon's flags and must honor that port.

Apply the change with `lando rebuild`, then connect through the generated client:

```sh
lando sqlcmd -Q "SELECT @@VERSION"
```

## Recover when credentials don't match

`creds:` seeds a fresh volume. The image ignores it once `/var/opt/mssql` holds data, so changing `rootPassword` on an existing app changes what Lando's clients send, not the `sa` password the server stores. SQL Server's startup launcher signs in before readiness, so a rejected administrator login fails `lando start` itself; Lando keeps the server's failure and adds the credential recovery advice. `lando restart` and `lando rebuild` check the services they restart, and `lando doctor --app` checks a running app, so a server that was already running and rejects the login still gets a warning from those commands.

Fix it without losing data, in this order:

1. Put `creds.rootPassword` back to the value the volume was created with, then run `lando start`.
2. To keep the new password, sign in with the old one and change it. Here the service is named `database`, and `-P` with no value prompts:

   ```sh
   lando exec database -- /opt/mssql-tools18/bin/sqlcmd -S localhost,1433 -U sa -C -P
   ```

   Then, in that shell, replace `<new-password>`:

   ```sql
   ALTER LOGIN sa WITH PASSWORD = '<new-password>';
   GO
   ```

   Set `creds.rootPassword` to the new value and run `lando start` again.
3. Only when the data is disposable, start over. This deletes the database:

   ```sh
   lando destroy -y --volumes
   lando start
   ```

Lando never picks option 3 for you. `lando doctor --app` runs the same login check against a running app and reports what it observed.

## Plan on amd64

Upstream SQL Server images are amd64-only. On a non-amd64 host the type fails at plan time unless the provider declares architecture emulation. Use an amd64 host or a provider with architecture emulation. This is a capability check, not a container start failure.
