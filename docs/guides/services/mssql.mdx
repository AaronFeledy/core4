# Add SQL Server

Use an amd64 host or a provider with architecture emulation; otherwise planning fails before the container starts. This service uses the Developer edition and sets `ACCEPT_EULA=Y`, so review the upstream license terms before starting it.

Add `type: mssql` under `services` in `.lando.yml`. That shorthand is the 2022 image. It listens on `1433`, keeps data in `/var/opt/mssql`, and ships `sqlcmd` tooling:

```yaml
name: mssql-demo
services:
  database:
    type: mssql
```

Start the service and check the database:

```sh
lando start
lando sqlcmd -d master -Q "SELECT name, state_desc FROM sys.databases"
```

On the selected catalog image, Lando starts SQL Server, waits for it to accept
connections, and creates the resolved `creds.database` if it doesn't exist. The
default name is your app name. Every start checks again without dropping or
replacing an existing database. Initialization failure fails startup. The
healthcheck connects to `master` and checks that the target database is online
and accessible, including after a restart. It never creates a database or keeps
a target connection open.

A custom `image:`, `build:`, `command:`, or `entrypoint:` owns initialization
instead. An explicit `image:` equal to the selected catalog image still gets
Lando's launcher unless you override the build or process. Your custom startup
must make the configured database available before the read-only healthcheck can
pass.

## Pick a version

Use `mssql:2022` when you want the default major written out. Choose `mssql:2019` for the previous line:

```yaml
services:
  database:
    type: mssql:2019
```

## Set credentials

Set `creds:` when you need explicit values. `rootPassword` becomes `SA_PASSWORD` inside the container. The login is `sa`. Lando sets `ACCEPT_EULA=Y` and `MSSQL_PID=Developer` on the image. Omit `rootPassword` and Lando generates one per app and service, so don't guess it. `lando info` redacts it too.

Use `sa`; another `creds.user` fails planning rather than creating a separate login.
`creds.password`, `creds.rootPassword`, and any authored native password aliases
must agree. Secret references must name the same reference, without reading the
secret during planning. The launcher and generated clients read the password from
the runtime environment, not a password argument.

Replace `ReplaceMe!2026` with a private password before using this example. SQL Server requires at least eight characters and characters from at least three categories: uppercase letters, lowercase letters, digits, and symbols. See [Microsoft's container password requirements](https://learn.microsoft.com/sql/linux/install-upgrade/quickstart-install-docker). Alternatively, omit `rootPassword` and use Lando's generated value.

```yaml
services:
  database:
    type: mssql
    creds:
      user: sa
      rootPassword: "ReplaceMe!2026"
      database: LANDO_DB
```

Another service reads the resolved `sa` password from its own environment:

```yaml
services:
  web:
    type: "node:22"
    environment:
      DB_HOST: database
      DB_USER: sa
      DB_PASSWORD: "{{ services.database.creds.rootPassword }}"
```

See [Plan-time service credentials](../landofile/expressions.mdx#plan-time-service-credentials).

The type ships the `sqlcmd` client task. After start:

```sh
lando sqlcmd -Q "SELECT @@VERSION"
```

## Change the port

Set `port:` to move the daemon's listener, healthcheck, endpoint, and Lando's own clients together:

```yaml
services:
  database:
    type: mssql
    port: 14330
```

Other services connect to `database` on port `14330`; SQL Server tools write that as `database,14330`. Lando sets `MSSQL_TCP_PORT` for the server and exposes the same value as `LANDO_DB_PORT`. The `sqlcmd` task and `lando db:*` commands pass `-S localhost,14330`.

Port `1434` fails during planning. SQL Server reserves it for its dedicated admin connection, so a server listening there never becomes ready.

Lando sets `MSSQL_TCP_PORT` from `port:`. An authored `MSSQL_TCP_PORT` must match the planned port, or planning fails; `lando app:config:lint` reports the mismatch at `services.<name>.environment.MSSQL_TCP_PORT`. An authored `command:` or `entrypoint:` owns the daemon's flags and must honor that port.

Apply the change with `lando rebuild`, then connect through the generated client:

```sh
lando sqlcmd -Q "SELECT @@VERSION"
```

## Plan on amd64

Upstream SQL Server images are amd64-only. On a non-amd64 host the type fails at plan time unless the provider declares architecture emulation. Use an amd64 host or a provider with architecture emulation. This is a capability check, not a container start failure.
