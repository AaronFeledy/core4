# Add Ruby

Add `type: ruby:3.3` to your primary service in `.lando.yml` at the root of your Ruby project. Ruby has no bare `type: ruby` alias, so pin a version.
Lando currently supports `ruby:3.3`, and the default image is
`ruby:3.3-slim`. Your repository is bind-mounted read-write at `/app` by
default, which is also the working directory:

```yaml
name: ruby-demo
services:
  app:
    type: "ruby:3.3"
    primary: true
```

## Run the app

The default keep-alive command holds the container open so you can install
gems and run your app. The commands below assume an existing Rails project and a `bundle` tooling alias targeting `app`; the Ruby service alone does not declare that alias:

Add `framework: rails` to the `app` service before running Rails so it receives the host default described below.

```sh
# Declare a bundle tooling alias to install gems inside the service
lando bundle install

# Run Rails using the preset's PORT and BINDING
lando exec app -- bundle exec rails server
```

## Pass `port:` to your Ruby server

| Framework | Port variable | Default host variable | Who reads it |
| --- | --- | --- | --- |
| `none` | `PORT`, default `3000` | None | Sinatra reads `PORT`; custom code can read `ENV["PORT"]` |
| `rails` | `PORT`, default `3000` | `BINDING=0.0.0.0` | `rails server` reads both variables |

Set `port:` to change the internal HTTP endpoint and `PORT` together. An authored `environment.PORT` must be a literal integer equal to the planned port; malformed or unequal values fail planning at `services.app.environment.PORT`, including inherited `appEnv` and env-file values. Set `port:` instead. `BINDING` is an overridable host default, not a port setting.

For Sinatra in development, pass `-o 0.0.0.0` when starting the app, such as `lando exec app -- bundle exec ruby app.rb -o 0.0.0.0`. Sinatra reads `PORT` but otherwise binds localhost in development. Non-Rails servers do not gain Rails' `BINDING` behavior.

Ruby publishes its port endpoint but has no default healthcheck or readiness probe, even with an authored `command:`. Add `readiness:` when you want start to wait for application readiness; use `healthcheck:` separately for native ongoing monitoring. Without an effective readiness command, Lando checks that the process stays running.

## Set the Ruby webroot context

Run `lando start` after adding `framework: rails` and your `webroot:` to the service:

```yaml
services:
  app:
    type: "ruby:3.3"
    primary: true
    framework: rails
    webroot: frontend/public
```

Rails defaults to `webroot: public`; without a framework, Ruby defaults to `.`.
Your `webroot:` wins in either case. Relative paths resolve against
`appMount.target` (default `/app`), so this sets `LANDO_WEBROOT` to
`/app/frontend/public`. Set `appMount: /site` to get
`/site/frontend/public`, or use an absolute container path such as `/srv/www`.
Relative paths can't escape the app mount with `..`.

Verify the value inside the running service:

```sh
lando start
lando exec app -- printenv LANDO_WEBROOT
```

The webroot doesn't move the working directory or start a Rails server.
Use `workingDirectory:` and `command:` for those. The Rails preset supplies
development environment and host defaults; authored values for those defaults still win.
With `appMount: false`, Ruby omits its implicit webroot context. If you explicitly
set a relative or absolute `webroot:`, planning fails instead of silently dropping it.
Remove `webroot:` or enable the app mount. A plugin can also supply a feature
that declares and handles the effective root. That declaration means root support,
not that an HTTP server is running.

Check planning without starting services:

```sh
lando app:cache:refresh --format=json
```

## Pin a version

Set `image:` to use the full (non-slim) or an alternate Ruby base image when
`ruby:3.3-slim` isn't what you want. Slim lacks build tools that some gems need:

```yaml
services:
  app:
    type: "ruby:3.3"
    image: ruby:3.3
```
