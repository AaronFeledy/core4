# Add Ruby

Add `type: ruby:3.3` to your primary service in `.lando.yml` at the root of your Ruby project. Ruby has no bare `type: ruby` alias, so pin a version.
Lando currently supports `ruby:3.3`, and the default image is
`ruby:3.3-slim`. Your repository is bind-mounted read-write at `/app` by
default, which is also the working directory. `.bundle` and `vendor/bundle`
are volumes that belong to the service, so Bundler's settings and installed
gems stay out of your project directory:

```yaml
name: ruby-demo
services:
  app:
    type: "ruby:3.3"
    primary: true
```

## Run the app

The default keep-alive command holds the container open so you can install
gems and run your app. The Ruby service adds no tooling by itself, so declare
the commands you want. This Landofile is for an existing Rails project. It adds
`framework: rails`, so the service receives the host default described below,
plus `lando bundle` and `lando rails`:

```yaml
name: ruby-demo
services:
  app:
    type: "ruby:3.3"
    primary: true
    framework: rails
tooling:
  bundle:
    service: app
    cmd: [bundle]
    wrapper: true
  rails:
    service: app
    cmd: [":ruby-local", "rails"]
    wrapper: true
```

Run these from the app directory on your host:

```sh
lando start
lando bundle install
lando rails server
```

`lando rails server` runs the Rails your `Gemfile.lock` pins and uses the
preset's `PORT` and `BINDING`.

### Run commands through your bundle

`:ruby-local` is a launcher that every Ruby service declares. Put it first in
an argv-list `cmd`, then the command. It decides how to run that command each
time, from the directory the command runs in:

| What Bundler finds | `lando rails server` runs |
| --- | --- |
| A `Gemfile` or `gems.rb` with its lockfile | `bundle exec rails server` |
| No Gemfile, or a Gemfile with no lockfile yet | `rails server` |

Bundler looks in the working directory first and then in each parent
directory. Set `BUNDLE_GEMFILE` to point somewhere else, and `:ruby-local`
uses that file. If it names a file that doesn't exist, the command fails.

When a lockfile exists, Bundler owns the result. A missing gem or a version
conflict is reported as Bundler printed it, and Lando doesn't retry with the
system copy of the tool. Run `lando bundle install` and try again.

The same marker works as the first item of an argv-list service `command`.
[Run a command through the project's toolchain](../tooling/flags-and-args.mdx#run-a-command-through-the-projects-toolchain)
covers where markers are recognized and how a bad one fails.

## Pass `port:` to your Ruby server

See the [Ruby listener reference](../../reference/service-listeners.mdx#ruby) for default ports, variables, and host defaults. Rails reads `PORT` and `BINDING`; Sinatra reads `PORT`, and custom code can read `ENV["PORT"]`.

Set `port:` to change the internal HTTP endpoint and `PORT` together. An authored `environment.PORT` must be a literal integer equal to the planned port; malformed or unequal values fail planning at `services.app.environment.PORT`, including inherited `serviceDefaults.environment` and env-file values. Set `port:` instead. `BINDING` is an overridable host default, not a port setting.

For Sinatra in development, pass `-o 0.0.0.0` when starting the app. Sinatra reads `PORT` but otherwise binds localhost in development, and non-Rails servers do not gain Rails' `BINDING` behavior. A tooling task keeps the flag in one place:

```yaml
tooling:
  serve:
    service: app
    cmd: [":ruby-local", "ruby", "app.rb", "-o", "0.0.0.0"]
```

`lando serve` then starts `app.rb` with the gems your lockfile pins.

Ruby publishes its port endpoint but has no default healthcheck or readiness probe, even with an authored `command:`. Add `readiness:` when you want start to wait for application readiness; use `healthcheck:` separately for native ongoing monitoring. Without an effective readiness command, Lando checks that the process stays running.

## Set the Ruby webroot context

Run `lando start` after adding `framework: rails` and your `webroot:` to the service:

```yaml
services:
  app:
    type: "ruby:3.3"
    primary: true
    framework: rails
    webroot: frontend/public
```

Rails defaults to `webroot: public`; without a framework, Ruby defaults to `.`.
Your `webroot:` wins in either case. Relative paths resolve against
`appMount.target` (default `/app`), so this sets `LANDO_WEBROOT` to
`/app/frontend/public`. Set `appMount: /site` to get
`/site/frontend/public`, or use an absolute container path such as `/srv/www`.
Relative paths can't escape the app mount with `..`.

Verify the value inside the running service:

```sh
lando start
lando exec app -- printenv LANDO_WEBROOT
```

The webroot doesn't move the working directory or start a Rails server.
Use `working_dir:` and `command:` for those. The Rails preset supplies
development environment and host defaults; authored values for those defaults still win.
With `appMount: false`, Ruby omits its implicit webroot context. If you explicitly
set a relative or absolute `webroot:`, planning fails instead of silently dropping it.
Remove `webroot:` or enable the app mount. A plugin can also supply a feature
that declares and handles the effective root. That declaration means root support,
not that an HTTP server is running.

Check planning without starting services:

```sh
lando app:cache:refresh --format=json
```

## Pin a version

Set `image:` to use the full (non-slim) or an alternate Ruby base image when
`ruby:3.3-slim` isn't what you want. Slim lacks build tools that some gems need:

```yaml
services:
  app:
    type: "ruby:3.3"
    image: ruby:3.3
```
