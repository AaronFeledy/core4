# Customize PHP

Start from `type: php:8.3` (or another supported minor). That image ships a fixed set of built-in PHP extensions. Add an extra extension, mount a `php.ini`, or replace the image. Build steps change the image, mounted settings change configuration, and a replacement image takes responsibility for its own tools and extensions.

## See built-in extensions

Stock PHP services using Apache, FPM, or CLI include these extensions alongside PHP's standard modules:

```text
gd, intl, mbstring, mysqli, opcache, pcntl, pdo_mysql, pdo_pgsql, pdo_sqlite, zip
```

| Extension | Purpose |
| --- | --- |
| `gd` | Image processing (GD) |
| `intl` | ICU internationalization functions |
| `mbstring` | Multibyte string handling |
| `mysqli` | MySQL/MariaDB driver for WordPress and Joomla |
| `opcache` | Zend OPcache |
| `pcntl` | Process control and signal handling for CLI workers, including Laravel Reverb and Horizon |
| `pdo_mysql` | PDO driver for MySQL/MariaDB |
| `pdo_pgsql` | PDO driver for PostgreSQL |
| `pdo_sqlite` | PDO driver for SQLite |
| `zip` | ZIP archive support |

Stock PHP services with `framework: wordpress` also install pinned, checksum-verified WP-CLI at `/usr/local/bin/wp` and set `WP_CLI_ALLOW_ROOT=1` for Lando tooling. Custom images supply their own WP-CLI and extensions.

Start an existing service to pick up the current extension set, then check it. Replace `app` with your PHP service name:

```sh
lando start
lando exec app -- php --ri pcntl
```

Reverb and Horizon don't need a separate `build.artifact` step to install `pcntl` on a stock PHP service.

## Turn on Xdebug

Xdebug is not a `build.artifact` PECL one-off. Set `xdebug: true` (or a mode string) on the PHP service. See the Xdebug in PhpStorm guide. `xdebug: false` is the default and installs nothing. `XDEBUG_MODE` in `environment:` does not add the extension.

## Install a database client

`db_client: auto` is the default. At plan time Lando looks at the other services in your app (MySQL, MariaDB, Postgres, MongoDB) and installs the matching client CLI into the PHP container. Managed MySQL services select 8.0, 8.4, or 9.7 to match their declared series. You can force one with `db_client: "mysql:9.7"` or `db_client: "mariadb:11.4"`, or skip clients entirely with `db_client: false`.
Detection is deterministic from the resolved plan; it never probes the
provider. Changing `db_client` changes the build key, so the next `lando start`
rebuilds that image. A custom `image:` still validates the option but skips
the install steps.

Oracle MySQL clients use Oracle's signed Bookworm APT repository on amd64. On Linux arm64, Lando installs pinned Oracle EL9 client RPM payloads: 8.0.46, 8.4.11, or 9.7.2 to match the selected series. All four package SHA256 checks must pass before extraction. Lando installs the client libraries and plugin paths without running RPM install scripts. Other architectures stop with `Unsupported architecture`; no MariaDB or wrong-series MySQL client is substituted.

The arm64 support policy covers the default `caching_sha2_password` authentication only. Live arm64 build, connection, and dump/restore verification is still pending; the pinned artifacts and generated commands are not proof of a working connection. LDAP/SASL authentication is not supported: Oracle's optional LDAP plugin requires `libsasl2.so.3`, which Bookworm does not provide.

Automatic selection also stops when a custom MySQL image has unknown compatibility or when one app declares mixed MySQL series. Set an explicit `db_client` only after verifying that client against your server, or set `db_client: false`.

```yaml
services:
  app:
    type: "php:8.3"
    db_client: auto
  database:
    type: mysql
    creds:
      user: app
      password: secret
      database: app
tooling:
  db-query:
    service: app
    cmd: mysql -h database -u app -p app -e "SELECT 1"
```

`lando mysql` / `lando psql` still run in the database service. Point a PHP
task at those same `services.<db>.creds.*` values when you want the client
that lives next to your app code. `db-query` above is that pattern. It prompts for the database password because `-p` has no inline value; enter the password from `services.database.creds.password`.

## Install an extra extension

Add a `build.artifact` step to compile or install an extension the built-in set doesn't cover. Lando runs each entry as a build-time shell command against the service's build layer. Imagick also needs ImageMagick development libraries and PHP build tools, which the first step installs. Run these package-install steps as root; add `user: root` to object-form steps if your service uses a non-root user:

```yaml
services:
  app:
    type: "php:8.3"
    build:
      artifact:
        - "apt-get update && apt-get install -y --no-install-recommends $PHPIZE_DEPS libmagickwand-dev && rm -rf /var/lib/apt/lists/*"
        - "pecl install imagick"
        - "docker-php-ext-enable imagick"
```

To use [PIE](https://github.com/php/pie/blob/1.5.2/docs/usage.md) instead,
install ImageMagick's development libraries and the build tools first.
This example uses the stock Debian Bookworm PHP image, not a custom image.
Its artifact commands run as root unless you override the service's `user`.
They need network access to Debian, GitHub, and Packagist.

PIE needs PHP 8.1 or newer to run, which all supported Lando PHP types satisfy.
PECL takes the short name (`imagick`); PIE takes the Packagist name
`imagick/imagick`. Fetch `pie.phar` into `/usr/local/bin/pie`, make it executable,
then run `pie self-verify` and `pie install`:

```yaml
services:
  app:
    type: "php:8.3"
    build:
      artifact:
        - "apt-get update && apt-get install -y --no-install-recommends $PHPIZE_DEPS automake libtool git libmagickwand-dev && rm -rf /var/lib/apt/lists/*"
        - "curl -fL --output /usr/local/bin/pie https://github.com/php/pie/releases/latest/download/pie.phar"
        - "chmod +x /usr/local/bin/pie"
        - "pie self-verify"
        - "pie install --no-interaction imagick/imagick"
```

The stock image supplies `curl`, `phpize`, PHP headers, and `$PHPIZE_DEPS`;
Lando adds `unzip` and PHP's `zip` extension. The explicit tool install also
restores `$PHPIZE_DEPS` if an earlier Xdebug build step removed them. Don't
install Debian's `php-dev`: these tools must match the image's PHP installation.
PIE won't automatically install missing tools or libraries in a non-interactive
build without its opt-in flags.

`pie self-verify` checks GitHub release attestations. Without the `gh` CLI,
it uses PHP's OpenSSL extension, which the stock image includes. PIE enables
Imagick through the image's `docker-php-ext-enable` helper, so you don't need
a second enable command.

Start, then check that PHP loads the extension:

```sh
lando start
lando exec app -- php --ri imagick
```

An artifact step runs after Lando's own PHP prerequisite build steps, in
the same image, so a manually compiled extension can depend on the apt
packages Lando already installed. A `build.artifact` edit changes the
build key, so the next `lando start` rebuilds that image. Bare `restart` also stop/starts and applies it. Selected `lando restart -s` stays in place and refuses the drift.

## See the security baseline

Stock PHP services write `/usr/local/etc/php/conf.d/10-lando-baseline.ini` during the image build. Custom `image:` values skip that file.

The current baseline sets `session.upload_progress.enabled = 0`. That follows the [php.net 23 Oct 2026 informational advisory](https://www.php.net/archive/2026.php#2026-10-23-1) for CVE-2026-115560. There is no patched PHP release yet, so Lando ships the mitigation on every stock Apache, FPM, and CLI image.

What you lose: PHP session upload progress. Some apps use that feature for session-based upload progress bars. Those bars stop updating until you override the setting.

To turn the feature back on, add a `conf.d` drop-in whose name sorts after `10-lando-baseline.ini`. Use the `mounts:` or `configs:` form in the next section. A name such as `zz-custom.ini` loads after `10-` and wins. Do not bind-mount a replacement `/usr/local/etc/php/php.ini` for this override. PHP loads that file before it scans `conf.d`, so the baseline still wins.

Create `php.ini` in your app root:

```ini
session.upload_progress.enabled = 1
```

Start the app after you add the mount shown next, then confirm the value inside the service. Replace `app` with your PHP service name:

```sh
lando exec app -- php -r "echo ini_get('session.upload_progress.enabled'), PHP_EOL;"
```

The command prints `1` when your drop-in loaded after the baseline.

## Mount a custom php.ini

Create `php.ini` in your app root with the settings you want to override, then add this `mounts:` entry to `.lando.yml`. It mounts the file into `/usr/local/etc/php/conf.d/` without rebuilding the image:

```yaml
services:
  app:
    type: "php:8.3"
    mounts:
      - source: "./php.ini"
        target: "/usr/local/etc/php/conf.d/zz-custom.ini"
        readOnly: true
```

php.ini drop-ins are read alphabetically after the base `php.ini`. Name your custom file so it sorts after any Lando-provided drop-in you want to override. For example, `zz-custom.ini` loads after the security baseline `10-lando-baseline.ini`, after the Drupal CMS recipe default `50-lando-drupal-cms.ini`, and after the `50-lando-wordpress.ini` that `framework: wordpress` builds into the image. Mark the mount read-only. The container never needs to write back to your source `php.ini`.

## Grant a php.ini with Compose configs

Lando mounts `configs:` grants as read-only files. Declare the file at the top level, then grant it onto the PHP service:

```yaml
configs:
  phpini:
    file: ./php.ini
services:
  app:
    type: "php:8.3"
    configs:
      - source: phpini
        target: /usr/local/etc/php/conf.d/zz-custom.ini
        mode: "0444"
```

Changing the source file busts the app-plan cache. Run `lando start` to
refresh the plan and apply the updated `mode:` copy. A mode-less grant binds
the live host file; changing its contents alone does not force an image build.

## Replace the image

Setting `image:` on a `php` service, or switching to `build.context` with your own Dockerfile, replaces the default `-apache` base entirely.
`service-lando.php` only adds its prerequisite build steps (the apt
packages, `docker-php-ext-install` compilation, Composer install, and
database clients) and generates the Apache virtual-host command when
`image:` is left unset. Set `image:` and those install steps are skipped:
you get none of the built-in extensions above, no generated Apache
startup, and no `db_client:` packages. The image's own `CMD`/`ENTRYPOINT` runs instead. Invalid `db_client:` values still fail at plan time.

What still applies regardless of `image:`: the app mount (`/app` unless
`appMount: /site` moves it, or `appMount: false` removes it), HTTP endpoint,
healthcheck, working directory, and `LANDO_*` environment.
