# PHP customization

`type: php:8.3` (and the other supported minors) ships a fixed set of
built-in PHP extensions. When your app needs something outside that set, or
a `php.ini` tweak, or a fully custom image, this guide covers the three
supported paths and what each one costs you.

## Built-in extensions

The default `-apache` build compiles and enables exactly these extensions —
no more, no less:

```text
gd, intl, mbstring, opcache, pdo_mysql, pdo_pgsql, pdo_sqlite, zip
```

| Extension | Purpose |
| --- | --- |
| `gd` | Image processing (GD) |
| `intl` | ICU internationalization functions |
| `mbstring` | Multibyte string handling |
| `opcache` | Zend OPcache |
| `pdo_mysql` | PDO driver for MySQL/MariaDB |
| `pdo_pgsql` | PDO driver for PostgreSQL |
| `pdo_sqlite` | PDO driver for SQLite |
| `zip` | ZIP archive support |

## Install an extra extension

Add a `build.artifact` step to compile or install an extension the
built-in set doesn't cover — Lando runs each entry as a build-time shell
command against the service's build layer, honestly, the same way it runs
its own prerequisite install:

```yaml
services:
  app:
    type: "php:8.3"
    build:
      artifact:
        - "pecl install imagick"
        - "docker-php-ext-enable imagick"
```

An artifact step runs after Lando's own PHP prerequisite build steps, in
the same image, so a manually compiled extension can depend on the apt
packages Lando already installed. A `build.artifact` edit changes the
build key, so `lando rebuild -y` is required for it to take effect —
restart alone reuses the previous image.

## Mount a custom php.ini

Bind-mount a `.ini` file into `/usr/local/etc/php/conf.d/` with `mounts:`
to override settings such as `memory_limit` without rebuilding the image:

```yaml
services:
  app:
    type: "php:8.3"
    mounts:
      - source: "./php.ini"
        target: "/usr/local/etc/php/conf.d/zz-custom.ini"
        readOnly: true
```

php.ini drop-ins are read alphabetically after the base `php.ini`, so a
`zz-` prefix guarantees this file loads last and wins. Mark the mount
read-only — the container never needs to write back to your source
`php.ini`.

## Custom image or Dockerfile tradeoffs

Setting `image:` on a `php` service — or switching to `build.context` with
your own Dockerfile — replaces the default `-apache` base entirely.
`service-lando.php` only adds its prerequisite build steps (the apt
packages, `docker-php-ext-install` compilation, and Composer install) and
generates the Apache virtual-host command when `image:` is left unset. Set
`image:` and both are skipped: you get none of the built-in extensions
above and no generated Apache startup — the image's own `CMD`/`ENTRYPOINT`
runs instead.

What still applies regardless of `image:`: the `/app` bind mount, HTTP
endpoint, healthcheck, working directory, and `LANDO_*` environment.

## Compose configs: is not a supported delivery path

Compose's own `configs:` key looks like the natural way to deliver a
`php.ini`, but the default `provider-lando` capability set only realizes
the `labels` Compose service field — `configs` and `secrets` content lives
only in `AppPlan.extensions.compose`, with no provider step that
materializes it into the container. Planning fails closed with a tagged
`CapabilityError` before any container work happens.

Declaring `configs:` on a service authors a Compose config grant that
decodes and merges into the Landofile without error, but planning still
fails closed once provider capabilities are checked. Replace `configs:`
with a `mounts:` bind mount, as shown in the php.ini section above, to
actually deliver the file.
