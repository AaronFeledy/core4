# Customize PHP

Start from `type: php:8.3` (or another supported minor). That image ships a fixed set of built-in PHP extensions. Add an extra extension, mount a `php.ini`, or replace the image. Each path costs you something different.

## See built-in extensions

The default `-apache` build compiles and enables exactly these extensions. No more, no less:

```text
gd, intl, mbstring, opcache, pdo_mysql, pdo_pgsql, pdo_sqlite, zip
```

| Extension | Purpose |
| --- | --- |
| `gd` | Image processing (GD) |
| `intl` | ICU internationalization functions |
| `mbstring` | Multibyte string handling |
| `opcache` | Zend OPcache |
| `pdo_mysql` | PDO driver for MySQL/MariaDB |
| `pdo_pgsql` | PDO driver for PostgreSQL |
| `pdo_sqlite` | PDO driver for SQLite |
| `zip` | ZIP archive support |

## Turn on Xdebug

Xdebug is not a `build.artifact` PECL one-off. Set `xdebug: true` (or a mode string) on the PHP service. See the Xdebug in PhpStorm guide. `xdebug: false` is the default and installs nothing. `XDEBUG_MODE` in `environment:` does not add the extension.

## Install a database client

`db_client: auto` is the default. At plan time Lando looks at the other services in your app (MySQL, MariaDB, Postgres, MongoDB) and installs the matching client CLI into the PHP container. You can force one with
`db_client: "mariadb:11.4"`, or skip clients entirely with `db_client: false`.
Detection is deterministic from the resolved plan; it never probes the
provider. Changing `db_client` changes the build key, so a running app needs
`lando rebuild -y`. A custom `image:` still validates the option but skips
the install steps.

```yaml
services:
  app:
    type: "php:8.3"
    db_client: auto
  database:
    type: mysql
    creds:
      user: app
      password: secret
      database: app
tooling:
  db-query:
    service: app
    cmd: mysql -h database -u app app -e "SELECT 1"
```

`lando mysql` / `lando psql` still run in the database service. Point a PHP
task at those same `services.<db>.creds.*` values when you want the client
that lives next to your app code. `db-query` above is that pattern.

## Install an extra extension

Add a `build.artifact` step to compile or install an extension the built-in set doesn't cover. Lando runs each entry as a build-time shell command against the service's build layer:

```yaml
services:
  app:
    type: "php:8.3"
    build:
      artifact:
        - "pecl install imagick"
        - "docker-php-ext-enable imagick"
```

An artifact step runs after Lando's own PHP prerequisite build steps, in
the same image, so a manually compiled extension can depend on the apt
packages Lando already installed. A `build.artifact` edit changes the
build key, so `lando rebuild -y` is required for it to take effect. Restart alone reuses the previous image.

## Mount a custom php.ini

Bind-mount a `.ini` file into `/usr/local/etc/php/conf.d/` with `mounts:`
to override settings such as `memory_limit` without rebuilding the image:

```yaml
services:
  app:
    type: "php:8.3"
    mounts:
      - source: "./php.ini"
        target: "/usr/local/etc/php/conf.d/zz-custom.ini"
        readOnly: true
```

php.ini drop-ins are read alphabetically after the base `php.ini`, so a
`zz-` prefix guarantees this file loads last and wins. Mark the mount
read-only. The container never needs to write back to your source `php.ini`.

## Replace the image

Setting `image:` on a `php` service, or switching to `build.context` with your own Dockerfile, replaces the default `-apache` base entirely.
`service-lando.php` only adds its prerequisite build steps (the apt
packages, `docker-php-ext-install` compilation, Composer install, and
database clients) and generates the Apache virtual-host command when
`image:` is left unset. Set `image:` and those install steps are skipped:
you get none of the built-in extensions above, no generated Apache
startup, and no `db_client:` packages. The image's own `CMD`/`ENTRYPOINT` runs instead. Invalid `db_client:` values still fail at plan time.

What still applies regardless of `image:`: the `/app` bind mount, HTTP
endpoint, healthcheck, working directory, and `LANDO_*` environment.

## Don't use Compose configs

Compose's own `configs:` key looks like the natural way to deliver a
`php.ini`, but the default `provider-lando` capability set only realizes
the `labels` Compose service field. `configs` and `secrets` content lives only in `AppPlan.extensions.compose`, with no provider step that materializes it into the container. Planning fails closed with a tagged
`CapabilityError` before any container work happens.

Declaring `configs:` on a service authors a Compose config grant that
decodes and merges into the Landofile without error, but planning still
fails closed once provider capabilities are checked. Replace `configs:`
with a `mounts:` bind mount, as shown in the php.ini section above, to
actually deliver the file.
