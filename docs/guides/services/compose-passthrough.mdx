# Add a Compose service

Add `type: compose` under `services` in `.lando.yml` to run a third-party image outside the catalog. A numeric route picks the hostname and the HTTP backend in one line. Use an endpoint alone when you want the default HTTPS hostname. The app root is mounted at `/app` by default:

```yaml
name: compose-passthrough-demo
services:
  whoami:
    type: compose
    image: traefik/whoami:v1.10
    routes:
      - whoami.{{ app.name }}.lndo.site:80
```

The `:80` selects container port 80 as the HTTP backend. When the service has no declared network listener there, Lando adds an unnamed internal HTTP listener on that port. It does not publish a host port. Because the image comes from your Landofile, Lando plans no home store for it.

For the default HTTPS hostname without choosing a custom host, declare the listener only:

```yaml
services:
  whoami:
    type: compose
    image: traefik/whoami:v1.10
    endpoints:
      - http:80
```

`endpoints: [http:80]` is shorthand for an internal HTTP listener on container port 80. Lando gives the service the default HTTPS URL on the shared router.

Save the Landofile in your app directory, then lint, start, and read the URL:

```sh
lando app:config:lint
lando start
lando info
```

`lando info` prints the HTTPS URL for `whoami`. Open that URL in a browser. The [whoami image](https://github.com/traefik/whoami/blob/v1.10.0/Dockerfile) returns request headers; its `Hostname:` line shows the container name, `lando-compose-passthrough-demo--whoami`.

Name a listener when a route should target it, or when several listeners share a service:

```yaml
services:
  whoami:
    type: compose
    image: traefik/whoami:v1.10
    endpoints:
      - ui=http:80
    routes:
      - hostname: whoami.{{ app.name }}.lndo.site
        endpoint: ui
```

`ui=http:80` is the same internal listener with alias `ui`. Shorthand covers only internal network listeners as `protocol:port` or `name=protocol:port`. Protocols are lowercase `http`, `https`, `tcp`, and `udp`. Ports are decimal 1 through 65535 with no leading zero. There is no host-port, Unix socket, `primary`, or `appProtocol` shorthand.

Use a `kind` object when you need those fields, a Unix socket, or an explicit host publication:

```yaml
endpoints:
  - kind: internal
    protocol: http
    port: 80
    primary: true
  - kind: published
    protocol: tcp
    port: 9000
    publication:
      bindAddress: 127.0.0.1
      hostPort: 9000
```

`kind: internal` stays on the app network. `kind: published` with `publication` is how you bind a host port. An explicit `endpoints:` list, including `endpoints: []`, replaces type and app-feature declarations and anything inferred from `ports:` or `expose:`. It does not suppress listeners that valid numeric routes declare. A numeric selector never invents a host bind: keep `kind: published` (or Compose `ports:`) when you need one. A TCP or UDP listener already declared at that port blocks the implication and fails the route entry instead of changing the protocol. For LAN binds and short-syntax ports, see [Reach an app from another device](../subsystems/external-access.mdx). For named endpoints, filters, and routes, see [Write routes as shorthand strings and add filters](../proxy/route-shorthand.mdx).

## Set `command` or `entrypoint`

A string `command:` or `entrypoint:` splits into argv like Compose: whitespace separates words, quotes group them, and no shell runs. `command: --port 8080` reaches the image's entrypoint as `["--port", "8080"]`. A list passes through as written. Splitting does not expand variables, and an unquoted `;`, `&`, `|`, `<`, or `>` ends the argv there.

`command` appends to the image's `ENTRYPOINT`, same as Compose. For shell features you need an image with a shell and no binary entrypoint in the way, then an explicit `sh -c` with the script in one quoted argument:

```yaml
services:
  sleeper:
    type: compose
    image: alpine:3.20
    appMount: false
    command: sh -c "printf ready && exec sleep infinity"
```

That becomes `["sh", "-c", "printf ready && exec sleep infinity"]`. Malformed quotes fail planning with `LandofileValidationError`. Only `type: compose` splits strings this way; other service types run a string `command` as a shell script.

## Choose an init process

A `type: compose` service leaves init unspecified unless you configure it, preserving the container runtime's default. Set `init: true` when the image's process does not handle SIGTERM as PID 1 or leaves zombie children behind, and Lando runs the runtime's init as PID 1, forwarding the stop signal to your command and reaping orphans. Set `init: false` to explicitly disable the runtime's init, even if the runtime enables it by default.

```yaml
services:
  worker:
    type: compose
    image: alpine:3.20
    appMount: false
    init: true
    command: sleep infinity
```

Init forwards the signal to the process it started, which is the first word of your argv. With `sh -c '...'` that is the shell; use `exec` so your program takes its place. Catalog services such as `type: node` already default to `init: true`; see [Stop cleanly](./node.mdx#stop-cleanly).

## Control when the image is pulled

Without `pull_policy`, `lando start` pulls an image only when your provider does not have it yet, and `lando rebuild` pulls it again so an updated tag takes effect. If that rebuild pull fails, Lando warns and keeps the local copy. Set `pull_policy` on the service to choose a different rule. It applies to `lando start`, `lando rebuild`, scratch commands, and `lando global:start` alike:

| `pull_policy` | Start | Rebuild |
| --- | --- | --- |
| omitted, `missing`, or `if_not_present` | Pull only a missing image | Pull again; keep the local copy if the pull fails |
| `always` | Pull every time; a failed pull fails the command | Same as start |
| `never` | Use the local image only; a missing image fails the command | Same as start |
| `build` | Run the service's `build:` every time | Same as start |

```yaml
services:
  api:
    type: compose
    image: ghcr.io/example/api:latest
    pull_policy: always
```

`always` and `never` win over the command. `lando rebuild` does not pull a `never` service, and it does not fall back to a local copy for an `always` service. With `never`, put the image into your provider first, for example by building or loading it, or the command fails and names the image. When the service also sets `platform:`, Lando pulls that platform.

An image Lando builds, from a `build:` section or from build steps on top of an image, exists only in your provider, so Lando never pulls it, whatever the policy. If it disappears, for example after you prune images, the next start fails, names the service and the image, and tells you to run `lando rebuild -s <service>` to build it again.

`build` needs a Compose `build:` section, and `always` and `never` cannot be combined with one, because the build replaces the image. `build` reruns the build even when its inputs are unchanged, but the build still reuses cached layers and pulls the Dockerfile's `FROM` image only as the builder normally would. The timed Compose policies `daily`, `weekly`, `every_<interval>`, and `refresh` fail planning; use `always`, or run `lando rebuild` when you want a fresh image. `lando app:config:lint` reports both mistakes at `pull_policy`, and its suggestion names the fix.

## See which Compose keys work

The compose passthrough accepts a subset of Compose service keys. The
generated [Compose key matrix](../../reference/compose-key-matrix.mdx) lists
every accepted, preserved, and rejected key. A rejected key fails
`lando app:config:lint` and `lando start` with a remediation that names its
replacement when Lando has one: `mem_limit`, for example, points you to
`deploy.resources.limits.memory`.

Some preserved keys also need the provider to support them. Resource limits
under `deploy.resources` work on the `docker` and `podman` providers, and on
the default `lando` provider on Linux with a systemd user session. GPU
requests work on `docker` only. When the selected
provider can't apply a key, planning fails with `CapabilityError`, and the
remediation names each installed provider that can, with the
`lando setup --provider=<id>` command that switches to it. See
[Limit memory, CPU, and processes](../config/compose-service-block.mdx#limit-memory-cpu-and-processes)
and [Give a service a GPU](../config/compose-service-block.mdx#give-a-service-a-gpu).

Compose `hostname` and `domainname` are rejected. Lando sets each container's
hostname to its container name, `lando-<app>--<service>`. To give a service
another name that other services can use, add a `hostnames:` alias. See
[Reach services by name](../subsystems/service-dns.mdx).

## Know what Lando adds

Lando injects none of its app identity or app-path `LANDO_*` variables into a
compose service. The only one it adds is `LANDO_HOST_IP`, the host alias
`host.lando.internal`, when the provider can reach your host. Set anything
else the image needs with `environment:` or `env_file:`.

Lando still bind-mounts the app source at `/app`, or at `appMount.target`
when you set one, and joins the service to the per-app network `lando-<slug>`
so it can reach the rest of the app by service name. To put it on more
networks as well, declare them under top-level `networks:` and list them on
the service; see [Reach another project's services](../config/networks.mdx).
To bring a whole compose file in as services of your app, use top-level
`include:`; the same guide covers it.

## Skip the app mount

Set `appMount: false` when the third-party image must not see the app
source. Every service type that mounts the app honors it:

```yaml
services:
  whoami:
    type: compose
    image: traefik/whoami:v1.10
    appMount: false
```
