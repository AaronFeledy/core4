# Run build steps as root or as your app user

A build step is a shell command Lando runs while it builds or starts a service. Give a step a `user:` when it needs a different identity than the rest of the service. Most of the time that means `user: root` for a package install, with everything else running as the app user.

```yaml
name: build-steps-demo
services:
  app:
    type: "node:22"
    primary: true
    user: node
    build:
      artifact:
        - run: apt-get update -y && apt-get install -y --no-install-recommends jq
          user: root
        - npm config set fund false
      app:
        - npm ci
        - run: ln -sf /app/bin/dev /usr/local/bin/dev
          user: root
```

Save this in `.lando.yml` at your project root. The `npm ci` step assumes your project already has a package lockfile. The last step links a project script onto the service's `PATH`: it needs root to write `/usr/local/bin` and runs in `build.app` because the script arrives with your code. From that directory, lint the configuration, then start:

```sh
lando app:config:lint
lando start
```

## Two phases

| Key | When it runs | Where | Good for |
| --- | --- | --- | --- |
| `build.artifact` | While the image is produced | Inside the image build, no app mount | System packages, global tools, anything that belongs in the image |
| `build.app` | After the container starts | Inside the running container with your app mounted | `npm ci`, `composer install`, links to scripts in your code |

Each key takes one entry or an ordered array. Lando runs the list top to bottom and keeps the order you wrote.

## Step forms

An entry is either a plain string or an object:

| Form | Example | Runs as |
| --- | --- | --- |
| String | `npm config set fund false` | The default for the step's phase |
| Object | `{ run: "apt-get install -y jq", user: root }` | The `user` you named |

A step with no `user` gets a default that depends on its phase. An artifact step runs as the service's planned user, which is what `services.<name>.user` sets, or as the base image's own user when you leave that out. An app step runs as the service's project user when the service has one, the same account `lando exec` and tooling use. Without a project user, it runs as the container's default user. [Who owns your app files](./file-ownership.mdx) explains which services have a project user.

Mixing root and non-root steps in one list is fine. The order is preserved, so `apt-get` as root followed by `npm config` as `node` does exactly that, in that sequence.

## Identity format

`user` is `<name|uid>` or `<name|uid>:<group|gid>`. Letters, digits, underscores, dots, and hyphens, and each part starts with a letter, digit, or underscore.

| Value | Result |
| --- | --- |
| `root` | Accepted |
| `node` | Accepted |
| `1000` | Accepted |
| `1000:1000` | Accepted |
| `root wheel` | Rejected, whitespace |
| `-root` | Rejected, leading hyphen |
| `root;id` | Rejected, shell metacharacter |

`lando app:config:lint` rejects a bad identity before anything builds. The report says `valid: false` and points at the field, `["services", "app", "build", "artifact", 0, "user"]` for the first artifact step above, so you fix the Landofile rather than reading a build log.

## What changes when you change `user`

The step's user is part of its build key. Change an app step's user and only that step re-runs on the next `lando start`, the same as changing the command text. Change an artifact step's user and the next `lando start` rebuilds the image, because those steps share one image key.

For the image phase, Lando resolves every step's user during planning and only emits a `USER` switch when a step's user differs from the one currently active. After the last artifact step it restores the service's final user: `services.<name>.user` when you set it, otherwise the base image's own user. Two root steps in a row cost one switch, not two.

## When a step runs again

Lando doesn't repeat a step whose work is still there. What "still there" means depends on the phase.

A `build.artifact` step is part of the image. While its inputs are unchanged and the built image still exists, `lando start` reports the image build as cached, however often the containers come and go.

Lando keeps the images of each service's five most recent image builds, so switching back to a recent version of a Dockerfile or build step reuses its image. Older ones are removed automatically after a build or a teardown. Lando never removes an image a container still uses, and it never removes images you pulled.

Built images are shared. Another app whose service has the same build inputs reuses the image instead of building it again. So does a scratch fork, and so does the same app after you rename it.

The files in the build context are build inputs. When the context is the app folder, the Landofile is inside it, so editing the Landofile builds the image again. To keep unrelated files out of the build, point the build's `context` at a subfolder or list them in a `.dockerignore`, as you would for any Docker build.

`lando destroy` keeps the newest image of each built service for up to seven days, so a `lando start` in that window reuses it without building. `lando destroy --purge-caches` removes those images right away. See [Tear down](../cli/everyday-commands.mdx#tear-down).

A `build.app` step did its work inside one container, so its result counts only for that container. `lando start` reports the step as cached while the service still has the container the step ran in, and runs the step in every new container:

| What you ran | `build.app` steps |
| --- | --- |
| `lando start` again, container kept | Cached |
| `lando stop`, then `lando start` | Cached. Stop keeps the container, and so does the step's work |
| `lando restart` | Cached, for every container it keeps |
| `lando restart -s <service>`, container kept | Not run. The container stays, and so does the step's work |
| `lando restart` or `lando restart -s <service>` that replaces or creates a container | Run again, for that service only |
| `lando destroy`, then `lando start` | Run again |
| `lando start` after a Landofile change that recreates a container, such as a new image, command, environment, or mount | Run again, for the recreated service only |
| `lando rebuild` | Run again, always |

A container you removed with your container runtime counts as new too. Services are tracked separately, so recreating one service doesn't rerun the steps of another whose container stayed.

Editing a step's command or `user` runs it on the next `lando start`, even in a container that stayed. So does changing it back. Only a step's most recent run in its container counts, so an older result is never revived.

An interrupted `build.app` step needs no cleanup. Press Ctrl-C during `lando start` or `lando rebuild`, then run `lando start`. The step you interrupted runs again, along with the steps that hadn't started. A step that had already finished stays cached while its container stays.

Because `build.app` steps repeat, write them so a second run is harmless. `npm ci`, `composer install`, and the `ln -sf` above already are. Your app mount and named volumes outlive the container, so a rerun step finds the files its last run left there. A step that appends to a file in your project should check before it appends.

Put anything that belongs to the image in `build.artifact`: system packages and global tools. The image keeps them when Lando replaces a container, and nothing has to run again.

Two limits:

- Lando doesn't read the files a `build.app` step uses. Editing `package-lock.json` doesn't rerun `npm ci` in a container that stayed. Run `lando rebuild` for that.
- A `tmpfs` mount is emptied whenever its container stops, including `lando stop` and `lando restart`, which keep the container, and the step isn't rerun to fill it.

## Read step output and failures

Lando shows every line a step prints while the step runs, in both phases. In a terminal the latest lines sit under the running step in the task tree. Piped or in CI, each line is printed with the step's id in front. For `build.artifact` steps the lines are the container engine's build output: each instruction, then what its command printed.

Lando also saves the full output of each step that runs. Print the output of the app's most recent build with `lando logs --build`, and add `--service <name>` to see one service:

```sh
lando logs --build
```

Image build lines are labeled `[build]` and `build.app` lines `[build:<step id>]`. Secrets Lando knows about, and text shaped like `password=...`, `password: "..."`, `{"token": "..."}`, `scheme://user:pass@host`, or `Bearer ...`, are masked as `[redacted]` in the live lines and before the output is saved. Masking follows a value across line breaks, so a quoted secret that wraps onto the next line is still hidden. Lando holds output only as long as it needs to decide, at most 64 lines or 16 KiB. If a value still has not closed at that limit or at the end of the step, Lando masks what it held and hides the rest of that value until its closing quote, for at most another 64 lines or 16 KiB, then shows later lines normally. A live line longer than 512 characters is cut there; the saved output keeps the line, up to 64 KiB.

A step that `lando start` reports as cached prints nothing new, and `lando logs --build` still prints the output of the run that produced it. A successful `lando destroy` removes the app's saved build output along with its containers.

Saved output belongs to the project folder, not to the app's `name`. A folder never prints output that another folder saved under the same name. Rename the app in its Landofile and the output you already saved stays with the folder.

The two phases fail differently:

| Phase | What a failure does | What is left running |
| --- | --- | --- |
| `build.artifact` | Stops the start, along with the other services' image builds, which are reported as aborted | Nothing. No container exists yet |
| `build.app` | Lets steps that don't depend on the failed one finish, then fails the start with every failed step listed | The app's containers |

Either way the error names the service, repeats the last lines of the step's output, and gives the `lando logs --build` command that prints all of it. To read it and get going again, see [Recover from a failed build step](./php-build-failures.mdx).

## Check what the planner sees

`lando app:config` prints the merged Landofile with your steps exactly as authored: strings stay strings, objects keep their `run` and `user`. `lando app:cache:refresh` rebuilds the plan and fails if any step cannot be resolved.

```sh
lando app:config --format=json
lando app:cache:refresh
```
