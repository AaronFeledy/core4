# Run build steps as root or as your app user

A build step is a shell command Lando runs while it builds or starts a service. Give a step a `user:` when it needs a different identity than the rest of the service. Most of the time that means `user: root` for a package install, with everything else running as the app user.

```yaml
name: build-steps-demo
services:
  app:
    type: "node:22"
    primary: true
    user: node
    build:
      artifact:
        - run: apt-get update -y && apt-get install -y --no-install-recommends jq
          user: root
        - npm config set fund false
      app:
        - npm ci
        - run: chown -R node:node /app/node_modules
          user: root
```

Save this in `.lando.yml` at your project root. The `npm ci` step assumes your project already has a package lockfile. From that directory, lint the configuration, then start:

```sh
lando app:config:lint
lando start
```

## Two phases

| Key | When it runs | Where | Good for |
| --- | --- | --- | --- |
| `build.artifact` | While the image is produced | Inside the image build, no app mount | System packages, global tools, anything that belongs in the image |
| `build.app` | After the container starts | Inside the running container with your app mounted | `npm ci`, `composer install`, permission fixes on mounted code |

Each key takes one entry or an ordered array. Lando runs the list top to bottom and keeps the order you wrote.

## Step forms

An entry is either a plain string or an object:

| Form | Example | Runs as |
| --- | --- | --- |
| String | `npm config set fund false` | The service's planned user |
| Object | `{ run: "apt-get install -y jq", user: root }` | The `user` you named |

A step with no `user` runs as the service's planned user, which is what `services.<name>.user` sets. Leave `services.<name>.user` out and an artifact step runs as the base image's own user, while an app step runs as the container's configured user.

Mixing root and non-root steps in one list is fine. The order is preserved, so `apt-get` as root followed by `npm config` as `node` does exactly that, in that sequence.

## Identity format

`user` is `<name|uid>` or `<name|uid>:<group|gid>`. Letters, digits, underscores, dots, and hyphens, and each part starts with a letter, digit, or underscore.

| Value | Result |
| --- | --- |
| `root` | Accepted |
| `node` | Accepted |
| `1000` | Accepted |
| `1000:1000` | Accepted |
| `root wheel` | Rejected, whitespace |
| `-root` | Rejected, leading hyphen |
| `root;id` | Rejected, shell metacharacter |

`lando app:config:lint` rejects a bad identity before anything builds. The report says `valid: false` and points at the field, `["services", "app", "build", "artifact", 0, "user"]` for the first artifact step above, so you fix the Landofile rather than reading a build log.

## What changes when you change `user`

The step's user is part of its build key. Change an app step's user and only that step re-runs on the next `lando start`, the same as changing the command text. Change an artifact step's user and the next `lando start` rebuilds the image, because those steps share one image key.

For the image phase, Lando resolves every step's user during planning and only emits a `USER` switch when a step's user differs from the one currently active. After the last artifact step it restores the service's final user: `services.<name>.user` when you set it, otherwise the base image's own user. Two root steps in a row cost one switch, not two.

## When a step runs again

Lando doesn't repeat a step whose work is still there. What "still there" means depends on the phase.

A `build.artifact` step is part of the image. While its inputs are unchanged and the built image still exists, `lando start` reports the image build as cached, however often the containers come and go.

A `build.app` step did its work inside one container, so its result counts only for that container. `lando start` reports the step as cached while the service still has the container the step ran in, and runs the step in every new container:

| What you ran | `build.app` steps |
| --- | --- |
| `lando start` again, container kept | Cached |
| `lando restart -s <service>` | Not run. The container stays, and so does the step's work |
| `lando stop`, then `lando start` | Run again |
| `lando restart` | Run again |
| `lando destroy`, then `lando start` | Run again |
| `lando start` after a Landofile change that recreates a container, such as a new image, command, environment, or mount | Run again, for the recreated service only |
| `lando rebuild` | Run again, always |

A container you removed with your container runtime counts as new too. Services are tracked separately, so recreating one service doesn't rerun the steps of another whose container stayed.

Because `build.app` steps repeat, write them so a second run is harmless. `npm ci`, `composer install`, and the `chown` above already are. Your app mount and named volumes outlive the container, so a rerun step finds the files its last run left there. A step that appends to a file in your project should check before it appends.

Put anything that belongs to the image in `build.artifact`: system packages and global tools. The image keeps them across `lando stop`, and nothing has to run again.

Two limits:

- Lando doesn't read the files a `build.app` step uses. Editing `package-lock.json` doesn't rerun `npm ci` in a container that stayed. Run `lando rebuild` for that.
- A `tmpfs` mount is emptied whenever its container stops, including `lando restart -s <service>`, and the step isn't rerun to fill it.

## Read step output and failures

Lando shows every line a step prints while the step runs, in both phases. In a terminal the latest lines sit under the running step in the task tree. Piped or in CI, each line is printed with the step's id in front. For `build.artifact` steps the lines are the container engine's build output: each instruction, then what its command printed.

Lando also saves the full output of each step that runs. Print the output of the app's most recent build with `lando logs --build`, and add `--service <name>` to see one service:

```sh
lando logs --build
```

Image build lines are labeled `[build]` and `build.app` lines `[build:<step id>]`. Secrets Lando knows about are masked as `[redacted]` in the live lines and before the output is saved. A live line longer than 512 characters is cut there; the saved output keeps the line, up to 64 KiB.

A step that `lando start` reports as cached prints nothing new, and `lando logs --build` still prints the output of the run that produced it. A successful `lando destroy` removes the app's saved build output along with its containers.

The two phases fail differently:

| Phase | What a failure does | What is left running |
| --- | --- | --- |
| `build.artifact` | Stops the start, along with the other services' image builds | Nothing. No container exists yet |
| `build.app` | Lets steps that don't depend on the failed one finish, then fails the start with every failed step listed | The app's containers |

Either way the error names the service, repeats the last lines of the step's output, and gives the `lando logs --build` command that prints all of it. To read it and get going again, see [Recover from a failed build step](./php-build-failures.mdx).

## Check what the planner sees

`lando app:config` prints the merged Landofile with your steps exactly as authored: strings stay strings, objects keep their `run` and `user`. `lando app:cache:refresh` rebuilds the plan and fails if any step cannot be resolved.

```sh
lando app:config --format=json
lando app:cache:refresh
```
