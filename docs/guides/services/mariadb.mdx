# Add MariaDB

Add `type: mariadb` under `services` in `.lando.yml`. Lando pulls `mariadb:11.4` and listens on `3306`:

```yaml
name: mariadb-demo
services:
  db:
    type: mariadb
```

Set a member under `creds:` when you want an explicit value. A member you leave out keeps its default. By default, the username, password, and root password are `lando`, and the database is named after the app. `lando info` prints those published defaults. `creds.user` is the database username. Container `user:` is not.

```yaml
services:
  db:
    type: mariadb
    creds:
      database: shop
      rootPassword: secret
```

Start it. Lando puts the database on the app network:

## Connect from another service

Other services use the service name as the hostname. Here that's `db`. Defaults:

| Setting | Value |
| --- | --- |
| Host | `db` |
| Database | the folder's data name (here `mariadb-demo`, the name this folder's data was first created under); override with `creds.database` under `services.db` |
| User | `lando` |
| Password | `lando` |

MariaDB also exports the `MYSQL_USER` / `MYSQL_PASSWORD` / `MYSQL_DATABASE` env names, so MySQL clients and frameworks connect unchanged. From inside the app network the connection URL is:

```
mysql://lando:lando@db:3306/mariadb-demo
```

MariaDB speaks the MySQL wire protocol, so that's the right scheme. That URL uses the default port; use your authored `port:` in application connection URLs.

## Open the client

The `mariadb` type ships the client task. After start:

```sh
lando mariadb
```

The readiness probe pings the server without requiring a working application login. See [Recover when credentials don't match](#recover-when-credentials-dont-match).

The generated client supplies its password for each invocation. Lando scopes the client-only `MYSQL_PWD` variable to client and healthcheck processes, not the database server's initialization environment.

The generated client, the healthcheck, and the `lando db:*` commands connect to the server from inside its own container, so they turn off server-certificate verification explicitly. TLS stays enabled, so a server that requires secure transport still accepts them.

Import a dump with `lando db:import`. See [Import and export app databases](../tooling/db-import-export.mdx). You can also pipe a plain SQL file directly into the client. This executes the statements in the dump against the database, so back up any data you need first:

```sh
lando mariadb < dump.sql
```

## Add server config

Set `config.server` to an app-relative file when you need to tune the server:

```yaml
services:
  db:
    type: mariadb
    config:
      server: ./config/my.cnf
```

Lando mounts that file read-only at `/etc/mysql/conf.d/99-lando.cnf`. The server reads it as a drop-in on startup, after its own defaults. It has to be a regular file, not a directory.

Lando's generated launcher gives the planned port, `port:` or the default, precedence over a port line in your config file. If you replace the launcher, see [Change the port](#change-the-port).

To add daemon flags without replacing Lando's launcher, use
[`extraArgs:`](./extra-args.mdx):

```yaml
services:
  db:
    type: mariadb
    extraArgs:
      - --max-connections=77
```

Lando keeps the planned port and any `config.server` handling, then appends
your list. Set `port:` or `config.server` rather than passing `--port`, `-P`,
or `--defaults-*`. `--datadir` is also reserved: keep the default data directory
or use `command:` for a custom launcher. With `config.server`, Lando still
reads the database version from `/var/lib/mysql`, the default data directory.
Custom images and Compose builds reject `extraArgs:`.

The path has to stay inside the app root. Absolute paths, paths that climb out of the app root, and symlinks that point outside it are rejected when Lando plans the app, before anything starts.

## Change the port

Set `port:` to move the daemon's listener, healthcheck, endpoint, and Lando's own clients together:

```yaml
services:
  db:
    type: mariadb
    port: 3307
```

Other services now connect to `db:3307`. Lando sets `MYSQL_TCP_PORT` for the server and in-container clients, and publishes the same value as `LANDO_DB_PORT`. `lando mariadb` and `lando db:*` commands use that planned port.

An authored `MYSQL_TCP_PORT` must match the planned port, or planning fails; `lando app:config:lint` reports the mismatch at `services.<name>.environment.MYSQL_TCP_PORT`. If you replace `command:` or `entrypoint:` and the option file sets another port, pass `--port={{ service.port }}` in your launcher. The [port expression](../landofile/expressions.mdx#your-services-own-port) supplies the value; you supply the flag.

Apply the change with `lando rebuild`, then check the running server:

```sh
lando mariadb -N -e 'SELECT @@port'
```

## Recover when credentials don't match

After editing `creds`, run `lando start`. Lando applies the settings to the catalog server without dropping or renaming existing users or databases. For these updates, Lando connects over the container's Unix socket as `lando_admin`, an account restricted to `localhost`. Its password is derived from a private key and the volume identity. Lando never prints it.

If start warns that it couldn't update the credentials, follow [Keep database credentials in sync](../tooling/db-creds-apply.mdx) to preview and apply a repair with `lando db:creds:apply`. If Lando needs a fallback password, supply the current root password, not the new one.

`LANDO_DATABASE_ADMIN_SEED_UNAVAILABLE` means Lando skipped adopting `lando_admin` and tried the previous or desired root password instead. See [how to restore access to the seed](../tooling/db-creds-apply.mdx).

## Pin a version

`type: mariadb` defaults to 11.4. To pin another catalog series, set `type: mariadb:10.11` or `type: mariadb:11.8`. For example, to pin 10.11:

```yaml
services:
  db:
    type: mariadb:10.11
```

For a version outside the catalog, use `type: mariadb` with an `image:` override. Lando can [check the configured login](../tooling/db-creds-apply.mdx#check-credentials-for-a-custom-image-or-launcher) for these images, but it doesn't apply credential changes.

## Change versions

Changing the MariaDB version keeps the data volume. Lando sets `MARIADB_AUTO_UPGRADE=1` on every `mariadb` service, so the official image runs `mariadb-upgrade` on the existing data when the version changes. To move from `mariadb:10.11` to `mariadb:11.4`, run these commands from the app directory on your host.

1. Stop the app, then set the service type to the newer catalog version:

   ```sh
   lando stop
   lando app:config:set services.db.type mariadb:11.4
   ```

2. Start the app. Lando saves a restore point before upgrading and prints its ID. With automatic upgrades enabled, the image backs up its system tables and runs `mariadb-upgrade` before the service reports ready:

   ```sh
   lando start
   ```

3. Check the running server version:

   ```sh
   lando mariadb -N -e 'SELECT VERSION()'
   ```

   It should report 11.4. Run your app's tests to check that its queries still work on the new server.

On later starts with the same version, the image skips the upgrade. To stop the image from running `mariadb-upgrade` automatically, override Lando's default with `MARIADB_AUTO_UPGRADE: "0"` under the service's `environment:`. If you run `lando start --format=json` for the upgrade, the final result's `dataVersionChanges[0].restorePoint` identifies the snapshot. The transition itself doesn't prove that the image rewrote any files. An unchanged version record doesn't prove a downgrade is safe.

Pass `--no-snapshot` to start without saving a restore point only if you have another backup or accept upgrading without one. Automatic retention leaves [upgrade restore points](../tooling/db-import-export.mdx#restore-points-before-version-upgrades) in place. Use `lando db:snapshots:prune --recovery` to remove them explicitly.

## Go back to the old version

MariaDB doesn't support downgrading data files that a newer series has created or upgraded. When Lando can verify the data version on a running service, it refuses before replacing the container:

```sh
lando app:config:set services.db.type mariadb:10.11
lando start --format=json
```

The JSON error has `_tag: "ServiceDataVersionError"` and `dataVersion.direction: "downgrade"`. The newer server keeps running unchanged, and the error names the restore point when one matches 10.11. Use that ID below in place of `<id>`. Restoring replaces the current database files, including changes made since the upgrade.

```sh
lando db:restore <id> --service db
lando start
lando mariadb -N -e 'SELECT VERSION()'
```

Check that the server reports 10.11 and that your app can read the data you expected to recover. To keep the upgraded data instead, restore the newer `type:` or your previous `image:` without running `db:restore`.

If the old container was already stopped, the official image's Lando launcher checks the files before starting MariaDB. That refusal has the same `dataVersion` fields under `ServiceNotReadyError` (or `ServiceStartError` when a dependent service is blocked). A service that sets `command:`, `entrypoint:`, or `build:` skips Lando's checks.

If you have no restore point, use a verified export taken before the upgrade. To make one before changing versions, run `lando db:export before-upgrade.sql.gz --service db` while the old server is running. The export holds the configured database, not other databases or user accounts. Importing a dump made on the newer version into the older version isn't guaranteed to work. **Back up other services first:** `--volumes` deletes the data of every service in the app, not only `db`. With `type:` already set to the old version:

```sh
lando destroy -y --volumes
lando start
lando db:import before-upgrade.sql.gz --service db --yes
```
