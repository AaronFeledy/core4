# Add MariaDB

Add `type: mariadb` under `services` in `.lando.yml`. Lando pulls `mariadb:11.4` and listens on `3306`:

```yaml
name: mariadb-demo
services:
  db:
    type: mariadb
```

Set a member under `creds:` when you want an explicit value. A member you leave out keeps its default. By default, the username, password, and root password are `lando`, and the database is named after the app. `lando info` prints those published defaults. `creds.user` is the database username. Container `user:` is not.

```yaml
services:
  db:
    type: mariadb
    creds:
      database: shop
      rootPassword: secret
```

Start it. Lando puts the database on the app network:

## Connect from another service

Other services use the service name as the hostname. Here that's `db`. Defaults:

| Setting | Value |
| --- | --- |
| Host | `db` |
| Database | the folder's data name (here `mariadb-demo`, the name this folder's data was first created under); override with `creds.database` under `services.db` |
| User | `lando` |
| Password | `lando` |

MariaDB also exports the `MYSQL_USER` / `MYSQL_PASSWORD` / `MYSQL_DATABASE` env names, so MySQL clients and frameworks connect unchanged. From inside the app network the connection URL is:

```
mysql://lando:lando@db:3306/mariadb-demo
```

MariaDB speaks the MySQL wire protocol, so that's the right scheme. That URL uses the default port; use your authored `port:` in application connection URLs.

## Open the client

The `mariadb` type ships the client task. After start:

```sh
lando mariadb
```

`lando start` checks the configured login when it started or recreated the database container, or when the planned connection changed since the last apply, and warns when the running server rejects it. An unchanged running database is checked by `lando doctor --app`, `lando restart`, and `lando rebuild`. See [Recover when credentials don't match](#recover-when-credentials-dont-match).

The generated client supplies its password for each invocation. Lando scopes the client-only `MYSQL_PWD` variable to client and healthcheck processes, not the database server's initialization environment.

The generated client, the healthcheck, and the `lando db:*` commands connect to the server from inside its own container, so they turn off server-certificate verification explicitly. TLS stays enabled, so a server that requires secure transport still accepts them.

Import a dump with `lando db:import`. See [Import and export app databases](../tooling/db-import-export.mdx). You can also pipe a plain SQL file directly into the client. This executes the statements in the dump against the database, so back up any data you need first:

```sh
lando mariadb < dump.sql
```

## Add server config

Set `config.server` to an app-relative file when you need to tune the server:

```yaml
services:
  db:
    type: mariadb
    config:
      server: ./config/my.cnf
```

Lando mounts that file read-only at `/etc/mysql/conf.d/99-lando.cnf`. The server reads it as a drop-in on startup, after its own defaults. It has to be a regular file, not a directory.

Lando's planned port, `port:` or the default, beats a port line in your config file. An authored `command:` or `entrypoint:` owns the daemon's flags instead.

The path has to stay inside the app root. Absolute paths, paths that climb out of the app root, and symlinks that point outside it are rejected when Lando plans the app, before anything starts.

## Change the port

Set `port:` to move the daemon's listener, healthcheck, endpoint, and Lando's own clients together:

```yaml
services:
  db:
    type: mariadb
    port: 3307
```

Other services now connect to `db:3307`. Lando sets `MYSQL_TCP_PORT` for the server and in-container clients, and publishes the same value as `LANDO_DB_PORT`. `lando mariadb` and `lando db:*` commands use that planned port.

An authored `MYSQL_TCP_PORT` must match the planned port, or planning fails; `lando app:config:lint` reports the mismatch at `services.<name>.environment.MYSQL_TCP_PORT`. With `config.server`, Lando pins `port:` or the default on its command line. If you author `command:` or `entrypoint:`, you own the daemon's flags; pass `--port=3307` yourself if the option file sets another port.

Apply the change with `lando rebuild`, then check the running server:

```sh
lando mariadb -N -e 'SELECT @@port'
```

## Recover when credentials don't match

`creds:` seeds a fresh volume. MariaDB ignores it once its data volume holds data, so changing `creds:` on an existing app changes what Lando's clients send, not the accounts the server stores. After the service is ready, `lando start` checks the configured login when it started or recreated the container, or when the planned connection changed since the last apply; `lando restart` and `lando rebuild` check the services they restart. Each warns when the server rejects it. When Lando has the previously applied plan to compare, the warning names the `creds` members whose descriptors changed and says that comparison does not prove the cause. It never names a value. Without the warning, the first `lando mariadb` or `lando db:*` command fails with `ERROR 1045 Access denied`.

Fix it without losing data, in this order:

1. Put `creds:` back to the values the volume was created with, then run `lando start` so Lando's clients send them again.
2. To keep the new password, sign in with the old one and change it inside MariaDB. The password prompt keeps the value out of your shell history and the container's argv:

   ```sh
   lando exec db -- mariadb -u root -p
   ```

   Then, in that shell, replace `<user>` and `<new-password>`:

   ```sql
   ALTER USER '<user>'@'%' IDENTIFIED BY '<new-password>';
   ```

   Set `creds:` to the new values and run `lando start` again.
3. Only when the data is disposable, start over. This deletes the database:

   ```sh
   lando destroy -y --volumes
   lando start
   ```

Lando never picks option 3 for you. `lando doctor --app` runs the same login check against a running app and reports what it observed.

## Pin a version

Set `image:` when `mariadb:11.4` isn't the version you want. For example, the 10.11 LTS line:

```yaml
services:
  db:
    type: mariadb
    image: mariadb:10.11
```

## Upgrade to a newer MariaDB

Changing `image:` keeps the data volume, so the newer server opens the old data files. Set `MARIADB_AUTO_UPGRADE` so the official image runs `mariadb-upgrade` on them when the version changes. Run these from the app directory on your host. This example moves an app pinned to `mariadb:10.11` up to the default `mariadb:11.4`.

1. Export a copy while the old version still runs:

   ```sh
   lando db:export before-upgrade.sql.gz
   ```

2. Turn on the upgrade, then drop the pin. To land on another version, set `image:` to it instead of removing it:

   ```sh
   lando app:config:set services.db.environment.MARIADB_AUTO_UPGRADE 1
   lando app:config:unset services.db.image
   ```

3. Apply it. Lando replaces the `db` container, and the image backs up its system tables and runs `mariadb-upgrade` before the service reports ready:

   ```sh
   lando start
   ```

4. Check the server version, and the version `mariadb-upgrade` last ran for:

   ```sh
   lando mariadb -N -e 'SELECT VERSION()'
   lando exec db -- cat /var/lib/mysql/mariadb_upgrade_info
   ```

   Both should name the new version, and your tables are still there. That proves the upgrade ran, not that your app's queries behave the same on the new server. Run your app's tests next.

You can leave `MARIADB_AUTO_UPGRADE` set. On later starts with the same version, the image logs `MariaDB upgrade not required` and skips it.

## Go back to the old version

MariaDB doesn't support downgrading data files that a newer series has opened, so don't just set `image:` back. Restore the export onto a fresh volume instead. `--volumes` deletes the data of every service in the app, not only `db`, so back up anything else you need first:

```sh
lando destroy -y --volumes
lando app:config:set services.db.image mariadb:10.11
lando start
lando db:import before-upgrade.sql.gz --yes
```

The same export, destroy, and import route also works when you'd rather start the new version on a clean volume than upgrade in place.
