# Add Mailpit

Add `type: mailpit` under `services` in `.lando.yml` to capture this app's outgoing mail. Lando gives the inbox a web URL:

```yaml
name: mailpit-demo
services:
  inbox:
    type: mailpit
```

From the app directory on your host, start the app and find the inbox URL:

```sh
lando start
lando info
```

Mailpit listens on SMTP port `1025` and serves its UI on `8025`. Open the
inbox URL from `lando info` and check that the inbox loads.

This is separate from the **global** Mailpit that lives in the host-level
Lando app at `https://mailpit.lndo.site`. Its hostname follows global
`proxy.defaultDomain`; see [Change the default domain](../subsystems/proxy-traefik.mdx#change-the-default-domain).
Keep the global one when every app on the machine should share one inbox.
Use `type: mailpit` when this app needs its own capture server.

## Choose PHP senders

Omit `mailFrom:` to connect every resolved PHP service to this inbox. Set it to `false` to wire none, or list only the PHP services that should send here:

```yaml
services:
  web:
    type: "php:8.3"
  worker:
    type: "php:8.3"
    via: cli
  inbox:
    type: mailpit
    mailFrom:
      - web
```

Run `lando start`, then send a message from `web`:

```sh
lando exec web -- php -r 'mail("you@example.test", "Mailpit check", "Hello from PHP");'
lando info
```

Open the inbox URL printed by `lando info` and check for the message. For the
PHP services selected by `mailFrom`, Lando installs a pinned `msmtp` from a
`snapshot.debian.org` snapshot matched to the PHP image's Debian family, then
sets PHP's `sendmail_path`. Here, `worker` keeps its existing mail configuration.

Stock Lando PHP images use Bookworm. A custom `image:` qualifies when it is a
canonical upstream PHP tag ending in `-bookworm` or `-bullseye`, for example
`php:8.3-fpm-bookworm` or `docker.io/library/php:8.3-fpm-bookworm`. A similarly
named image under another namespace does not prove its family. Each supported
family has its own pin. Additive `build.artifact` and `build.app` steps alone
keep the stock-family selection.

If planning says it cannot pin msmtp for a PHP service, choose the recovery
that matches the cause:

- `replacement-build`: your Dockerfile controls the resulting image, so an
  `image:` reference cannot prove its family, even if the Dockerfile starts
  from an official PHP image. Exclude the sender with `mailFrom: false` or a
  list of other PHP services, or use a known image **without** a replacement build.
- `unproven-image-family`: use a canonical upstream PHP reference ending in
  `-bookworm` or `-bullseye`, or exclude that sender with `mailFrom`.

The underlying `MailpitMsmtpBaseFamilyError` carries the PHP `service`, `reason`,
and `image` when a reference is available. The CLI reports this planning failure
as `LandofileValidationError`, preserving the specific recovery and the source
error's identifiers in `error.context`. Lando validates all selected senders before adding any mail wiring;
an unsupported sender fails planning before provider action. After changing
the selection, run `lando app:cache:refresh --format=json` from the app directory
to check planning without starting containers.

Duplicate names are removed in first-occurrence order. Unknown names and
non-PHP targets also fail planning. An app with no PHP services needs no opt-out.

## Open the UI

SMTP stays on `1025` unless you set `port:`. The UI stays on `8025`. Lando
adds a default hostname route to that UI port; override `routes:` when you
want a different URL. SMTP is the service's primary listener, but the route
still lands on the UI because it's the only HTTP listener. `lando info` lists
both as App Network connections, `tcp://inbox:1025` and `http://inbox:8025`.

## Replace MailHog

`type: mailhog` still plans as a working SMTP + UI service, but it is
deprecated since 4.2.0 and scheduled for removal in 5.0.0. Switch to
`type: mailpit`. `lando doctor --deprecations` reports the old type.
