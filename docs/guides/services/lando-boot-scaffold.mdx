Every `type: lando` service includes `lando.boot`. At priority 100, it adds a provider-neutral,
artifact-phase scaffold intent to the service's build plan: an idempotent `mkdir -p` step, not a
mount:

```text
/etc/lando
/etc/lando/env.d
/etc/lando/certs
```

Because the scaffold is not a mount, it does not hide files that higher-priority features add under
these directories. When a privileged build step targets a referenced parent, the artifact realizer
first builds a local intermediate base from that parent and then inspects that built artifact to
learn its inherited effective user, rather than trusting the reference alone. This materialization
lets an uncached referenced parent follow the same privilege-preserving path. When the inherited
user is non-root, the realizer grants the scaffold step temporary build-time privilege and restores
that exact inherited user before later artifact steps and in the final image. A separate service `user:` override
remains runtime intent recorded on the service plan: it is never baked into the derived artifact,
and applying it to the running container is a provider concern outside this scaffold.

`lando.certs` mounts service leaf material under the certificate directory. `lando.security`
creates `/etc/lando/certs` itself when it writes the injected CA bundle described in
[Corporate network trust](../config/corporate-network-trust.mdx).

`lando.boot` owns directories only. The higher-priority `lando.env` feature owns
`/etc/lando/environment`, `/etc/lando/env.d` content and per-exec sourcing, and the `LANDO_LINUX_*`
distro exports. See [Certificates with mkcert](../subsystems/certificates-mkcert.mdx) for the
separate leaf certificate paths and environment contract.
