Every `type: lando` service includes the `lando.boot` feature. `lando.boot` (priority 100) emits one
provider-neutral, artifact-phase scaffold intent: an idempotent `mkdir -p` step compiled into the
service's build plan, not a mount:

```text
/etc/lando
/etc/lando/env.d
/etc/lando/certs
```

The scaffold step is not a mount, so it does not hide files that higher-priority features add
beneath these directories. It currently runs as whichever effective user the parent artifact has
already inherited at that point in the build. Temporarily elevating privilege to create these
directories on a parent artifact that has inherited a non-root effective user, and then restoring
that exact non-root user afterward, is not yet implemented; today the scaffold step depends on the
inherited user already being able to create these paths.

`lando.certs` mounts the certificate directory for service leaf material, while `lando.security`
creates its own `/etc/lando/certs` trust-store directory when it writes the injected CA bundle
described in [Corporate network trust](../config/corporate-network-trust.mdx).

`lando.boot` owns directories only. The higher-priority `lando.env` feature owns
`/etc/lando/environment`, `env.d/` content and per-exec sourcing, and the `LANDO_LINUX_*` distro
exports. See [Certificates with mkcert](../subsystems/certificates-mkcert.mdx) for the separate leaf
certificate paths and environment contract.
