# See what lando.boot adds

Every `type: lando` service includes `lando.boot`. At priority 100 it adds a provider-neutral, artifact-phase scaffold to the build plan. That is an idempotent `mkdir -p` step, not a mount:

```text
/etc/lando
/etc/lando/env.d
/etc/lando/certs
```

Because the scaffold is not a mount, it does not hide files that higher-priority features add under
these directories. The scaffold step declares `user: root`, the same per-step `user` any build step
can name (see [Run build steps as root or as your app user](./build-steps.mdx)). Planning resolves
every step's user before the provider runs, so the provider never re-resolves one. When the base is a
referenced parent image, the artifact realizer still builds a local intermediate base from that
parent and inspects the built artifact to learn that image's own effective user, because that
identity is not knowable at planning time. The realizer then emits a `USER` switch only when a step's
resolved user differs from the active one and restores the service's final user after the last step.
That final user is `services.<name>.user` when you set it, otherwise the base image's own user. A
service `user:` override is therefore both the identity the derived artifact ends on and the identity
the container runs as.

`lando.certs` mounts service leaf material under the certificate directory. `lando.security`
creates `/etc/lando/certs` itself when it writes the injected CA bundle described in
[Corporate network trust](../config/corporate-network-trust.mdx).

`lando.boot` owns directories only. The higher-priority `lando.env` feature owns
`/etc/lando/environment`, `/etc/lando/env.d` content and per-exec sourcing, and the `LANDO_LINUX_*`
distro exports. See [Certificates with mkcert](../subsystems/certificates-mkcert.mdx) for the
separate leaf certificate paths and environment contract.

Raw Compose services (`type: compose`) use the l337 base and do not include `lando.boot`.
