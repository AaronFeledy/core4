# Paste a Compose service into a Landofile

Put `type: compose` on a service and keep the Compose keys the [generated Compose key matrix](../../reference/compose-key-matrix.mdx) accepts. `extra_hosts`, published `ports`, and `depends_on` conditions all survive into the plan.

After completing `lando setup`, save the following as `.lando.yml` in an app directory. It defines a cache service and a web service published on host port 8080:

```yaml
name: compose-service-block-demo
services:
  cache:
    type: compose
    image: valkey/valkey:8-alpine
  web:
    type: compose
    image: traefik/whoami:v1.10
    ports:
      - target: 80
        published: "8080"
        protocol: tcp
    depends_on:
      cache:
        condition: service_started
    extra_hosts:
      - "internal.test:127.0.0.1"
```

From that directory, run `lando start`, then `lando info` to inspect the services and their connection details.

`configs:` grants are realized as read-only binds. Declare the file at the top level, grant it onto a service with `source` / `target` / `mode`, and the bundled providers mount it. Use this for a file such as a custom `php.ini`. With `mode`, Lando mounts a private copy of the file with those permissions, and editing the file gives the container a new copy on the next `lando start`. A grant takes a path like any other mount: two grants, or a grant and a `volumes:` entry, at the same container path fail `lando app:config:lint`, and a `mounts:` entry at that path wins. `uid` and `gid` are not supported, because Lando cannot change the owner of a host file it mounts; use `mode` so the service user can read it.

A string `command:` or `entrypoint:` on a `type: compose` service splits into argv the way Compose does: whitespace separates, quotes group, no shell runs. Neither a string nor a list starts a shell on its own; put `sh -c '<script>'` in the argv yourself when you need pipes, `&&`, or variable expansion. See [Add a Compose service](../../services/compose-passthrough/) for the details.

A service-level `networks:` key works too, with one difference from Compose: it adds networks and never takes the service off the app network. Declare each network under top-level `networks:` first. If you'd rather not paste at all, top-level `include:` pulls a whole compose file in as services. See [Reach another project's services](./networks.mdx) for both, plus external networks, app-owned networks, and the names you get on them.

## Limit memory, CPU, and processes

Set resource limits under `deploy.resources`, the Compose spelling. The `docker` and `podman` providers apply them. The default `lando` provider doesn't apply them yet, so on it planning fails with `CapabilityError`, and the remediation names the providers that can and the `lando setup --provider=<id>` command that switches to one. Save this as `.lando.yml`:

```yaml
name: limits-demo
services:
  worker:
    type: compose
    image: alpine:3.20
    appMount: false
    command: sleep infinity
    deploy:
      resources:
        limits:
          memory: 512m
          cpus: "0.5"
          pids: 200
        reservations:
          memory: 256m
```

`limits.memory` caps the container's memory, `limits.cpus` caps its CPU time as a share of one CPU, and `limits.pids` caps how many processes it can run at once. `reservations.memory` is a soft floor the kernel tries to keep available under memory pressure. As in Compose, `0` means no limit, and so does `pids: -1`.

Run `lando start`, then read the memory cap from inside the service:

```sh
lando exec worker -- cat /sys/fs/cgroup/memory.max
```

On a cgroup v2 host the file holds `536870912`, which is 512 MiB. `cpu.max` and `pids.max` in the same directory show the other two limits.

Lando reads these settings only from `deploy.resources`. The flat Compose keys `mem_limit`, `cpus`, `pids_limit`, and `mem_reservation` are rejected; move each value to `deploy.resources.limits.memory`, `limits.cpus`, `limits.pids`, or `reservations.memory`. `deploy.resources.reservations.cpus` and `reservations.generic_resources` are rejected too, because Compose applies them only to Swarm services. Use `limits.cpus` to cap CPU instead.

`lando app:config:lint` checks these values before anything starts. `limits.cpus` takes a number or a decimal string such as `"0.5"`, from `0` up to `9007199`. `limits.memory` and `reservations.memory` take a byte size such as `512m` or a whole number of bytes. `limits.pids` takes a whole number. Anything else fails lint and `lando start` at the value's own path, such as `services.worker.deploy.resources.limits.cpus`, so you can fix the Landofile before Lando creates a network or a container.

## Give a service a GPU

GPU requests work on the `docker` provider, which hands them to Docker Engine the way Docker Compose does. Docker needs the GPU vendor's container runtime, such as the NVIDIA Container Toolkit, before a container can see the device.

```yaml
services:
  ollama:
    type: compose
    image: ollama/ollama
    gpus: all
```

`gpus: all` requests every GPU. For a specific device, use the list form, or the equivalent `deploy.resources.reservations.devices` entry:

```yaml
services:
  ollama:
    type: compose
    image: ollama/ollama
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              device_ids: ["0"]
              capabilities: [gpu]
```

After `lando start`, confirm Docker received the request. Replace `<app>` with your app name:

```sh
docker inspect lando-<app>--ollama --format '{{json .HostConfig.DeviceRequests}}'
```

The `lando` and `podman` providers don't apply GPU requests. On them, planning fails with `CapabilityError`, and the remediation names `docker` when that provider is installed. Switch with `lando setup --provider=docker`; see [Pick a container provider](../setup/provider-selection.mdx).

## Keep Lando features on a custom image

Use `type: lando` instead when you want Lando's environment and app mount. Its
directory scaffold works on shell-less images, including images built from
`scratch`. Lando plans no home store for a custom image unless you declare its home path with `home.path`.

```yaml
services:
  web:
    type: lando
    image: traefik/whoami:v1.10
    ports:
      - "8080:80"
```

Run `lando start`, then `lando info` to inspect the service. The image keeps its
own entrypoint. Shell build hooks and CA trust-store installation still require
the corresponding tools inside the image; leave them unconfigured for a
shell-less image. If your host injects custom CAs, set
`security.inheritNetworkCa: false` on that service. Use `type: compose` to skip
the Lando feature stack entirely.
