# Trust a corporate CA and proxy

Project-specific certificate authorities belong under each service's `security` block. The canonical
form is a list of certificate paths:

```yaml
services:
  appserver:
    security:
      ca:
        - ./certs/corporate-root.pem
      inheritNetworkCa: true
      inheritNetworkProxy: false
```

`inheritNetworkCa` and `inheritNetworkProxy` override the corresponding host network-injection
setting for only that service. Omit either flag to inherit the host default.

For compatibility, `cas`, `certificate-authority`, and `certificate-authorities` are accepted inside
`security`. Each alias accepts one path or a list and canonicalizes to `security.ca`. The top-level
`certs` field configures a service's leaf TLS certificate and is not an alias for additional CAs.

## Load local CA files

Use `load()` when `security.ca` only needs the decoded PEM text. Use `import()` when the CA should
also retain its authored path, basename, checksum, and Landofile layer for later image packing:

```yaml
services:
  appserver:
    security:
      ca:
        - "{{ load('./certs/corporate-root.pem') }}"
        - "{{ import('./certs/team-root.pem') }}"
```

Both helpers resolve relative to the Landofile or include fragment where the expression appears. The
resolved file must stay inside the app root, including after symlink resolution. An outside-root read
fails with remediation to move the file under the app root or enable the global
`allowLoadOutsideRoot` policy; opted-in outside-root reads are logged. Unreadable files and values
without a complete PEM `CERTIFICATE` block fail before planning with a path-specific correction.

## Resolve host CA paths

Host-global CA paths come from `network.ca.certs` or the JSON array in
`LANDO_NETWORK_CA_CERTS`. Use host-readable absolute paths; one shared loader supplies setup and
outbound HTTP with the UTF-8 PEM bytes and a stable SHA-256 digest for service planning. Landofile
`security.ca` remains the project-local CA path list.

This is set-and-forget for `type: lando` services: global CAs inject by default. Set
`security.inheritNetworkCa: false` on one service to opt out of the global CA set while retaining
that service's own `security.ca` entries. `lando setup` remains the preflight for host trust and
reports unreadable CA paths before service startup.

Follow the [guided setup workflow](../setup/provider-auto-setup.mdx) before app lifecycle commands,
use the [doctor walkthrough](../subsystems/doctor-walkthrough.mdx) to diagnose CA and network-trust
readiness, and configure service leaf TLS separately through the
[certificates with mkcert guide](../subsystems/certificates-mkcert.mdx).

If a path cannot be read, Lando names that path and points to all three correction surfaces:
`network.ca.certs`, `LANDO_NETWORK_CA_CERTS`, and Landofile `security.ca`.

This host-global and per-service CA injection is separate from browser trust of the
[Traefik reverse proxy's HTTPS certificates](../subsystems/proxy-traefik.mdx): injected corporate
or service CAs let in-container runtimes trust outbound HTTPS calls, while a browser trusting the
proxy's own HTTPS certificates depends on the CertificateAuthority root that `lando setup` installs
into the host trust store.

Use `LANDO_NETWORK_CA_INJECT_INTO_SERVICES=true|false` to override
`network.ca.injectIntoServices`, and `LANDO_NETWORK_PROXY_INJECT_INTO_SERVICES=true|false` to
override `network.proxy.injectIntoServices`. Values other than `true` or `false` are rejected as
invalid global config. `LANDO_NETWORK_CA_CERTS` remains a JSON array of additional CA paths; it does
not replace either injection flag.

## Runtime CA environment and rebuilds

When a `type: lando` service receives one or more injected CAs, each host PEM is mounted read-only
under `/usr/local/share/ca-certificates`. The runtime trust paths stay fixed before and after the
service image is rebuilt. The [`lando.boot` scaffold](../services/lando-boot-scaffold.mdx) emits a
provider-neutral, artifact-phase intent for the shared `/etc/lando/certs` directory; `lando.security`
also creates that directory itself before it writes its CA bundle there, so the bundle path below is
independent of `lando.boot`'s realization state:

```text
NODE_EXTRA_CA_CERTS=/etc/lando/certs/ca-bundle.pem
SSL_CERT_FILE=/etc/lando/certs/ca-bundle.pem
SSL_CERT_DIR=/etc/lando/certs
LANDO_CA_CERT=/etc/lando/certs/ca-bundle.pem
LANDO_CA_BUNDLE=/etc/lando/certs/ca-bundle.pem
LANDO_CA_DIR=/etc/lando/certs
```

The bundled language service types consume that trust material as follows:

| Runtime | Effective CA behavior when CA material injects |
| --- | --- |
| Python | `REQUESTS_CA_BUNDLE` points to `/etc/lando/certs/ca-bundle.pem`. `SSL_CERT_FILE` uses that path unless the service already authored a value, which Lando preserves. |
| Node.js | `NODE_EXTRA_CA_CERTS` points to `/etc/lando/certs/ca-bundle.pem`. |
| PHP | `SSL_CERT_FILE` and `SSL_CERT_DIR` provide the OpenSSL trust paths. |
| Ruby | `SSL_CERT_FILE` and `SSL_CERT_DIR` provide the OpenSSL trust paths. |
| Go | The derived service artifact installs the injected CAs into the system trust store; no Go-specific environment variable is required. |

These runtime variables are absent when the service receives no injected CA material.

Run `lando rebuild` after CA material changes so the service artifact registers the updated trust
store. The bundle and directory paths do not change across that rebuild.

## Confirm injection during setup

When `lando setup` resolves at least one readable host CA file and CA injection is enabled, it
reports that configured host CAs are set to inject into eligible `type: lando` services:

```text
Configured host certificate authorities are set to inject into eligible type: lando services on the next plan or rebuild.
```

The note is informational and never fails setup. It is omitted when no host CA files are configured
or when `network.ca.injectIntoServices` (or `LANDO_NETWORK_CA_INJECT_INTO_SERVICES`) disables
injection. Machine consumers read the boolean `networkCaInjectionConfigured` from
`lando setup --format json`; it is `true` only when both conditions hold, and `false` both when no
host CAs are configured and when injection is disabled. Human-facing setup text is renderer output
and must not be parsed as machine state.

Setup reports host-global configuration, not the CA set of any particular service, and it
deliberately publishes no certificate count. Setup runs before any app plan, so it cannot know the
CAs a service actually receives: the planner collapses duplicates by content digest, a single file
may carry several certificate authorities, and `security.inheritNetworkCa: false` opts an individual
service out. Read a service's effective trust material from its plan or from
`/etc/lando/certs/ca-bundle.pem` inside the running service, not from setup output.

## Configure a global proxy

Author the corporate proxy under `network.proxy` in the global config. `http` and `https` are each
a URL string or `null`; `noProxy` is a list of hostnames or suffixes; `injectIntoServices` controls
whether the resolved proxy env reaches `type: lando` services:

```yaml
network:
  proxy:
    http: "http://proxy.corp.example:8080"
    https: "http://proxy.corp.example:8080"
    noProxy:
      - "localhost"
      - ".corp.example"
    injectIntoServices: false
```

Proxy precedence is block-level, not field-level: a non-empty `http` or `https` value, or a
non-empty `noProxy` list, makes the whole `network.proxy` block the sole source of proxy values for
outbound requests. Lando then ignores the `HTTP_PROXY`, `HTTPS_PROXY`, and `NO_PROXY` environment
variables (and their lowercase forms), even for a field you left unset. An absent block, or a block
whose `http`, `https`, and `noProxy` values are all empty or unset, falls back to those environment
variables instead. Within a block selected by another non-empty proxy value, set `http` or `https`
to `null` to disable that direction without falling back to its environment variable. A block that
contains only `null` values does not select config precedence by itself.

`network.proxy.injectIntoServices` defaults to `false`, the opposite of
`network.ca.injectIntoServices`'s default `true`. Proxy URLs can carry embedded credentials
(`http://user:pass@proxy.corp.example:8080`), so Lando never writes proxy env into a service unless
you opt in; CA certificates carry no comparable secret, so CA injection is set-and-forget by
default. Set `security.inheritNetworkProxy` on one service to override the global default for that
service only, independent of `security.inheritNetworkCa`: each flag is `true`, `false`, or omitted,
and an omitted flag inherits its own global default, not the other flag's setting.

When proxy injection runs for a service, `type: lando` services receive `HTTP_PROXY` only when an
`http` value resolved and `HTTPS_PROXY` only when an `https` value resolved, both uppercase; there
is no lowercase `http_proxy`/`https_proxy` pair written into the service. `NO_PROXY` is always
written when injection runs, as a comma-joined string, even when `noProxy` resolved to an empty
list (an empty string is still a defined `NO_PROXY=` env entry, not an absent variable).

`lando doctor` reports proxy state through `proxyConfigured` (whether an `http` or `https` value
resolved), `proxyInjectIntoServices`, and `noProxyCount`. It does not print the resolved proxy URL
or any embedded credential. `lando setup` does not publish those proxy fields; proxy failures still
run through the command redaction boundary before they reach a human or a `--format json` consumer.
