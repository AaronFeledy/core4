# Read and write global config

Run `lando config --format=json` to read your effective host-level settings. It never changes a project's Landofile or the shared global app.

## Set app defaults and read them back

Use `appEnv` for environment defaults and `appLabels` for container-label defaults. They apply to user-app services; values authored on a service win. The full view includes both maps under `result.config`. A lookup also returns the selected map or scalar under `result.value`.

These commands replace each whole map. Keep any existing entries you want before running them.

```sh
lando config set appEnv '{"TEAM":"platform"}' --type=json
lando config set appLabels '{"team":"platform"}' --type=json
lando config get appEnv --format=json
lando config get appLabels --format=json
lando config --format=json
```

The equivalent `config.yml` entries are:

```yaml
appEnv:
  TEAM: platform
appLabels:
  team: platform
```

The view exposes public settings, not internal bookkeeping. Secret-bearing environment values and proxy credentials are redacted before output, including single-key lookups and JSON or YAML output. Redaction does not change the values stored in `config.yml`.

## Choose the effective value

`ConfigService` merges the global config in a deterministic order. A later source wins: defaults, then `config.yml`, then `LANDO_CONFIG__*` env vars, then inline flags. A `LANDO_CONFIG__*` env var maps its SCREAMING_SNAKE_CASE path to the matching camelCase config key and overrides the file for that key, for example `LANDO_CONFIG__DEFAULT_PROVIDER_ID=podman`.

The installation config lives at `config.yml` under the resolved user config root, for example `/home/user/.local/share/lando/config.yml` on Linux.

`LANDO_PROVIDER` does not persist as last-used. After a successful `lando setup --provider=docker`, later `lando doctor` and `lando start` stay on Docker.

## Get, set, unset, validate, or edit a key

```sh
# Read a single dot-path key
lando config get defaultProviderId

# Write a single dot-path key to config.yml; --type controls how the value is parsed
lando config set defaultProviderId podman --type string

# Remove a key from config.yml
lando config unset defaultProviderId

# Decode config.yml against the GlobalConfig schema without changing anything
lando config validate

# Open config.yml in $VISUAL or $EDITOR, or pass --editor
lando config edit
```

## Configure the shared global app

`lando global:config` reads and writes the shared global app, the always-on app that runs host-wide services such as the proxy, Mailpit, and the SSH agent. Lando starts Traefik for you as part of that app. It's a Landofile stack, not `config.yml`: `lando config` owns host settings such as `appEnv` or `router`, and `lando global:config` owns the global app's services.

Install the global app first, then override a bundled service, check the effective result, and apply it:

```sh
lando global:install
lando global:config set services.mailpit.environment.MP_MAX_MESSAGES 1000
lando global:config --format=json
lando global:rebuild
```

`set`, `unset`, and `edit` write only the canonical Landofile at `<userDataRoot>/global/.lando.yml`, for example `/home/user/.local/share/lando/global/.lando.yml` on Linux. `validate` checks that same file. Leave the generated `.lando.dist.yml` alone; Lando regenerates it.

## Read the effective global config

`lando global:config --format=json` prints the effective global Landofile, not the raw files. `result.landofile` is every present layer merged in order, and `result.paths` names the files behind it. The envelope also reports `app` (always `global`), `source` (the fixed literal `global`), and `materialized` (whether the generated file exists yet). Until `lando global:install` generates `.lando.dist.yml`, the view reports `materialized: false` with an empty Landofile, even if your `.lando.yml` already has overrides. Run `lando global:install` to see the merged result.

Lando merges the six standard Landofile layers from `<userDataRoot>/global/`. A later layer wins:

| Order | File | Who writes it |
| --- | --- | --- |
| 1 | `.lando.base.yml` | You, optional |
| 2 | `.lando.dist.yml` | Lando, from plugin `globalServices:` |
| 3 | `.lando.upstream.yml` | You, optional |
| 4 | `.lando.yml` | `lando global:config set`, `unset`, and `edit` |
| 5 | `.lando.local.yml` | You, optional |
| 6 | `.lando.user.yml` | You, optional |

The generated file sits below your canonical Landofile, so your overrides beat plugin defaults. The merged app is always named `global` and always runs on the `lando` provider, whatever the layers say.

## Change the global app

```sh
# Write a dot-path key into the canonical global Landofile
lando global:config set services.mailpit.environment.MP_MAX_MESSAGES 1000

# Remove a dot-path key from the canonical global Landofile
lando global:config unset services.mailpit.environment.MP_MAX_MESSAGES

# Decode the canonical global Landofile against the Landofile schema without changing anything
lando global:config validate

# Open the canonical global Landofile in $VISUAL or $EDITOR, or pass --editor
lando global:config edit
```

Writes don't touch running containers. Check `lando global:config --format=json`, then run `lando global:rebuild` to apply the change.
