Run `lando config --format=json` to read your effective host-level settings. It never changes a project's Landofile or the shared global app.

## Set app defaults and read them back

Use `appEnv` for environment defaults and `appLabels` for container-label defaults. They apply to user-app services; values authored on a service win. The full view includes both maps under `result.config`. A lookup also returns the selected map or scalar under `result.value`.

These commands replace each whole map. Keep any existing entries you want before running them.

```sh
lando config set appEnv '{"TEAM":"platform"}'
lando config set appLabels '{"team":"platform"}'
lando config get appEnv --format=json
lando config get appLabels --format=json
lando config --format=json
```

The equivalent `config.yml` entries are:

```yaml
appEnv:
  TEAM: platform
appLabels:
  team: platform
```

The view exposes public settings, not internal bookkeeping. Secret-bearing environment values and proxy credentials are redacted before output, including single-key lookups and JSON or YAML output. Redaction does not change the values stored in `config.yml`.

## Choose the effective value

Lando reads global config from ordered layers. A later layer wins:

| Order | Layer | Notes |
| --- | --- | --- |
| 1 | Built-in defaults | Platform roots, `defaultProviderId: lando` |
| 2 | `<userConfRoot>/config.yml` | The file `lando config set` writes |
| 3 | `<userConfRoot>/config.d/*.yml` | Drop-ins, lexical filename order, `.yml` only |
| 4 | Environment | `LANDO_CONFIG__*`, aliases such as `LANDO_ROUTER_HTTP_PORT`, root vars such as `LANDO_USER_DATA_ROOT` |
| 5 | Host `config` option | Embedding hosts only, see [Embed the runtime](../library/embedding-runtime.mdx) |

Maps deep-merge across layers. Arrays and scalars replace. `appEnv` and `appLabels` replace as whole maps. A `LANDO_CONFIG__*` env var maps its SCREAMING_SNAKE_CASE path to the matching camelCase key, for example `LANDO_CONFIG__LOG_LEVEL=debug` or `LANDO_CONFIG__ROUTER__HTTP_PORT=8080`.

The installation config lives at `config.yml` under the resolved user config root, for example `/home/user/.config/lando/config.yml` on Linux. That root is fixed before any file is read, so a `userConfRoot` key inside `config.yml` or a drop-in is ignored. The other roots resolve as runtime option, then root env var, then config files, then the platform default.

Each command resolves config once, at startup, and keeps that snapshot. Long-lived runtimes such as `lando mcp serve` or an embedding host keep the config they started with until you restart them.

Lando warns once per command about an unknown key, with the closest match when it has one: `Unknown config.yml key "routerr". Did you mean "router"?`. Text mode prints it as a `⚠` line before the result, including from `lando config get`, `lando config`, and `lando doctor`. `--format=json` carries the same text under `warnings` with code `LANDO_MESSAGE_WARN`.

Double-quoted YAML treats `\t` and `\n` as escapes, so `"C:\temp\new"` becomes a tab and a newline. Use single quotes (`'C:\temp\new'`) or doubled backslashes (`"C:\\temp\\new"`) for Windows paths. Lando warns at load when a path-like root value decodes with control characters.

`defaultProviderId` is the provider `lando setup` persisted. `LANDO_PROVIDER` overrides it per command and never writes it. See [What persists](../setup/provider-selection.mdx#what-persists).

## Allow additional host URL schemes

Use `hostProxy.allowedSchemes` to allow URL schemes beyond the host proxy's built-in list. From your host terminal, set the full list of additional schemes and check the effective value:

```sh
lando config set hostProxy.allowedSchemes '["figma","slack"]' --type=json
lando config get hostProxy.allowedSchemes --format=json
```

The equivalent `config.yml` entry is:

```yaml
hostProxy:
  allowedSchemes:
    - figma
    - slack
```

The lookup should contain `figma` and `slack` unless a higher-precedence layer replaces the array. Arrays replace across layers; include every additional scheme you want to keep. Use scheme names without a trailing colon. Scheme comparisons ignore case. `file` is always rejected, regardless of case; reveal files by path instead. Each host-proxy call reads current disk config in a fresh Lando process, so changes take effect on the next call without restarting the app. The worker's host environment remains the one captured when it started.

## Choose a host-wide file-sync policy

`defaultFileSyncEngine` controls acceleration on providers with slow bind mounts. Leave it unset for automatic selection. Lando considers only engines that support your platform, the provider's sync-target capabilities, exclusion patterns, and `two-way-safe` synchronization. It chooses a unique matching default, then a sole eligible engine. With no eligible engine, apps use ordinary binds with reason `no-compatible-engine`; macOS and Docker Desktop do not need an opt-out workaround. Ambiguous choices fail with remediation rather than depending on plugin load order.

To deliberately keep every app mount ordinary, set the reserved policy `passthrough` and verify the effective value:

```sh
lando config set defaultFileSyncEngine passthrough
lando config get defaultFileSyncEngine --format=json
```

The equivalent `config.yml` entry is:

```yaml
defaultFileSyncEngine: passthrough
```

You can name an installed engine instead, but its id never bypasses support checks. An unknown or unsupported explicit choice fails when host policy is evaluated, including on native providers. A valid choice does not force native binds to accelerate. `passthrough` is a no-session policy, not an engine. For one service only, use `appMount.accelerate: false` in its Landofile.

After changing the setting, run these commands from an app directory to inspect the desired policy without starting services:

```sh
lando app:cache:refresh
lando info --format=json
```

Read `result.fileSync.planned` and, when available, `result.fileSync.applied`. `pendingChange` is true when both realizations are known and their snapshots differ. If desired planning fails, available applied state is still shown, `planned` is absent, and `pendingChange` is false. Run `lando app:cache:refresh` to inspect that planning failure. The engine appears once at app level; each service reports its mode and reason, exclusion mechanism, and host-backed includes. These are plan facts, not daemon health. Historical reasons can be `unknown`.

Changes take effect on the next `lando start`. Existing accelerated apps must first drain through their recorded engine, preserving container-side edits. Missing tools or failed setup, availability, or target preparation after acceleration is planned fail with remediation; they never silently downgrade the app. See [Switch between accelerated and ordinary mounts](../setup/file-sync-mutagen.mdx#switch-between-accelerated-and-ordinary-mounts) before changing an app that already uses sync.

To return to automatic selection, run `lando config unset defaultFileSyncEngine`, then `lando config get defaultFileSyncEngine --format=json`. If a drop-in or `LANDO_CONFIG__DEFAULT_FILE_SYNC_ENGINE` still supplies a value, clear it in that higher-precedence layer too.

## Get, set, unset, validate, or edit a key

Lando picks the value type from the config schema: text first, then number, boolean, null, or JSON. Use `--type` to force a type, for example `--type=json` to write a JSON array into a field that also accepts text.

`set` and `unset` keep comments and formatting outside the value or entry you change. If Lando can't edit safely, it refuses without changing the file. Use `lando config edit` or edit by hand instead. The same rule applies to `lando app:config` and `lando global:config`; use their `edit` verb when an edit is refused.

Use diagnostic logging to try these commands without changing your provider. First read the effective value and the value stored in `config.yml`. Record the stored value, or note that the key is absent, before changing it:

```sh
lando config get logLevel
lando config get logLevel --source raw
```

Enable debug logging and read the effective value again:

```sh
lando config set logLevel debug
lando config get logLevel
```

The last command should report `debug` unless a higher-precedence layer overrides it. When finished, restore a previously stored value with `lando config set logLevel <previous-value>`, replacing `<previous-value>` with the value you recorded. Only if `config.yml` had no `logLevel` key before this example, remove the added key:

```sh
lando config unset logLevel
```

Read `lando config get logLevel` again to check the restored effective value. Validate every config layer without changing it, or open `config.yml` in your editor:

```sh
lando config validate
lando config edit
```

`edit` uses `$VISUAL` or `$EDITOR`; pass `--editor` to choose another editor. Add `--dry-run` to `set`, `unset`, or `edit` to run the same validation and report the result, including `"dryRun": true` in `--format=json`, without writing `config.yml`. A dry-run `edit` still opens your editor; Lando validates the buffer you save and then discards it.

A change that would leave `config.yml` as it is still validates and writes nothing: `set` to the value the file already holds reports `logLevel is already set to "debug" (text) (no change)`, `unset` of a key the file doesn't hold reports `(no change)`, and `edit` where you save the buffer untouched reports `no edits made to config (no change)`. JSON carries `"changed": false` in each case, dry run or not. Both compare against `config.yml` alone: a value that only a drop-in, env override, or default supplies is not a key in the file, so `set` to that value writes it and `unset` of it changes nothing and keeps the effective value.

`--source raw` shows the parsed `config.yml` by itself, before drop-ins, env, and defaults. It works even when that file fails validation, which makes it the quickest way to see what you actually wrote:

```sh
lando config --source raw --format=json
lando config get router --source raw --format=json
```

## Repair an invalid global config

Every command that needs global config fails the same way when any layer doesn't decode: one `ConfigError` at exit `1`, raised before the command runs. That covers `lando info`, `lando start`, `lando app:config:lint`, and the resolved `lando config` views. Nothing deletes or rewrites a file for you.

Each issue names where the bad value came from and the exact fix. With `httpPort: 99999` in `config.yml`, `lando config` prints:

```
Invalid config file /home/user/.config/lando/config.yml: router.httpPort: Expected a value between 1 and 65535. Run `lando config unset router.httpPort` or `lando config set router.httpPort <value>`.
  ↳ Run `lando config unset router.httpPort` or `lando config set router.httpPort <value>`. Run `lando config validate`, then use `lando config set <key> <value>` / `lando config unset <key>`, or `lando config edit` to repair config.yml.
code: ConfigError
commandId: meta:config
issues:
/home/user/.config/lando/config.yml: router.httpPort: Expected a value between 1 and 65535. Run `lando config unset router.httpPort` or `lando config set router.httpPort <value>`.
path: /home/user/.config/lando/config.yml
logsDir: /home/user/.cache/lando/logs
cacheDir: /home/user/.cache/lando
```

Messages say what the schema expected (`Expected string | null`, `Expected a value between 1 and 65535`, `Expected one of lando, json, plain, verbose.`) and never echo the value you wrote, so a secret pasted into the wrong key doesn't land in a log.

`--format=json` carries the same facts under `error.path`, `error.remediation`, and `error.issues`. Each issue is `{ path, message, suggestion, source }`: `path` is an array of keys, `suggestion` is the fix, and `source` says which layer supplied the value:

| Layer | `source` | `suggestion` |
| --- | --- | --- |
| `config.yml` | `{ layer: "config-file", file, path }` | `` Run `lando config unset <key>` or `lando config set <key> <value>`. `` |
| Drop-in | `{ layer: "config-drop-in", file, path }` | `Edit <file>.` |
| Environment | `{ layer: "env", variable, path }` | `Unset <variable> or set it to a valid value.` |
| Host option | `{ layer: "host", path }` | `` Fix the `<key>` host config option. `` |

The message starts with `Invalid config file <path>` when every issue comes from `config.yml`, and `Invalid global configuration (<sources>)` otherwise, for example `(environment override LANDO_ROUTER_HTTP_PORT)` or `(config file /home/user/.config/lando/config.d/10-team.yml and environment override LANDO_ROUTER_HTTP_PORT)`. When several layers are wrong, it names each.

`lando config` itself doesn't need a valid config, so the repair verbs keep working:

```sh
# List every issue across config.yml, config.d, and env; exits 1 with the same ConfigError
lando config validate

# See the file you wrote, even when it fails validation
lando config --source raw --format=json

# Replace the bad value, or drop the key to fall back to the default
lando config set router.httpPort 8080
lando config unset router.httpPort

# Fix it by hand; the editor flow validates before it saves
lando config edit
```

`set` and `unset` let you repair one key at a time. A write fails with `LandofileWriteValidationError` only when it introduces a problem or leaves the written key (or anything beneath it) invalid. The file stays unchanged on rejection. Problems already present elsewhere in `config.yml` don't block the write: the command succeeds and reports each remaining issue and its fix once, as a text warning or a `LANDO_CONFIG_PREEXISTING_ISSUES` warning in `--format=json`. Issue identity is its path plus its message. `telemetry off` follows the same rule for `telemetry.enabled`; `edit` still requires the whole edited file to be valid.

For example, if `router.httpPort`, `defaultProvidreId`, and `tracing.otlp.headers` are all invalid, unset or fix one of them, then use the warnings to repair the others. Comments in the file stay put. `lando app:config set` / `unset` and `lando global:config set` / `unset` use the same write rule for their Landofiles.

Problems in another config layer never block the write: fixing `config.yml` while `LANDO_ROUTER_HTTP_PORT=99999` is still exported succeeds. Once the candidate file is valid, the command reports the other source and its fix with `LANDO_CONFIG_OTHER_SOURCE_INVALID`. Unset the variable or edit the drop-in it names, then rerun `lando config validate`.

## Add host-wide lifecycle steps

Edit `<userConfRoot>/config.yml` to add `hostEvents` for every user app. The shared global app and scratch apps are excluded. Environment overrides cannot set this key, and `lando config set` / `lando config unset` refuse every `hostEvents` path.

```yaml
hostEvents:
  pre-start:
    - cmd: echo host-wide
      service: ":host"
```

Run `lando config validate`, then `lando config --format=json` to check the result. `lando config edit` validates the same rules before saving. See [Run tasks at app lifecycle events](../landofile/events.mdx) for step forms, ordering, and skip rules.

## Configure the shared global app

`lando global:config` reads and writes the shared global app, which runs host-wide services such as the proxy, Mailpit, and the SSH agent when needed. Lando starts Traefik for you as part of that app. It's a Landofile stack, not `config.yml`: `lando config` owns host settings such as `appEnv` or `router`, and `lando global:config` owns the global app's services.

Generate the global configuration first, then override a bundled service, check the effective result, and apply it:

```sh
lando global:reconcile
lando global:config set services.mailpit.environment.MP_MAX_MESSAGES 1000
lando global:config --format=json
lando global:start
```

`set`, `unset`, and `edit` write only the canonical Landofile at `<userDataRoot>/global/.lando.yml`, for example `/home/user/.local/share/lando/global/.lando.yml` on Linux. `validate` checks the whole layer stack. Leave the generated `.lando.dist.yml` alone; Lando regenerates it.

## Read the effective global config

`lando global:config --format=json` prints the effective global Landofile, not the raw files. `result.landofile` is every present layer merged in order with ineligible contributions excluded, and `result.paths` names the files behind it. The envelope also reports `app` (always `global`), `source` (the fixed literal `global`), and `materialized` (whether the generated file exists yet). Until `.lando.dist.yml` has been generated, the view reports `materialized: false` with an empty Landofile, even if your `.lando.yml` already has overrides. Run `lando global:reconcile` to generate configuration from your saved choices without starting services.

Lando loads the global root exactly like an app root: the same six layers from `<userDataRoot>/global/`, each in YAML or TypeScript form. A later layer wins:

| Order | Layer | Who writes it |
| --- | --- | --- |
| 1 | `.lando.base.yml` or `.lando.base.ts` | You, optional |
| 2 | `.lando.dist.yml` | Lando, from plugin `globalServices:` |
| 3 | `.lando.upstream.yml` or `.lando.upstream.ts` | You, optional |
| 4 | `.lando.yml` or `.lando.ts` | `lando global:config set`, `unset`, and `edit` (YAML form only) |
| 5 | `.lando.local.yml` or `.lando.local.ts` | You, optional |
| 6 | `.lando.user.yml` or `.lando.user.ts` | You, optional |

A layer takes one form, not both. A root with `.lando.yml` and `.lando.ts` side by side fails with `LandofileFormConflictError` naming both files; remove one. TypeScript layers follow the rules in [Write a Landofile](../landofile/your-landofile.mdx#replace-or-remove-a-value-with-override-and-reset): default-export `defineLandofile({...})`, and Lando supplies `@lando/sdk` and `effect` at load time with no `node_modules` in the global root.

Every layer resolves its `includes:` before precedence applies, with `<userDataRoot>/global/.lando.lock.yml` as the lockfile that pins remote fragments. See [Includes and the lockfile](../landofile/includes-and-lockfile.mdx).

The generated file sits below your canonical Landofile, so your overrides beat plugin defaults. The merged app is always named `global` and runs on the host provider, whatever the layers say. A `name:` or `provider:` key in these layers does not rename or move it. See [Where the global app runs](../setup/provider-selection.mdx#where-the-global-app-runs).

Contribution enablement is separate from service configuration. Use
`lando global:disable mailpit` to disable Mailpit, and
`lando global:enable mailpit` to re-enable it. Lando saves policy by plugin owner in
`<userConfRoot>/global.config.yml`; `lando global:list --format=json` reports your
choice and its source. Lando uses an individual contribution choice first, then a
package choice, then the contribution's first recorded default. A package action
clears that package's individual choices and applies to its future contributions
too. `lando global:reconcile` preserves choices and retries pending work; it never
starts a container.

Disabling a dependency can affect running user or scratch apps. Disable and
reconcile protect those consumers before saving policy; unavailable inspection
also causes refusal. Inspect `--dry-run --format=json` before proceeding. The
explicit `--allow-disruption` acknowledgement applies only to its invocation and
leaves the affected apps running. It doesn't relax resource ownership checks,
named-volume retention, or protection for an in-flight global or app activation.
Finish that active operation before retrying a refused policy command. See [Disable a shared service](../global/uninstall-and-purge.mdx#disable-a-shared-service)
for the consumer details and recovery steps.

Global mutations first lock the saved policy, then the actual global app root.
Embedded hosts that share `<userConfRoot>/global.config.yml` serialize changes
even when their runtime or data roots differ. Hosts sharing a runtime root also
serialize changes to that root.

Nested in-process command or SDK calls can reuse ownership for the same policy
file and global root. Finish the current operation before switching either
target. A child CLI process needs its own locks; recognized parent ownership
causes refusal rather than lending the parent's locks. Run that mutation
separately after the parent finishes. A child can then acquire fresh locks normally.

A disabled, blocked, or unverified contribution is omitted from the effective
Landofile, including any overrides for its id in the six layers or their includes.
View, validation, and config writes use the same eligibility rules. Those overrides
stay on disk and take effect again when the contribution becomes eligible. Editing
an override does not enable a service. Policies retained for removed plugins do
not hide authored services that reuse those ids. `global:list` explains eligibility
with `state`, `reasons`, and `capabilitySource`, without starting a provider runtime.
Startup uses the same rules with the provider's actual capabilities. See
[Disable a shared service](../global/uninstall-and-purge.mdx#disable-a-shared-service)
for the stop, data-retention, and recovery behavior.

### Write the canonical layer as TypeScript

If `<userDataRoot>/global/.lando.ts` exists, it is the canonical layer. `lando global:config --format=json` and `lando global:config validate` load it. `set`, `unset`, and `edit` refuse with `NotImplementedError`; edit the TypeScript file directly. `lando global:reconcile` still generates `.lando.dist.yml` but does not create a competing `.lando.yml`.

## Change the global app

```sh
# Write a dot-path key into the canonical global Landofile
lando global:config set services.mailpit.environment.MP_MAX_MESSAGES 1000

# Remove a dot-path key from the canonical global Landofile
lando global:config unset services.mailpit.environment.MP_MAX_MESSAGES

# Decode the canonical global Landofile against the Landofile schema without changing anything
lando global:config validate

# Open the canonical global Landofile in $VISUAL or $EDITOR, or pass --editor
lando global:config edit

# Validate a change and report it without writing; works with set and unset too
lando global:config edit --dry-run
```

`set`, `unset`, and `edit` validate the candidate the same way `lando app:config` does, so [Set, unset, and edit from the CLI](../landofile/your-landofile.mdx#set-unset-and-edit-from-the-cli) applies to the global root. A dry run, a rejected candidate, and a no-op such as setting a key to the value `.lando.yml` already holds write neither `.lando.yml` nor a pin in `<userDataRoot>/global/.lando.lock.yml`; the no-op reports `(no change)` or `"changed": false`. An accepted write changes only `.lando.yml`, and the next ordinary load, for example `lando global:config`, publishes any new include pin once the effective config loads successfully. An unfinished multi-file write in that directory stops all three with `ManagedFileTransactionError`; run `lando global:config` to finish it, then retry.

When `.lando.yml` is missing or empty, `edit` opens a buffer seeded with `name: global` and `runtime: 4`. Saving that buffer, edited or not, creates the file, because the seed is new content for a file that had none. Add `--dry-run` to validate the seed and your edits without creating anything.

Writes don't touch running containers. Check `lando global:config --format=json`, then run `lando global:start` to apply env, bind, and image changes. `lando global:rebuild` forces a pull and build refresh. `validate` loads every present layer, including TypeScript layers and their includes, so a bad value in `.lando.local.ts` reports there even though `set` and `unset` only write `.lando.yml`.
