# Pull secrets from the environment or 1Password

Put a `${secret:...}` reference in a service `environment` value, a database `creds.password`, or a tooling `env` value in your `.lando.yml`; Lando resolves it from a secret store when it creates the container or runs the command, never saving the resolved value in the Landofile, the plan cache, or a transcript. The example below uses both the environment and 1Password stores. If you only want the environment store, omit `STRIPE_KEY` before starting the app.

```yaml
name: demo
services:
  app:
    type: "node:22"
    primary: true
    environment:
      DB_PASSWORD: '${secret:DB_PASSWORD}'
      STRIPE_KEY: '${secret:op://Dev Vault/Stripe/credential}'
```

Two stores ship in the box:

| Store | Reference | Where the value comes from |
| --- | --- | --- |
| `env` (default) | `${secret:DB_PASSWORD}` | The host env var `LANDO_SECRET_DB_PASSWORD` |
| `1password` | `${secret:op://Vault/Item/field}` | `op read --no-newline op://Vault/Item/field` through the 1Password CLI |

## Use the env store

From your app directory in a POSIX shell, export the value with the `LANDO_SECRET_` prefix and start the app. Replace the demonstration password with your own value; do not commit real secrets to your Landofile or shell scripts:

```sh
export LANDO_SECRET_DB_PASSWORD='hunter2'
lando start
```

A bare id is anything matching `[A-Za-z0-9_.-]+`. It goes to `defaultSecretStore`, which is `env` unless you change it. A missing variable fails the start with `SecretNotFoundError` naming the exact env var to set.

## Use the 1Password store

Install the 1Password CLI on the host and make sure `op` is on PATH. Replace the example `op://` URI with an item you can access, sign in, then start the app from its directory:

```sh
op signin
lando start
```

The reference is `op://<vault>/<item>/[section/]<field>`, exactly what `op read` accepts. Spaces are fine inside a segment (`op://Dev Vault/Stripe/credential`), so quote the YAML value. An optional `?attribute=<value>` or `?ssh-format=openssh` suffix passes through to `op`.

Desktop app integration works too. Lando waits up to two minutes for you to approve the biometric or unlock prompt before it gives up with `reason: timeout`.

For CI or any host without a person at the keyboard, give the CLI a service account:

```sh
export OP_SERVICE_ACCOUNT_TOKEN='ops_...'
lando start
```

`OP_CONNECT_HOST` and `OP_CONNECT_TOKEN` pass through the same way. Both are redacted wherever Lando prints environment.

Each `op://` reference is read once per Lando process and cached in memory for that process only. Nothing is written to disk and vaults are never enumerated.

## Change the default store

`defaultSecretStore` picks the store that handles bare ids. Scheme references such as `op://` ignore it and always route to the scheme's owner.

```yaml
# config.yml
defaultSecretStore: 1password
```

Or for one invocation:

```sh
LANDO_CONFIG__DEFAULT_SECRET_STORE=1password lando start
```

Naming a store that isn't installed fails with `SecretReferenceInvalidError` the first time a bare id needs it. Since the `1password` store only understands `op://` references, a bare id routed to it fails the same way; set the default to a store that owns bare ids, or keep `env`.

## Where references resolve

Lando recognizes `${secret:...}` only at these authored sites. The reference can be the whole value or part of a value that mixes text and references:

| Site | YAML path |
| --- | --- |
| A service `environment` value | `services.<name>.environment.<KEY>` |
| A database password | `services.<name>.creds.password` or `services.<name>.creds.rootPassword` |
| A Redis password | `services.<name>.password` |
| A tooling `env` value | `tooling.<task>.env.<KEY>`, `tooling.<task>.cmds.<index>.env.<KEY>`, or `toolingDefaults.env.<KEY>` |
| A tooling var `env` value | `tooling.<task>.vars.<name>.env.<KEY>` |
| An event step `env` value | `events.<event>.<index>.env.<KEY>` |

For example, `API_URL: 'https://${secret:HOST}/v1'` keeps the surrounding text and resolves `HOST` when the value is needed. Lando stores that combination as a `BoundText` descriptor, not as the resolved URL. This inserts the secret's bytes unchanged; it does not URL-encode them. The escaped spelling `$${secret:HOST}` is plain text that reaches the container as `${secret:HOST}`.

A reference you write anywhere else in the Landofile, outside the `recipe:` block, fails loading with `LandofileValidationError` before Lando reads a store. Lando skips the entries of an include whose `when` condition is false, so it doesn't check them. The error names the value path and tells you what to write instead for that spot. [Use a secret in a command or build](#use-a-secret-in-a-command-or-build) covers the common cases.

Text that arrives any other way is data, not a request to a store: results of `load()`, `import()`, and `{{ ... }}` expressions, values from `env_file:`, global `appEnv` defaults, and environment that a service type or app feature generates during planning. Lando parses your files once and remembers which values you authored as references. A produced string that happens to read `${secret:KEY}` reaches the container as those exact bytes.

### Credentials carry the reference with them

A database password you author as a reference stays a reference everywhere the service type projects it. Postgres, for example, writes the same value into `POSTGRES_PASSWORD`, into `LANDO_DB_PASSWORD`, into the environment of its `psql` task, and into `lando db:*` operations. None of those copies is a literal; each resolves from the store when the container is created or the command runs.

```yaml
name: bound-creds
services:
  web:
    type: "node:22"
    primary: true
    environment:
      DATABASE_URL: "postgresql://{{ services.db.creds.user }}:{{ url.encodeComponent(services.db.creds.password) }}@db:{{ services.db.port }}/{{ services.db.creds.database }}"
  db:
    type: "postgres:17"
    creds:
      user: lando
      database: bound-creds
      password: '${secret:DB_PASSWORD}'
```

`{{ services.db.creds.password }}` in another service keeps the binding too. You can copy it whole, concatenate it with text, or wrap it in `url.encodeComponent()`, which percent-encodes the resolved bytes for a URL. Any other helper applied to a bound value fails planning with `ConfigExpressionError` at that site, because Lando would need the secret to compute the result. See [Plan-time service credentials](../landofile/expressions.mdx#plan-time-service-credentials).

Lando resolves the database connection once, in the service type: user, database, password, and the planned port. Clients, `lando info`, and `lando db:*` read those facts. `lando info` prints the user and database and redacts the password without reading the store, so you can lint, plan, and inspect this app with `LANDO_SECRET_DB_PASSWORD` unset; only `lando start` and the commands that run against the database need it. If you also author a native variable such as `POSTGRES_PASSWORD` and it disagrees with `creds.password`, planning fails and names both paths, never the values.

For an existing database, generated clients such as `psql` and the `lando db:*` commands use the connection last applied to that service. Editing its user, database, port, or secret reference in the Landofile does not retarget those commands before you apply the change. Your current authored tooling overrides still take precedence over a generated client.

`lando info` lists addresses under `connections`, grouped by App Network and Host scope, alongside the redacted `creds` block. A published host port can differ from the database's internal port. These addresses omit the password rather than resolving its secret reference; generated clients still resolve the binding when they run.

### Precedence is the ordinary kind

A reference is a value like any other. A higher Landofile layer replaces or removes the whole value with the normal merge rules, and a plugin that writes the same key during planning replaces the whole value too, reference or not. Keys a database type owns, such as `POSTGRES_PASSWORD`, are different: an authored value there must agree with the service's connection facts or planning fails at both paths. Changing a reference to `$${secret:HOST}` turns that key into literal text and drops its store lookup. There is no special pass that puts references back after planning.

### When Lando reads the store

- `lando start`, `lando rebuild`, and global-app creation resolve the bindings needed by containers they actually create or replace. Each reference is read once in that operation, even when several keys share it. Provider creation preflight resolves those bindings before replacing containers; reusing an existing container does not fetch its creation secrets.
- Tooling and `lando db:*` commands that need a bound value resolve it when the command runs. Each operation has its own lookup memo; a later operation calls the store again, subject to that store's documented cache policy. Lando does not detect or reconcile password changes in a running database. Recreating a container can change its environment, but does not change credentials already initialized in its persistent database.
- `lando restart --service=db` restarts that existing container in place without resolving its creation secrets. A full `lando restart` is stop plus start and can need the store to create containers again.
- `lando stop`, `lando info`, and `lando logs` do not resolve container-creation secrets. Lifecycle hooks can still need their own bindings when they run tooling or another command.
- `lando app:config` and the plan cache keep the reference, not the value. `lando app:config --format=json` prints a key that holds one as a typed descriptor, `{"_tag":"SecretRef","reference":"DB_PASSWORD"}`, so you can see which store id or `op://` path it points at. The descriptor names a secret; it isn't one, so there's nothing in it to mask. `[redacted]` is what Lando prints in place of a resolved value, as `lando info` does for a database password. Inspecting config never touches a store.
- Image builds don't receive service environment, so a reference in `environment` never reaches a Dockerfile, a `build.args` value, or a `build.artifact` step. `build.app` steps run inside the container after Lando creates it, so they see the values resolved for that container, and their output is redacted. See [Use a secret in a command or build](#use-a-secret-in-a-command-or-build).
- `lando shell` in host mode resolves `${secret:...}` inside a line only when that line runs, with the same grammar and the same stores.

Plans built by this Lando carry a marker for this value model. Containers an older Lando recorded are still observable: `lando info`, `lando stop`, and `lando destroy` read that older plan as it is. Creating or recreating a container from such a plan is refused with `PlanReplanRequiredError` instead of guessing which strings were references. `lando start` plans the app fresh before it creates anything, so the fix is to run it with the current Lando; an embedding host gets the error back with `remediation` set.

Some older applied plans also lack the service-type identity needed to choose a generated database client, especially for a plugin's derived type. Those clients refuse to run with `PlanReplanRequiredError` rather than guess a parent type. Run `lando start` with the current Lando to record the applied identity; refreshing only the plan cache does not update it. Observation and teardown still work.

Every resolved value is registered with the redactor before any event, result, transcript, or failure can carry it. `lando info`, logs, and error envelopes print `[redacted]` in its place. That includes `lando setup` failure evidence and `lando doctor` repair diagnostics, which mask values registered during that same command. Provider errors handed back to a library host mask them in `message` and `details` too. You don't need any extra settings.

Lando also masks URL-encoded, JSON-escaped, and base64 forms of known secret values, including standard base64 and base64url with or without padding, in both text and streamed output.

Any command that runs in or reads from a service container masks its secret values as `[redacted]`, without accessing the secret store. This still works for containers created before you edited the Landofile or upgraded Lando. Host-only tooling and provider-free inspection do not initialize a provider for redaction. This covers surviving containers, not historical values from containers that have been removed. If Lando cannot read those values, the command fails before emitting app output. Lando never saves a decrypted secret cache.

A value resolved from a secret store stays masked even if it matches a public default, a database user, or a database name.

### What gets masked, and where

For literal values in your configuration, Lando uses sensitive names to decide which values to mask. Recognized environment names include `DB_PASSWORD`, `dbPassword`, and `stripe-secret-key`. Automatic value collection does not recognize names such as `PGPASSWORD` or `MYSQL_PWD`. Passwords in `creds` are also recognized.

Where Lando masks a value depends on where the value came from:

- **Everywhere it appears, even inside a longer word.** Values resolved from a secret store, explicitly registered values, host environment values, and values read back from a container, even when they equal a committed literal. Other collected values use this mode unless the same value is also written as a sensitive literal in a committed YAML layer. This includes values that come only from env files, global `appEnv`, the `.lando.local` and `.lando.user` layers, TypeScript or template-rendered Landofiles, or expressions and `load()` results.
- **Only where it stands alone as a whole token.** Sensitive values written as plain literals in a committed YAML layer (`.lando.base.yml`, `.lando.dist.yml`, `.lando.upstream.yml`, `.lando.yml`). The mode follows the value wherever the same value appears: the database service's own variables such as `MYSQL_PASSWORD` and `LANDO_DB_PASSWORD`, generated clients such as `MYSQL_PWD` and `REDISCLI_AUTH`, `{{ services.<name>.creds.password }}` copies, and tooling and event environments.

A token is a run of letters, digits, `_`, `-`, `.`, `/`, and non-ASCII characters. Anything else is a boundary: spaces, quotes, `=`, `:`, `@`, `\`, `%`, `+`, and brackets. Take a committed literal password `wordpress`. Lando masks it in `PASSWORD=wordpress`, `"wordpress"`, `user:wordpress@host`, and `--password wordpress`. It leaves `wp-content/plugins/wordpress-seo`, `wordpress.lndo.site`, `/srv/wordpress/`, `-pwordpress`, and `wordpress.` at the end of a sentence as written. Use a `${secret:...}` reference when a value must be masked everywhere regardless of its other uses. An env-file value also gets that protection if you keep it out of shared YAML.

The `committed-literal-whole-token` scenario at the end of this page shows both modes in one `lando app:config --format=json` run: a `creds.password` of `wordpress` in `.lando.yml` leaves `wp-content/plugins/wordpress-seo` readable, even with a copy of that password in `.lando.local.yml`. A different token written only in `.lando.local.yml` is masked even inside `localtoken-rotated`, which prints as `[redacted]-rotated`.

Automatic collection skips the published defaults `lando` and `landolando`. It also skips a database password or root password that exactly matches its own user or database name, so that name stays readable elsewhere in output. These exceptions do not apply to explicitly registered secrets or secret-store values. Password fields in structured output and password assignments in `lando logs` are still masked.

## Use a secret in a command or build

Bind the secret where the process gets its environment, then read it like any other variable. In a shell command, write `$NAME`: Lando leaves it as written, and the shell expands it when the command runs. Keep it inside double quotes, as in `"$NAME"`, so a value with spaces or a `*` reaches the program as one argument. This Landofile gives a `build.app` step a token for a private asset download and a `deploy` task a deploy token:

```yaml
name: secret-commands
services:
  app:
    type: "node:22"
    primary: true
    environment:
      ASSETS_TOKEN: '${secret:ASSETS_TOKEN}'
    build:
      app:
        - 'curl -fsSL -H "Authorization: Bearer $ASSETS_TOKEN" https://assets.example.com/fonts.tgz | tar -xz -C /app/public'
tooling:
  deploy:
    service: app
    cmd: 'curl -fsS -X POST -H "Authorization: Bearer $DEPLOY_TOKEN" https://deploy.example.com/hooks/secret-commands'
    env:
      DEPLOY_TOKEN: '${secret:DEPLOY_TOKEN}'
```

With the env store, export both values on your host before you start the app and run the task:

```sh
export LANDO_SECRET_ASSETS_TOKEN='assets_example'
export LANDO_SECRET_DEPLOY_TOKEN='deploy_example'
lando start
lando deploy
```

`lando app:config:lint` accepts this file without reading a store, and `lando app:config --format=json` shows `DEPLOY_TOKEN` as a `SecretRef` and the command exactly as written.

Pick the binding by where the command runs:

| Command | Bind the secret in | Read it with |
| --- | --- | --- |
| A catalog service `command` string, or a `build.app` step | `services.<name>.environment.<NAME>` | `$NAME` |
| A tooling `cmd` string or `cmds` step, on a service or on `":host"` | `tooling.<task>.env.<NAME>`, or a step object's own `tooling.<task>.cmds.<index>.env.<NAME>` | `$NAME` |
| An event step's `cmd` or `defer` command | `events.<event>.<index>.env.<NAME>` | `$NAME` |
| A string `healthcheck` or `readiness` command | `services.<name>.environment.<NAME>` | `$NAME` |
| A tooling `vars.<name>.sh` command | The `environment` of the service that runs the var | `$NAME` |
| A `type: compose` string `command` or `entrypoint` | `services.<name>.environment.<NAME>` | `sh -c` with `$NAME` inside one quoted argument |
| `entrypoint`, or a `command` or `cmd` written as a list, on any other type | The matching `environment` or `env` | Your program reads `NAME` from its environment |

A `type: compose` string is split into arguments and is not a shell: `$NAME` stays literal, and an unquoted `;`, `&`, `|`, `<`, or `>` ends the argv there. Write `sh -c 'printf %s "$NAME" && exec sleep infinity'` instead; see [Add a Compose service](../services/compose-passthrough.mdx). Lists and entrypoints on other types also run without a shell. Read the variable in your program, or write a `command` or tooling `cmd` as a string to get a shell; a string `entrypoint` still names one program. A bare string under `events:` has no `env` field, so turn it into a step object first. A tooling task on `":host"` doesn't see any service's `environment`, which is why tooling secrets go in the task's own `env`. Use the bare `$NAME` form there. The host runs Bun Shell, which expands `$NAME` but not `${NAME}`, so `lando app:config:lint` reports an escaped `$${NAME}` in a host command as `landofile.host-shell`.

A `vars.<name>.sh` command doesn't receive the task's `env`. It runs in the var's own `service`, or else the task's, and reads that service's `environment`. Set `sensitive: true` on a var whose output is secret. A var command on `":host"` and a `readiness` probe with `target: host` run on your host without any secret binding, so run them in a service when they need one.

Image builds don't receive service environment, and Lando's bundled providers have no build-time secret input. `build.args`, Dockerfile steps, and `build.artifact` steps never see a reference you bind in `environment`, `${secret:...}` isn't accepted in `build.args`, `build.dockerfile_inline`, or `build.artifact`, and anything written there can be recorded in image history. If the work can run after the service starts, put it in `build.app`, as above. A service built from a Dockerfile (`build.context`) can't also have `build.app` steps, so run that work in a `post-start` event step on the service, with the secret in the step's `env`; it runs on every start. Lando reruns a `build.app` step when its commands or references change, not when the stored value changes, so run `lando rebuild` after you rotate a secret that a step uses.

If you write `${secret:...}` directly in one of those commands, loading fails and the error names the binding to use. When the change is mechanical, Lando also prints the exact edits. For a `deploy` task whose `cmd` holds `${secret:DEPLOY_TOKEN}`, `lando app:config:lint` ends its finding with:

```
    fix: Set tooling.deploy.env.DEPLOY_TOKEN to the ${secret:...} reference and write $DEPLOY_TOKEN in the command. The shell reads it when the task runs.
       | tooling.deploy.env.DEPLOY_TOKEN: "${secret:DEPLOY_TOKEN}"
       | tooling.deploy.cmd: "curl -fsS -X POST -H \"Authorization: Bearer $DEPLOY_TOKEN\" https://deploy.example.com/hooks/secret-command-misuse"
```

Each `|` line is a key to set in that Landofile and its new value. A reference that sat outside quotes comes back as `"$NAME"`, so the shell passes the value as one argument. `lando start` prints the same edits when it refuses the file. With `--format=json`, the violation carries `"reason": "unsupported-secret-reference"` and the same edits in `fix.edits`. A value with several references gets one variable per reference in a single fix.

Lando leaves the edits out when it can't make them safely, and the suggestion still says what to change. For example, it won't rewrite a reference inside single quotes, a command that already uses the chosen variable name, or a command with a here-document or command substitution. A binding removed by a reset directive also gets no fix. Tooling string shorthands, Compose and list commands, healthcheck, readiness, and var commands carry suggestions only. A command that output redaction would mask, such as `npm publish --token=${secret:NPM_TOKEN}`, also gets no edits.

## Errors

Each of these is tagged and carries `remediation`, so `--format=json` output tells you what to do without parsing prose.

| Tag | Fields | When | Fix |
| --- | --- | --- | --- |
| `SecretNotFoundError` | `secret` | The store answered and the secret isn't there | Set `LANDO_SECRET_<id>`, or check the vault, item, section, and field in the `op://` reference |
| `SecretStoreUnavailableError` | `storeId`, `reason: cli-missing` | `op` is not on `PATH` | Install the 1Password CLI |
| `SecretStoreUnavailableError` | `storeId`, `reason: unauthenticated` | `op` reports you're not signed in | `op signin`, or set `OP_SERVICE_ACCOUNT_TOKEN` |
| `SecretStoreUnavailableError` | `storeId`, `reason: locked` | The desktop app is locked | Unlock 1Password and approve CLI access |
| `SecretStoreUnavailableError` | `storeId`, `reason: denied` | Access refused, or `op` failed in a way Lando can't classify | Allow CLI access in the desktop app and check vault permissions |
| `SecretStoreUnavailableError` | `storeId`, `reason: timeout` | No answer within two minutes | Approve the prompt, then retry |
| `SecretReferenceInvalidError` | `reference` | Bad grammar, an unknown scheme, or an uninstalled default store | Use a bare id or `scheme://seg/seg[/seg[/seg]]`; install the store that owns the scheme |
| `LandofileValidationError` | `issues[].path`, `issues[].rule: unsupported-secret-reference` | A reference outside the [supported sites](#where-references-resolve), such as a `build.args` value or a tooling `cmd` | Follow `remediation`; it names the binding for that spot. Apply `issues[].fix.edits` when the issue has them. See [Use a secret in a command or build](#use-a-secret-in-a-command-or-build) |

An unrecognized `op` failure is reported as `denied` rather than `SecretNotFoundError`, because a diagnostic Lando can't read doesn't prove the secret is absent. Errors never include `op` stdout or raw stderr.

## Write your own store

A plugin contributes stores under `contributes.secretStores`, each entry `{ id, module, schemes }`. `schemes` lists the `<scheme>://` prefixes the store owns; leave it empty for a store that only serves bare ids. The module exports `secretStores`, a map from `id` to a `SecretStore` Layer that may require `ProcessRunner`, `PathsService`, and `FileSystem`. Every scheme has exactly one owner across installed plugins; a duplicate is a bootstrap error, not a precedence contest. The store must fail only with `SecretNotFoundError`, `SecretStoreUnavailableError`, and `SecretReferenceInvalidError`, and must pass the secret-store contract suite from `@lando/sdk/test`. `@lando/secret-store-1password` under `plugins/` is a small, complete example.
