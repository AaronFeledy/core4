# Pull secrets from the environment or 1Password

Put a `${secret:...}` reference in a service `environment` value, a database `creds.password`, or a tooling `env` value and Lando resolves it from a secret store when it creates the container or runs the command. Nothing on disk, in the plan cache, or in a transcript ever holds the raw value.

```yaml
name: demo
services:
  app:
    type: "node:22"
    primary: true
    environment:
      DB_PASSWORD: '${secret:DB_PASSWORD}'
      STRIPE_KEY: '${secret:op://Dev Vault/Stripe/credential}'
```

Two stores ship in the box:

| Store | Reference | Where the value comes from |
| --- | --- | --- |
| `env` (default) | `${secret:DB_PASSWORD}` | The host env var `LANDO_SECRET_DB_PASSWORD` |
| `1password` | `${secret:op://Vault/Item/field}` | `op read --no-newline op://Vault/Item/field` through the 1Password CLI |

## Use the env store

Export the value with the `LANDO_SECRET_` prefix and start the app:

```sh
export LANDO_SECRET_DB_PASSWORD='hunter2'
lando start
```

A bare id is anything matching `[A-Za-z0-9_.-]+`. It goes to `defaultSecretStore`, which is `env` unless you change it. A missing variable fails the start with `SecretNotFoundError` naming the exact env var to set.

## Use the 1Password store

Sign in to the 1Password CLI once, then reference the item with an `op://` URI:

```sh
op signin
lando start
```

The reference is `op://<vault>/<item>/[section/]<field>`, exactly what `op read` accepts. Spaces are fine inside a segment (`op://Dev Vault/Stripe/credential`), so quote the YAML value. An optional `?attribute=<value>` or `?ssh-format=openssh` suffix passes through to `op`.

Desktop app integration works too. Lando waits up to two minutes for you to approve the biometric or unlock prompt before it gives up with `reason: timeout`.

For CI or any host without a person at the keyboard, give the CLI a service account:

```sh
export OP_SERVICE_ACCOUNT_TOKEN='ops_...'
lando start
```

`OP_CONNECT_HOST` and `OP_CONNECT_TOKEN` pass through the same way. Both are redacted wherever Lando prints environment.

Each `op://` reference is read once per Lando process and cached in memory for that process only. Nothing is written to disk and vaults are never enumerated.

## Change the default store

`defaultSecretStore` picks the store that handles bare ids. Scheme references such as `op://` ignore it and always route to the scheme's owner.

```yaml
# config.yml
defaultSecretStore: 1password
```

Or for one invocation:

```sh
LANDO_CONFIG__DEFAULT_SECRET_STORE=1password lando start
```

Naming a store that isn't installed fails with `SecretReferenceInvalidError` the first time a bare id needs it. Since the `1password` store only understands `op://` references, a bare id routed to it fails the same way; set the default to a store that owns bare ids, or keep `env`.

## Where references resolve

Lando reads a `${secret:...}` reference only where you author it, as the whole value at one of these sites:

| Site | YAML path |
| --- | --- |
| A service `environment` value | `services.<name>.environment.<KEY>` |
| A database password | `services.<name>.creds.password` or `services.<name>.creds.rootPassword` |
| A Redis password | `services.<name>.password` |
| A tooling `env` value | `tooling.<task>.env.<KEY>`, a step's `env.<KEY>`, or `toolingDefaults.env.<KEY>` |

`API_URL: 'https://${secret:HOST}/v1'` is not a reference; put the whole value in the store. The escaped spelling `$${secret:HOST}` is plain text that reaches the container as `${secret:HOST}`.

Text that arrives any other way is data, not a request to a store: results of `load()`, `import()`, and `{{ ... }}` expressions, values from `env_file:`, global `appEnv` defaults, and environment that a service type or app feature generates during planning. Lando parses your files once and remembers which values you authored as references. A produced string that happens to read `${secret:KEY}` reaches the container as those exact bytes.

### Credentials carry the reference with them

A database password you author as a reference stays a reference everywhere the service type projects it. Postgres, for example, writes the same value into `POSTGRES_PASSWORD`, into `LANDO_DB_PASSWORD`, into the environment of its `psql` task, and into `lando db:*` operations. None of those copies is a literal; each resolves from the store when the container is created or the command runs.

```yaml
name: bound-creds
services:
  web:
    type: "node:22"
    primary: true
    environment:
      DATABASE_URL: "postgresql://{{ services.db.creds.user }}:{{ url.encodeComponent(services.db.creds.password) }}@db:{{ services.db.port }}/{{ services.db.creds.database }}"
  db:
    type: "postgres:17"
    creds:
      user: lando
      database: bound-creds
      password: '${secret:DB_PASSWORD}'
```

`{{ services.db.creds.password }}` in another service keeps the binding too. You can copy it whole, concatenate it with text, or wrap it in `url.encodeComponent()`, which percent-encodes the resolved bytes for a URL. Any other helper applied to a bound value fails planning with `ConfigExpressionError` at that site, because Lando would need the secret to compute the result. See [Plan-time service credentials](../landofile/expressions.mdx#plan-time-service-credentials).

Lando resolves the database connection once, in the service type: user, database, password, and the planned port. Clients, `lando info`, and `lando db:*` read those facts. `lando info` prints the user and database and redacts the password without reading the store, so you can lint, plan, and inspect this app with `LANDO_SECRET_DB_PASSWORD` unset; only `lando start` and the commands that run against the database need it. If you also author a native variable such as `POSTGRES_PASSWORD` and it disagrees with `creds.password`, planning fails and names both paths, never the values.

### Precedence is the ordinary kind

A reference is a value like any other. A higher Landofile layer replaces or removes the whole value with the normal merge rules, and a plugin that writes the same key during planning replaces the whole value too, reference or not. Keys a database type owns, such as `POSTGRES_PASSWORD`, are different: an authored value there must agree with the service's connection facts or planning fails at both paths. Changing a reference to `$${secret:HOST}` turns that key into literal text and drops its store lookup. There is no special pass that puts references back after planning.

### When Lando reads the store

- `lando start`, `lando rebuild`, and the global app resolve every reference once per operation, before any container is created or replaced, and fail the whole operation on the first store error. Nothing starts half-configured. Each reference is read once in that operation, even when several keys share it.
- Tooling and `lando db:*` commands that need a bound value resolve it when the command runs. Each operation has its own lookup memo; a later operation calls the store again, subject to that store's documented cache policy. Lando does not detect or reconcile password changes in a running database. Recreating a container can change its environment, but does not change credentials already initialized in its persistent database.
- `lando restart`, `lando stop`, `lando info`, and `lando logs` work from the plan and the running containers and never read a store. Restarting an existing container with the store unavailable works.
- `lando app:config` and the plan cache keep the reference, not the value. `lando app:config --format=json` prints a key that holds one as a typed descriptor, `{"_tag":"SecretRef","reference":"DB_PASSWORD"}`, so you can see which store id or `op://` path it points at. The descriptor names a secret; it isn't one, so there's nothing in it to mask. `[redacted]` is what Lando prints in place of a resolved value, as `lando info` does for a database password. Inspecting config never touches a store.
- Build steps see the reference unresolved and the build transcript is redacted. Don't interpolate secrets into build arguments.
- `lando shell` in host mode resolves `${secret:...}` inside a line only when that line runs, with the same grammar and the same stores.

Plans built by this Lando carry a marker for this value model. Containers an older Lando recorded are still observable: `lando info`, `lando stop`, and `lando destroy` read that older plan as it is. Creating or recreating a container from such a plan is refused with `PlanReplanRequiredError` instead of guessing which strings were references. `lando start` plans the app fresh before it creates anything, so the fix is to run it with the current Lando; an embedding host gets the error back with `remediation` set.

Every resolved value is registered with the redactor before any event, result, transcript, or failure can carry it. `lando info`, logs, and error envelopes print `[redacted]` in its place. That includes `lando setup` failure evidence and `lando doctor` repair diagnostics, which mask values registered during that same command. Provider errors handed back to a library host mask them in `message` and `details` too. You don't need any extra settings.

Lando also masks URL-encoded, JSON-escaped, and base64 forms of known secret values, including standard base64 and base64url with or without padding, in both text and streamed output.

Any command that runs in or reads from a service container masks its secret values as `[redacted]`, without accessing the secret store. This still works for containers created before you edited the Landofile or upgraded Lando. Host-only tooling and provider-free inspection do not initialize a provider for redaction. This covers surviving containers, not historical values from containers that have been removed. If Lando cannot read those values, the command fails before emitting app output. Lando never saves a decrypted secret cache.

A resolved value stays masked even when it matches one of Lando's published default credentials, `lando` or `landolando`. Plain `environment` values are masked only by key name, and those two defaults print as-is there because they're public.

## Errors

All three are tagged and carry `remediation`, so `--format=json` output tells you what to do without parsing prose.

| Tag | Fields | When | Fix |
| --- | --- | --- | --- |
| `SecretNotFoundError` | `secret` | The store answered and the secret isn't there | Set `LANDO_SECRET_<id>`, or check the vault, item, section, and field in the `op://` reference |
| `SecretStoreUnavailableError` | `storeId`, `reason: cli-missing` | `op` is not on `PATH` | Install the 1Password CLI |
| `SecretStoreUnavailableError` | `storeId`, `reason: unauthenticated` | `op` reports you're not signed in | `op signin`, or set `OP_SERVICE_ACCOUNT_TOKEN` |
| `SecretStoreUnavailableError` | `storeId`, `reason: locked` | The desktop app is locked | Unlock 1Password and approve CLI access |
| `SecretStoreUnavailableError` | `storeId`, `reason: denied` | Access refused, or `op` failed in a way Lando can't classify | Allow CLI access in the desktop app and check vault permissions |
| `SecretStoreUnavailableError` | `storeId`, `reason: timeout` | No answer within two minutes | Approve the prompt, then retry |
| `SecretReferenceInvalidError` | `reference` | Bad grammar, an unknown scheme, or an uninstalled default store | Use a bare id or `scheme://seg/seg[/seg[/seg]]`; install the store that owns the scheme |

An unrecognized `op` failure is reported as `denied` rather than `SecretNotFoundError`, because a diagnostic Lando can't read doesn't prove the secret is absent. Errors never include `op` stdout or raw stderr.

## Write your own store

A plugin contributes stores under `contributes.secretStores`, each entry `{ id, module, schemes }`. `schemes` lists the `<scheme>://` prefixes the store owns; leave it empty for a store that only serves bare ids. The module exports `secretStores`, a map from `id` to a `SecretStore` Layer that may require `ProcessRunner`, `PathsService`, and `FileSystem`. Every scheme has exactly one owner across installed plugins; a duplicate is a bootstrap error, not a precedence contest. The store must fail only with the three errors above and must pass the secret-store contract suite from `@lando/sdk/test`. `@lando/secret-store-1password` under `plugins/` is a small, complete example.
