# Work offline

Lando reuses cached state wherever it can, so a lot of everyday work keeps running without network access.

Before going offline, start the app while connected so Lando can pull images and build containers. If the Landofile uses remote includes, run `lando app:includes:update` from the app directory while connected to populate its lockfile and cache. Later, `lando app:includes:update --no-network --format=json` checks those cached includes without fetching them.

## What works offline

Starting an app you already ran before works offline, as long as its images were already pulled and its containers already built. `lando start` and `lando restart` reuse images already in your provider instead of pulling them again, including the images for global services like the proxy. Scratch apps, `lando global:start`, and `lando global:restart` work the same way. Command routing reads the on-disk command cache under the user cache root without network access, and plugin commands resolve from the plugins already installed on disk. When that index is missing or out of date, the host CLI rebuilds it before the command runs; that rebuild plans the Landofile the same way `lando app:cache:refresh` does, so remote includes must already be in the local cache. Otherwise the command fails with the include error that names the include.

The bundled SSH sidecar installs `openssh-client` and `socat` when the global app builds its image, not when the container starts. After that first online build, later starts reuse the image and cached build layers without network access. SSH agent forwarding can come back offline after a poweroff or reboot.

`lando rebuild` and `lando global:rebuild` re-pull the images your services reference so updated tags take effect, then rerun the build. If the registry can't be reached, Lando warns and rebuilds from the local copies. With `--format=json`, that warning is in the result's `warnings` array with code `LANDO_ARTIFACT_REFRESH_FAILED`. Only an image that was never pulled needs network access.

Stopping, inspecting, and removing an app you already started never needs the network. `lando stop`, `lando logs`, `lando info`, and `lando destroy` talk to the runtime that is already running and do not start it, rewrite its configuration, or download anything, so an interrupted upgrade or a missing download cannot block you from reading logs or tearing an app down.

On Linux with the default `lando` provider, the init process that Lando runs in front of each service command ships inside the runtime payload. A runtime installed before that helper was part of the payload fetches the pinned helper once, during `lando setup` or the first `lando start` of a service that uses init, and reuses the verified copy offline from then on. Services with `init: false` never need it.

Runtime bundle and tool downloads first check their local caches. Remote includes, recipe sources, and plugin packages share one source store under your user cache root at `sources/`, keyed by git commit or archive SHA-256. A git recipe pinned to a full commit SHA or a tarball recipe whose `--checksum` matches a stored archive is reused from there without touching the network. An npm recipe or plugin still asks the registry for package metadata, but skips the tarball download when the stored package matches that registry's published version and integrity. A git recipe on a branch, tag, or default branch checks the remote commit on every init with `git ls-remote` and reuses its stored tree when available. When a fetch is needed and fails for a reason other than authentication, `lando init` warns and uses the cached commit, for the `--source=git` recipe and for any remote git `extends:` parent it resolves. When a source download is actually required and the network is unavailable, the failure surfaces as the consumer's error instead of hanging or silently retrying: `RecipeSourceError` for a recipe, `LandofileIncludeError` for an include, `PluginPackageOperationError` for a plugin. Runtime bundle and tool downloads report `DownloadOfflineError`. Entries stay in the store until you remove them with [`lando sources:gc --prune`](../cli/sources-gc.mdx).

Once a remote include has a lockfile entry and a source-store entry, loading the app reads that entry instead of the network. `lando start`, `lando app:config`, tooling, `lando app:includes:verify`, and `lando app:includes:update --no-network` all work offline from then on. See [Pin a remote include](../landofile/includes-and-lockfile.mdx#pin-a-remote-include).

## Honest limits

A successful config or cache check does not prove that every build step can run offline. Build steps that download packages need network access when their cached layers are missing or their inputs change.

An image that was never pulled has nothing in the local cache, so the first `lando start` for that image still needs network access. A remote include can only be resolved offline once it already has a lockfile entry and a source-store entry from a prior online run. Changing an include's `version:` also needs network access, because the next load fetches the new version. There is no global `--offline` flag. Offline behavior is scoped per command, such as `--no-network` on `app:includes:update`.

Bun controls package resolution and cache use for `lando bun` and `lando x`.
When one of them fails offline you get Bun's exit code and Bun's message, not
an offline error from Lando. Pass the Bun flag for the behavior you want and
read Bun's `stderr` to tell a cache miss from a broken package. Under
`--format=json` that output sits in the envelope, described in
[Script Lando with JSON](../scripting-with-json.mdx#capture-bun-backed-commands).

The fixture above has no remote includes, so `--no-network` succeeds trivially. A remote include with no prior lockfile or source-store entry fails with `LandofileIncludeError` instead of falling back to a network fetch. The error names the missing source and says `--no-network` blocked the fetch.

Run the same command once with network access (`lando app:includes:update`) to populate the lockfile and source store. `--no-network` works offline from that point on.
