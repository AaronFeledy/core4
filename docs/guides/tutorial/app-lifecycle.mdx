# Start, inspect, and tear down an app

Start a Node and Postgres environment, inspect it, run a command inside Node, then stop or remove it. First [install Lando](../install/path-and-setup.mdx) and complete `lando setup` for your platform. Create a separate app directory and save the following as `.lando.yml` in it:

```yaml
name: app-lifecycle-demo
services:
  app:
    type: "node:22"
    primary: true
  db:
    type: postgres
```

The primary service is the default target whenever a command omits
`--service`.

## Run the everyday loop

From the directory containing `.lando.yml`, run `lando start`, then `lando info`. Check that both `app` and `db` appear before continuing. The Node service supplies a development environment; this example does not launch a web application.

Keep the app running for the inspection and shell commands below. Use `lando stop` when you finish working, or follow [Tear down](#tear-down) when you want to remove its containers and networks.

## Inspect a running app

These commands are read-only. Run them as often as you like:

```sh
# Show every service, its connection details, and the app URLs
lando info

# The same data as machine-readable JSON
lando info --format=json

# Show a bounded snapshot of the combined logs from every service
lando logs

# Follow just the primary app service's logs in real time
lando logs --service app --follow

# Print the fully-resolved Landofile (includes merged, templates rendered)
lando app:config --format=json
```

## Work inside the app

Run one-off commands in a service, or open a shell:

```sh
# Run a command in a named service
lando exec app -- node --version

# Omit the service to target the primary service
lando exec -- node --version

# Open an interactive shell in the primary service
lando ssh

# Or in a specific service
lando ssh --service db
```

Tooling aliases declared under `tooling:` run inside their target service.
`lando npm install`, `lando psql`, and so on.

## Start one service

If you only need Postgres, start `db` from the app directory. Repeat `-s` (or `--service`) to name more than one service. Lando also starts their prerequisites and sidecars.

```sh

```

On a fresh app, `result.servicesStarted` lists `db`, and `result.servicesStayedDown` lists `app`. In `lando info`, `app` still appears with status `stopped`. The last command brings up the rest of the app. Start `db` alone again and the running `app` stays running, so there is no `servicesStayedDown` field. ## Stop one service

Stop `db` while `app` keeps running. Repeat `-s` (or `--service`) to name more than one service. Lando stops only those containers and keeps them; the rest keep running, and named volumes and the applied state stay.

```sh
lando start
lando stop -s db --format=json
lando info --format=json
lando start -s app --format=json
lando start
```

`result.servicesStopped` names `db`, and `result.servicesKeptRunning` names `app`. `lando info` reports `db` as `stopped`, and the later `start -s app` names `db` in `servicesStayedDown`. Running `lando stop -s db` again reports an empty `servicesStopped`. The last command brings `db` back without restarting `app`. See [Stop one service in the CLI guide](../cli/everyday-commands.mdx#stop-one-service) for what Lando leaves in place.

## Restart and rebuild

`lando rebuild` and `lando destroy` ask for confirmation first. Pass `-y` to skip the prompt in scripts.

`lando stop` stops the app's containers and keeps them. The next `lando start` starts each one again in place, so files written inside a container, its anonymous volumes, and its `build.app` results are still there, and those steps report as cached. `lando start` also applies Landofile changes such as command, environment, image, and mounts: it replaces only a container whose settings changed, prints the reason, and names any anonymous volume that went with it. Bare `restart` is the same `stop` then `start` in one step, with the same replacement notices. Reach for `rebuild` when you need a forced image pull, fresh containers, or a forced rerun of build steps. `start` does not take `-y`.

Because a stopped container stays in place, a service with a Compose `restart: always` policy can start again on its own when the container runtime or your machine restarts. Use `restart: unless-stopped` to keep a stopped app stopped.

`lando restart --service web` (or `-s`, repeatable) restarts only the services you name and brings each one back the way `lando start` would. An unchanged container restarts in place; a container whose settings changed, or that is missing, is replaced or created, and Lando prints why, naming any anonymous volume that went with it. Route changes on the named services publish with the restart. It refuses only when the app was never started or was destroyed. See [Restart or rebuild one service](../cli/everyday-commands.mdx#restart-or-rebuild-one-service) for the full rules and the `--format=json` fields.

`lando stop` withdraws the app's published hostnames when it stops the containers, and the next `lando start` publishes them again. `lando restart` and `lando rebuild` keep them published, even when the start that follows fails. A selected `restart -s` or `rebuild -s` publishes route changes on the services it applies and leaves the other running services' published routes untouched. `lando stop -s db` stops only `db`; `app` keeps running, named volumes stay, and the next `lando start` brings `db` back without restarting `app`.

```sh
# Stop the app's containers and keep them, their data, and named volumes
lando stop

# Bring the app up and apply create-config changes. Named volumes stay
lando start

# Stop then start in one step, keeping unchanged containers
lando restart

# Force a pull and build refresh, then recreate containers
lando rebuild
```

To change one service without touching the rest, edit it and restart just that service. Here the `app` service gets a new environment variable, so its container is replaced while `db` keeps running:

```sh
# Add an environment variable to the app service
lando app:config:set services.app.environment.GREETING hello

# Replace only the app container and print why
lando restart -s app

# Read the new value inside the replaced container
lando exec app -- printenv GREETING
```

## Remove a service

Delete the service from `.lando.yml`, or let Lando edit the file for you with `lando app:config:unset`, then run `lando start`:

```sh
# Remove the db service from the Landofile
lando app:config:unset services.db

# Remove the db container and keep the rest of the app running
lando start
```

`lando start` removes the container of every service the Landofile no longer defines, prints a notice naming those services, and stops publishing their URLs. `lando restart` and `lando rebuild` remove them too and print the same notice. With `--format=json`, all three commands list the removed services under `result.servicesRemoved`: the field is present and empty when nothing was removed, and a selected `-s` operation that removed nothing omits it. Run `lando info` and check that the removed service no longer appears.

The service's named volumes stay, so if you add the service back later with the same storage, it starts with its old data. To delete that data, use the flags in [Keep data across stop, restart, and destroy](#keep-data-across-stop-restart-and-destroy).

If the removed service was the last one that used `lando` from inside a container, SSH agent forwarding, or GPG agent forwarding, the same command also stops the background worker that served it.

Lando removes a container only when its labels prove it belongs to this app. If a container for a removed service carries labels that say otherwise, such as another provider's, `lando start` stops before removing anything and names that container. Inspect it with your container runtime and remove it yourself if it is a leftover, then run `lando start` again.

## Read what stop reports

`lando stop` sends each container its stop signal, waits out the container's stop grace period, and then kills whatever is still running. Once a container has stopped, Lando asks the runtime how it ended and repeats the answer beside the service name in the `stopped:` line, for example `app (exit 143)`. `lando destroy` does the same before it removes each container and prints the answers in its `destroyed:` line. Catalog services such as `node` and `postgres` run under a small init process by default that forwards the stop signal to your command, so a server that handles SIGTERM gets the chance to finish in-flight work; see [Stop cleanly](../services/node.mdx#stop-cleanly) for how commands, wrappers, and `init: false` affect that.

| Reported | What the runtime said |
| --- | --- |
| `exit 0` | The process exited with status 0. |
| `exit 143` | Conventionally 128 + 15 for SIGTERM, but an application can also return 143 itself. The code alone does not prove how it ended. |
| `exit 137` | Conventionally 128 + 9 for SIGKILL, but an application can also return 137 itself. The code alone cannot distinguish an expired grace period, an OOM kill, an external signal, or an application-selected status. |
| `exit 137, OOMKilled` | The runtime explicitly reported an out-of-memory kill. Lando also prints a warning on stderr. |
| `container absent`, `state unavailable`, `not exited`, `inspect failed` | No terminal state was available: the container was already gone, its state could not be read, it was not in an exited state, or inspection failed. Only `inspect failed` prints a warning. The stop or removal still proceeds. |

These are facts the runtime reported, not a verdict. Exit `0` does not prove your application flushed its data, and exit `137` alone does not mean Lando forced the stop. A provider that does not observe shutdown lists bare service names instead; the result is the same `stopped` or `destroyed` outcome either way. If you need proof that your own shutdown handler ran, have the handler record its completion somewhere you can check, such as a log line or a file in a named volume.

Stop an app that is already stopped and Lando reports `unchanged: app-lifecycle-demo - already stopped: app, db`. With `--format=json`, `result.outcome` is `unchanged` and `result.containers` lists what happened to each container: `action` is `stopped`, `already-stopped`, or `absent` when the service had no container, with the service name and the `containerId` it acted on.

A stopped container runs nothing, so `lando exec`, `lando ssh`, tooling commands, and database commands fail with `Service app is not running.` and tell you to run `lando start`. `lando info` still lists each stopped service with status `stopped`, and `lando logs` still shows what the containers printed before they stopped.

`lando stop --format=json` and `lando destroy -y --format=json` carry the same facts under `result.shutdownObservations`. Each entry names the `appId`, `providerId`, and `service`, the exact `containerId` when it was known, and a `status`: `exited` with an optional integer `exitCode`, or `unknown` with a `reason` of `container-absent`, `state-unavailable`, `not-exited`, or `inspect-failed`. A missing `exitCode` means the runtime did not report one; it is never read as `0`. `oomKilled` appears only when the runtime reported it. The field is omitted entirely when the provider supplied no observations.

## Keep data across stop, restart, and destroy

Database data stores, persistent homes, excluded directories such as `node_modules`, and caches use named volumes. The app lifecycle commands retain that storage unless you request its removal with `--volumes`, `--purge`, or `--purge-caches`. Bind mounts keep their files on the host instead.

Images Lando built stay around too. `lando destroy` keeps the newest one for each service for up to seven days, so the next `lando start` reuses it without building. `--purge-caches` removes those images right away.

An image that declares a `VOLUME` path you never mapped gets an anonymous volume instead. The runtime creates it with the container, and it lasts as long as the container does. `lando stop` and `lando restart` keep the container, so the volume and its data stay. Lando asks the runtime to drop the volume whenever it removes the container: `lando destroy`, `lando rebuild`, removing the service from the Landofile, and a `lando start` or `lando restart` that replaces a changed container. The runtime keeps one that another live container still uses. `lando start` and `lando restart` print the reason for a replacement and name any anonymous volume the old container took with it. A failed start retains established resources for inspection rather than rolling them back.

To keep data at such a path, name it. A bare container path under `volumes:` becomes a named store Lando owns:

```yaml
services:
  search:
    type: compose
    image: getmeili/meilisearch:v1.12
    volumes:
      - /meili_data
```

`lando app:config:lint` confirms the Landofile is valid, and from then on only `--volumes` or `--purge` removes that store. Declaring the store does not migrate existing data: the next `lando start` recreates the container on the named store, and whatever the anonymous volume held leaves with the old container. Export anything you need first, for example with [Import and export app databases](../tooling/db-import-export.mdx). Lando only drops the anonymous volumes of the container it is removing; it never prunes unlabeled volumes left behind by anything else.

This app gives `app` a `build.app` step that counts its runs in `build-runs.log`, and adds a `cache` service whose image declares a `VOLUME`. Write a file inside each container, then see what each command keeps. After `lando stop` and `lando start`, and after `lando restart`, `lando start` reports `app` as `started` in place, the file is still there, and the step has run once. `lando rebuild` and `lando destroy` give `app` a new container: the file is gone and the step runs again.

```yaml
name: app-lifecycle-keep
services:
  app:
    type: "node:22"
    primary: true
    build:
      app:
        - echo run >> /app/build-runs.log
  cache:
    type: compose
    image: docker.io/library/redis:7-alpine
    appMount: false
```

### Check what a service mounts

`lando info --format=json` lists each service's mounts under `services[].mounts` and its application source mount under `services[].appMount`. Ordinary `info` builds these rows from the one container inspection it already performs per service, not from image or volume queries, so it reports evidence rather than guesses:

| Field | Values | Meaning |
| --- | --- | --- |
| `type` | `bind`, `volume`, `tmpfs`, `unknown` | Mount kind as the runtime reports it. |
| `target`, `source`, `readOnly` | path, host path or volume name, boolean | Where it mounts, what backs it, and whether it is read-only. `source` and `readOnly` appear only when known. |
| `origin` | `planned`, `runtime` | Whether the mount matches your resolved plan or only appeared on the running container. |
| `observation` | `present`, `missing`, `unknown` | Whether the container's mount table confirmed it, the container is absent, or evidence was unavailable. |
| `lifetime` | `retained`, `container`, `unknown` | Bind mounts and declared stores are `retained`; `tmpfs` is `container`; a runtime-only volume is `unknown`. |
| `provenance` | `authored`, `service`, `derived` | For planned mounts: you declared it in the Landofile, the service type added it, or Lando derived it (an excluded directory's volume, a nested include, Git metadata, or the service home). |

The human view labels each retained mount by its role, so a persisted home reads `/home/node (home)` beside the stores you declared, and the JSON carries the same fact as `services[].home` with a `state` of `persisted`, `authored`, `disabled`, or `unknown`. A service whose home Lando can't place gets a `home` row in the human view that says why and names the `home.path` key to set. See [Keep a service home across rebuilds](../services/home-and-host.mdx#check-what-lando-keeps).

A runtime-only volume with `lifetime: unknown` is unverified, not proven anonymous. Lando does not infer lifetime from a volume name, so decide from the image: if the path is an image `VOLUME` you have not declared, declare it as above. The agent-forwarding and host-proxy mounts Lando adds for its own SSH, GPG, and `lando` integration are not user data and need no declaration.

## Tear down

`destroy` removes the app's containers and networks. Named volumes stay unless you pass `--volumes` or `--purge`. The `-y` flag is required in non-interactive contexts:

```sh
lando destroy -y
```

Snapshots survive plain `destroy` and `--volumes`. **`lando destroy --purge -y` also deletes this folder's catalogued snapshots**, including native data through the provider that recorded each snapshot. It works when an earlier destroy left only ownership inventory. Snapshots belong to the source volume's canonical owner root, so other app folders keep theirs even if they share this app's name. See [Import and export app databases](../tooling/db-import-export.mdx) before moving a database between apps or providers.

If a selected volume is still in use, the removal error names the containers holding it when the runtime can report them. Holder lookup is best effort; unavailable details do not make the removal succeed.

If the holder is a database import, export, or snapshot that is still running, let it finish, then run the same `destroy` again. You don't need to remove Lando's data helper containers yourself. Lando removes each helper when its command ends, and tries to remove it right away if creating it fails. If a helper is still left, for example because a `lando` command was killed, Lando removes it once it confirms the process that started it has exited: during a later database import, snapshot, or restore, or when the helper blocks `destroy --volumes`. Helpers started from another machine or container that shares the engine are left for that `lando` to clean up. If Lando couldn't record which process started a helper, it waits until the helper has been stopped for 10 minutes instead.

Changing providers doesn't move an applied app. If `lando start` fails with `AppPlacementError`, retire the old copy explicitly:

```sh
lando destroy --provider=lando --yes
```

Only the selected provider's state and resources are touched. See [Recover an app left on another provider](../setup/provider-selection.mdx#recover-an-app-left-on-another-provider).

`stop` and `destroy` use the provider's last applied plan when the Landofile is
missing or invalid. That means you can still tear down an app after deleting its
directory or breaking its config. Lando verifies the stored app root, owner, and
provider before it touches anything.

If that saved state is damaged or unreadable, `start`, `stop`, `restart`, and
`destroy` refuse to change anything and name the state file. Restore the file
from a backup if you have one. Otherwise move it aside and run `lando destroy`
again: Lando then finds the app's containers and volumes by their ownership
labels. On Windows with accelerated file sync, changes that had not synced
back yet can be lost that way.

If a newer Lando wrote that state in a format this binary cannot read, those
same commands refuse with a version error that names the file and the stored
and supported format versions. Run that newer Lando, or upgrade this one, and
leave the file in place. Moving it aside or destroying it throws away ownership
state the newer Lando still needs.

`info` and `logs` keep working either way. When the saved state is damaged or
newer-format, `info --format=json` adds an optional `appliedStateIssue` with
the reason, path, message, and remediation (plus format versions for a
newer-format record). Readable and missing state omit that field. If you use
file sync, its applied settings are unknown until Lando can read the record.

Teardown looks at what is actually running before it reads your config. An app
that was never started reports `unchanged` and exits 0, even when its Landofile
does not validate. If a plain `destroy` kept your named data volumes, a later
`lando destroy -y --volumes` still removes them and tells you what it removed.

After a plain `destroy`, the app behaves like one that never started, apart from
the named volumes it kept. `lando info` lists each service as `stopped` and still
shows those volumes under `services[].mounts` with `lifetime: retained`.
`lando logs` succeeds with no lines, and `lando stop -s <service>` reports
`unchanged`.

The next commands affect the whole host, not just this tutorial app. Poweroff also removes scratch apps and their disposable data unless you pass `--keep-scratch`. Run it only when you mean to stop all targeted apps:

```sh
# List every Lando app known on this host and its status
lando apps:list

# Stop every running Lando app and the shared services at once
lando apps:poweroff
```
