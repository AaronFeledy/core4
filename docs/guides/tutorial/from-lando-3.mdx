# Run Lando 4 next to Lando 3

Lando 4 installs as `lando` (`lando.exe` on Windows). Verify the version before running setup:

```sh
lando --version
```

If you keep Lando 3 installed, use its saved executable path explicitly. Every `lando` command on this page means Lando 4.

The installer refuses to replace an executable without a matching Lando 4 install record. Back up an existing Lando 3 executable before a manual install, and keep its apps and data until you choose to convert them. Follow [Put lando on PATH and run setup](../install/path-and-setup.mdx) and check which executable your shell resolves.

## Put lando on PATH

Download the platform-qualified binary from a `v4.0.0-dev.N` prerelease. Release assets still start with `lando-` (`lando-linux-x64`, `lando-darwin-arm64`, `lando-windows-x64.exe`). The asset name does not pick the installed name. Save the file as `lando` (`lando.exe` on Windows) and put it on PATH. These commands preserve an existing executable in a unique backup before installing:

```sh
(
  set -eu
  chmod +x lando-linux-x64
  mkdir -p "$HOME/.local/bin"
  if [ -e "$HOME/.local/bin/lando" ] || [ -L "$HOME/.local/bin/lando" ]; then
    landoBackup=$(mktemp "$HOME/.local/bin/lando.bak.XXXXXX")
    mv "$HOME/.local/bin/lando" "$landoBackup"
  fi
  mv -n lando-linux-x64 "$HOME/.local/bin/lando"
  test ! -e lando-linux-x64
) &&
export PATH="$HOME/.local/bin:$PATH" &&
command -v lando &&
lando --version
```

Then run setup once. The default provider is `lando` (managed Podman), so Lando 4 does not borrow the Docker daemon Lando 3 uses:

```sh
lando setup
```

If default setup fails and you have working system Docker, run `lando setup --provider=docker`. `LANDO_PROVIDER=docker` does the same for one shell and does not persist.

## lando shellenv

`lando shellenv` prints the profile snippet that puts the Lando 4 install directory on PATH. It exports `LANDO_USER_DATA_ROOT` and uses the verified install record for installer-managed copies. Without a record, a compiled manual install uses its current executable directory. Applying the snippet can change which `lando` your shell finds first, so keep using an explicit executable path for Lando 3.

```sh
lando shellenv
lando shellenv --shell=powershell
```

Append the output to `~/.bashrc`, `~/.zshrc`, or your PowerShell profile, then open a new shell.

## Update lando

`lando update` replaces the binary Lando 4 installed, and nothing else.

```sh
lando update --dry-run
lando update
```

Both read the signed release manifest from the update server before they look at your disk, so neither one runs offline.

Lando 4 writes an install record when it installs itself. Update reads that record to find the executable, confirms the file on disk still matches the record byte for byte, and only then stages, verifies, and swaps the new binary. Only a recorded executable with the Lando command name is a target; sharing the name does not prove ownership. Earlier prereleases recorded `lando4` or `lando4.exe`, and those recorded copies remain manageable.

If the record is missing, points somewhere else, or no longer matches the file, update refuses and tells you to rerun the installer. It does not guess, and it never adopts a binary it did not install. Installed Lando 4 some other way, such as through a package manager? Update it the same way you installed it.

Windows cannot replace a running executable, so Lando 4 stages the new binary, exits, and lets a helper finish the swap. The helper re-reads the install record before it moves anything, moves only the recorded executable, and puts the original back if the swap fails. You see the result on your next `lando` command.

After a successful swap Lando 4 rewrites the record to describe the new binary, so the next update and any later uninstall still recognize it. The previous binary stays beside it as `<recorded-executable>.bak` and is yours to delete.

## Uninstall lando

```sh
lando uninstall --dry-run
lando uninstall --yes
```

Uninstall removes what the install record lists and leaves everything else alone. A separately installed Lando 3 executable, `~/.lando`, and your Lando 3 containers stay where they are. Run the dry run first: it prints every step and what it will do before anything is removed.

A binary Lando 4 did not install is never removed, even if it sits in Lando 4's own `bin` directory. If the recorded binary changed underneath, uninstall reports it and leaves the file for you.

Add `--purge` to also remove Lando 4's data, cache, and config roots, and to strip the `# >>> LANDO4 shellenv >>>` block from the profiles Lando 4 wrote to. That deletes Lando 4 app state, so check the dry run first. A Lando 3 `# >>> LANDO shellenv >>>` block is a foreign PATH entry and survives, as does every line you added yourself.

Uninstall is safe to run twice. The second run finds nothing left and removes nothing.

## Check for Lando 3 leftovers

```sh
lando doctor
```

Doctor adds two read-only Lando 3 checks. Neither changes anything.

- `lando3-leftovers` runs when you are inside an app on the `docker` or `podman` provider. It looks for volumes named after the app's Lando 3 project (`<project>_...`) and containers labeled with the app's root. A hit is a warning that names what it found. Back up or confirm any data you need, then invoke the saved Lando 3 executable with `destroy` to remove those resources. Outside an app, and on the default `lando` provider where Lando 3 never ran, the check says it skipped. Lando 3's old proxy is not this check. If that proxy still holds port 80 or 443, the existing preferred-port check names it.
- `lando3-shadow` looks on `PATH` for a `lando` executable other than the running `lando`. It never runs or opens that file, and it does not say what that file is. A different resolved path is information: check which version your shell finds, and use the saved Lando 3 executable path for its commands. If the running path cannot be resolved, the check stays unverified instead of calling the other file a shadow.

Add `--format=json` when a script or an agent reads the result. Each check reports a `runtimeStatus` such as `skipped`, `none-found`, `lando3-resources-found`, or `potential-shadow`.

## Convert an app when you are ready

Keep running the app with your saved Lando 3 executable until you choose to move it. Lando 4 never reads a Lando 3 Landofile on the fly: run `lando start` in that directory and it stops with `Lando3LandofileDetected` and the exact command to run instead.

Conversion is explicit, and preview comes first:

```sh
lando app:config:translate --from lando3
lando app:config:translate --from lando3 --write
lando app:config:lint
lando start
```

The preview prints every Lando 4 layer the Lando 3 files would become, with a diagnostic for each key it generated, rewrote, dropped, or could not carry. Nothing is written until `--write`, and `--write` refuses while any `unsupported` diagnostic stands. The full walkthrough, layer by layer, is [Convert a Lando 3 app to Lando 4](../landofile/convert-from-lando-3.mdx).

`--write` keeps an immutable backup beside every file it replaces or removes, named `<file>.bak.<sha256>` after the original bytes. Going back to Lando 3 is copying each backup over its original name (and deleting a `.lando.dist.yml` the conversion created). Lando 4 does not adopt Lando 3 containers or volumes. They stay owned by Lando 3, so its saved executable can pick the app up where it left it.

## Or start fresh on Lando 4

Would rather not carry the old config? Leave the Lando 3 `.lando.yml` where it is for Lando 3 and give Lando 4 its own app in another directory:

```sh
lando init --recipe lamp --yes
lando start
```

Or write a [Landofile](../landofile/your-landofile.mdx) by hand. Supported recipes today: `lamp`, `lemp`, `wordpress`, `drupal`, and `drupal-cms`. Then use the [everyday CLI loop](../cli/everyday-commands.mdx) with `lando` in front.

## What each lando command touches

| Command | Changes | Leaves alone |
| --- | --- | --- |
| `lando shellenv` | Nothing. It prints a profile snippet | Your profiles and `PATH` until you paste it |
| `lando update` | The recorded Lando 4 binary, the install record, and a backup beside it | Any executable the record doesn't match |
| `lando uninstall --yes` | Entries in the install record | Unrecorded executables, `~/.lando`, and Lando 3 containers and volumes |
| `lando uninstall --purge --yes` | The above, Lando 4's data, cache, and config roots, and the `LANDO4` shellenv block | The Lando 3 `LANDO` shellenv block and every line you wrote |
| `lando doctor` | Nothing. The shadow check never runs or opens another executable | Everything |
| `lando app:config:translate --from lando3 --write` | Landofile layers in that app, each replaced file kept as `<file>.bak.<sha256>` | Lando 3 containers, volumes, and `~/.lando` |

## Gotchas

- Two apps with the same name, one on each version, do not know about each other. Stop the Lando 3 one before starting the Lando 4 one if they share a port.
- `lando poweroff` powers off Lando 4. Use your saved Lando 3 executable path to power off its apps.
- Alpha install details and where to file bugs: [Alpha install and bug reports](../../alpha-install-and-bug-reports.md).
