# Run Lando 4 next to Lando 3

Lando 4 installs as `lando4`. Lando 3 stays `lando`. Keep both:

```sh
lando --version
lando4 --version
```

Installing Lando 4 never renames, replaces, shims, or removes `lando`, and it never touches `~/.lando`. Your Lando 3 apps keep running exactly as they did. Every Lando 4 command on this page is spelled `lando4`. When this page says `lando`, it means Lando 3 and says so.

## Put lando4 on PATH

Download the platform-qualified binary from a `v4.0.0-dev.N` prerelease. Release assets still start with `lando-` (`lando-linux-x64`, `lando-darwin-arm64`, `lando-windows-x64.exe`). The asset name does not pick the installed name. Save the file as `lando4` (`lando4.exe` on Windows) and put it somewhere on PATH:

```sh
chmod +x lando-linux-x64
mv lando-linux-x64 ~/.local/bin/lando4
lando4 --version
```

Then run setup once. The default provider is `lando` (managed Podman), so Lando 4 does not borrow the Docker daemon Lando 3 uses:

```sh
lando4 setup
```

If default setup fails and you have working system Docker, run `lando4 setup --provider=docker`. `LANDO_PROVIDER=docker` does the same for one shell and does not persist.

## lando4 shellenv

`lando4 shellenv` prints the profile snippet that puts the Lando 4 install directory on PATH. It exports `LANDO_USER_DATA_ROOT` and prepends the directory Lando 4 recorded when it installed itself, so the snippet stays correct even when you installed outside the default `bin` directory. Nothing else on PATH moves, so wherever Lando 3's `lando` lives keeps working, and appending the block twice to a profile does not add the directory twice.

```sh
lando4 shellenv
lando4 shellenv --shell=powershell
```

Append the output to `~/.bashrc`, `~/.zshrc`, or your PowerShell profile, then open a new shell.

## Update lando4

`lando4 update` replaces the binary Lando 4 installed, and nothing else.

```sh
lando4 update --dry-run
lando4 update
```

Lando 4 writes an install record when it installs itself. Update reads that record to find the executable, confirms the file on disk still matches the record byte for byte, and only then stages, verifies, and swaps the new binary. A file named anything other than `lando4` (`lando4.exe` on Windows) is never a target, so Lando 3's `lando` is safe even when it sits in the same directory.

If the record is missing, points somewhere else, or no longer matches the file, update refuses and tells you to rerun the installer. It does not guess, and it never adopts a binary it did not install. Installed Lando 4 some other way, such as through a package manager? Update it the same way you installed it.

Windows cannot replace a running `lando4.exe`, so Lando 4 stages the new binary, exits, and lets a helper finish the swap. The helper re-reads the install record before it moves anything, moves only `lando4.exe`, and puts the original back if the swap fails. You see the result on your next `lando4` command.

After a successful swap Lando 4 rewrites the record to describe the new binary, so the next update and any later uninstall still recognize it. The previous binary stays beside it as `lando4.bak` and is yours to delete.

## Uninstall lando4

```sh
lando4 uninstall --dry-run
lando4 uninstall --yes
```

Uninstall removes what the install record lists and leaves everything else alone. `lando`, `~/.lando`, and your Lando 3 containers stay exactly where they are. Run the dry run first: it prints every step and what it will do before anything is removed.

A binary Lando 4 did not install is never removed, even if it sits in Lando 4's own `bin` directory. If the recorded binary changed underneath, uninstall reports it and leaves the file for you.

Add `--purge` to also remove Lando 4's data, cache, and config roots, and to strip the `# >>> LANDO4 shellenv >>>` block from the profiles Lando 4 wrote to. That deletes Lando 4 app state, so check the dry run first. A Lando 3 `# >>> LANDO shellenv >>>` block is a foreign PATH entry and survives, as does every line you added yourself.

Uninstall is safe to run twice. The second run finds nothing left and removes nothing.

## Start fresh on Lando 4

Lando 4 does not read a Lando 3 Landofile and there is no converter. Leave the old `.lando.yml` where it is for `lando`, and give Lando 4 its own app:

```sh
lando4 init --recipe lamp --yes
lando4 start
```

Or write a [Landofile](../landofile/your-landofile.mdx) by hand. Supported recipes today: `lamp`, `lemp`, `wordpress`, `drupal`, and `drupal-cms`. Then use the [everyday CLI loop](../cli/everyday-commands.mdx) with `lando4` in front.

Do not wait for a key-by-key converter. It is not up.

## Gotchas

- Two apps with the same name, one on each version, do not know about each other. Stop the Lando 3 one before starting the Lando 4 one if they share a port.
- `lando poweroff` only powers off Lando 3. `lando4 poweroff` only powers off Lando 4.
- Alpha install details and where to file bugs: [Alpha install and bug reports](../../alpha-install-and-bug-reports.md).
