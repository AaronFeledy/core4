# Fork an existing app into a scratch

From inside an app, run `lando scratch --fork` to start a scratch using that app's
Landofile. By default the fork works on its own copy of your project, so its
edits never touch your files. It creates separate containers and does not stop
or rename the original app.

```sh
lando scratch --fork --detach
```

After startup succeeds, run `lando scratch:list` to find the fork's id and use
`lando scratch:info <id>` to inspect it.

## Start the fork

```sh
lando scratch:start --fork --detach
lando scratch --fork --name review --detach
```

`lando scratch` and `lando scratch:start` are aliases of `apps:scratch:start`. Pass exactly one of `--fork` or `--from`. Bare `lando scratch --help` shows the scratch topic page, the same as `lando help scratch`; ask `lando scratch:start --help` for this command's flags.

`--detach` returns only after the fork passes startup readiness, including enabled healthchecks. Without it the session stays attached until Ctrl+C, then Lando tries to destroy the scratch. If the fork's routes can't be published, readiness fails, or you interrupt acquisition, Lando tries to clean up the scratch, including any routes the router already wrote. Use `--keep-on-failure` to skip that cleanup and inspect what the failed start created. User-app start retention does not apply to scratch apps.

If cleanup fails, Lando reports the scratch id without replacing the original startup error. If the scratch still appears in `lando scratch:list`, run `lando scratch:destroy <id>` after fixing the reported problem.

`--name` sets the base of the generated id (`scratch-<base>-<6hex>`), so `--name review` gives an id like `scratch-review-3f9a1c`. Lando shortens the base to at most 25 characters. The source Landofile is not rewritten. Scratch commands that take an id also accept that name; see [Inspect one scratch](./list-and-info.mdx#inspect-one-scratch).

## Fork an app from another directory

From a workspace directory with a Lando app in `site`, run:

```sh
lando scratch --fork --source site --detach
```

Pass `--source` with `--fork`. Relative paths start from the directory where
you run the command. Give Lando an existing directory, not a Landofile.
Lando looks for the Landofile there and then in its parent directories, so a
subdirectory of `site` works too. If Lando can't find an app from that
directory, it fails without creating a scratch.

The fork uses the plugins already selected for the command or embedding
runtime. When app-local plugin discovery is enabled, Lando refuses an explicit
source whose effective plugin selection differs. It does not load the source
app's plugins to compare the selections.

## Choose a copy or a shared tree

By default a fork uses `--isolate=full`: Lando copies your project into the scratch's own directory under the user data root and mounts that copy. Edits inside the fork stay in the copy, and edits to your project after startup don't reach the fork. The copy skips `.git/`, `node_modules/`, `vendor/`, `.lando/cache/`, and `.DS_Store`; see [Control a full fork copy](./mount-and-share-flags.mdx#control-a-full-fork-copy) for more exclusions.

To skip the copy, share the directory you run the command from:

```sh
lando scratch --fork --detach --isolate=cwd
```

With `--isolate=cwd` (or `--mount-cwd`), Lando copies nothing. Edits in the
mounted directory affect your host files. If you also pass `--source`, it
selects the Landofile but does not change which directory is mounted.
Use `--mount-cwd=<target>` to bind the working directory at one path in the
primary service instead of rebasing the app-relative mounts.

## What stays separate

The fork gets its own scratch id, slug, containers, and per-app bridge (`lando-<scratch-id>`).

Service DNS uses the scratch slug (`web.<scratch-id>.internal`).

## Inspect and destroy

Replace `<id>` with the fork's id from `lando scratch:list`. Inspect it before
running the final command: destroy removes the fork's containers, volumes, and
snapshots. Use `--keep-volumes` if you need its volumes and snapshots afterward.

```sh
lando scratch:list
lando scratch:info <id>
lando scratch:destroy <id>
```

`scratch:destroy` removes the fork's containers, volumes, and snapshots it took. Snapshots of the app you forked stay put, even with `--isolate=cwd`. A cwd fork still owns its own volumes under the scratch instance, so destroying it does not break `lando info` or `lando start` in the source app. Add `--keep-volumes` to keep the fork's named volumes and snapshots for inspection; an anonymous volume from an image `VOLUME` path still leaves with its container.

A fork whose services have the same build inputs as the app's reuses the images Lando already built for the app. Destroying the fork keeps the newest image Lando built for each of its services for up to seven days, so the next fork of the same stack starts without building.

To materialize a recipe instead of forking the app, use [Start a scratch app from a recipe](./scratch-from-recipe.mdx).
