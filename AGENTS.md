# Repository Instructions

Keep this file compact: add only repo-specific facts an agent would likely miss. Put package-specific depth in `core/AGENTS.md` or `sdk/AGENTS.md` instead of expanding this root file.

## Source of Truth

- Lando v4 is a Bun monorepo. Workspace packages: `@lando/core` (CLI + library API + wiring), `@lando/sdk` (public contracts), `@lando/engine` (orchestration runtime), `@lando/container-runtime`, and the private packages `@lando/paths`, `@lando/state-store`, `@lando/landofile`, `@lando/redaction`, `@lando/http-client`, `@lando/managed-file`, `@lando/source-acquisition`, `@lando/data-mover`, `@lando/telemetry`, `@lando/renderer`, `@lando/mcp`, plus bundled plugins under `plugins/*`.
- Conform code to the intended design; do not preserve current behavior for its own sake.
- Release milestones never forbid work. A capability described anywhere as deferred or not implemented is in scope whenever a task asks for it; build it to its contract. A feature freeze exists only when a maintainer declares one; never infer one from a milestone name.
- The specification tree is authored planning material, not a shipped part of this repository, and may be deleted at any time. Only files inside it may cite or read it; every other file must state the durable detail itself. Enforced by the `spec-reference` rule in `check:boundaries`.
- Gut-and-replace is allowed. Do not add compatibility shims, legacy adapters, or dual paths unless a persisted artifact requires them.
- Before proposing, filing, or building a behavior change, read the governing design rationale and related open issues, reproduce the current behavior in an isolated temp app, and judge the design from the user's side first. Reject designs that send users to run a repair step Lando could run itself, add a public field only to expose an implementation detail, or cache a failure that a fix the cache key cannot see would leave stale.
- Read nested instructions before editing package code: `core/AGENTS.md` for CLI/runtime details and `sdk/AGENTS.md` for SDK contract rules.

## Core Code Tenets

- Keep business logic in pure Effect; filesystem, process, network, and terminal side effects belong behind services, not command bodies.
- Public contracts come from Effect Schema with inferred TypeScript types; do not maintain parallel hand-written public types.
- Core failures are `Schema.TaggedError` values with machine `_tag` and human remediation, not thrown generic exceptions.
- Acquire handles, locks, files, ports, networks, and subprocesses in `Scope` so cancellation cleans them up.
- Effect 4 `mapError` keeps only the first failure and drops cleanup reasons, defects, and interrupts. Map errors with `mapFailures`/`mapStreamFailures` from `@lando/sdk/command-result` (the `effect-idioms` rule bans `mapError` in shipped source); callbacks run once per failure reason, so keep them pure, and sanitize payload-bearing defects with `mapDefectCause`.
- Effect 4 `Queue.takeAll` waits for at least one item. Use `Queue.clear` for a nonblocking drain of currently buffered items, especially in finalizers and event assertions; waiting on an empty queue inside a finalizer can prevent shutdown.
- Validate provider capabilities before planning, and plan before provider action; do not let providers discover unsupported intent at execution time.
- Lifecycle state that outlives one call (journal phases, registry statuses, receipts, exclusive claims) declares operation-keyed edges with `defineTransitions` from `@lando/sdk/transitions` and writes through `StateBucket.transition` or `StateBucket.mutate` (in memory: `planTransition` inside `Ref.modify`), which check and write under one lock, skip the write when an operation is settled, and remove the file instead of storing a tombstone. The operation, not the caller, picks the stored state, and test doubles reuse the owner's pure planner instead of copying its table. When the lock lives outside the bucket, pass a lock handle only the lock can construct rather than relying on a comment. A record re-derived from host observation each run gets a schema that cannot hold contradictory fields, not a transition table. Every durable bucket spec must be registered in `scripts/schema-compatibility/internal-stores.ts` with its lifecycle declaration, or exempted there with a reason; `core/test/build/persisted-store-registration.test.ts` enforces it.
- Prefer interfaces/plugins over config flags when implementations can differ; flags should tune one implementation, not choose architecture.
- Use Bun primitives first. Node compatibility APIs need a narrow adapter; use `ProcessRunner` for argv-precise spawn and `ShellRunner` for shell-shaped pipelines.
- User-facing surfaces must be agent-drivable: structured output, tagged failures, remediation, and preserved context across boundaries beat prose scraping.

## Commands

- Use Bun only: `bun install`, `bun run ...`, `bun test`. Do not introduce Node/npm/yarn/pnpm workflows.
- Standard gate after code changes is `bun run typecheck` plus `bun test`; root `tsc -b` typechecks non-docs test trees and `scripts/` through referenced projects. The Astro-owned `docs/**` tree stays outside that graph and uses `docs:check` plus `docs:test`.
- `tsc` is TypeScript 7, installed as `@typescript/native` (an `npm:typescript@^7` alias) because Bun links the first `tsc` bin by folder name; `core/test/build/typescript-toolchain.test.ts` guards that. TypeScript 7 has no compiler API: import it from `@typescript/typescript6`. The bare `typescript` name is a `docs` alias of that package for `astro check`, which Bun hoists to the root, so do not repurpose it. Dependabot skips `npm:` aliases; bump `@typescript/native` by hand. TypeScript 6+ defaults `types` to `[]` and TypeScript 7 rejects `baseUrl`: every tsconfig lists `types`, and generated tsconfigs use absolute `paths`.
- Biome configuration is `biome.jsonc`: Biome parses `biome.json` as strict JSON and rejects the rationale comments there. Biome 2's `recommended` preset demoted rules Biome 1 raised as errors, so `biome.jsonc` re-pins each one at `error` and `core/test/build/biome-config-pins.test.ts` fails when a pin is weakened. `bun run fix` applies fixable diagnostics; reformat-only commits are listed in `.git-blame-ignore-revs`.
- Also run `bun run lint` and any touched boundary/codegen/guide gate: `check:boundaries`, `check:guide-coverage`, `check:guide-drift`, `check:public-transcripts`, `check:telemetry-inventory`, or `lint:guides`. Debug one boundary rule with `bun run scripts/check-boundaries.ts <rule-id>`.
- Pre-PR quality script is `bun run gate:pr`: typecheck, lint, codegen:check, check:boundaries, and guide-drift against `origin/main`. Use that instead of typecheck+lint alone before pushing.
- Focused tests run by path, e.g. `bun test core/test/unit/bootstrap.test.ts`. Single-package scripts use Bun filters, e.g. `bun run --filter='@lando/core' typecheck`.
- That path is a filter, not a path: a stale or misspelled one emits a `did not match any test files` diagnostic and exits nonzero. Scripted spot-check loops must require both command success and a positive test count; never infer a pass only from the absence of failures.
- Test preload fills each unset Lando root in one per-process temp tree before application imports; explicit roots are preserved and CLI children inherit them. Only `LANDO_TEST_USE_REAL_ROOTS=1` disables isolation.
- `bun run test` only prints the CI shard commands. `bun run test:affected` only lists the selected files; add `--run` to execute them. Run it first, then `bun run test:unit:shard <i>/3`. Full shards and `test:unit` outlast agent tool timeouts: launch them detached (`setsid nohup ... &`) and poll the log, and read a gate's exit status from the command itself, never `$?` after `| tail`. Before calling a shard failure a regression, rerun that shard with tracked changes stashed (`git stash push` keeps untracked files, so the partition stays identical). A stale container-helper build fails every compiled-CLI test; rebuild it before reading those as regressions.
- `bun run test:unit` and PR shards run every `*.test.ts` in workspace `test/` trees and `scripts/`, minus files a `unit: "exclude"` selection keeps. `*.integration.test.ts` means a live or native prerequisite. Every other test a workflow step runs is a named selection in `scripts/test-selections.ts`, run as `bun run test:selection <id>` in CI and locally; only the provider matrix keeps its own plan (`scripts/provider-matrix-plan.ts`). `check:test-ownership` fails when an integration suite has no selection or `MANUAL_TESTS` entry, a selection is not run by its declared job, or a workflow calls `bun test` directly. Serial live suites require an answering `LANDO_TEST_PODMAN_SOCKET`, with no managed fallback. Missing/dead sockets skip local suites; explicit `LANDO_GUIDE_E2E=1` fails instead of skipping.
- `NIGHTLY_TIER_TESTS` in `scripts/test-selections.ts` (the CI-workflow codegen suite and the Linux acceptance suite) is excluded from PR shards, so drift those files guard can reach `main` without a red PR. Run them by path whenever you touch their generator.
- After adding a new `plugins/*` workspace package, run `bun install` so workspace imports resolve from the repo root.
- In a fresh worktree, run `bun install` and then `bun run codegen` from the repo root before tests or the source CLI (`bun core/bin/lando.ts`). The test preload rejects missing generated modules; the source CLI adds codegen guidance when a module-resolution error occurs and generated modules are missing.
- The in-container helper (host-proxy `lando` client, `lando logs --source` reader, and mounted `exec-run` supervisor) is static Go in `core/container-helper/`, built with Lando: `bun run build:container-helper` (`--test` runs `go vet`/`go test`) writes `core/container-helper/dist/`; never install Go on the host. Compiling `lando` refuses helpers older than their sources; tests that compile but never run the helper set `LANDO_CONTAINER_HELPER_DIR` to stubs (`core/test/build/fixtures/container-helper-stubs.ts`). `core/test/container-helper/helper.integration.test.ts` needs the real build.
- Linux runtime bundles also compile in a container: `bun run scripts/assemble-runtime-bundle.ts --platform linux-<arch>` builds natively on Docker Buildx or the running Lando runtime (`--engine docker|lando`); never install Go, Rust, or APT build packages on the host. Assembly is byte-reproducible, so compare two archives with `scripts/check-runtime-bundle-reproducibility.ts` instead of trusting a rebuild.

## Generated Files

- Do not hand-edit generated CI workflows, pin manifests, or the vendored Compose spec JSON. Edit the generator, run the matching `bun run codegen:*`. The Compose vendor generator writes checksum-pinned upstream bytes verbatim and must not format that file.
- **Pins vs derived (architecture-simplicity):** pin manifests (runtime-bundle, mutagen, compose vendor) and human-reviewed CI workflows stay committed. Pure build products (`dist/schemas/**`, `dist/command-schemas/**`, bake-time generated TS tables, command registry embed manifest, generated schema docs) are **derived** — produce them with codegen; they are not required as git SoT once US-510+ lands. Model: treat them like guide transcripts, which are regenerated every test run, gitignored, and never committed.
- `core/dist/schemas/**` and `core/dist/command-schemas/**` are ignored derived package mirrors produced byte-identically by schema snapshot codegen.
- `bun run codegen` runs generators in dependency order (see `scripts/codegen-catalog.ts`, the machine-readable ordered catalog; each entry carries exactly one ownership value (`committed-pin`, `committed-workflow`, or `derived`); `scripts/codegen.ts` is the runner).
- **Pure-drift `codegen:check` gate (architecture-simplicity US-505):** `codegen:check` runs the full codegen catalog and then `check:codegen-drift`, which fails on drift for the generated paths named by `CATALOG_OUTPUT_PATHS` in `scripts/check-codegen-drift.ts`. Its pathspec-scoped `git status --porcelain=v1 --untracked-files=all` catches tracked and newly untracked outputs without false-failing on unrelated dirty files elsewhere in the working tree. Gitignored derived trees stay outside that git-status half; they're covered instead by their existing generator/consumer validation. Deprecation checks stay in `lint`, while `typecheck` remains a separate gate. Use `bun run codegen` alone when you just want to iterate. Semantic gates stay separate: `check:guide-coverage`, `check:schema-compatibility`, `check:public-transcripts`, and `check:boundaries`.

| Gate | Class |
| --- | --- |
| `codegen:check` | pure drift |
| `check:guide-coverage` | semantic |
| `check:schema-compatibility` | semantic |
| `check:public-transcripts` | semantic |
| `check:boundaries` | semantic |

- Codegen scripts are expected to finish with `biome check --write` on emitted files; do not replace that with formatting-only steps.
- Route generated-file formatting through `scripts/_codegen-output.ts`; it explicitly disables Biome's VCS-ignore handling so gitignored derived outputs are still processed.
- Clean checkout bootstrap (target): `git clone && bun install && bun run codegen && bun run --filter='@lando/core' build:container-helper` before typecheck/test/compile; helper build needs a working `lando setup` provider, not host Go.

## Architecture Boundaries

- `@lando/sdk` is the public contract surface. Follow `sdk/AGENTS.md`: update `sdk/test/fixtures/sdk-public-surface.json` for public export or service-tag signature changes, and refresh schema artifacts with `bun run codegen:schema-snapshot` for schema changes.
- Each plugin-abstraction contract suite from `@lando/sdk/test` must stay listed in `core/test/contract/plugin-abstraction-coverage.test.ts` and exercised by its documented built-in invocation in the owning package's test tree, including `renderer/test/**` and `plugins/renderer-lando/test/**` for renderer implementations, unless the abstraction's pluggability-catalog entry documents that no built-in ships.
- `@lando/core` owns the CLI, library API, generated bootstrap layers, and bundled-plugin wiring. CLI/runtime quirks live in `core/AGENTS.md`.
- `@lando/engine` is the orchestration runtime: planner, operations, lifecycle, app/provider/subsystem services. It is not a grab-bag; cohesive self-contained concerns must be extracted to primitive packages (as `@lando/paths`, `@lando/state-store`, `@lando/landofile`, `@lando/redaction`, `@lando/http-client`, and `@lando/managed-file` were), and each extraction pays the scanner-retirement ratchet.
- `@lando/engine` ships an explicit exports map (no wildcard); every externally-consumed subpath must be listed there.
- Route priority is one shared space, not per app: `routePriority` (`engine/src/planner/route-identity.ts`) derives rank from the route alone (wildcard hostnames 2..65,538, exact hostnames 65,539..131,075, each widened by path-prefix length) because every app's dynamic config is merged into one router table. `@lando/sdk/schema` owns the band constants; the diagnostic fallback keeps `ROUTE_PRIORITY_DIAGNOSTIC`, and a router that contributes its own routers must pin them above `ROUTE_PRIORITY_MAX` or an app that claims that hostname captures them. Never reintroduce a plan-size or in-plan-index term: a plan ranked in isolation must compose correctly with plans it cannot see.
- One volume ownership path: `container-runtime/src/volume-ownership.ts` is the only producer of `dev.lando.volume-owner` (canonical root, the ownership PROOF that docker's planful delete, create-race detection, adoption, and SQL recovery compare against) and `dev.lando.volume-selector` (ownership-complete SELECTION value, because the daemon ORs values under one label key). The selector's owner key is `appIdentityKey("owner", <owner label>)` from `@lando/sdk/schema` — the derivation the planner stamps onto `AppPlan.identity`. A plan carrying no `identity` is migrated from `plan.root` there; never re-spell an ownership key or fall back to a raw root at a call site.
- Planning never contacts a certificate authority. `resolveCertsFeature` records `CertificatePlan` intent and strict binds to Lando-owned leaf paths (`engine/src/lifecycle/service-certificate-paths.ts`); `prepareServiceCertificates` (`engine/src/lifecycle/service-certificates.ts`) decides reuse at apply: it reads the authority's `root` once, keeps a pair on disk that is still current, otherwise calls `issueCert`, checks the result, writes key then certificate, and stamps the certificate digest as `sourceIdentity`. Every path that reaches `provider.apply` must call it first and identically, or create fingerprints flap and services recreate.
- A `CertificateAuthority` keeps no leaf store and returns PEM values, not paths: `root` yields the signing root and `issueCert` issues fresh material on every call (it is not idempotent). Consumers own their copy and decide when to reissue; never add a cache or a persistent output directory to an authority. `certificatePairIsCurrent` in `@lando/sdk/certificates` is the one currency check, shared by the engine (30-day renewal margin, root check) and the Traefik router (neither); do not write a second one.
- The mkcert root lives in the directory `mkcert -CAROOT` reports and is shared by every Lando data root on the host. Only `setup` (`plugins/ca-mkcert/src/ca.ts`) may create it, through `ensureRoot` in `plugins/ca-mkcert/src/root.ts` under the lock there, and it never replaces one. Any issuing mkcert run creates a missing root, so `root` and `issueCert` must check for it first and fail with the `lando setup` remediation. Leaves are issued into a private temp directory that is removed afterwards.
- The `RouterService` in context may be the unavailable router (`engine/src/subsystems/proxy/api.ts`): an unselectable router never fails bootstrap. Detect it only through `unavailableRouterReason`, never by id. Every operation that activates a routed plan calls `requireSelectableRouter` (global start, restart, and rebuild: `requireSelectableGlobalRouter`; both in `engine/src/operations/global-consumer-admission.ts`) before hooks, certificates, builds, any stop or destroy, and apply. Admission repeats the check only as a backstop, so a new activation path needs its own early call. Whole-owner route withdrawal uses `withdrawOwnerRoutes` and selected global stop republishes surviving routes through `republishRetainedRoutes` (`engine/src/lifecycle/route-withdrawal.ts`); never call `removeRoutes` directly from teardown. With no selectable router, `withdrawOwnerRoutes` removes routes through every installed router, built only when a withdrawal runs (`engine/src/subsystems/proxy/registry.ts`), never at bootstrap. It returns `withdrawn` only when every one was built and removed the routes; otherwise it warns and returns `skipped`, which is not cleanup proof. `republishRetainedRoutes` still warns and skips for an unavailable router. A selected router's failure stays fatal. A targeted global stop rebinds the router to the discovered root (`engine/src/operations/global-stop.ts`); wrap any router layer rebuilt for another root in `Layer.fresh`, because Effect's memo map otherwise returns the instance built at bootstrap for the configured root.
- One Compose serializer, many providers: `renderCompose`/`emitCompose` live only in `container-runtime/src/podman/compose.ts`; each provider exports a thin adapter that injects its own `ProviderErrorContext` and delegates. Values always go through `quoteYamlScalar` from `@lando/sdk/yaml`; every dynamic mapping key goes through `yamlMappingKeyText`, which emits a plain key only when an allowlist accepts it and YAML cannot re-resolve it.
- `@lando/redaction` owns the canonical `RedactionService`/standalone redactor, and `@lando/redaction/provider-error` owns `redactProviderError`, the one tag-preserving reconstruction of provider errors that providers and the registry both use (wrap it with `mapFailures`/`mapStreamFailures` so merged cleanup reasons survive); `@lando/http-client` owns HTTP egress (its `layer` provides Effect's `HttpClient.HttpClient`, plus network trust and downloader) and is the only package allowed to call global `fetch` or import Effect's `FetchHttpClient`; `@lando/managed-file/service` owns the `ManagedFileService` implementation (`layer`/`layerWithPrivateFileAccess`), ownership markers, codecs, and overwrite decisions, while `@lando/managed-file/transaction` owns the private multi-file transaction coordinator and `@lando/managed-file/transaction-guard` exports its SDK guard implementation layers. Recoverable multi-file edits go through that coordinator instead of hand-rolled staging: it takes a canonical-app-root advisory lock, rejects symlinked targets and parents outside that root, writes same-directory `<target>.lando-stage.<id>` files plus immutable `<file>.bak.<full-before-sha256>` backups, then fsyncs an owner-only `prepared` journal (under the state-store user-data root, the one exception to app-root containment) before any mutation and steps it through `committing` and `committed`. Journals, errors, and receipts carry digests, modes, and paths only, never file bytes.
- `@lando/source-acquisition` owns remote git/npm/archive acquisition, integrity checks (git commit identity, npm `dist.integrity`/`shasum`, archive SHA-256), extraction, and the `<userCacheRoot>/sources/` store (`git/<commit>/`, `archive/<sha256>/`, `.leases/`, and the `npm-*`/`ref-*`/`root-*` index records in the single user-cache `sources` StateStore namespace). Consumers (Landofile includes, recipe init, plugin install/update) inject transports and open a scoped `SourceSession`; never fetch, verify, extract, or publish remote trees elsewhere. `meta:sources:gc` is the only removal path.
- `@lando/mcp` owns MCP catalog projection, JSON-RPC transport, and retained-runtime dispatch. It consumes core command execution only through `McpCommandExecutor`; core implements that port with its command lifecycle and injects it at composition.
- Plugins may not depend on `@lando/core`; core imports plugin packages only via the generated composition root (`core/src/plugins/generated/**`), enforced by the `package-dag` rule in `check:boundaries`.
- Tests live in the package that owns the code under test; cross-package test imports use the target's root export or a named exports subpath (wildcard subpaths do not count), follow the package DAG (a package's tests import only its `dependencies`/`devDependencies` or a commented `testTargets` override in `scripts/boundary/rules/package-dag-policy.ts`), and every workspace package with `src/` ships tests under `<pkg>/test/`; enforced by the `package-dag` test tier in `check:boundaries`. Plugin tests never import `@lando/core`: engine-owned doubles live on `@lando/engine/testing/*` (`state-store`, `downloader`, `live-provider-socket`), implementation layers on their `@lando/engine/*` subpaths, and renderer IO on `@lando/renderer/*`; `@lando/core/testing` is for core's own tests and embedding hosts.
- `RemoteSource` and `Dataset` move data only and never sync application code; `CodeSync` owns code movement.
- **Single native CLI dispatcher** (architecture-simplicity): source and compiled `$bunfs` entries share one native command registry/dispatcher (`core/src/cli/run.ts`). Do not add a second OCLIF shipping path. The CLI surface is split three ways by role: `core/src/cli/commands/` is operation invocation plus render helpers, `core/src/cli/command-specs/` is the declarative CLI surface (`LandoCommandSpec`, flags/args/aliases, `*OptionsFromInput` parsers), and `core/src/cli/spec/` is the spec machinery (base class, spec type and validation, pre-command boundary, flag metadata primitives, bootstrap hooks). Prefer registry completeness + machine-output + relocated-binary smoke over dual-path parity tests. See `core/AGENTS.md`.
- The compiled binary target is `core/bin/lando.ts`, not `core/src/cli/index.ts`. Compiled-mode code must avoid top-level `await` and must not rely on `import.meta.url` for package/install metadata.
- Cold-start files must not statically import Effect, OCLIF, `@lando/sdk`, renderers, or plugins; startup regressions are release-blocking performance bugs.
- Command output goes through the `Renderer` service. `@lando/renderer` owns terminal writes; property-access-based calls, aliases, or assignments involving `console.*` or `process.std*.write` under `core/src/**`, `data-mover/src/**`, `engine/src/**`, `http-client/src/**`, `landofile/src/**`, `managed-file/src/**`, `mcp/src/**`, `paths/src/**`, `redaction/src/**`, `state-store/src/**`, `telemetry/src/**`, `plugins/**`, and `core/bin/**` fail the owner-excluding renderer-boundary gate, with no file carve-outs. Computed access such as `console["log"]` is outside this rule's detection.
- In Effect layers, `Effect.serviceOption(X)` sees services provided to that sub-layer, not sibling layers in `Layer.mergeAll`; provide dependencies directly to the layer that needs them.
- `effect-idioms` bans Data errors, native Date in Effect-importing modules, named bare-gen wrappers, local object predicates, exported `*Live` names, and `@effect/*` imports without carve-outs. Cause assembly (`combine`/`fromReasons`) is reserved to engine failure-compensation and SDK command-result/failure owners; consumers use role-aware helpers.
- The `RuntimeProvider` tag resolves to a non-functional stub (`engine/src/runtime/bootstrap-layer-support.ts`): `isAvailable` is false and every operational member, including streams, fails with `ProviderUnavailableError`. A real provider comes only from `RuntimeProviderRegistry.select(plan)`, which resolves by `plan.provider`. The global app is created on the host provider (`engine/src/providers/host-provider.ts`: setup's `HostProviderOverride`, then `LANDO_PROVIDER`, then `defaultProviderId`, then `lando`), never a Landofile `provider:`, and observed or torn down on the provider that holds its applied plan; go through `engine/src/global-app/placement.ts` (`globalCreateProviderId` / `globalObserveProviderId`) instead of selecting a provider directly. Provider `logs` resolves the applied plan itself from `target.app`, so omit `target.plan` unless you hold the real plan.
- Use the Effect-free paths primitive in `@lando/paths` (`paths/src/paths.ts`; re-exported through the semver-stable `@lando/core/paths` subpath via the `core/src/config/paths.ts` shim) for Lando roots and derived paths; do not re-spell `$HOME`, XDG, `%APPDATA%`, or platform separators. Hand-rolled `join(<userDataRoot>, "plugins"|"bin")` / `join(<userCacheRoot>, "scratch"|"sources")` is blocked by package-dag/paths rules; the residual paths rule scans the shared shipped-runtime tier (`core/src/**`, `data-mover/src/**`, `engine/src/**`, `http-client/src/**`, `landofile/src/**`, `managed-file/src/**`, `mcp/src/**`, `redaction/src/**`, `renderer/src/**`, `source-acquisition/src/**`, `state-store/src/**`, `telemetry/src/**`, and `plugins/**`) with no carve-outs, excluding only the owning `paths/src/**` implementation. Route consumers through `makeLandoPaths` (pure) or `PathsService` (Effect). A genuinely host-bound path that must ignore a faked `process.platform` (e.g. mutagen install dirs) should pin `makeLandoPaths({ platform: sep === "\\" ? "win32" : "linux" })` from `node:path.sep`, not read `process.platform`.
- Durable atomic, versioned, lockable state belongs in the private `@lando/state-store` package; plugins use `LandoPluginContext.stateStore`; host/tests override `StateStore` or use `TestStateStore`. The `package-dag` rule owns package direction, while the residual `state-store` rule forbids hand-rolled write-temp+rename+lockfile+version-envelope combinations in core and plugins.
- Narrowing a schema reachable from persisted state requires a state-version bump with a migration, enforced by `check:schema-compatibility`.
- Host/provider-shaped retry/backoff/timeout-to-verdict probing (healthcheck, scanner, doctor, downloader, setup readiness) must build on `@lando/sdk/probe`'s `runProbe`; net-new hand-rolled `Effect.retry`/`Effect.repeat`/`Effect.schedule`/`Schedule.*` loops across the shared shipped-runtime tier (`core/src/**`, `data-mover/src/**`, `engine/src/**`, `http-client/src/**`, `landofile/src/**`, `managed-file/src/**`, `mcp/src/**`, `paths/src/**`, `redaction/src/**`, `renderer/src/**`, `state-store/src/**`, `telemetry/src/**`, and `plugins/**`) are blocked by the `probe` rule in `check:boundaries` with no allowlist. Consumers redact `ProbeResult.lastError` through `RedactionService` before it reaches an event, transcript, or readiness summary.
- User-app resolution should go through `loadUserLandofile(...)` from `engine/src/landofile/app-resolution.ts`; core CLI modules may use the CLI-only re-export at `core/src/cli/app-resolution.ts`. Do not call raw `LandofileService.discover`.
- Landofile acquisition/preparation lives in `landofile/src/source.ts` and `root-compile.ts`; `include-*` owns fragment acquisition, and `pipeline/` owns authored composition and the single strict runtime finalizer shared by user, global, and scratch adapters.
- A versioned service type (`type: mariadb:10.6`) makes the planner write the type's own published artifact tag onto the config as `image` before service-type resolution, so `ServiceConfig.image` inside the planner does not prove the author supplied an image. Compare against the `resolvedArtifactTag` carried on `ResolvedService` before treating a service as custom-imaged.
- **Package seams first, AST second:** when a boundary is a private workspace package, the `package-dag` rule is primary. Propose a package seam before adding a scanner. **Scanner-retirement ratchet:** every new private workspace package seam must delete or shrink at least one boundary rule; every new boundary-rule registration needs a seam-impossibility justification in `scripts/boundary/registry.ts` and a matching `scripts/boundary/README.md` row. Net rule count may grow only with that recorded argument. `bun run check:boundaries` runs every registered rule in one pass; use `bun run scripts/check-boundaries.ts <rule-id>` for focused debugging.
- A plugin that installs host-global artifacts (socket-proxy units, polkit rules) owns their uninstall through `HostMaintenanceContribution.uninstall`: engine uninstall merges its `plan` steps (namespaced `<maintainer>:<step>`, `preserveOnKeepData` honored) before global-state deletion and runs its `execute`; an owned step that fails or loses ownership keeps the data root for resume and never falls through to generic removal. Engine uninstall must not encode plugin paths.

## Platform and Runtime Gotchas

- CI/release platform id `windows-x64` is different from runtime host key `win32-x64`; keep both names in their existing domains.
- Intel Mac (`darwin`/`x64`): `@lando/provider-lando` fail-closes via `rejectIntelMacHost` (setup, bundle, ensureRuntime, getStatus) with remediation naming `lando setup --provider=docker` / `LANDO_PROVIDER=docker`. Do not flip the capability default to docker, and do not set `isAvailable` false (file-sync would skip).
- The Windows Lando-owned Podman machine exposes its API at `\\.\pipe\podman-lando`; use HTTP over the named-pipe socket transport, not `curl --unix-socket`, and do not probe the Linux managed-service socket under `runtime/run/podman.sock` on win32.
- The committed `@lando/provider-lando` runtime-bundle manifest points at real published assets. To test a local unpublished bundle, build it locally and point `LANDO_RUNTIME_BUNDLE_MANIFEST` at it; verification is never disabled.
- Managed Podman's `--config <dir>` does not load `<dir>/containers.conf`; the service launcher must also set `CONTAINERS_CONF=<dir>/containers.conf` so bundled helper paths are honored.
- Managed Podman argv, the Linux child env (host allowlist plus Lando overlay), and the socket-path byte limit come only from `@lando/container-runtime/podman/managed-invocation` (pure argv/env/limits); the private runtime dir (`/run/user/<uid>/lando-<16 hex of sha256(realpath(runtimeDir))>`) and private pause teardown come only from `@lando/container-runtime/podman/managed-runtime-dir`. Never spread `process.env` into a managed Podman spawn and never run managed Podman with a different `XDG_RUNTIME_DIR`: that starts a second user namespace against the same storage.
- Hand probes of the managed Linux runtime must use its launch env and placement: the managed launcher starts Podman in a delegated `systemd-run --user --scope` with the private `XDG_RUNTIME_DIR` and no D-Bus address. A Podman CLI that inherits the shell's `DBUS_SESSION_BUS_ADDRESS` puts containers in a different cgroup, so resource limits, healthcheck timers, and pause placement differ from Lando's. Probe through the service socket or `lando`.
- Podman 6 volume-prune safety requires one ownership-complete selector per `label` value because values are ORed; keep named-volume intent in the top-level `all=true` query parameter, not inside the encoded `filters` map, or it broadens deletion.
- OpenTUI prompt support belongs behind the renderer plugin and dynamic import boundary described in `core/AGENTS.md`; never add `@opentui/core` to `@lando/core` or import it statically. Production code loads it only via a Bun-traceable literal `import("@opentui/core")`, lazy and TTY/default-renderer-only; a constructed or aliased specifier (e.g. string concatenation) is not a substitute and is treated as a boundary violation.

## Guides and Docs-as-Tests

- Load `lando-write-docs` (`.agents/skills/lando-write-docs/SKILL.md`) for reader-facing documentation, executable guides, and recipe READMEs. Not for normative specifications, RFCs/ADRs, implementation plans, issue/PR descriptions, changelogs, or marketing. In mixed tasks, apply per artifact; reader-facing architecture explanations still count as documentation.
- Executable guides are prose-first MDX: Markdown is the reader surface; `<Run>`/`<Verify>` wrap real harness execution only. No documentation-only `<Variable>` scenarios.
- Object-valued guide props (`expect={{ ... }}`) are parsed by converting the expression to JSON, which replaces every `'` with `"`. A regex or string inside one must contain no single quote; match it with `.` or a character class instead.
- A guide page gets exactly one `<Guide>` element. The shared guide compiler fails fast on a second block, reporting its source location and the line of the first declaration; nothing is generated for that page until the duplicate is removed. Put every `<Scenario>` in that one block and confirm the scenario count rose.
- A guide cannot assert plain-text output from a command with a boxed TTY renderer; that box wraps at terminal width, so the assertion passes piped in CI and fails in a terminal. Assert `--format=json`. Scenarios get an isolated temp cwd and nothing else, so they must never run a destructive command and must hold on a host that may already have Lando installed.
- Use `bun run dev:guides docs/guides/<path>.mdx --once` for a focused guide pass (require success and a positive test count). Full sequence: `docs/contributing/ci.md`.
- If a guide, recipe README, or guide-owned CLI surface changes, run `bun run lint:guides` and any relevant coverage/transcript/drift gates.
- `check:guide-drift` fires when a **covered source** path changed and no owned guide was touched — not only when a guide file changed. After `git fetch origin main`, run `GUIDE_DRIFT_BASE_REF=origin/main bun run check:guide-drift`. A bare `bun run check:guide-drift` prints `Guide-drift gate skipped` and exits 0; that is not a pass. If no guide update is genuinely needed, record `Guide-Coverage-Skip: <reason>` (≥ 24 characters) for the PR body instead of a token guide edit.
- `recipes/<id>/README.mdx` feeds both guide-scenario generation and committed scaffold README generation, so it must remain executable-guide-valid, not just readable prose.

## Working Tree Discipline

- Parallel agent work: give each track its own worktree, bootstrapped (`bun install`, `bun run codegen`, SDK build) before the agent starts, and confirm the agent actually started before treating the worktree as owned. Tracks run only focused tests; run full shards once, serially, on the merged tree, because concurrent shard runs on one host cause spurious timeouts. Review every track's diff before merging it, and land the result as one commit per lifecycle or behavior change, with behavior changes named in the PR.
- Generated outputs and `dist/`/`.tsbuildinfo` can appear after typecheck/build/codegen; clean with `bun run clean` when needed.
- Do not commit or stage unrelated generated drift. If a generator change is intentional, include the generator and its emitted outputs in the same change.
- Adding a member to the planner error channel means adding it to `AppPlannerError` in `sdk/src/services/planner.ts` (landofile-load members go to `LandofileServiceError` in `sdk/src/services/landofile.ts`, provider-selection members to `ProviderSelectionError` in `sdk/src/services/provider.ts`), then updating `sdk/test/fixtures/sdk-public-surface.json` for affected exports or service signatures; `sdk/test/types/plan-error-channels.test.ts` and `engine/test/operations/plan-error-channels.test.ts` fail typecheck on drift. Intentionally narrower consumers (`AppConfigApi.lint`, `engine/src/operations/app-config-lint.ts`, and the direct-parser CLI commands `app-config*`/`app-includes-*`) do not inherit new members and need manual review. `StopAppError` and `LogsAppError` inherit planner/provider additions, but their narrower landofile-load subsets remain explicit and need manual review. `engine`/`core` typecheck against `sdk/dist`, so run `bun run --filter='@lando/sdk' build` after an SDK type change or TS reports "Two different types with this name exist, but they are unrelated".
