# `@lando/sdk` Instructions

The SDK is the public contract surface. Root rules apply; this file keeps SDK-specific schema and compatibility traps.

## Navigation

- `src/schema/` is the canonical Effect Schema home, imported as `@lando/sdk/schema`.
- `src/events/` contains lifecycle payload schemas; event discriminators live on `_tag`.
- `src/errors/` contains Effect `TaggedError` classes.
- `src/services/` contains `Context.Tag` shapes only; Live Layers belong in `@lando/core`.
- `src/test/` is re-exported as `@lando/sdk/test` for contract helpers.

## Schema Conventions

- Brand primitives (`AppId`, `ServiceName`, `ProviderId`, `AbsolutePath`, `PortablePath`) as `Schema.String.pipe(Schema.brand(...))`; plain strings remain the `.Encoded` wire form.
- Shared schemas live once in `src/schema/`; consuming barrels should `import` and `export type` rather than redefining.
- Schema files use `// ====` section banners with a one-line description of what the section covers.

## Gotchas

- `.Encoded` is wire/input shape and `.Type` is decoded output. `Schema.DateTimeUtc` encodes as an ISO string but decodes to `DateTime.Utc`; build fixtures on `.Encoded` and date strings via `DateTime.formatIso(dt)`.
- Do not `Schema.decodeUnknown` an already-decoded runtime value. Use `Schema.is(MySchema)` for runtime-shape assertions, or `Schema.encodeUnknownEither(MySchema)` when a test needs an encoded round trip.
- Additive public exports must be documented in `sdk/API_COMPATIBILITY.md` or `sdk/test/library/sdk-backward-compatibility.test.ts` fails. The compat test reads the "Additive Alpha schema exports" and "Additive Alpha service tags" headings even for Beta-era additions; new `@lando/sdk/test` helpers belong under "Additive Beta test helper exports".
- Public JSON Schema membership is the single `JSON_SCHEMA_REGISTRY` in `sdk/src/schema/json-schema.ts`. Add public schemas/events there, then run `bun run codegen:schema-snapshot` to **write** `dist/schemas`, `dist/command-schemas`, `sdk/test/fixtures/bundled-plugin-manifests.json`, and `docs/reference/schemas`. The schema and reference trees are **derived build outputs**, so committing them is not required once untracked; CI validates them through deterministic generator and consumer checks. `bun run codegen:check` separately owns pure drift for committed catalog outputs, including the bundled-plugin manifest fixture. Still update `sdk/API_COMPATIBILITY.md` for additive public exports.
- A `ServiceConfig` field transform must accept its own canonical output as an input variant. The Landofile pipeline decodes twice (per file, then over the merged result — files apply low-to-high precedence, `base` < `dist` < `upstream` < the canonical `.lando.yml` < `local` < `user`, maps deep-merge and scalar arrays replace — with `onExcessProperty: "error"`), so a transform whose canonical keys differ from its accepted keys (camelCase `readOnly` vs Compose `read_only`) rejects its own first-pass output. Cover new alternate-form fields with a `decode(decode(x))` test under BOTH default and `onExcessProperty: "error"` options; an encode round trip alone does not catch it. Make the accepted-form and canonical-form union members mutually exclusive with `Schema.optional(Schema.Never)` anti-fields for the opposite spelling. Under the default `onExcessProperty: "ignore"` an earlier union member structurally matches the canonical object and silently strips the camelCase keys, so a `"readOnly" in input` style guard inside `decode` never fires and the value is silently re-defaulted.
- Attach an `x-*` extension record as the SECOND POSITIONAL ARGUMENT to `Schema.Struct(fields, ExtensionRecord)`. `Schema.extend(struct, Schema.Record(...))` destroys `.fields`, and `landofile/src/service.ts` builds its service-key allowlist from `Object.keys(ServiceConfig.fields)`. An `x-` key never appears in that allowlist either, so the unsupported-key predicate needs its own `key.startsWith("x-")` escape.
- A field `description` set only at the field site does not survive `Schema.encodedBoundSchema` when the field is a transform, so the field ships undocumented in `ServiceConfigInput` and its published artifact. Annotate the transform's `from` schema too; the description then reaches both the artifact and the public-field-description gate, which resolves it from the single declared member of the optional `Union(T, undefined)`. Do NOT reach for `PUBLIC_FIELD_DESCRIPTION_EXEMPTIONS`: entries there are permanent and unpoliced, so an exempted field keeps passing after its description is deleted. The pre-existing transformed entries in that set are legacy debt, not the pattern to copy. The gate only fires during `codegen:schema-snapshot`, so run that early rather than as a final formality.
- `TaggedError` fields named `line` or `column` collide with Bun's `Error` source-location fields if declared as `Schema.optional(Schema.Number)`. Use `Schema.UndefinedOr(Schema.Number)` so Effect assigns `undefined` explicitly.
- The dependency-free Landofile parser intentionally implements a YAML subset; do not replace it wholesale with `Bun.YAML.parse`, which would also enable unrelated tags, block scalars, populated flow collections, and directives. Native references resolve in `landofile/yaml-references.ts` before schema decode. In sequence items, map detection must require whitespace after `:` while preserving that raw whitespace for source columns, or a scalar like `8080:80` becomes a mapping.
- Do not pipe `Schema.filter` onto an exported snapshotted struct with `optionalWith` defaults or `Schema.Record` fields; it collapses the published JSON Schema root. Keep the exported struct plain and apply cross-field validation on a separate decode-only schema.
- `@lando/sdk/expressions` is not `@lando/sdk/schema` and is not compatibility-frozen except for exported errors. Keep the evaluator pure data-in/data-out: no `Bun`, `process`, `node:fs`, Layers, host IO helpers, or secret values in error messages.
- A `Context.Tag<Self, {...}>` whose inline service-object methods are generic over and reference a large discriminated union (e.g. typed `EventService` methods returning `Extract<LandoEvent, {_tag:Name}>`) trips `TS2310/TS2506` ("recursively references itself as a base type"). Extract the service object into a named `export interface XShape` and pass `Context.Tag<Self, XShape>`; the indirection breaks the eager self-reference evaluation. The `services/index.ts` `declare class` MIRROR must stay an INLINE `{...}` type literal, NOT a reference to that interface — `sdk-backward-compatibility.test.ts` parses `index.ts` alone and resolves only the inline 2nd type-arg, so a cross-file interface reference reads as zero methods.
- Evolving a frozen service tag's method signatures (adding methods, changing a param shape) requires updating its entry in `sdk/test/fixtures/sdk-mvp-surface.json` (exact per-tag `toEqual`) AND adding an `## Compatibility notes` bullet in `API_COMPATIBILITY.md`. The fixture stores readable signatures; the test normalizes both sides, so match the source spelling (generics included).

## Tests

- SDK tests import public paths (`@lando/sdk/schema`, `@lando/sdk/services`, etc.) so they exercise the plugin-author surface.
- Root `tsc -b` walks `sdk/test/` through the aggregate test project; keep `bun run typecheck` and `bun test` paired for SDK changes because runtime assertions remain distinct from static checking.

## Plugin-abstraction contract kit

- Each pluggable-abstraction interface in the pluggability catalog publishes a shared contract suite from `@lando/sdk/test` as a `make*ContractSuite` + `run*ContractSuite` pair (the `make*` form is an alias of the `run*` form). The six kit abstractions are `ToolingEngine`, `RouteFilter`, `SecretStore`, `ConfigTranslator`, `PluginSource`, `DoctorCheck`.
- Every kit suite MUST be exercised against its built-in implementation(s) by a `core/test/**` invocation — NEVER an `sdk/test/**` self-test (those are suite self-tests, not built-in coverage). The `core/test/contract/plugin-abstraction-coverage.test.ts` test-layer coverage gate holds a canonical manifest and FAILS when a published kit suite has no built-in invocation, when an invocation file is deleted or stops calling its suite, or when a kit suite export is renamed/removed. Adding a new pluggable abstraction with a suite means adding a manifest row AND a built-in invocation.
- Manifest `defaultPolicy` encodes how built-in coverage is provided: `built-in` (a concrete core impl is run), `reference-mirror` (schema-only in core today, so the suite runs over the documented reference transforms for that abstraction — e.g. `RouteFilter`), or `none-bundled` (the abstraction's catalog entry documents no built-in by default — e.g. `ConfigTranslator` — so the gate requires only the suite exports). Do not fabricate a fake "built-in" to satisfy the gate for a `none-bundled` abstraction.
