# `@lando/core` Instructions

Inherit root `AGENTS.md`; keep only core-specific traps here.

## Effect services and tracing

- SDK tags use `Context.Service<X, { ...inline shape... }>()("@lando/core/X")`; preserve public ids, allowing a separate shape only for TS2310/TS2506. Package-private service classes use `@lando/<package>/<Name>` ids, `static readonly layer = Layer.effect(this, Effect.gen(...))`, `X.of({...})`, and static `layer<Variant>` variants.
- Cross-package SDK implementations export `layer`, `layer<Variant>`, or `layer(options)` and are consumed via implementation-named namespaces: `import * as BunProcessRunner from "@lando/engine/services/process-runner"`, then `BunProcessRunner.layer`. New layer exports must not use `*Live`/`make*Live` names.
- Use `Effect.fn("<Owner>.<method>")` for public service methods, engine operations, provider/runtime calls, planner phases, network egress, managed-file transactions, command lifecycle stages, and MCP calls. Use `Effect.fnUntraced` for schema helpers, per-frame renderer work, redaction, path math, and the tooling hot path; attach combinators as extra builder arguments rather than trailing `.pipe`.
- CLI enables `References.TracerEnabled` only for `--trace`/`LANDO_TRACE` or configured OTLP; embedding hosts keep their own tracer in `openLandoRuntime`/`makeLandoRuntime`. Redact span attributes through `RedactionService` before retention/export; never retain raw secrets, environment values, or file contents.
- `runWithRendererHandling` runs each dispatched command under one root span `lando <command-id>` (attributes: `lando.command.id`, `lando.invocation.id` only) with `CommandLifecycle.init` (runtime build + init event), `CommandLifecycle.run`, and `CommandLifecycle.render` children. Spans record only when a `tracer` is passed to it. Stage parents go through `Tracer.ParentSpan`, not `Effect.withSpan`/`withParentSpan`, because those push frames into `Cause.pretty` failure output.
- The CLI installs ahead-of-time decoders from the derived `core/src/cli/generated/compiled-decoders.mjs` for the schemas listed, in order, in `core/src/cli/compiled-decoder-targets.ts`. Install trusts that order and those AST instances, so run `bun run codegen` after changing a listed schema or the Effect version. Keep the decoders that run on a hot path in that list; library embedders still use the interpreter.
- Effect code uses `Clock` for milliseconds and `DateTime` for instants/formatting, preserving wire formats; host boundaries alone convert native `Date` values.

## Tests and Guides

- `core/test/cli/fixtures/*.json` is formatted by `bun run lint`. Renderer tests should compare `JSON.parse(output)` to `Bun.file(fixture).json()`, not raw compact JSON strings.
- Guide TDD specifics live in the root file. Use the core notes here only when changing the guide generator/runtime behavior, not for routine MDX edits.
- `runScenarioLayerCommand` in `core/src/testing/scenario-context.ts` short-circuits `start`, `destroy`, and `curl` with canned results before the real CLI runs, so a guide `<Run command="lando start" expectExit={1} />` can only fail on the one hardcoded landofile substring it looks for. Prove planner or validation rejections with a command that falls through to `invokeRealCli`, such as `lando app:cache:refresh`.
- Under Bun, `process.exitCode = undefined` is a no-op that keeps the previous value, so a hook resetting it that way is decoration and a leaked code fails the next file in the shard. Reset with `0`, and inject `setExitCode` in any test that drives a failure envelope so the renderer boundary never writes the real process code. Trace an unattributable write with a `Proxy` over `globalThis.process`; the property is non-configurable, so `Object.defineProperty` cannot trap it.
- Bun does not cancel the body of a test that exceeds its time budget: it records the failure, starts the next test, and the abandoned body keeps running, so its teardown lands mid-test. A fixture that moves `process.cwd()` or a process-global env var such as `LANDO_USER_CACHE_ROOT` must therefore restore a value no test removes rather than the ambient value on entry, must not clobber a later owner, and must still repair the value when it still names a root that is about to be deleted. `core/test/_support/temp-cwd.ts` implements those rules (`withCwd`, `withEnvVar`); use them instead of a bare `process.chdir` / `process.env` + `finally` pair, and pass every temp root the fixture removes.
- `core/test/tsconfig.json` remains an editor/LSP project. The root aggregate test project owns gate coverage for `core/test/**` and its imports, so `bun run typecheck` is the authoritative test-type gate.
- `@lando/engine` exposes an explicit export map in `engine/package.json`; core tests import `@lando/engine/<named subpath>` directly. Adding an engine subpath used outside engine requires adding it to the export map, guarded by `engine/test/package-seam.test.ts`; that guard also requires the key to mirror the file path exactly, so `./src/install/record.ts` must be exported as `./install/record`, never a flattened `./install-record`. Engine-owned tests live in `engine/test`.

## Recipe Sources

- `lando init --name=foo` without an explicit positional destination writes `<cwd>/foo` (`resolveInitDestination` in `init-destination.ts`). A follow-up `lando start` must run in that directory, not the parent; use `lando init <destination>` to choose another directory, not a `--destination` flag.
- The only accepted author format is `RecipeSource` from `@lando/sdk/schema` (`sdk/src/schema/recipe-source.ts`): metadata, keyed `options` (`{ type, default?, prompt? }`, secret `{ type: { kind: "secret" }, disposition }`, or `{ drop: true }`), required `config`, ordered `variants: [{ when, config }]`, `files` (plus `{ dest, drop: true }`), and `postInit`. `parseRecipeSource`/`validateRecipeSourceObject` in `source-parse.ts` decode strictly with excess properties as errors, so authored `prompts:`/`snapshot:`/digests are rejected, never adapted. `options.name` is reserved; the generic app-name prompt is CLI-supplied. The restricted YAML parser spells an empty mapping as a bare `config:` line, not `{}`.
- Historical `RecipeSnapshot`/`RecipeProducer` wire data is derived, never authored: `compileRecipeSource` (`sdk/src/schema/recipe-source-compiler.ts`) lowers config layers into bounded ASTs and `core/src/recipes/compiled-source.ts` (`compileResolvedRecipe`) supplies observed asset/script digests and trusted producer coordinates. `RecipeManifest` survives only as a derived runtime carrier (`CompiledRecipeManifest`). Do not reintroduce a hand-written snapshot, `contentDigest`, or asset inventory anywhere, bundled or external.
- `lando init --source=git` is acquisition then the shared path: `core/src/recipes/git-source.ts` shallow-clones, publishes by commit SHA under `<userDataRoot>/recipe-cache/git/`, and the published tree resolves like a local directory. Remote trees load `recipe.yml` only (never `recipe.ts`); a local directory may ship `recipe.ts`. Raw `.lando.yml` templates in `files:` are never the render path; preparation rejects a duplicate Landofile destination.
- `lando init --source=tarball` downloads through the resolver seam, SHA-256-verifies before extraction, uses the pure-JS tar(.gz) reader, and publishes under `<userDataRoot>/recipe-cache/tarball/<sha256>/`. `--checksum` hard-fails on mismatch; without it, verification/prompt handling belongs in `acquireInitRecipe` in `core/src/recipes/acquire.ts`, not the resolver.
- Keep remote-source CLI parsing centralized in `core/src/cli/commands/init-source.ts`; the single native dispatcher must preserve identical `--source`/`--url`/`--path`/`--checksum` acceptance and exact missing-url wording (`<git-url>` vs `<tarball-url>`) for source and compiled entries. The default git cloner must stay non-interactive.

## Recipe composition

- `resolveRecipeSource(resolved)` in `resolved-source.ts` is the private origin-bearing resolver: it returns ordered parent-first `sources`, the composed `source`, explicit `files`/`postInit` entries shaped `{ value, origin, evidence, evaluation }`, `configLayers` (parent base, parent variants, child base, child variants, in that order), and `historyEligible`. `manifest/flatten.ts` reads a bundled parent from `BUNDLED_RECIPES[...].authoredSource`, never by reparsing `manifestYaml`, and `manifest/merge.ts` (`composeRecipeSources`) replaces options by name, files by destination, drops consume inherited entries, and appends actions parent-first. Do not import `service.ts` from `flatten.ts` (import cycle).
- Pass resolution entries straight to preparation and post-init; never zip parallel arrays onto a decoded manifest or look entries up by index. Origins are `{ kind: "bundled", id }` or `{ kind: "directory", root, acquisitionRoot? }` (`manifest/origins.ts`); directory roots are private read coordinates and never portable identity. After a remote hop, further local parents stay inside that published tree and load YAML only.
- `historyEligible` means all resolved sources are declarative and can produce inert declarative history; it is false when the source or ANY ancestor evaluated TypeScript. It does not establish external published versions or installed migration edges; bundled history lookup is unchanged. Initialization stays supported. Describe/validate expose `initializable`, `readiness` (`ready` | `requires-input` | `conflict`), `missingAnswers`, `historyEligible`, and `preview` through `RecipeReadinessFields` (`cli/commands/recipe-init-schemas.ts`); init shares preparation and returns its own preview. Inspection uses default answers and the current-directory app name/destination; add no flags for them.
- `meta recipes describe/validate .` is not a local path; use `./` or a `recipe.yml` path.
- A dropped option may not be referenced by any remaining `config`/`when`; the compiler rejects that instead of treating the drop as a declaration.

## Bundled recipes and compiled decomposition

- Bundled sources are TypeScript `source` constants under `builtin/<id>/source.ts` registered in `builtin/source-catalog.ts`, sharing helpers from `source-php.ts`/`source-web.ts`. `scripts/build-bundled-recipes.ts` compiles all 24 through the same SDK compiler and emits `generated/bundled-recipes.ts` (inert `authoredSource` + `manifest`) and `generated/catalog.ts` for the cold path; `builtin/decomposers.ts` and `builtin/snapshots.ts` are thin lookups over that output. Edit a `source.ts`, run `bun run codegen:bundled-recipes`, and commit nothing by hand under `generated/`. The bundled entry's `source` label `<id>/recipe.yml` is a display coordinate; runtime never reads `recipes/<id>/` from disk, and an on-disk `recipes/<id>/recipe.yml` must be author-source format (no `prompts:`/`snapshot:`) to pass `meta recipes validate`.
- `core/src/recipes/manifest/parser.ts` is a deliberately restricted YAML reader, not a general one: keys must match `^[A-Za-z0-9_-]+$`, tabs are rejected, a `#` after whitespace starts a comment only outside a YAML-quoted scalar, and a populated inline `{...}` mapping is a hard error. Author docs must show block mappings and block sequences.
- Public `lando init` has one path: `compileResolvedRecipe` once, `prepareRecipeInit` (read-only: no destination directories, locks, stages, journals, or provider calls) returning `requires-input` or a `ready` plan with exact bytes/modes/digests, then `runRecipeInitPipeline`. The decomposer for every source, bundled or external, is `makeCompiledRecipeDecomposer(manifest, context)` from `compiled-decomposer.ts`; there is no renderer registry, no per-recipe decomposer module, and no fallback. Static files are copied byte-exact; `template: true` files are decoded as strict UTF-8 and only `{{ app.name }}` is replaced. File `when`/`engine` are rejected at preparation; do not document them as supported.
- Publication is one `makeManagedFileTransactions.run` with `create` operations for the Landofile and all authorized auxiliary files (default mode `0644`, Windows applies only the owner-write bit), then separately bound post-init. An existing Landofile is `InitTargetExistsError`; any existing auxiliary member skips the whole auxiliary set and effectful actions. The create set is sequentially recoverable, not all-files-atomic: a late conflict is `RecipeInitCommitError` with journal id/state and a retained prefix, never a claimed rollback. Post-init external effects are not rolled back (`RecipeInitPostInitError.rolledBack: false`).
- A versioned service type already stamps `image`; compare against `resolvedArtifactTag` before treating a service as custom-imaged (root `AGENTS.md`). Enum option values may be typed scalars including `false` (`composer: false` in `lamp`), which survive Landofile reload as typed false.
- The 24-id shipping list is `buildConfig.bundledRecipes` in `core/build.config.ts`; `core/test/recipes/builtin-decomposers.test.ts` pins the registry against it and `core/test/recipes/bundled-recipe-milestone.test.ts` holds the aggregate evidence (README, scaffold output, default/nondefault coverage, auxiliary inventory) for the whole set.
- Adding `recipes/<id>/README.mdx` means running `codegen:recipe-readmes` and committing the generated `.scaffold/` output: `check:codegen-drift` reads `git status --untracked-files=all`, so a newly generated scaffold file fails `codegen:check` while it is merely untracked or staged. Execute the guide itself with `bun run dev:guides recipes/<id>/README.mdx --once`, which accepts a recipe README path, not just `docs/guides/**`.

## Programmatic `recipe.ts`

- A local recipe directory may contain `recipe.ts` or `recipe.yml`, never both (`resolveLocal` rejects both). `recipe.ts` default-exports a `RecipeSource` object or (async) factory, loads through `loadRecipeTs`, reuses Landofile sandbox scanning, imports via Bun's TS loader, and times out via `LANDO_RECIPE_TS_TIMEOUT_MS`. Acquisition evaluates once and carries `authoredSource`, `sourceContent`, `evaluation: "typescript"`; resolution never calls the factory again.
- `defineRecipe` (`@lando/sdk/schema`) types `Recipe = RecipeSource` or `RecipeFactory`; it is a value export covered by `subpathExports` in `sdk/test/fixtures/sdk-public-surface.json`. Author modules receive Lando's own `@lando/sdk` (including public author subpaths) and `effect` instances without a local install.
- Describe/validate on a `recipe.ts` do evaluate the module on the host (there is no YAML-only inspection path). The import scan is a boundary check, not a security sandbox; a disallowed import fails as `RecipeManifestParseError` before any code runs, and so does a missing default export, while an invalid exported recipe is `RecipeManifestValidationError`.

## Dynamic Prompt Choices

- `choicesFrom: { command, args?, parse }` runs in `core/src/recipes/prompts/choices-command.ts` behind `ChoicesCommandRunner`. Use `landoInvocationPrefix(execPath, argv)`: compiled binaries run as `[process.execPath]`, source mode uses `argv[1]`. Do not set `BUN_BE_BUN` here.
- `collectPrompts` expands `choicesFrom` at prompt time, not manifest validation time. A supplied `--answer` bypasses the command. Unit-test dynamic choices with an injected fake `choicesRunner` rather than a real subprocess.

## Renderer Task Tree

- `TaskDetailRing` and the pure `TaskTreeViewModel` live in `plugins/renderer-lando/src/task-tree-tail.ts`; core has NO re-export shims (the old `core/src/cli/renderer/{task-tree-tail,format,keybindings}.ts` shims are deleted). Pure formatters live in `@lando/sdk/renderer` (`sdk/src/renderer/format.ts`); tests import painter/keybinding internals from `@lando/renderer-lando/*` subpaths directly. TTY mutation belongs only to `opentui/live-region-controller.ts` and `opentui/inline-live-region.ts`: the view model emits content with no cursor/erase bytes. Default TTY paint is inline at the cursor (log-update). OpenTUI is acquired only for full-tail expand.
- The bundled `@lando/renderer-lando` plugin OWNS the default `lando` renderer and contributes it via its `plugin` descriptor (`renderers` map carrying the finished `RendererContribution` plus `loadInteractivePromptDriver`), composed in `plugins/renderer-lando/src/renderer-runtime.ts`. `core/src/cli/renderer/bundled-renderers.ts` only RESOLVES contributions from the generated `BUNDLED_RENDERER_MODULES` table (`core/src/plugins/generated/renderers.ts`); it does not assemble the renderer from parts and never imports `@lando/renderer-lando` by name. Tests needing the Lando layer import `landoRenderer`; pure painter behavior asserts `LandoTreePainter` directly via `@lando/renderer-lando/task-tree-tail`.
- `RendererNarrationIO.isTTY`, dimensions, and `externalOutputStream` describe stderr. The live region requires both a narration TTY and stream; otherwise it degrades to stderr lines. `createStdioRendererIO` omits the stream when stdout is a pipe or socket, since a downstream process may share the terminal. Event consumers have no stdout writer. Full `RendererIO` adds payload writers and `stdoutIsTTY`/`stdoutColumns` for result formatting. Terminal stdout payloads suspend the stderr frame, write to stdout, then repaint; redirected stdout never interacts with the region. Buffered IO has no terminal stream, so live-region tests supply one explicitly.
- Full-tail uses OpenTUI `alternate-screen` with `externalOutputMode = "passthrough"`. On return, destroy/leave OpenTUI and resume inline paint. Do not restore split-footer. Do not pin the live tree to the terminal footer.
- `task.tree.start` first-paints pending child placeholders and must not emit rewind bytes on that first frame; tests assert absence of `cursorUp`/`eraseDown`, not absence of all ANSI SGR.
- `--tail`/`--no-tail` is still deferred; do not wire a CLI flag. Expand/collapse events remain non-renderable in `format.ts` to avoid publish/consume echo loops.
- TTY key input is wired inside `TaskTreeConsumer.layer` (`plugins/renderer-lando/src/task-tree-consumer.ts`), not command modules; fake input uses `createBufferedRendererIO({ isTTY: true, terminalRows }).injectKey(...)`.
- The OpenTUI renderer is acquired lazily on full-tail expand, not on first `task.tree.start`. Module prefetch on allowlisted `cli-*-init` stays. Non-tree events (`message.*`, `log.line`) before any tree stay line-mode. Eager OpenTUI acquisition would fight interactive prompts for the same terminal.
- The alt-screen full-tail reader (`transcript-tail-reader.ts`) requires an injected `PathsService` and fails closed without it. It contains the branded transcript path against `roots.userDataRoot` both lexically and by realpath, revalidating at open and around every read, so a parent-symlink swap after open is rejected. Input-generated `task.detail.expand`/`collapse` publish only AFTER the fallible screen transition succeeds; a failed transition restores view state and suppresses publication.
- `outputJournalFor(io)` keys one bounded narration journal by the shared IO object. Event consumers receive its narration-only type; services retain full output access. Narration commits on stderr; payload suspension takes a writer callback and never acquires stdout through the journal. Publishing a transcript path on `task.start` is renderer-facing metadata only; producing the transcript file/stream and `task.detail` remain the build orchestrator's job (it opens the per-step transcript on `build-step-start`, appends each `execStream` chunk, and closes it on `build-step-complete`/`build-step-fail`), and the reader degrades gracefully (collapse, no false expand) when the file is absent.

## CLI dispatch (single native engine)

Architecture-simplicity retired dual OCLIF/`runCompiledCli` dispatch. Register new work on the native registry/dispatcher path (`core/src/cli/run.ts` / command registry). The CLI surface is split three ways by role:

- `core/src/cli/commands/` — operation invocation plus the `render*` helpers for a command.
- `core/src/cli/command-specs/` — the declarative CLI surface: `LandoCommandSpec` objects, flags/args/aliases, and `*OptionsFromInput` parsers.
- `core/src/cli/spec/` — the spec machinery: the spec type and its validation, the pre-command boundary, and flag metadata primitives. `command-base.ts` re-exports those types from `command-spec.ts`.
- Built-in commands are class-free `LandoCommandSpec` records in `command-specs/`. `built-in-command-registry.ts` is the single catalog: each entry is `{ spec, status }` (`implemented` | `deferred` | `embedding-exempt`). Native dispatch (`run.ts` → `runBuiltInCommand`) and `EventCommandExecutorLayer.layer` consume the same entries. The four embedding-exempt ids (`apps:init`, `meta:setup`, `meta:shellenv`, `meta:uninstall`) stay behind `native-only-built-in-adapters.ts` and must not be imported through the default `@lando/core` entry.
- Inject `BuiltInCommandCatalogLayer.layer` through the bootstrap generator and the hand-maintained runtime service union (`core/src/runtime/layer.ts`). Do not import the registry back from a generated bootstrap service, and do not add a second dispatcher.
- One command registry is the SoT for canonical ids, flags, bootstrap level, `run`, help metadata, and `resultSchema`. Implemented vs deferred ids must not be split across a second engine switch.
- Declare confirmation flags with `yesFlag` or `nonPromptingYesFlag` from `core/src/cli/spec/confirmation-flag.ts`; plugin `yes` flags get `-y` from `pluginFlagDefinitions`.
- Source (`bun core/bin/lando.ts`) and compiled `$bunfs` entries share the same dispatcher. Faithful compiled reproduction runs the binary **outside** the repo tree.
- In source mode, `core/bin/lando.ts` adds `bun run codegen` guidance to module-resolution failures when generated modules are missing. Compiled `$bunfs` entries already embed those modules and skip this check.
- Pre-command failures (pre-parse flag validation, missing/invalid bootstrap, runtime-layer construction) use `renderPreCommandFailure` / `runCompiledCommand(..., { preCommand: true })`: standard machine result envelope or text bug-report, non-zero exit, and **no** `cli-<id>-init`/`-run`/`-error` lifecycle events. Only resolved command execution attaches an invocation snapshot.
- Tooling `command_not_found` routing requires a fresh `readFreshAppCommandCacheForCwd` index, never the `CommandRegistry` `list` method (its cache-miss path performs live discovery). A fresh-index miss may resolve only the matching `.lando/scripts/<segments>.bun.sh` after cached alias policy checks; stale/missing indexes never use that fallback. Script routing fingerprints cover relative paths and parsed front-matter, not executable bodies. Command listings opt into full script-inventory freshness.
- JSON machine output must produce a schema-valid `CommandResultEnvelope` through the single `encodeCommandResult` serialization seam (never a per-command `JSON.stringify`), passed through `RedactionService` before emission; plain/`lando` stderr may differ in wrapping/prefixes but must preserve tagged-error fields.
- Host-safe `meta:setup` tests should force `PATH=/no-such-path`, isolated `LANDO_USER_*` roots, and `--provider=podman`; the default `lando` provider attempts a network bundle download.
- Manually verifying the `meta:setup` CA path needs real certificates: `defaultSetupNetworkTrustProbe` performs a live HTTPS probe whenever any CA material is configured and builds its TLS trust from exactly those files, so placeholder PEM text fails setup with `SetupNetworkTrustError` before any CA-related output renders. Generate throwaway roots (`openssl req -x509 -newkey rsa:2048 -nodes`) instead. Setup also reports only host-global CA configuration, never a certificate count: it runs before any app plan, so digest de-duplication, multi-certificate bundles, and per-service `security.inheritNetworkCa` opt-out are all still unresolved.
- Manual host-safe CLI verification runs `bun core/bin/lando.ts <command>` from inside the target app directory. `bun core/src/cli/index.ts <command>` exits 0 and prints nothing, so it silently looks like a passing command.
- `--renderer`/`--help`/`--version` are stripped before command dispatch; command-scoped unknown flags still need exit-2 rejection.
- Main-binary compilation must use `scripts/build-compiled-binary.ts`; its ESM bytecode format is required by OpenTUI's top-level await, and cross-target release builds need a frozen `bun install --os=* --cpu=*` first so every locked native optional package is present.
- Compare binary size and RSS with the same Bun compiler on both revisions, and record its version: even Bun patch releases can materially change bytecode size. Keep lazy Effect imports on concrete subpaths (`effect/Effect`, `effect/Schema`, etc.); a dynamic `import("effect")` retains unused modules in the binary.
- Topic/write-verb commands need **explicit canonical ids** in the registry (not greedy multi-token parsing). After registry edits, regen command-manifest + `codegen:schema-snapshot`.
- `--format` is stripped pre-parse and reinjected as `flags.format`; the real allow-list is `RESULT_FORMATS` in `core/src/cli/format-flags.ts`.
- `--json` is optional-valued; `-j` is not; bare `--json` lists keys and skips run.
- MCP projections for a mixed read/write umbrella command must replace the umbrella with constrained read specs and omit separately registered write-verb ids from the MCP registry.
- Tooling tasks reach the MCP catalog only through `lando mcp --tooling`; `--allow` validates against built-in ids and rejects an `app:<task>` id outright. Tooling uses the SDK `ToolingInputDeclaration` (ordered flags/args, `acceptsArguments`, derived `revision`). CLI supplies `ToolingInvocationInput.RawArgv`; MCP/event/library adapters preserve `NamedMaps` and carry the discovered `expectedInputRevision`, never serialize maps or pre-apply defaults. The invocation-authoritative target binds once after normal precedence and late client resolution, then lowers only for argv-only adapters (reject positional holes; false omits the positive switch). Scripts consume `ToolingInputValues` (`LANDO_INPUT` is exactly `{ flags, args }`), accept sparse named args, retain original numeric argv only for RawArgv calls, and inherit no full-task execution shape. Register explicit/name-derived sensitive values before admission failures or observable records; pre-admission snapshots without authoritative metadata stay value-free. Sensitive declarations forbid defaults/choices; no false opt-out. Missing/stale/invalid command metadata is `ToolingCommandUnavailableError`, repaired explicitly with `lando app:cache:refresh`, never live registry/planner fallback; retained MCP sessions require reconnection after refresh.
- Bundled plugin `setup.flags` merge from `core/src/cli/generated/setup-plugin-flags.ts` (regen: `codegen:setup-plugin-flags`) through the native CLI merger. Never import `core/src/plugins/generated/bundled.ts` from a command module (cold-start regression). Flag-name collisions surface as `SetupFlagCollisionError` from `core/src/plugins/setup-flags.ts`.
- Command topic descriptions live in `core/src/cli/command-topics.ts` and project into the generated command-registry manifest; cold-path root help reads only that embedded manifest.

## Engine operations tier

- App-lifecycle operations (`start`, `stop`, `restart`, `rebuild`, `destroy`, `exec`, `logs`, `info`, `config lint`, `remote`, `share`, `tooling`) live in `engine/src/operations/**`, not in command bodies. Core app shims and the CLI both consume them through `@lando/engine`; engine modules must never import the core shell (enforced by `bun run scripts/check-boundaries.ts package-dag`).
- `core/src/cli/commands/<op>.ts` (or its namespace-specific equivalent) holds only the `render*` functions for that command; result schemas belong with the operation because machine output is a contract, not shell.
- Operations may publish events but must not couple to `Renderer` or `InteractionService` beyond event publication. Optional renderer output and CLI result passthrough belong in private CLI helpers such as `core/src/cli/renderer-output.ts`; engine operation modules never import the core shell.
- `@lando/core/cli/operations` re-exports both halves, so a symbol moved between the operation and render module keeps the same public specifier; verify with `core/test/library/cli-operations-export.test.ts`.
- `lando init` has no engine operation and stays in `core/src/cli/commands/init.ts`: its body pulls in the entire `core/src/recipes/**` domain (catalog, builtin registry, manifest service, git/npm/tarball/registry sources, post-init runtime, prompt answer parsing) plus `core/src/interaction/**` (16 core-only imports at `core/src/cli/commands/init.ts:27-46`), and engine may never import the core shell. Extracting init means relocating the recipes domain first; re-evaluate once that domain has its own package seam.

## Runtime layer service wiring

- A plugins-tier layer that reads `PluginContributionGraph` via `Effect.serviceOption` must be piped `Layer.provide(Layer.merge(minimalRuntimeLayer, contributionGraphLayer))` in `renderPlugins()` (as `PluginRegistryLayer.layerWith` and `ConfigTranslatorRegistryLayer.layerWith` are); a bare `Layer.mergeAll` sibling sees `None` and silently falls back to bundled-only modules.
- `ConfigTranslatorRegistry` (plugins tier) reads translator loaders only inside `list`; never call it from help/version/loading/tooling paths. `app:config:translate` takes `translators` from options first, then `Effect.serviceOption(ConfigTranslatorRegistry)`, so tests inject fakes without a runtime and hosts below `plugins` see an empty list rather than a bootstrap failure.
- Adding a service layer to a generated bootstrap layer (`core/src/runtime/generated/layers/*.ts`) is two edits: the generator (`scripts/build-bootstrap-layers.ts` `renderApp()`/etc., then `bun run codegen:bootstrap-layers`) AND the hand-maintained runtime-service type union in `core/src/runtime/layer.ts` (e.g. `AppRuntimeServices`). Skip the type union and a command whose `R` now needs the service fails native dispatch typechecking because `runCompiledCommand` requires the effect's `R` to be a subtype of that union.
- `BuildOrchestrator.build(plan)` returns the plan with produced or cached artifact refs stamped into its services; callers must apply the returned plan, and artifact cache hits require a persisted ref.
- `lando app:cache:refresh` is the host-safe CLI surface that drives the full `AppPlanner` (and writes the binary app-plan cache) without starting a service or touching a container runtime; `app:config` only echoes the resolved Landofile, so planner-derived mounts and env need this command instead. `AppPlannerLayer.layer` reads its optional services (`CacheService`, `ConfigService`, `FileSystem`, `PathsService`, `CertificateAuthorityResolver`) at layer construction, so a test or driver must provide them to the layer, not to the effect that calls `plan()`.
- A command's bootstrap tier is the `LandoCommandSpec` `bootstrap` field alone: native dispatch (`run-built-in-command.ts`) builds the runtime from `cliRuntimeOptions({ bootstrap: entry.spec.bootstrap, ... })`, so an ordinary built-in has no second place to update. Only the retained native-only exceptions choose their runtime independently in an adapter and need both sites reviewed: `meta:setup`/`meta:shellenv`/`meta:uninstall` (`native-only-built-in-adapters.ts` → `cli-adapters/app-lifecycle.ts`, `cli-adapters/meta-plugin.ts`), `meta:mcp` (`run-built-in-command.ts` → `runMetaMcp`), and `meta:version` (`run.ts` → `runMetaVersion`). The shellenv and version adapters use `Layer.empty`, not a hard-coded bootstrap tier. `app:config:lint` runs at `plugins` because its shared event resolution needs `PluginRegistry`, which the `minimal` tier does not merge.
- Host `app:shell` uses the Bun Shell line REPL behind `ShellRunner.interactive`, not a raw system-shell child. Keep each line behind the host-shell evaluator, resolve secrets only when typed, and redact before output, events, or history; service mode remains provider-backed. `BunShellRunner.layerWithPrivateFileAccess` is wired into the `app` bootstrap layer.
- `check:deprecations` (in `bun run lint`) rejects a `BUILT_IN_COMMAND_DEPRECATIONS` notice whose `since` is not a released/pending version (`4.0.0`/`4.1.0`/`4.2.0`/`5.0.0`) or is >12 months old without a future-major/minor `removeIn`; use the most recent pending version (`4.2.0`) as `since` for a new default-flip notice.

## Host-proxy workers

- Bun subprocess `FileSink.write()` completion values are not partial-write offsets. Write each bounded chunk once, await `write`/`flush`, and await `end`; retrying from the returned value duplicates bytes.

## Machine-output gate

- `bun run scripts/check-boundaries.ts machine-output` runs the declarative rule (`scripts/boundary/rules/machine-output.ts`) as a TypeScript-AST gate over the full shared shipped-runtime tier, including `mcp/src`, with zero carve-outs. Canonical encoding lives outside that tier at `@lando/sdk/command-result`; every runtime consumer must use it instead of directly stringifying an envelope or result stream frame. The rule also flags core `LandoCommandSpec` literals missing a direct `resultSchema`.
- Live stream-as-you-go commands use `streamingMode: "live"` and read `StreamFrameSink` with `Effect.serviceOption`. The sink is optional: YAML runs collect output into their single result envelope. With a sink, the command emits chunks without also collecting them; the renderer boundary owns redaction and frame encoding, then emits the terminal result frame. If a live variant is derived by spreading a base command spec, leave the spread object type inferred rather than annotating it as `LandoCommandSpec`, or the `machine-output` rule will read it as a literal spec missing a direct `resultSchema`.
- Frame transport is a JSON concern, not a frame-schema one: a live run terminates in a result frame whenever the format is `json`, even when the spec declares no `streaming` schema, while `yaml` emits the envelope document alone. Gating that terminal emit on the declared schema breaks the frame sequence the run already started.
- `RendererOutput.layerStreamFrameSink` (renderer-boundary.ts) redacts through `RedactionService` on BOTH surfaces: the `--format json` branch redacts the encoded frame, and the TTY branch redacts the raw chunk before labeling. When a command streams user/file content (e.g. `app:logs` file sources), emit raw `LogChunk`s from the provider and let the sink redact — never redact mid-pipeline. Stream frames and `StreamFrameSinkFrame` carry an optional `source` for per-line provenance.

## Downloader / HttpClient

- `@lando/http-client/downloader` exports `layer` implementing the SDK `Downloader` contract over Effect's `HttpClient.HttpClient`; every byte comes from `HttpClientResponse.stream`. Its `download()` requirement stays `Scope.Scope` because the layer captures the client.
- Import the standard client from `effect/http/HttpClient`. `@lando/http-client` exports `layer` and `layerWith({ fetch, systemCaPems, direct })`, not an SDK-owned tag. Set `RequestPolicy` with `Effect.provideService` for Lando-only fields (`callerId`, `onBehalfOf`, `redactionTokens`, `allowFileSource`, `offline`, `redirect`). The requesting fiber supplies trust and policy. Pre/post events and spans redact sensitive URLs. Proxy/CA/NO_PROXY resolution remains pure in `@lando/sdk/network-trust`; `@lando/http-client/network-trust` re-exports it and owns `NetworkTrust` injection.
- Bun `tls.ca` replaces the default store: `trustHost: true` merges system and custom PEMs, while `trustHost: false` uses only custom PEMs. Inject deterministic roots with `layerWith({ systemCaPems: () => [] })`; production uses cached `defaultSystemCaPems` from the network-trust seam.
- The `network` boundary rule excludes only `http-client/src/**`. It rejects direct global fetch calls and imports of `effect/http/FetchHttpClient` or named `FetchHttpClient` from `effect/http` elsewhere. Object-method fetch calls, injected aliases, and bare references are not direct-fetch calls. Plain-async JSON consumers use `httpJsonFetch` in `engine/src/services/json-fetch.ts`; Effect callers use response `.json`, `.text`, or `.stream`. Apply `Effect.timeout` around the whole request/body operation instead of a request timeout field.
- Reuse `@lando/sdk/verified-stream` for stream -> hash -> temp -> atomic rename; do not add another checksum/temp-file implementation.
- Trust resolves from `ConfigService` per request, not at layer construction. Provide it where egress runs; injected `NetworkTrust` takes precedence. Downloader permits only HTTPS or explicitly allowed local files. A fixture server must serve HTTPS with its CA in `LANDO_NETWORK_CA_CERTS`.
- Bootstrap wiring provides the HTTP client and EventService to `VerifiedDownloader.layer`. Edit `scripts/bootstrap-layer-renderers.ts` / `scripts/build-bootstrap-layers.ts` and run `codegen:bootstrap-layers`; never hand-edit generated layers.
- Downloader progress/redaction/egress-fence contracts are implemented through the SDK contract suite; memory downloads return verified metadata without raw bytes.

## Doctor subsystems

- `subsystemDoctor` inspects provided runtime services; missing services become report-level `skipped` entries. Host DNS is independent: `host-proxy` runs with `HostDnsResolver` even without `HostProxyService`, using the canonical host-proxy loopback default and reporting DNS observations only. Healthcheck/scanner are skipped because doctor executes neither service probes nor endpoint scans; runner ids are not evidence of readiness. `doctorReport()` skips the subsystem section only when neither runtime services nor a DNS resolver are supplied. `resilientDoctorReport` supplies host DNS even after provider-bootstrap failure (but not invalid global config), never a fabricated default subsystem graph. Proxy readiness includes `status().state === "running"`; a selected-but-stopped proxy is recoverable via `--fix`. Readiness/build gates construct healthcheck runners from the selected provider directly.
- Traefik doctor display name is `router` (`PROXY_SPEC.name`). Setup step id stays `proxy` and the flag stays `--skip-proxy`. Do not rename `HostProxyService` / `--host-proxy` with the ingress tag.
- A guide id is global: fixtures resolve from `docs/guides/<id>/fixtures` for every guide with that id, and generated scenarios land in `test/scenarios/generated/guides/<id>/`. A new `recipes/<id>/README.mdx` collides with any same-id `docs/guides/<id>.mdx`; the recipe README keeps the id because `build-recipe-readmes.ts` derives its `.scaffold/` output from frontmatter, so re-id the docs-only guide.
- The restricted `parseRecipeYaml` reads a bare `config:` key as `{}`; `Bun.YAML.parse` reads it as `null`, so parse recipe fixtures through `parseRecipeYaml` in tests.
