# Config translation progress

## Codebase Patterns
- Spec-class stories edit `spec/01..19-*.md` + `spec/README.md`; cross-refs use `§N.N` numbers (README topic lookup maps `§N` to file). Core spec text must state durable detail itself and never cite story ids or the PRD subdirectories.
- Gates for spec-only work: `bun run spec/config-translation/check-coordinated-plan.mjs` (omit `--initial` once any story passes), `bun run check:boundaries`, `bun run lint`, plus a grep scan for forbidden tokens (`ConfigFormat`, `LANDO_MOUNT`, `!lando3`, `LANDO_INFO`, `US-6xx`) and no new em-dashes in added lines.
- The plan checker only scans the three PRD directories for stale story refs and forbidden strings; the core spec files are covered by the grep scan, not the script.
- Parallel spec editing works well when partitioned by file (no two editors on one file); README topic rows go last because they cite final headings.
- Frozen naming contract for later stories: translators `lando4` / `recipe` / `lando3` (decode-only); inputs `landofile-document-set` / `recipe-request`; diagnostics `generated | dropped | rewritten | unsupported | non-portable | needs-review`; transaction states `prepared | committing | committed | blocked`; artifacts `<file>.bak.<full-before-sha256>` and `<target>.lando-stage.<transaction-id>`; secret dispositions `secret-store` or one `postInit.stdin` / `postInit.secretEnv.<name>` sink; commands `app:config:translate --to`, `app:config:explain`, `app:config:migrate`; events `pre-restart` / `post-restart`; doctor checks `lando3-leftovers` / `lando3-shadow`; binary `lando4` / `lando4.exe` during Alpha/Beta.
- Managed-file transactions keep the StateStore journal bucket unlocked (`lock: "none"`) while one scoped canonical-root lock covers every journal transition and filesystem mutation; transaction locks must not expire a valid live owner, but old malformed owner-owned locks remain reclaimable.
- A Landofile value site may legitimately hold an expression the loader cannot resolve yet. Scopes still deferred at load time are shared through `LOAD_DEFERRED_EXPRESSION_SCOPES` in `landofile/src/recipe-expressions.ts`; the raw content scanner and `resolveLandofileLoadExpressions` must agree on that one list or a value passes one gate and dies at the other. `LOAD_RESOLVABLE_EXPRESSION_SCOPES` in the same module names the subset the loader resolves itself (`recipe`, `env`); the rest belong to the planner. Scope membership alone is not enough: `expressionTouchesOnlyScopes` also requires every callee to be a pure helper, derived from the evaluator's own table, so host-reaching helpers stay loudly unsupported.
- Resolution that reads merged file data belongs after `mergeLandofiles` and before `rejectComposeKeys`/`validateLandofile` in `loadLandofileLayers`. Per-layer validation still runs first, so a deferred expression must sit at a site whose per-file schema accepts a plain string.

Publication was blocked first by the loop's story-id pattern (`609e0` did not match) and then by an upstream `snapshot.ubuntu.com` outage on PR #926.

**US-609E1–E6** converted all 24 bundled recipes to decomposers plus current snapshots, family by family (PHP web, PHP CMS, Node apps, Node frontend, Python/Ruby, static/utility). Each batch published replacements and kept the existing `render.ts` bindings active: decomposer Landofiles carry `{{ recipe.<option> }}`, and the native load path still raised `NotImplementedError`, which would have broken `lando start`. Provider-free init byte-parity against `origin/main` was the batch gate. Missing recipe guides were authored as they went. After E6 the decomposer catalog equals the renderer registry.

Learnings that still matter:

- A new `plugins/*` package needs four registrations beyond its own files: root `tsconfig.json` reference, `WORKSPACE_EDGE_TABLE`, `core/build.config.ts` ship list, and `bun install`.
- Recipe manifests are a restricted YAML parser (no inline mappings, naive quotes). Snapshots serialize as block YAML; large literals go through `b64decode`. `extends:` children must keep `snapshot` / `migrations` as whole-value replacements.
- Snapshot templates read `options.<name>`; Landofile authoring reads `recipe.<name>`. Do not swap the heads. A structural toggle belongs in the decomposer and one snapshot `Conditional`; option text stays a `{{ recipe.<option> }}` token.
- Do not activate decomposers until the load path can resolve recipe/env (and mixed shell) sites. That gap had no owning story until the US-609E7/E8 split below.
- The derived authoring shape currently accepts `{}`, so "complete authoring" validation is vacuous until the schema derivation is fixed.
- `lando4ConfigTranslator.encode` returns `{ text, diagnostics }` and wants a complete `{ context, fragment }`. Verify emitted Landofiles with `parseLandofile`, not `Bun.YAML.parse` (`packageName: @lando/recipe-<id>` is a reserved YAML indicator).
- Auxiliary `files:` on the private pipeline fail closed on a relative `src`; bundled bytes need an in-memory content-source port (US-609E7).
- `check:codegen-drift` fails on untracked or merely staged generator output; commit it with the change that caused it.
- `bun test <path>` is a filter. Assert `EXIT=0` and a positive test count; a misspelled path exits nonzero with `did not match any test files`.

## 2026-09-09 17:05 - US-609E7

Completed the cutover enabler. The native load path now resolves both loader-owned scopes, and the private init pipeline can write auxiliary scaffold assets that exist only in memory.

Root cause of the env gap was not the deferred-scope list: `expressionTouchesOnlyScopes` returned false for every `Call` and `Conditional`, so node-ts's `{{ default(env.LANDO_NODE_VERSION, 'lts') }}` could never be deferred. The SDK predicate now separates context scopes (path heads) from callees (helper names) and answers "analyzable, scopes subset of allowed, callees all pure". Pure callees come from the evaluator's own helper table.

The materializer generalized from recipe-only to both loader-owned scopes: it parses every `{{` site, resolves when the site reads only `recipe`/`env`, and leaves a site that also reads `app` or `proxy` untouched as a whole. Failure names the exact value path and distinguishes a missing recipe option from an unset environment variable with no `default()`. The env scope is a string-filtered snapshot of the process environment, built once in the landofile package.

Init pipeline gained a content-source port: in-memory bytes no longer need an absolute `src`, `template: true` entries render before the secret check, and bundled source over existing scaffold constants is byte-identical to the still-bound renderers for mean, node-postgres, and rails. The pipeline also stops treating a manifest's own Landofile entry as an auxiliary file.

Real surface: `app:config --format=json` on a Landofile carrying all four scopes returned `node:22`/`NODE_ENV: production` with the variables set, `node:lts`/`development` with them unset, `API_FRAMEWORK: express` from merged provenance, and left the route hostname literal for the planner.

Review: load-time recipe/env evaluation now carries a bounded `EvaluationBudget`; provenance-skip and budget failures are tested; expressions.mdx names load-time recipe/env instead of claiming those sites are still blocked.

Learnings:

- Scopes and callees are different axes: `env` is a path head, `load` is a capability. Derive the pure-helper set from `HELPERS`; the parser desugars `==`/`</`>` into helper calls.
- `${VAR}` never reaches the expression walk: `CONFIG_EXPRESSION_PATTERN` rejects it before any parse.
- Every bundled manifest declares its own Landofile in `files:`. Filter Landofile-layer destinations explicitly or node-ts writes a second dialect.
- Auxiliary `template: true` rendering stays a literal `{{ app.name }}` replacement. Key any content source by `dest`, not manifest `src`.
- Once Call nodes can defer at load, pass an `EvaluationBudget` or a typo'd `range()` allocates before schema validation.

## 2026-09-09 19:55 - US-609E8

Unblocked the last loader gap. The PRD premise was wrong: composite interpolation already worked (`type: "php:{{ recipe.php }}"` has loaded since E7). What rejected drupal was `ShellParamSegment` — the expression parser claims bare `$name`, and the scope predicate reported any template containing one as unanalyzable, so drupal's ~90 shell variables poisoned the single option reference sitting among them.

`@lando/sdk/expressions` now publishes `expressionInterpolationsTouchOnlyScopes`, which judges only the `{{ ... }}` interpolations and treats shell and secret text as inert. The strict `expressionTouchesOnlyScopes` is unchanged, because the evaluator resolves `$name` from `env` and would silently blank every variable in a shell script. The three load-path gates moved to the new predicate, and the materializer replays bare shell parameters as literal text.

Braced forms stay fail-closed with a source-level guard: `${VAR}` and `$VAR` parse to the same segment, and the raw pre-parse scan that rejects `${` is skipped for files containing `load(` / `import(` (and for `.lando.ts`).

Real surface: compiled `app:config --format=json` on the decomposed drupal Landofile exits 0, reports `recommended-project:^11` inside the scaffold command with every `$target` / `$staging_root` / `$(ls -A ...)` intact, resolves `php:8.3` and `mariadb:11.4`, and keeps the route hostname literal.

Review: load-path braced-form detection now ignores the parser's `$${` escape on scan-skipped files while still rejecting unescaped `${VAR}` / `${secret:...}`.

Learnings:

- Verify a suspected expression gap by parsing the actual failing scalar. Two adjudications named "composite interpolation"; the parse showed composite was fine and the shell segments were the whole story.
- The pre-parse scan is skippable. Put the guard where the value is actually handled.
- Only `$` immediately followed by an identifier start becomes a shell segment. `$$`, `$1`, and `$(cmd)` are ordinary literal text.
- Follow-up (not this story): event-invoked tooling re-evaluates string `cmd` / `cmds[]` through the generic evaluator and blanks `$name`; direct tooling hands the command to `sh -c` untouched. An additive `ParseExpressionOptions` bare-parameter mode plus a shell-source site classifier is the shape to reach for.

## 2026-09-10 10:38 - US-611B

Shipped `lando app:config:migrate`. It resolves a chain between the recorded and target versioned producer identities, walks each edge against an in-memory prospective document plus option map, classifies every stable hunk id as `already-satisfied` / `selected` / `retained-option` / `blocking`, and commits only the longest fully satisfied edge prefix through the shared managed-file transaction. `--dry-run` prints the complete ordered hunk set and calls none of the coordinator; `--yes` selects untouched hunks; default interactive asks once per selectable hunk; non-interactive without `--yes` fails closed.

**Rendering the old snapshot is what makes classification possible.** A managed site holds `{{ recipe.<option> }}`, which never deep-equals a hunk's `old` value. The engine resolves a managed site's `current` from the rendered *old* snapshot at the canonical path. Selected structural edits write the managed expression form, never the resolved literal.

`classifyHunk` cannot classify a `rename`: those fields are canonical path strings. Core owns rename classification and updates `recipe.services` plus every managed `dependsOn`, tooling, and expression reference atomically or blocks the whole edge. Higher-layer ownership is a layer check, not a filesystem walk. Shared raw-Landofile helpers moved out of explain into `app-config-recipe-analysis.ts`.

Real surface: compiled CLI on a throwaway lamp app returned `already-current` for migrate, `--dry-run`, and space-separated `app config migrate --dry-run`, with an identical `.lando.yml` SHA-256 before and after.

Review: dry-run now inspects `pending` without locking; rename already-satisfied requires the rendered after-state (later: every managed reference, not just a present target key); route/event `service` fields rewrite via segment walks; hunk-snapshot mismatch blocks bad option-default/remove declarations; guide `<Verify file>` paths use the UseFixture subdirectory.

Learnings:

- No bundled recipe publishes `migrations:` yet, so bundled runs honestly report `already-current`. Drive real multi-edge chains from `core/test/cli/fixtures/recipe-migrations.ts`.
- A `decide` callback for a pure engine can still be interactive: enumerate selectable hunks with a recording pass, prompt, then re-run with the recorded answers.
- `<UseFixture name="x">` copies to `<testDir>/x` and chdirs there; `<Verify file>` is resolved from `testDir`, so the path must be `x/.lando.yml`.
