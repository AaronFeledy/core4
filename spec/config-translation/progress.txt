# Config translation progress

## Codebase Patterns
- Spec-class stories edit `spec/01..19-*.md` + `spec/README.md`; cross-refs use `§N.N` numbers (README topic lookup maps `§N` to file). Core spec text must state durable detail itself and never cite story ids or the PRD subdirectories.
- Gates for spec-only work: `bun run spec/config-translation/check-coordinated-plan.mjs` (omit `--initial` once any story passes), `bun run check:boundaries`, `bun run lint`, plus a grep scan for forbidden tokens (`ConfigFormat`, `LANDO_MOUNT`, `!lando3`, `LANDO_INFO`, `US-6xx`) and no new em-dashes in added lines.
- The plan checker only scans the three PRD directories for stale story refs and forbidden strings; the core spec files are covered by the grep scan, not the script.
- Parallel spec editing works well when partitioned by file (no two editors on one file); README topic rows go last because they cite final headings.
- Frozen naming contract for later stories: translators `lando4` / `recipe` / `lando3` (decode-only); inputs `landofile-document-set` / `recipe-request`; diagnostics `generated | dropped | rewritten | unsupported | non-portable | needs-review`; transaction states `prepared | committing | committed | blocked`; artifacts `<file>.bak.<full-before-sha256>` and `<target>.lando-stage.<transaction-id>`; secret dispositions `secret-store` or one `postInit.stdin` / `postInit.secretEnv.<name>` sink; commands `app:config:translate --to`, `app:config:explain`, `app:config:migrate`; events `pre-restart` / `post-restart`; doctor checks `lando3-leftovers` / `lando3-shadow`; binary `lando4` / `lando4.exe` during Alpha/Beta.
- Managed-file transactions keep the StateStore journal bucket unlocked (`lock: "none"`) while one scoped canonical-root lock covers every journal transition and filesystem mutation; transaction locks must not expire a valid live owner, but old malformed owner-owned locks remain reclaimable.
- A Landofile value site may legitimately hold an expression the loader cannot resolve yet. Scopes still deferred at load time are shared through `LOAD_DEFERRED_EXPRESSION_SCOPES` in `landofile/src/recipe-expressions.ts`; the raw content scanner and `resolveLandofileLoadExpressions` must agree on that one list or a value passes one gate and dies at the other. `LOAD_RESOLVABLE_EXPRESSION_SCOPES` in the same module names the subset the loader resolves itself (`recipe`, `env`); the rest belong to the planner. Scope membership alone is not enough: `expressionTouchesOnlyScopes` also requires every callee to be a pure helper, derived from the evaluator's own table, so host-reaching helpers stay loudly unsupported.
- Resolution that reads merged file data belongs after `mergeLandofiles` and before `rejectComposeKeys`/`validateLandofile` in `loadLandofileLayers`. Per-layer validation still runs first, so a deferred expression must sit at a site whose per-file schema accepts a plain string.

## 2026-09-07 11:35 - US-608D
- Added journal recovery to `@lando/managed-file`: a new `blocked` terminal journal state, a preflight that classifies every entry against the complete recorded before/after plan (containment, symlink, link count, absence, digest, mode, immutable backup, and exclusive owner-only stage), and a roll-forward recovery that mutates only unapplied entries. A conflict marks the journal `blocked`, preserves every user file byte for byte, and demands manual resolution instead of overwriting forward or rolling back over an edit.
- Handled the crash window between a stage rename and its chmod as its own `applied-needs-mode` disposition, so a target that already carries the recorded after digest at the stage's owner-only mode gets its intended output mode completed rather than being misread as a conflict. Applied writes must additionally still be the renamed stage inode with no stage left behind; originally absent creations and removals classify from presence.
- Recovery of a `committed` journal performs cleanup only: it never inspects or restores targets or backups, removes stages only when identity *and* digest still prove ownership (`removeRecordedStage` replaces the identity-only removal used everywhere), and then removes the journal.
