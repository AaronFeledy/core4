# IR gaps progress

Append one entry per step. This file is the narrative record; `git log` is the
file-level record. An entry says what changed about the **product** and what it
**cost** — never which files were touched, and never a restatement of the entry
above it.

**Belongs here:** what a story actually changed for a user; defects found and
where they were found; what a gate or QA pass caught that the suites did not;
work deliberately deferred, with the reason; anything a future agent would
otherwise rediscover the hard way.

**Does not belong here:** file lists, line counts, formatting or comment-only
changes, a sync step echoing the step before it, or a gate reporting that it
skipped. Entry shapes in use are Build (what shipped + verification +
learnings), Review (blockers fixed, deferrals with reasons), Verify (real-binary
evidence, out-of-scope findings), and Babysit (PR, CI outcome, review feedback,
merge). Drift Audit is a fifth shape — trigger, weakened proofs, ceremony,
fixes — but its gate has been failing since roughly US-631, so no real audit
entry appears after US-637. That is queued as US-656.

## Codebase Patterns
- A real `RuntimeProvider` comes only from `RuntimeProviderRegistry.select(plan)` (the `RuntimeProvider` tag is a capability-less stub), `select` resolves by `plan.provider`, and the global app is always pinned to the Lando-managed provider.
- A fail-closed planner default lands its blast radius in FIXTURES, not source. Measure before implementing: `bun --no-orphans test --path-ignore-patterns='**/*.integration.test.ts' <pkg>/test` per package. Raw `bun test <dir>` pulls in `*.integration.test.ts`, which fail with `ProviderUnavailableError` on a host with no runtime and mask the real count.
- Adding one member to a plan-carrying error union touches ~16 unions. Insert it ONCE per union: a second copy is type-identical (`A | A = A`) so nothing fails, and it silently pads line counts and the frozen SDK signature string. Many of those files hold TWO unions (an exported `XError` alias plus an inline channel); both need the member, so a blind dedupe breaks the alias.
- An SDK error-union change is a three-file commit: the union, `sdk/test/fixtures/sdk-mvp-surface.json` (frozen service-tag signature), and `sdk/API_COMPATIBILITY.md` (additive exports). New exported primitives must be listed in the latter or `sdk-backward-compatibility.test.ts` fails.
- Build-step identity is resolved ONCE in `servicePlanExtensionsFromDraft` (`engine/src/planner/extensions.ts`), the only point where the final composed `draft.user` and the complete step list (authored plus feature-contributed) meet. Resolve anything that depends on the final planned user there, never in `authored.ts`.
- Widening a public Landofile union needs a `sdk/compatibility-exceptions.json` row per affected surface (keyed surface + changeKind + path); one union change fans out to every schema and command surface that embeds `ServiceConfigInput`.
- Type planner helpers with the exported schema types, not re-spelled structural shapes: `Schema.optional(X)` produces `k?: T | undefined`, which `exactOptionalPropertyTypes` rejects against a hand-written `k?: T`.
- Tooling metadata normalizes ONCE via `normalizeToolingTask` in `@lando/landofile/tooling-normalize`; every consumer (command cache, CLI help, machine index, MCP, execution) reads that IR instead of re-deriving from the authored `ToolingTaskShape`. Argv validation lives beside it in `@lando/landofile/tooling-input` so CLI and MCP share one validation path and emit identical error tags.
- Adding a publicly registered schema needs THREE edits, not one: the schema itself, `JSON_SCHEMA_REGISTRY` in `sdk/src/schema/json-schema.ts`, and a fixture row in `sdk/test/schema/public-schema-contracts.ts`. Missing the third fails `codegen:schema-snapshot` with "Public schema contract fixture list does not match JSON_SCHEMA_NAMES".
- Widening a Landofile value type ripples into expression resolution: `engine/src/tooling/step-runner.ts` walks the same shape and must handle every new union member, and `Effect.forEach` over a heterogeneous union needs an explicit callback return annotation under `exactOptionalPropertyTypes`.
- A hand-built `AppPlan` in a live test needs `stores` populated from each service plan's `storage`, or `bringDown({ volumes: true })` has nothing to remove and every run leaks its named data volume. `removeAppScopedVolumes` iterates `plan.stores`; the label-based prune does not cover a store the plan never declared.
- `bringUp` never pulls an image. A live test that introduces a new image must also add it to the pre-pull list in `scripts/build-ci-workflow.ts` and regenerate `.github/workflows/ci.yml`, or CI fails with `no such image` instead of a useful assertion.
- `check:guide-coverage` only scans PRDs listed in `docs/guides/prd-sources.json`. A PRD outside that list needs no `docs/guides/INDEX.md` row, so do not add one speculatively.
- Guide fixtures resolve from `docs/guides/<frontmatter-id>/fixtures/<name>/`, never from the MDX's own subdirectory.
- A non-zero exit from a tooling command is a RESULT, not an Effect failure: `runTooling` stops at the first non-zero step and returns the accumulated streams carrying that exit code, and the CLI maps it through `successExitCode`. Reserve tagged failures for compile, input, and disabled errors so CLI, MCP, and library surfaces stay uniform.
- Adding a member to a planner error channel is repo-wide: grep `| CommandAliasConflictError` to find every plan-carrying union across `sdk/src/app`, `sdk/src/services`, `engine/src/operations`, and `core/src/cli/commands`, and patch them in one pass.
- `engine` and `core` typecheck against `sdk/dist`, not `sdk/src`. After an SDK type change run `bun run --filter='@lando/sdk' build`, or TS reports "Two different types with this name exist, but they are unrelated".
- Pattern-validated schemas (`ContainerUser`, `AbsoluteContainerPath`) are NOT branded, so their `.Type` is plain `string` and declaration sites need no `.make()`. Brand only when call sites should be forced through a constructor.
- Removing or widening a public schema property needs an entry in `sdk/compatibility-exceptions.json` keyed by surface + changeKind + path with a justification. `check:schema-compatibility` is its own gate; typecheck, lint, and the test suites all stay green while it fails.
- A new `services.<name>.*` key must clear two gates, not one: the Effect schema, and `SERVICE_CONFIG_KEYS` in `landofile/src/service.ts`, which is derived from `Object.keys(ServiceConfig.fields)` and rejects everything else as an "unsupported MVP key". Decoding an unknown service key silently DROPS it and looks like success, so only a real CLI run proves the key is accepted.
- A scoped provider apply must persist the full app plan with the newly built selected service definitions overlaid. Remembering only the subplan loses unrelated services; remembering the original full plan loses newly stamped artifact references.
- Service features are filesystem-free by type: `apply` is `(ctx) => Effect<void, ServiceFeatureError>` with no requirements channel. Anything needing `stat`/`readdir`/realpath belongs in the planner (see certs), leaving the feature the pure `resolveBindSource` join.
- Export container mount destinations as `PortablePath.make(...)` constants. A bare string constant typechecks at the `addMount` call site but fails every whole-`MountPlan` `toEqual`/`toContainEqual` assertion, because `target` is branded.
- The guide harness fakes `lando start`: `runScenarioLayerCommand` in `core/src/testing/scenario-context.ts` returns a canned `ready` / exit 0 before the real CLI runs, and only one hardcoded landofile substring makes it exit non-zero. A guide scenario that must prove a planner or validation rejection has to run a command that falls through to `invokeRealCli`, such as `lando app:cache:refresh`.
- Service-type config rejections belong in `ServiceType.resolve`, not in the feature. `engine/src/services/feature.ts` decodes `feature.definition.schema` against the feature REF config, never against the service config, so a feature schema cannot see `services.<name>.*` keys. `ServiceType.schema` is catalog metadata that nothing decodes. `assemble.ts` maps a resolve failure through `servicePlanError`, so the plugin's `ServiceTypeError` message becomes the user-visible `LandofileValidationError` body: lead that message with the exact key path (`services.<name>.<key>[<i>]`) because `issues` stays at service granularity.
- One resolution prefix, many surfaces: `resolveKnownEventSet` (`engine/src/planner/event-set.ts`) is the provider-free prefix of `planApp` — provider precedence, plugin manifests, per-service seeds through `ServiceType.resolve`, effective tooling, and the valid event set. Lint, doctor, and start all call it, and `planApp` consumes the seeds it returns instead of re-resolving, so a service still resolves exactly once per plan.
- Internal-task exclusion rides a WeakMap keyed on object identity (`tooling-include-provenance`). Nothing between `compileEffectiveTooling` and `validEventNames` may spread, clone, or re-sort the tooling map; `compileEffectiveTooling` already sorts, so `attachEffectiveTooling` must store the object it was handed.
- A `ServiceType.resolve` that reads `input.capabilities` must treat `undefined` as "not asked", not as "unsupported". Provider-free surfaces pass no capabilities, so a bare `input.capabilities?.x !== true` check fails a service that `lando start` accepts.
- One Compose serializer, many providers: `renderCompose`/`emitCompose` live only in `container-runtime/src/podman/compose.ts`; each provider exports a thin adapter that injects its own `ProviderErrorContext` and delegates. Values always go through `quoteYamlScalar` from `@lando/sdk/yaml`; every dynamic mapping key goes through `yamlMappingKeyText`, which emits a plain key only when an allowlist accepts it and YAML cannot re-resolve it.
- A generated default `command` runs as the service's planned `user:`: the feature that emits the command also calls `ctx.setUser`, so any launcher that writes a config file at start fails for a non-root user. Prefer directives the daemon accepts on its command line. Compose knobs are not an escape hatch — `findUnsupportedComposeKnob` fails closed when the active provider declares no `composeKnobs`, and `@lando/provider-docker` declares none.
- `check:schema-compatibility` reads the WORKING side from the gitignored derived tree (`core/dist/schemas`), which goes stale the moment you merge main. A schema that main added but your local dist predates reports as `BREAKING surface-removed` for a surface your branch never touched. Run `bun run codegen:schema-snapshot` before believing a breaking row, and cross-check the PR's `schema-snapshot` job.
- Prove a "did not happen" claim with `spyOn` plus `not.toHaveBeenCalled()`, never a wall-clock threshold; Bun's `spyOn` calls through, so behavior stays real while the count becomes deterministic. To fixture a socket that exists but refuses connection, listen on a temp path, hard-link the socket inode elsewhere, then close the server: Node unlinks the listening path, the link survives with nothing behind it.
- Manual CLI QA on the real binary catches what green suites do not; it found the only two defects in US-613 and the one in US-633 after hundreds of passing tests. `bun core/src/cli/index.ts` exits 0 silently — `core/bin/lando.ts` is the only faithful source entry, and the compiled `core/dist/lando` is a third behavior worth checking separately when a story touches argv or dispatch.
- Compiled-CLI behavior diverges from source. US-629 passed every source-level spot check and then failed CI on compiled teardown, aliases, and flag parsing. A story that changes dispatch, argv, or bootstrap tiers proves itself on the compiled binary too.
- Raising a command's bootstrap tier is two edits, not one: the `LandoCommandSpec` `bootstrap` field and the `cliRuntimeOptions({ bootstrap })` call in the compiled adapter. Only the second governs the real binary, and a mismatch typechecks.
- Establish a failure baseline in a detached `git worktree` of `origin/main` before triaging a red suite. It needs its own `bun install` and `bun run codegen`; symlinking the branch's `node_modules` resolves `@lando/*` back to branch source and produces a useless comparison.
- The spec-reference boundary rule reads a bare `spec/...` path argument as a citation of the specification tree, so `resolve(cliRoot, "spec/x.ts")` fails even though it means `core/src/cli/spec`. Spell such paths relatively (`"./spec/x.ts"`); a separate AST check also rejects a bare `"spec"` path segment argument.
- Parallel codegen waves are only safe when every entry that imports a generated file declares `dependsOn` for its generator. `Bun.write` is not atomic, so a reader can observe a truncated file. It surfaces first on the slowest runner and looks like a flake.
- `RuntimeProviderShape` is declared TWICE: in `sdk/src/services/provider.ts` and again in `sdk/src/services/index.ts`, where the local declaration shadows the `export *`. A contract change must edit both or consumers keep the old shape while the file that looks canonical is already correct.
- A provider-contract signature change lands in ~45 files at once, because every scenario test builds its own provider literal instead of spreading `TestRuntimeProvider`. Change the contract, then sweep by directory; `bun run typecheck` is the only honest list of what is left.
- Apache `Listen` is additive and `-c` directives are read after the configuration tree, so no generated directive can withdraw the image's own `Listen 80`. Moving the listener means deleting that line during the image build; emitting a directive alone opens a second socket. Prove which one you produced by reading the container's listening sockets, not by a successful request on the new port.

## 2026-09-19 03:00 - US-645

Machine output is now durable in both directions a program consumes it.

- A downstream consumer that closes the pipe early ends output cleanly on every renderer write path. `@lando/renderer/io` guards each stdio write, catching the synchronous EPIPE and consuming the asynchronous stream `error` event, then marks that stream instance broken so later writes to it are silent no-ops while the other stream keeps working. An explicitly installed exit policy sets 141 on the first broken pipe and re-asserts it from a one-shot exit listener, so the terminated-pipeline status survives a later failure assigning 1. Detection lives in the renderer; policy is installed by core only on the real-process path, so tests with injected streams never poison the runner's exit code.
- A command whose stdout dies is now interrupted rather than left writing into a dead pipe: the boundary races the command against a broken-pipe signal, so an unbounded producer terminates while its Scope finalizers still run. That interruption renders nothing and sets no failure code, because the consumer is gone and the exit policy already owns the status. SIGINT suppression is untouched.
- One YAML scalar and key quoting policy now lives on the public `@lando/sdk/yaml` subpath and serves every emitter. The Compose exporter's private `scalar`/`mappingKey` pair and the CLI config command's unquoted `formatYaml` are both deleted; `emitLandofileYaml` routes its string values through the same policy while keeping its stricter key rule, since its round-trip target is also the Landofile subset parser. A general `emitYamlDocument` handles the config command's scalar, array, and record roots.
- The policy is fail-closed against what a YAML 1.2 core loader re-resolves: case-insensitive bool/null spellings, `~`, every int and float spelling including hex, octal, exponent, leading-zero and signed forms, `.inf`/`.nan`, a trailing `:`, and the standalone indicator strings. The character shape is unchanged from the previous emitter, so `8080:80` and `:host` stay plain and no committed fixture churned.
- The Landofile parser now unescapes the full JSON escape set in double-quoted scalars, which is what lets a control character survive the emit-then-parse round trip.

Verification: gate:pr passed (typecheck, lint, codegen drift, all thirteen boundary rules, guide-drift). Focused suites green: renderer 70, sdk yaml 10, sdk landofile 105, sdk export/compat 45, compose 24, core broken-pipe 6, core config round trip 4, doctor and app-config surfaces 37. The JSON scripting guide passes 3/3. Manual CLI QA on the real binary: a closed stdout exits 141 with zero bytes on stderr on both the renderer and cold paths, a fully consumed pipe still exits 0 with identical bytes, a failing text-format command with closed stderr exits 141, `config --format=yaml` deep-equals the JSON result, and `app:config --format=yaml` quotes `True`, `~`, `1e5`, `0x10`, `+5`, `.inf`, `-`, `foo:`, `a: b`, `*anchor`, and `[redacted]` while leaving `8080:80` and `:host` plain.

- **Learnings for future iterations:**
  - Prove a YAML quoting policy against a real loader, not against intuition. Bun follows YAML 1.2 core, so `yes`/`no`/`on`/`off`/`y`/`n` stay strings while `True`, `0x10`, `1e5`, `+5`, `007`, and `~` do not; a policy written from the YAML 1.1 folklore over-quotes the first group and still corrupts the second. Measure with `Bun.YAML.parse` before choosing the rejection set.
  - A closed-pipe guard that only swallows the error converts a crash into a hang: an unbounded producer keeps writing into a dead stream forever. Swallowing must be paired with interrupting the command.
  - `Effect.interruptWhen` does not exist in the pinned Effect version; `Effect.raceFirst` against an `Effect.async` signal gives the same result and still waits for the loser's finalizers.
  - `process.once("exit", () => { process.exitCode = 141 })` is honored by Bun and survives a later assignment, which is how a terminated-pipeline status stays sticky across a failure path that sets 1.
  - Construct a closed-pipe repro with a consumer that exits before the writer starts (`| head -n 0`); `| head -n 1` is buffer-size dependent and produces flaky tests.
  - In JSON mode the failure envelope goes to stdout, so closing stderr on a `--format=json` command proves nothing. Exercise the stderr path with a text-format failure.

## 2026-09-19 06:45 - US-646

A tooling task's declared positional arguments now keep their own identity in both directions, on the CLI and through MCP.

- Positional slots resolve by declaration index and are never compacted. `serializeToolingInput` used to drop every absent positional with `flatMap` while `parseToolingArgv` read them back by index, so a declaration with two optional positionals and a caller naming only the second serialized to `["--", "<second>"]` and rebound that value to the first name. The parser carried the same defect on its own canonical argv: an optional argument with no default followed by one with a default emitted a single token that re-parsed into the wrong slot.
- Both halves now share one slot resolver and one error constructor. A slot is the supplied value, else the declared default, else a hole. Trailing holes are dropped — the serializer stops at the last *supplied* value, so a trailing default is still applied by the parser instead of being baked into argv, which is what keeps the existing MCP projections byte-identical. A hole below the last filled slot cannot be written into a command line at all, so both surfaces refuse with `ToolingInputError` naming that argument rather than binding the value to the wrong name.
- Rejection is at invocation time, not normalization, so a declaration that is expressible for some inputs stays valid. That also avoids a real failure mode: normalization errors are thrown synchronously by the command compiler and swallowed by the command registry, so a declaration-time rejection would make the task vanish from the MCP catalog instead of producing an input error.
- `serializeToolingInput` returns an `Either` and carries the task name and source, so the MCP projection and the event `command:` target both fail the run rather than handing a mis-bound argv to the engine. Its passthrough field is now `passthroughArgv`, because `ToolingInputValues.argv` is resolved execution argv and was structurally assignable to the old field, which would have duplicated every value on a second round trip. Passthrough tokens trail the declared slots and never count as a later slot.
- The parser's canonical argv deliberately keeps no `--` separator: it is handed verbatim to the tooling command as its real `$1..$n`. The serializer already emits the delimiter, so the serialize/parse cycle is stable without leaking a literal `--` into a user command.
- Verification: `gate:pr` green (typecheck, lint, codegen drift, all thirteen boundary rules, guide-drift reporting a matching guide change rather than skipping) plus `lint:guides` and `check:guide-coverage`. 90 focused tests across the tooling-input, MCP projection, CLI/event/MCP parity, and engine tooling suites, and 239 more across the adjacent event-command, tooling-normalize, MCP catalog/dispatch/service, tooling scenario, and command-compiler suites. Both the serializer and the parser regressions went RED first, as did the new guide scenario, whose RED run caught the real CLI executing `echo tagging ... stable` with a default occupying `$1`.
- Real-surface evidence on the compiled binary in lando4-dev: `lando tag` (leading positional omitted, later one defaulted) exits 1 with `ToolingInputError` naming `label`; `lando tag v1` runs `slots: v1 stable` and `lando tag v1 beta` runs `slots: v1 beta`; a trailing hole still drops, so `lando release` runs `slots: HEAD` with no second token. Over real stdio MCP with `--tooling`, `args: {channel: "beta"}` returns `isError: true` with a message and remediation byte-identical to the CLI envelope, while `args: {label: "v1"}` returns `slots: v1 stable`.
- **Out-of-scope finding:** `lando tag -- -x beta` reports `Too many positional arguments` against a two-argument declaration, so the CLI router appears to forward the `--` delimiter itself as a positional. The parser's delimiter handling is untouched by this story and its unit coverage still binds `["--", "--file"]` correctly.
- **Learnings for future iterations:**
  - A collection built by compaction and consumed by index is a latent mis-bind wherever the two ends are different functions. Fixing only the producer moves the defect rather than removing it; the resolver has to be the same code on both sides or the next caller reintroduces it.
  - A flat process argv cannot represent an absent interior positional. Filling the hole with an empty string looks tempting and is wrong: an empty string is an observable value through `$#`, `$1`, and the resolved args map, and it fails a `choices` list that does not include it. Default-or-refuse is the only honest pair.
  - Rejecting at normalization is not the cheap option it looks like. `compileToolingCommands` throws normalization failures synchronously and `CommandRegistryLive` catches registry discovery failures and returns an empty list, so a newly invalid declaration silently disappears from the catalog instead of erroring.
  - `Effect.flatMap` accepts an `Either` directly, so lifting a fallible pure helper into a command `run` costs no adapter and no new error member.
  - `lando mcp --allow` validates against built-in command ids and rejects an `app:<task>` id outright; tooling tools reach the catalog only via `--tooling`. MCP dispatch also always passes `argv: []`, so a tooling task's positionals arrive solely as named `args`.
  - A `:host` tooling task whose `cmd` is a string containing `$1` or `$@` is refused by Bun Shell. Give it an array `cmd` when you need to observe the argv Lando produced: the tokens appended to it are exactly the resolved canonical argv.
