## 6. Service Specification

### 6.1 Model

A service is a planned runtime component composed from one base and an ordered set of features.

| Base | Contract |
|---|---|
| `l337` | Artifact and build plumbing only. It is the low-level escape hatch and provides no `/etc/lando/*` scaffolding, opinionated environment, packages, or app mount. |
| `lando` | Opinionated development service with boot scaffolding, environment, packages, build steps, app mounts, healthchecks, certificates, SSH agent, and hooks. An authored `type:` wins. When `type:` is omitted, apply bundled image inference first, then use the service key if it matches a registered type. Otherwise an authored image or Compose build selects raw `lando`. Without either, resolve the service key as the type and report an unsupported type if it cannot be resolved. |

Composition is normative. A `ServiceType` resolves to `ServiceTypeResolution`; the core planner composes its `base`, `normalizedConfig`, and priority-ordered `features` into a `ServicePlan`. A type that builds a plan directly is non-conforming and bypasses inheritance, `AppFeature` injection, and feature conformance (§6.11).

`api: 4` is the only service API. Core defaults it after confirming that the Landofile targets `runtime: 4`; no `api: 3` path exists.

A service inherits the app provider. Per-service provider configuration is non-portable and belongs under `services.<name>.providers.<id>`. `ServicePlan.provider` records the resolved app provider.

### 6.2 Common service schema

`ServiceConfigInput` accepts the supported Compose service-key subset (§7.4) alongside Lando keys. Authored service keys use Compose spelling (`working_dir`, `env_file`, `depends_on`, long-form port and volume keys); there is no camelCase service-key alias. Decoded `ServiceConfig` retains the Compose service-key names, while nested values may normalize to internal shapes. The planner maps these to provider-neutral fields such as `ServicePlan.workingDirectory` and `ServicePlan.dependsOn`. The optional `port` is a TCP port number (integer 1–65535). Unsupported or rejected Compose keys fail validation unless an explicit provider extension owns them.

- `image:` and Compose `build:` normalize to `artifact:`. Compose-build fields and Lando build-script fields (`artifact:`, `app:`) are shape-discriminated; mixing them fails with a tagged error and remediation.
- `command:`, `entrypoint:`, `user:`, `working_dir:`, `environment:`, and `env_file:` are the one authored spellings and normalize to execution and environment fields on `ServicePlan` (`workingDirectory`, environment maps, and plan mounts as applicable). A build-script step, and a string `command:` on any type except `type: compose`, run as `sh -c "<string>"`, a non-login shell, so the image environment, including `PATH`, applies unchanged. A `type: compose` string `command:` or `entrypoint:` is word-split into argv without shell evaluation, and any other string `entrypoint:` names one executable. An argv list runs exactly as written. Environment input never inherits unset host values. A null label value becomes an empty string.
- `extraArgs:` is an optional argv list (`string[]`) of additive launcher arguments. It has no string/shell form. Higher layers replace the list (scalar-array merge); `[]` clears it. Elements are service-process argv text sites with the same expression admission as argv `command` elements (§7.3.1), including `service.port` and numeric rendering, an execution-site annotation, direct `${secret:...}` refused as `unsupported-secret-reference` with service-environment advice, and binding descriptors refused before argv is built. A type that marks its Lando-owned launcher as accepting `extraArgs` (append-at-end slot) receives the authored, materialized tokens exactly once after its own flags; shell-wrapped launchers pass them as positional parameters and `exec` the daemon with `"$@"`. Types whose image default starts only when no extra configuration is set (catalog postgres, mysql, mariadb, mongodb) own an args-only launcher that preserves the image entrypoint, pins the planned port, and retains authored `config.server` when `extraArgs` is present. Custom images or Compose builds of those types MUST reject the key. A non-empty list with any effective authored `command:` or `entrypoint:` fails with a located `LandofileValidationError` at `services.<name>.extraArgs` whose remediation is to put the flags in `command:`. If no launcher is marked in the effective configuration, a non-empty list fails with a located `LandofileValidationError` at `services.<name>.extraArgs`, using type-provided refusal advice when available and otherwise advising the author to use `command:` or remove `extraArgs`. After expression evaluation, reserved options the type owns (primary port and managed secondary or config flags) fail at the offending index with remediation to set the Landofile key instead (for example `port:`). After final composition the engine verifies the effective process is still that launcher plus the args; otherwise it fails with a located error. `extraArgs` never changes listener ownership.
- `volumes:` short and long forms normalize into `ServicePlan.mounts` on every service type: host paths become bind entries, named and anonymous volumes become store entries, and `tmpfs` becomes tmpfs entries. Service-level `tmpfs:` strings normalize the same way, with their options canonicalized (`ro`/`rw` become the read-only flag, numeric modes octal).
- `ports:` and `expose:` normalize to `endpoints` through the single mandatory normalizer (§6.6); host bindings require provider capability. Long-form ports use Compose `host_ip` and `app_protocol` (distinct from endpoint-native `appProtocol`). Long-form volumes use Compose `read_only`, `bind.create_host_path`, and `volume.subpath` (distinct from `appMount.readOnly`, storage `readOnly`, and relay `createHostPath`).
- `depends_on:` accepts a list of service names or a condition map (`depends_on.<svc>.condition`); the list-of-objects Compose arm is not accepted. Both accepted forms normalize to `ServicePlan.dependsOn`. `service_started`, `service_healthy`, and `service_completed_successfully` retain their lifecycle meaning (§6.13).
- Compose `healthcheck:` normalizes to native health; Lando `readiness:` uses the same input forms for an independent lifecycle policy (§6.7).
- `init:` normalizes to the canonical `ServicePlan.init` boolean (§6.2.1). It is not a preserved knob and never appears under `ServicePlan.extensions.compose`.
- `restart`, `cap_add`, `cap_drop`, `privileged`, `devices`, `ulimits`, `sysctls`, `shm_size`, `dns`, `dns_search`, `dns_opt`, `extra_hosts`, `stop_signal`, `stop_grace_period`, `security_opt`, `group_add`, `read_only`, `platform`, `logging`, `gpus`, and supported `deploy.resources` fields are preserved in `ServicePlan.extensions.compose` and capability-checked (§5.4, §5.5.1). Resource controls and reserved device requests require their separate exact knob declarations.
- Preserved knob values that no container engine can realize are rejected by the service schema, so `app:config:lint`, planning, and the published JSON Schema report them at their own Landofile path before provider action: `privileged` and `read_only` accept a boolean or a YAML 1.1 spelling (`true`, `false`, `yes`, `no`, `on`, `off`, `1`, `0`, ASCII case-insensitive); `ulimits` soft and hard bounds are safe integers or integer text; `shm_size` is a byte size greater than zero; `stop_grace_period` is finite, non-negative, and within the safe-integer range; a `gpus` or reserved-device `count` is `all` (case-insensitive) or an integer; `deploy.resources.limits.cpus` is a non-negative number or decimal text no larger than `floor(MAX_SAFE_INTEGER / 1e9)`, so its nanoCPU value stays a safe integer; `limits.memory` and `reservations.memory` are non-negative byte sizes, where `0` means no limit; `limits.pids` is a safe integer or integer text, where `0` and negative values mean no limit. Provider-dependent restrictions, such as a log driver a remote engine refuses, remain provider checks. The realizer re-decodes the untyped `extensions.compose` record against the same field schemas before building a create request. It realizes `stop_grace_period` as `StopTimeout` truncated to whole seconds the way Compose does, after rejecting a negative or non-finite value, so a sub-second period is an explicit `StopTimeout: 0`.
- `pull_policy` normalizes to optional `ServicePlan.pullPolicy`, whose values are `always`, `never`, and `build`; omission, `missing`, and `if_not_present` normalize to absence. It MUST NOT be preserved under `extensions.compose`. Timed policies (`daily`, `weekly`, `every_<interval>`, `refresh`) are rejected during planning. `always` and `never` cannot accompany a Compose `build:` section, and `build` requires one. These restrictions do not prohibit Lando build scripts on an image service. Explicit `always` or `never` requires `artifactPull`; acquisition behavior follows §6.13.3.
- Service `configs:` grants normalize into read-only bind entries in `ServicePlan.mounts` (§6.4): the project `configs.<name>.file` resolved from the app root, at the grant's target or `/<name>`, with the grant's `mode` as the entry's `fileMode`; `uid` and `gid` are rejected because Lando cannot change a mounted host file's owner. Supported `secrets:`, `labels:`, and `profiles:` forms are preserved and capability-checked. Service-level `x-*` fields remain inert (§5.4).
- Service `networks:` is a normalized Lando key targeting `AppPlan.networking`, not a preserved Compose field. Keys name `default` (the per-app bridge) or a top-level `networks:` entry; any other key fails validation. Attachments accept `aliases` and inert `x-*` metadata; all other attachment settings MUST be rejected with remediation. `default` is valid only when the plan has a per-app bridge, so global services reject it. Membership is additive: a service keeps the app and shared memberships its `NetworkingPlan` gives it and joins the listed networks too, so `networks:` provides no isolation (§10.1). Authored attachments and bridge aliases require `authoredNetworks`.
- Rejected keys, including `extends`, `container_name`, `hostname`, `domainname`, `network_mode`, `links`, and Swarm orchestration fields, including `deploy.resources.reservations.cpus` and `deploy.resources.reservations.generic_resources`, fail with a tagged error and remediation; they are never silently dropped. Lando owns the container hostname (§10.1). Flat `mem_limit`, `cpus`, `pids_limit`, and `mem_reservation` are rejected with remediation naming `deploy.resources.limits.memory`, `deploy.resources.limits.cpus`, `deploy.resources.limits.pids`, and `deploy.resources.reservations.memory`, respectively. Other rejected resource-tuning keys MUST NOT imply that Lando lacks all resource controls.

Core normalizes an authored `image:` (including the artifact tag pinned by an explicitly versioned service type) to a reference artifact when no service or app feature supplied one. A feature-set artifact takes precedence over this image fallback. An authored Compose `build:` replaces the feature artifact with build intent. Lando build scripts add steps to a base artifact and do not supply one themselves. After feature application and authored normalization, every service sent to the provider's pull/build lifecycle MUST have an artifact; missing intent fails planning through `ServiceTypeError` wrapped in `LandofileValidationError` at `services.<name>.type`, before provider action. The error names the service, resolved type, and contributing plugin when known, and directs the author to set `image:` or Compose `build:`, or request a feature that calls `setArtifact`. An app with no services remains valid. These rules concern the planned artifact; the separately tracked authored `artifact:` grammar (#1483) is unchanged.

Lando keys include `api`, `type`, `primary`, `artifact`, `appMount`, `mounts`, `storage`, `home`, `projectUser`, `endpoints`, `routes`, `healthcheck`, `readiness`, `logs`, `certs`, `hostnames`, `security`, `build`, `packages`, `schedule`, and `providers`. Where a Compose spelling and a more specific Lando spelling conflict, the Lando value wins and `lando app config` SHOULD report the resolution.

`BuildScriptStep` is a command string or `{ run, user? }`; `BuildScript` is one step or an ordered list.

The published boundary retains the named component contracts `ArtifactInput` (not yet published; see #1483), `CommandSpec`, `ContainerUser`, `PortablePath`, `AppMountInput`, `MountInput`, `StorageInput`, `EndpointInput`, `RouteInput`, `HealthcheckInput`, `LogSourceInput`, `CertsInput`, `CaInput`, and `ProviderId`. The scheduled-job contracts `ScheduleConfig`, `ScheduleJob`, `ScheduleJobName`, and `CronExpression` are published with them (§6.2.2).

#### 6.2.1 Native container init (`init`)

`services.<name>.init` is the one authored spelling of container init intent. The schema accepts a boolean or one of the boolean spellings `true`, `false`, `on`, `off`, `yes`, `no`, `1`, and `0` in any letter case, decodes it to a boolean before planning, and rejects any other string as a validation issue at `services.<name>.init`. The planner writes the result to the optional canonical `ServicePlan.init` boolean (§5.5); there is no second representation.

Resolution precedence is fixed. A composed authored value wins. Otherwise a feature's `setInit` contribution (§6.11) wins. Otherwise a service composing the `lando` base defaults to `true`. A service composing the `l337` base, including `type: compose`, leaves `init` unset when nothing authored or contributed it; absence means the provider's own default and MUST NOT be rewritten to `false`. An explicit `false` is preserved at every step and is the only opt-out.

An effective `init: true` requires the `serviceInit` provider capability (§5.4). Capability validation runs on fresh plans and on cache hits before any provider action and fails with `CapabilityError` naming the provider, `init`, and the service; an explicit `false` or absence never requires the capability. Offline lint (§7.8) sees only authored intent because it MUST NOT apply features: an authored `init: true` against a provider whose offline declaration lacks `serviceInit` is a `landofile.capability` error at `services.<name>.init`; an authored `false` needs nothing; and an absent value on such a provider yields one `landofile.capability` warning that the effective value depends on feature contributions and is validated at `lando start`, rather than an invented base-default failure. Final planning stays fail-closed. Shared container-runtime lowering owns the mapping from `ServicePlan.init` to the engine create request, emitted Compose output, and create-config identity (§5.3.2): `true` and `false` emit the engine's init setting, absence emits nothing, and providers MUST NOT add a second mapping.

Native init is the container's PID 1. It forwards the stop signal to its immediate child, the planned `entrypoint`/`command` process, and reaps orphaned descendants. This avoids the kernel's special handling of default-disposition signals for PID 1; it does not guarantee completion before the stop grace period. A child that ignores the signal or exceeds that deadline may still be terminated through `SIGKILL`. This is not a promise about descendants: a shell or process manager that is the immediate child still decides whether to pass the signal on to its own children. Lando-owned keep-alive commands for `lando` language runtimes, `dotnet`, and PHP CLI mode run as direct argv so the idle process is init's immediate child; authored `command` and `entrypoint` values are never rewritten.

Exec supervision (§5.3) is independent of native init: `init: false` or absence does not disable the helper mount or supervised non-TTY commands. The exec helper does not replace the service's entrypoint or become its PID 1.

#### 6.2.2 Scheduled jobs (`schedule`)

`services.<name>.schedule` is a `ScheduleConfig`: an ordered list of `ScheduleJob` values `{ name, every, run, user? }`. No top-level `schedule` key exists. Scheduled jobs are an app-runtime concern realized inside the app; Lando MUST NOT register them with a host scheduler.

- `name` is a `ScheduleJobName`: a letter followed by letters, digits, `_`, or `-`. Names MUST be unique within one service; a duplicate fails validation at the service's `schedule` path. Different services MAY reuse a name.
- `every` is a `CronExpression`: a cron expression of exactly five fields; one of the named schedules `@hourly`, `@daily`, `@midnight`, `@weekly`, `@monthly`, `@yearly`, and `@annually`; or `@every <duration>`. A six-field expression with a seconds field MUST fail validation. An `@every` duration MUST be a whole number of seconds and a clock-aligned step: seconds or minutes that divide 60, or hours that divide 24. `@every 24h` is accepted and means daily at midnight. Any other duration, including `1500ms`, `7m`, and a compound duration such as `1h30m`, MUST fail validation with a message that directs the author to a 5-field cron expression. No other form is accepted.
- `run` is a `CommandSpec`. Each job is installed as its own script in the sidecar's artifact. A string `run` is that script's body, executed by `sh`, and MAY span several lines; a list `run` is executed as that argument vector with no shell interpretation (§6.2). A newline in either form MUST NOT become a schedule entry. `run` is an authored execution site named `schedule-job` (§7.3.1). Job commands are compiled into the sidecar's artifact, so a `${secret:...}` reference in `run` MUST be rejected when the Landofile is loaded, with issue rule `unsupported-secret-reference` and remediation that names the service `environment` binding and `$NAME` in a string `run`; a list `run` has no shell, so its remediation names the process environment.
- `user` is an optional `ContainerUser`.
- The list declares the replace layer-merge rule (§7.2): a higher layer's `schedule` replaces a lower layer's list wholesale, jobs never merge by name, and an empty list clears it.

Validation happens when the Landofile is decoded, so `app:config:lint` and planning report an invalid job at its own Landofile path before provider action. The cadence rules and name uniqueness are decoder checks that JSON Schema cannot express: the published JSON Schema accepts some schedules the decoder rejects, and the parity test lists each such intentional mismatch with its reason (§7.8).

**Cadence.** `@every` is clock-aligned and never counted from scheduler start or from the previous run: at 12:02, `@every 5m` next fires at 12:05. Timed runs of one job MUST NOT overlap: an occurrence that comes due while a timed run of the same job is in progress is skipped, never queued, and the job next runs at its first occurrence after that run ends. Each skipped occurrence is reported in the sidecar's log. Different jobs run independently of each other, and a manual `schedule:run` (§8.2.8) starts regardless of a timed run in progress. Lando does not catch up on missed runs. Occurrences that were due while the app was stopped MUST NOT be replayed. After host sleep, at most the single occurrence that was already pending MAY start late on wake; earlier missed occurrences MUST NOT be replayed.

**Timezone.** A service's schedule zone is that service's authored `environment.TZ` when it is a literal string there, with one leading `:` ignored, and UTC otherwise. A `TZ` that reaches the container any other way, including an `env_file` and a value Lando computes, MUST NOT set the schedule zone. No app-level timezone setting exists. The scheduler MUST be given the schedule zone explicitly. The zone governs when jobs run; a job's process environment, including `TZ`, is the service's environment unchanged. Job listing (§8.2.8) and job execution MUST evaluate a job's `every` in the same zone and under the same rules, so a listed next occurrence is an occurrence the scheduler honors. The scheduler MUST NOT fall back to UTC or any other zone for a zone it cannot load. A schedule zone other than UTC requires timezone data in the sidecar's artifact. When the parent's artifact has no timezone database, Lando installs one in the sidecar's artifact through the artifact's package manager, where that is `apk` or `apt-get`; the parent's artifact is never changed, so the zone the parent service itself can load is unaffected. When the installation fails or the sidecar's artifact still cannot load the zone, its build MUST fail, on the `start` or `restart` that builds it, with one line that names the service and the `TZ` value and directs the author to the failed installation or to check the zone name, or to install the timezone database in the service's `build.artifact`. After the cause of a failed installation is fixed, the next ordinary `start` or `restart` MUST succeed without clearing any cache. A `TZ` that is not a zone name, such as the POSIX rule string `EST5EDT,M3.2.0,M11.1.0`, MUST fail that build with one line that asks for a zone name such as `America/Chicago` or `UTC`. The finished job table MUST be validated by the scheduler during the artifact build, so a table the scheduler would reject fails the build and never the running sidecar.

**Output.** A timed run's stdout and stderr are written to the sidecar's stdout and stderr as the job wrote them, so `lando logs --service <sidecar>` (§6.14) shows job output unwrapped. The scheduler's own lines, including the start and result of each run, share those streams.

**Working directory.** A job starts in the parent service's planned container working directory, the directory the service's own process starts in: the app mount for Lando service types that set one, and the artifact's `WORKDIR` for a `type: compose` service. Lando MUST NOT substitute another directory.

**Identity.** A job without `user` MUST run with the parent service's effective identity: the service's `user` when one is planned, otherwise the artifact's default user. Lando MUST NOT substitute root or any other identity for an absent `user`. A job with `user`, in any `ContainerUser` spelling (`name`, `uid`, `name:group`, `uid:gid`), runs in a sidecar whose container user is that user, with the home directory, primary group, and supplementary groups the container runtime resolves for a container started as that user. The job command MUST NOT be wrapped in an in-container privilege-switching tool to obtain that identity.

**Sidecars.** The bundled `schedule.compile` app feature (§1.4, §9.5) realizes a service's jobs as generated companion services (§6.11.5) cloned from that service, called schedule sidecars. Jobs are grouped by `user`, with the jobs that declare none forming one group, and each group yields exactly one sidecar that runs as the group's identity and executes only the scheduler. A sidecar's name is a function of the service name and the group's `user` alone:

| Group | Sidecar name |
|---|---|
| Jobs without `user` | `<service>-schedule` |
| Jobs with `user` | `<service>-schedule-<suffix>`. A user spelled only with `a-z`, `0-9`, and single interior `-` is its own suffix (`www-data`, `1002`). For any other spelling the suffix is the user lowercased, each run of characters outside `a-z` and `0-9` replaced by one `-`, leading and trailing `-` removed, followed by `-` and the first six hex digits of the SHA-256 of the exact user, so distinct users MUST NOT yield the same name (`www-data:staff` yields `www-data-staff-95d9a1`) |

Job order MUST NOT affect a sidecar's name, and no `-default` name exists. A service whose jobs all declare the same `user` has exactly one sidecar, named with that user. A sidecar name is subject to the companion name rule (§6.11.5): a collision fails planning and is never resolved by renaming. A sidecar requires a shell in its artifact. Planning rejects, with `AppFeatureCloneError` reason `unsupported-image`, only an artifact reference known to have no shell: the empty `scratch` image and `gcr.io/distroless/*`. Any other artifact without a shell fails in the artifact build.

**Scheduler acquisition.** The scheduler binary is acquired as a step of the sidecar's artifact build, from a version and per-architecture SHA-256 pin reviewed in source, and MUST be verified against that digest before it is installed (§6.13.3). It MUST NOT be downloaded, verified, or installed at container start. The pin is a `buildKey` input. The job table is built separately from the binary: a `schedule` edit MUST NOT re-acquire the binary, MUST take effect on the next ordinary `start` or `restart` without `rebuild`, and MUST NOT rerun the parent's build steps.

#### 6.2.3 Project user

A service that mounts host content has one project user: the in-container identity whose files belong to the host user on a provider that maps exactly one container id to the host user. A service cannot have two project users.

`services.<name>.projectUser` accepts one of three forms. `false` opts the service out and restores the provider's historical identity behavior. A numeric `"<uid>:<gid>"` pair names both ids directly; a pair whose uid is `0` fails planning, because root keeps its own identity and cannot be mapped to the host user. A bare name is accepted only when it equals the project-user name the service type declares. Every other value, including a bare uid, `name:group`, and an unknown name, fails planning with `LandofileValidationError` at `services.<name>.projectUser` and remediation naming the accepted grammar. Explicit authoring is fail-closed: when the selected provider reports `projectUserMapping: "unsupported"` (§5.4), planning fails with `CapabilityError` before hooks, builds, stops, or apply.

When `projectUser` is absent, resolution order is fixed. An authored process `user:` wins when it is a numeric `uid:gid` pair or the service type's declared project-user name; otherwise the service type's declared project user applies; otherwise the service has none. An authored `root`, uid `0`, or a resolved root identity means none. The project user applies to user apps and to template step environments (§23.8), whose destination mount counts as the app-source bind, and only to a service whose finalized mounts include that bind. Other scratch apps, the global app, and services without that bind are `not-applicable`. An implicit catalog default never fails planning: the service keeps today's behavior and the plan explains the absence. A custom image under §6.5's catalog-identity equivalence rules, or an authored Compose replacement build, has no service-type identity, so only a numeric project user is resolvable for it.

The realized plan field is `ServicePlan.projectUser` (`{ name, uid, gid }`), written only when the provider can realize the mapping. Execution identity reads that field alone. The provider's declared `projectUserMapping` selects how creation realizes it, and planning records an `image-renumber` realization in the `@lando/core/project-user-mapping` service extension so create-config identity distinguishes it from keep-id; an absent extension means keep-id, which keeps plans recorded before the extension existed valid. When the field is absent, `ServicePlan.projectUserExplanation` records one of `opted-out`, `provider-unsupported`, `unresolved`, or `not-applicable`, whether the value was authored, and a human-readable detail; `lando info` and `app:config:lint` surface it. Every durable plan exposes the realized field to plan cache identity, and both project-user capability facts, plus the host ids when the realization is `image-renumber`, enter the desired-plan cache key (§12).

On an engine where a container id is the host id, `projectUserMapping: image-renumber` realizes the catalog project user by renumbering that image account to the invoking host uid and gid in the derived image. The rule is decided at planning from the ids the service type declares: an exact match already satisfies the mapping, any other non-zero host id emits one root build step, and host uid or gid 0 fails planning with remediation. The step uses `usermod -o` and `groupmod -o` when available and truncates any lastlog/faillog files they may have expanded. On minimal images without those tools, it edits the matching local `/etc/passwd` and `/etc/group` records by their declared ids without installing anything. Both paths permit target id collisions, transfer the files the old ids owned without touching files owned by uid 0, and carry the ids into the build key. A custom image or replacement build that §6.5's equivalence rules do not treat as the catalog artifact has no catalog account, so only a numeric project user equal to the service's numeric process user is realized, by creating the container as the host ids; any other explicit request fails planning and an implicit one is explained.

Home persistence follows the effective user-command identity. With a realized project user, the planned home is that principal's declared home, keyed by that principal; a numeric principal with no declared home leaves the home unknown instead of guessing. User commands surface matching `HOME`, `LANDO_USER`, `LANDO_UID`, and `LANDO_GID`; root processes keep the image's own home.

Write targets derive from the winning finalized mounts. With a realized project user, writable derived volumes, including exclude shadows, writable feature cache and dependency-environment stores, and writable authored named volumes strictly inside or enclosing the app bind target are write targets, excluding a persisted home the service type already prepares (§6.5). Other authored volumes keep image ownership; clones share the parent's stores and do not prepare them again. After feature artifact steps and before authored artifact steps, the root build step creates each write target and the parent directories of mounts strictly below it after lexical normalization, then recursively gives the tree to the project user's numeric `uid:gid` (mode `0770` at the root, or `0775` for a tree enclosing the app bind so a sibling web server can read it). It creates only the parents, since a nested bind may target a file. Ordinary fresh volumes can copy up the prepared image tree and ownership; dependency environments MUST NOT rely on copy-up (§6.5.1). When a service feature already claims a target, that owner wins and the mount parents are still created. Image preparation never reseeds or reowns an existing volume. Authored binds are never reowned, and no recursive host `chown` runs at start. A tmpfs mount receives `uid`, `gid`, and a writable group mode unless the author already set those options.

Before provider apply creates a service container, Lando creates, as the invoking host user, every directory the runtime would otherwise create inside the host source of that service's passthrough app bind: the planned working directory when it lies below the app-mount target, and the mount-point directory of every mount nested below that target, including an exclude shadow, a nested home, and an authored nested volume, tmpfs, or bind. Container paths map through the app bind's source and MUST stay inside the canonical app root: a target that leaves the app mount after lexical normalization (as the runtime itself cleans it) and a path whose existing ancestor resolves through a symlink outside the root are refused, existing paths are never modified or chowned, a nested file bind contributes its missing parent directories and an empty regular file at its target (created exclusively, so an existing path or symlink is never replaced), and a bind source the CLI cannot see (an accelerated app mount or a remote provider) is a no-op. The preparation runs before the provider creates any container, so restart-with-recreate and rebuild prepare the same directories that start does. This keeps a runtime-created directory or file mount point from belonging to a subordinate container id under `keep-id`, which would be writable for neither the host user nor the project user.

Content created under a mapping from before this contract is not translated by ordinary start; a follow-up owns the journaled, resumable ownership transition. A newly selected principal gets a fresh home.

### 6.3 Artifact build

`services.<name>.build` accepts a Compose context string or one nonempty object from exactly one family: Compose image-build keys (`context`, `dockerfile`, `dockerfile_inline`, `args`, `target`) or Lando build-script keys (`artifact`, `app`). The Compose object defaults an omitted context to `.` (local Compose includes rebase it from the fragment, §7.7). `dockerfile` and `dockerfile_inline` are mutually exclusive. Author and encode inline Dockerfiles as `dockerfile_inline` only; `dockerfileInline` is the decoded spelling, not an authored alias. Build `args` accepts a string-valued map or `KEY=value` entries, not bare names or null values; it does not inherit host values.

`artifact:` accepts an existing artifact reference, an external `sourcefile:` plus context, or inline provider-neutral build intent. Inline intent includes `source`, `tag`, `context`, `args`, `secrets`, `ssh`, `platform`, `groups`, and `steps`.

Build instructions use named, weighted, user-scoped groups. Final order follows group weight and step weight. Service types, features, fragments (§7.7), and Landofile input contribute steps; recipes contribute only through the Landofile they scaffold. Group overrides may select a group, relative offset, before/after placement, and user; their concrete grammar is schema-owned.

`build.artifact:` and `build.app:` preserve every step's resolved user through `BuildPlan`, provider execution, and ordered `buildKey` hashing. An omitted `build.artifact:` step user resolves to the planned service user; an omitted `build.app:` step user follows the command-identity selector (§8.12), so it runs as the applied project user when the service has one and otherwise as the container default, which is the planned service user. An explicit step user overrides its group's user. Interleaved users are valid. Artifact generation switches users only when required and restores the final service user; app steps pass the resolved user to `execStream`.

`sourcefile:` is the provider-neutral external build-definition key. Compose build fields normalize when possible; other provider aliases belong in provider schemas. Build secrets and SSH require `buildSecrets` and `buildSsh`. Artifact tags are not assumed globally meaningful or pushable.

Artifact builds, including setup probes, MUST remove their temporary build containers and release those containers' mounts whether the build succeeds, fails, or is cancelled. Reusable build cache MAY remain; a built artifact remains while a build result or an in-flight build claim names it, and a teardown releases it for a bounded time (§6.13.5).

### 6.4 App mounts and mounts

`appMount:` (`AppMountInput`) accepts `false`, a destination string, or an object with `target` and optional `readOnly`, `excludes`, `includes`, and `accelerate`. `accelerate` (boolean) permits automatic file-sync acceleration; omitted or `true` never forces it, `false` keeps an ordinary provider bind with no session and no engine acquisition. No engine id is authorable. A string is shorthand for `{ target: <string> }`, interpreted after authored composition. A higher-layer string replaces the inherited object, including its options; object forms deep-merge with other object forms. Consumers see only `false` or the decoded object form. Ordinary service configuration fixes the app mount's source to the app root (scratch isolation may rebase it, §21.7), and core selects provider-bind or accelerated file-sync realization, so `MountInput`'s `type` and `source` are not authoring options and `false` is the only disable spelling. Target validity is a planning check, so the published schema and decoding agree on every string. The `lando.app-mount` feature is its only owner: a service type opts in by declaring its default target, usually `/app`, and optionally a default working directory; types without one, such as data stores, get no app mount. When active, the app source mounts at the authored target or the type's default. Planning sets `working_dir` to that target unless the author sets one or the type names another default (§6.12.1), exports `LANDO_APP_ROOT` and `LANDO_PROJECT_MOUNT` as that container path, and records the result in `ServiceInfo`. The plan carries the app mount as the one bind entry in `ServicePlan.mounts` with `role: app`. Core, not the feature, realizes authored `mounts:`, `volumes:`, `storage:`, and `tmpfs:` on every service type, after all service and app features have run; an authored mount at the app mount target replaces the app mount and keeps the app-path variables and default working directory. `false` means the service does not use the app source, as with a data store: on every type it disables the mount, both variables, `LANDO_WEBROOT`, and the default working directory, and an authored working directory still applies. Raw `compose` services get the mount but no default working directory and no app-path variables (§6.9).

| Mount type | Contract | Capability |
|---|---|---|
| `bind` | Live host path | `bindMounts` |
| `volume` | Named store | `persistentStorage` |
| `tmpfs` | Memory filesystem with container lifetime | Always |

`MountInput` accepts only these three types. `copy` (host path copied during artifact build, `copyMounts`), `inline` (literal content), `template` (`TemplateEngine` output materialized as `inline`), and `disabled` (removes an inherited mount by target) are deferred (#1810); a Landofile using them fails validation.

`ServicePlan.mounts` is the single ordered list of logical service mounts: binds (the app mount, authored binds, certificate and configuration files, worktree Git directories), named stores (authored storage, exclude shadows, caches, home), and tmpfs. Targets are canonical and unique, and the list is ordered shallow to deep, so the deepest target wins: a bind nested inside an excluded directory or a store shows through. Precedence at one target is fixed: `mounts:`, `storage:`, and `tmpfs:` beat the Compose tier (`volumes:` and `configs:` grants); two Compose-tier entries at one target fail validation, as Compose rejects duplicate mount points; two of those Lando spellings at one target fail validation in both lint and planning; an authored entry replaces any service-type, feature, or app-feature entry, including the app mount and a type's own data store, and a replaced store's ownership preparation is dropped unless the winner is also a store; two non-authored entries at one target fail planning with `LandofileValidationError` naming the service and target, the same channel as other feature failures. Derived entries (exclude shadows, nested includes, worktree Git directories, home) fill only unoccupied targets. Providers render the list in order and refuse a plan with a duplicate target instead of deduplicating it.

The runtime-owned read-only helper bind at `/run/lando/helper` (§5.3, §5.5) is added at creation with `origin: integration` in the physical mount list, together with read-only binds of the helper command shims at `/usr/local/bin/<name>` and the login-profile stub at `/etc/profile.d/zz-lando-service-path.sh`, all helper assets (§17.3). Distro login profiles reset `PATH`, so a login shell in the service (`app:ssh`, service-mode `app:shell`, and a supplied `bash -l` or `sh -l` alike) runs the stub after the other profile scripts. The guarantee covers POSIX login shells whose profile sources `/etc/profile.d` in the current shell and does not reset `PATH` afterwards: bash, dash, and BusyBox ash with the distro `/etc/profile`. zsh, fish, and profiles that reset `PATH` after sourcing `/etc/profile.d` are outside it. The stub is immutable and only sources the profile hook body from the mounted helper directory when that file is readable; the body restores the `PATH` the shell started with verbatim, including order and empty components, then appends each entry the profiles added that it lacks, so neither image nor authored `PATH` entries are dropped and later user dotfiles can still prepend. The trade-off is ordering: entries that `/etc/profile.d` scripts add, such as a system-wide rvm or sdkman install, follow the service `PATH` in login shells instead of preceding it; a user who wants such a toolchain first puts it in `environment.PATH`. Both are POSIX `sh`, change no shell option, and do nothing when that initial `PATH` is unreadable, empty, or holds a newline, or when `PATH` is readonly. The stub's source is stable, like the shims', so a new body reaches running containers at their next login and never changes create-config identity. Explicit argv is never wrapped in a login shell.

Overlap between those binds and a mount the service already has is judged by one canonical POSIX predicate (the same path or an ancestor, after normalization), shared by planning, lint, and the provider. Reserved helper targets fail validation in both lint and planning with `LandofileValidationError` at the offending `services.<name>.mounts`, `storage`, `tmpfs`, or `volumes` entry, before any hook or build: a mount at `/run/lando/helper` or beneath it, a bind or volume above it (whose source would gain Lando's mountpoints), or a mount at a helper command shim's exact target. A service with the host-proxy feature also fails the same way for a mount at the exact `lando`, `xdg-open`, or `open` target (§10.10.2); eligibility comes from the service's declared features, known when its seed resolves, so a service without that feature (a Compose service, for example) keeps such a mount, and the start-time overlay repeats the check only for plans the planner did not build. The remediation names the path and the command Lando provides there. A tmpfs above the helper directory persists nothing and is allowed. Providers repeat the same check for plans that did not come from the planner. A bind or volume strictly above a command shim target, including the host-proxy `lando`, `xdg-open`, and `open` shims (§10.10.2), skips those binds rather than create mountpoint files in that mount's source; a tmpfs above them skips nothing, because a bind beneath it persists nothing. Every operation that creates or recreates service containers then publishes one `LANDO_HELPER_COMMANDS_UNAVAILABLE` command warning per service whose commands were skipped, with `service`, `mount`, and `commands` context, at the same point and on the same operations as the low-port warning (§6.15): recorded for machine output and printed once for people. The profile stub is optional: a mount at its exact target, or a bind or volume above it (`/etc/profile.d`, `/etc`), owns that path and the stub is skipped silently; a tmpfs above it skips nothing. This applies to user, global (§20.1), and scratch (§21.7) service containers, including `l337` and Compose services, regardless of `appMount: false` or scratch isolation mode. It exposes only helper artifacts, not the user's configuration directory, and does not restore legacy `/lando` or `/helpers` mounts.

Every entry records its `origin`: `authored` (the Landofile), `service` (the service type, a feature, or an app feature, including the app mount), `derived` (exclude shadows, nested includes, Git directories, home), or `integration` (agent-forwarding and host-proxy overlays added at start). A bind whose source was resolved lexically from the app root also records `relativeTo: app`, which is what scratch isolation rebases or drops (§21.7). Provenance never enters build keys or create fingerprints, and plans recorded before it existed carry none rather than an inferred value. A bind with `fileMode` binds a private copy of its file source with those permission bits; the provider materializes the copy before create as an immutable, content-addressed file in a Lando-owned directory that survives host restarts, and the create fingerprint covers the logical source, content digest, and mode, never the copy's path. Bind and store entries are capability-checked (`bindMounts`, `persistentStorage`); tmpfs is a baseline every provider MUST realize, so it has no capability flag.

When they ship, template mounts use app-root-relative `source`, optional `engine`, `vars`, and `mode`. Sources obey include containment (§7.7.6). Engine selection is explicit, then extension-based, then `lando`; values resolve through the standard expression context. Providers receive only rendered `inline` mounts. Rendered output uses the `<userCacheRoot>/templates/<engineId>/...` `template-render` cache (§12.1).

An excluded path belongs to the service. Every bind accepts `excludes` and `includes`. App binds have no universal excludes. Service types can declare presets for their machine-specific trees: Python declares `.venv` and `__pycache__`, Ruby declares `.bundle` and `vendor/bundle`, and Node declares `node_modules` according to §6.12.1. Authored excludes add to the presets and authored includes can cancel or narrow them. Composer's `vendor`, `tmp`, and other project content stay on the app mount on every platform unless a preset, authored exclude, or explicit child mount covers the path; accelerated file sync carries the remaining content subject to the transport rules below.

Each eligible directory exclude gets a service-scoped storage shadow; an exclude whose host path exists as a non-directory gets no shadow and stays visible through passthrough binds. When producing a fresh bind plan, the planner canonicalizes authored entries by removing redundant POSIX separators, `.` segments, and trailing slashes. Includes cancel equal entries in the plan, so `./vendor/` cancels `vendor` in a new plan. Retained plans verify against their recorded entries without rewriting them. An entry that is a literal relative path beneath a shadowed exclude of the same bind keeps that host path: planning binds it from the same source over the shadow, so the Lando 3 translation of `!vendor/acme` works. Includes that are absolute, contain `..`, or contain glob characters fail validation; `excludes` or `includes` on a store or tmpfs entry fail validation. A bare `!` entry in either list fails validation with remediation naming `includes`; the Lando 3 translator lowers `!x` to `includes: [x]` on a writable app-root bind and to an explicit read-write child bind elsewhere, because Lando 3 re-bound those paths from the app root (§7.4.1). VCS metadata is a fixed rule, not a key: `.git` is never shadowed and remains visible through ordinary binds. Every accelerated engine MUST support exclusion patterns and never sync `.git` unless `includes` in the plan names it exactly. The exact patterns are derived from the finalized plan, not just the authored list: every effective exclude, including non-directory paths, the relative target of every other entry mounted beneath that bind (storage shadows, authored and cache stores, tmpfs, and nested binds, which also hide that subtree), and `.git`, deduplicated. A `storage` entry under the app mount and an `excludes` entry for the same path therefore produce the same container layout and the same patterns. Copy includes become binds. Ordering preserves nested-path semantics.

When a passthrough app mount's `.git` is a gitfile (a Git worktree or submodule checkout), planning bind-mounts the resolved common git directory, and the worktree git directory when it lies outside it, so git works at the app mount. An absolute `gitdir` mounts at the same container path; a relative one mounts where the gitfile resolves from the container app mount target, so git follows the file unchanged. Planning verifies each directory is a Git directory (it holds `HEAD`) before mounting; a gitfile alone never authorizes a host path. The binds are read-only when the app mount is read-only, never file-sync sessions, never override an authored mount or storage at the same destination, and are skipped when a host path is not a POSIX absolute path. Shared metadata is writable by every worktree's containers, as on the host.

Every bind entry has `realization: passthrough | accelerated`. The app mount's realization is decided once, from `bindMountPerformance` (§5.4), `appMount.accelerate`, and global `defaultFileSyncEngine`, and that one decision drives Git overlays, mount keys, session construction, and required-capability checks; every other bind, including authored directory binds and configuration files, is `passthrough`:

- `native` uses provider binds and no `FileSyncEngine` or `pre-file-sync-*` events; an explicit engine choice is still validated when host policy is evaluated (§4.3).
- `slow` with `accelerate: false`, or with `defaultFileSyncEngine: passthrough`, uses provider binds with no session and acquires no engine; bind capability errors still apply.
- `slow` with no eligible automatic engine uses ordinary binds and records `no-compatible-engine`.
- `slow` with an eligible engine and no opt-out uses a provider-managed volume named by the shared `fileSyncVolumeName` contract (`<app-name>-<service>-<mountKey>`, sanitized for the runtime) and a `FileSyncSessionSpec` under the engine selected by §4.3; the bundled engine is `@lando/file-sync-mutagen` (§4.2). This name is not a rename-stable ownership identity: provider labels and retained-plan evidence remain authoritative, and renaming an app follows the same-root reconciliation rule in §7.4.
- `none` fails with `CapabilityError`.

The realization is invisible in canonical config and MUST NOT expose engine or session ids there. Every accelerated plan requires `two-way-safe` mode and exclusion-pattern support; engines receive exactly the derived pattern list, including non-directory paths. Directory overlays MUST NOT substitute for transport filtering. Eligibility is checked from metadata before any provider action, lifecycle hook, or rotation (§4.3). Verification compares exact lists for both new and historical plans; exclude entries remain in mount intent and are never silently dropped. The desired-plan cache key covers host platform, provider capabilities, configured default, selected engine id, and planning-sensitive engine capabilities and support metadata, so a policy change misses the cache without touching durable session state.

`AppPlan.fileSync` deliberately remains a flat persisted session array. At the operation boundary, one canonical internal bundle normalizes it into ordinary execution (zero accelerated binds and zero sessions) or accelerated execution (one engine id and exact session coverage). Mixed engines, contradictory realization, duplicate, missing, or orphan sessions fail closed before acquisition or action. Execution consumers use that bundle instead of independently rescanning engine ids. Normalization MUST NOT rewrite original persisted entries, session bytes, or journal digest inputs, and structural validation MUST NOT replace provider ownership or prepared-target verification. Retained plans and journals keep their original engine identity and synchronization history.

A passthrough app bind's host source is the only base for pre-create directory preparation (§6.2.3): the working directory and nested mount points are created there, as the host user, before the service container is created. An accelerated app mount realizes its source as a provider-managed volume, so it has no host source to prepare.

Optional bounded `AppPlan.fileSyncPolicy` metadata records one app-level engine and selection reason plus each service's realization and reason. Mixed service opt-outs are allowed. This metadata explains mount/session facts; it is not a second execution authority. Missing historical reasons stay unknown rather than being inferred from current global config (§6.10).

`mountKey` identifies an accelerated mount within its service: `app-mount` for the app mount, otherwise derived from its canonical target, so reordering `mounts:` never moves a session. It correlates the mount, sync volume, `FileSyncSessionSpec`, the engine's durable session state (§10.6.2), and lifecycle events. The planner stamps it on the bind entry once and every renderer and verifier reads it from there. A changed source or exclusion set changes the session spec, not the key. A changed engine id or an accelerated-to-ordinary change (`accelerate: false`, `passthrough`, or a provider that is no longer slow) is the same kind of transition even when the session specs would otherwise match. Under the app lock, after runtime preparation and any required same-root rename retirement (§7.4, §6.15), start detects any of them before it mutates the selected realization: it validates the desired intent, verifies that the previously applied state is fully app-owned, acquires the engine recorded in that applied plan (never the newly selected one), quiesces the app's writers, drains pending target-side edits to the host, disposes the previous sessions and sync targets with their recorded specs, retires the previous applied state without removing named data or cache volumes and without running authored destroy steps, then applies the new plan: an ordinary start that creates zero sessions, or a normal accelerated start whose new sessions populate from the host. An unresolved conflict, missing session history, an unreachable recorded engine, unknown applied state, a failed drain, or an unfinished accelerated-start journal whose identity does not match the desired plan blocks the transition without applying the new plan or deleting targets. Each step resumes from the existing disposal phase or accelerated-start journal after interruption, and the user never terminates engine sessions by hand.

Engine selection errors, module/factory load failures, and disagreement between declared and acquired capabilities MUST fail before app lifecycle hooks or provider mutation. Once acceleration is planned, acquisition, setup, availability, target preparation, and ownership failures MUST remain tagged failures with actionable remediation, even for a new app. They MUST NOT silently downgrade to ordinary binds. A desired ordinary plan still passes the applied-state guard before replacing accelerated state and MUST NOT bypass drainage or retained history.

An eligible dependency environment claims its target before exclude shadows are derived. It replaces any shadow at that target and its mounted tree stays out of accelerated app sync (§6.5.1, §10.6).

### 6.5 Storage

#### 6.5.1 Dependency environments

A service feature MAY declare a `DependencyEnvironmentIntent` through `ServiceFeatureContext.addDependencyEnvironment`: a short kind, canonical absolute target strictly below the app mount, string-valued toolchain identity, and nonempty prepare argv. It MAY supply activation defaults, a global job cache (name, target, and environment variable), and a description of the inputs for failure remediation. Invalid intents fail feature composition. This is not a Landofile key. The planner resolves authored mounts and project users before materializing the intent, and materializes it before exclude shadows and file-sync filters. It MUST skip services without an app bind sourced within the app root, and scratch and global plans. An authored mount of any kind at the exact target suppresses both the store and activation; the author owns that environment and its activation. Any other feature mount at the target conflicts. Otherwise the environment mounts at service precedence and activation fills only unset variables.

Consumers with equal canonical keys share one app-scoped data store: kind, feature identity, target, app source relative to the app root, effective writer identity and mapping, platform pin, and artifact-intent digest. The writer is the realized project user's numeric `uid:gid`, otherwise the planned service user, otherwise `root`. The digest covers the base and artifact steps, excluding service-specific ownership and log redirect work. The bounded store name uses the data-name slug, kind, and 16 hexadecimal digest characters. Distinct keys MUST NOT map to the same store. A changed key selects a fresh environment; the previous store follows ordinary app data retention. Its replacement notice MUST NOT suggest reattaching it or migrating installed dependencies into the new tree.

Each store has one generated `<kind>-env` prepare job, suffixed with the first eight hexadecimal key-digest characters when there is more than one store of that kind. Check the generated name and its derived names case-insensitively against service keys, hostnames, network aliases, and companion names; conflicts fail with a located `LandofileValidationError` and rename remediation. The lexicographically first consumer supplies the artifact intent, platform pin, and environment. The prepare job builds normally and MUST run as root in the app mount directory with the same app source and target, always as a passthrough bind even for accelerated consumers. It mounts only that bind, the dependency store, and any declared cache; it receives the effective writer as the final argument. It MUST override the image entrypoint, disable image healthchecks and restart, and omit inherited dependencies, app build steps, listeners, readiness, routes, certificates, integration mounts, and privileges. The job MUST leave a prepared tree writable by its effective writer without relying on image copy-up for content or ownership. Ordinary image-tree ownership preparation (§6.2.3) is not a runtime preparation substitute.

After mutating the dependency tree, the job MUST restore its ownership to the effective writer, including on failed preparation where the tree remains available for retry. It MUST NOT change ownership of the app bind.

Consumers require verified exit zero through `service_completed_successfully`. The provider MUST schedule the job only when it starts or creates at least one consumer (§5.3). A warm start that keeps all consumers MUST NOT run it; restart after changing dependency inputs while running. Selected restart adds only the environment jobs of selected consumers; selected rebuild includes them in its normal dependency closure (§6.15). An unselected consumer MAY remain running during additive preparation. Failed completion blocks the consumer with `ServiceStartError`, verified exit evidence when available, and a bounded redacted log tail when available (§6.7); remediation MUST name `lando logs -s <job>` and the declared inputs, if any. The failed job's logs MUST remain available after a first failed apply (§8.2). Successful jobs appear as `completed` in start and info (§6.10) and MUST NOT make an active app appear stopped (§8.2).

#### 6.5.2 Store declarations and lifecycle

Storage declarations are a target path or `{ store, target, readOnly?, scope?, kind?, key? }`; they become volume entries in the mount list. An explicit data `store` names the runtime volume verbatim. File-sync target volumes keep the separate §6.4 naming contract. For user apps, every derived name that embeds an app slug MUST use the folder's **data name** slug from per-folder data identity (§7.4), not the current Landofile name after a rename. `planDataId(plan)` is that slug when `plan.identity.dataName` is set, otherwise `plan.id`. Scratch apps substitute their own id and the global app its native slug (§10.1); neither reads the identity record. A service type's ordinary service-scoped data store belongs to that one service: the type names it with `ServiceFeatureContext.serviceStoreName(role)`, which is `landoServiceStoreName`, `<container name>--<role>` (§10.1), where the container-name prefix is built from the data-name slug and the service key. Dependency environments follow the sharing rule in §6.5.1 instead.

`home: false | { path? }` controls planned-user home persistence and is enabled by default. The planner always records `ServicePlan.home` as one of four states: `persisted` (`target`, generated `store`, optional user principal), `authored` (`target`, mount kind `volume`, `bind`, or `tmpfs`), `disabled`, or `unknown` (`reason`: `custom-image`, `no-identity`, or `undeclared-user`, plus the user principal when known). A persisted home adds a volume entry with `origin: derived` to `ServicePlan.mounts`; `ServicePlan.home` records that decision rather than providing another mount source. Unknown homes omit automatic persistence without failing planning. `home.path` supplies an explicit destination; `home: false` disables persistence. Any entry in the mount list exactly at the canonical home target wins, including the app bind, another bind, a volume, or tmpfs: the home is recorded as authored and Lando generates nothing over it.

A generated persisted home store holds user state such as credentials, tokens, and shell and client history, not application dataset content; it remains service-scoped `kind: data` storage for ownership and retention. When selecting contents for snapshots, data movement, dataset sync, scratch materialization, or diagnostics and support bundles, a store-iterating consumer MUST exclude every store referenced by a `ServicePlan.home` whose `state` is `persisted`, unless the operation explicitly references that store. The rule does not hide home metadata from reporting or exempt home stores from provisioning, ownership accounting, or teardown: plain destroy retains them, `destroy --volumes` and `--purge` remove them under the existing ownership rules, and scratch home stores follow §21.8.

Start, rebuild (including selected services), and restart MUST warn before apply once per (app root, service, target) per command when an applied data volume changes or is no longer mounted. Compare the applied plan or plans already in memory against the desired plan for persisted homes, volume mounts with `origin: service`, and `origin: authored` volumes listed as `kind: data` in `AppPlan.stores`. A missing mount origin is unknown: report it only when home metadata identifies it or the store is listed as data. Exclude derived non-home shadows except as described below. Exclude caches, global-scope stores, binds (including accelerated/file-sync binds), removed services, and services outside a selected plan. Persisted homes also warn when their store or target moves or the desired home becomes unknown, retaining the reason; authored or disabled desired homes and older applied plans without home metadata do not trigger automatic-home notices. A replacement notice MUST name both volumes and targets; a removed mount notice MUST say the previous volume is no longer mounted. Every notice MUST say Lando leaves the previous volume untouched. For dependency environments use §6.5.1 instead of reattachment or export/import advice. For other data stores, offer explicit `storage: [{ store: <previous>, target: <previous target> }]` under `services.<name>` only when both plans record the same `serviceTypeId`. Normalized `type` equality MUST NOT substitute for missing declaration identity (§6.11.0). On a known type change, instruct the user to export data from the old service and import it using the new service's tools. When either identity is missing, say compatibility is unverified and give the same export/import advice without suggesting reattachment. Notice comparison MUST add no provider or filesystem calls, and nested operation delegation MUST share fiber-local deduplication.

Warn under the same rules when a derived volume shadow strictly below the applied app bind disappears and its target is exposed by the desired app bind, whether a preset or authored includes/excludes changed. A mount at that target or between it and the desired app bind prevents this notice, including a replacement dependency-environment store. Also omit the notice when the target's canonical relative path is still excluded by the desired app bind, such as when the host path became a non-directory and no longer gets a shadow. This notice does not inherit the data-store reattachment or export/import advice, and there is no replacement volume to name. The notice MUST name the service, target, and previous volume, and say Lando left the volume untouched and did not copy its contents to the host. If the desired service has no app-phase build steps, advise rerunning the dependency install or other setup the service needs there. Otherwise omit that advice because container replacement runs those steps again.

Catalog `ServiceImageIdentity` declares `defaultUser`, principal-keyed `homes`, and optional `preparedHomes`: principals whose passwd home the image does not create or give to that user. An authored image canonically equal to the artifact pinned by an explicitly versioned service type retains this identity; without such a pin, an authored image is custom. Genuine Docker Hub aliases and implicit `library/` and `:latest` compare equally, but other registries, tags, and digests remain distinct. A different image or authored Compose build context does not inherit catalog identity. The principal is the realized project user's principal, otherwise the planned process user's name without its group suffix, otherwise the catalog default user. `landoServiceHomeStoreName` generates `<container>--home--<readable>-<digest8>`, where `<container>` comes from `landoServiceContainerName` applied to the **data-name** slug (§7.4), readable is the lowercased principal with each run outside `[a-z0-9]` replaced by `-`, edge hyphens trimmed, capped at 32 characters and trimmed again, or `user` when empty; digest8 is the first eight hex digits of SHA-256 of `<service>\0<principal>`. Only an explicit path with no known principal uses `<container>--home--default`. Running containers still use `landoServiceContainerName` with the current app slug; only store and persisted-default naming follow the data-name slug.

For a generated persisted home on a non-custom image, a non-root principal in `preparedHomes` has its target created and owned in the existing root data-tree build step (`mkdir`, `chown`, `chmod`), including when selected implicitly by `defaultUser`. A fresh named volume seeds that ownership from the derived image; existing populated volumes keep their ownership. Home contents MUST NOT affect build keys. Legacy `/lando`, `/helpers`, and user-config-directory mounts MUST NOT return.

| Scope | Lifetime |
|---|---|
| `service` | One service in one app; default |
| `app` | Shared within one app |
| `global` | Shared across one installation's apps when supported; survives `lando destroy` |

`scope: project` is not accepted. A `ConfigTranslator` MAY rewrite it to `app` (§7.4.1). While global data storage is deferred, translating legacy `scope: global` produces `unsupported` rather than substituting another scope.

`kind: data` is the default. `kind: cache` defines a named cross-app dependency cache, auto-named by `landoCacheStoreName` as `lando-cache-<encoded key>` with `key` defaulted to `kebab(target)`, labeled `dev.lando.storage-kind: "cache"`, and removed only by `lando destroy --purge-caches` or `meta:cache:*`. Key encoding keeps canonical keys of at most 64 characters verbatim and otherwise uses `<segment(key,48)>--<sha256(key)[0:8]>`. Canonical `nuget` and `composer` caches keep their names. Cache kind is global by nature; combining it with `scope: service` is a planning error. It is distinct from data movement (§10.11).

Storage string shorthand and `mounts:` or `volumes:` volume entries without a source use `landoServiceStorageName`: `<container>--storage--<segment(target,48)>-<sha256(target)[0:8]>`, with service scope. Exclude shadows use `landoServiceShadowStoreName`: `<container>--shadow--<segment(target,48)>-<sha256(target)[0:8]>`. Both build `<container>` from the data-name slug via `landoServiceContainerName` and always hash the exact canonical target because `/foo/bar` and `/foo-bar` have the same readable words. `segment(value,n)` lowercases, replaces every run outside `[a-z0-9]` by `-`, trims edge hyphens, caps at n, and trims again. An empty shadow-target segment becomes `shadow`; an empty anonymous-storage target or encoded app-store/cache segment becomes `x`. Home-principal encoding uses `user` when empty, while an unknown principal uses `default`. A canonical segment matches `^[a-z0-9]+(?:-[a-z0-9]+)*$`. Compose volume entries with a source use `landoAppStoreName`: `lando-<slug>_<source>` for canonical sources of at most 64 characters, otherwise `lando-<slug>_<segment(source,48)>--<sha256(source)[0:8]>`, where `<slug>` is the data-name slug for user apps; these carry app scope. Name and scope/kind/key metadata compile together for both mount spellings. Definitions of one physical store MUST agree on scope, kind, and key, or planning fails with `LandofileValidationError` naming the store and the affected service or services. Matching metadata permits intentional sharing. Generated purpose tokens add a `--` part beyond service-type stores and cannot be eight-hex fallback digests; app stores use `_`, keeping these namespaces structurally separate. Global data storage remains deferred (#1810), as do copy, inline, template, and disabled mount kinds.

Every planned data/cache store volume Lando creates carries one label set, written by the single volume-creation owner in `@lando/container-runtime`: `dev.lando.app` (data id from `planDataId(plan)`), `dev.lando.store` (store name), `dev.lando.scope` (`service`, `app`, or `global`), `dev.lando.volume-instance` (a per-creation generation id that every volume-delete gate rechecks live before a name-addressed removal), the ownership pair below, `dev.lando.data-root` on app-owned stores (§5.3.1), the scratch labels when a scratch app planned the store, and `dev.lando.storage-kind: "cache"` for cache stores only, so its absence means a data volume. The data id preserves the original data name across app renames and falls back to `plan.id` when `identity.dataName` is absent. Containers, networks, and service selection retain the runtime app id. Providers MUST NOT invent additional labels for planned store classification. Prepared file-sync targets follow their recorded runtime session/journal ownership (§10.6.3); Windows sync volumes use the runtime app id and `dev.lando.sync.*` labels. Agent transport volumes follow their bridge lifecycle (§10.4), not planned data-store retention. The `dev.lando.*` namespace is reserved. Teardown chooses deletion candidates from planned store names and ownership-selector matches, and proves each candidate through the ownership proof below before removal, never by name or by a label subset: plain destroy retains data volumes, `--volumes` removes the app- and service-scoped data volumes the selector proves this app owns, `--purge-caches` removes caches, and `dev.lando.scope: "global"` data volumes stay. Provider receipts report actual removal counts as `volumesRemoved: { data, cache }`. App and global destroy results report `dataVolumesRemoved` and `cacheVolumesRemoved`, each true only when at least one named volume of that class was removed; neither proves complete cleanup.

**Anonymous volumes have container lifetime.** A planned store is a named volume: every `storage` entry, every `volumes:` or `mounts:` volume form (including the bare `/path` spelling), home persistence, exclude shadows, caches, and file-sync targets. Only named volumes are subject to the retention rules in this specification. No retention rule or volume flag addresses anonymous volumes, as defined by the provider `apply` contract in §5. Whenever Lando removes a container (destroy, rebuild, create-config recreate, removed-service convergence, scratch and global teardown, ownership-inventory cleanup, and helper and ephemeral containers), the provider MUST request runtime removal of that container's unused anonymous volumes (Docker-compatible `v=true`) and MUST NOT remove a named volume by that path. An anonymous volume another live container still uses stays, by runtime rule. User-app `stop` (whole-app and `--service`) and bare `restart` keep containers, so their anonymous volumes survive, like the writable layer, until something removes the container. Selected restart removes a container, and with it that container's anonymous volumes, only when it replaces that container (§6.15); a failed or interrupted start retains live resources unchanged (§6.15). Ordinary `start` and selected `restart` announce every replacement and name the anonymous volume paths the provider reports for the removed container (§6.15). This is container-scoped removal, not a prune: Lando MUST NOT enumerate or remove anonymous volumes it did not just detach, including ones left by earlier revisions. Data that must outlive a container MUST be declared as a store.

**Ownership proof and selection.** Two further labels carry volume ownership, and they are not interchangeable:

- `dev.lando.volume-owner` records the canonical app root verbatim for app-owned storage. A global cache instead uses a reserved logical class owner; its creator's app id is not ownership proof. A global cache created before class ownership carries its first app's coherent ownership pair (owner root plus the selector derived from it); because volume labels cannot change, that persisted pair still proves the volume is Lando's shared cache on that provider, never that its creator owns it.
- `dev.lando.volume-selector` packs provider id, data id (`planDataId(plan)`), owner key, and volume class (optionally scope) into one `:`-joined value. A global cache substitutes its class identity for the data id and includes global scope. A daemon-side selector is an enumeration hint; exact deletion also verifies the ownership proof and generation.

The invariant: the selector's owner key is `appIdentityKey("owner", <owner>)` from `@lando/sdk/schema`, where the owner is the canonical app root for app-owned storage and the reserved class owner for a global cache, the same derivation the planner stamps onto `AppPlan.identity`, so both labels are derived from one root. One owner in `@lando/container-runtime` emits the pair together and every reader resolves ownership through the same function; a label is never written without its partner, and no call site re-spells the key or falls back to a raw root. A plan that carries no `identity` is migrated at read time from `plan.root` through the same derivation (the planner assigns `root` from `identity.appRoot`, so the key is byte-identical), never written in a second selector format. Only volumes predating the owner-key selector format carry selectors that cannot match and are neither adopted nor pruned by selection; recovery of those volumes goes through the proof label and the documented adoption paths, not through a looser selector. Volumes already carrying the ownership-complete format remain selectable using their recorded app/data id. This invariant governs storage ownership. Scratch routing uses the separately namespaced route owner defined in §10.2 and does not change volume or snapshot ownership.

Global-app storage uses the native slug `global-<token>` (§10.1) for generated names, while `dev.lando.app` remains `global`. User containers and networks follow the current slug; generated user storage follows the retained data-name slug. Explicit store names remain verbatim. New app-owned planned stores carry `dev.lando.data-root` with the canonical data root verbatim; class-owned caches, file-sync targets, and agent-transport volumes are outside this generic label contract. A foreign data-root label cannot authorize reuse or removal, including for non-cache stores with global scope. A missing label follows the unknown-owner rule in §5.3.1. An unproven volume is not replaced with empty storage. Ordinary destroy retains named stores; `--volumes` selects app- and service-scope data, and `--purge-caches` selects caches. Non-cache global-scope stores survive app teardown and are not shared across installations.

Scratch storage substitutes `<scratch-id>` for the app slug in the same owner functions: storage string shorthand uses `<container>--storage--<segment(target,48)>-<sha256(target)[0:8]>` and Compose named sources use `lando-<scratch-id>_<encoded source>`. It labels volumes with `dev.lando.scratch: "TRUE"` and `dev.lando.scratch-id`, and rewrites global scope to app scope unless `--share-global-storage` is present. Scratch destroy removes effective service/app storage unless `--keep-volumes` is used (§21). Explicit data-store names stay verbatim, catalog-owned stores use `serviceStoreName(role)`, and generated home stores keep their own naming rule.

### 6.6 Endpoints, hostnames, and routes

`EndpointInput` accepts a checked shorthand string or a closed object discriminated by `kind` (`internal` network or Unix, `published` network). Shorthand is an ASCII string `protocol:port` or `name=protocol:port`: lowercase protocol `http|https|tcp|udp`; optional alias `[A-Za-z0-9][A-Za-z0-9_-]*` (case-sensitive, no trimming); decimal port 1 through 65535 with no leading zero, sign, decimal point, exponent, or whitespace. Load-owned expressions and data from `load()` or `import()` MAY supply shorthand. The loader MUST strictly decode the resulting data without interpreting it as expression source (§7.2). There is no shorthand for host publication, Unix sockets, `primary`, or `appProtocol`; unnamed shorthand supplies neither a name nor `primary`. Decode maps shorthand to an internal network object. Encode MUST emit `kind` objects. `_tag` and mixed `_tag`/`kind` records are excess authoring keys. `EndpointPlan` uses the same `kind: internal | published` discriminator on every plan and applied-state variant; there is no live dual-key API. Plan-only fields such as `scan` and publication observations stay off Landofile `EndpointInput`. Compose `ports[].name`, route string selectors, and historical applied names remain lenient under their existing schemas so punctuation-bearing aliases stay addressable.

`InternalEndpoint` carries a network protocol and port or a Unix `socketPath`. `PublishedEndpoint` permits `http`, `https`, `tcp`, or `udp` and requires `publication`; `{}` requests defaults. Default bind is `127.0.0.1`; omitted `hostPort` requests provider assignment. Runtime assignments are provider observations (§5.3, §6.10) and never rewrite desired state. Unix sockets cannot be published.

The shorthand alias grammar applies only to the scalar spelling. Object names in `EndpointInput` and `EndpointDeclaration` retain the string contract and are subject to logical listener invariants below.

**Logical listener identity.** Network endpoint entries are facets of a logical listener identified by container port plus transport, where `http` and `https` imply `tcp`. One listener MAY carry several facets: an internal entry beside one or more publications, each with its own bind address or host port. `EndpointRef` (`port`, `transport`, sorted unique `names`, `primary`) is the public reference to a listener; `groupLogicalEndpoints`, `endpointInvariantIssues`, and `selectHttpEndpoint` in `@lando/sdk/schema` are the only grouping, invariant, and selection rules, and every consumer uses them.

- `name` is an alias of the listener. Different facets of one listener MAY carry different aliases, and repeating a name on facets of the same listener is allowed; the same name on two different listeners is an `alias-collision`. Unix endpoints own their names in the same alias space.
- Explicit protocols of one listener MUST agree; `http` beside `tcp` on one port is a `protocol-conflict`. A publication synthesized from `ports:` with no matching declaration is `tcp` or `udp` and is not an explicit protocol declaration.
- Optional `primary: true` (the only accepted value) marks the logical primary network listener regardless of facet count. At most one listener per service MAY be primary (`multiple-primary`). Marking a listener primary is metadata: it changes selection and reporting, never what the daemon launches or whether a host port is published.
- Optional `appProtocol` is opaque application-layer metadata preserved verbatim. It is never a URI scheme, never promotes a `tcp` listener to HTTP, and never affects selection or scanning.

Invariant violations are shared resolved-Landofile findings at `services.<name>.endpoints` under `landofile.service`. Lint reports them as violations; planning aggregates them as `ValidationIssue`s inside one `LandofileValidationError` before provider action. A service with invalid endpoints is unavailable for route binding, not a service with zero HTTP listeners.

**One mandatory normalizer, after every declaration.** The provider-independent endpoint projection (§6.11.0) gathers service-feature declarations followed by app-feature declarations, then MUST normalize them with the effective service config and the effective post-merge authored routes (service `routes:` followed by top-level `proxy:` entries, retaining source paths). Lint and planning MUST share this projection. Planning retains its original contributions for finalization; it MUST NOT invoke declaration callbacks again or obtain additional endpoints from feature application. Finalization MUST normalize the original declarations and effective routes, never treating synthesized output as a declaration.

An explicit `endpoints:` list, including `endpoints: []`, MUST replace type and app-feature declarations and synthesis from `ports:` and `expose:`. This does not suppress declarations from effective authored routes. A valid numeric `endpoint` selector on an effective service `routes:` or top-level `proxy:` entry MUST declare an internal HTTP listener at that container port if the service has no declared network listener there. The normalizer MUST add it after the authoritative endpoint list when one exists, or treat it as a late declaration when synthesizing Compose facets; matching TCP `ports:` publications and `expose:` listeners therefore use HTTP without changing any requested host bind. Repeated numeric selectors on a service at one port declare one listener. An existing declared HTTP or HTTPS listener keeps its protocol. A numeric selector that would depend on an explicitly declared TCP or UDP listener MUST report a protocol conflict at the route entry rather than silently changing its protocol. An HTTPS backend MUST be declared as `https` on the selected port; the route's public scheme does not change an implied listener's HTTP protocol. Both halves of `scheme: both` with that numeric selector MUST bind the same listener. A string selector, an omitted selector, and a generated default route MUST NOT declare a listener. Only the effective post-merge authored route set participates. Without an explicit `endpoints:` list, contributed listeners survive, `ports: []` is not an opt-out, and `ports:` and `expose:` retain their ordinary synthesis and metadata inheritance rules. Neither image metadata, port 80 by itself, `ports:`, `expose:`, nor `appProtocol` implies HTTP. Providers and consumers MUST use the normalized listener facts and MUST NOT re-derive them from transport configuration or routes.

Evaluated numeric selectors MUST satisfy `PortNumber` before listener derivation. Known TCP or UDP type and feature declarations veto implication at their port even when replaced by an explicit list, including `endpoints: []`; an explicit authored HTTP(S) listener at that port overrides this veto. An independent UDP facet MUST NOT block a surviving declared HTTP(S) listener, and synthesis from a Compose UDP publication MUST NOT block an implied HTTP listener. A protocol conflict MUST be reported once per original authored entry, even when overlays split `scheme: both` across effective entries. Unavailable contribution facts MUST NOT authorize implication. Native generated TLS demand MUST be determined before implication, and scratch hostname rewrites MUST occur after derivation and binding.

**HTTP selection never falls back to list order.** `selectHttpEndpoint(endpoints, selector?, preferredScheme?)` is the one selection rule. An authored name or numeric selector restricts candidates to that alias or port and is authoritative: the scheme preference is ignored entirely, so a route may deliberately select an HTTP backend or the opposite protocol. Without a selector, an optional `http` or `https` preference first restricts HTTP(S) candidates to listeners that serve that protocol when any exist; the ordinary primary/unique-listener rule then chooses within that set. When no listener serves the preferred protocol the full HTTP(S) set keeps its current meaning. A call with no preference retains its current meaning. Route binding derives that preference through the shared `routeListenerPreference(scheme, generatedCertificate)` rule: an HTTP route prefers an HTTP listener, and an HTTPS route prefers an HTTPS listener only when the service holds a Lando-generated certificate (`certs === true`), so finalization stamps `backend.tls` and the router can verify the backend. Without one, an HTTPS route passes no preference and falls back to the explicit primary, the single listener, or the ambiguity error. `selectHttpEndpoint` itself keeps its literal preference semantics; binding, default discovery, lint, `app:open`, and sharing all call the derivation instead of hard-coding a scheme, so two unmarked HTTP and HTTPS listeners are ambiguous without a generated certificate. A mixed-protocol listener stays a `protocol-conflict` and is never disambiguated by preference, and list order never decides. A service whose generated default route, or an authored route without `endpoint`, is ambiguous fails planning with `LandofileValidationError` and remediation to mark one listener `primary: true` or name the endpoint; `app:open` and sharing never pick an ambiguous target by order. A TCP primary beside one HTTP secondary (Mailpit's SMTP primary and HTTP UI) selects the HTTP listener for routes while `ServiceConnection.endpoint.primary` still identifies SMTP.

HTTP(S) network objects in plugin `EndpointDeclaration` MAY supply sparse `scan` defaults for `path` and `okCodes` (§6.11.0, §10.5.3). Landofile `EndpointInput` MUST reject `scan`. Matching publications synthesized from `ports:` inherit the listener defaults. Defined contradictory defaults for one logical endpoint fail normalization; omission can inherit, and equivalent status-code sets are not contradictions. Explicit `endpoints:` replaces contributed listeners and their scan defaults. Final planning resolves endpoint defaults below explicitly supplied global and service scanner fields, storing the effective policy on the endpoint; absent metadata on historical applied plans uses service-policy fallback rather than type-name inference. Scan metadata does not change listener identity, routing selection or host publication and is not a readiness contract.

**Authored route binding is a shared validation check.** Every evaluated authored entry under service `routes:` or top-level `proxy:` MUST bind through that same HTTP selection rule after the normalizer has applied effective numeric route declarations (§6.6). Protocol conflicts between a numeric selector and an explicitly declared TCP or UDP listener, missing HTTP listeners for non-declaring selectors, selectors that match no HTTP listener, and ambiguous selection are indexed `landofile.route` findings in lint and issues in planning's aggregate `LandofileValidationError`. Conflict evidence is keyed by route identity and source path, not by display text or filtered-list ordinal. The binding result is pure and shared with runtime route assembly. A single-scheme route binds once; `scheme: both` binds HTTP then HTTPS as two independent plans, each deriving the route-listener preference above from its own effective scheme (an omitted scheme means `https`). Both plans retain the entry's filters, path prefix, source attribution, and an explicitly authored selector. A selection failure in either half fails the whole authored entry; a route is never partially published, and the two plans are never recombined even when both select the same backend. Historical and plugin-contributed `scheme: both` plans stay readable and are normalized by the same per-scheme publication rule when assembled. It retains the effective path (`["services", name, "routes", index]` or `["proxy", name, index]`) separately from authored source provenance and the display key, even when earlier entries were malformed or blocked. Remediation distinguishes declaring HTTP from selecting among existing HTTP listeners. Binding validation does not contact the listener. Automatic route generation/selection and assembled-route conflicts remain planning-only (§7.8).

`hostnames:` adds provider-network aliases; each entry MUST satisfy `DomainName` once evaluated. The planner adds `<service>.<app>.internal` when `sharedCrossAppNetwork` is supported. Whenever a service joins the shared cross-app network, its realized alias set MUST contain the canonical qualified alias `<service>.<slug>.internal` exactly once, unioned with any additional authored aliases, including when the authored alias map is empty; `landoServiceNetworkAliases` in `@lando/sdk/schema` is the only derivation.

Authored `extra_hosts` host names and planned `HostAliasPlan.hostname` values MUST satisfy `HostAliasName` in `@lando/sdk/schema`: a DNS-shaped name whose labels use letters, digits, hyphens, and underscores (no leading or trailing hyphen, at most 63 characters per label and 253 overall), with no wildcard, scheme, port, path, whitespace, or trailing dot. Underscores are allowed because `/etc/hosts` and Compose names use them. Resolved-Landofile validation reports `landofile.hostname` at `["services", <name>, "extra_hosts", <host>]` when a host fails that grammar, skipping blocked or pending expression sites. Final plan decode rejects a contributed host alias that is not a `HostAliasName` at `["services", <name>, "hostAliases", <i>, "hostname"]`.

Every DNS name a service answers to MUST be its own. Within an app, service keys, `hostnames:` entries, `networks.default.aliases`, and the derived `<service>.<slug>.internal` names form one namespace, and each authored network's member aliases and derived `.internal` names form another; names compare case-insensitively. A name claimed by two services in one namespace, two services whose derived container names collide (§10.1), and an authored single-label name shaped like a Lando container name (`lando-…--…`), fail lint and planning as `landofile.dns-name` at the later entry. A service repeating a name it already claims is not a conflict.

Every key under `services:` MUST satisfy the `HostAliasName` grammar because peers, probes, and the router resolve it on the app network. Authoring and effective validation report invalid keys at `services.<name>` independently of the service body; lint uses `landofile.validation`. A fragment's `!reset` still names a service and MUST use a valid key, even if composition removes that entry. Once the app slug is known, lint and planning check the derived `<service>.<slug>.internal` length even when a service value is unresolved or blocked. A derived name over 253 characters fails at `services.<name>` as `landofile.dns-name` with reason `invalid-service-dns-name`, before any route or certificate is derived. Plugin clones bypass authored decoding, so the planner checks both constraints when materializing a clone and reports `CloneError` with reason `invalid-name`.

The authored service map enforces `HostAliasName` with a property-name check. This does not narrow the `ServiceName` brand or historical plan schemas.

Routes live under top-level `proxy:` or preferred service `routes:`. Every `RoutePlan` has a resolved `backend` with service, protocol, and port; proxies MUST NOT guess. The backend MAY also carry plan-only verified TLS intent, `backend.tls: { caId, serverName }`: it means the router MUST verify the backend under that Lando certificate authority and name, and it never carries PEM, a host path, a leaf private key, or a skip-verification option. Finalization stamps it on every route whose backend speaks HTTPS on a service that holds a generated certificate, whatever the public scheme: a service asks Lando for that leaf in order to serve it, and the router's system trust can never verify it. A backend of a service with custom certificate material or none keeps the router's ordinary system trust, which preserves external and custom HTTPS endpoints. Planning rejects intent on a backend that does not speak HTTPS without narrowing historical schema decoding; `RoutePlan` remains an applied-state component, so absent intent and historical `both` plans stay readable. Shorthand normalizes to `hostname`, `scheme`, `endpoint`, `pathPrefix`, and `filters`. Shorthand and object routes share hostname and path-prefix constraints: in object form `hostname` contains only the host pattern, with any port in `endpoint` and any path in `pathPrefix`, and an explicit `pathPrefix` MUST begin with `/` and contain no whitespace, query string, or fragment. Each hostname label is at most 63 characters and the whole hostname at most 253. The constraints apply to concrete values, so the planner's resolved-Landofile validation (§7.8), shared by lint and planning, checks every route after its expressions are evaluated and reports every invalid field in one run. `RoutePlan.hostname` and optional `RoutePlan.pathPrefix` use the public `RouteHostname` and `RoutePathPrefix` schemas, and final plan validation enforces those grammars for authored routes, generated defaults, and plugin contributions. Invalid object fields identify `hostname` or `pathPrefix`, invalid shorthand identifies the route entry, and both carry actionable remediation. Invalid authored route fields are `ValidationIssue`s that planning aggregates in one `LandofileValidationError`; `RouteInputError` is reserved for conflicts between assembled routes.

**HTTPS routes MUST be certificate-coverable.** When a route's effective scheme is `https` (the default) or `both`, `certificateNameForHostname(hostname)` in `@lando/sdk/schema` MUST yield a `CertificateName`. The helper returns a certificate name unchanged; maps a hostname with at least two labels whose `*` characters occur only in the leftmost label to `*.` plus the remainder (`*-app.lndo.site` becomes `*.lndo.site`, `api*.app.lndo.site` becomes `*.app.lndo.site`); and otherwise returns undefined. Authored failures are `landofile.route` findings at the shorthand entry or object `hostname` field, with remediation to move the wildcard leftmost or use the object form with `scheme: http`. Final plan validation applies the same rule to every route, including generated and plugin-contributed ones. Coverage is planning policy, not `RoutePlan` grammar (the `RoutePlan.hostname` description states it), so applied state recorded before a route became invalid stays readable for observation and teardown (§5.5.2), and deep-wildcard hostnames stay valid `RouteHostname` values on `scheme: http`. Docs MUST state that a partial leftmost wildcard is served by the broader `*.<rest>` SAN.

`RouteInputError` carries required `path` and `otherPath` arrays of effective coordinates, including a service path for a generated default route. Optional `file` and `otherFile` name physical files for the respective sides. Keep explicit files; otherwise use each side's exact authored origin independently. The primary `file` may fall back to the discovered Landofile; never guess `otherFile`.

Non-empty filter overlays merge by `name`, then unnamed `kind` identity, and retain authored order; an explicitly empty overlay clears inherited filters (§7.2). Authored filters, plan filters, and applied filters use `kind` on every branch (`RouteFilterKind`); a same-name entry whose `kind` changes is replaced rather than deep-merged. The legacy filter `type` key is not accepted. Prefix stripping MUST NOT be implicit (§10.2). Layered route matching uses the same scheme, case-insensitive hostname, and path-prefix identity as planning (§7.2), regardless of shorthand or object spelling.

The built-in filter kinds are `stripPrefix`, `addPrefix`, `requestHeader`, `responseHeader`, and `redirect`. Plugins contribute `routeFilters:`. Middleware identity continues to embed the kind value (for example `-f${index}-${kind}`) without a new naming prefix.

Default route hostnames are `<service-part>.<app-slug>.<domain>`, where `<domain>` is the global `proxy.defaultDomain` (default `lndo.site`). It MUST satisfy `DomainName`: dot-separated ASCII letter, digit, and hyphen labels without empty labels or leading or trailing hyphens, at most 63 characters per label and 253 overall; schemes, ports, paths, whitespace, trailing dots, and wildcards are invalid. Global-config decoding and schema-validated writes reject other values, and `lando config set --dry-run` performs the same validation without writing. `defaultRouteHostname` derives both the default route hostname and its certificate SAN candidate. It retains a lowercased service key that already forms valid DNS labels (including multi-label keys such as `8.3`); otherwise, as for a key with underscores, the shared segment normalizer collapses non-alphanumeric runs to hyphens, trims edge hyphens, and caps the result at 63 characters, using a short hash if empty. This derivation does not change service keys, container names, aliases, or authored routes. The planner MUST validate each generated route hostname with `RouteHostname` before binding and report an overlong hostname as `landofile.route` at `services.<name>`, with remediation naming `proxy.defaultDomain` and authored routes. Generated route conflicts MUST use service paths for their sources.

When a service authors neither `services.<name>.routes` nor `proxy.<name>`, core finalization routes that hostname over HTTPS to the listener the HTTPS route-listener preference above chooses: the generated HTTPS listener when the service holds a generated certificate, otherwise its primary or single HTTP(S) listener. Discovery passes an unselected normalized default route to the same binder rather than turning its own choice into an authoritative selector; it MAY record the resulting alias or port on the plan afterward for reporting. `none` generates no route and `ambiguous` fails planning; an explicitly empty route list still suppresses defaults, and an explicit `endpoints:` still replaces type and app-feature discovery while numeric authored routes may still declare listeners. Service types contribute endpoints, not default routes. A service that authors either gets exactly its authored routes, so an explicitly empty list opts it out of routing without affecting published endpoints. LAN publication is opt-in and warns. Internal endpoints never bind the host.

Service types MAY contribute default checks (§10.5.2) for the endpoints they declare, such as a `tcp` check for a database, and `service-error` rules for their own server pages (a web server's 502 when its upstream is down). Authored service-level `checks` tune or disable them. Types never contribute `expected` or `app-error` rules; those come from profiles and the Landofile.

Scratch plans apply the `ScratchHostnameSuffix` hostname transform unless suppressed by `--hostname` or `--no-hostname-suffix` (§21.9.2).

**Cross-app route priority.** Every app a router serves has its routes merged into that router's one table, so `RoutePlan.priority` is one shared space, not a per-app ranking. The planner derives priority from the route alone: wildcard-hostname routes occupy the band `ROUTE_PRIORITY_WILDCARD_BASE` (2) through `ROUTE_PRIORITY_WILDCARD_BASE + ROUTE_PATH_WEIGHT_CAP`, exact-hostname routes occupy `ROUTE_PRIORITY_EXACT_BASE` through `ROUTE_PRIORITY_MAX`, and within a band the path-prefix length widens the priority up to `ROUTE_PATH_WEIGHT_CAP` so bands never overlap. `@lando/sdk/schema` owns these constants. For any two routes on concurrently applied apps that match the same request, an exact hostname MUST win over a wildcard and a longer path prefix MUST win over a shorter one, independently of how many routes each app declares and without relying on a router's own rule-length tie-break. The derivation MUST NOT include a plan-size or in-plan-index term: a plan ranked in isolation MUST compose correctly with plans it cannot see. The diagnostic fallback keeps `ROUTE_PRIORITY_DIAGNOSTIC` (1), below every app route, and a router that contributes its own routers MUST pin them above `ROUTE_PRIORITY_MAX` or an app claiming that hostname captures them. Backend TLS intent never changes a route's intrinsic rank, and per-scheme plans rank each half independently from its own hostname and path prefix. This does not introduce cross-app hostname ownership: two apps MAY still claim overlapping hostnames; only the more specific claim wins deterministically.

### 6.7 Native health and lifecycle readiness

Disabled objects MUST validate every supplied sibling, including `kind: none` and effective Compose disabling. Normalization MUST discard executable fields but retain validated settings and execution metadata as `kind: none` when any remain; an otherwise empty disabled object becomes `false`. Role validation MUST still reject unsupported native execution metadata. Authored `kind: http` requires an absolute `http://` or `https://` URL and runs a single GET inside the service container through the in-container helper (`probe-http`); status codes 200 through 399 succeed, redirects are not followed, and TLS certificates are not verified. Authored `kind: tcp` requires a TCP port (1 to 65535) or a TCP listener `target` and dials through `serviceListenerTarget` (the same managed-network host catalog TCP probes use) via the helper (`probe-tcp`). HTTP and TCP probes MUST reject `executionTarget: host` before action with `HealthcheckTargetUnsupportedError` and service-or-command remediation. Missing `url` or `port`/`target` MUST fail planning with `LandofileValidationError` at the corresponding field. Native `healthcheck` of either kind compiles to the same helper argv in create requests; lifecycle readiness executes them through the shared runner.

`HealthcheckInput` accepts `false`, command forms, or an object. `false` disables the corresponding policy. A non-empty string is a shell command and a non-empty bare string array is literal argv, both shorthand for `{ command }`; Compose `CMD`/`CMD-SHELL`/`NONE` markers are interpreted only in an object's `test` array. `load()` MAY provide any form (§7.3). Forms are interpreted after authored composition. Literal `false` replaces lower probes wholesale, and a higher object then replaces that scalar rather than reviving its discarded probe. Object disabled spellings (`disable: true`, `test: [NONE]`, `kind: none`) are ordinary mappings during composition, not reset barriers; inherited siblings remain unless replaced or reset explicitly. Literal `false` remains `false`; disabled objects retain normalized settings as described above. Lando keys retain precedence over equivalent Compose fields. Shared execution metadata (`target: service | host`, optional `user: ContainerUser`) MUST survive normalization with either dialect and MUST NOT select the Lando dialect by itself. An authored `false` drops the service type's default for that policy only. `HealthcheckRunner` executes `HealthcheckPlan` through `runProbeDetailed`, one of two entry points (`runProbe`, `runProbeDetailed`) to the shared retry driver. `withDeadline` and `raceJoined` in `@lando/sdk/command-result` join cancellation before settlement. Service execution uses the selected `RuntimeProvider.exec`; host execution uses the host runners (§10.5.1).

**Dialect validation.** Before normalizing either probe object, Landofile load MUST refuse conflicting Lando and Compose fields that survive from the same file and layer. The `LandofileValidationError` MUST identify each conflicting Compose field and its source, with the replacement spelling and units. For example, `command` with `interval: 1s` requires `intervalSeconds: 1`, or a Compose `test` in place of `command`. Different retained sources MAY contribute different dialects; the existing normalization precedence applies and lint warns (§7). Shared fields such as `retries` do not select a dialect. Compose `start_interval` is preserved as a lossless duration string under extensions; Lando health and readiness author numeric `startIntervalSeconds`, kept separate from that Compose field. Under `readiness`, `startIntervalSeconds` paces the engine's readiness runner on every provider. Under `healthcheck`, it lowers to the preserved path `healthcheck.start_interval`, which only a provider declaring it in `composePreservedPaths` realizes (§5.4): Docker Engine at API 1.44 or newer, and the Lando-managed Linux runtime from 0.1.9, whose service scheduler applies it (§5.8.1). Realization follows Docker's rule: while the container is `starting` within its start period, the check runs every start interval; after the first success, or once the start period ends, it runs every interval, and failures after the start period count toward retries. System Podman and the Lando-managed macOS and Windows machines refuse it. A refusing provider refuses it during planning, before provider action, with `CapabilityError` whose remediation moves the cadence to `readiness.startIntervalSeconds` or removes the field, led by the provider's withheld remediation when it lists one. When both a Lando start-interval field and a conflicting Compose twin survive from the same source, load rejects them; across different sources lint warns.

**Independent policies and defaults.** Both authored `healthcheck` and `readiness` accept disabled, string, argv, and normalized command/timing object forms through `HealthcheckInput`. `ServicePlan.healthcheck` is ongoing native container health; only this field enters native create requests and Compose output. A feature MAY contribute stronger `ServicePlan.readiness` through `setReadiness`. Authored `healthcheck` overrides only native health, and authored `readiness` overrides only lifecycle readiness. Omitted readiness MUST preserve contributed readiness, otherwise `effectiveReadiness(service)` selects effective native health. Authored `readiness: false` MUST produce explicit `kind: none`, blocking fallback while preserving process-running and completion supervision. `healthcheck: false` disables native/image health without disabling explicit or contributed readiness. `ServicePlan.readinessSource` records only `authored` or `contributed`; healthcheck fallback and historical unknown provenance are derived. Every barrier, app-build gate, and `service_healthy` dependency MUST use effective readiness. A healthy dependency requires an enabled readiness probe; planning MUST reject a disabled target rather than relax the gate. Policies and resolved listener identity participate in cache/fingerprint identity. Readiness provenance is retained as plan metadata, not execution intent. MongoDB's contributed readiness proves final-server protocol access on its declared listener, not authentication or agreement between Landofile credentials and persisted users.

**Execution location and identity.** Authored `target` defaults to `service` and lowers to plan `executionTarget`, separate from persisted listener `target: EndpointRef`. Native `healthcheck` MUST reject `target: host` or ANY explicit probe `user`, including disabled objects, before action with `HealthcheckTargetUnsupportedError` and move-to-readiness remediation; explicit `target: service` is a no-op. Readiness supports service probe users without changing main-process identity or native monitoring. Host readiness requires its own authored/composed command and MUST inherit no type command, listener, or container user. Host plus user, listener, or missing command MUST fail planning before mutation with `HealthcheckTargetUnsupportedError` at the authored readiness field. Host execution is CLI-current-identity at app-root cwd, Bun Shell for strings (subject to the host shell dialect check, §3.4) and exact ProcessRunner argv, never a provider VM, sandbox, or permanent monitor. It MUST NOT depend on routes or dependent services behind its own gate.

A native healthcheck is container-only; execution-target validation still applies after successful materialization of a pending `service.port` expression in its command. An effective host readiness command instead refuses `service.port` during Landofile admission (§7.3.1).

**Declared probe targets.** A service-executed command `HealthcheckPlan` MAY carry `target: EndpointRef` naming one of the service's declared logical listeners by port and transport (§6.6); `names` and `primary` are descriptive. This listener identity is distinct from authored `healthcheck.target: service | host` and plan `executionTarget`. `serviceListenerTarget` in `@lando/sdk/schema` is the single derivation of the host a targeted probe dials: the service name on the private app network when the plan has one, otherwise the canonical `<service>.<slug>.internal` alias on the shared network. A plan with no managed network or a loopback host fails planning with `LandofileValidationError` before any provider action; an authored custom probe may describe a different topology. `requireDeclared` guards authoring, while a type-contributed probe relaxes it: an explicit `endpoints:` list replaces exposure and routing declarations (§6.6), so a service whose author hid or narrowed its endpoints still listens on its own port, and contributed health MUST keep dialling that listener through the same derivation rather than lose its check. One container-runtime probe compiler resolves the target and supplies it to the command as `LANDO_PROBE_HOST` and `LANDO_PROBE_PORT`; native create requests, dependency gates, Compose output, fingerprints, and the engine runner MUST use that compiler rather than interpolating hostnames separately, and an untargeted command receives no injected target. Probes MUST NOT discover interface addresses, fall back to loopback, or add a provider networking API. App-scoped `ServiceConnection` listener hosts (§6.10) use the same derivation. Listener, protocol, and executable failures MUST yield short safe evidence: the runner retains bounded redacted stderr together with the safe target, attempt count, elapsed time, and exit code rather than reducing the failure to `exit N`.

Start, restart, rebuild (full or selected), and global-service start MUST complete a concurrent readiness barrier before publishing `post-app-start` or `post-start`. One private engine startup-completion owner (`completeStartup`, taking a closed discriminated request union rather than a callback bag or phase array) runs every post-apply sequence. User start runs app build, route publication, then readiness. Selected restart and rebuild run file-sync start for the selected services, the selected app build (forced only for rebuild), publication of the composed route table, minus the routes of unselected services observed down, with the router progress phase when non-empty, then readiness. Ensure-global runs readiness; global groups run concurrent readiness per applied group, aggregate failures, and publish routes only when every group succeeded. Scratch publishes routes before readiness; router setup or publication failure MUST fail a routed scratch's acquisition whether or not it binds public URLs (§21.9.2). Before readiness, each policy that bound public URLs verifies successful publication against the prepared authorities, failing with `RouteUrlBindingError` (`authority-changed`) on disagreement. Publication failure itself retains the actual failure and remediation.

**Catalog database liveness is independent of Landofile credentials.** PostgreSQL keeps `pg_isready`; MySQL and MariaDB keep `mysqladmin ping`. MongoDB readiness is a credential-free protocol `ping` against the declared listener (no `MONGO_URI`, disposable `HOME`, no rc). SQL Server health and readiness use local catalog `sqlcmd` against `master` with `SQLCMDPASSWORD` from `MSSQL_SA_PASSWORD` and a fixed `SELECT 1`; exit 0 or the tools18 `Login failed for user 'sa'` diagnostic means the server is up; missing client, TLS, timeout, or transport failure means it is not. Authored probe replacements and timing remain authoritative. These probes prove process/listener liveness only; they are not application login or credential agreement.

**Credential convergence is not a readiness sub-barrier.** After a successful provider apply, the activation applier (§6.15) runs catalog credential convergence once while the activation environment session is open and before `completeStartup` (app build, routes, remaining readiness, and post-start hooks). Convergence does not partition, replace, or replay public readiness, and it MUST NOT lift readiness ahead of build or routes. Ordinary readiness failures remain ordinary readiness failures. A convergence failure is a best-effort warning and MUST NOT fail start.

Startup completion owns nothing before or during apply: user-app admission and provider apply each have one private owner (§6.15), and initial inspection, accelerated journals, agent acquisitions, pre/post events, and scans stay with the operation that runs them. Readiness is never skippable, success events publish only after completion succeeds, global rebuild revalidation still precedes its post-event, and selected requests carry the full classification plan including unselected job consumers. Unsupervised exited services and exhausted healthchecks MUST fail with `ServiceNotReadyError`, naming the service, reason, available stopped-container exit code, bounded redacted log tail, observed listener evidence when available (below), and remediation. User/global startup failure or interruption MUST preserve established resources at every phase. Ordinary blocked provider gates use `ServiceStartError`; exceptional causes propagate under §5.7 and §10.5.1. Retry MUST reconcile observed resources with desired intent. Scratch ownership follows §21. Interruption MUST stop waiting, cancel in-flight probes, and still propagate to the CLI. Prepared sync targets, sessions, and an unfinished accelerated-start journal stay for the next start to resume (§10.6.3). URL-scan failures MUST warn, not fail startup. A post-start check reporting router `upstream-unreachable`, or a marker-free transport failure or timeout, observes the service's expected TCP listener at most once per service per scan when it matches the scanned endpoint. Available evidence supplies the warning's finding and action, worded for an unreachable endpoint rather than a failed readiness probe, and the check result's `listener` field. Ready, app-error, service-error, and unmatched-route checks add no provider work.

Selected start uses the same startup-completion owner and runs the selected app build, composed routes, and selected readiness in that order. It MUST NOT start file sync again after apply: it prepares and flushes the selected sessions before apply (§6.15, §10.6.3). The subsequent URL scan concerns the services in this start, and is non-gating.

A target of a `service_completed_successfully` dependency in the full plan is a completion-intent service: it MUST have verified exit code 0 and MUST skip waiting on readiness probes, including selected operations. Other unsupervised services MUST remain running throughout readiness; services without an enabled readiness probe settle against their current container start, with the remaining host-side wait bounded to two seconds despite engine clock skew. Container replacement or restart invalidates unsupervised readiness. Successful rows are `ready` after effective readiness passes, `running` without an enabled probe gate, or `completed` after verified successful completion.

For non-completion services with an authored restart policy that enables supervision, a coherent observed `restarting` state takes precedence. An `exited` service under `on-failure` requires a verified nonzero code; `always` and `unless-stopped` permit a warning on verified exit. A newer start time for the same known container proves a restart even if it is observed running again. That observation can settle as `restarting` under `always` or `unless-stopped`; under `on-failure` it still requires evidence of a nonzero exit unless the provider reports `restarting`. Warning and final settlement accept the original container at its initial or a newer start time; a replacement or older start time fails. Missing `restart` and `restart: no` remain strict. Exhausted readiness MUST fail for every service: restart policies do not restart a running-but-unhealthy process. Provider inspection failure MUST use reason `inspect-failed` and MUST NOT become a supervised warning. The `LANDO_SERVICE_RESTARTING` warning MUST name the service and reason and include available terminal exit code and a short redacted log tail. `restarting` rows MUST use a warning tone. Non-instant readiness waits MUST publish progress naming the waiting services and settle their rows individually.

Lifecycle readiness MUST probe immediately. Failures during `startPeriodSeconds` MUST NOT count against retries; probes during that period use at most a one-second interval and return on first success. After that period, allow at least one attempt, otherwise `retries` attempts at `intervalSeconds`, each bounded by `timeoutSeconds`. Native scheduling remains the container runtime's responsibility.

**Listener authority.** A service type sets `ServicePlan.listenerAuthority` (`ListenerAuthority` in `@lando/sdk/schema`) when something other than Lando configures its planned primary listener: `application` for a language runtime whose app owns the listener, with the port variables Lando projects; `launcher` when an authored `command` or `entrypoint` replaced the Lando launcher that set it, with the argument to pass; and `image` when a custom image or build owns the daemon configuration, with the setting and file. It is configuration advice, never socket attribution. When a `not-listening` or `loopback-only` observation matches the authority's port, the first remediation line remains one diagnostic action and the authority line follows it. Without an observation, a lifecycle probe failure, a probe timeout, or a failed `service_healthy` gate (provider or app-build) uses the authority line, which starts with one action, as its first remediation line, except when the provider reports `dependencyExit` or `dependencyUnavailable`. A gate uses the dependency's authority, never the blocked consumer's. A `listening` observation omits it. `ServiceInfo` projects it for `lando info` and MCP. It survives plan serialization and the plan cache and never enters container create identity.

Both provider dependency gates report verified terminal exits as `ServiceStartError.details.dependencyExit` with dependency `service`, `gate`, `status` (`exited` or `dead`), and `exitCode` when verified. `dead` never supplies an exit code. The error names the blocked consumer, identifies the exit before naming the blocked gate, and names the dependency's logs command in remediation. Exit evidence survives an empty log; any captured tail comes from the verified ID. If completion cannot be verified or the dependency disappears or is replaced, report `details.dependencyUnavailable` with `service`, `gate`, and reason `missing`, `replaced`, or `unverified`. Either diagnostic omits listener diagnosis, listener advice, and name-based log capture. Terminal evidence stops retries, including during the start period. Required edges remain blocked and optional edges may proceed past a gate verdict; provider operation failures propagate for both. A one-shot completion requires an observed `exited` state and verified exit code zero. Post-apply supervision uses planned restart policy and MUST verify the original container identity and start time both before warning and at final settlement.

Readiness remediation MUST address the app kind: user apps use `lando logs -s <service>` and `lando start`; global apps use `lando global:logs -s <service>` and `lando global:start`; scratch apps use their scratch-addressed inspection surface and MUST NOT prescribe user-app start. Provider observation failures prescribe `lando doctor`, not service logs. The supervised warning follows the same app-kind rule, and so does a failed dependency gate's `ServiceStartError`, which names the failing dependency's logs command instead of the blocked service's. Other provider apply failures on a scratch app MUST NOT prescribe user-app start.

**Observed listener diagnosis.** A lifecycle probe failure or timeout (`ServiceNotReadyError`), a failed provider `service_healthy` dependency gate (`ServiceStartError`, observing the failing dependency), and a failed app-build healthy gate (`BuildPhaseFailedError`) carry optional `listener` evidence (`ListenerObservation` in `@lando/sdk/schema`), except when the provider reports `dependencyExit` or `dependencyUnavailable`. The expected listener is the effective readiness probe's declared TCP target, otherwise the service's unique marked primary TCP logical listener; host-executed readiness and services without either get no observation. Lando reads the LISTEN entries of `/proc/net/tcp` and `/proc/net/tcp6` through the provider's exec boundary, bounded to two seconds and 128 KiB and propagating interruption. Lifecycle and app-build gates collect this evidence only after failure, concurrently with log-tail capture where applicable. The same bounded read is also permitted for the failed post-start reachability checks described above and for explicit `lando doctor --app` inspection (§10.9). Successful gates and ready, app-error, service-error, and unmatched-route checks MUST NOT trigger collection, and collection MUST NOT persist state or run a monitor. The evidence describes bindings in the service's network namespace, not process ownership: `not-listening`, `loopback-only` (every binding on the port is loopback), or `listening`, with a bounded list of observed bindings. A failed, empty, truncated, or unparseable read omits the field and MUST NOT be reported as an absent listener. The message leads with the finding and the remediation's first line is one action; a `port:` change is suggested only when exactly one other TCP port is observed on a typed service's primary listener. App-build failures put the finding in the blocked step's summary.

The user/global startup retention rules above apply to the selected realization. Explicit retirement of a superseded realization under §7.4 is a committed reconciliation step that a later launch failure does not undo; its named data volumes and ownership inventory MUST stay. Removing the owned containers of services a whole-app user start no longer names (§5.3.1) is committed reconciliation too, not failure compensation: a later failure does not restore them, and their named volumes stay.

`ServiceNotReadyError` applies only after committed provider apply. Ordinary blocked provider gates use `ServiceStartError`; exceptional causes propagate under §5.7 and §10.5.1. The retention policy above applies. Supervision MUST NOT relax `service_healthy` or `service_completed_successfully` gates. Scratch acquisition runs the barrier but readiness failure and interruption follow §21 scope cleanup and `--keep-on-failure`, not user-app retention.

Language runtimes (`node`, `python`, `ruby`, `go`, and `dotnet`) MUST NOT infer default health or readiness checks from ports or commands; endpoints remain available and authors MAY declare either policy explicitly.

The engine owns each service/host readiness attempt through an invocation-scoped `executeReadinessAttempt` delegate (§5.3, §10.5.1). Providers retain resource ownership and start-graph scheduling. Full engine-owned scheduling is deferred pending provider-neutral per-service lifecycle primitives and partial-apply/cancellation ownership; this contract MUST NOT be represented as a completed scheduler extraction.

### 6.8 Certificates and security

`certs:` accepts enabled, disabled, a certificate path, or custom certificate/key paths. `CertificatePlan.cn` and `CertificatePlan.sans` (and the matching `CertificateSpec` and certs-feature config fields) MUST be `CertificateName` values from `@lando/sdk/schema`: an unbracketed IPv4 or IPv6 literal, or a `HostAliasName`-grammar DNS name optionally prefixed by a whole leftmost `*.` label. A generated leaf certificate covers the service name, `<service>.<app>.internal`, configured `hostnames:` (passed as-is), route hostnames mapped through `certificateNameForHostname` (skipping undefined results, which remain only for HTTP-only routes after the §6.6 coverage check), `localhost`, and `127.0.0.1`, deduplicated case-insensitively. Planning records that request as the `CertificatePlan`, selects the issuing `CertificateAuthority` by id from plugin contributions without constructing it, and binds the Lando-owned leaf paths (§10.3). Planning MUST NOT ask a certificate authority to issue; issuance belongs to apply (§10.3). Mandatory identities that are not certificate names, and a certificate authority that cannot be selected, fail planning with `LandofileValidationError` at `services.<name>.certs`. Paths are exposed as `LANDO_SERVICE_CERT` and `LANDO_SERVICE_KEY`.

`security.ca:` and aliases `cas`, `certificate-authority`, and `certificate-authorities` add project CAs. The `lando.security` feature mounts and installs them; core defines intent, not distribution mechanics.

Global `network.ca` and `network.proxy` each expose `injectIntoServices`. CA injection defaults on; proxy injection defaults off. Per-service `security.inheritNetworkCa` and `security.inheritNetworkProxy` override those defaults. Only services composing `lando.security` participate; `l337` and raw Compose do not auto-inject.

The effective CA set is global `network.ca.certs`/`LANDO_NETWORK_CA_CERTS` followed by project CAs, deduplicated by content. Open-ended host Dockerfile drop-ins are a non-goal. Installation precedes `build.app:` and tooling. Injected CA identity participates in artifact `buildKey` calculation. Providers MUST honor resolved proxy/CA settings for every Lando-initiated pull and build regardless of service injection.

When CAs are injected, services expose `SSL_CERT_FILE`, `SSL_CERT_DIR`, `NODE_EXTRA_CA_CERTS`, `LANDO_CA_BUNDLE`, and `LANDO_CA_DIR`; service types MAY add equivalents. Proxy injection writes `HTTP_PROXY`, `HTTPS_PROXY`, and `NO_PROXY`; credentials MUST be redacted from logs, telemetry, caches, rendered config, and build transcripts.

### 6.10 Service info

An observed completion-intent service, including a dependency-environment job, reports `completed` only on verified exit zero. A nonzero exit is not successful readiness (§6.7).

Provider-neutral `ServiceInfo` contains `app`, `service`, `api`, `type`, `provider`, `primary`, `status`, the required array `connections`, optional `logSources`, and optional `creds`. `status` is the shared `ServiceState` vocabulary: `unknown`, `stopped`, `starting`, `running`, `healthy`, `unhealthy`, `ready`, `completed`, `restarting`, `paused`, or `error`. `StartedService` (`name`, `state`, `connections`, optional `container`) in `StartAppResult.servicesStarted`, global ready output, restart, and rebuild carry the same `connections` contract; `ServiceConnection` is the only connection-address contract. `ServiceInfo` also carries optional `url`, the value `{{ services.<name>.url }}` resolves to at that moment: the primary route's URL (§7.3.1) taken from its assigned route connection, read from the applied route table when the app has one and from the shown plan otherwise, and absent when no concrete route, router authority, enabled router, or readable applied state exists. `container` is the provider's `ServiceContainerChange` report of what apply did to that service's container, including a replacement reason and the anonymous volume paths that went with it; it is absent when the provider reports no container-level outcome.

**`ServiceConnection`.** Every connection carries `host` (hostname or unbracketed IP), `endpoint` (the `EndpointRef` of the logical listener it originates from, §6.6), `scope`, `source`, `protocol`, `binding`, and `state`. The union is:

| `scope` | `source` | `protocol` | `binding` | Meaning |
|---|---|---|---|---|
| `app` | `listener` | `http`, `https`, `tcp`, `udp` | `assigned` | The service key on the per-app network plus the listener port, for every planned network listener including the container side of a published port |
| `host` | `publication` | `http`, `https`, `tcp`, `udp` | `assigned` or `pending` | A direct host publication of the listener |
| `host` | `route` | `http`, `https` | `assigned` or `pending` | Router ingress for a `RoutePlan`; adds `pathPrefix`, retained in the URL |

An `assigned` connection carries `port`, `url`, `alternateUrls`, and `state` in `active`, `inactive`, or `unknown`. A `pending` connection carries `state` in `inactive` or `unknown` and MUST NOT carry `port`, `url`, or `alternateUrls`: a configured publication whose host port is unassigned, or a route with no ingress authority, is represented without an invented address. The declared listener `protocol` is independent of `appProtocol`, and an unknown secondary TCP publication is never reported as HTTP. Addresses come from the §6.7 listener-target derivation: the service key on the per-app network, or the canonical `<service>.<slug>.internal` alias only when the service has no per-app network and sits on the shared network alone. Unix sockets are excluded because their sharing is not established.

**URL formatting.** One central formatter produces `url` and `alternateUrls` from host, port, protocol, and route path. Hosts are lowercased and stored unbracketed; a wildcard or loopback bind address is reported as the host a local client dials (`0.0.0.0` and `127.0.0.1` as `localhost`, `::` as `::1`). URLs bracket IPv6 hosts, omit default ports `80` and `443` for `http`/`https`, preserve route `pathPrefix`, and keep `tcp://` and `udp://` for unknown transports. Client URI policies are scoped to the declared database listener of the service type: PostgreSQL emits the encoded user and database and never the password; memcached emits `memcached://`; Valkey emits `valkey://` with a `redis://` alternate. Arbitrary secondary or unplanned bindings are not painted as database connections.

`DatabaseConnection` (§6.12.4) is a separate planned credential/primary-port fact, not a scoped address. PostgreSQL URI enrichment reads its canonical family, user, and database only when the TCP listener's container port matches the fact's port; an assigned host publication may use a different port in its URL. Missing facts produce the generic connection URI, without environment scraping or guessed credentials. Neither password descriptors nor resolved passwords enter canonical or alternate addresses, and observation never reads a secret store to format them.

**Observation versus plan.** Configured listeners, publications, and routes are always retained, including pending dynamic ports, so a stopped service reports its addresses as `inactive` rather than erasing them. An `app` listener is always `assigned`; its state follows the service state and is `inactive` when the container is proven missing. A `host` publication is `active` only when an actual `PublicationObservation` binding matches its listener, bind address, and any explicit `hostPort` (§5.3); the connection then reports the observed host port. Without a matching binding, an explicit `hostPort` stays `assigned` and a provider-assigned port stays `pending`, each with state `inactive` (evidence present, or service inactive) or `unknown`. An observed binding that matches no planned publication is still reported, as a `tcp` or `udp` publication of an unnamed, non-primary listener, never as HTTP. A route is `active` only from matching `RouteEvidence` (§10.2); with no configured or observed ingress authority it is `pending`, and with routing disabled it is never `active`. Service state maps to connection activity through one shared rule: `stopped`, `completed`, `paused`, and `error` are `inactive`; `starting`, `restarting`, and `unknown` are `unknown` unless absence is proven; `running`, `healthy`, `unhealthy`, and `ready` permit `active`. Active never asserts health. One collector/projector powers `info`, `start`, `restart`, `rebuild`, and global status as well as the hyperlink, `app:open`, and scanner consumers; no command concatenates routes or erases state on its own. Only `host` connections that are `assigned`, `active`, `http` or `https`, and not wildcard hostnames are eligible for hyperlinks, `app:open`, and HTTP scans; `app` connections are never host-clickable. `info` reads the applied plan when one exists, so connection metadata describes the last applied plan, not necessarily an unapplied Landofile edit.

`ServiceInfo` also projects safe planned per-service metadata when its source exists: `artifact`, `user`, `home`, `workingDirectory`, resolved `appMount` (the `role: app` bind entry), `hostnames`, `certs`, and `health`. These fields remain schema-optional for historical or hand-built plans; absence means no fact was recorded, not an inferred default. `artifact` carries either `{ kind: "ref", ref, digest? }` or `{ kind: "build", contentHash? }`; build context, arguments, inline specs, commands, environment, and raw provider extensions never enter info. `hostnames` is the stable deduplicated list of aliases from the canonical service network attachments, empty when no network attaches the service. It excludes route hosts, certificate SANs, and host-file aliases. `certs` carries only `{ state: "none" | "generated" | "custom" }`. `generated` is a planned source: Lando issues and maintains the certificate when it applies the service (§10.3), and the value does not assert that files exist yet. A historical generated `{ cn, sans, caId }` certificate plan projects `generated`, while the certificate feature records custom or disabled provenance as a private scalar `@lando/core/certs` service extension that projects `custom` or `none`. Only those two exact scalar extension values are accepted; malformed, missing, and historical facts leave `certs` absent. The public `CertificatePlan` remains the original generated leaf certificate struct. `health` carries the planned ongoing healthcheck kind and timings when declared, plus the provider's existing inspected health state (`unknown`, `starting`, `healthy`, or `unhealthy`); it omits probe commands, URLs, and targets. With `starting`, `healthy`, or `unhealthy`, `health.checkedAt` carries the completion time, on the engine's clock, as a UTC ISO-8601 string with millisecond precision (`YYYY-MM-DDTHH:mm:ss.sssZ`), of the newest native check recorded in the current run: the `End` of the last `State.Health.Log` entry whose `Start` is at or after `State.StartedAt`, from the same inspect response, so it adds no provider call. Engines spell that time differently (Docker in UTC with nanoseconds, Podman in the host's local offset), so the provider boundary normalizes it. Docker keeps the previous run's log across a restart, which is why older entries are skipped. It is omitted for `unknown` (including `serviceHealth: none`), `not-monitored`, a container that is not running, and missing evidence, and it never exposes check output. It is not proof of readiness or that checks are still scheduled. A readiness-only probe does not count as an ongoing healthcheck. The optional JSON-safe `providerInfo` slot is reserved for explicit provider-supplied details and remains absent while no such source exists. It is the sole provider-specific field; everything else is provider-neutral. Human info summaries show artifact and user, and plain text adds detail rows without changing its service table columns.

`ServiceInfo.readiness` MUST describe configuration, not last-proof state. Its states are `disabled`, `not-configured`, and `not-observed`; its sources are `authored`, `contributed`, `healthcheck` (fallback), `unknown` (historical provenance), and `none`. Safe metadata includes execution target, `userSource`, listener, timings, command presence, and configuration pointer, never raw commands. Native `health` uses existing provider observations (`healthy`, `starting`, `unhealthy`); explicit native `none` is `not-monitored`, and missing evidence is neutral `unknown`. A provider declaring `serviceHealth: none` (§5.4) has nothing that schedules native checks, so its inspected state is not evidence: any native check other than an explicit `none`, whether declared or inherited from the image, projects `unknown` whatever the engine last recorded, and the global ensure cache does not treat that `starting` as a reason to re-ensure (§18). Info MUST NOT run probes, add provider inspect calls, write durable state, infer readiness from running/native health, or imply a last-readiness proof. Start's `ready` result remains observed gate success for that invocation. Durable proof is deferred pending generation/probe identity, provenance, failure/interruption invalidation, and orphan handling.

`home` is schema-optional for historical or hand-built plans; newly planned services always carry it. Info projects `home` unchanged when present: human output labels the retained persisted-home mount `home`, shows one `home` explanation and `services.<name>.home.path` hint only for unknown automatic persistence, and adds no home row for authored or disabled homes.

`ServiceInfoLogSource` distinguishes file sources from pathless console aliases (§6.14). A console alias carries `strategy: console`, its selected `stream`, id, and availability state with an optional reason; it MUST NOT fabricate `path`, `required`, or `timestamps` fields. Human summaries render the destination as `console/stdout` or `console/stderr`. File-source info retains its path and existing availability contract.

Structured `EndpointPlan` stays the plan contract and `PublicationObservation` stays the provider contract. Library consumers read `EndpointPlan` through `App.plan`; observed bindings come from runtime inspection, not from `App.plan`, `ServiceInfo`, or `app:config`. `ServiceInfo` carries connection addresses only.

`ServiceInfo.mounts` projects every user-visible planned mount (entries with `origin: integration` excluded) with `origin: planned` and its `provenance` (`authored`, `service`, or `derived`), plus any extra mount the container inspection reports with `origin: runtime`. Each entry carries `observation` (`present` when the container's mount table confirms it, `missing` when the container lacks it, `unknown` without evidence) and `lifetime` (`retained` for binds and named stores, `container` for tmpfs, `unknown` for runtime-only volumes). An accelerated bind is matched against its sync volume.

`creds` exists only for opted-in types; `ServiceInfo` displays its password fields under the §6.12.4 rules, which keep published development defaults readable and mask every other value.

Application info (`InfoAppResult`) carries `app` (the current Landofile name when it loads, otherwise the recorded applied-plan name) and optional `dataName` when the observed plan's recorded data name (`identity.dataName ?? name`) differs from that app-level name. A desired-planning failure MUST NOT hide a successfully loaded current name. Service rows retain the applied runtime app id and observations. It additionally exposes optional `fileSync` (`FileSyncInfo`), separate from `ServiceInfo`. Its optional `planned` and `applied` snapshots (`FileSyncPolicyInfo`) describe desired policy and recorded applied-plan evidence respectively; missing evidence omits the snapshot. `pendingChange` compares the two snapshots when both exist and is false otherwise. Neither a snapshot nor `pendingChange` certifies running services, live sessions, or daemon health.

`InfoAppResult.appliedStateIssue` is an optional `InfoAppliedStateIssue`, present only when the app's applied-state record is protected (§5.5.2) and omitted for readable or absent state. It is a union on `reason`: `"unreadable"` or `"newer-version"`, each with `path`, `message`, and `remediation`; only the `newer-version` arm adds integer `storedVersion` and `supportedVersion`. Info MUST diagnose the record of the exact discovered app identity, never an enclosing app's readable record, and MUST do so before runtime observation can hide the issue; unrelated provider failures still propagate. With an issue present, `fileSync.applied` is `{ mode: "unknown", reason: "unknown", services: [] }` and `pendingChange` is false. Applied evidence is unknown, but service rows keep what the runtime independently shows: running, or verified stopped.

User-app info lists the union of applied and current desired services when an applied record exists; with none, it reports the current desired plan unchanged. A plain `destroy` leaves no applied record, so info afterwards matches an app that never started: its services are `stopped`, and the named stores the destroy kept appear as planned mounts with `lifetime: retained` (§5.3.1). Info adds no field for this state. Applied service metadata wins on a name collision. A desired-only row (a desired service the applied record lacks) MUST NOT claim applied mounts or connection addresses: omit `mounts` and return empty `connections`. Verified absence is `stopped`; absent proof MUST NOT be invented. `app:info -s` selects from this same union without expanding dependencies or companions (§8.2).

Each file-sync snapshot carries `mode: ordinary | accelerated | unknown`, one optional app-level `engineId`, a `FileSyncPolicyReason`, and a `services` list. Each service carries its name, `mode: ordinary | accelerated | absent | unknown`, reason, `exclusions` (`kind: transport-patterns | directory-overlays | none | unknown`, exact `patterns`, and derived `overlays`), and `hostBackedIncludes` pairs (`source`, `target`). Ordinary patterns are empty. Exact includes that cancel overlays and nested host-backed includes both remain visible in this projection. Engine ids MUST NOT repeat per service. Reasons distinguish explicit/default/sole engine selection, native providers, global passthrough, no compatible engine, service opt-out, absent app mounts, and unknown history. Mode and engine identity are validated against mount/session facts; absent or contradictory explanatory metadata yields unknown reasons, not invented facts. Info MUST NOT acquire an engine, probe tools, list daemon sessions, or reselect an applied engine to construct this view.

### 6.11 Service type and feature contracts

A `ServiceType` MAY opt into `plannedPort`. This pure, deterministic selector receives only the decoded `port`, `type`, `framework`, and `via` fields before launcher expressions run, and returns a `PortNumber` or `undefined`. A type that owns listener planning MUST use the same selection as its primary listener and return `undefined` when that listener does not apply. Raw `lando` and `compose` instead select only an authored `port:` for the self scope (§7.3.1) and return `undefined` when it is omitted. Inheritance does not implicitly opt a child type in. Core MUST NOT insert the result into `ServiceConfig.port` or infer it from final endpoints, which authors may override or remove. Bundled types with a planned listener share the selector with their listener implementation.

#### 6.11.0 Planning and conformance

Core performs one deterministic pipeline:

1. Materialize each service's planner-owned expression sites in peer-reference order, selecting any needed `plannedPort` before invoking the resolver (§7.3.1). Resolve each `ServiceType` to `ServiceTypeResolution`, including parent and artifact version resolution. `resolve()` MAY be asynchronous but MUST NOT build a plan. Lower any launcher marker in the final normalized service command before feature preparation and endpoint projection.
2. Resolve the effective base defaults and `FeatureRef`s. Prepare feature occurrences once, validate effective service-feature configuration, then project endpoints through optional service declarations in stable ascending priority and optional activated app declarations in stable ascending app-feature priority. Pass effective numeric route declarations into the same pure normalizer before application, then validate authored route bindings in the shared resolved-Landofile stage (§7.8).
3. Seed `ServiceFeatureContext` from explicit base and authored environment. `lando` seeds its default feature stack; `l337` seeds only artifact/build plumbing. Retain the projected endpoint contributions, without replaying declarations.
4. Apply `ServiceFeature`s in ascending priority.
5. After every service draft is complete, apply activated `AppFeature`s in ascending app-feature priority.
6. Emit provider-neutral `ServicePlan`s.
7. Finalize once in core with capability validation, bind realization, file-sync generation, storage shadows, routes, networking, excludes, and `AppPlan` decoding.

Features MUST emit provider-neutral intent. Both `ServiceFeatureDefinition` and `AppFeatureDefinition` MAY supply typed `declareEndpoints` callbacks; these are the only feature-owned listener authority. Neither `ServiceFeatureContext` nor `AppFeatureServiceMutators` exposes `addEndpoint`. Both expose `setInit(boolean)` so a feature can contribute native container init intent (§6.2.1); a composed authored `init` value still wins over any contribution, and conflicting contributions follow the ordinary write-conflict rules. This replaces the unreleased apply-time endpoint API without a compatibility path. Declaration callbacks return encoded wire values: service features return `readonly EndpointDeclaration.Encoded[]`, and app features return a read-only record of those arrays keyed by selected service name. `EndpointDeclaration` shares shorthand and object fields with Landofile `EndpointInput` and additionally permits optional `scan` (`EndpointScan`) only on HTTP(S) network objects; Landofile `EndpointInput` still rejects `scan`. Core strictly decodes the entire callback result once during feature preparation, keeps the decoded plan-compatible contributions in the prepared snapshot, and MUST NOT log raw payloads or accept partial contributions from a failed callback. Malformed service output maps to `ServiceFeatureError` with feature id, contributing plugin identity, affected service, declaration index, and a safe field path; app output uses the same tagged shape on `AppFeatureError`. Declaration callbacks MUST be deterministic and MUST NOT mutate their input, read `ports:` or `expose:`, publish host ports, or rely on contribution order for primary selection. A type marks its primary listener `primary: true`. The single §6.6 normalizer owns publications, explicit endpoint overrides, and effective numeric route-declared listeners. Finalization MUST replay the normalizer from the original declaration inputs plus those routes rather than from a previously synthesized result. Plan and observation consumers read `EndpointPlan` with `kind`; only declaration outputs use the encoded declaration form. The app-plan cache input MUST include base, ordered `FeatureRef`s, and `AppFeature` contributions.

Declaration receives read-only resolved identity and configuration facts, including the original schema-decoded feature configuration. It MUST NOT depend on earlier `apply` mutations or application-only materialized certificate, security, or SSH configuration. It MAY consume effective `certs` intent established by the pure route-demand phase before feature preparation; lint, declaration, application, and cache identity MUST share that same resolved intent. Core shares base-default expansion, configured-ref handling, config decoding, and stable priority ordering with composition; an explicit feature ref replaces the same-id base default, and equal-priority entries retain their effective input order. Missing callbacks contribute no endpoints. Declaration Effects require no runtime services and fail through the feature's typed error channel. They MUST NOT acquire a runtime, inspect images, issue certificates, write caches, or perform general feature application. Lint MUST NOT replay `apply` to discover endpoints: application and its planner preparation may realize resources that authoring validation must not acquire.

Core MUST prepare feature definitions and occurrence order once per resolution, retaining each occurrence rather than collapsing equal ids into a map. Effective validation, declaration and application consume those prepared decisions. Original feature configuration is decoded once when validation or declaration requires it; application-only configuration MUST NOT be decoded before planner preparation. Application reuses a decoded original when applicable, but explicitly materialized certificate, security, or SSH configuration is decoded as a replacement even when empty. Materialized application configuration MUST NOT rerun Original validation or grant Original service-field claims. Private prepared values are invocation-local, not global caches or serialized plan fields.

`ServiceFeatureDefinition.validateEffective` is an optional deterministic, provider-free validation callback over `ServiceEndpointContext`: immutable final inherited normalized service facts and Original schema-decoded feature configuration, without draft mutators or required runtime services. Success returns schema-derived `ServiceFeatureValidationResult`, whose `handledServiceFields` admits `webroot`, `consolePort`, `uploadDirs`, `bucket`, and `creds`. Expected findings use the single `ServiceFeatureError.issues` channel, not a second successful findings channel. Each prepared occurrence validates once before declaration and before cache lookup, including when authored endpoints replace discovery. A failed occurrence does not declare endpoints; independent occurrences and services continue far enough to aggregate their findings. Core MUST NOT invoke `apply`, inspect images, perform network/filesystem actions, acquire provider resources or decode unrelated application-only configuration to validate.

An explicitly authored `webroot`, `consolePort`, `bucket`, or `creds`, or non-empty `uploadDirs`, MUST be handled by at least one successfully validated final feature occurrence. An authored `uploadDirs: []` clears protection and MUST NOT require a claim. A property name or value inside `FeatureRef.config`, a normalized-config field or an arbitrary endpoint does not grant support. Core aggregates explicit claims after inheritance, excluding occurrences whose configuration is substituted by planner preparation, and checks them before cache-key construction and lookup. Unsupported explicit input fails with `LandofileValidationError`, an issue at the authored service field and actionable remediation. When effective validation already failed for a service, core MUST NOT add derivative unsupported-field noise. A feature claiming `webroot` MUST actually consume the effective root for server configuration or supported context; the claim does not prove HTTP serving. Conditional mount-dependent context MUST NOT grant support without its required mount, while a genuine active webserver can handle an absolute root without an app mount. No type/provider blacklist or legacy config-key convention remains.

Every type MUST name `l337` or `lando`, return `ServiceTypeResolution`, and satisfy `runServiceCompositionContract`. `lando` receives `lando.env`; `l337` receives no injected environment or scaffolding. Only `lando.env` may invoke `buildLandoEnv`.

Contributed `logSources` MUST have unique ids and compatible strategies; file sources require absolute paths, while console aliases forbid paths. The id `console` is reserved for the implicit native source. `redirect` requires an owned build; a BYO/`l337` service may contribute file `follow` sources or pathless `console` aliases. Feature ordering and inheritance are replay-stable.

**Declared project-file inputs.** A service type MAY declare an optional finite, ordered list of app-root-relative candidate files through the existing `ServiceType.projectFiles` seam. The declaration names paths and a per-file byte cap. The planner normalizes each relative path against the canonical app root, rejects an absolute path, a path that escapes the root, and any symlinked component, then owns the bounded stat and read, the SHA-256 fingerprint, and a presence marker for every authorized candidate. The planner de-duplicates canonically equivalent paths while preserving declaration order. A physical read, kind, size, or symlink failure of an authorized candidate uses `project-file` attribution against that contained candidate path, never the symlink target (§7.8). An invalid service declaration or an invalid `packageRoot` is a service-config issue at the Landofile field, not a project-file source. The rule in this section that validation MUST NOT perform filesystem actions governs effective-feature validation; it does not forbid the planner from acquiring these declared inputs before resolution. A type MUST NOT read project files directly.

`ServiceType` declares `name`, optional `versions`, explicit `base`, optional `extends`, optional `artifacts`, `schema`, and Effectful `resolve` with `ServiceTypeError`. A type that contributes database clients may also expose pure `toolingForConnection(name, connection)`, returning their task definitions from a `ServiceName` and `DatabaseConnection`. A type that accepts `extraArgs` MUST mark the launcher it sets as accepting them (append-at-end slot) and supply token-aware reserved-option rules for the settings it owns; the engine inserts materialized tokens once and verifies the effective process after composition (§6.2). A type that never marks a launcher cannot accept `extraArgs`. `ServiceTypeError` and `ServiceFeatureError` MAY carry structured `issues` with paths relative to that service's config; the planner prefixes each path with `services.<name>`, preserving suggestions, source attribution and remediation. When `issues` is absent or empty, the failure applies to the whole service. Feature-config schema paths MUST NOT be presented as authored service fields unless a validator supplies that semantic mapping. Core MUST NOT reconstruct machine paths or suggestions by parsing prose. `ServiceTypeResolution` carries `base`, `normalizedConfig`, `features`, optional `connection` or `nonSqlCreds` (mutually exclusive), optional `tooling`, optional `connectionClientNames`, optional `logSources`, optional `sync` (`defaultDataset` per dataset kind and `postApply` tasks, §10.12.2), optional `metadata`, and optional `launchers`. Optional `launchers` is a schema-backed record from a launcher marker (`^:[a-z][a-z0-9]*(?:-[a-z0-9]+)*$`, never `:host`) to a non-empty argv prefix the service type computes at resolve time from inputs it already reads (for example Node package-manager selection). Engine lowering consumes exactly one leading marker on tooling `cmd` argv and on service `command` argv form: it replaces that marker with the declared prefix and does not rescan the expansion, so launchers never chain. A marker matching the grammar that the target type does not declare, or a marker with no command after it, fails with a located error naming the service, type, and declared launchers (tooling: per-task `ToolingCompileError` after the actual target binds, §8.5; service command: `LandofileValidationError` at `services.<name>.command`). Manager and Bundler policy live in the service-type plugin, never in the engine. `./:name` is the literal escape for an argv that would otherwise look like a marker. Authored tokens stay in the document and in `app:config`; the planner lowers only the effective command used for build key and create-config identity. Launcher facts participate in resolved-service cache identity. It MAY also declare the optional `generatedCertificateEndpoint` capability: a typed `{ port }` association, owned by the public `GeneratedCertificateEndpoint` schema, meaning an owned launcher can serve the service's own generated certificate on that HTTPS port. The resolver emits the candidate port for every Lando-owned launcher whether or not a certificate has been requested yet and whether or not the authored `user:` still lets the parent read the generated key; the certificate-demand phase, not the resolver, refuses a non-root parent, so the association also records why native TLS is unavailable. The association is active only while the effective config demands a generated certificate and the selected HTTPS route lands on that port. It is a capability declaration, not a certificate request, an extra endpoint, or a persisted TLS registry: the durable result is the bound route's `backend.tls` intent. Authored endpoint replacement keeps the association only when it still declares that generated HTTPS listener. Inheritance carries it explicitly: a child that replaces the image, supplies a replacement `build.context`, or changes the command or entrypoint loses inherited ownership. Additive `build.artifact` and `build.app` steps do not transfer ownership.

**Route-demanded generated certificates.** A generated certificate is demanded once, before immutable feature preparation, from the service-owned `generatedCertificateEndpoint` capability, effective router enablement, normalized service/top-level route intent, and authoritative endpoint overrides. HTTPS or `both` route intent that selects the generated listener, including a named selector resolving to an authoritative HTTPS endpoint on the capability's port or a default HTTPS route when discovery survives and the parent can read the key, materializes effective `certs: true` in the resolution seeds shared by endpoint projection, assembly, plan-cache identity, and tooling projection. HTTP-only, explicitly empty, router-disabled, and non-root-parent cases keep no generated leaf and no TLS listener, though an owned non-root launcher still carries the association that records the opt-out; an authored `certs` value in any form (`true`, `false`, or custom material) stays authoritative. A blocked route expression stays unavailable rather than becoming a default-HTTPS guess. Route binding reads that same decision: an HTTPS route prefers the generated listener only while the certificate is active, and a suppression (an authored `certs: false`, custom material, or a non-root parent) leaves no preference, so the route binds the plain listener and TLS terminates at the router. The same classifier reports the `service.router-tls-termination` warning (§6.11.4). The decision never contacts a certificate authority, never mutates the authored Landofile, and never reruns service resolvers or endpoint declarations. The association only drives this demand and the generated listener; finalization stamps `backend.tls` from the actual certificate plan on whichever HTTPS backend each route selected (§6.6), and no endpoint is mutated during apply.

A type MAY declare the pre-resolution `plannedPort` selector described above; that member is not inherited.

A type-contributed service feature opts an argv launcher in through `ServiceFeatureContext.setCommand(command, { extraArgs: check })`. The pure check inspects the materialized suffix and returns the first reserved argument's index and remediation, if any. `ServiceType.extraArgsRemediation` MAY be a string or a pure function of decoded `ServiceConfig`, used only when no launcher accepts the non-empty list. It does not grant support.

#### 6.11.1 Service-type inheritance (`extends:`)

Launchers merge by marker, like contributed tooling: a child entry replaces the parent's entry for that marker, and markers the child omits are inherited. Compare parent and child normalized `command` and `entrypoint` before lowering. Even if the command is unchanged, a change to the prefix the merged table selects for its leading marker revokes inherited `generatedCertificateEndpoint` ownership unless the child explicitly declares the capability. Changes to unused entries do not revoke ownership.

A type MAY extend one parent, inheriting normalized config, features, tooling, artifacts, and `sync` before child overlay. Normalized config and tooling overlay under §7.2. Feature and log-source lists merge by `id` with child precedence, and same-id feature config overlays under §7.2; an empty child list contributes nothing rather than clearing inherited entries. Inheritance has no diamonds, is bounded, and rejects cycles with `ServiceTypeCollisionError`.

Canonical credentials also survive inheritance. An omitted child credential source inherits the parent's `connection` or `nonSqlCreds`; an explicit child source replaces the parent's source as a whole, never combining both. Each raw resolution rejects simultaneous sources before a later child can conceal the invalid contribution. The nearest explicitly declared `toolingForConnection` replaces the inherited function as a whole, including an empty factory. Existing task-content merging remains unchanged.

`connectionClientNames` carries explicit generated-client provenance, not credentials or a task snapshot. A raw contribution that omits it may seed names from its own declared factory; an explicit array, including `[]`, suppresses that automatic seeding. Without an own factory, untouched parent claims survive, but any child contribution for a task name revokes that name even if its content is identical. Explicit child claims may reauthorize it through the effective factory. An own factory establishes a new claim baseline from its explicit names or its returned names present in merged tooling. Claims are deduplicated deterministically and require a corresponding task, effective connection, and supporting factory output. Direct resolutions and inheritance hops use the same normalization; composed results always carry an explicit array so planner consumers cannot recreate revoked authority by inspecting an inherited factory.

`sync.defaultDataset` and `sync.postApply` MUST merge per dataset kind. An omitted child kind inherits its parent value; a child default Dataset id replaces that kind's parent id. A child `postApply` list replaces that kind's entire inherited list in declaration order, and an explicit empty list clears it; lists MUST NOT concatenate. The final merged defaults participate in §10.12 binding selection, while an explicit binding Dataset still wins. The final task lists run under §10.12.2 grouping and ordering, never once for each ancestor.

#### 6.11.2 Declarative version pinning (`artifacts:`)

`artifacts:` maps exact versions to artifact tags and MAY reference a sibling file. Version ranges are not supported. The `ServiceType` version metadata is the single matrix for planning, docs, and tests. Unknown, absent, or unavailable versions fail before provider action with supported-version remediation and MUST NOT fall back to guessed tags. Resolved tags enter the app-plan cache key.

#### 6.11.3 Service-type-shipped tooling

`ServiceTypeResolution.tooling` merges below resolved Landofile `tooling:`. Conflicts replace whole tasks by name. After dropping ambiguous Node manager contributions (§8.5), the primary service's contribution wins if it contributes the task. Otherwise, the lexicographically first contributing service name wins. A surviving contribution defaults its target to its contributor; `toolingDefaults` fills only unset fields.

For generated connection clients, private tooling metadata records the winning task's contributing service, not another credential or task snapshot. Invocation regenerates the factory-owned defaults from ownership-matched applied connection facts, preserving current unrelated defaults and their parsed expression sites. A current authored whole-task replacement bypasses this generated-client path. Both top-level tooling and event `task:` calls obey the same rule; neither imports applied lifecycle events or old authored tooling. Missing historical connection facts or an incompatible applied client family fail with `PlanReplanRequiredError`, not desired-credential fallback.

The applied service's `serviceTypeId`, not its normalized `type` or the current desired declaration, selects the composed factory. The loaded declaration's ID must match exactly. Missing or unavailable applied declaration identity fails with `PlanReplanRequiredError`; observation and teardown remain supported. Only normal application records new applied identity, not plan-cache refresh or inference from task winners. This identity survives service-record persistence and partial application but does not change physical container-create fingerprints.

Reserved tooling names `run`, `scratch`, and `scratch:*` produce `landofile.tooling` issues in lint and planning; planning aggregates them in one `LandofileValidationError` (§7.8). Service types MUST NOT use `topLevelAlias` while the unsupported tooling-task key list (`UNSUPPORTED_TOOLING_TASK_KEYS` in `@lando/landofile`) rejects it (§8.5).

#### 6.11.4 App-scoped features (`AppFeature`)

`AppFeatureDefinition` declares `id`, optional `schema`, `priority`, optional `AppFeatureActivation` as `activatedBy`, optional `AppFeatureSelectors` as `selectors`, optional `declareEndpoints`, optional `requires.providerCapabilities`, optional `requires.globalServices`, and Effectful `apply`. `declareEndpoints` receives `AppEndpointDeclarationContext` and returns an Effect of a read-only record from selected service names to `EndpointDeclaration.Encoded` arrays, with `AppFeatureError` and no required runtime services. Returning an unselected name is a typed selector error; omitting a selected name contributes nothing to it. Activation can match service type or feature; selectors can match `types`, `framework`, `hasFeature`, `names`, or `fromConfig`. A `fromConfig` selector reads one environment snapshot shared by declaration and application, and the environment variables it reads are part of the `app-plan` cache key, so changing one invalidates the cached selection.

Activation and selection inspect immutable resolved service facts, not mutable draft results, raw authored config, or finalized plans. The facts include service identity, base, framework, primary status, the complete declared feature-id set, normalized configuration, and optional connection facts. Declaration and application MUST use the same activation and selector implementation: trigger type and feature conditions intersect, selector clauses union, and selected names are deduplicated in service order. An absent activation match is a no-op; an activated feature selecting nothing fails with a typed selector error. `AppEndpointDeclarationContext` exposes selected read-only views without mutators. `AppFeatureContext` provides replay-safe non-endpoint plan mutators across those same services. App declarations follow service declarations; app application still follows all service application, and app features order only against each other. Application cycles fail with `AppFeatureCycleError`. `AppFeatureError` includes selector, mutation-conflict, cycle and clone failures, and `ServiceFeatureError` for invalid endpoint declarations (§6.11.0).

Activation and selection decisions MUST be captured once against the resolved facts and selector-environment snapshot, then carried into application rather than recomputed. Application cannot silently drop a selected service whose draft is absent. Inactive and non-declaring app-feature configuration remains undecoded until application needs it. A plan-cache hit still performs shared preparation and declaration validation, but MUST NOT apply features or decode application-only configuration. Cache inputs retain relevant original declaration configuration separately from materialized application configuration; definitions, Effects, and prepared records are not serialized as cache inputs.

`AppFeatureServiceView.resolutionMetadata` is the optional read-only projection of `ServiceTypeResolution.metadata`, using the existing service provenance record value type. Preparation, endpoint declaration, and application MUST carry the same service-type-produced facts. These facts are not authored `x-*` fields, provider state, mutable draft extensions, or the final artifact after feature application. The engine MUST preserve plugin-owned keys without interpreting their private semantics. Consumers MUST validate required facts rather than reconstructing lost ownership from normalized config or a later artifact reference.

`AppFeatureContext.addClonedService(ClonedServiceRequest)` queues one generated companion service (§6.11.5). The request carries `from` (the parent service name), `name` (the companion's service name), `command` (a `CommandSpec` that replaces the parent's command), and optional `user`, `extraBuildSteps`, `extraEnv`, and `omitConfigKeys`. The call records intent only. The planner materializes every queued clone from its parent's completed draft after all app features have applied and before ordinary finalization, so a clone reflects every service-feature and app-feature contribution to its parent regardless of feature priority. Clones do not take part in activation or selection: no feature, including the one that requested the clone, is activated by, selects, or applies to it. Clone failures are `AppFeatureCloneError`, the `AppFeatureError` member tagged `CloneError`, with `feature`, `service`, optional `from` and `image`, remediation, and `reason`:

|---|---|

Plugins register `serviceFeatures:`, `appFeatures:`, and `serviceTypes:`; all three MUST exist in `PluginManifest` and be consumed by loading and planning.

Activated `requires.globalServices` are ensured during `pre-start` before user-app build. Missing services fail with `GlobalServiceMissingError` and installation remediation (§20.6.3).

#### 6.11.5 Generated companion services

A generated companion service is a service the planner derives from a parent service through `addClonedService` (§6.11.4). It is never authored: it has no Landofile entry and MUST NOT appear in resolved-Landofile output or be written to any Landofile.

**Shared with the parent.** A companion uses the parent's artifact build, including the parent's artifact-phase build steps other than those Lando derives from the parent's log sources; its app mount and mounts; its service-scoped stores; its resolved environment, with `extraEnv` applied on top; and its network memberships. A shared service-scoped store is the same physical store, not a copy. The parent remains its owner, and ownership seeding (§6.5) runs for the parent only. A companion without a `user` override keeps the parent's home intent and shares the parent's home store. A companion whose `user` differs from the parent's MUST NOT keep a persisted home volume and MUST NOT add a home-preparation build step: its artifact build is the parent's artifact-phase build plus its `extraBuildSteps`. A companion depends on its parent and starts after it.

**Not inherited.** A companion MUST NOT inherit the parent's endpoints or listeners, host port publications, routes, `hostnames`, network aliases, native healthcheck or readiness policy, certificates, database connection identity (`creds` and connection facts, §6.10, §6.12.4), log sources (§6.14) and the build steps Lando derives from them, or app-phase build steps (§6.13.1). A companion's container process is exactly the requested `command`: neither the parent's planned entrypoint nor the artifact's `ENTRYPOINT` applies, and the parent's server process never runs. Its healthcheck MUST be explicitly disabled, which also disables a healthcheck the artifact declares. Keys named in `omitConfigKeys` are removed from its normalized configuration. A companion is never primary and is never a SQL target (§10.7).

**Name.** A companion's name and its derived internal name (`<name>.<slug>.internal`) MUST satisfy §6.6 or planning fails with `AppFeatureCloneError` reason `invalid-name` (§6.11.4). Both MUST also be free, compared case-insensitively, among the app's service keys, `hostnames`, network aliases, derived internal names, and the other requested companions (§6.6). A name that is not free fails planning before provider action: reason `duplicate-clone` when two requests use the same `name` compared case-insensitively, otherwise `name-collision`. The planner MUST NOT rename a companion, add a suffix, or drop it to resolve a collision.

**Provenance and build identity.** The companion's `ServicePlan` carries `provenance.clonedBy = { feature, from }`, naming the requesting app feature and the parent. An inherited artifact-phase step that declares an explicit user keeps it, even when the companion overrides `user`. An inherited step without an explicit user runs as the parent's planned user, or as root when the parent plans no user; on an artifact whose default user is not root, that differs from the identity the step has in the parent's own build. Inherited steps MUST always precede the companion's `extraBuildSteps`, and only `extraBuildSteps` are attributed to the companion. A change that affects only `extraBuildSteps` MUST NOT invalidate the inherited steps' results (§6.13.5).

**Shutdown.** The parent's authored stop signal is not inherited. On a native container provider that supports an explicit stop signal, a companion uses `SIGTERM`, overriding a stop signal baked into its artifact for the parent's server. A short-running job can therefore finish within the stop grace period rather than being killed because the scheduler ignored the parent's signal.

**Shell.** A planning-time `unsupported-image` rejection applies only to an artifact reference known to have no shell: the empty `scratch` image and `gcr.io/distroless/*`. A companion on any other artifact without a shell fails in the artifact build.

**Lifecycle.** A companion is an ordinary planned service. It appears in service info, is addressable by `lando logs --service` and `lando exec`, and is accepted by every explicit `--service` selection. Whole-app `start`, `stop`, `restart`, `rebuild`, and `destroy` include it. Selected start and rebuild close over prerequisites and generated companions together: adding a prerequisite also adds its companions, and adding a companion also adds its prerequisites, including its parent. Selected restart adds no ordinary companions. Its only automatic addition is the selected consumers' dependency-environment jobs (§6.5.1, §6.15); those jobs are prerequisites, not ordinary app-feature companions. A companion that leaves the desired plan, because its request is no longer made or its parent is removed, is removed by ordinary removed-service convergence on the next whole-app `start`, `restart`, or `rebuild` and reported in `servicesRemoved` (§6.15, §5.3.1). Named data is kept. No companion-specific cleanup path exists.

**Default launchers run as the planned user.** A type's default `command` (installed when the author declares neither `command` nor `entrypoint`) runs as `ServicePlan.user`. Prefer daemon command-line configuration; when a file is required, use a path writable by the planned user and configure the daemon to read it. Volume-backed write targets require explicit ownership setup; if the provider cannot realize that ownership, planning MUST fail with `DataTreeOwnershipCapabilityError` naming the service and its effective configuration `path` as an array of segments. Shared generated assets use one helper rather than per-launcher copies. The contract is verified by the running service serving its configured content, not merely by successful planning. Provider-specific Compose overrides MUST NOT substitute for a provider-neutral ownership contract. Any remaining privilege requirements, including restricted low ports on the target runtime, MUST be documented for the affected type.

**Listen port follows `port:`.** For a typed service that plans a primary listener, its port is the applicable authored `ServiceConfig.port`, or the type or variant's published default when omitted; a configuration of that type with no primary listener has no planned port. Bundled launchers MUST configure that listener, and Lando-owned clients (healthchecks, tooling tasks, database commands, and wired consumers such as phpMyAdmin) MUST use the same port. Supported daemon-native variables for that primary listener MUST be derived from the planned port and projected into the service environment; malformed or unequal authored values MUST fail planning before provider action with an issue at that variable (`services.<name>.environment.<VAR>`). Lando MUST NOT rewrite an authored `command` or `entrypoint` to add listener flags; its author MUST configure the planned port, and can reference it with `{{ service.port }}` (§7.3.1). Authored `extraArgs` on a type that accepts them keeps the Lando-owned launcher and does not set launcher authority. When authorship removes the only Lando-owned configuration of the primary listener (launcher flags, a generated server configuration, or the baked configuration a custom image replaces), the type MUST set `ServicePlan.listenerAuthority` with owner `launcher` or `image` and the effective setting the author must supply, such as `--port 27018` for MongoDB (§6.7). Types whose daemon-native variables still configure the listener, and authored entrypoints that still receive Lando's generated arguments, set no authority. For MySQL, MariaDB, PostgreSQL, and MongoDB, a Lando-owned launcher loading `config.server` MUST pin the planned port on its command line, including the default. For Apache, the planned port determines `Listen <port>` and, for `php` via `apache`, `<VirtualHost *:<port>>`; a non-default port MUST replace the image's `Listen 80`, not add a listener alongside it. A primary port equal to a secondary listener that is open in the effective configuration MUST fail before plan-cache lookup and provider action, with an issue at `services.<name>.port` naming the occupied use; moving a secondary releases its former port. The bundled secondaries are MySQL's X Protocol listener `33060`; SQL Server's dedicated admin connection `1434`; RabbitMQ's EPMD `4369`, management UI `15672`, and Prometheus `15692`; Elasticsearch and OpenSearch `transport.port`, which Lando pins to `9300` unless an authored scalar port moves it (ranges and malformed values fail at `services.<name>.environment.transport.port`); Tomcat's loopback shutdown listener `8005` when Lando owns `server.xml`; Varnish's loopback management interface `6082` when Lando owns the launcher; LocalStack's DNS server (`DNS_PORT`, default `53`, closed when `DNS_ADDRESS` is `0`); Solr's loopback Jetty stop listener (`STOP_PORT`, which a Lando-owned launcher derives as the planned port minus 1000; a derived value below 1 fails at `services.<name>.port` unless an authored distinct `STOP_PORT` is valid); and the MinIO console and mail UI/API listeners below. Varnish's healthcheck probes its primary HTTP listener, not its management interface. Each bundled typed service declares its listener contract once, with a variant entry wherever a framework or mode changes the mechanism: primary port, daemon name, integer port variables, host:port and list-valued bind variables, host defaults, fixed and port-derived secondary listeners with their override variables, and the setting an authored launcher or custom image must supply. Validation and listener authority consume the declaration, published service-type facts derive from it, and a generated reference page renders it. The catalog conformance suite keeps independent literal expectations for how each type applies the planned port, rejects collisions with every effective declared secondary, proves that moving or disabling a secondary releases its former port, and rejects an unequal or malformed authored value for every environment-variable mechanism. RabbitMQ MUST also reject an invalid distribution port or one colliding with AMQP or a reserved secondary listener, identifying `services.<name>.environment.RABBITMQ_DIST_PORT` when it is authored and `services.<name>.port` when the distribution port is derived. Fixed secondary ports MUST be documented as limits in the type's guide. Each type contributes that listener with `primary: true` so selection and reporting identify it without relying on list order (§6.6); a type whose primary is not HTTP (Mailpit's SMTP) marks it primary and contributes its HTTP UI as an unmarked secondary. The primary listener survives `ports:`: publishing it, publishing other ports, or authoring `ports: []` keeps it in the plan with its marking; only an explicit `endpoints:` list removes it (§6.6).

Raw `lando` and `compose` passthrough retain author-owned daemon configuration; their authored `port:` supplies only the self fact. The Tomcat custom-image/build exception below and PHP's custom-image/build exception (§6.12.5) also retain author-owned daemon configuration.

**Language runtimes project the planned port.** `node`, `python`, `ruby`, `go`, and `dotnet` have no default server launcher: their default command is a keep-alive and the application owns its listener. Each MUST project its planned port, `port:` or the selected framework's default, into the port variables below under the same derived-and-validated rule as daemon-native variables, so an unequal or malformed value from any environment source (service `environment`, env files, or `serviceDefaults.environment`) fails planning at `services.<name>.environment.<VAR>`. Host defaults are ordinary overridable environment values and are not validated. Projection does not prove that application code reads these variables; each runtime guide MUST name the servers that read them and the ones that still need command-line arguments or application code. A higher-precedence author-owned listener setting, such as ASP.NET Core's `ASPNETCORE_URLS` or a launch profile, remains the author's.

The plan records `listenerAuthority.keepAlive: true` when a language runtime selects its idle command without an authored `command:` or `entrypoint:`. The fact survives plan caching and lets HTTP checks distinguish an intentionally idle listener from a server that failed to start (§10.5.2).

**Stock Python project environment.** With the catalog artifact (including a canonically equivalent reference), no replacement `build.context`, and an enabled app mount, Python declares a dependency environment at `<app mount target>/.venv` keyed on the catalog interpreter version (§6.5). Activation defaults `VIRTUAL_ENV` to that path and puts its `bin` first on `PATH`; authored environment wins. A canonical `.venv` include, `:` in the target, or any authored mount at `.venv` opts out of preparation and activation. Authored process fields do not opt out.

Preparation MUST use the absolute stock Python and uv paths, refuse a symlinked target or nested mounts before modifying the tree, and keep a venv only if its config, prefix, interpreter major/minor, and base interpreter are valid. It recreates an invalid venv with `--clear --system-site-packages`, clearing contents rather than the mount point; the system-site-packages setting itself is not a validity check. A framed SHA-256 digest covers input mode, preparation revision, full interpreter version, pinned uv version, and the names and bytes of `requirements.txt` and its transitive requirements and constraints. References resolve from the referring file, MUST stay within the app mount source, and are bounded by depth and count. Missing files and cycles fail preparation; local package contents are not tracked. A valid tree with unchanged digest MUST skip uv and pip entirely. Otherwise preparation removes `.lando-dependencies` before mutation and additively installs with `uv pip install --python <target>/bin/python -r requirements.txt`; it MUST set tree ownership for the writer and publish the marker atomically only after successful preparation and rechecking inputs. Failed preparation MUST NOT leave a success marker. The no-input case prepares only the venv. The job uses the global uv cache with copy link mode (§12.4). Automatic installation is limited to `requirements.txt`; `pyproject.toml` and `uv.lock` remain launcher-owned (§8.5).

**Node version selection.** The Node type's supported majors, their LTS codenames, and its `lts` alias derive from a committed pin of Node's release schedule, so retargeting `lts` is a reviewed pin update, never an upstream tag movement and never a wall-clock comparison during planning. `lts` selects the newest supported major the pin records as LTS. Bare `node` alone infers its runtime from the selected package directory: it reads `<packageRoot>/.nvmrc` first (exact and minor pins keep their precision; a major, codename, or `lts/<codename>` selects that major's channel; `lts` and `lts/*` select the `lts` alias; `lts/-N` selects the Nth older supported LTS major). For bare inference, a declared `engines.node` in that same selected directory's `package.json` MUST contain the whole selected channel. Without `.nvmrc`, that `engines.node` selects the `lts` major when it contains that whole channel, otherwise the highest supported major whose whole channel it contains, and fails when none qualifies. Bare version inference never falls back to an ancestor or app-root manifest; package-manager selection uses its own nearest-declaring walk (§6.12.1 below). An explicitly versioned Node type ignores `.nvmrc` and `engines.node` entirely: its runtime comes from the type. A failure attributable to a declared project file, including its read, size, kind, parse, and constraint failures, reports that file; an invalid `packageRoot`, and the absence of every version input, are reported at the service declaration.

**Node package managers.** Every catalog-owned Node type, bare or explicitly versioned, selects a package manager from the nearest declaring `package.json`. Candidates are `<packageRoot>/package.json`, then the app-root `package.json`, canonical de-duplication, no intermediate walk. `packageRoot` defaults to `.` and, for a catalog-owned Node type, MUST name an existing app-contained directory; it changes neither the mount target nor the working directory.

**Node app-mount presets.** Node services with an app mount declare `node_modules` as an app-root-relative exclude, including custom images and services that select Bun. Catalog-owned services with a non-root `packageRoot` also exclude `<packageRoot>/node_modules`: workspace installs may hoist dependencies to the app root, while standalone packages may install them in the package directory. These paths are POSIX-normalized and de-duplicated. Yarn Plug'n'Play is the exception below. Authored excludes add to the presets, and exact authored includes cancel the matching excludes (§6.4).

**Yarn Plug'n'Play mounts.** Catalog-owned Node types declare bounded `.yarnrc.yml` inputs at `packageRoot` and the app root, canonically de-duplicated. For selected Yarn 2 or later, parse those files as YAML and use the nearest declared `nodeLinker`; absence means `pnp`. Invalid YAML or a non-string `nodeLinker` fails planning with a project-file issue at `nodeLinker`. No other ancestor files or `YARN_NODE_LINKER` environment values are considered. Because PnP does not maintain a `node_modules` tree, the `pnp` linker declares neither a `node_modules` preset exclude nor a preset include. Authored excludes still apply. Yarn Classic and the `node-modules` and `pnpm` linkers retain the Node presets. `.yarn/` is unchanged. Yarn may remove an existing host `node_modules` in PnP mode. After changing linkers, run whole-app `lando start` to converge the mount plan; selected relaunch rejects changes to accelerated sync sessions with that remediation.

**Eager candidate snapshot.** The planner takes an eager bounded snapshot of every authorized candidate. An unreadable, oversized, non-regular, or symlinked root candidate fails planning even when a nested candidate would win. A readable shadow that was not selected is fingerprinted in full and never parsed.

**Declaration fields.** A present top-level `packageManager` wins; otherwise `devEngines.packageManager` is read. A manifest that declares neither falls through to the next candidate; a malformed declaration fails at its file and field and never defers further. The secondary `devEngines.packageManager` entry is an object whose `name` is required whenever that field is read, and whose `version` is required when that field is selected as the winner for Yarn or pnpm; a non-object `devEngines`, a non-object nested entry, a missing or invalid `name`, a missing `version` on a winning Yarn or pnpm entry, an invalid version range, or an invalid `onFail` fails at that file and field. `onFail` accepts absent, `error`, `warn`, or `ignore`.

**npm and bun.** A recognised valid `npm` or `bun` declaration is a no-op that stops fallback: it never provisions Yarn/pnpm and never continues the candidate walk. Correct winner version is required only for Yarn and pnpm. For `npm` and `bun`, normal checks still apply, including same-file compatibility when both `packageManager` and `devEngines.packageManager` appear in one manifest; the no-op does not skip those checks and does not fail planning solely for lacking an exact provisionable pin.

**Yarn and pnpm pins.** A winning Yarn or pnpm pin MUST be an exact release (prerelease allowed), with an optional authored `sha224`/`sha256`/`sha384`/`sha512` integrity passed through unchanged; ranges, tags, aliases, URLs, and `v` prefixes fail with remediation naming the field to edit. When both fields appear in one manifest, the top-level entry wins and `devEngines` is only a secondary compatibility check: Lando validates the secondary shape and name; an omitted secondary version is allowed; an exact or range secondary version MUST admit the winning pin; a secondary integrity while the winning pin has none is ambiguous and fails with remediation to move the hash onto the winning pin; both integrity hashes present and identical are accepted; both present and different conflict. A name mismatch or a range that excludes the pinned version fails by default (`onFail` absent or `error`) and is suppressed only under `onFail: warn` or `onFail: ignore`. There is no planner warning channel, so `warn` is silent success. `onFail` never suppresses the winning pin's shape, exactness, or integrity requirements.

**Host acquisition and launchers.** The host acquires exact releases from npm: `pnpm`, `yarn` for Classic, and `@yarnpkg/cli-dist` for Berry. Planning rejects Yarn 2.0.0 through 2.4.0; upgrade to 2.4.1 or later, or use a custom image. The verified package tree is copied to the root-owned, world-readable `/usr/local/lib/lando/package-managers/<name>/<version>` prefix. Only the selected family (`yarn`/`yarnpkg` or `pnpm`/`pnpx`) gets launchers, and each executes its designated package bin with Node. A `--version` smoke through the primary launcher fails the build if the selected runtime cannot run the manager. Lando does not install or invoke Corepack for this feature.

Launchers prevent nested manifests and Yarn's `yarnPath` from selecting a different binary, without disabling project dependency downloads or integrity checks. pnpm 9 and 10 disable auto-selection and package-manager strictness; pnpm 11 sets `pmOnFail=ignore`. Yarn Classic ignores `yarnPath`; releases before 1.22.21 lack the override for the conflicting-manifest check. Berry keeps recursive scripts on the installed bundle and leaves other `.yarnrc.yml` settings in effect. The installed manager can run without network access or container-start provisioning as any service user. Global installs such as `pnpm add -g` and `yarn global` are outside that guarantee. The image's npm and npx stay untouched. A same-name Landofile `globals.yarn` or `globals.pnpm` entry with the same exact version is dropped as redundant; a different version is a located Landofile error at `services.<name>.globals.<manager>` naming the project file, field, and pin, because the declaration owns it. Any unknown manager name fails planning.

**BYO ownership.** An explicitly versioned catalog Node type whose authored `image` differs from the resolved catalog reference, or that supplies a replacement Compose `build`, owns its toolchain—the planner reads no Node project files for it, emits no manager provisioning, and rejects an authored `packageRoot` on that field; an authored image reference equivalent to the resolved catalog reference remains catalog-owned. Bare `node` with an image or replacement Compose build fails with a suggestion to use an explicit type. Authored `globals` and additive `build.artifact` / `build.app` scripts remain normal and do not transfer toolchain ownership. `yarn set version`, `corepack`, `npx corepack`, and project-local binaries are separate entry points; an edited pin takes effect on the next converging `lando start`.

**Command markers.** The Node service type declares `:node-local` on all Node services, using `pnpm exec` or `yarn run` for the selected family and `npm exec --no --` for npm, Bun, no declaration, or BYO. It declares `:node-install-run` only for catalog-owned Node with npm, pnpm, Yarn, or no declaration (npm). Unlike the installed manager binaries described above, this command marker performs the project's install at execution time and may use the network, update a lockfile, and run package lifecycle scripts. It runs the requested package script through the same manager only after a successful install; every process start repeats the install, but a warm `lando start` that leaves the process running does not. Managers run scripts through a shell that forwards no signal, so the install runner starts the script in its own process group, forwards stop signals to that whole group, and exits only after the group is empty; a server's shutdown handler therefore completes before the container's init exits. Both markers keep the selected command's working directory (§8.5).

**Python command marker.** Python declares `:python-local` only when the catalog image receives the Lando-owned uv build step. A matching catalog reference and additive build steps retain ownership; a custom image or replacement Compose build does not. The marker runs uv project-mode commands for `pyproject.toml` projects; that sync is separate from the dependency environment job and can require network access (§8.5).

**LocalStack gateway.** The primary listener is `port:` or `4566`; it is never inferred from `GATEWAY_LISTEN`. Without an authored value, Lando sets `GATEWAY_LISTEN=0.0.0.0:<port>`. An authored value MUST be a literal comma-separated list containing exactly one entry on the planned port; every entry MUST use a wildcard bind (`:port`, `0.0.0.0:port`, or `[::]:port`) on a distinct port other than the DNS port while DNS is enabled. Authored `DNS_PORT` MUST be a literal decimal integer from 1 to 65535 even when DNS is disabled; an invalid value fails at `services.<name>.environment.DNS_PORT`. A primary listener on the enabled DNS port fails at `services.<name>.port`. Gateway-list syntax, duplicate-port, missing-primary, and additional-entry DNS collisions fail at `services.<name>.environment.GATEWAY_LISTEN`. All of these fail before provider action. An accepted value is preserved verbatim, and each additional entry contributes an unmarked internal HTTP endpoint named `gateway-<port>`.

**MinIO artifact and secondary listener.** MinIO is a bring-your-own-image service: after inheritance, the effective configuration MUST provide a nonblank compatible `image` or an authored Compose `build`. A Lando build-script alone is not a base artifact. Missing artifact intent fails effective validation at `services.<name>.image`, with remediation naming both choices and without registry/provider access. This type-specific effective validation runs before the common final artifact check (§6.2). There is no implicit registry image, mirror fallback or automatic source build, and the type MUST NOT claim identity metadata for an image it does not supply. The generated launcher requires a shell, filesystem utilities, `minio`, writable `/data`, and `mc`; the image author owns those compatibility and maintenance facts. An authored Compose build supplies its artifact through the existing build owner, without a placeholder image from the MinIO feature.

`MinIOServiceConfig.bucket` names the bucket created at start. An authored name MUST be one MinIO accepts: 3 to 63 letters, digits, dots, hyphens, and underscores, starting and ending with a letter or digit, with no two adjacent dots. It is used verbatim, and any other value fails planning at `services.<name>.bucket`. The default derives from the data name and MUST itself satisfy that grammar, collapsing disallowed characters and falling back to `app` or a short-name suffix when needed. MinIO claims `bucket` (§6.11), so another type that sets it fails planning. `MinIOServiceConfig.consolePort` is an optional `PortNumber` (integer 1..65535), defaulting to `9001`; `port` defaults to the primary S3 API listener at `9000`. The MinIO effective validator explicitly claims `consolePort` after validating the composed listener configuration. Inherited service types retain executable feature configuration and MUST NOT be rejected by a hardcoded type name or a parent's superseded default. Every Lando-owned launcher and the unmarked HTTP endpoint named `console` use the effective console port; the API remains primary, and a route selects the console through `endpoint: console`. API readiness and the `mc` alias use the API port. Equal effective API/console ports fail before provider action with a structured issue at `services.<name>.port` and actionable remediation. Moving the console permits reuse of its former port by the API. Authored process fields remain untouched. The API declares scan default `/minio/health/live` and the console `/`; a normal unauthenticated S3 root403 MUST NOT be globally reclassified as a successful response.

**Mail service secondary listeners.** Mailpit's HTTP UI/API listener defaults to `8025` and follows literal `MP_UI_BIND_ADDR`. MailHog's UI/API bind addresses default to `0.0.0.0:8025` and follow `MH_UI_BIND_ADDR`/`MH_API_BIND_ADDR` independently. Typed mail services advertise app-network listeners, so native SMTP/UI/API binds MUST use `:port`, `0.0.0.0:port`, or `[::]:port`, with integer ports1..65535. Loopback, named and container-specific hosts, invalid syntax and nonliteral values fail effective validation at their environment field, with wildcard-bind or explicitly managed Compose remediation. Accepted strings are preserved exactly; no native bind creates a host publication. Endpoint replacement cannot bypass this reachability contract.

SMTP bind ports MUST equal the effective primary `port`; mismatches identify `MP_SMTP_BIND_ADDR` or `MH_SMTP_BIND_ADDR`. SMTP MUST NOT collide with effective HTTP listeners; reject at `services.<name>.port`, not by reserving a default after HTTP moves. Cross-field checks run against final inherited configuration before cache lookup and provider action, not a parent's intermediate defaults. MailHog shares one HTTP listener only when UI/API bind strings are identical; different strings on one HTTP port fail with identical-string/distinct-port remediation. Distinct ports contribute named `ui`/`api` HTTP endpoints and use ordinary ambiguous-route rules (§6.6). Lando MUST NOT invent a browser-facing `MH_API_HOST`. Generated HTTP scan paths must exist on the listener being scanned: a split UI-only listener is not assumed to serve the API. Bind settings, endpoints, routes and owned clients agree without rewriting authored process fields.

**Tomcat configuration ownership.** Catalog Tomcat references pair an immutable multi-platform image digest with the reviewed Apache configuration for that exact release (§17.2). For a catalog-owned image, the service feature MUST bake `server.xml` with the planned HTTP port during the image build, including the omitted-port default of `8080`, without a startup-time rewrite. The baked engine MUST include a `RemoteIpValve` reading `X-Forwarded-Proto` and `X-Forwarded-Port`, so `isSecure()`, `getScheme()`, and absolute request URLs report the router's public scheme and port (§10.2). The endpoint and healthcheck MUST use that same port. The separate ROOT context uses the resolved `webroot`; authored `command` and `entrypoint` remain unchanged. An authored image reference equal to the selected exact catalog reference retains this ownership. A custom image or authored `build.context` is the explicit exception to the listener rule above: its author owns the daemon configuration, and Lando writes neither `server.xml` nor a ROOT context. `port:` still declares its endpoint and healthcheck target, which the author's configuration must match.

**SQL Server catalog process and health.** On a bundled catalog image, including an authored `image` equal to that catalog image, Lando uses the stock entrypoint and CMD with catalog init enabled (`init: true`); an authored `init: false` is honored. Healthcheck and readiness use the §6.7 SQL Server liveness probe (local `sqlcmd` on `master` with the SA password from the environment): success or the exact tools18 SA login-failed diagnostic means up. The probe MUST NOT select or create the application database. Catalog database creation and `sa` password repair belong to credential convergence on activation and to `db:creds:apply` (§6.12.4, §10.7): create only on positive catalog absence. An authored custom image, replacement `build`, `command`, or `entrypoint` stays author-owned and is outside automatic convergence. `db:export` does not create or initialize the database (§10.7).

On first start, the catalog SQL Server `service_healthy` gate MUST NOT be interpreted as proof that the configured database exists: dependents MAY start during provider apply, before post-apply convergence ensures the database exists. Successful convergence completes before `lando start` returns; convergence failure remains a warning and does not guarantee database creation.

**`webroot` is relative to the app mount.** `php`, `nginx`, `apache`, `static`, and `tomcat` resolve `webroot` against the effective app mount target, which defaults to `/app` and follows `appMount.target`; `webroot` defaults to `.`, the app root itself. Authors normally write a relative path such as `web` or `public`. An absolute container path is accepted for a document root outside the usual layout. A relative path that leaves the app mount, or a path with characters other than letters, digits, `.`, `_`, `-`, and `/`, MUST fail during planning. With `appMount: false` there is nothing to resolve against: a relative or omitted `webroot` MUST fail during planning, and an absolute one names content the image provides. The exception is `tomcat` on a custom image or authored `build.context` (Tomcat configuration ownership, above) with `appMount: false`: the bundled features write no ROOT context and expose no `LANDO_WEBROOT`, so they MUST NOT resolve, default, or claim `webroot`. An omitted `webroot` MUST plan. An authored one, relative or absolute, falls under the field-ownership rule in §6.11.0: unless another composed feature claims it, it MUST fail as unused, with remediation to remove it. Generated document-root configuration uses the resolved absolute path; `LANDO_WEBROOT` exposes it only when `appMount` is not `false`. When the app mount is enabled, `php` and `nginx` default their working directory to that path; `apache`, `static`, and `tomcat` default to the app mount target; an authored working directory wins. On a standalone `apache` service an authored `APACHE_DOCUMENT_ROOT` overrides the generated document root. Configuration views such as `app:config` keep the authored spelling rather than the resolved path. Lando 3 translation MUST preserve the served content root where representable, rewrite `webroot` when the Lando 3 layout semantics differ, and diagnose deployment behavior that needs manual configuration (§7.4.1).

**nginx serves its webroot.** Unless the author declares `command` or `entrypoint`, `nginx` generates its own server configuration. Without `backend`, it serves static files from `webroot`; with `backend`, it passes PHP requests to that service's PHP-FPM listener. Either way it listens on `port` and serves Lando's shared 403/404 pages for server-generated errors. `uploadDirs` lists webroot-relative directories under which PHP MUST NOT execute. Entries allow only letters, digits, `.`, `_`, `/`, `-`, and `*`; empty entries, bare `*`, leading or trailing `/`, `..`, `**`, empty segments, and `.` segments MUST be rejected. A single-segment `*` matches zero or more non-slash characters, never multiple segments. The shared glob translator MUST defensively recheck the allowlist, escape literal dots, and translate `*` to `[^/]*`.

Generated FastCGI configuration MUST make one case-insensitive decision inside the PHP location, immediately after `fastcgi_split_path_info` and before the script-file 404 check: `if ($fastcgi_script_name ~* "^/(?:<re1>|<re2>)/") { return 403; }`. It MUST check the same script name passed in `SCRIPT_FILENAME`, not maintain a separate URI-based deny location; this avoids drift such as the URI-decoded newline bypass. The guard has no wildcard dot or end anchor. Both nginx render paths use this generator. The built-in nginx feature claims `uploadDirs` only with a non-empty trimmed PHP-FPM `backend` and no authored `command` or `entrypoint`.

**PHP Apache protects upload directories only with a Lando-owned launcher.** The PHP feature claims `uploadDirs` only for `via: apache` (including its default) when runtime policy gives Lando process authority: a stock catalog image, no authored `command` or `entrypoint`, and no `build.context`. Its launcher places a case-insensitive `DirectoryMatch` on the regex-escaped resolved webroot plus the combined upload directory regex, joined by exactly one `/` even when the webroot is the filesystem root, with a directory boundary `(?:/|$)`. This block belongs inside the generated VirtualHost when a port is authored. Separate command-line directives set `php_admin_flag engine off` inside `IfModule php_module`, which an uploaded `.htaccess` handler mapping cannot override, and deny `(?i)\.php$` through `FilesMatch` / `Require all denied` to return the shared 403 page. Standalone `type: apache` has no PHP and MUST NOT claim the field; PHP FPM/CLI, static, and unrelated services do not claim it either. A non-empty unsupported list MUST fail planning and lint at the service's `uploadDirs` field with plain-language remediation, never silently do nothing. `uploadDirs: []` clears recipe defaults and is accepted even with a replacement launcher or another service type.

**Generated web servers report the router's public scheme.** The router replaces client-supplied forwarded headers with the scheme and port of the connection it accepted (§10.2). nginx FastCGI configuration MUST map the forwarded protocol to a public scheme and present coherent `HTTPS`, `REQUEST_SCHEME`, and `SERVER_PORT` to PHP: `HTTPS=on` and `REQUEST_SCHEME=https` with the public HTTPS port when the effective scheme is `https`, otherwise `HTTPS` unset and `REQUEST_SCHEME=http`. Because the generated server declares no `server_name`, it MUST also pass `SERVER_NAME` as the request host, matching Apache's `UseCanonicalName Off`. A valid forwarded port wins; an invalid, empty, comma-separated, or out-of-range value falls back to the scheme's default (443 or 80) and then to the local listener port, and a direct plain request without forwarded headers keeps its actual listener scheme and port. Generated nginx (`absolute_redirect off`) and `static:caddy` redirects MUST stay relative so the client keeps its public scheme and authority. Generated Apache redirects keep the public scheme when the route's public scheme and its selected backend agree, and keep the request `Host` authority through the canonical-name settings below; a plain-backend fallback or an explicitly selected opposite-scheme backend keeps Apache's own transport scheme. Generated `static:caddy` configuration serves plain HTTP only, with automatic HTTPS and the admin API disabled. The FastCGI projection rules apply to generated nginx FastCGI configuration and the relative-redirect rules to generated nginx and `static:caddy` configuration, while their generated launcher remains the planned command; generated Apache (PHP via Apache under the runtime ownership rules of §6.12.5, and standalone `apache`) follows the native-TLS and reduced-fallback rules below. Catalog Tomcat honors the same headers through its baked `server.xml` (Tomcat configuration ownership, below). A published host port bypasses the router, so a client of a plain published port can claim HTTPS through forwarded headers; local development accepts that.

Generated Apache uses native TLS instead of header emulation. When Lando owns the launcher, the parent process runs as root, and the effective configuration materializes a generated certificate, PHP via Apache and standalone `apache` declare a plain listener plus one non-primary internal HTTPS listener (`443`, or `8443` when the plain listener already occupies `443`) and serve the service's generated pair on it. That TLS virtual host is the only one for its port, uses the canonical internal alias and an explicit `:443` canonical name with `UseCanonicalName Off` and `UseCanonicalPhysicalPort Off`, and passes the browser `Host` unchanged, so a port-less `Host` yields `443` and an explicit `Host` port wins. APT-based images enable Debian `ssl` at build time and retire the conditional `Listen` lines from `ports.conf`; httpd images load their shipped `ssl` and `socache_shmcb` modules and keep the stock SSL sample host disabled. Exactly one definition of each planned listener remains, and no directory rewrite is injected: normal `DirectorySlash` and the application's rewrite order are preserved, so an app `.htaccess` force-HTTPS rule sees `%{HTTPS}=on` over the TLS listener and does not redirect. Relative `[R]` targets and mod_dir redirects keep the client's public scheme, host, and port.

The reduced fallback is explicit. `certs: false` or custom certificate material keeps its existing meaning and HTTPS routes bind the plain listener, with TLS terminating at the router; an explicitly non-root Apache parent keeps that parent and gets no automatic TLS listener or leaf. In both cases the plain PHP vhost retains `SetEnvIf X-Forwarded-Proto` so a TLS-terminating client still sets PHP's `HTTPS` value, but Apache did not terminate TLS: `%{HTTPS}` stays off, and its own redirects remain `http`. Lando MUST NOT downgrade a generated TLS listener after a certificate-authority failure. A custom image, replacement context build, or authored `command`/`entrypoint` owns its server setup and receives none of this generated TLS configuration. Catalog Tomcat honors forwarded headers through its baked `server.xml` (Tomcat configuration ownership, below), and Caddy shares the generated error and hidden-path protections with relative canonical redirects. A published host port bypasses the router, so a client of that port can claim HTTPS; local development accepts that.
`lando app:config:lint` and `lando doctor --app` report `service.router-tls-termination` at `services.<name>.certs` or `services.<name>.user` for this reduced fallback when an HTTPS route would land on the generated listener, naming the loop risk and the field to change; an explicit endpoint selector for the plain listener, an HTTP-only or empty route list, a disabled router, a custom image, and a service without the generated-listener association stay silent.

**Generated PHP serving refuses `.php` case variants.** PHP handlers match the lowercase `.php` extension, but a case-insensitive app mount, which macOS and Windows hosts can have, resolves `settings.PHP` to `settings.php`, so a static fallback would serve PHP source. Generated PHP via Apache and nginx FastCGI configuration MUST answer every other case variant of a `.php` path with the shared 403 page: Apache denies `\.(?!php$)(?i:php)$` through `FilesMatch` / `Require all denied`, and nginx adds a case-insensitive `\.php(/|$)` deny location after its case-sensitive FastCGI location. This deny is independent of `uploadDirs`, whose decision stays on `$fastcgi_script_name` inside the FastCGI location.

**Generated web servers refuse hidden paths.** The default webroot is the app root, so a generated server would otherwise serve `.git/`, `.env`, and `.lando.yml`. Lando-generated nginx configuration (with or without a PHP-FPM `backend`, and `static` nginx) and Apache configuration (PHP via Apache and standalone `apache`) MUST answer a request whose path contains a segment beginning with `.` with 403, except a `.well-known` segment. Both generators MUST share one pattern, `/\.(?!well-known(?:/|$))`. nginx declares it as the first regex location of each generated server, so it precedes PHP handling; Apache declares it as a `LocationMatch`, which merges after directory and `.htaccess` grants. The rule matches the leading dot rather than a name, so a case-insensitive app mount cannot bypass it. Generated `static:caddy` configuration MUST apply the same rule and serve Lando's shared 403/404 pages with their original status; only the segment exactly named `.well-known` is exempt, so a path that merely mentions `.well-known` elsewhere still loses any other hidden segment.

#### 6.12.2 Framework presets

Language types may expose `framework:` presets as ordinary overridable config. A preset's implicit default webroot is relative to the app mount and is omitted when `appMount` is `false`; this MUST NOT silently discard an explicitly authored root. Ruby supplies root context only (`rails` defaults to `public`, `none` to `.`), with authored-over-preset precedence. Its built-in context requires an active mount, so an explicit relative or absolute root with `appMount: false` MUST fail unless another composed feature declares support. Genuine webservers may still use an absolute root without the app mount and without `LANDO_WEBROOT`. Python and Go have no built-in webroot declaration. Framework selection does not start an application server: Ruby, Python, and Go keep their keep-alive command unless the author supplies `command`, and preserve authored `entrypoint`. A preset MAY select the default port and add port variables and host defaults to the runtime's listener projection (§6.12.1). Unused language command hints are not part of preset config or extensions. Recipes materialize the framework settings they need as concrete service config and tooling. Published ids are `drupal`, `wordpress`, `laravel`, `symfony`, `magento`, `django`, `fastapi`, `flask`, `rails`, `sinatra`, `echo`, `fiber`, and `none`.

Canonical PHP does not interpret framework ids. It uses `webroot` (§6.12.1) and `allowOverride` (default false); recipes own framework choices. Invalid paths fail during planning.

#### 6.12.3 Catalog membership rules

Catalog membership is frozen by this specification; additions or removals require a spec amendment. Version additions MAY ship in a minor release only through the single metadata matrix with available artifacts and matching docs/tests. Canonical collisions fail with `ServiceTypeCollisionError`. Plugins MAY add types and composable features. Library consumers receive the catalog only through bundled discovery (§16.4).

#### 6.12.4 The `creds:` schema

`ServiceCreds` contains literal `user` and `database` plus `password` and optional `rootPassword` as `EnvironmentValue` (§7.3.1). `mariadb`, `mysql`, `postgres`, `mongodb`, `mssql`, and opted-in plugin types share this contract.

Authored `creds` is `ServiceCredsConfig`: the same four members, each optional, with no decoding defaults, so layer composition and native aliases are settled before a resolver fills anything in. It is the only authored home for service credentials; no service-level `database` or `password` key exists. Landofile layers merge its members like any other mapping (§7.2). A type MUST reject a supplied member it does not use, with an issue at `creds.<member>` that names the member it does use: PostgreSQL and MongoDB reject `rootPassword` because `user` and `password` already are the administrator account, Redis accepts only `password`, and phpMyAdmin accepts only `user` and `password`. phpMyAdmin logs in with the credentials its selected sibling hosts agree on, overlaid by its authored members; an authored member is never dropped, and a member that neither source supplies fails planning with `PhpMyAdminHostsCredsError`.

A database type resolves its connection exactly once and returns it through `ServiceTypeResolution` as `DatabaseConnection { family, creds, port }`; the planner persists it on `ServicePlan.connection` and exposes it read-only to service and app features. Defaults fill only missing facts, one member at a time. Effective `creds` and any authored native alias (`POSTGRES_PASSWORD`, `MYSQL_ROOT_PASSWORD`, `MONGO_INITDB_ROOT_PASSWORD`, `SA_PASSWORD`, and siblings) MUST agree, and aliases MUST agree with each other, compared as descriptors, never as decrypted values; a conflict fails planning naming both paths without values. After feature composition the planner checks that type-owned projections still agree with the connection.

Initialization environment, `LANDO_DB_*` metadata, generated client environment (`PGPASSWORD` and equivalents), SQL operations, `ServiceInfo.creds`, and the `services.<name>.creds.*` expression scopes derive from the connection facts. `services.<name>.port` is the connection port when a service publishes one, otherwise the type's planned listen port from seed selection, recorded on `ServicePlan.plannedPort`. Consumers MUST NOT rescrape the plan environment or apply SQL-specific credential defaults. Projections are typed and deliberate: a bound password stays a `SecretRef`/`BoundText` through every native key, metadata variable, client environment, and URL template, and bundled URL templates use the connection `port` with explicit `url.encodeComponent()` on the password. MongoDB dump/restore pass credentials through a bounded anonymous-fd config, and MSSQL clients read the password from projected environment; no bundled tooling places a secret in argv.

**Catalog TCP probes.** Catalog types that check a TCP listener (MongoDB, RabbitMQ, Memcached, Valkey, Tomcat, phpMyAdmin, PHP's Apache and FPM listeners, nginx, Apache, and static) use one shared probe that declares the listener as its `target` (§6.7), so it dials `LANDO_PROBE_HOST`/`LANDO_PROBE_PORT` and never loopback. A POSIX `sh` script dials with Bash `/dev/tcp` under a two-second `timeout` when present, otherwise `nc -z -w 2`, and fails with one stderr line naming the missing tools when the image has neither. An optional trailing command runs, with exact argv and exit status, only after the dial succeeds.

**MongoDB probes.** The `mongodb` type targets its declared primary TCP listener for both probes through `connectionFor(ctx)`. Ongoing health is the catalog TCP dial only, on the existing cadence, and MUST NOT launch `mongosh` or create shell state. Startup readiness performs that dial first, then runs a bounded credential-free protocol ping as the trailing command (`mongosh --quiet --norc`, direct connection, bounded server-selection, connect, and socket timeouts). No client launches while only the image's loopback initialization daemon exists. The ping sets `HOME` to a disposable owner-only temporary directory removed on exit. It MUST NOT use `MONGO_URI`, mutate the container's `HOME`, write under the data volume, add a wire-protocol client, or deploy a helper binary. The probes do not return credential verdicts; convergence and doctor own those observations.

**Catalog credential convergence and observation.** Bundled catalog database services (`postgres`, `mysql`, `mariadb`, `mongodb`, `mssql`) with canonical artifact, stock process, and expected catalog data mount MAY receive automatic credential convergence. Custom image, build, authored launcher, unprovable storage, SQLite, and reserved/protected identities are refused rather than guessed. Convergence is lifecycle-owned DDL for the stock baseline, not a generic SQL framework; transfer and reset stay in `@lando/sql`.

Activation invokes one private engine worker from `applyActivation` immediately after a successful provider apply, while the activation environment session is open, and before app build, routes, readiness, and post-start (§6.7, §6.15). The same path covers whole and selected user start/restart/rebuild, scratch (only positively owned private storage), global groups, and cold ensure-global. Scope is services actually applied whose apply action is `started`, `replaced`, or `created`, or whose connection intent changed versus the previous plan; unchanged kept-running services are skipped before key, lock, or volume work, so a warm no-op start performs zero credential execs. One bounded convergence budget applies per activation (concurrent across services). The worker's first read-only attempt MAY retry bounded startup/recovery states with `runProbe` (§10.5); it does not partition public readiness.

Per service, one fixed family read-only batch (values via env/stdin, never interpolated into shell scripts) proves managed-admin login and privilege, minimal inventory, and fresh app/root login with distinct verdicts. When everything matches, that is the only exec. Otherwise the worker computes a minimal delta (never drop or rename, no grant reset, no unrelated root rows, root/`sa` rotation last, no MongoDB durable empty-database materialization), takes the physical volume lock under the lifecycle mutation lock, revalidates mount generation, applies, and verifies with fresh logins (non-loopback TCP for PostgreSQL app password proof where trust could mask auth). When a stock client requires a password literal in a DDL statement, send that statement on stdin with family-specific literal encoding under a known SQL mode; never put it in argv. Mutation execs MUST bind to the verified native container id at dispatch, never fall back to its service name (§5.3). Partial failure keeps positively acknowledged actions and reports uncertainty when a write may have happened; uncertain writes are not blindly retried. Raw SQL and client output MUST NOT enter warnings.

**Read-only fallback.** For a typed catalog-family connection in activation scope that cannot prove convergence eligibility, check the configured login without modifying the database. Warn with `LANDO_DATABASE_CREDENTIALS_REJECTED` or `LANDO_DATABASE_MISSING` only on positive evidence, and give author-owned recovery guidance: restore the previous settings or fix the account or database in the image. Do not recommend `db:creds:apply` for a custom image or launcher. Convergence-eligible services MUST NOT also run this observer.

**Managed administrator.** Each supported family adopts one fixed Lando-owned login named `lando_admin` when positively absent and another authorized admin path can authenticate:

| Family | Managed admin |
|---|---|
| PostgreSQL | Create a `LOGIN SUPERUSER` role with `PASSWORD NULL` and comment `lando:db-admin:v1` in one transaction. Connect over the stock trusted Unix socket. Refuse authorization rules that trust non-loopback hosts. Use an existing role only when its marker and attributes match. Do not edit `pg_hba` or `pg_ident`. |
| MySQL / MariaDB | `'lando_admin'@'localhost'` with a derived password over the Unix socket and grants sufficient for intended root/app operations; mark via supported user attribute/comment where available. |
| MongoDB | `admin.lando_admin` with root role, derived password, `authenticationRestrictions` to `127.0.0.1`, and customData marker. |
| SQL Server | `lando_admin` sysadmin login with derived password, reached locally; `sa` remains the app login and `password`/`rootPassword` are aliases. |

Derived password is `L1a!` plus base64url(HMAC-SHA-256(seed, canonical JSON `["lando-db-admin/v1", family, volume generation]`)), where generation is the native volume generation UUID. The seed is one versioned 32-byte random file at `<userDataRoot>/db-admin/key.v1` (§12.4): create-once under lock with private-file primitives, owner-only modes, reject symlinks, never replace malformed or insecure material. No key I/O on skipped services or preview. Candidate order: verified `lando_admin`, previous applied administrator candidate, desired administrator candidate, then (explicit command only) piped `-` or masked prompt after known paths fail. An existing reserved login that cannot be authenticated is a classified warning, never a silent rekey or DROP.

**Database creation.** Create only on positive catalog absence. When `ApplyResult.createdVolumes` proves this activation created the mounted storage (native name, generation, and owner), treat successful convergence as first-time initialization: emit neither a credential-change notice nor a `credentialChanges` entry, and do not warn about creation. Otherwise emit `LANDO_DATABASE_CREATED_ON_EXISTING_STORAGE` naming the empty new database, a bounded sibling list (or none), and how to point `creds.database` back or restore. PostgreSQL/MySQL/MariaDB vendor entrypoints may still bootstrap brand-new data directories before Lando converges; that first native bootstrap is not reported as a Lando convergence creation. A MongoDB name-only change is logical namespace selection with no DDL.

**Output.** One human `message.info` per service with verified app changes (for example “Applied changed database credentials to `db`: password”). Optional structured `credentialChanges: [{service, family, changedMembers}]` on startup result data through existing result paths; omit when empty. Failures yield `LANDO_DATABASE_CREDENTIAL_CONVERGENCE_FAILED` with remediation; start MUST NOT fail because of convergence. If the private seed cannot be read or created, activation MUST warn once with `LANDO_DATABASE_ADMIN_SEED_UNAVAILABLE`, skip managed administrator adoption for the affected database, and continue with proven previous or desired administrator credentials if available. This does not affect PostgreSQL's passwordless socket role. MCP-authorized `app:start` MAY converge inside already admitted lifecycle scope; `db:creds:apply` stays MCP never-allow and event-step rejected (§10.14).

**Explicit repair.** `lando db:creds:apply` is the thin plugin command over the engine-backed `DatabaseCredentialConvergence` SDK port (§3.4, §10.7): default read-only preview; `--yes` applies the previewed delta after revalidation; pipe/prompt only after known admin paths fail, outside locks. Doctor stays read-only with no seed access (§10.9.1). Shared remediation for doctor and residual observations: edited descriptors → `lando start`; same-reference rotation or drift on a kept container → `lando restart --service <svc>` or `db:creds:apply` preview/`--yes`; restore previous creds/database name as corrective alternative; never prescribe deleting data by default. Global and scratch remediation names their own lifecycle. Password material is registered for redaction and never enters a warning, event, or log.

**RabbitMQ defaults and probes.** The `rabbitmq` type MUST default `RABBITMQ_NODENAME` to `rabbit@<host>`, where `<host>` is `landoServiceContainerName` of the app's data-name slug and the service, and MUST preserve an authored environment override. That host equals the container hostname until the app is renamed, so brokers initialized under the hostname keep their database; when it differs from the current container name, the type adds a host alias mapping it to `127.0.0.1`, so the node name stays resolvable and the database directory on the retained `serviceStoreName("rabbitmq-data")` volume is unchanged across renames. The type targets its planned AMQP listener for both probes. Ongoing health is the catalog TCP dial only and MUST NOT launch an Erlang CLI. Startup readiness performs that dial first, then `rabbitmq-diagnostics -q ping` against the local node as the trailing command. The image's `HOME` is the data volume, and the broker creates its Erlang cookie there during boot after the entrypoint's one-time ownership fix. The type-contributed default probes MUST NOT launch an Erlang client before the AMQP listener accepts connections, because a client running as another identity in that window creates a cookie the broker cannot read. Neither default probe sets an explicit user or overrides `HOME`; readiness shares the broker's cookie through the image's `HOME`. Neither proves AMQP authentication or management API availability. Authored replacements retain the independent-policy and execution-identity rules of §6.7.

**MySQL and MariaDB client environment.** Default server initialization MUST NOT receive the application password through the client-only `MYSQL_PWD` variable: doing so can authenticate the image's first root setup with the wrong password. Generated clients retain their per-invocation `MYSQL_PWD` projection from canonical connection facts. Catalog liveness pings do not require that password. Authenticated local MariaDB clients using TCP pass `--skip-ssl-verify-server-cert` before caller arguments; TLS negotiation stays enabled without the MariaDB 11.4+ warning on `MYSQL_PWD` logins. Other MySQL clients MUST NOT receive that option. Verified server identity remains required for remote endpoints and tunnels (§10.11). Native initialization variables and `LANDO_DB_*` metadata remain derived from the same connection fact.

A non-SQL type may publish `nonSqlCreds: ServiceCreds` instead of `connection`. Redis derives it from its authored `creds.password`, the same value used for its initialization and client environments; without one it requires no authentication and publishes no credentials. Fresh service scopes and scopes reconstructed from serialized plans expose these credentials unchanged; they do not infer them from environment or generic normalized configuration. SQL-family services continue publishing only `connection`, with no competing credential copy.

`ServiceInfo.creds` is the string-only `ServiceCredsDisplay`, redacted without any store read. Structured output redacts password fields by default; a type MAY mark additional fields secret. Free-text output follows §3.7, which prints published default credentials, and a literal password or root password equal to its own credential's user or database name, as-is; a value resolved from a reference or explicitly registered stays masked regardless. Clients of an existing database use the applied connection fact and resolve references afresh per operation. Catalog services converge Landofile credential changes on activation as above; a warm unchanged start does no credential work. Out-of-band database changes and secret-store value rotations behind an unchanged reference are not watched on warm starts: use selected `restart` or `db:creds:apply`. `lando doctor --app` remains observe-only (§10.9.1).

#### 6.12.5 PHP service depth

`via` is `apache` by default, `fpm`, or `cli`. Modes select compatible artifacts and reject incompatible keys at planning. FPM exposes its service endpoint for a sibling web server; CLI has no implicit HTTP server.

`composer` accepts a version, `false`, or `{ version, packages }`; all forms remain supported. Versions and packages are validated, checksum-pinned, deterministically ordered, and included in `buildKey`.
Stock PHP services with Composer enabled mount the shared `composer` cache store (`lando-cache-composer`) writable at `/var/lib/lando/composer-cache`; an authored mount at that target takes precedence, and `COMPOSER_CACHE_DIR` defaults to that path unless the service environment sets it.

`xdebug` accepts `false`, `true`, or modes. Enabled Xdebug contributes `lando xdebug on|off|status`, sets the managed client host to `debugger.lando.internal` (not `host.lando.internal`), and relies on global `debugger.host` (§7.5, §10.1) for the alias target; environment variables alone MUST NOT be documented as enabling it, and `environment.XDEBUG_CONFIG` MUST NOT be documented as the WSL-to-Windows fix.
Explicit `lando xdebug status` MUST attempt a one-second PHP TCP connection and close immediately, reporting TCP reachability or the failure reason without claiming DBGp acceptance or changing exit status on connection failure; hostname resolution MUST be bounded, and `on`, `off`, ordinary execution, and lifecycle operations MUST NOT run this diagnostic.
On a stock artifact, every catalog PHP version MUST plan `xdebug: true` or a valid mode list in every `via` mode. Each catalog version selects exactly one compatible upstream Xdebug release, pinned by version and SHA-256 and verified before installation (§6.13.3); the pin is a `buildKey` input, and selection is deterministic and offline during planning. A catalog version MAY pin an upstream pre-release only when no compatible stable release exists. `lando xdebug status` MUST report the loaded Xdebug version, or that the extension is not loaded.

`dbClient` accepts `auto`, `false`, or an explicit family/version. Auto detection uses resolved database services without provider probing and participates in `buildKey`.

**PHP runtime ownership.** A custom image or a Compose replacement build (normalized `build.context`, including shorthand and defaulted contexts) makes the PHP runtime author-owned in every `via` mode, even when planning supplies the type's catalog Apache image reference. Without a replacement build, that catalog reference retains stock ownership; additive `build.artifact` and `build.app` scripts do not transfer ownership. An author-owned runtime MUST NOT receive PHP-managed prerequisite, Composer-binary, WP-CLI, Xdebug-extension, or database-client installers, nor a PHP-generated launcher or Apache configuration-preparation step. Explicit `composer.packages` steps and enabled Xdebug configuration/tooling remain; the author supplies their required binaries/extensions. This does not remove ordinary `lando` base features. Authored process fields remain authoritative. For Apache and FPM, `port:` still declares the endpoint and probe target, which the author's daemon configuration MUST match; CLI gains no implicit listener.

PHP MUST compute one immutable, schema-backed runtime policy during service-type resolution, separating artifact source (`stock`, `image`, `context-build`), process authority (`lando`, `authored`, `image-default`), supported base-family evidence or unknown reason, optional selected reference, and log mode. The service feature receives that policy through its feature config; app features receive it through a private namespaced resolution-metadata entry (§6.11.4). Selected PHP consumers with missing or malformed policy MUST fail with `AppFeatureMutationConflictError`, not re-infer it. The private key is not public Landofile authoring vocabulary.

Canonical aliases of the catalog Apache reference retain stock ownership in all `via` modes; another registry or namespace does not. Replacement context takes precedence over that reference. Canonical upstream `docker.io/library/php` tags ending in `-bookworm` or `-bullseye` establish the respective family only without a replacement build; Dockerfile contents MUST NOT be inspected to manufacture family proof.

An authored `command` or `entrypoint` on a stock artifact changes process authority, not artifact ownership: stock installers and baseline INI remain, while generated startup launchers, Apache process preparation, and implicit console aliases are omitted; command launchers such as `:php-local` stay declared and need the image to supply a POSIX shell and the selected tool. Custom images and replacement builds also omit implicit PHP aliases and file-log redirects. Container stdout/stderr and explicitly authored log sources remain available. Only Lando-generated Apache/FPM processes receive the aliases in §6.14.6; CLI receives none.

**PHP security baseline.** Stock PHP artifacts in every `via` mode MUST receive Lando's active PHP security mitigations as a build-time `conf.d` INI drop-in that a later-sorting drop-in can override; author-owned runtimes MUST NOT receive it. A Lando release MAY retire a mitigation only when the stock base of every catalog PHP version provides equivalent protection by default.

Stock PHP `www-data` retains its declared `/var/www` home and prepared-home ownership contract (§6.5). Default persistence MUST NOT require `home: false`; preparation occurs during the image build and a fresh named volume inherits it, while populated volumes retain their ownership. Custom runtimes may disable persistence or supply an explicit valid home path under the ordinary home contract. This policy does not alter the stock baseline INI or existing framework preset behavior.

**Mailpit sender proof.** Selecting a PHP sender requires a provable supported base family for the pinned msmtp installer. A replacement build MUST NOT derive that proof from `image:`, including a catalog reference: the build may replace the base. An unprovable selected sender MUST fail before wiring mutations with `MailpitMsmtpBaseFamilyError` (aggregated by planning); excluding it with `mailFrom` MUST avoid its installation and wiring. Exclusion does not waive other service validation.

The existing error tag MUST carry `service`, reason `replacement-build` or `unproven-image-family`, and optional `image`. Replacement-build diagnostics MUST explain that the Dockerfile controls the result and offer sender exclusion or a known image without a replacement build. Image-family diagnostics MUST offer canonical supported references or exclusion without irrelevant build advice. All selected senders MUST be validated before any wiring mutation; family policy is read once per selected sender and database-client auto detection is computed once when needed. Planning aggregation MUST retain actionable remediation rather than replace it with a generic feature-removal instruction.

### 6.13 Build orchestration

`BuildOrchestrator` executes one provider-neutral `BuildPlan`, streams lifecycle events, and preserves independent service concurrency.

#### 6.13.1 Phases

| Phase | Source and dispatch | Dependency | Default policy |
|---|---|---|---|
| `artifact` | Artifact intent to `buildArtifact` or `pullArtifact` | Independent across authored services; scheduling of a generated companion's build relative to its parent's is implementation-owned | fail-fast |
| `app` | Runtime scripts to `execStream` | Own artifact, running service, and authored `depends_on` | continue-all |

The build scope publishes `pre-build`, `post-build`, `pre-build-phase`, `post-build-phase`, `build-step-start`, `build-step-progress`, `build-step-skip`, `build-step-complete`, and `build-step-fail` through `EventService`. Global, app, and service `build:` configuration resolves concurrency and failure policy; limits are bounded but tuning constants are implementation-owned.

#### 6.13.2 `BuildPlan`

`BuildPlan` contains an `AppRef`, typed `BuildStep`s, and per-phase caps. `BuildStep` contains `stepId`, phase, service, `buildKey`, `BuildCommand`, dependencies, failure policy, redaction tokens, and optional estimate.

Artifact intent creates one artifact step per service. App scripts create ordered steps. Each app step depends on its service artifact and running state plus authored cross-service conditions. Artifact builds never inherit service `depends_on`. Independent siblings may run concurrently. Cycles fail with `BuildPlanCycleError`.

Within an artifact build, project-user image renumbering precedes service feature steps. Image data-tree ownership preparation (§6.2.3) follows those steps and precedes authored artifact scripts, so features can seed files before ownership is applied and authored scripts can use the prepared tree. The resulting order participates in the build key (§6.13.5).

The `authored-` build-step ID prefix is reserved for steps lowered from the Landofile. Service features that claim this prefix MUST fail composition with `ServiceFeatureError` and remediation to rename the step.

Ready predecessors are `complete` or `skip`. Interrupts propagate to in-flight provider work and publish `build-step-fail`; `service-running` is the synthetic running-state predecessor.

#### 6.13.3 Provider dispatch

Built-image ownership follows the build store derived from the canonical cache root, not the app's data root label. Shared-engine image cleanup MUST stay within that store.

Full artifacts use `RuntimeProvider.buildArtifact`; pull-only artifacts use `RuntimeProvider.pullArtifact`; app scripts use `RuntimeProvider.execStream`. Every command retains its planned user, working directory, and environment. Providers MUST NOT re-resolve users at execution time. A Lando-contributed artifact-build step that fetches a third-party artifact inside the build MUST pin its version and SHA-256 and verify the digest before installing. Host network policy does not automatically reach those builds.

Stock Python installs uv in the artifact with a pinned stable version and SHA-256 requirements for each supported Linux x86-64 and arm64 manylinux and musllinux wheel. The install MUST reject unpinned wheels and source distributions. The artifact does not create the dependency environment.

The engine acquires project-selected Node managers on the host after image reuse checks miss and before provider dispatch. It uses the shared source store (§12.8) and host HTTP egress (§10.3). The store checks the registry's npm integrity and any authored hash: pnpm and Yarn Classic hash the original tarball; Berry hashes `bin/yarn.js` exactly as published. A wrong hash aborts before dispatch. A warm exact coordinate for the configured registry needs no metadata or tarball request. The engine leases the verified extracted tree through provider dispatch; the provider verifies the packed context bytes and copies the tree before running the launcher's publication step. A reused image needs no access to the source store.

A dispatched artifact build passes an output sink (§5.3), so the orchestrator records and publishes build output as it arrives (§6.13.6). The engine names the artifact: `lando-build-<store>-<provider>-<service>-<first 24 characters of the build key>`, where the provider id and service name are lower-cased, every run of characters other than `a-z0-9` in them becomes `-`, and they are cut to 64 and 128 characters with trailing `-` removed, and `<store>` is the first eight hex digits of the SHA-256 of the canonical user cache root that holds the build results. Installations with different cache roots therefore never share, reuse, or remove each other's built artifacts on one engine; installations that share a cache root share artifact ownership. Every image a build produces for the service also carries the label `dev.lando.build-store=<store>`; the value is fixed for a cache root, so it never splits the layer cache, and it is how the engine finds what this build store holds (§6.13.5).

`BuildOrchestrator.build` defaults `BuildOptions.refresh` to false. With no explicit `ServicePlan.pullPolicy`, referenced artifacts use `missing`: reuse a provider-local copy and contact the source only when absent. App, scratch, and global start and acquisition-bearing restart flows, including global auto-start, use that default. A service extension `@lando/artifact-refresh` with a positive `afterMs`, and no explicit `pullPolicy`, changes that default when a local copy exists and the last successful registry check for that provider runtime, platform, and reference is older than `afterMs`, or has never been recorded: the orchestrator then uses `always`. Stock PHP floating tags set `afterMs` to seven days. A successful registry check records that time. The pull-check record is regenerable and opts into `onNewerVersion: "discard"` (§12.7.1): a corrupt, older, or newer-format record reads as no recorded check. A missing local image still pulls and does not treat the record as presence. A failed refresh that falls back to the local copy does not update the record. An older check must not overwrite a newer one. An explicit `pullPolicy` is unchanged by the extension. `app:rebuild` and `meta:global:rebuild` pass `{ refresh: true }`; absent an explicit policy, providers declaring `artifactPull` refresh referenced artifacts with `always`. A typed refresh failure then permits one local acquisition with `never`; success records command warning `LANDO_ARTIFACT_REFRESH_FAILED`, while failure preserves the original refresh error. Interrupts and defects propagate without fallback.

An explicit `always` uses strict `always` acquisition on start and rebuild and MUST NOT fall back to a local copy. An explicit `never` uses only a local copy on start and rebuild; absence or an incompatible pinned platform fails without pulling. Provider apply, including missing-image recovery, MUST preserve that prohibition. An explicit `build` dispatches the Compose build on every acquisition-bearing invocation and bypasses recorded artifact-result reuse, including scratch build results; provider build-layer caching remains permitted. Selected restart acquires with the default cache policy, like start. `ArtifactPullSpec.platform` carries an authored service platform pin through source-image acquisition; container providers MUST forward it to their pull implementation, and omission leaves platform selection to the provider. Provider pull policies remain strict. Apart from `build`, acquisition policy does not change build-result reuse under §6.13.5.

Only the branch that actually dispatches `RuntimeProvider.buildArtifact` marks its result produced: the realized `ServicePlan.artifact` ref carries `origin: "build"`. A pull-only service, an acquired source ref with no build steps, stays an unmarked registry ref. Projecting an artifact onto a service preserves the provenance it is given and never invents it. A produced image exists in no registry, so bring-up MUST NOT contact a registry for it on any path, whatever the service's pull policy: a missing image, an image whose platform does not match the service pin (regardless of `RepoDigests` its base left behind), and a Docker create that reports the image missing all fail with `ProviderUnavailableError` naming the service and image, with remediation `lando rebuild -s <service>`. Unmarked registry refs keep the provider safety net: pull when missing, re-pull a registry image for a mismatched platform pin, and force one pull and retry when Docker inspect finds an image its create then rejects, all except under `never`. `origin` is provenance, not create intent, and MUST NOT enter the container create identity. Applied records written before `origin` existed carry no provenance and keep registry semantics; the guarantee applies from the next build.

#### 6.13.4 Failure policy

Artifact failure is fail-fast by default: it interrupts siblings, skips queued work as `phase-aborted`, and fails start. App failure continues independent siblings and raises one `BuildPhaseFailedError` containing `BuildStepFailedError`s after `post-build-phase`. A provider failure while an app step runs is that step's failure: it keeps the provider's message and remediation, carries the provider error as `cause`, and MUST NOT be reported as a command exit code. A `SecretStoreError` is not a step failure; it propagates unchanged (§9.5.1). A blocked step has no exit code. App and service overrides MAY change fail-fast behavior; per-step overrides are not exposed. For explicit global lifecycle operations, these failure policies apply within each dependency-connected service group (§20.6.5).

**App-step settlement.** Each app phase has one settlement owner. Execution returns a blocked, reused, or ran outcome. The settlement owner registers every step the phase considers, observes the exit of each dispatched step, records that step's result (§6.13.5), and only then publishes the step's single terminal task event and gives the scheduler a succeeded, failed, or blocked disposition. A terminal event MUST NOT precede the record it reports. Blocked and never-started steps settle through the same owner, so every registered step gets exactly one terminal disposition, and the phase summary and the task-tree outcome (success, failure, or interrupted) are derived from that one ledger. The step runner captures output and progress and publishes no terminal event.

**Artifact-phase settlement.** The artifact phase settles its task tree on every exit: success, typed failure, defect, and interruption. Success closes the tree. On any other exit each service task that has not settled is settled as aborted, and the tree settles as interrupted when the cause contains only interruption and as failed otherwise. A service whose own build exits with an interrupt-only cause settles as aborted, any other non-success as failed. An artifact task failure carries no exit code, because no command exit is observed. `phase-aborted` skip events for aborted services, including interrupted siblings and queued work, are published only when the cause contains typed failures alone; a failure while publishing them is added to the cause as cleanup and MUST NOT replace the originating failure.

App-result persistence has two rules. A failure to read the index, to mark a reused result as used, or to record a success is fatal to the step: it publishes `task.fail` and never `task.complete`, and the phase fails with the persistence error. A success-record failure MUST say that the command completed but its result could not be recorded, and MUST NOT present that recording failure as a command exit. When a command failed and its failure result cannot be recorded, the command failure stays the primary error and the phase adds the redacted structured warning `LANDO_BUILD_RESULT_NOT_RECORDED` carrying the persistence context. No app-result write error is dropped.

#### 6.13.5 `buildKey` and results

Every step uses a content-derived `buildKey`. Unless forced or governed by `pullPolicy: build`, a matching successful build-result cache entry emits `build-step-skip` with `up-to-date`; failures never suppress retries, so the latest recorded attempt for that build key must be successful. App steps also require current eligibility in the observed container, as defined below. `pullPolicy: build` bypasses recorded artifact-result reuse without disabling provider build-layer caching.

Both phases MUST hash ordered commands and resolved users, tools, versions, packages, config-source identities, and applicable provider/artifact/mount inputs deterministically with secrets redacted. Project-file inputs fingerprinted for plan identity MUST NOT enter an artifact build key as a whole-file digest: only the normalized intent a build step consumes does, so an unrelated manifest edit replans without rebuilding and a pin edit rebuilds. For Node package managers the key includes the base identity, exact package coordinates, source policy, any authored digest and its byte domain, the image destination, and the launcher revision. It excludes host paths, credentials, and acquired bytes. Reordering or user changes MUST change the key; home contents, clocks, undeclared environment, bind contents, and resolved secret values MUST NOT. Forced rebuild commands bypass the result.

**Build owner.** Results and transcripts belong to a build owner, never to an app name. For a user or global app the owner is the plan's `AppIdentity.ownerKey`, derived from the canonical app root (§6.5); for a scratch app it is the scratch id. Artifact records are still reused across owners by build key (§6.13.5), so scratch forks reuse their source app's built artifacts without sharing an owner. Every reader, writer, sweep, and removal takes an owner, and obtains it from a plan or from the canonical root being torn down, never from a display name. Two roots that declare the same app name therefore share no result and no transcript, and renaming an app in place keeps its build history; a rename that changes a hashed input still changes the affected build keys. Global cleanup uses the root of the applied global plan, which can differ from the configured root. Owned storage separates what Lando shows and reuses; it does not make two same-name apps runnable side by side.

`BuildResult` is a union of two records discriminated by phase. Both record `buildKey`, service, outcome, duration, transcript path, and completion time. An app record adds a required step id, an exit code only when a command exit was observed, and the container ID the step ran in, optional only because a provider may report none; app records live in the owner's own index. An artifact record adds its owner (the build owner key of the user, global, or scratch app), the provider id, the artifact reference (the engine-chosen name for a dispatched build, the source reference otherwise), the digest, whether the provider produced that artifact (`artifactOrigin` `build`, also on a failed attempt of a dispatched build) or acquired it as a source ref, the source reference and digest, and `releasedAt` once a teardown released it; it carries no command exit code. Artifact records of every owner live in one data-root index, so one locked read answers which owners still name a built artifact; every read, write, rotation, and removal still filters by owner. A record carrying the other phase's fields is invalid. Each index holds one entry per step and build key, the latest attempt; an app step is identified by its step id, an artifact step by its provider and service. Each step keeps its five most recently used build keys and each index is bounded. Reuse counts as use, and the overall bound drops older keys before any step's newest one, so the key an app is running is rotated out only when there are more steps than the bound; an artifact write rotates only the writing owner's records. A failure without an observed command exit records no exit code. Artifact-step reuse applies to user, global, and scratch apps; app-step reuse applies wherever app steps run. An artifact step reuses the owner's own complete record for its provider, service, and build key, and otherwise any other owner's, because equal build keys mean equal inputs: identical service definitions in two apps, a renamed app, and a scratch fork share one built artifact. Reusing another owner's record writes a copy for the reusing owner, and reusing a released record moves it to that owner, in the same write. A result for a produced artifact is reused only after a provider-local lookup (`pullArtifact` with `never`) finds the image; absence, or a lookup containing only typed failures, makes the entry a miss and the step builds again. A lookup defect or interruption propagates with its complete cause, including any accompanying typed failures.

**App-step results are bound to a container.** An app step's result describes the container the step ran in, so it records that container's provider-observed ID (`ServiceRuntimeInfo.containerId`, §5.3). Before lookup or dispatch, the app-build runner holds one observation of each service that has unblocked app steps, forced runs included. During activation, startup completion hands the phase the post-apply service observations it already holds, through a private execution context and no public option. An entry there is authoritative for that activation: an entry without an ID is a miss and is not probed again. A service with no entry, and every service of a standalone build, is observed through `RuntimeProvider.inspect` once per service per phase, with the selector the runner uses for `execStream`. An app-step result is reused only when its build key matches, it is a success and the latest recorded attempt, its recorded container ID equals the ID observed for this phase, and it is the step's current result in that container: the most recent dispatch of that step id there, under any build key. Dispatching a step under a different build key ends the eligibility of every earlier success of that step in that container, so changing a step's inputs and then restoring them runs the step both times. A superseded result and its transcript remain as history under the retention rules and are never reused. A result without a recorded ID, an observation without a nonempty ID, and an inspection containing only typed failures are all misses: the step dispatches and succeeds or fails through its ordinary path. Inspection defects and interruption propagate with their complete cause, even when that cause also contains a typed failure. A result written without an observed ID records none and is never reused. The app-build runner MUST NOT add container IDs to events or command output. Artifact-step results carry no container ID and are unaffected.

Reuse therefore follows the container, per service:

| Since the recorded success | App steps of that service |
|---|---|
| Same container: repeated `start`, `stop` then `start`, bare `restart`, a `start` that converges after failure, selected `restart` of an unchanged container | Reused |
| New container: `destroy` then `start`, create-config recreation by `start` or bare `restart`, replacement or creation by selected `restart`, removal outside Lando | Run |
| Kept container, step inputs changed, or restored after a run under different inputs | Run |
| `rebuild`, whole-app or selected | Run (forced) |

A recreated service runs its steps while a sibling whose container was kept reuses its own. The ID is captured before dispatch, so a container replaced during a phase leaves a result bound to the earlier ID and the next phase misses. Step execution is not pinned to the observed container: a container replaced outside Lando after the observation can make one reuse decision stale. The activation's readiness identity checks reject that activation, and the next start observes the new container and runs its steps.

A forced run can dispatch a step whose recorded success would otherwise be reusable in the observed container. Before that dispatch the runner invalidates the recorded success atomically, so an interrupted or killed run never leaves the earlier success eligible beside a truncated transcript; the next ordinary start runs the step. A step with no reusable success writes no invalidation, and sibling successes and artifact results are untouched. The guarantee covers the container's writable layer. It does not cover tmpfs mounts, whose contents do not survive a stop of the same container, and it does not make a step's writes to binds or named stores exclusive to one container: those outlive the container and a rerun step meets them again, so app steps are expected to be idempotent. Work that must survive container replacement without rerunning belongs in the artifact phase.

**Built artifact lifetime.** A built artifact lives while an artifact record or a live build claim names it, and a teardown releases it for a bounded time. The artifact index holds the records and one claim per dispatched provider build: an id, the provider, the artifact name, the claimant's process id, and the claim time. A build claims under the data-root `built-artifacts` operation lock before it calls the provider, also when a record of that build key exists (refresh, `pull_policy: build`). Its finalizer writes the result (`complete`, or `fail`; an interruption writes none) and then removes only its own claim, so two builds of one key hold and settle separate claims. A claim whose process is gone is dropped by the next index write. A cache hit verifies its image and adopts its record under the same lock. Rotation keeps the writing owner's five most recently used keys per provider and service and the overall bound, and touches no other owner's records except released ones: every write drops a released record older than seven days or beyond the ten most recently released.

Reclamation is a sweep. Under the operation lock it reads the index and lists, through `RuntimeProvider.listArtifacts`, each swept provider's images labeled with this data root's store. It keeps an image when any of its names, or its ID, is named by any record or live claim of the store, whichever provider recorded it, and when any of its names is not a `lando-build-<store>-` name, because a user tagged it. It removes every name of each other image through `RuntimeProvider.removeArtifact`. An untagged image, a dangling leftover of a rebuild or a failed derived build, is removed by ID only when the store holds no live claim, and parent images left without children are pruned only then, because an in-flight build may be about to start `FROM` an untagged base. The sweep never removes an image the listing did not return, never forces, never starts a runtime, and never removes an acquired source image, which carries no store label. Artifacts left behind by a crash, an unreachable provider, or a discarded or quarantined index are removed by the next sweep on that provider. A sweep runs after a `BuildOrchestrator.build` that is not interrupt-only and dispatched a provider build or dropped a record, for that build's provider, and after each teardown for every provider whose records it released or dropped (`apps:gc --prune` and `apps:scratch:gc --prune` sweep once for all the roots they reap); a warm start whose services all reuse records does not sweep. The operation lock lives beside the index under the user cache root, MUST NOT expire a live holder, and uses the `operation` wait class and contention notice in §12.7.1. It is taken after any app mutation lock and before index locks.

A sweep at the end of a build keeps an in-use image silently; the next sweep tries it again. An unselectable or unreachable provider, or any other failure on a provider, adds one command warning `LANDO_BUILT_IMAGE_CLEANUP_FAILED` per provider whose message says that the next build on that provider removes unused images; an index or lock failure adds one such warning for the whole sweep; a sweep never fails its command. `lando destroy`, `apps:gc`, and `meta:global:destroy` report `builtImages`: the images the sweep `removed`, the records `released`, and the images kept `inUse` with the names of the containers that use them.

**Release and removal.** After teardown succeeds, the owner's artifact records (only that provider's under `--provider`) are released or removed. Release keeps, for each provider and service, the newest complete record of an artifact the provider built, stamped `releasedAt`, and drops the rest; a start of the same stack within the release window, in this app or another, reuses that image without building. `lando destroy`, `apps:gc --prune`, `meta:global:destroy`, and scratch destroy, stop, poweroff, and `apps:scratch:gc --prune` release. `lando destroy --purge-caches`, `apps:gc --prune --purge-caches`, and `meta:global:destroy --purge` remove every record of the owner, including records it released earlier, so the sweep removes those images at once. `lando uninstall --purge` removes every image labeled with the purged cache root's build store from the host Docker and Podman runtimes before it deletes the cache root (§17.7).

Both indexes are regenerable caches: owner app-result buckets at version 5 and the artifact index (records and claims) at version 2. An index of an earlier version, and the former per-owner artifact entries and shared scratch artifact index, are discarded with no migration and no second reader: their steps run once more and record fresh results. A discarded or quarantined artifact index forgets what it named, so the next sweep removes those artifacts unless a container still uses them, and the next start builds what it needs. Results and transcripts stored under an app name by development builds that predate ownership cannot be attributed to a root; Lando never reads, adopts, sweeps, or removes them, and `lando uninstall --purge` removes them with the data and cache roots. After teardown succeeds, `lando destroy` removes the owner's app-step results and transcripts (§6.13.6) and releases or removes its artifact records as above; a failed teardown keeps all of it as evidence. Removing app-step results is storage cleanup: correctness comes from the container binding, not from when results are deleted.

#### 6.13.6 Transcripts

Each dispatched step writes `<userDataRoot>/builds/owners/<ownerKey>/<phase>/<service>/<buildKey>.log` for a user or global app, and `<userDataRoot>/builds/scratch/<scratch-id>/<phase>/<service>/<buildKey>.log` for a scratch app (§6.13.5), created owner-only (mode 0600 where the platform has POSIX modes). An artifact step records the provider's build output; a step that acquires a published artifact without building records one line naming the artifact and its digest; an app step records stdout and stderr. A failed step's transcript ends with its error message. A line longer than the log line bound (64 KiB) is truncated with the SDK truncation marker. Source acquisition runs before a step's build key is known, so a failed acquisition fails the step with the provider's error and no transcript. A step that never dispatches (blocked, or not started before an abort or interrupt) has no transcript and MUST NOT advertise one; a reused step advertises the transcript recorded with its result while that file still exists. `transcriptPath` appears on the step's `task.start` and on its build result; renderers and `lando logs --build` use the same artifact. Transcripts stay local and are never telemetry.

A transcript lives while a recorded result of any owner points at it. After a phase that succeeded and dispatched at least one step, transcripts of that owner and phase that no result references are removed; a failed, interrupted, or fully reused phase removes none. `lando destroy` removes the owner's transcripts and app-step results and releases or removes its artifact records after teardown succeeds (§6.13.5), and a failed teardown keeps them. A record can outlive its transcript (a record reused from another owner, or a released one, still points at a transcript its first owner's teardown removed), which is why a reused step checks the file. Removal never follows a symlink and never leaves the user data root.

`lando logs --build` plans from the current Landofile and contacts no provider. For each selected service it prints the transcript of the latest retained attempt for its artifact step, then for each current app step id in plan order, including failed attempts and output retained after a rename; `--service` selects one service and `--tail N` keeps the last N lines of each transcript. Lines carry the source `build` (artifact step) or `build:<step id>` (app step). It reads only regular files inside the owner's transcript directory under the user data root, so a root that has recorded nothing returns no build-log lines, whatever another root with the same app name recorded. An app with no recorded output succeeds with an empty line result; the text renderer states that no build output is recorded without prescribing a forced rebuild. Combining `--build` with `--follow`, `--since`, or `--source` is a usage error (§8.11.4).

Step output is redacted before it is written or published; raw step output MUST NOT be persisted. Per stream, bytes pass the value layer of §3.7 (exact values, across chunk boundaries and multi-line values) and are framed into lines. The framed lines then pass one bounded line-stream redactor per stream: it redacts the held block plus each new line as a whole and releases the lines that redaction produced. Between lines a stream holds at most 64 unresolved lines and 16 KiB (UTF-8). A quoted assignment or signed-query value, or the whitespace after a `Bearer` introducer, therefore stays masked when it spans newlines and arbitrary chunk boundaries. An open construct the canonical patterns could still complete is held only within those bounds; at a bound, after a line the framer truncated, or at end of output it fails closed by masking from the construct's value to the end of the held region, and continuation suppression then applies as specified below. An unquoted-key opener whose secret name is immediately preceded by the same quote character as its value (`"token="`, as in a shell string) does not start a hold. An escaped opener (`password=\"…`) holds like any other quoted value. After a fail-closed release the stream suppresses the rest of that value until its closer, end of output, or the same bound counted again, as §3.7 specifies, so a quoted value that outlasts the hold is not exposed line by line. Released lines are appended to the transcript and published as `task.detail`; an unterminated final line is flushed through the same path on completion, failure, and interruption. Ordering is per stream, so a held stdout block can be overtaken by stderr lines. Build output holds without a time bound and never shares one hold across stdout and stderr: the transcript must stay deterministic, a quiet step only delays its own detail lines until the line bound or step end, and the two pipes have no exact relative order to preserve (§3.7). The published line and each `outputTail` line are cut to 512 characters with the truncation marker; the transcript keeps the line up to the log line bound. A build's redaction inventory is the plan inventory plus the URL credentials of proxy variables (service environment, build arguments, app-step environment, and the host's own) and the values under secret-named build arguments and app-step environment entries. Other build arguments are public.

#### 6.13.7 Cancellation

`Effect.interrupt` closes every step scope, terminates provider children, closes transcripts, and publishes interrupted failures within the §2.1 cancellation contract. In an app phase the settlement owner (§6.13.4) settles in-flight and never-started steps: an interrupted step records no success, steps that finished earlier keep their results, and each step still gets one terminal event. Only the bounded recording and terminal bookkeeping of work that already finished is protected from interruption; provider work and readiness waits are never masked, and every reason of a mixed cause is preserved. An interrupted artifact phase settles its queued services and its tree as §6.13.4 describes. Fail-fast uses the same path with reason `phase-aborted` and the originating failure. Known limit: an engine that cannot stop an in-flight build step leaves that step running after the interrupt. Podman's build API stops only at the next step boundary, so on the `lando` and `podman` providers the running step of an artifact build finishes on its own; Lando still closes the connection, the step scope, and the transcript at once.

#### 6.13.8 Errors

Build failures are tagged `BuildPlanCycleError`, `BuildStepFailedError`, `BuildPhaseFailedError`, and `BuildOrchestratorUnavailableError`. They carry a human `message` and the relevant app, phase, step/failures, transcript, and remediation context. A failed step that produced output carries `outputTail`: its last redacted lines, at most 20 lines and 4096 characters. A step that never dispatched carries no transcript path, and `exitCode` is present only when a command exit was observed. When the provider returns `ArtifactBuildError` (§5.7), the orchestrator keeps its message and remediation, appends the transcript location to the remediation, and adds `service`, `transcriptPath`, and `outputTail`. For a user app the remediation of a failed artifact or app step also names the command that prints the transcript, `lando logs --build --service <name>`. A scratch app's remediation names no path, because failure cleanup removes its transcripts. Every other provider failure from a dispatched artifact build keeps its own tag, message, and remediation. Both are redacted with the step's inventory. Only `BuildOrchestrator` publishes the `Build` event scope.

### 6.14 Service log sources

`RuntimeProvider.logs` always exposes the implicit container stdout/stderr source. `LogSource` adds provider-neutral file sources and pathless aliases for a native console pipe.

#### 6.14.1 `LogSource`

`LogSource` is a discriminated union. Its file branch contains branded `LogSourceId`, optional label, absolute path, `stdout`/`stderr` classification, `redirect`/`follow` strategy, `required`, and timestamp capability. Each file source names one file; globs are not supported. Its native alias branch contains id, optional label, `stream`, and `strategy: console` only; `path`, `required`, and `timestamps` MUST be rejected. The id `console` remains reserved for the implicit source and is distinct from the strategy name.

Landofile `LogSourceInput` remains file-only: it requires `path` and optionally accepts `id`, `label`, `stream`, and `timestamps`, always resolving to `follow`. `strategy: console` is catalog descriptor vocabulary, not a new authored syntax. Service types may declare aliases or owned redirects. An explicit authored file id replaces a same-id catalog alias or file source.

#### 6.14.2 `LogChunk` source and line

`LogChunk` contains service, optional source, stream, line, and optional timestamp. Missing source means `console`; renderers label interleaved sources.

Each `LogChunk.line` is one complete line; line terminators, including a carriage return at either end, are not part of it. For the console source, providers MUST reassemble engine log messages per stream before emitting: a line written as several partial messages becomes one chunk carrying its first message's timestamp, engine timestamp prefixes on continuation messages are discarded, lines get the same complete UTF-8 framing and line bound as follow sources, and a trailing partial line is emitted only when the stream completes successfully, never on idle, failure, or interruption.

#### 6.14.3 Reification

`redirect` routes owned daemon log files to stdout/stderr during build and requires an owned image path, not `serviceLogSources`. A `console` alias describes existing native-pipe output and MUST NOT emit filesystem build steps or acquire a file reader. `follow` is implemented by `RuntimeProvider.logs`, never a core shell-out, and requires `serviceLogSources`. Providers that read container files through exec MUST use the creation-time read-only helper mount (§5.3), serve every read for a followed source from one helper session, and close that session when the follow ends or is interrupted. They MUST NOT upload or remove helper binaries per source or invocation. The helper does not depend on the image's libc.

The file reader invokes the mounted helper's `log-file` mode directly, using its internal file protocol rather than `exec-run` framing. This internal session is exempt from payload supervision; its scoped transport cleanup remains required. Finite file snapshots use the same delivery path as follow mode.

Selecting an alias or redirect MUST select its native stdout/stderr pipe before daemon-side `tail`/`since`, defensively filter decoded chunks by that stream, and stamp the selected source id. This selects a pipe, not the original producer: aliases on a shared pipe return its shared output. Default logs MUST subscribe to native console once plus real file followers, never once per alias. `--source console` selects both native streams without file followers. Services lacking a requested id MUST be skipped rather than falling back to their console; an id unknown across the selected services fails with known-source remediation. These rules add no provider method or log-option field and preserve framing, redaction, and scoped cancellation.

Without that capability, required follow sources fail with `CapabilityError`; optional sources are explicitly reported unavailable and skipped. Sources are never silently dropped.

#### 6.14.4 Follow semantics

Providers declaring `serviceLogSources` MUST support finite snapshots and scoped follow mode, bounded pending diagnostics for missing files, rotation and truncation, complete UTF-8 line framing, bounded lines, per-source `tail`, timestamp-gated `since`, preserved per-source order, arrival-order merging, and interruption cleanup. No global chronological guarantee or global-total tail exists.

#### 6.14.5 Redaction

Providers return raw `LogChunk`s. Each renderer, lifecycle, telemetry, and machine-output boundary applies its canonical redaction policy before disclosure, and redacting already-redacted output is idempotent. Library log streams and app-owned files remain raw.

A line cut by the line bound ends in the SDK truncation marker. Before that marker, the value layer masks a nonempty proper prefix of a known value when a `substring` value continues from it, or when a `whole-token` value continues from it and the prefix's original left neighbour is a boundary (§3.7). The marker does not create a left boundary.

#### 6.14.6 Catalog defaults

Catalog types may use `redirect` for owned daemon files; MySQL/MariaDB optional slow/general logs use `follow`; framework file logs are declared by the recipe or type that knows their paths. Generated PHP Apache declares pathless `access`/stdout and `error`/stderr aliases. Generated PHP-FPM declares both `access` and `error` as stderr aliases and MUST describe the shared pipe, not producer isolation.

For stock PHP via Apache with neither authored `command` nor `entrypoint`, access logs MUST reach inherited stdout and error logs inherited stderr for both default and authored non-root users. The owned build MUST remove the stock default site and additive global access-log include; the launcher MUST supply global piped logging inherited by its generated virtual host, preserving stderr before Apache reassigns the logger's descriptors. It MUST NOT depend on reopening root-owned log paths or write Apache configuration at startup. Logging MUST preserve webroot and `allowOverride` behavior and reach the inherited streams from every generated virtual host. Without native TLS, the omitted-port main-server and explicit-port virtual-host shapes remain; native TLS uses separate plain and TLS virtual hosts even when `port` is omitted. Custom images, replacement builds, and authored process overrides MUST NOT receive this PHP-specific preparation or launcher.

### 6.15 Lifecycle apply

`start`, bare `restart`, selected `restart`, and `rebuild` are different operations. Create-config drift is applied by ordinary start (§5.3.2). Rebuild is not that path.

Each of them, and scratch and global starts, calls the selected provider's `ensureReady` (§5.3) before runtime-dependent volume coordination or apply, and start also before file-sync rotation, so a runtime stopped by `lando poweroff` is relaunched rather than reported unreachable. Launch-class apply and volume coordination accept only a provider that has been prepared this way; stop and observation operations keep an unprepared provider and never launch a runtime; destroy prepares only an `idle` provider that holds its target's resources, because removal needs the runtime (§5.3.1). This preparation does not acquire the native-init helper; apply still prepares that for services that need it.

**Admission.** User-app `start`, `restart`, and `rebuild`, whole-app or selected, share one private engine admission owner (`withAppActivation`). Under the root mutation lock (§12.7.1) it runs, in order: data-name reconciliation (§7.4); the router refusal (§10.2); service selection; the placement check (§5.3.1); the selected-service rename refusal (§7.4); when no rename retirement is pending, resolution of any unfinished accelerated attempt and, when needed, its resumption and a fresh placement read (§10.6.3); selected-start file-sync compatibility preflight against that placement; desired file-sync engine validation (§6.4), on the execution plan for `start` and the whole desired plan for `restart` and `rebuild`; overlay preparation, which reads no runtime state (§10.4); `ensureReady`; for whole-app requests, the data-name claim that precedes retirement; superseded-realization retirement (§7.4); for whole-app `start`, file-sync rotation (§6.4); volume coordination excluding global caches, which covers the desired plan and, for `restart` and `rebuild`, the applied plan as one union (below), and the data-name claim; stop preflight for `restart` and `rebuild`; drain preflight (on the execution plan for selected start); the managed-file transaction check when retirement did not already run it (§12.4.1); selected relaunch preflight for `restart -s` and `rebuild -s`; and init events unless a nested resume ran them. The operation body MUST run only after admission succeeds and receives a value only the admission owner can construct.

Whole-app `restart` and `rebuild` run one shared private halt-and-relaunch body (`haltAndRelaunchApp`) and do not repeat admission after the halt. A matching unfinished accelerated attempt first resumes through the start path for its recorded scope (§10.6.3), including that start's own admission and transaction check; the enclosing admission then continues with its transaction check but without another init-event run. After the halt, the relaunch runs the start body and repeats only what the halt and its `post-stop` hook can change: `ensureReady`, so a runtime that went away during the halt is relaunched before volume discovery needs it; file-sync rotation (§6.4); the volume ownership check under the coordination already held; and drain preflight, which validates the desired file-sync engine again and invalidates the drain the halt recorded. The relaunch MUST NOT repeat data-name reconciliation, the placement check, either data-name claim, superseded-realization retirement, the managed-file transaction check, or init events.

After the ownership preflight and superseded-realization retirement phases §7.4 requires, the halt-and-start phase of whole-app `restart` and whole-app `rebuild` MUST coordinate the desired and applied plans as one physical-volume key union before its halt, excluding global caches. Each plan's volumes MUST be located through that plan's own data identity; a synthesized merged plan MUST NOT stand in for both. The union uses canonical lock order (§12.7.1). After acquiring the union, lifecycle MUST re-observe the volumes and bind verification to that observation. If the key set changed or a held mode no longer satisfies the request, it MUST release the newly acquired holds and retry before protected work begins. Nested phases reuse compatible holds; acquiring a lower-sorting key or upgrading a shared hold to exclusive is a defect (§12.7.1).

Admission, stop, and teardown that keeps caches coordinate the plan's other stores and prepared file-sync targets with exclusive holds; they MUST NOT lock global caches. When the selected provider reports `serializesVolumeCopyUp` and a global cache is observed present, activation apply requests a shared hold. An absent global cache takes an exclusive hold, as does a present cache when the provider does not guarantee serialization. A teardown that deletes caches, including `destroy --purge-caches`, holds each volume it deletes exclusively at deletion time, as **Exact destroy selection** below describes; a provider without exact destroy selection holds the affected cache keys exclusively in its upfront union instead. `destroy --volumes` alone does not lock a retained global cache. A creation receipt belongs only to the operation that verified creation (§5.3).

**Exact destroy selection.** Before removal, providers MUST enumerate eligible named stores and app-owner selector matches. A global cache is eligible through a named planned store, or its inventory hint when no plan accounts for that endpoint, never through an app-wide selector. The deletion set MUST be frozen before acquisition, after the app's containers and networks are removed. Providers acquire exclusive physical-volume holds on the app-owned candidates as one batch in canonical lock order (§12.7.1), then on each global cache separately, each under the operation wait budget, and recheck name, ownership, and generation under the hold before an exact, non-forced removal. No daemon prune may expand that set. A disappeared or replaced candidate MUST NOT authorize a new deletion. A cache that another container still uses, or whose hold is not granted within the budget, is kept and reported as `in use` in the structured `skipped` result without failing the remaining teardown; a cache whose ownership cannot be verified is kept and reported the same way with that reason.

**Activation apply.** Every activation reaches the provider through one private engine applier (`applyActivation`): user-app start, selected restart, selected rebuild, global ensure, each explicit global start or rebuild group, and scratch start. It takes the certificate preparation proof and stamps the plan it applies (§10.3). Public URL consumers also require a proof derived from the router's authorities for the full publication table (§10.2). The applier lowers URL descriptors to literal environment text for provider create identity and injects realized URL evidence into the recorded consumer services, which keep their descriptors. Completion plans stay unchanged. The applier supplies `resolveServiceEnvironment` from an environment session (§5.5.2) that a caller applying several groups MAY share, records volume creations as reported (§5.3), runs the caller's final admission check and sibling removals inside the caller's reservation (§20.3.1, §20.6.3, §20.6.5), and then calls provider apply. Each operation decides when preparation runs.

Immediately after a successful provider apply, while the activation environment session is still open and before the applier returns, it runs catalog database credential convergence (§6.12.4) for eligible applied services. Verified app credential changes on existing storage become optional `credentialChanges` on the engine's activation outcome and on startup result data (`StartAppResult` and the restart/rebuild/scratch/global projections that carry them); omit when empty. The provider's `ApplyResult` does not carry these changes. The same facts drive the human `message.info` notice. Positive storage creation proof suppresses both surfaces for that service: first-time initialization is not a credential change. Convergence failures and empty databases created on existing storage become command warnings without failing apply. Startup completion (app build, routes, readiness) runs after apply returns (§6.7).

The applier requires `StateStore` and acquires the global cache keys and any unheld receipt keys from the plan it actually applies, never from the recorded or completion plan. It verifies admission-bound stores against their existing bindings and uses fresh, post-lock bindings for the other stores. It runs the caller's before-apply work, host mount preparation, provider apply, and creation receipts under this hold, capturing the receipt recorder inside the hold so receipts can reenter. It releases the locks it acquired for provider apply before credential convergence. Credential writes use their own revalidated physical-volume lock under the lifecycle mutation hold (§6.12.4).

**Early low-port warning.** Before start hooks and builds, the engine MUST record `LANDO_NONROOT_LOW_PORT_UNVERIFIED` once per service/unique planned container port below 1024 when a user is declared other than explicit root or UID 0. Start warnings (this one and `LANDO_HELPER_COMMANDS_UNAVAILABLE`, §6.4) come from one publisher that every operation creating or recreating service containers calls with the plan it will apply: user-app start (whole and selected), restart and rebuild (whole and selected, before their `pre-restart` or `pre-rebuild` hook), global start, restart, and rebuild (once before the group fan-out), cold global ensure (before its build), and scratch start (before its build and apply). It runs before builds rather than inside activation apply so a failing build still reports them. Within one command a warning with the same code and context is recorded and printed once, so nested or resumed launches (a whole relaunch, or a user start that ensures global services) do not repeat it. Stock global services declare no user and earn none. Missing users and ports at or above 1024 produce no warning. Named identities MUST use conditional wording because their resolved UID is not known. Context contains string-valued service, provider, user, port, and `policy: unknown`. Machine output retains the structured command warning without duplicate generic narration; human output narrates it. The warning MUST NOT probe runtime permissions, reject the plan, change ports, or infer effective permission from provider name or rootless mode. Remediation recommends a portable high container listen port or explicitly configuring and verifying bind permission; any future effective-bind fact belongs to a separate provider contract.

| Command | Contract |
|---|---|
| `stop -s` / `--service` | A new selection path, not a flag on whole-app destroy. Stops exactly the observed containers of the named services and keeps them, with no dependency or dependent expansion. An omitted or empty selection is whole-app stop, as for `start`, `restart`, and `rebuild`. Unknown or empty names fail with `ServiceNotFoundError` before mutation, checked against the app's plan before any provider work; the CLI rejects an empty `--service=` value earlier through flag-value validation, as for `start -s`. It MUST refuse with `FileSyncStopError` while an accelerated-start attempt is unfinished, naming the recorded start command (for example `lando start -s web`), for every resolution (applied record, orphaned containers, cleanup-only ownership, and a missing app root), because that attempt still owns prepared targets and sessions that only its recorded start can resume; it never clears or rewrites the journal. With no unfinished attempt, a missing app root, or orphaned or owned resources without an applied record, MUST fail with `AppResolveError` before mutation, with remediation to run `lando stop` without `--service`. An app with no applied record and no containers of its own, or an `idle` runtime, returns `outcome: "unchanged"` with empty `servicesStopped` and `servicesKeptRunning` and mutates nothing: no route publication and no worker retirement. Otherwise the order is fixed. (1) File-sync preflight runs while every writer is still in place, before any container is stopped: `unknown` applied file-sync state fails closed with `FileSyncStopError`; for accelerated mounts of selected services the engine MUST be available, every listed session of the selected services MUST match exactly one saved mount with no duplicate or unrecorded session, a mount of a service whose container is gone or provably not executing (`isIdleRunStatus`) MAY have no session (an earlier selected stop terminated it) or a paused one (an earlier selected stop paused it), and every session still to be quiesced MUST be `running`. (2) Per selected service, in reverse plan order: `pre-service-stop`, a stop of that service's running observed containers through `bringDownObserved` with `stop`, then `post-service-stop`, the same per-service bracket as selected restart. A service with no container, or whose containers are all observed idle (`isIdleRunStatus`), gets no events and is reported `already-stopped` or not at all. (3) Each still-running unselected service that depends on a stopped one produces a `MessageWarnEvent` and does not fail the command. (4) Only when the app's router is enabled and a selected service owns routes, the applied routes of the services in `servicesKeptRunning` are republished through `republishRetainedRoutes`; with no selectable router that warns and continues, and a selected router's failure is fatal (§10.2). (5) File sync for the selected services is flushed after their writers stopped, so their last writes reach the project, the same order as whole-app stop (writers first, then drain); the sessions are then paused on a durable engine (`appLifecycle`), which the next start resumes, or terminated on an engine without `appLifecycle`. (6) Host-proxy, SSH-agent, and GPG-agent workers are retired only when no remaining active service uses them. **Selected relaunch.** `restart -s` and `rebuild -s` run one body and differ only in data: selection (as above), whether an applied plan is required (restart only), artifact refresh, `reconcile`, forced app build, and notices (restart only). Its preflight runs in admission before init events: it resolves the applied plan freshly, because placement is read before a resumed accelerated start; selected restart refuses without one. Each refuses with `FileSyncStartError` naming the service, with remediation `lando start`, when a selected service's accelerated session is new, changed, or removed, that is, when the selected services' desired sessions and applied session specs, including each session's engine, differ: only start prepares sync targets before apply and flushes and retires them (§10.6.3), so applying an unprepared accelerated mount would create an empty volume and dropping one would discard unflushed changes. The body prepares certificates (§10.3), acquires start overlays with adopt reuse (§10.4, §10.10.1), and builds, in that order and before it stops anything, so a failure in any of them leaves the selected services running. It then stops each selected service in reverse order inside a `pre-service-stop`/`post-service-stop` pair, where an absent container is not a failure, applies, prepares GPG homes (§10.4.1), inspects the selected services, and completes startup under the selected policy (§6.7). The applied record keeps every unselected and removed service as previously recorded, never its desired but unapplied metadata, and records the selected services as applied. One router publication replaces an app's whole route set, so the selected policy publishes the composed table and records that same table: every previously applied route of a service the relaunch did not select, in its applied order, then the selected services' desired routes, with each selected service's route references remapped onto it. With no previous record the table is only the selected services' desired routes. An unselected service's unapplied route edit therefore never publishes, while a selected service's added, changed, or removed route does. Publication omits the recorded routes of an unselected service observed down (`isDownRunStatus`: idle, paused, or being removed), so a service that stayed down never gets a route to a missing container; the record still keeps those routes for the next start. A service whose route URL a consumer in the operation reads keeps its route published, because activation verifies that authority, and a service that does not answer observation keeps its route.

For start-like recovery, the recorded start is separate from the caller's selected operation; only a resumed whole-app start can sweep removed services or retire unused workers. Selected relaunch preflight still resolves the applied plan after any resume and retains its separate accelerated-session refusal. Adding accelerated sessions only to services with no prior sessions is expansion, not rotation; a whole-app start MUST keep compatible existing sessions and MUST NOT retire their targets merely because of expansion (§6.4).

**Apply outcome notices.** `ApplyResult.services` reports what apply did to each service container it executed: `kept` (an existing container stayed running), `started` (an existing stopped container started in place), `replaced` (an existing container was removed and recreated), or `created` (no container existed). A `replaced` entry carries `reason`: `reconcile` when reconciliation forced it, otherwise the first detected drift (`config`, `publish-port`, `bind-source`, or `network`), or `host-port` when the bind-rejection recovery recreated a container that existed before this apply. It also reports the replaced container's anonymous volume paths in `anonymousVolumes`, as defined by the `apply` contract in §5; named volumes the plan stopped mounting are not listed. A provider that cannot report a container-level outcome omits `services`; Lando then publishes no notice and adds no `container` field instead of inferring one. `StartedService.container` carries the same report in `servicesStarted` for every operation.

Ordinary `start` publishes one info notice per replaced container: `Lando replaced web's container because its configuration changed.` The clause after `because` is `its configuration changed` (config), `its published ports changed` (publish-port), `a mounted host path changed` (bind-source), `it was missing a network` (network), or `its host port was taken` (host-port). A replaced container with anonymous volumes appends `Its anonymous volume at /data went with it; declare that path under storage: to keep its data.`, or `Its anonymous volumes at /a and /b went with it; declare those paths under storage: to keep their data.` for several. `start` never announces a created container.

Selected restart publishes the same replacement notices and one combined creation message for the services that apply created: `web had no container, so Lando created one.` or `web and worker had no containers, so Lando created them.` It publishes them after the post-apply inspection and before startup completion, so a later readiness failure still reports them. Selected rebuild announces neither. Bare `restart` keeps containers across its halt, so it publishes the same replacement notices as ordinary `start`. Whole-app `rebuild` recreates every container by design and announces nothing; its result still carries each service's `container`. Global start, global rebuild, and the ensure-global path report the same `container` field in `servicesStarted`/`servicesRebuilt` and publish no apply-outcome notice. A notice states no confirmation.

App-step reuse is bound to the container that ran the step (§6.13.5). `start` reuses a successful step only for a service whose container it kept or started in place, including after `stop` and bare `restart`, which keep containers; a service whose container was removed by `destroy`, create-config recreation, or anything outside Lando runs its app steps on the next start. Selected `restart` does not force the app phase: a selected service whose container it kept reuses its results, and one whose container it replaced or created runs its app steps. An unchanged `build.app` command whose bind-mounted inputs alone changed, in a kept container, retains its cached build result and skips the step. `rebuild` forces that step to rerun; a forced step that is interrupted runs again on the next `start`, while steps that finished keep their results (§6.13.5). Changing command text, step user, or artifact inputs changes the build key, so ordinary start reruns the affected step.

Failure and interruption keep the selected realization's established resources at every phase (§6.7); no phase compensates by removing its containers, networks, volumes, routes, workers, or sessions, and only acquisition-local cleanup runs (§10.4, §10.6.1, §10.10.2). Explicit superseded-realization retirement under §7.4, and removal of the owned containers of services a whole-app user start no longer names (§5.3.1), are committed reconciliation that a later launch failure does not undo; named data volumes and their ownership inventory stay. Full restart and rebuild keep their explicit stop phase but MUST NOT remove routes when the following start fails; selected restart and selected rebuild stop only their selected services, and only after their build succeeds. With no pending rename retirement, restart and rebuild, full or selected, first resume a matching unfinished accelerated-start journal through the start path under the app mutation lock, performing the pending-aware preflight, transaction check, init events, and resumed attempt; they then continue without running init events again, and a failed resume fails the command (§10.6.3). An unfinished journal at the root blocks rename retirement under §7.4.

Only acquisition-local cleanup runs after failure: an acquisition that was never published and cannot safely be reused (for example a worker without a validated handshake or ownership record, or an incomplete temporary artifact) is finalized. Completed build artifacts stay; temporary files and build children finalize. The selected realization's containers, including created-but-not-started containers, networks, volumes with creation receipts, the anonymous volumes of retained containers, valid file-sync sessions, and the recorded host-proxy, SSH, and GPG workers the desired plan still needs stay in place for every error tag; a worker the plan no longer needs is retired after a successful apply and is not restored by a later failure (§10.4, §10.10.1). Superseded-realization retirement under §7.4 is committed reconciliation and is not undone by a later launch failure; the retired realization's named data volumes and ownership inventory stay. Creation alone MUST NOT count as readiness. Published route configuration stays, including the previous routes when a replacement fails. Shared networks MUST NOT be deleted as compensation. Established SSH/GPG forwarding remains enabled until stop/destroy, verified superseded-realization retirement, or a whole-app start whose desired plan no longer needs it.

**Retained public route-fact consumers.** In selected start and selected relaunch, after admission prepares the router and before any service stops or is applied, one authority query receives the full composed publication table. Lando resolves route facts for both selected consumers and consumers retained from the applied record. A retained consumer for which any fact it binds would change, or whose applied record lacks evidence, MUST cause a `RouteUrlBindingError` (`retained-consumer`); a hostname reader survives a port move and an origin reader a path-only edit (§7.3.1.1). Remediation lists the selected services and every affected retained consumer as `--service` options to the selected command, or directs the user to `lando start`. The provider's applied-plan merge preserves unselected consumers' evidence and records new evidence for selected consumers.

**Failure reporting.** The primary error tag, remediation, and role-annotated additional failures are unchanged, and the machine envelope gains no fields. Human output of `lando start`, `lando restart`, and `lando rebuild` adds exactly one warning after the primary error:

The warning names the command that failed. `lando start` begins `Start did not complete.` `lando restart` and `lando rebuild` begin `Restart did not complete.` and `Rebuild did not complete.` When present, the warning's rerun advice MUST name that same command, including each requested service with `-s` for a selected operation. Before mutation, an invalid service selection MUST NOT include rerun advice, and remediation naming a different command MUST NOT be contradicted by rerun advice. This does not override a `retained-consumer` refusal's primary remediation: include all affected consumers using `--service`, or run `lando start`.

> Start did not complete. Resources were left in place. Running: …; created/stopped: …; unverified: …. Agent forwarding/file sync remain active where established. Inspect `lando info` and `lando logs`; fix the reported error, then run `lando start`. Run `lando stop` to shut down or `lando destroy` to remove resources; named volumes require `--volumes`.

The inventory uses a one-second best-effort observation budget; anything unobserved is reported as unverified/unknown, never as stopped. A failure before any app resource mutation says `<Verb> did not complete. No app resources changed.` instead of the inventory, followed by the same rerun advice unless the failure's remediation names a different `lando` command; that remediation is then the only advice, so the warning never contradicts it. Machine output (`json`, `yaml`) omits the warning; agents use `lando info`. Pre-events and actual service-start events for phases reached before the failure still publish on a failed attempt, and a launch-preflight failure (§10.3) need not enter later lifecycle brackets; `post-app-start` / `post-start` publishes only after the readiness barrier succeeds.
