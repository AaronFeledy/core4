## 6. Service Specification

### 6.1 Model

A service is a planned runtime component composed from one base and an ordered set of features.

| Base | Contract |
|---|---|
| `l337` | Artifact and build plumbing only. It is the low-level escape hatch and provides no `/etc/lando/*` scaffolding, opinionated environment, packages, or app mount. |
| `lando` | Opinionated development service with boot scaffolding, environment, packages, build steps, app mounts, healthchecks, certificates, SSH agent, and hooks. It is the default when `type:` is omitted. |

Composition is normative. A `ServiceType` resolves to `ServiceTypeResolution`; the core planner composes its `base`, `normalizedConfig`, and priority-ordered `features` into a `ServicePlan`. A type that builds a plan directly is non-conforming and bypasses inheritance, `AppFeature` injection, and feature conformance (§6.11).

`api: 4` is the only service API. Core defaults it after confirming that the Landofile targets `runtime: 4`; no `api: 3` path exists.

A service inherits the app provider. Per-service provider configuration is non-portable and belongs under `services.<name>.providers.<id>`. `ServicePlan.provider` records the resolved app provider.

### 6.2 Common service schema

`ServiceConfigInput` accepts the supported Compose service-key subset (§7.4) alongside Lando keys and decodes to canonical `ServiceConfig`. Its optional `port` is a TCP port number (integer 1-65535). Unsupported or rejected Compose keys fail validation unless an explicit provider extension owns them.

- `image:` and Compose `build:` normalize to `artifact:`. Compose-build fields and Lando build-script fields (`artifact:`, `app:`) are shape-discriminated; mixing them fails with a tagged error and remediation.
- `command:`, `entrypoint:`, `user:`, `working_dir:`/`workingDirectory`, `environment:`, and `env_file:`/`envFile` normalize to execution and environment fields. Environment input never inherits unset host values. A null label value becomes an empty string.
- `volumes:` short and long forms normalize into `ServicePlan.mounts` on every service type: host paths become bind entries, named and anonymous volumes become store entries, and `tmpfs` becomes tmpfs entries. Service-level `tmpfs:` strings normalize the same way, with their options canonicalized (`ro`/`rw` become the read-only flag, numeric modes octal).
- `ports:` and `expose:` normalize to `endpoints` through the single mandatory normalizer (§6.6); host bindings require provider capability.
- `depends_on:` list and condition-map forms normalize to `dependsOn`. `service_started`, `service_healthy`, and `service_completed_successfully` retain their lifecycle meaning (§6.13).
- Compose `healthcheck:` normalizes to native health; Lando `readiness:` uses the same input forms for an independent lifecycle policy (§6.7).
- `init:` normalizes to the canonical `ServicePlan.init` boolean (§6.2.1). It is not a preserved knob and never appears under `ServicePlan.extensions.compose`.
- `restart`, `cap_add`, `cap_drop`, `privileged`, `devices`, `ulimits`, `sysctls`, `shm_size`, `dns`, `dns_search`, `dns_opt`, `extra_hosts`, `stop_signal`, `stop_grace_period`, `security_opt`, `group_add`, `read_only`, `platform`, `pull_policy`, `logging`, `gpus`, and `deploy.resources` are preserved in `ServicePlan.extensions.compose` and capability-checked (§5.5.1).
- Service `configs:` grants normalize into read-only bind entries in `ServicePlan.mounts` (§6.4): the project `configs.<name>.file` resolved from the app root, at the grant's target or `/<name>`, with the grant's `mode` as the entry's `fileMode`; `uid` and `gid` are rejected because Lando cannot change a mounted host file's owner. Supported `secrets:`, `labels:`, and `profiles:` forms are preserved and capability-checked. Service-level `x-*` fields remain inert (§5.4).
- Service `networks:` is a normalized Lando key targeting `AppPlan.networking`, not a preserved Compose field. Keys name `default` (the per-app bridge) or a top-level `networks:` entry; any other key fails validation. Attachments accept `aliases` and inert `x-*` metadata; address and interface settings are rejected. `default` is valid only when the plan has a per-app bridge, so global services reject it. Membership is additive: a service keeps the app and shared memberships its `NetworkingPlan` gives it and joins the listed networks too, so `networks:` provides no isolation (§10.1). Authored attachments and bridge aliases require `authoredNetworks`.
- Rejected keys, including `extends`, `container_name`, `network_mode`, `links`, and Swarm orchestration fields, fail with a tagged error and remediation; they are never silently dropped.

Lando keys include `api`, `type`, `primary`, `artifact`, `appMount`, `mounts`, `storage`, `home`, `endpoints`, `routes`, `healthcheck`, `readiness`, `logs`, `certs`, `hostnames`, `security`, `build`, `packages`, and `providers`. Where a Compose spelling and a more specific Lando spelling conflict, the Lando value wins and `lando app config` SHOULD report the resolution.

`BuildScriptStep` is a command string or `{ run, user? }`; `BuildScript` is one step or an ordered list.

The published boundary retains the named component contracts `ArtifactInput` (not yet published; see #1483), `CommandSpec`, `ContainerUser`, `PortablePath`, `AppMountInput`, `MountInput`, `StorageInput`, `EndpointInput`, `RouteInput`, `HealthcheckInput`, `LogSourceInput`, `CertsInput`, `CaInput`, and `ProviderId`.

#### 6.2.1 Native container init (`init`)

`services.<name>.init` is the one authored spelling of container init intent. The schema accepts a boolean or one of the boolean spellings `true`, `false`, `on`, `off`, `yes`, `no`, `1`, and `0` in any letter case, decodes it to a boolean before planning, and rejects any other string as a validation issue at `services.<name>.init`. The planner writes the result to the optional canonical `ServicePlan.init` boolean (§5.5); there is no second representation.

Resolution precedence is fixed. A composed authored value wins. Otherwise a feature's `setInit` contribution (§6.11) wins. Otherwise a service composing the `lando` base defaults to `true`. A service composing the `l337` base, including `type: compose`, leaves `init` unset when nothing authored or contributed it; absence means the provider's own default and MUST NOT be rewritten to `false`. An explicit `false` is preserved at every step and is the only opt-out.

An effective `init: true` requires the `serviceInit` provider capability (§5.4). Capability validation runs on fresh plans and on cache hits before any provider action and fails with `CapabilityError` naming the provider, `init`, and the service; an explicit `false` or absence never requires the capability. Offline lint (§7.8) sees only authored intent because it MUST NOT apply features: an authored `init: true` against a provider whose offline declaration lacks `serviceInit` is a `landofile.capability` error at `services.<name>.init`; an authored `false` needs nothing; and an absent value on such a provider yields one `landofile.capability` warning that the effective value depends on feature contributions and is validated at `lando start`, rather than an invented base-default failure. Final planning stays fail-closed. Shared container-runtime lowering owns the mapping from `ServicePlan.init` to the engine create request, emitted Compose output, and create-config identity (§5.3.2): `true` and `false` emit the engine's init setting, absence emits nothing, and providers MUST NOT add a second mapping.

Native init is the container's PID 1. It forwards the stop signal to its immediate child, the planned `entrypoint`/`command` process, and reaps orphaned descendants. This avoids the kernel's special handling of default-disposition signals for PID 1; it does not guarantee completion before the stop grace period. A child that ignores the signal or exceeds that deadline may still be terminated through `SIGKILL`. This is not a promise about descendants: a shell or process manager that is the immediate child still decides whether to pass the signal on to its own children. Lando-owned keep-alive commands for `lando` language runtimes, `dotnet`, and PHP CLI mode run as direct argv so the idle process is init's immediate child; authored `command` and `entrypoint` values are never rewritten.

### 6.3 Artifact build

`artifact:` accepts an existing artifact reference, an external `sourcefile:` plus context, or inline provider-neutral build intent. Inline intent includes `source`, `tag`, `context`, `args`, `secrets`, `ssh`, `platform`, `groups`, and `steps`.

Build instructions use named, weighted, user-scoped groups. Final order follows group weight and step weight. Service types, features, fragments (§7.7), and Landofile input contribute steps; recipes contribute only through the Landofile they scaffold. Group overrides may select a group, relative offset, before/after placement, and user; their concrete grammar is schema-owned.

`build.artifact:` and `build.app:` preserve every step's resolved user through `BuildPlan`, provider execution, and ordered `buildKey` hashing. Omitted users resolve to the planned service user; an explicit step user overrides its group's user. Interleaved users are valid. Artifact generation switches users only when required and restores the final service user; app steps pass the resolved user to `execStream`.

`sourcefile:` is the provider-neutral external build-definition key. Compose build fields normalize when possible; other provider aliases belong in provider schemas. Build secrets and SSH require `buildSecrets` and `buildSsh`. Artifact tags are not assumed globally meaningful or pushable.

Artifact builds, including setup probes, MUST remove their temporary build containers and release those containers' mounts whether the build succeeds, fails, or is cancelled. Built artifacts and reusable build cache MAY remain.

### 6.4 App mounts and mounts

`appMount:` (`AppMountInput`) accepts `false`, a destination string, or an object with `target` and optional `readOnly`, `excludes`, `includes`, and `accelerate`. `accelerate` (boolean) permits automatic file-sync acceleration; omitted or `true` never forces it, `false` keeps an ordinary provider bind with no session and no engine acquisition. No engine id is authorable. A string is shorthand for `{ target: <string> }`, interpreted after authored composition. A higher-layer string replaces the inherited object, including its options; object forms deep-merge with other object forms. Consumers see only `false` or the decoded object form. Ordinary service configuration fixes the app mount's source to the app root (scratch isolation may rebase it, §21.7), and core selects provider-bind or accelerated file-sync realization, so `MountInput`'s `type` and `source` are not authoring options and `false` is the only disable spelling. Target validity is a planning check, so the published schema and decoding agree on every string. The `lando.app-mount` feature is its only owner: a service type opts in by declaring its default target, usually `/app`, and optionally a default working directory; types without one, such as data stores, get no app mount. When active, the app source mounts at the authored target or the type's default. Planning sets `workingDirectory` to that target unless the author sets one or the type names another default (§6.12.1), exports `LANDO_APP_ROOT` and `LANDO_PROJECT_MOUNT` as that container path, and records the result in `ServiceInfo`. The plan carries the app mount as the one bind entry in `ServicePlan.mounts` with `role: app`. Core, not the feature, realizes authored `mounts:`, `volumes:`, `storage:`, and `tmpfs:` on every service type, after all service and app features have run; an authored mount at the app mount target replaces the app mount and keeps the app-path variables and default working directory. `false` means the service does not use the app source, as with a data store: on every type it disables the mount, both variables, `LANDO_WEBROOT`, and the default working directory, and an authored working directory still applies. Raw `compose` services get the mount but no default working directory and no app-path variables (§6.9).

| Mount type | Contract | Capability |
|---|---|---|
| `bind` | Live host path | `bindMounts` |
| `volume` | Named store | `persistentStorage` |
| `tmpfs` | Memory filesystem with container lifetime | Always |

`MountInput` accepts only these three types. `copy` (host path copied during artifact build, `copyMounts`), `inline` (literal content), `template` (`TemplateEngine` output materialized as `inline`), and `disabled` (removes an inherited mount by target) are deferred (#1810); a Landofile using them fails validation.

`ServicePlan.mounts` is the single ordered list of every container path a service gets: binds (the app mount, authored binds, certificate and configuration files, worktree Git directories), named stores (authored storage, exclude shadows, caches, home), and tmpfs. Targets are canonical and unique, and the list is ordered shallow to deep, so the deepest target wins: a bind nested inside an excluded directory or a store shows through. Precedence at one target is fixed: `mounts:`, `storage:`, and `tmpfs:` beat the Compose tier (`volumes:` and `configs:` grants); two Compose-tier entries at one target fail validation, as Compose rejects duplicate mount points; two of those Lando spellings at one target fail validation in both lint and planning; an authored entry replaces any service-type, feature, or app-feature entry, including the app mount and a type's own data store, and a replaced store's ownership preparation is dropped unless the winner is also a store; two non-authored entries at one target fail planning with `LandofileValidationError` naming the service and target, the same channel as other feature failures. Derived entries (exclude shadows, nested includes, worktree Git directories, home) fill only unoccupied targets. Providers render the list in order and refuse a plan with a duplicate target instead of deduplicating it.

Every entry records its `origin`: `authored` (the Landofile), `service` (the service type, a feature, or an app feature, including the app mount), `derived` (exclude shadows, nested includes, Git directories, home), or `integration` (agent-forwarding and host-proxy overlays added at start). A bind whose source was resolved lexically from the app root also records `relativeTo: app`, which is what scratch isolation rebases or drops (§21.7). Provenance never enters build keys or create fingerprints, and plans recorded before it existed carry none rather than an inferred value. A bind with `fileMode` binds a private copy of its file source with those permission bits; the provider materializes the copy before create as an immutable, content-addressed file in a Lando-owned directory that survives host restarts, and the create fingerprint covers the logical source, content digest, and mode, never the copy's path. Bind and store entries are capability-checked (`bindMounts`, `persistentStorage`); tmpfs is a baseline every provider MUST realize, so it has no capability flag.

When they ship, template mounts use app-root-relative `source`, optional `engine`, `vars`, and `mode`. Sources obey include containment (§7.7.6). Engine selection is explicit, then extension-based, then `lando`; values resolve through the standard expression context. Providers receive only rendered `inline` mounts. Rendered output uses the `<userCacheRoot>/templates/<engineId>/...` `template-render` cache (§12.1).

An excluded path belongs to the service. Every bind accepts `excludes` and `includes`; the app mount additionally starts from the defaults `node_modules`, `vendor`, `tmp`, plus service-type presets. Each eligible directory exclude gets a service-scoped storage shadow; an exclude whose host path exists as a non-directory gets no shadow and stays visible through passthrough binds. An `includes` entry that names an exclude exactly cancels it. An entry that is a literal relative path beneath a shadowed exclude of the same bind keeps that host path: planning binds it from the same source over the shadow, so the Lando 3 translation of `!vendor/acme` works. Includes that are absolute, contain `..`, or contain glob characters fail validation; `excludes` or `includes` on a store or tmpfs entry fail validation. A bare `!` entry in either list fails validation with remediation naming `includes`; the Lando 3 translator lowers `!x` to `includes: [x]`. VCS metadata is a fixed rule, not a key: `.git` is never shadowed and remains visible through ordinary binds. Every accelerated engine MUST support exclusion patterns and never sync `.git` unless `includes` names it. The exact patterns are derived from the finalized plan, not just the authored list: every effective exclude, including non-directory paths, the relative target of every other entry mounted beneath that bind (storage shadows, authored and cache stores, tmpfs, and nested binds, which also hide that subtree), and `.git`, deduplicated. A `storage` entry under the app mount and an `excludes` entry for the same path therefore produce the same container layout and the same patterns. Copy includes become binds. Ordering preserves nested-path semantics.

When a passthrough app mount's `.git` is a gitfile (a Git worktree or submodule checkout), planning bind-mounts the resolved common git directory, and the worktree git directory when it lies outside it, so git works at the app mount. An absolute `gitdir` mounts at the same container path; a relative one mounts where the gitfile resolves from the container app mount target, so git follows the file unchanged. Planning verifies each directory is a Git directory (it holds `HEAD`) before mounting; a gitfile alone never authorizes a host path. The binds are read-only when the app mount is read-only, never file-sync sessions, never override an authored mount or storage at the same destination, and are skipped when a host path is not a POSIX absolute path. Shared metadata is writable by every worktree's containers, as on the host.

Every bind entry has `realization: passthrough | accelerated`. The app mount's realization is decided once, from `bindMountPerformance` (§5.4), `appMount.accelerate`, and global `defaultFileSyncEngine`, and that one decision drives Git overlays, mount keys, session construction, and required-capability checks; every other bind, including authored directory binds and configuration files, is `passthrough`:

- `native` uses provider binds and no `FileSyncEngine` or `pre-file-sync-*` events; an explicit engine choice is still validated when host policy is evaluated (§4.3).
- `slow` with `accelerate: false`, or with `defaultFileSyncEngine: passthrough`, uses provider binds with no session and acquires no engine; bind capability errors still apply.
- `slow` with no eligible automatic engine uses ordinary binds and records `no-compatible-engine`.
- `slow` with an eligible engine and no opt-out uses a provider-managed volume named by the shared `fileSyncVolumeName` contract (`<app-name>-<service>-<mountKey>`, sanitized for the runtime) and a `FileSyncSessionSpec` under the engine selected by §4.3; the bundled engine is `@lando/file-sync-mutagen` (§4.2). This name is not a rename-stable ownership identity: provider labels and retained-plan evidence remain authoritative, and renaming an app requires a separate safe reconciliation design.
- `none` fails with `CapabilityError`.

The realization is invisible in canonical config and MUST NOT expose engine or session ids there. Every accelerated plan requires `two-way-safe` mode and exclusion-pattern support; engines receive exactly the derived pattern list, including non-directory paths. Directory overlays MUST NOT substitute for transport filtering. Eligibility is checked from metadata before any provider action, lifecycle hook, or rotation (§4.3). Verification compares exact lists for both new and historical plans; exclude entries remain in mount intent and are never silently dropped. The desired-plan cache key covers host platform, provider capabilities, configured default, selected engine id, and planning-sensitive engine capabilities and support metadata, so a policy change misses the cache without touching durable session state.

`AppPlan.fileSync` deliberately remains a flat persisted session array. At the operation boundary, one canonical internal bundle normalizes it into ordinary execution (zero accelerated binds and zero sessions) or accelerated execution (one engine id and exact session coverage). Mixed engines, contradictory realization, duplicate, missing, or orphan sessions fail closed before acquisition or action. Execution consumers use that bundle instead of independently rescanning engine ids. Normalization MUST NOT rewrite original persisted entries, session bytes, or journal digest inputs, and structural validation MUST NOT replace provider ownership or prepared-target verification. Retained plans and journals keep their original engine identity and synchronization history.

Optional bounded `AppPlan.fileSyncPolicy` metadata records one app-level engine and selection reason plus each service's realization and reason. Mixed service opt-outs are allowed. This metadata explains mount/session facts; it is not a second execution authority. Missing historical reasons stay unknown rather than being inferred from current global config (§6.10).

`mountKey` identifies an accelerated mount within its service: `app-mount` for the app mount, otherwise derived from its canonical target, so reordering `mounts:` never moves a session. It correlates the mount, sync volume, `FileSyncSessionSpec`, the engine's durable session state (§10.6.2), and lifecycle events. The planner stamps it on the bind entry once and every renderer and verifier reads it from there. A changed source or exclusion set changes the session spec, not the key. A changed engine id or an accelerated-to-ordinary change (`accelerate: false`, `passthrough`, or a provider that is no longer slow) is the same kind of transition even when the session specs would otherwise match. Start detects any of them before any other mutation, under the app lock: it validates the desired intent, verifies that the previously applied state is fully app-owned, acquires the engine recorded in that applied plan (never the newly selected one), quiesces the app's writers, drains pending target-side edits to the host, disposes the previous sessions and sync targets with their recorded specs, retires the previous applied state without removing named data or cache volumes and without running authored destroy steps, then applies the new plan: an ordinary start that creates zero sessions, or a normal accelerated start whose new sessions populate from the host. An unresolved conflict, missing session history, an unreachable recorded engine, unknown applied state, a failed drain, or an unfinished accelerated-start journal whose identity does not match the desired plan blocks the transition without applying the new plan or deleting targets. Each step resumes from the existing disposal phase or accelerated-start journal after interruption, and the user never terminates engine sessions by hand.

Engine selection errors, module/factory load failures, and disagreement between declared and acquired capabilities MUST fail before app lifecycle hooks or provider mutation. Once acceleration is planned, acquisition, setup, availability, target preparation, and ownership failures MUST remain tagged failures with actionable remediation, even for a new app. They MUST NOT silently downgrade to ordinary binds. A desired ordinary plan still passes the applied-state guard before replacing accelerated state and MUST NOT bypass drainage or retained history.

### 6.5 Storage

Storage declarations are a target path or `{ store, target, readOnly?, scope?, kind?, key? }`; they become volume entries in the mount list. An explicit `store` names the runtime volume verbatim; only the string shorthand derives a store name.

`home: false | { path? }` controls planned-user home persistence and is enabled by default. The planner always records `ServicePlan.home` as one of four states: `persisted` (`target`, generated `store`, optional user principal), `authored` (`target`, mount kind `volume`, `bind`, or `tmpfs`), `disabled`, or `unknown` (`reason`: `custom-image`, `no-identity`, or `undeclared-user`, plus the user principal when known). A persisted home adds a volume entry with `origin: derived` to `ServicePlan.mounts`; `ServicePlan.home` records that decision rather than providing another mount source. Unknown homes omit automatic persistence without failing planning. `home.path` supplies an explicit destination; `home: false` disables persistence. Any entry in the mount list exactly at the canonical home target wins, including the app bind, another bind, a volume, or tmpfs: the home is recorded as authored and Lando generates nothing over it.

Start, rebuild (including selected services), and restart warn once per affected service when an applied persisted home becomes unknown or changes store or target, before apply, naming the untouched previous volume and the explicit storage declaration that mounts it at its previous target; authored or disabled homes, removed services, and older applied plans without home metadata stay quiet.

Catalog `ServiceImageIdentity` declares `defaultUser`, principal-keyed `homes`, and optional `preparedHomes`: principals whose passwd home the image does not create or give to that user. An authored image canonically equal to the artifact pinned by an explicitly versioned service type retains this identity; without such a pin, an authored image is custom. Genuine Docker Hub aliases and implicit `library/` and `:latest` compare equally, but other registries, tags, and digests remain distinct. A different image or authored Compose build context does not inherit catalog identity. The principal is the planned user's name without its group suffix, otherwise the catalog default user. Generated home stores are `lando-<slug>-<service>-home-<readable>-<digest8>`, where readable is the lowercased principal with characters outside `[a-z0-9_.-]` replaced by `-`, surrounding hyphens trimmed, and capped at 32 characters; digest8 is the first eight hex digits of SHA-256 of `<service>\0<principal>`. Only an explicit path with no known principal uses `lando-<slug>-<service>-home`.

For a generated persisted home on a non-custom image, a non-root principal in `preparedHomes` has its target created and owned in the existing root data-tree build step (`mkdir`, `chown`, `chmod`), including when selected implicitly by `defaultUser`. A fresh named volume seeds that ownership from the derived image; existing populated volumes keep their ownership. Home contents MUST NOT affect build keys. Legacy `/lando`, `/helpers`, and user-config-directory mounts MUST NOT return.

| Scope | Lifetime |
|---|---|
| `service` | One service in one app; default |
| `app` | Shared within one app |
| `global` | Shared across apps when supported; survives `lando destroy` |

`scope: project` is not accepted. A `ConfigTranslator` MAY rewrite it to `app` (§7.4.1).

`kind: data` is the default. `kind: cache` defines a named cross-app dependency cache, auto-named `lando-cache-<key>` with `key` defaulted from the target, labeled `dev.lando.storage-kind: "cache"`, and removed only by `lando destroy --purge-caches` or `meta:cache:*`. Cache kind is global by nature; combining it with `scope: service` is a planning error. It is distinct from data movement (§10.11).

For the string shorthand, names are `lando-<kebab(target)>` for `global`, `<project>-<kebab(target)>` for `app`, and `<project>-<service>-<kebab(target)>` for `service` (shipped naming and deferred `global` data storage are tracked in #1810).

Every volume Lando creates carries one label set, written by the single volume-creation owner in `@lando/container-runtime`: `dev.lando.app` (app id), `dev.lando.store` (store name), `dev.lando.scope` (`service`, `app`, or `global`), `dev.lando.volume-instance` (a per-creation generation id that every volume-delete gate rechecks live before a name-addressed removal), the ownership pair below, the scratch labels when a scratch app planned the store, and `dev.lando.storage-kind: "cache"` for cache stores only, so its absence means a data volume. No other storage label exists; providers MUST NOT invent one. The `dev.lando.*` namespace is reserved. Teardown selects volumes through the ownership selector and the class table (§5.3.1), never by name or by a label subset: plain destroy retains data volumes, `--volumes` removes the app- and service-scoped data volumes the selector proves this app owns, `--purge-caches` removes caches, and `dev.lando.scope: "global"` data volumes stay.

**Anonymous volumes have container lifetime.** A planned store is a named volume: every `storage` entry, every `volumes:` or `mounts:` volume form (including the bare `/path` spelling), home persistence, exclude shadows, caches, and file-sync targets. Only named volumes are subject to the retention rules in this specification. A volume the runtime creates on its own for an image `VOLUME` path that no planned store, mount, or tmpfs covers is anonymous: it carries no Lando labels and no ownership proof, and no retention rule or volume flag addresses it. Whenever Lando removes a container (whole-app stop, destroy, bare restart, rebuild, create-config recreate, scratch and global teardown, ownership-inventory cleanup, and helper and ephemeral containers), the provider MUST request runtime removal of that container's unused anonymous volumes (Docker-compatible `v=true`) and MUST NOT remove a named volume by that path. An anonymous volume another live container still uses stays, by runtime rule. Selected in-place restart removes no container and so no volume; a failed or interrupted start retains live resources unchanged (§6.15). This is container-scoped removal, not a prune: Lando MUST NOT enumerate or remove anonymous volumes it did not just detach, including ones left by earlier revisions. Data that must outlive a container MUST be declared as a store.

**Ownership proof and selection.** Two further labels carry volume ownership, and they are not interchangeable:

- `dev.lando.volume-owner` records the canonical app root verbatim. It is the ownership **proof**: the planful volume-delete gate, create-race detection, adoption and witness checks, and SQL recovery adoption compare it against a root they already hold.
- `dev.lando.volume-selector` packs provider id, app id, owner key, and volume class (optionally scope) into one `:`-joined value. It is the ownership-complete **selection** value: bring-down's local match and the daemon-side prune filter select on it alone, because a daemon ORs the values listed under one label key, so ownership split across keys would broaden a prune.

The invariant: the selector's owner key is `appIdentityKey("owner", <canonical app root>)` from `@lando/sdk/schema`, the same derivation the planner stamps onto `AppPlan.identity`, so both labels are derived from one root. One owner in `@lando/container-runtime` emits the pair together and every reader resolves ownership through the same function; a label is never written without its partner, and no call site re-spells the key or falls back to a raw root. A plan that carries no `identity` is migrated at read time from `plan.root` through the same derivation (the planner assigns `root` from `identity.appRoot`, so the key is byte-identical), never written in a second selector format. Volumes created by earlier revisions carry selectors that match neither form and are neither adopted nor pruned by selection; recovery of such volumes goes through the proof label and the documented adoption paths, not through a looser selector.

Global-app storage substitutes `global` for project identity, so its volumes carry `dev.lando.app: "global"` and an ownership pair derived from the global root rather than a separate global-app volume marker; service and app names are `global-<service>-<destination>` and `global-<destination>`. Only global scope survives `meta:global:destroy --purge` (§20.9).

Scratch storage substitutes `<scratch-id>`, producing `<scratch-id>-<service>-<destination>` and `<scratch-id>-<destination>`, labels volumes with `dev.lando.scratch: "TRUE"` and `dev.lando.scratch-id`, and rewrites global scope to app scope unless `--share-global-storage` is present. Scratch destroy removes effective service/app storage unless `--keep-volumes` is used (§21).

### 6.6 Endpoints, hostnames, and routes

`EndpointInput` and `EndpointPlan` are discriminated unions. `InternalEndpoint` carries a network protocol and port or a Unix `socketPath`. `PublishedEndpoint` permits `http`, `https`, `tcp`, or `udp` and requires `publication`; `{}` requests defaults. Default bind is `127.0.0.1`; omitted `hostPort` requests provider assignment. Runtime assignments are provider observations (§5.3, §6.10) and never rewrite desired state. Unix sockets cannot be published.

**Logical listener identity.** Network endpoint entries are facets of a logical listener identified by container port plus transport, where `http` and `https` imply `tcp`. One listener MAY carry several facets: an internal entry beside one or more publications, each with its own bind address or host port. `EndpointRef` (`port`, `transport`, sorted unique `names`, `primary`) is the public reference to a listener; `groupLogicalEndpoints`, `endpointInvariantIssues`, and `selectHttpEndpoint` in `@lando/sdk/schema` are the only grouping, invariant, and selection rules, and every consumer uses them.

- `name` is an alias of the listener. Different facets of one listener MAY carry different aliases, and repeating a name on facets of the same listener is allowed; the same name on two different listeners is an `alias-collision`. Unix endpoints own their names in the same alias space.
- Explicit protocols of one listener MUST agree; `http` beside `tcp` on one port is a `protocol-conflict`. A publication synthesized from `ports:` with no matching declaration is `tcp` or `udp` and is not an explicit protocol declaration.
- Optional `primary: true` (the only accepted value) marks the logical primary network listener regardless of facet count. At most one listener per service MAY be primary (`multiple-primary`). Marking a listener primary is metadata: it changes selection and reporting, never what the daemon launches or whether a host port is published.
- Optional `appProtocol` is opaque application-layer metadata preserved verbatim. It is never a URI scheme, never promotes a `tcp` listener to HTTP, and never affects selection or scanning.

Invariant violations are shared resolved-Landofile findings at `services.<name>.endpoints` under `landofile.service`. Lint reports them as violations; planning aggregates them as `ValidationIssue`s inside one `LandofileValidationError` before provider action. A service with invalid endpoints is unavailable for route binding, not a service with zero HTTP listeners.

**One mandatory normalizer, after every declaration.** The provider-independent endpoint projection (§6.11.0) gathers ORIGINAL service-feature declarations followed by app-feature declarations, then runs one pure normalizer over that complete set plus `normalizedConfig`. Lint and planning inherit this projection. Planning retains its original contributions for finalization; it MUST NOT invoke declaration callbacks again or obtain additional endpoints from feature application. Finalization uses the same normalizer, and synthesized output is never fed back in as a new declaration.

The normalization policy is unchanged: an explicit `endpoints:` list, including `endpoints: []`, is authoritative and replaces type and app-feature contributions and anything inferred from `ports:` or `expose:` (§6.2). Otherwise every contributed listener survives (`ports: []` is not an opt-out), each `ports:` entry adds a publication of its target port carrying the matching contribution's protocol and `primary` marking, plus its single alias and single `appProtocol` hint unless the entry authors its own Compose `name` or `app_protocol`; a target no contribution declares is `tcp` or `udp` from the entry, and each `expose:` port adds an internal `tcp` listener when that identity is not already present. Identical facets dedupe; aliases are preserved. A late app-feature HTTP declaration therefore classifies a matching `ports:` publication as HTTP before selection. Neither image metadata, port 80, `expose:`, nor `appProtocol` implies HTTP. No provider or consumer may re-derive listeners from `ports:`.

**Default HTTP selection has no ordering fallback.** `selectHttpEndpoint(endpoints, selector?)` chooses the marked primary when it is `http` or `https`, else the service's single distinct HTTP(S) listener, else returns `none` or `ambiguous` with the candidate listeners; a named or numeric selector restricts candidates to that alias or port. List order never decides. A service whose generated default route, or an authored route without `endpoint`, is ambiguous fails planning with `LandofileValidationError` and remediation to mark one listener `primary: true` or name the endpoint; `app:open` and sharing never pick an ambiguous target by order. A TCP primary beside one HTTP secondary (Mailpit's SMTP primary and HTTP UI) selects the HTTP listener for routes while `ServiceConnection.endpoint.primary` still identifies SMTP.

HTTP(S) network endpoints MAY carry plan-only sparse `scan` defaults for `path` and `okCodes`, using the scanner's existing constraints (§10.5.3). These are not endpoint-authoring syntax, a readiness contract or another listener registry. Matching publications synthesized from `ports:` inherit the listener defaults. Defined contradictory defaults for one logical endpoint fail normalization; omission can inherit, and equivalent status-code sets are not contradictions. Explicit `endpoints:` replaces all discovery, including its scan defaults. Final planning resolves endpoint defaults below explicitly supplied global and service scanner fields, storing the effective policy on the endpoint; absent metadata on historical applied plans uses service-policy fallback rather than type-name inference. Scan metadata does not change listener identity, routing selection or host publication.

**Authored route binding is a shared validation check.** Every evaluated authored entry under service `routes:` or top-level `proxy:` MUST bind through that same HTTP selection rule. Missing HTTP listeners, selectors that match no HTTP listener, and ambiguous selection are indexed `landofile.route` findings in lint and issues in planning's aggregate `LandofileValidationError`. The binding result is pure and shared with runtime route assembly. It retains the effective path (`["services", name, "routes", index]` or `["proxy", name, index]`) separately from authored source provenance and the display key, even when earlier entries were malformed or blocked. Remediation distinguishes declaring HTTP from selecting among existing HTTP listeners. Binding validation does not contact the listener. Automatic route generation/selection and assembled-route conflicts remain planning-only (§7.8).

`hostnames:` adds provider-network aliases; each entry MUST satisfy `DomainName` once evaluated. The planner adds `<service>.<app>.internal` when `sharedCrossAppNetwork` is supported. Whenever a service joins the shared cross-app network, its realized alias set MUST contain the canonical qualified alias `<service>.<slug>.internal` exactly once, unioned with any additional authored aliases, including when the authored alias map is empty; `landoServiceNetworkAliases` in `@lando/sdk/schema` is the only derivation.

Routes live under top-level `proxy:` or preferred service `routes:`. Every `RoutePlan` has a resolved `backend` with service, protocol, and port; proxies MUST NOT guess. Shorthand normalizes to `hostname`, `scheme`, `endpoint`, `pathPrefix`, and `filters`. Shorthand and object routes share hostname and path-prefix constraints: in object form `hostname` contains only the host pattern, with any port in `endpoint` and any path in `pathPrefix`, and an explicit `pathPrefix` MUST begin with `/` and contain no whitespace, query string, or fragment. Each hostname label is at most 63 characters and the whole hostname at most 253. The constraints apply to concrete values, so the planner's resolved-Landofile validation (§7.8), shared by lint and planning, checks every route after its expressions are evaluated and reports every invalid field in one run. `RoutePlan.hostname` and optional `RoutePlan.pathPrefix` use the public `RouteHostname` and `RoutePathPrefix` schemas, and final plan validation enforces those grammars for authored routes, generated defaults, and plugin contributions. Invalid object fields identify `hostname` or `pathPrefix`, invalid shorthand identifies the route entry, and both carry actionable remediation. Invalid authored route fields are `ValidationIssue`s that planning aggregates in one `LandofileValidationError`; `RouteInputError` is reserved for conflicts between assembled routes. Non-empty filter overlays merge by `name`, then unnamed type identity, and retain authored order; an explicitly empty overlay clears inherited filters (§7.2). Prefix stripping MUST NOT be implicit (§10.2). Layered route matching uses the same scheme, case-insensitive hostname, and path-prefix identity as planning (§7.2), regardless of shorthand or object spelling.

Built-in route filters are `requestHeader`, `responseHeader`, `redirect`, `rewritePath`, `stripPrefix`, `addPrefix`, `auth.basic`, and `rateLimit`. Plugins contribute `routeFilters:`.

Default route hostnames are `<service>.<app>.<domain>`, where `<domain>` is the global `proxy.defaultDomain` (default `lndo.site`). It MUST satisfy `DomainName`: dot-separated ASCII letter, digit, and hyphen labels without empty labels or leading or trailing hyphens, at most 63 characters per label and 253 overall; schemes, ports, paths, whitespace, trailing dots, and wildcards are invalid. Global-config decoding and schema-validated writes reject other values, and `lando config set --dry-run` performs the same validation without writing. When a service authors neither `services.<name>.routes` nor `proxy.<name>`, core finalization routes that hostname over HTTPS to the listener `selectHttpEndpoint` chooses (above), recording its alias or port as the route `endpoint`; `none` generates no route and `ambiguous` fails planning. Service types contribute endpoints, not default routes. A service that authors either gets exactly its authored routes, so an explicitly empty list opts it out of routing without affecting published endpoints. LAN publication is opt-in and warns. Internal endpoints never bind the host.

Service types MAY contribute default checks (§10.5.2) for the endpoints they declare, such as a `tcp` check for a database, and `service-error` rules for their own server pages (a web server's 502 when its upstream is down). Authored service-level `checks` tune or disable them. Types never contribute `expected` or `app-error` rules; those come from profiles and the Landofile.

Scratch plans apply `RouteFilter.ScratchHostnameSuffix` unless suppressed by `--hostname` or `--no-hostname-suffix` (§21.9.2).

**Cross-app route priority.** Every app's routes are merged into one router table, so `RoutePlan.priority` is one shared space, not a per-app ranking. The planner derives priority from the route alone: wildcard-hostname routes occupy the band `ROUTE_PRIORITY_WILDCARD_BASE` (2) through `ROUTE_PRIORITY_WILDCARD_BASE + ROUTE_PATH_WEIGHT_CAP`, exact-hostname routes occupy `ROUTE_PRIORITY_EXACT_BASE` through `ROUTE_PRIORITY_MAX`, and within a band the path-prefix length widens the priority up to `ROUTE_PATH_WEIGHT_CAP` so bands never overlap. `@lando/sdk/schema` owns these constants. For any two routes on concurrently applied apps that match the same request, an exact hostname MUST win over a wildcard and a longer path prefix MUST win over a shorter one, independently of how many routes each app declares and without relying on a router's own rule-length tie-break. The derivation MUST NOT include a plan-size or in-plan-index term: a plan ranked in isolation MUST compose correctly with plans it cannot see. The diagnostic fallback keeps `ROUTE_PRIORITY_DIAGNOSTIC` (1), below every app route, and a router that contributes its own routers MUST pin them above `ROUTE_PRIORITY_MAX` or an app claiming that hostname captures them. This does not introduce cross-app hostname ownership: two apps MAY still claim overlapping hostnames; only the more specific claim wins deterministically.

### 6.7 Native health and lifecycle readiness

Disabled objects MUST validate every supplied sibling, including `kind: none` and effective Compose disabling. Normalization MUST discard executable fields but retain validated settings and execution metadata as `kind: none` when any remain; an otherwise empty disabled object becomes `false`. Role validation MUST still reject unsupported native execution metadata. Authored `kind: http` and `kind: tcp` MUST fail planning before provider actions with `LandofileValidationError` at the corresponding `services.<name>.<policy>.kind`, preserving the authored source when available and command-probe remediation. Schema acceptance describes future intent, not runner availability.

`HealthcheckInput` accepts `false`, command forms, or an object. `false` disables the corresponding policy. A non-empty string is a shell command and a non-empty bare string array is literal argv, both shorthand for `{ command }`; Compose `CMD`/`CMD-SHELL`/`NONE` markers are interpreted only in an object's `test` array. `load()` MAY provide any form (§7.3). Forms are interpreted after authored composition. Literal `false` replaces lower probes wholesale, and a higher object then replaces that scalar rather than reviving its discarded probe. Object disabled spellings (`disable: true`, `test: [NONE]`, `kind: none`) are ordinary mappings during composition, not reset barriers; inherited siblings remain unless replaced or reset explicitly. Literal `false` remains `false`; disabled objects retain normalized settings as described above. Lando keys retain precedence over equivalent Compose fields. Shared execution metadata (`target: service | host`, optional `user: ContainerUser`) MUST survive normalization with either dialect and MUST NOT select the Lando dialect by itself. An authored `false` drops the service type's default for that policy only. `HealthcheckRunner` executes `HealthcheckPlan` using `runProbe`; service execution uses the selected `RuntimeProvider.exec`, while host execution uses the host runners (§10.5.1).

**Independent policies and defaults.** Both authored `healthcheck` and `readiness` accept disabled, string, argv, and normalized command/timing object forms through `HealthcheckInput`. `ServicePlan.healthcheck` is ongoing native container health; only this field enters native create requests and Compose output. A feature MAY contribute stronger `ServicePlan.readiness` through `setReadiness`. Authored `healthcheck` overrides only native health, and authored `readiness` overrides only lifecycle readiness. Omitted readiness MUST preserve contributed readiness, otherwise `effectiveReadiness(service)` selects effective native health. Authored `readiness: false` MUST produce explicit `kind: none`, blocking fallback while preserving process-running and completion supervision. `healthcheck: false` disables native/image health without disabling explicit or contributed readiness. `ServicePlan.readinessSource` records only `authored` or `contributed`; healthcheck fallback and historical unknown provenance are derived. Every barrier, app-build gate, and `service_healthy` dependency MUST use effective readiness. A healthy dependency requires enabled command readiness; planning MUST reject a disabled target rather than relax the gate. Policies and resolved listener identity participate in cache/fingerprint identity. Readiness provenance is retained as plan metadata, not execution intent. MongoDB's contributed readiness proves final-server protocol access on its declared listener, not authentication or agreement between Landofile credentials and persisted users.

**Execution location and identity.** Authored `target` defaults to `service` and lowers to plan `executionTarget`, separate from persisted listener `target: EndpointRef`. Native `healthcheck` MUST reject `target: host` or ANY explicit probe `user`, including disabled objects, before action with `HealthcheckTargetUnsupportedError` and move-to-readiness remediation; explicit `target: service` is a no-op. Readiness supports service probe users without changing main-process identity or native monitoring. Host readiness requires its own authored/composed command and MUST inherit no type command, listener, or container user. Host plus user, listener, or missing command MUST fail planning before mutation with `HealthcheckTargetUnsupportedError` at the authored readiness field. Host execution is CLI-current-identity at app-root cwd, Bun Shell for strings and exact ProcessRunner argv, never a provider VM, sandbox, or permanent monitor. It MUST NOT depend on routes or dependent services behind its own gate.

**Declared probe targets.** A service-executed command `HealthcheckPlan` MAY carry `target: EndpointRef` naming one of the service's declared logical listeners by port and transport (§6.6); `names` and `primary` are descriptive. This listener identity is distinct from authored `healthcheck.target: service | host` and plan `executionTarget`. `serviceListenerTarget` in `@lando/sdk/schema` is the single derivation of the host a targeted probe dials: the service name on the private app network when the plan has one, otherwise the canonical `<service>.<slug>.internal` alias on the shared network. An undeclared listener, a plan with no managed network, or a loopback host fails planning with `LandofileValidationError` before any provider action; an authored custom probe may describe a different topology. One container-runtime probe compiler resolves the target and supplies it to the command as `LANDO_PROBE_HOST` and `LANDO_PROBE_PORT`; native create requests, dependency gates, Compose output, fingerprints, and the engine runner MUST use that compiler rather than interpolating hostnames separately, and an untargeted command receives no injected target. Probes MUST NOT discover interface addresses, fall back to loopback, or add a provider networking API. App-scoped `ServiceConnection` listener hosts (§6.10) use the same derivation. Listener, protocol, and executable failures MUST yield short safe evidence: the runner retains bounded redacted stderr together with the safe target, attempt count, elapsed time, and exit code rather than reducing the failure to `exit N`.

Start, restart, rebuild (full or selected), and global-service start MUST complete a concurrent readiness barrier before publishing `post-app-start` or `post-start`. One private engine startup-completion owner (`completeStartup`, taking a closed discriminated request union rather than a callback bag or phase array) runs every post-apply sequence and preserves each policy's order: user start runs app build, routes, then readiness; selected restart runs file-sync start then readiness; selected rebuild runs forced selected app build then readiness; ensure-global runs readiness; global groups run concurrent readiness per applied group, aggregate failures, and publish routes only when every group succeeded; scratch runs the existing soft-fail routes then readiness. Apply and preflight wrappers, initial inspection, accelerated journals, agent acquisitions, volume locks, pre/post events, and scans keep their current owners. Readiness is never skippable, success events publish only after completion succeeds, global rebuild revalidation still precedes its post-event, and selected requests carry the full classification plan including unselected job consumers. Unsupervised exited services and exhausted healthchecks MUST fail with `ServiceNotReadyError`, naming the service, reason, available stopped-container exit code, bounded redacted log tail, and remediation. User/global startup failure or interruption MUST preserve established resources at every phase. Dependency gates remain strict and retain `ServiceStartError`; readiness failures retain `ServiceNotReadyError`. Retry MUST reconcile observed resources with desired intent. Scratch ownership follows §21. Interruption MUST stop waiting, cancel in-flight probes, and still propagate to the CLI. Prepared sync targets, sessions, and an unfinished accelerated-start journal stay for the next start to resume (§10.6.3). URL-scan failures MUST warn, not fail startup.

A target of a `service_completed_successfully` dependency in the full plan is a completion-intent service: it MUST have verified exit code 0 and MUST skip readiness command waiting, including selected operations. Other unsupervised services MUST remain running throughout readiness; services without enabled command readiness settle against their current container start, with the remaining host-side wait bounded to two seconds despite engine clock skew. Container replacement or restart invalidates unsupervised readiness. Successful rows are `ready` after effective readiness passes, `running` without an enabled command gate, or `completed` after verified successful completion.

For non-completion services, authored `restart: always` or `unless-stopped` permits a `restarting` warning on exit or observed restart; `on-failure` permits it only with an observed non-zero exit code. Missing `restart`, `restart: no`, and `on-failure` exit 0 remain strict. Exhausted readiness MUST fail for every service: restart policies do not restart a running-but-unhealthy process. Provider inspection failure MUST use reason `inspect-failed` and MUST NOT become a supervised warning. Warnings MUST name the service and reason and include available terminal exit code and a short redacted log tail. `restarting` rows MUST use a warning tone. Non-instant readiness waits MUST publish progress naming the waiting services and settle their rows individually.

Lifecycle readiness MUST probe immediately. Failures during `startPeriodSeconds` MUST NOT count against retries; probes during that period use at most a one-second interval and return on first success. After that period, allow at least one attempt, otherwise `retries` attempts at `intervalSeconds`, each bounded by `timeoutSeconds`. Native scheduling remains the container runtime's responsibility.

Readiness remediation MUST address the app kind: user apps use `lando logs -s <service>` and `lando start`; global apps use `lando global:logs -s <service>` and `lando global:start`; scratch apps use their scratch-addressed inspection surface and MUST NOT prescribe user-app start. Provider observation failures prescribe `lando doctor`, not service logs. The supervised warning follows the same app-kind rule.

`ServiceNotReadyError` applies only after committed provider apply; apply and dependency-gate failures use `ServiceStartError`. Both share the retention policy above. Supervision MUST NOT relax `service_healthy` or `service_completed_successfully` gates. Scratch acquisition runs the barrier but readiness failure and interruption follow §21 scope cleanup and `--keep-on-failure`, not user-app retention.

Language runtimes (`node`, `python`, `ruby`, and `go`) MUST NOT infer default health or readiness checks from ports or commands; endpoints remain available and authors MAY declare either policy explicitly.

The engine owns each service/host readiness attempt through an invocation-scoped `executeReadinessAttempt` delegate (§5.3, §10.5.1). Providers retain resource ownership and start-graph scheduling. Full engine-owned scheduling is deferred pending provider-neutral per-service lifecycle primitives and partial-apply/cancellation ownership; this contract MUST NOT be represented as a completed scheduler extraction.

### 6.8 Certificates and security

`certs:` accepts enabled, disabled, a certificate path, or custom certificate/key paths. `CertificateAuthority` generates leaf certificates covering the service name, `<service>.<app>.internal`, configured hostnames, route hostnames, `localhost`, and `127.0.0.1`. Paths are exposed as `LANDO_SERVICE_CERT` and `LANDO_SERVICE_KEY`.

`security.ca:` and aliases `cas`, `certificate-authority`, and `certificate-authorities` add project CAs. The `lando.security` feature mounts and installs them; core defines intent, not distribution mechanics.

Per-service `security.inheritNetworkCa` and `security.inheritNetworkProxy` override those defaults. Only services composing `lando.security` participate; `l337` and raw Compose do not auto-inject.

The effective CA set is global `network.ca.certs`/`LANDO_NETWORK_CA_CERTS` followed by project CAs, deduplicated by content. Open-ended host Dockerfile drop-ins are a non-goal. Installation precedes `build.app:` and tooling. Injected CA identity participates in artifact `buildKey` calculation. Providers MUST honor resolved proxy/CA settings for every Lando-initiated pull and build regardless of service injection.

### 6.10 Service info

Provider-neutral `ServiceInfo` contains `app`, `service`, `api`, `type`, `provider`, `primary`, `status`, the required array `connections`, optional `logSources`, and optional `creds`. `status` is the shared `ServiceState` vocabulary: `unknown`, `stopped`, `starting`, `running`, `healthy`, `unhealthy`, `ready`, `completed`, `restarting`, `paused`, or `error`. `StartedService` (`name`, `state`, `connections`) in `StartAppResult.servicesStarted`, global ready output, restart, and rebuild carry the same `connections` contract; `ServiceConnection` is the only connection-address contract.

**`ServiceConnection`.** Every connection carries `host` (hostname or unbracketed IP), `endpoint` (the `EndpointRef` of the logical listener it originates from, §6.6), `scope`, `source`, `protocol`, `binding`, and `state`. The union is:

| `scope` | `source` | `protocol` | `binding` | Meaning |
|---|---|---|---|---|
| `app` | `listener` | `http`, `https`, `tcp`, `udp` | `assigned` | The service key on the per-app network plus the listener port, for every planned network listener including the container side of a published port |
| `host` | `publication` | `http`, `https`, `tcp`, `udp` | `assigned` or `pending` | A direct host publication of the listener |
| `host` | `route` | `http`, `https` | `assigned` or `pending` | Router ingress for a `RoutePlan`; adds `pathPrefix`, retained in the URL |

An `assigned` connection carries `port`, `url`, `alternateUrls`, and `state` in `active`, `inactive`, or `unknown`. A `pending` connection carries `state` in `inactive` or `unknown` and MUST NOT carry `port`, `url`, or `alternateUrls`: a configured publication whose host port is unassigned, or a route with no ingress authority, is represented without an invented address. The declared listener `protocol` is independent of `appProtocol`, and an unknown secondary TCP publication is never reported as HTTP. Addresses come from the §6.7 listener-target derivation: the service key on the per-app network, or the canonical `<service>.<slug>.internal` alias only when the service has no per-app network and sits on the shared network alone. Unix sockets are excluded because their sharing is not established.

**URL formatting.** One central formatter produces `url` and `alternateUrls` from host, port, protocol, and route path. Hosts are lowercased and stored unbracketed; a wildcard or loopback bind address is reported as the host a local client dials (`0.0.0.0` and `127.0.0.1` as `localhost`, `::` as `::1`). URLs bracket IPv6 hosts, omit default ports `80` and `443` for `http`/`https`, preserve route `pathPrefix`, and keep `tcp://` and `udp://` for unknown transports. Client URI policies are scoped to the declared database listener of the service type: PostgreSQL emits the encoded user and database and never the password; memcached emits `memcached://`; Valkey emits `valkey://` with a `redis://` alternate. Arbitrary secondary or unplanned bindings are not painted as database connections.

`DatabaseConnection` (§6.12.4) is a separate planned credential/primary-port fact, not a scoped address. PostgreSQL URI enrichment reads its canonical family, user, and database only when the TCP listener's container port matches the fact's port; an assigned host publication may use a different port in its URL. Missing facts produce the generic connection URI, without environment scraping or guessed credentials. Neither password descriptors nor resolved passwords enter canonical or alternate addresses, and observation never reads a secret store to format them.

**Observation versus plan.** Configured listeners, publications, and routes are always retained, including pending dynamic ports, so a stopped service reports its addresses as `inactive` rather than erasing them. An `app` listener is always `assigned`; its state follows the service state and is `inactive` when the container is proven missing. A `host` publication is `active` only when an actual `PublicationObservation` binding matches its listener, bind address, and any explicit `hostPort` (§5.3); the connection then reports the observed host port. Without a matching binding, an explicit `hostPort` stays `assigned` and a provider-assigned port stays `pending`, each with state `inactive` (evidence present, or service inactive) or `unknown`. An observed binding that matches no planned publication is still reported, as a `tcp` or `udp` publication of an unnamed, non-primary listener, never as HTTP. A route is `active` only from matching `RouteEvidence` (§10.2); with no configured or observed ingress authority it is `pending`, and with routing disabled it is never `active`. Service state maps to connection activity through one shared rule: `stopped`, `completed`, `paused`, and `error` are `inactive`; `starting`, `restarting`, and `unknown` are `unknown` unless absence is proven; `running`, `healthy`, `unhealthy`, and `ready` permit `active`. Active never asserts health. One collector/projector powers `info`, `start`, `restart`, `rebuild`, and global status as well as the hyperlink, `app:open`, and scanner consumers; no command concatenates routes or erases state on its own. Only `host` connections that are `assigned`, `active`, `http` or `https`, and not wildcard hostnames are eligible for hyperlinks, `app:open`, and HTTP scans; `app` connections are never host-clickable. `info` reads the applied plan when one exists, so connection metadata describes the last applied plan, not necessarily an unapplied Landofile edit.

`ServiceInfo` also projects safe planned per-service metadata when its source exists: `artifact`, `user`, `home`, `workingDirectory`, resolved `appMount` (the `role: app` bind entry), `hostnames`, `certs`, and `health`. These fields remain schema-optional for historical or hand-built plans; absence means no fact was recorded, not an inferred default. `artifact` carries either `{ kind: "ref", ref, digest? }` or `{ kind: "build", contentHash? }`; build context, arguments, inline specs, commands, environment, and raw provider extensions never enter info. `hostnames` is the stable deduplicated list of aliases from the canonical service network attachments, empty when no network attaches the service. It excludes route hosts, certificate SANs, and host-file aliases. `certs` carries only `{ state: "none" | "generated" | "custom" }`: a historical generated `{ cn, sans, caId }` certificate plan projects `generated`, while the certificate feature records custom or disabled provenance as a private scalar `@lando/core/certs` service extension that projects `custom` or `none`. Only those two exact scalar extension values are accepted; malformed, missing, and historical facts leave `certs` absent. The public `CertificatePlan` remains the original generated leaf certificate struct. `health` carries the planned ongoing healthcheck kind and timings when declared, plus the provider's existing inspected health state (`unknown`, `starting`, `healthy`, or `unhealthy`); it omits probe commands, URLs, and targets. A readiness-only probe does not count as an ongoing healthcheck. The optional JSON-safe `providerInfo` slot is reserved for explicit provider-supplied details and remains absent while no such source exists. It is the sole provider-specific field; everything else is provider-neutral. Human info summaries show artifact and user, and plain text adds detail rows without changing its service table columns.

`ServiceInfo.readiness` MUST describe configuration, not last-proof state. Its states are `disabled`, `not-configured`, and `not-observed`; its sources are `authored`, `contributed`, `healthcheck` (fallback), `unknown` (historical provenance), and `none`. Safe metadata includes execution target, `userSource`, listener, timings, command presence, and configuration pointer, never raw commands. Native `health` uses existing provider observations (`healthy`, `starting`, `unhealthy`); explicit native `none` is `not-monitored`, and missing evidence is neutral `unknown`. Info MUST NOT run probes, add provider inspect calls, write durable state, infer readiness from running/native health, or imply a last-readiness proof. Start's `ready` result remains observed gate success for that invocation. Durable proof is deferred pending generation/probe identity, provenance, failure/interruption invalidation, and orphan handling.

`home` is schema-optional for historical or hand-built plans; newly planned services always carry it. Info projects `home` unchanged when present: human output labels the retained persisted-home mount `home`, shows one `home` explanation and `services.<name>.home.path` hint only for unknown automatic persistence, and adds no home row for authored or disabled homes.

`ServiceInfoLogSource` distinguishes file sources from pathless console aliases (§6.14). A console alias carries `strategy: console`, its selected `stream`, id, and availability state with an optional reason; it MUST NOT fabricate `path`, `required`, or `timestamps` fields. Human summaries render the destination as `console/stdout` or `console/stderr`. File-source info retains its path and existing availability contract.

Structured `EndpointPlan` stays the plan contract and `PublicationObservation` stays the provider contract. Library consumers read `EndpointPlan` through `App.plan`; observed bindings come from runtime inspection, not from `App.plan`, `ServiceInfo`, or `app:config`. `ServiceInfo` carries connection addresses only.

`ServiceInfo.mounts` projects every user-visible planned mount (entries with `origin: integration` excluded) with `origin: planned` and its `provenance` (`authored`, `service`, or `derived`), plus any extra mount the container inspection reports with `origin: runtime`. Each entry carries `observation` (`present` when the container's mount table confirms it, `missing` when the container lacks it, `unknown` without evidence) and `lifetime` (`retained` for binds and named stores, `container` for tmpfs, `unknown` for runtime-only volumes). An accelerated bind is matched against its sync volume.

`creds` exists only for opted-in types; its password fields are always redacted in `ServiceInfo` (§6.12.4).

Application info additionally exposes optional `fileSync` (`FileSyncInfo`), separate from `ServiceInfo`. Its optional `planned` and `applied` snapshots (`FileSyncPolicyInfo`) describe desired policy and recorded applied-plan evidence respectively; missing evidence omits the snapshot. `pendingChange` compares the two snapshots when both exist and is false otherwise. Neither a snapshot nor `pendingChange` certifies running services, live sessions, or daemon health.

Each snapshot carries `mode: ordinary | accelerated | unknown`, one optional app-level `engineId`, a `FileSyncPolicyReason`, and a `services` list. Each service carries its name, `mode: ordinary | accelerated | absent | unknown`, reason, `exclusions` (`kind: transport-patterns | directory-overlays | none | unknown`, exact `patterns`, and derived `overlays`), and `hostBackedIncludes` pairs (`source`, `target`). Ordinary patterns are empty. Exact includes that cancel overlays and nested host-backed includes both remain visible in this projection. Engine ids MUST NOT repeat per service. Reasons distinguish explicit/default/sole engine selection, native providers, global passthrough, no compatible engine, service opt-out, absent app mounts, and unknown history. Mode and engine identity are validated against mount/session facts; absent or contradictory explanatory metadata yields unknown reasons, not invented facts. Info MUST NOT acquire an engine, probe tools, list daemon sessions, or reselect an applied engine to construct this view.

### 6.11 Service type and feature contracts

#### 6.11.0 Planning and conformance

Core performs one deterministic pipeline:

1. Resolve each `ServiceType` to `ServiceTypeResolution`, including parent and artifact version resolution. `resolve()` MAY be asynchronous but MUST NOT build a plan.
2. Resolve the effective base defaults and `FeatureRef`s. Prepare feature occurrences once, validate effective service-feature configuration, then project endpoints through optional service declarations in stable ascending priority and optional activated app declarations in stable ascending app-feature priority. Normalize the combined declarations and validate authored route bindings in the shared resolved-Landofile stage (§7.8).
3. Seed `ServiceFeatureContext` from explicit base and authored environment. `lando` seeds its default feature stack; `l337` seeds only artifact/build plumbing. Retain the projected endpoint contributions, without replaying declarations.
4. Apply `ServiceFeature`s in ascending priority.
5. After every service draft is complete, apply activated `AppFeature`s in ascending app-feature priority.
6. Emit provider-neutral `ServicePlan`s.
7. Finalize once in core with capability validation, bind realization, file-sync generation, storage shadows, routes, networking, excludes, and `AppPlan` decoding.

Features MUST emit provider-neutral intent. Both `ServiceFeatureDefinition` and `AppFeatureDefinition` MAY supply typed `declareEndpoints` callbacks; these are the only feature-owned listener authority. Neither `ServiceFeatureContext` nor `AppFeatureServiceMutators` exposes `addEndpoint`. Both expose `setInit(boolean)` so a feature can contribute native container init intent (§6.2.1); a composed authored `init` value still wins over any contribution, and conflicting contributions follow the ordinary write-conflict rules. This replaces the unreleased apply-time endpoint API without a compatibility path. Declaration callbacks MUST be deterministic and MUST NOT mutate their input, read `ports:` or `expose:`, publish host ports, or rely on contribution order for primary selection. A type marks its primary listener `primary: true`. The single §6.6 normalizer owns publications and explicit endpoint overrides. The app-plan cache input MUST include base, ordered `FeatureRef`s, and `AppFeature` contributions.

Declaration receives read-only resolved identity and configuration facts, including the original schema-decoded feature configuration. It MUST NOT depend on earlier `apply` mutations or planner-materialized certificate, security, or SSH configuration. Core shares base-default expansion, configured-ref handling, config decoding, and stable priority ordering with composition; an explicit feature ref replaces the same-id base default, and equal-priority entries retain their effective input order. Missing callbacks contribute no endpoints. Declaration Effects require no runtime services and fail through the feature's typed error channel. They MUST NOT acquire a runtime, inspect images, issue certificates, write caches, or perform general feature application. Lint MUST NOT replay `apply` to discover endpoints: application and its planner preparation may realize resources that authoring validation must not acquire.

Core MUST prepare feature definitions and occurrence order once per resolution, retaining each occurrence rather than collapsing equal ids into a map. Effective validation, declaration and application consume those prepared decisions. Original feature configuration is decoded once when validation or declaration requires it; application-only configuration MUST NOT be decoded before planner preparation. Application reuses a decoded original when applicable, but explicitly materialized certificate, security, or SSH configuration is decoded as a replacement even when empty. Materialized application configuration MUST NOT rerun Original validation or grant Original service-field claims. Private prepared values are invocation-local, not global caches or serialized plan fields.

`ServiceFeatureDefinition.validateEffective` is an optional deterministic, provider-free validation callback over `ServiceEndpointContext`: immutable final inherited normalized service facts and Original schema-decoded feature configuration, without draft mutators or required runtime services. Success returns schema-derived `ServiceFeatureValidationResult`, whose `handledServiceFields` initially admits only `webroot` and `consolePort`. Expected findings use the single `ServiceFeatureError.issues` channel, not a second successful findings channel. Each prepared occurrence validates once before declaration and before cache lookup, including when authored endpoints replace discovery. A failed occurrence does not declare endpoints; independent occurrences and services continue far enough to aggregate their findings. Core MUST NOT invoke `apply`, inspect images, perform network/filesystem actions, acquire provider resources or decode unrelated application-only configuration to validate.

An explicitly authored `webroot` or `consolePort` MUST be handled by at least one successfully validated final feature occurrence. A property name or value inside `FeatureRef.config`, a normalized-config field or an arbitrary endpoint does not grant support. Core aggregates explicit claims after inheritance, excluding occurrences whose configuration is substituted by planner preparation, and checks them before cache-key construction and lookup. Unsupported explicit input fails with `LandofileValidationError`, an issue at the authored service field and actionable remediation. When effective validation already failed for a service, core MUST NOT add derivative unsupported-field noise. A feature claiming `webroot` MUST actually consume the effective root for server configuration or supported context; the claim does not prove HTTP serving. Conditional mount-dependent context MUST NOT grant support without its required mount, while a genuine active webserver can handle an absolute root without an app mount. No type/provider blacklist or legacy config-key convention remains.

Every type MUST name `l337` or `lando`, return `ServiceTypeResolution`, and satisfy `runServiceCompositionContract`. `lando` receives `lando.env`; `l337` receives no injected environment or scaffolding. Only `lando.env` may invoke `buildLandoEnv`.

Contributed `logSources` MUST have unique ids and compatible strategies; file sources require absolute paths, while console aliases forbid paths. The id `console` is reserved for the implicit native source. `redirect` requires an owned build; a BYO/`l337` service may contribute file `follow` sources or pathless `console` aliases. Feature ordering and inheritance are replay-stable.

`ServiceType` declares `name`, optional `versions`, explicit `base`, optional `extends`, optional `artifacts`, `schema`, and Effectful `resolve` with `ServiceTypeError`. A type that contributes database clients may also expose pure `toolingForConnection(name, connection)`, returning their task definitions from a `ServiceName` and `DatabaseConnection`. `ServiceTypeError` and `ServiceFeatureError` MAY carry structured `issues` with paths relative to that service's config; the planner prefixes each path with `services.<name>`, preserving suggestions, source attribution and remediation. When `issues` is absent or empty, the failure applies to the whole service. Feature-config schema paths MUST NOT be presented as authored service fields unless a validator supplies that semantic mapping. Core MUST NOT reconstruct machine paths or suggestions by parsing prose. `ServiceTypeResolution` carries `base`, `normalizedConfig`, `features`, optional `connection` or `nonSqlCreds` (mutually exclusive), optional `tooling`, optional `connectionClientNames`, optional `logSources`, optional `sync` (`defaultDataset` per dataset kind and `postApply` tasks, §10.12.2), and optional `metadata`.

#### 6.11.1 Service-type inheritance (`extends:`)

A type MAY extend one parent, inheriting normalized config, features, tooling, artifacts, and `sync` before child overlay. Normalized config and tooling overlay under §7.2. Feature and log-source lists merge by `id` with child precedence, and same-id feature config overlays under §7.2; an empty child list contributes nothing rather than clearing inherited entries. Inheritance has no diamonds, is bounded, and rejects cycles with `ServiceTypeCollisionError`.

Canonical credentials also survive inheritance. An omitted child credential source inherits the parent's `connection` or `nonSqlCreds`; an explicit child source replaces the parent's source as a whole, never combining both. Each raw resolution rejects simultaneous sources before a later child can conceal the invalid contribution. The nearest explicitly declared `toolingForConnection` replaces the inherited function as a whole, including an empty factory. Existing task-content merging remains unchanged.

`connectionClientNames` carries explicit generated-client provenance, not credentials or a task snapshot. A raw contribution that omits it may seed names from its own declared factory; an explicit array, including `[]`, suppresses that automatic seeding. Without an own factory, untouched parent claims survive, but any child contribution for a task name revokes that name even if its content is identical. Explicit child claims may reauthorize it through the effective factory. An own factory establishes a new claim baseline from its explicit names or its returned names present in merged tooling. Claims are deduplicated deterministically and require a corresponding task, effective connection, and supporting factory output. Direct resolutions and inheritance hops use the same normalization; composed results always carry an explicit array so planner consumers cannot recreate revoked authority by inspecting an inherited factory.

`sync.defaultDataset` and `sync.postApply` MUST merge per dataset kind. An omitted child kind inherits its parent value; a child default Dataset id replaces that kind's parent id. A child `postApply` list replaces that kind's entire inherited list in declaration order, and an explicit empty list clears it; lists MUST NOT concatenate. The final merged defaults participate in §10.12 binding selection, while an explicit binding Dataset still wins. The final task lists run under §10.12.2 grouping and ordering, never once for each ancestor.

#### 6.11.2 Declarative version pinning (`artifacts:`)

`artifacts:` maps exact versions to artifact tags and MAY reference a sibling file. Version ranges are not supported. The `ServiceType` version metadata is the single matrix for planning, docs, and tests. Unknown, absent, or unavailable versions fail before provider action with supported-version remediation and MUST NOT fall back to guessed tags. Resolved tags enter the app-plan cache key.

#### 6.11.3 Service-type-shipped tooling

`ServiceTypeResolution.tooling` merges below resolved Landofile `tooling:`. Conflicts replace whole tasks by name. Between service contributions, the lexicographically first service name wins. A surviving contribution defaults its target to its contributor; `toolingDefaults` fills only unset fields.

For generated connection clients, private tooling metadata records the winning task's contributing service, not another credential or task snapshot. Invocation regenerates the factory-owned defaults from ownership-matched applied connection facts, preserving current unrelated defaults and their parsed expression sites. A current authored whole-task replacement bypasses this generated-client path. Both top-level tooling and event `task:` calls obey the same rule; neither imports applied lifecycle events or old authored tooling. Missing historical connection facts or an incompatible applied client family fail with `PlanReplanRequiredError`, not desired-credential fallback.

The applied service's `serviceTypeId`, not its normalized `type` or the current desired declaration, selects the composed factory. The loaded declaration's ID must match exactly. Missing or unavailable applied declaration identity fails with `PlanReplanRequiredError`; observation and teardown remain supported. Only normal application records new applied identity, not plan-cache refresh or inference from task winners. This identity survives service-record persistence and partial application but does not change physical container-create fingerprints.

Reserved tooling names `run`, `scratch`, and `scratch:*` produce `landofile.tooling` issues in lint and planning; planning aggregates them in one `LandofileValidationError` (§7.8). Service types MUST NOT use `topLevelAlias` while the unsupported tooling-task key list (`UNSUPPORTED_TOOLING_TASK_KEYS` in `@lando/landofile`) rejects it (§8.5).

#### 6.11.4 App-scoped features (`AppFeature`)

`AppFeatureDefinition` declares `id`, optional `schema`, `priority`, optional `AppFeatureActivation` as `activatedBy`, optional `AppFeatureSelectors` as `selectors`, optional `declareEndpoints`, optional `requires.providerCapabilities`, optional `requires.globalServices`, and Effectful `apply`. `declareEndpoints` receives `AppEndpointDeclarationContext` and returns an Effect of a read-only record from selected service names to endpoint arrays, with `AppFeatureError` and no required runtime services. Returning an unselected name is a typed selector error; omitting a selected name contributes nothing to it. Activation can match service type or feature; selectors can match `types`, `framework`, `hasFeature`, `names`, or `fromConfig`. A `fromConfig` selector reads one environment snapshot shared by declaration and application, and the environment variables it reads are part of the `app-plan` cache key, so changing one invalidates the cached selection.

Activation and selection inspect immutable resolved service facts, not mutable draft results, raw authored config, or finalized plans. The facts include service identity, base, framework, primary status, the complete declared feature-id set, normalized configuration, and optional connection facts. Declaration and application MUST use the same activation and selector implementation: trigger type and feature conditions intersect, selector clauses union, and selected names are deduplicated in service order. An absent activation match is a no-op; an activated feature selecting nothing fails with a typed selector error. `AppEndpointDeclarationContext` exposes selected read-only views without mutators. `AppFeatureContext` provides replay-safe non-endpoint plan mutators across those same services. App declarations follow service declarations; app application still follows all service application, and app features order only against each other. Application cycles fail with `AppFeatureCycleError`; `AppFeatureError` tags are `SelectorMatchedNothing`, `MutationConflict`, and `CycleDetected`.

Activation and selection decisions MUST be captured once against the resolved facts and selector-environment snapshot, then carried into application rather than recomputed. Application cannot silently drop a selected service whose draft is absent. Inactive and non-declaring app-feature configuration remains undecoded until application needs it. A plan-cache hit still performs shared preparation and declaration validation, but MUST NOT apply features or decode application-only configuration. Cache inputs retain relevant original declaration configuration separately from materialized application configuration; definitions, Effects, and prepared records are not serialized as cache inputs.

`AppFeatureServiceView.resolutionMetadata` is the optional read-only projection of `ServiceTypeResolution.metadata`, using the existing service provenance record value type. Preparation, endpoint declaration, and application MUST carry the same service-type-produced facts. These facts are not authored `x-*` fields, provider state, mutable draft extensions, or the final artifact after feature application. The engine MUST preserve plugin-owned keys without interpreting their private semantics. Consumers MUST validate required facts rather than reconstructing lost ownership from normalized config or a later artifact reference.

Plugins register `serviceFeatures:`, `appFeatures:`, and `serviceTypes:`; all three MUST exist in `PluginManifest` and be consumed by loading and planning.

Activated `requires.globalServices` are ensured during `pre-start` before user-app build. Missing services fail with `GlobalServiceMissingError` and installation remediation (§20.6.3).

`ServiceFeatureDefinition` declares `id`, optional `schema`, `priority`, optional required `ProviderCapabilities`, optional `validateEffective`, optional `declareEndpoints`, and Effectful `apply` with `ServiceFeatureError`. Validation and declaration receive `ServiceEndpointContext`; validation returns `ServiceFeatureValidationResult`, and declaration returns a read-only endpoint array. Both Effects have `ServiceFeatureError` and no required runtime services. Their context contains service name/type/base/primary, app name/root, optional host and connection facts, normalized configuration, and the original decoded feature config, with no draft mutators. `apply` mutates only its `ServiceFeatureContext` through non-endpoint mutators; features run low priority first, MUST be idempotent, declare conflicts or return typed planning errors, and emit provider-neutral changes.

**Default launchers run as the planned user.** A type's default `command` (installed when the author declares neither `command` nor `entrypoint`) runs as `ServicePlan.user`. Provider-specific Compose overrides MUST NOT substitute for a provider-neutral ownership contract. Any remaining privilege requirements, including restricted low ports on the target runtime, MUST be documented for the affected type.

**Listen port follows `port:`.** For typed services, the planned primary listen port is `ServiceConfig.port`, or the type's published default when omitted. Bundled launchers MUST configure that listener, and Lando-owned clients (healthchecks, tooling tasks, database commands, and wired consumers such as phpMyAdmin) MUST use the same port. Supported daemon-native variables for that primary listener MUST be derived from the planned port and projected into the service environment; malformed or unequal authored values MUST fail planning before provider action with an issue at that variable (`services.<name>.environment.<VAR>`). Lando MUST NOT rewrite an authored `command` or `entrypoint` to add listener flags; its author MUST configure the planned port. For MySQL, MariaDB, PostgreSQL, and MongoDB, a Lando-owned launcher loading `config.server` MUST pin the planned port on its command line, including the default. For Apache, the planned port determines `Listen <port>` and, for `php` via `apache`, `<VirtualHost *:<port>>`; a non-default port MUST replace the image's `Listen 80`, not add a listener alongside it. MySQL, SQL Server, and RabbitMQ MUST reject primary-port collisions with their reserved secondary listeners before provider action, with an issue at `services.<name>.port`. RabbitMQ MUST also reject an invalid distribution port or one colliding with AMQP or a reserved secondary listener, identifying `services.<name>.environment.RABBITMQ_DIST_PORT` when it is authored and `services.<name>.port` when the distribution port is derived. Fixed secondary ports MUST be documented as limits in the type's guide. Each type contributes that listener with `primary: true` so selection and reporting identify it without relying on list order (§6.6); a type whose primary is not HTTP (Mailpit's SMTP) marks it primary and contributes its HTTP UI as an unmarked secondary. The primary listener survives `ports:`: publishing it, publishing other ports, or authoring `ports: []` keeps it in the plan with its marking; only an explicit `endpoints:` list removes it (§6.6). Raw `compose` passthrough, the Tomcat custom-image/build exception below, and PHP's custom-image/build exception (§6.12.5) retain author-owned daemon configuration.

**MinIO artifact and secondary listener.** MinIO is a bring-your-own-image service: after inheritance, the effective configuration MUST provide a nonblank compatible `image` or an authored Compose `build`. A Lando build-script alone is not a base artifact. Missing artifact intent fails effective validation at `services.<name>.image`, with remediation naming both choices and without registry/provider access. There is no implicit registry image, mirror fallback or automatic source build, and the type MUST NOT claim identity metadata for an image it does not supply. The generated launcher requires a shell, filesystem utilities, `minio`, writable `/data`, and `mc`; the image author owns those compatibility and maintenance facts. An authored Compose build supplies its artifact through the existing build owner, without a placeholder image from the MinIO feature.

`MinIOServiceConfig.consolePort` is an optional `PortNumber` (integer 1..65535), defaulting to `9001`; `port` defaults to the primary S3 API listener at `9000`. The MinIO effective validator explicitly claims `consolePort` after validating the composed listener configuration. Inherited service types retain executable feature configuration and MUST NOT be rejected by a hardcoded type name or a parent's superseded default. Every Lando-owned launcher and the unmarked HTTP endpoint named `console` use the effective console port; the API remains primary, and a route selects the console through `endpoint: console`. API readiness and the `mc` alias use the API port. Equal effective API/console ports fail before provider action with a structured issue at `services.<name>.port` and actionable remediation. Moving the console permits reuse of its former port by the API. Authored process fields remain untouched. The API declares scan default `/minio/health/live` and the console `/`; a normal unauthenticated S3 root403 MUST NOT be globally reclassified as a successful response.

**Mail service secondary listeners.** Mailpit's HTTP UI/API listener defaults to `8025` and follows literal `MP_UI_BIND_ADDR`. MailHog's UI/API bind addresses default to `0.0.0.0:8025` and follow `MH_UI_BIND_ADDR`/`MH_API_BIND_ADDR` independently. Typed mail services advertise app-network listeners, so native SMTP/UI/API binds MUST use `:port`, `0.0.0.0:port`, or `[::]:port`, with integer ports1..65535. Loopback, named and container-specific hosts, invalid syntax and nonliteral values fail effective validation at their environment field, with wildcard-bind or explicitly managed Compose remediation. Accepted strings are preserved exactly; no native bind creates a host publication. Endpoint replacement cannot bypass this reachability contract.

SMTP bind ports MUST equal the effective primary `port`; mismatches identify `MP_SMTP_BIND_ADDR` or `MH_SMTP_BIND_ADDR`. SMTP MUST NOT collide with effective HTTP listeners; reject at `services.<name>.port`, not by reserving a default after HTTP moves. Cross-field checks run against final inherited configuration before cache lookup and provider action, not a parent's intermediate defaults. MailHog shares one HTTP listener only when UI/API bind strings are identical; different strings on one HTTP port fail with identical-string/distinct-port remediation. Distinct ports contribute named `ui`/`api` HTTP endpoints and use ordinary ambiguous-route rules (§6.6). Lando MUST NOT invent a browser-facing `MH_API_HOST`. Generated HTTP scan paths must exist on the listener being scanned: a split UI-only listener is not assumed to serve the API. Bind settings, endpoints, routes and owned clients agree without rewriting authored process fields.

**Tomcat configuration ownership.** Catalog Tomcat references pair an immutable multi-platform image digest with the reviewed Apache configuration for that exact release (§17.2). For a catalog-owned image, the service feature MUST bake `server.xml` with the planned HTTP port during the image build, including the omitted-port default of `8080`, without a startup-time rewrite. The endpoint and healthcheck MUST use that same port. The separate ROOT context uses the resolved `webroot`; authored `command` and `entrypoint` remain unchanged. An authored image reference equal to the selected exact catalog reference retains this ownership. A custom image or authored `build.context` is the explicit exception to the listener rule above: its author owns the daemon configuration, and Lando writes neither `server.xml` nor a ROOT context. `port:` still declares its endpoint and healthcheck target, which the author's configuration must match.

**SQL Server default database.** On a bundled catalog image, including an authored `image` equal to that catalog image, the service-owned startup launcher MUST create the resolved `creds.database` idempotently before readiness and MUST NOT drop an existing database. Actual creation MUST be reported in the service logs after it succeeds; startup reuse MUST NOT claim another creation. An authored custom image, `build`, `command`, or `entrypoint` stays untouched and MUST NOT receive that launcher. The healthcheck MUST stay read-only and MUST NOT create the database. `db:export` does not perform this initialization (§10.7).

**`webroot` is relative to the app mount.** `php`, `nginx`, `apache`, `static`, and `tomcat` resolve `webroot` against the effective app mount target, which defaults to `/app` and follows `appMount.target`; `webroot` defaults to `.`, the app root itself. Authors normally write a relative path such as `web` or `public`. An absolute container path is accepted for a document root outside the usual layout. A relative path that leaves the app mount, or a path with characters other than letters, digits, `.`, `_`, `-`, and `/`, MUST fail during planning. With `appMount: false` there is nothing to resolve against: a relative or omitted `webroot` MUST fail during planning, and an absolute one names content the image provides. Generated document-root configuration uses the resolved absolute path; `LANDO_WEBROOT` exposes it only when `appMount` is not `false`. When the app mount is enabled, `php` and `nginx` default their working directory to that path; `apache`, `static`, and `tomcat` default to the app mount target; an authored working directory wins. On a standalone `apache` service an authored `APACHE_DOCUMENT_ROOT` overrides the generated document root. Configuration views such as `app:config` keep the authored spelling rather than the resolved path. Lando 3 translation MUST preserve the served content root where representable, rewrite `webroot` when the Lando 3 layout semantics differ, and diagnose deployment behavior that needs manual configuration (§7.4.1).

**nginx serves its webroot.** Unless the author declares `command` or `entrypoint`, `nginx` generates its own server configuration. Without `backend`, it serves static files from `webroot`; with `backend`, it passes PHP requests to that service's PHP-FPM listener. Either way it listens on `port` and serves Lando's shared 403/404 pages for server-generated errors.

#### 6.12.2 Framework presets

Language types may expose `framework:` presets as ordinary overridable config. A preset's implicit default webroot is relative to the app mount and is omitted when `appMount` is `false`; this MUST NOT silently discard an explicitly authored root. Ruby supplies root context only (`rails` defaults to `public`, `none` to `.`), with authored-over-preset precedence. Its built-in context requires an active mount, so an explicit relative or absolute root with `appMount: false` MUST fail unless another composed feature declares support. Genuine webservers may still use an absolute root without the app mount and without `LANDO_WEBROOT`. Python and Go have no built-in webroot declaration. Framework selection does not start an application server: Ruby, Python, and Go keep their keep-alive command unless the author supplies `command`, and preserve authored `entrypoint`. Unused language command hints are not part of preset config or extensions. Recipes materialize the framework settings they need as concrete service config and tooling. Published ids are `drupal`, `wordpress`, `laravel`, `symfony`, `magento`, `django`, `fastapi`, `flask`, `rails`, `sinatra`, `echo`, `fiber`, and `none`.

Canonical PHP does not interpret framework ids. It uses `webroot` (§6.12.1) and `allowOverride` (default false); recipes own framework choices. Invalid paths fail during planning.

#### 6.12.3 Catalog membership rules

Catalog membership is frozen by this specification; additions or removals require a spec amendment. Version additions MAY ship in a minor release only through the single metadata matrix with available artifacts and matching docs/tests. Canonical collisions fail with `ServiceTypeCollisionError`. Plugins MAY add types and composable features. Library consumers receive the catalog only through bundled discovery (§16.4).

#### 6.12.4 The `creds:` schema

`ServiceCreds` contains literal `user` and `database` plus `password` and optional `rootPassword` as `EnvironmentValue` (§7.3.1). `mariadb`, `mysql`, `postgres`, `mongodb`, `mssql`, and opted-in plugin types share this contract.

A database type resolves its connection exactly once and returns it through `ServiceTypeResolution` as `DatabaseConnection { family, creds, port }`; the planner persists it on `ServicePlan.connection` and exposes it read-only to service and app features. Defaults fill only missing facts. Effective `creds` and any authored native alias (`POSTGRES_PASSWORD`, `MYSQL_ROOT_PASSWORD`, `MONGO_INITDB_ROOT_PASSWORD`, `SA_PASSWORD`, and siblings) MUST agree, and aliases MUST agree with each other, compared as descriptors, never as decrypted values; a conflict fails planning naming both paths without values. After feature composition the planner checks that type-owned projections still agree with the connection.

Initialization environment, `LANDO_DB_*` metadata, generated client environment (`PGPASSWORD` and equivalents), SQL operations, `ServiceInfo.creds`, and the `services.<name>.creds.*` and `services.<name>.port` expression scopes derive from the connection facts. Consumers MUST NOT rescrape the plan environment or apply SQL-specific credential defaults. Projections are typed and deliberate: a bound password stays a `SecretRef`/`BoundText` through every native key, metadata variable, client environment, and URL template, and bundled URL templates use the connection `port` with explicit `url.encodeComponent()` on the password. MongoDB dump/restore pass credentials through a bounded anonymous-fd config, and MSSQL clients read the password from projected environment; no bundled tooling places a secret in argv.

**MongoDB probes.** The `mongodb` type targets its declared primary TCP listener for both probes through `connectionFor(ctx)`. Ongoing health is a Bash TCP dial only, on the existing cadence, and MUST NOT launch `mongosh` or create shell state. Startup readiness performs that dial first, so no client launches while only the image's loopback initialization daemon exists, then a bounded credential-free protocol ping (`mongosh --quiet --norc`, direct connection, bounded server-selection, connect, and socket timeouts) with `HOME` set to a disposable owner-only temporary directory removed on exit. It MUST NOT mutate the container's `HOME`, write under the data volume, add a wire-protocol client, or deploy a helper binary. The generated `mongosh` task distinguishes an authentication rejection from the server with Mongo-owned recovery wording that names restoring the matching credentials or changing the user through an authorized administrator and states that data is retained; any other non-zero script is not classified as an authentication failure, and deleting data is never the prescribed default repair.

**MySQL and MariaDB client environment.** Default server initialization MUST NOT receive the application password through the client-only `MYSQL_PWD` variable: doing so can authenticate the image's first root setup with the wrong password. Generated clients retain their per-invocation `MYSQL_PWD` projection from canonical connection facts. Default admin probes scope `MYSQL_PWD` to the client process using the applied `MYSQL_PASSWORD`; passwords MUST NOT be embedded in probe argv. Native initialization variables and `LANDO_DB_*` metadata remain derived from the same connection fact.

A non-SQL type may publish `nonSqlCreds: ServiceCreds` instead of `connection`. Redis derives it from the same resolved `password` used for its initialization and client environments. Fresh service scopes and scopes reconstructed from serialized plans expose these credentials unchanged; they do not infer them from environment or generic normalized configuration. SQL-family services continue publishing only `connection`, with no competing credential copy.

`ServiceInfo.creds` is the string-only `ServiceCredsDisplay`, redacted without any store read. Structured output redacts password fields by default; a type MAY mark additional fields secret. Free-text output follows §3.7, which prints published default credentials, and a literal password or root password equal to its own credential's user or database name, as-is; a value resolved from a reference or explicitly registered stays masked regardless. Clients of an existing database use the applied connection fact and resolve references afresh per operation; Lando does not reconcile a changed store value against a running database or rotate credentials.

#### 6.12.5 PHP service depth

`via` is `apache` by default, `fpm`, or `cli`. Modes select compatible artifacts and reject incompatible keys at planning. FPM exposes its service endpoint for a sibling web server; CLI has no implicit HTTP server.

`composer` accepts a version, `false`, or `{ version, packages }`; all forms remain supported. Versions and packages are validated, checksum-pinned, deterministically ordered, and included in `buildKey`.

`xdebug` accepts `false`, `true`, or modes. Enabled Xdebug contributes `lando xdebug on|off|status`, sets the managed client host to `debugger.lando.internal` (not `host.lando.internal`), and relies on global `debugger.host` (§7.5, §10.1) for the alias target; environment variables alone MUST NOT be documented as enabling it, and `environment.XDEBUG_CONFIG` MUST NOT be documented as the WSL-to-Windows fix.

`db_client` accepts `auto`, `false`, or an explicit family/version. Auto detection uses resolved database services without provider probing and participates in `buildKey`.

**PHP runtime ownership.** A custom image or a Compose replacement build (normalized `build.context`, including shorthand and defaulted contexts) makes the PHP runtime author-owned in every `via` mode, even when planning supplies the type's catalog Apache image reference. Without a replacement build, that catalog reference retains stock ownership; additive `build.artifact` and `build.app` scripts do not transfer ownership. An author-owned runtime MUST NOT receive PHP-managed prerequisite, Composer-binary, WP-CLI, Xdebug-extension, or database-client installers, nor a PHP-generated launcher or Apache configuration-preparation step. Explicit `composer.packages` steps and enabled Xdebug configuration/tooling remain; the author supplies their required binaries/extensions. This does not remove ordinary `lando` base features. Authored process fields remain authoritative. For Apache and FPM, `port:` still declares the endpoint and probe target, which the author's daemon configuration MUST match; CLI gains no implicit listener.

PHP MUST compute one immutable, schema-backed runtime policy during service-type resolution, separating artifact source (`stock`, `image`, `context-build`), process authority (`lando`, `authored`, `image-default`), supported base-family evidence or unknown reason, optional selected reference, and log mode. The service feature receives that policy through its feature config; app features receive it through a private namespaced resolution-metadata entry (§6.11.4). Selected PHP consumers with missing or malformed policy MUST fail with `AppFeatureMutationConflictError`, not re-infer it. The private key is not public Landofile authoring vocabulary.

Canonical aliases of the catalog Apache reference retain stock ownership in all `via` modes; another registry or namespace does not. Replacement context takes precedence over that reference. Canonical upstream `docker.io/library/php` tags ending in `-bookworm` or `-bullseye` establish the respective family only without a replacement build; Dockerfile contents MUST NOT be inspected to manufacture family proof.

An authored `command` or `entrypoint` on a stock artifact changes process authority, not artifact ownership: stock installers and baseline INI remain, while generated launchers, Apache process preparation, and implicit console aliases are omitted. Custom images and replacement builds also omit implicit PHP aliases and file-log redirects. Container stdout/stderr and explicitly authored log sources remain available. Only Lando-generated Apache/FPM processes receive the aliases in §6.14.6; CLI receives none.

Stock PHP `www-data` retains its declared `/var/www` home and prepared-home ownership contract (§6.4). Default persistence MUST NOT require `home: false`; preparation occurs during the image build and a fresh named volume inherits it, while populated volumes retain their ownership. Custom runtimes may disable persistence or supply an explicit valid home path under the ordinary home contract. This policy does not alter the stock baseline INI or existing framework preset behavior.

**Mailpit sender proof.** Selecting a PHP sender requires a provable supported base family for the pinned msmtp installer. A replacement build MUST NOT derive that proof from `image:`, including a catalog reference: the build may replace the base. An unprovable selected sender MUST fail before wiring mutations with `MailpitMsmtpBaseFamilyError` (aggregated by planning); excluding it with `mailFrom` MUST avoid its installation and wiring. Exclusion does not waive other service validation.

The existing error tag MUST carry `service`, reason `replacement-build` or `unproven-image-family`, and optional `image`. Replacement-build diagnostics MUST explain that the Dockerfile controls the result and offer sender exclusion or a known image without a replacement build. Image-family diagnostics MUST offer canonical supported references or exclusion without irrelevant build advice. All selected senders MUST be validated before any wiring mutation; family policy is read once per selected sender and database-client auto detection is computed once when needed. Planning aggregation MUST retain actionable remediation rather than replace it with a generic feature-removal instruction.

### 6.13 Build orchestration

`BuildOrchestrator` executes one provider-neutral `BuildPlan`, streams lifecycle events, and preserves independent service concurrency.

#### 6.13.1 Phases

| Phase | Source and dispatch | Dependency | Default policy |
|---|---|---|---|
| `artifact` | Artifact intent to `buildArtifact` or `pullArtifact` | Independent across services | fail-fast |
| `app` | Runtime scripts to `execStream` | Own artifact, running service, and authored `depends_on` | continue-all |

The build scope publishes `pre-build`, `post-build`, `pre-build-phase`, `post-build-phase`, `build-step-start`, `build-step-progress`, `build-step-skip`, `build-step-complete`, and `build-step-fail` through `EventService`. Global, app, and service `build:` configuration resolves concurrency and failure policy; limits are bounded but tuning constants are implementation-owned.

#### 6.13.2 `BuildPlan`

`BuildPlan` contains an `AppRef`, typed `BuildStep`s, and per-phase caps. `BuildStep` contains `stepId`, phase, service, `buildKey`, `BuildCommand`, dependencies, failure policy, redaction tokens, and optional estimate.

Artifact intent creates one artifact step per service. App scripts create ordered steps. Each app step depends on its service artifact and running state plus authored cross-service conditions. Artifact builds never inherit service `depends_on`. Independent siblings may run concurrently. Cycles fail with `BuildPlanCycleError`.

Ready predecessors are `complete` or `skip`. Interrupts propagate to in-flight provider work and publish `build-step-fail`; `service-running` is the synthetic running-state predecessor.

#### 6.13.3 Provider dispatch

Full artifacts use `RuntimeProvider.buildArtifact`; pull-only artifacts use `RuntimeProvider.pullArtifact`; app scripts use `RuntimeProvider.execStream`. Every command retains its planned user, working directory, and environment. Providers MUST NOT re-resolve users at execution time.

`BuildOrchestrator.build` defaults `BuildOptions.refresh` to false and acquires referenced artifacts with policy `missing`: reuse a provider-local copy and contact the source only when absent. App, scratch, and global start and restart, including global auto-start, use the default. `app:rebuild` and `meta:global:rebuild` pass `{ refresh: true }` so providers that declare `artifactPull` refresh referenced artifacts with `always`. When a refresh fails, the orchestrator tries the provider-local copy with `never` and on success records command warning `LANDO_ARTIFACT_REFRESH_FAILED`, failing with the original refresh error only when no local copy exists. Interrupts and defects propagate without fallback. Provider policies remain strict. Acquisition policy does not change build-result reuse under §6.13.5.

#### 6.13.4 Failure policy

Artifact failure is fail-fast by default: it interrupts siblings, skips queued work as `phase-aborted`, and fails start. App failure continues independent siblings and raises one `BuildPhaseFailedError` containing `BuildStepFailure`s after `post-build-phase`. App and service overrides MAY change fail-fast behavior; per-step overrides are not exposed. For explicit global lifecycle operations, these failure policies apply within each dependency-connected service group (§20.6.5).

#### 6.13.5 `buildKey` and results

Every step uses a content-derived `buildKey`. A matching successful `build-results` cache entry emits `build-step-skip` with `up-to-date`; failures never suppress retries.

Both phases MUST hash ordered commands and resolved users, tools, versions, packages, config-source identities, and applicable provider/artifact/mount inputs deterministically with secrets redacted. Reordering or user changes MUST change the key; home contents, clocks, undeclared environment, bind contents, and resolved secret values MUST NOT. Forced rebuild commands bypass the result.

`BuildResult` records `buildKey`, service, phase, outcome, exit code, duration, optional artifact reference, transcript path, and completion time. Results are bounded and rotated.

#### 6.13.6 Transcripts

Each dispatched step writes `<userDataRoot>/builds/<app-id>/<phase>/<service>/<buildKey>.log`. `transcriptPath` appears on `BuildStepEvent` and `BuildStepResultEvent`; renderers and `lando logs <service> --build` use the same artifact. Transcripts stay local, are never telemetry, retain raw output while CLI/events apply redaction, and are removed by `lando destroy`.

#### 6.13.7 Cancellation

`Effect.interrupt` closes every step scope, terminates provider children, closes transcripts, and publishes interrupted failures within the §2.1 cancellation contract. Fail-fast uses the same path with reason `phase-aborted` and the originating failure.

#### 6.13.8 Errors

Build failures are tagged `BuildPlanCycleError`, `BuildStepFailedError`, `BuildPhaseFailedError`, and `BuildOrchestratorUnavailableError`. They carry the relevant app, phase, step/failures, transcript, and remediation context. Only `BuildOrchestrator` publishes the `Build` event scope.

### 6.14 Service log sources

`RuntimeProvider.logs` always exposes the implicit container stdout/stderr source. `LogSource` adds provider-neutral file sources and pathless aliases for a native console pipe.

#### 6.14.1 `LogSource`

`LogSource` is a discriminated union. Its file branch contains branded `LogSourceId`, optional label, absolute path, `stdout`/`stderr` classification, `redirect`/`follow` strategy, `required`, and timestamp capability. Each file source names one file; globs are not supported. Its native alias branch contains id, optional label, `stream`, and `strategy: console` only; `path`, `required`, and `timestamps` MUST be rejected. The id `console` remains reserved for the implicit source and is distinct from the strategy name.

Landofile `LogSourceInput` remains file-only: it requires `path` and optionally accepts `id`, `label`, `stream`, and `timestamps`, always resolving to `follow`. `strategy: console` is catalog descriptor vocabulary, not a new authored syntax. Service types may declare aliases or owned redirects. An explicit authored file id replaces a same-id catalog alias or file source.

#### 6.14.2 `LogChunk` source and line

`LogChunk` contains service, optional source, stream, line, and optional timestamp. Missing source means `console`; renderers label interleaved sources.

Each `LogChunk.line` is one complete line; line terminators, including a carriage return at either end, are not part of it. For the console source, providers MUST reassemble engine log messages per stream before emitting: a line written as several partial messages becomes one chunk carrying its first message's timestamp, engine timestamp prefixes on continuation messages are discarded, lines get the same complete UTF-8 framing and line bound as follow sources, and a trailing partial line is emitted only when the stream completes successfully, never on idle, failure, or interruption.

#### 6.14.3 Reification

`redirect` routes owned daemon log files to stdout/stderr during build and requires an owned image path, not `serviceLogSources`. A `console` alias describes existing native-pipe output and MUST NOT emit filesystem build steps or acquire a file reader. `follow` is implemented by `RuntimeProvider.logs`, never a core shell-out, and requires `serviceLogSources`. Providers that read container files through exec install the static in-container helper (§17.3) once per followed source, serve every read for that source from one helper session, and, when the follow ends or is interrupted, close that session and make one bounded attempt to remove the helper. Removal is best-effort when the container or exec transport is already gone. The helper does not depend on the image's libc.

Selecting an alias or redirect MUST select its native stdout/stderr pipe before daemon-side `tail`/`since`, defensively filter decoded chunks by that stream, and stamp the selected source id. This selects a pipe, not the original producer: aliases on a shared pipe return its shared output. Default logs MUST subscribe to native console once plus real file followers, never once per alias. `--source console` selects both native streams without file followers. Services lacking a requested id MUST be skipped rather than falling back to their console; an id unknown across the selected services fails with known-source remediation. These rules add no provider method or log-option field and preserve framing, redaction, and scoped cancellation.

Without that capability, required follow sources fail with `CapabilityError`; optional sources are explicitly reported unavailable and skipped. Sources are never silently dropped.

#### 6.14.4 Follow semantics

Providers declaring `serviceLogSources` MUST support finite snapshots and scoped follow mode, bounded pending diagnostics for missing files, rotation and truncation, complete UTF-8 line framing, bounded lines, per-source `tail`, timestamp-gated `since`, preserved per-source order, arrival-order merging, and interruption cleanup. No global chronological guarantee or global-total tail exists.

#### 6.14.5 Redaction

Providers return raw `LogChunk`s. Renderer, lifecycle, telemetry, and machine-output boundaries apply `RedactionService` exactly once. Library log streams and app-owned files remain raw.

A line cut by the line bound ends in the SDK truncation marker. Redaction masks any trailing prefix of a known secret value before that marker, so the bound never exposes part of a secret.

#### 6.14.6 Catalog defaults

Catalog types may use `redirect` for owned daemon files; MySQL/MariaDB optional slow/general logs use `follow`; framework file logs are declared by the recipe or type that knows their paths. Generated PHP Apache declares pathless `access`/stdout and `error`/stderr aliases. Generated PHP-FPM declares both `access` and `error` as stderr aliases and MUST describe the shared pipe, not producer isolation.

For stock PHP via Apache with neither authored `command` nor `entrypoint`, access logs MUST reach inherited stdout and error logs inherited stderr for both default and authored non-root users. The owned build MUST remove the stock default site and additive global access-log include; the launcher MUST supply global piped logging inherited by its generated virtual host, preserving stderr before Apache reassigns the logger's descriptors. It MUST NOT depend on reopening root-owned log paths or write Apache configuration at startup. Logging MUST preserve the existing omitted-port main-server shape, explicit-port virtual host, webroot, and `allowOverride` behavior. Custom images, replacement builds, and authored process overrides MUST NOT receive this PHP-specific preparation or launcher.

### 6.15 Lifecycle apply

`start`, bare `restart`, selected `restart`, and `rebuild` are different operations. Create-config drift is applied by ordinary start (§5.3.2). Rebuild is not that path.

**Early low-port warning.** Before start hooks and builds, the engine MUST record `LANDO_NONROOT_LOW_PORT_UNVERIFIED` once per service/unique planned container port below 1024 when a user is declared other than explicit root or UID 0. Missing users and ports at or above 1024 produce no warning. Named identities MUST use conditional wording because their resolved UID is not known. Context contains string-valued service, provider, user, port, and `policy: unknown`. Machine output retains the structured command warning without duplicate generic narration; human output narrates it. The warning MUST NOT probe runtime permissions, reject the plan, change ports, or infer effective permission from provider name or rootless mode. Remediation recommends a portable high container listen port or explicitly configuring and verifying bind permission; any future effective-bind fact belongs to a separate provider contract.

| Command | Contract |
|---|---|
| `start` | Plans and builds with the default cache policy (`refresh: false`, §6.13.3), then applies create-config drift. Keeps unchanged containers and named volumes; a recreated container's anonymous volumes go with it (§6.5). Has no confirmation flag. After a failed or interrupted attempt it converges: starts matching containers, recreates only drifted ones, resumes an unfinished accelerated-start journal, and reuses healthy workers and file-sync sessions. Init and lifecycle hooks run on every invocation; convergence is about resources, not exactly-once hooks. |
| bare `restart` | Stop, then start. Removes and recreates containers under existing stop semantics, so anonymous volumes do not survive it (§6.5). Not an in-place process restart. Uses the default cache policy. With an unfinished accelerated attempt, first resumes it under the same lock (§10.6.3). |
| `restart -s` / `--service` | In-place. No dependency closure. Refuses when the selected container is missing or would be recreated for published-port, bind-source, network, or create-config drift, or a missing `dev.lando.create-config` label. Create-config drift and a missing label fail with `ServiceRestartWouldRecreateError` reason `config`. Remediation is `lando rebuild -s <service>`. |
| `rebuild` | Forced pull (`refresh: true`), cache and app-build refresh, explicit recreate, and confirmation. A floating-tag refresh failure falls back to the local copy and records `LANDO_ARTIFACT_REFRESH_FAILED` (§6.13.3, §12.6). With an unfinished accelerated attempt, first resumes it under the same lock (§10.6.3). `rebuild -s` gives the rebuilt services the running app's host-proxy session and reuses healthy agent relays (§10.10.1, §10.4). |
| explicit `global:start` | Applies new environment, bind, and image configuration. `reconcile: false`. An explicit call is not warm-skipped. `global:rebuild` remains the forced refresh. |

An unchanged `build.app` command whose bind-mounted inputs alone changed retains its cached build result and skips the step (§6.13.5). `rebuild` forces that step to rerun. Changing command text, step user, or artifact inputs changes the build key, so ordinary start reruns the affected step.

Failure and interruption keep established resources at every phase (§6.7); no phase compensates by removing containers, networks, volumes, routes, workers, or sessions, and only acquisition-local cleanup runs (§10.4, §10.6.1, §10.10.2). Full restart and rebuild keep their explicit stop phase but MUST NOT remove routes when the following start fails; selected restart stays in place. Restart and rebuild, full or selected, that find an unfinished accelerated-start journal run the start path first under the app mutation lock, which performs the pending-aware preflight, the transaction check, the init events, and the resumed attempt; the restart or rebuild then continues without running init events again, and a failed resume fails the command (§10.6.3).

Only acquisition-local cleanup runs after failure: an acquisition that was never published and cannot safely be reused (for example a worker without a validated handshake or ownership record, or an incomplete temporary artifact) is finalized. Completed build artifacts stay; temporary files and build children finalize. Containers, including created-but-not-started containers, networks, volumes with creation receipts, the anonymous volumes of retained containers, valid file-sync sessions, and recorded host-proxy, SSH, and GPG workers stay in place for every error tag. Creation alone MUST NOT count as readiness. Published route configuration stays, including the previous routes when a replacement fails. Shared networks MUST NOT be deleted as compensation. Established SSH/GPG forwarding remains enabled until stop/destroy.

**Failure reporting.** The primary error tag, remediation, and role-annotated additional failures are unchanged, and the machine envelope gains no fields. Human output of `lando start`, `lando restart`, and `lando rebuild` adds exactly one warning after the primary error:

> Start did not complete. Resources were left in place. Running: …; created/stopped: …; unverified: …. Agent forwarding/file sync remain active where established. Inspect `lando info` and `lando logs`; fix the reported error, then run `lando start`. Run `lando stop` to shut down or `lando destroy` to remove resources; named volumes require `--volumes`.

The inventory uses a one-second best-effort observation budget; anything unobserved is reported as unverified/unknown, never as stopped. A failure before any app resource mutation says `No app resources changed.` instead of the inventory. Machine output (`json`, `yaml`) omits the warning; agents use `lando info`. Pre-events and actual service-start events still publish on a failed attempt; `post-app-start` / `post-start` publishes only after the readiness barrier succeeds.
