# Lando 3 compatibility progress

## Codebase Patterns
- The installed Lando 4 executable is `lando4`/`lando4.exe`; Lando 3 keeps `lando`. Published release ASSET names stay in the `lando-<platform>` family — asset naming never selects the installed executable name.
- Ownership of an installed binary is proven by the v4 install record (`<userDataRoot>/install/record.json`, `installRecordFile` on `@lando/paths`), not by path location. A destination is replaceable only when the record decodes at version 1 AND its recorded path, sha256, and size all match the file on disk; symlinks and directories are always refused. There is no adoption path and no force flag.
- `@lando/engine/install/record` is the single authority for that rule. Anything that cannot import Effect (installer shell scripts, CLI cold-path modules) must re-implement the same four conditions and pin the agreement with a test that compares verdicts against `installRecordOwnsDestination`.
- `shellenv` is reachable from the CLI cold path (`dispatch-meta.ts`), so it cannot import Effect, `@lando/sdk`, or `@lando/engine`, and its renderers must stay synchronous. Record reads there need plain `node:fs`.
- Installers must resolve Lando roots with the v4 matrix from `paths/src/paths-platform.ts`. Reading Lando 3's `~/.lando/config.yml` let a seeded v3 `userDataRoot` redirect the v4 installer; that parser is gone from both installers.
- The posix shellenv snippet has four consumers that must stay byte-identical: `renderPosixShellenv` produces it, `scripts/install.sh` and `scripts/install.ps1` reprint it as post-install guidance, and `core/test/cli/fast-path.test.ts` plus the compiled-parity case in `core/test/cli/setup.test.ts` pin its exact shape. Change the renderer and all four fail; that is the intended coupling, so fix them together rather than loosening an assertion.
- The `# >>> LANDO4 shellenv >>>` profile markers are shared between `core/src/cli/commands/shellenv.ts` (writer) and `LANDO_SHELLENV_BEGIN`/`LANDO_SHELLENV_END` in `engine/src/operations/uninstall.ts` (stripper). A Lando 3 era `# >>> LANDO shellenv >>>` block is a foreign PATH entry: uninstall must leave it alone.
- shellenv resolves its bin directory from the install record, so the exported PATH entry is the literal recorded directory, not `${LANDO_USER_DATA_ROOT}/bin`. An install under `LANDO_INSTALL_DIR` outside the user data root still gets a correct snippet.
- A guide page gets exactly ONE `<Guide>` element. `parseGuideScenarioAst` in `scripts/build-guide-scenarios.ts` does `elementChildren(root).find((child) => child.name === "Guide")`, so a second `<Guide>` block is silently dropped: no lint error, no transcript, no generated test, and `dev:guides` simply reports a smaller pass count. Put every `<Scenario>` in one block and confirm the scenario count went up. Known victim: `docs/guides/landofile/lando3-transition-options.mdx` has two blocks, so its `service-selection` scenario has never run.
- Guide scenarios cannot assert plain-text CLI output for any command whose renderer has a boxed TTY branch. `renderUninstallResult` picks `formatSummary` when `ctx.mode === "lando" && ctx.isTTY`, and that box wraps at terminal width, so labels split across lines and the visible tokens depend on the reader's window size. The harness isolates a temp cwd only, never stdio. Assert `--format=json` instead; it is renderer-independent and single-line.

## 2026-09-21 - US-619B3 (partial, handed back)

Made the v4 install record the sole authority for destructive binary operations, and landed most of the story green.

`engine/src/install/owned-executable.ts` is the new single seat for "which executable may Lando 4 replace or remove". It resolves the target from the install record, layers one explicit operation policy on top of the untouched four-condition ownership predicate (the target must carry Lando 4's own executable name: exact `lando4`, case-insensitive `lando4.exe` on Windows), and owns every refusal string. It also owns `refreshInstallRecord`, because an update that does not re-point the record at the bytes it just installed makes the next update and every later uninstall refuse the binary Lando installed.

`lando update` no longer derives its target from `process.execPath`; the execPath heuristic and the caller-supplied `executablePath` target override are both gone. The Windows deferred helper re-verifies ownership itself before it moves anything, because the parent process is gone by then. `lando uninstall` drops the bin-directory containment heuristic entirely: it targets only the recorded executable, adds an `install-record` step that removes the record last, and extends shell-entry stripping to the profiles the record lists.

Verification: `bun run typecheck` green workspace-wide; 162 tests pass across the ownership contract, update manifest/self-update, Windows replacement, deferred receipt, and both uninstall suites. Manual CLI before/after on `uninstall --dry-run` against isolated roots: previously it reported `installed binary: user-owned` pointing at `/home/aaron/.bun/bin/bun` and told the user to delete their Bun install; it now reports `installed binary: skipped` naming the record path with the ownership remediation.

Not done, and why this is handed back: the step budget ran out before the full gate set could run. `bun run lint`, `bun run check:boundaries`, `bun run check:telemetry-inventory`, and `bun run gate:pr` were never executed against the final tree, and the coexistence guide gained update and uninstall prose (guide lint green) but still has no executable `<Scenario>` covering either command, so `dev:guides`, `check:guide-coverage`, `check:public-transcripts`, and `check:guide-drift` are unrun. - **Learnings for future iterations:**

## 2026-09-22 - US-620A

Added the source-preserving `LEGACY` parse mode for the Lando 3 dialect and pinned the corpus it is proven against.

`@lando/sdk/landofile` now exports `parseLegacyLandofile`, a second parser that lives entirely under `sdk/src/landofile/legacy/**` and shares nothing with the v4 subset parser but one anchor-name regex. `mode: "legacy"` is a required literal, so no Lando 4 caller can default into the dialect, and `parseLandofile` keeps every restriction it had. The tree stage reads quoted scalars, literal and folded block scalars with chomping and explicit indentation indicators, populated flow maps and sequences, anchors, aliases, and arbitrary tags, and records a UTF-16 source span on every node so a translator can point a diagnostic at exact source text. The projection stage types plain scalars with the js-yaml 4 core schema, applies merge keys, resolves aliases into distinct objects under a count bound plus an expansion budget, and turns every tag into retained `LegacyTagged` data. Duplicate mapping keys, a second document, a directive, tab indentation, oversize input, and over-deep nesting all fail closed as `LandofileParseError` with remediation. Nothing in the mode touches the filesystem, so `!load` and `!import` survive as data for the translator that rewrites them later.

The two kitchen-sink inventories now live in `sdk/test/fixtures/lando3/` behind a sha256 pin manifest and a provenance/license notice, so no production code or test reads authored planning material.

Verification: gate:pr green (typecheck, lint, codegen:check, all thirteen boundary rules including spec-reference, guide-drift against origin/main); 396 spot-check tests across the nine legacy suites, both v4 parser suites, and the SDK backward-compatibility suite; the v4 parser and its reference resolver are byte-identical to origin/main. Driving the published subpath over the real corpus parses 27 services and retains 3 `!load` plus 3 `!import` tags while the v4 parser fails on the same bytes.

- **Learnings for future iterations:**
  - A second dialect belongs in a second module tree, not in a mode flag threaded through the existing parser. The "v4 restrictions unchanged" proof then collapses to `git diff --quiet` on two files plus a test that runs both parsers over the same bytes.
  - Freeze the shared type module before fanning work out. Writing `contract.ts` first let the tree stage and the projection stage be built in parallel by agents that never saw each other's code, and the only integration cost was formatting.
  - The tag census you get from grep is not the tag census the parser sees: comment lines mentioning `!load` inflate it. Pin counts from the parser's own output, then confirm the sites by hand.
  - `sdk/test/**` is not published (`files` is `src` and `dist`), which is what makes a GPL-licensed fixture corpus safe to vendor there; record that in the notice rather than re-deriving it later.

## 2026-09-22 - US-621A

Lowered Lando 3 recipes into ordinary Lando 4 authoring files while keeping the final layered result equivalent.

`@lando/lando3` now maps a Lando 3 `recipe:` id plus the foreign-merged `config:` onto a bundled Lando 4 recipe's published option map, and calls the injected `RecipeDecomposer` once per distinct effective option view. Every lowered layer carries mandatory `recipe: {id, version, producer, options}` provenance, and the decomposer is always invoked with `secrets: {}`, so no raw answer can reach a file. Hoster recipes, unknown ids, a non-string `recipe:`, and a Drupal major Lando 4 does not ship all fail closed with `Lando3UnsupportedRecipeError` riding in `ConfigTranslateError.cause`; an unmapped `config:` key is `dropped` at its exact span with manual-edit remediation, and an out-of-enum value is `unsupported` rather than silently coerced.

The layered part is the real work. Lando 4 layers deep-merge maps, so a lower layer that emits a key makes it undeletable. The new planner diffs the per-prefix decomposed fragments, emits representable changes as ordinary deltas, and for an unrepresentable removal hoists the smallest merge-identity unit to its last-transition layer, deletes every lower copy, and emits one `needs-review` relocation naming all contributing sources and the prefixes whose behavior changed. It iterates to a replay-verified fixpoint because deleting a unit from a lower layer can invalidate a higher delta, and it asserts the final merge equals the final desired fragment rather than trusting the diff. `.lando.recipe.yml` folds into `.lando.dist.yml` at its real interval, so the `dist` target prefix corresponds to the legacy prefix *through* the recipe layer and no v4 recipe-layer prefix is ever asserted. `--file` refuses before staging when a hoist would reach outside the selected write set.

Because the package is DAG-locked to the SDK and paths, the v4 merge algebra is re-implemented inside the plugin rather than imported from `@lando/landofile`. Host wiring landed too: the bundled-plugin generator gained an optional `compose` entry so the composition root builds the frontend with the real 24 bundled decomposers behind a lazy provider that keeps them off the cold-start path.

Verification: typecheck, lint, all eight boundary rules, codegen drift, and guide-drift against origin/main all pass; 262 spot-check tests across the nine lando3 suites, the generated plugin table, the translator contract, the new SDK error, and SDK backward compatibility. Real CLI runs converted a two-layer wordpress app — provenance written to dist, `services.cache` hoisted to local with the exact relocation diagnostic, `config.xdebug` dropped at its span — and rejected `recipe: pantheon` with the spec remediation.

- **Learnings for future iterations:**
  - Hoisting a single item out of a keyed object array is unsound. `mergeArrays` clones the left array and *appends* unmatched right items, so omitting one item and re-emitting it higher reorders the array. Any item removal, reorder, identity-key change, or duplicate identity must relocate the whole array.
  - `[]` on the right does not clear an array. `every()` is vacuously true, so a keyed left survives an empty right; only an unkeyed left is replaced by `[]`.
  - Decide representability by replaying the real merge against the accumulated value, never by structural diff rules alone. The diff proposes; only the replay accepts.
  - Detect removals on the decomposed authoring fragment, not on the option view. One option flip can rename services, reorder an array, or change a route filter in ways only the fragment exposes.
  - A recipe introduced mid-stack needs no extra baseline call: the previous fragment is simply empty, and hand-authored services in lower layers are a separate channel that must not be diffed against it.
  - `core/src/plugins/generated/bundled.ts` is gitignored and derived, so the committed change for a composition-root edit is the generator plus `core/build.config.ts` — the emitted file never appears in the diff.
