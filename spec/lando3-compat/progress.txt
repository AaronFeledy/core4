# Lando 3 compatibility progress

## Codebase Patterns
- The installed Lando 4 executable is `lando4`/`lando4.exe`; Lando 3 keeps `lando`. Published release ASSET names stay in the `lando-<platform>` family — asset naming never selects the installed executable name.
- Ownership of an installed binary is proven by the v4 install record (`<userDataRoot>/install/record.json`, `installRecordFile` on `@lando/paths`), not by path location. A destination is replaceable only when the record decodes at version 1 AND its recorded path, sha256, and size all match the file on disk; symlinks and directories are always refused. There is no adoption path and no force flag.
- `@lando/engine/install/record` is the single authority for that rule. Anything that cannot import Effect (installer shell scripts, CLI cold-path modules) must re-implement the same four conditions and pin the agreement with a test that compares verdicts against `installRecordOwnsDestination`.
- `shellenv` is reachable from the CLI cold path (`dispatch-meta.ts`), so it cannot import Effect, `@lando/sdk`, or `@lando/engine`, and its renderers must stay synchronous. Record reads there need plain `node:fs`.
- Installers must resolve Lando roots with the v4 matrix from `paths/src/paths-platform.ts`. Reading Lando 3's `~/.lando/config.yml` let a seeded v3 `userDataRoot` redirect the v4 installer; that parser is gone from both installers.
- The posix shellenv snippet has four consumers that must stay byte-identical: `renderPosixShellenv` produces it, `scripts/install.sh` and `scripts/install.ps1` reprint it as post-install guidance, and `core/test/cli/fast-path.test.ts` plus the compiled-parity case in `core/test/cli/setup.test.ts` pin its exact shape. Change the renderer and all four fail; that is the intended coupling, so fix them together rather than loosening an assertion.
- The `# >>> LANDO4 shellenv >>>` profile markers are shared between `core/src/cli/commands/shellenv.ts` (writer) and `LANDO_SHELLENV_BEGIN`/`LANDO_SHELLENV_END` in `engine/src/operations/uninstall.ts` (stripper). A Lando 3 era `# >>> LANDO shellenv >>>` block is a foreign PATH entry: uninstall must leave it alone.
- shellenv resolves its bin directory from the install record, so the exported PATH entry is the literal recorded directory, not `${LANDO_USER_DATA_ROOT}/bin`. An install under `LANDO_INSTALL_DIR` outside the user data root still gets a correct snippet.

- **Learnings for future iterations:**
  - Two agents sharing one user-visible string (the installer prints the shellenv snippet verbatim) is a false-independent partition. Either the installer stops reproducing that text or one agent owns both sides.
  - `bun install` will not rewrite the workspace `bin` name in `bun.lock` from a `package.json` edit alone; the stale `.bin` symlink survives. Do not reach for `bun update` to force it — it bumps unrelated dependency ranges.
  - Three install-posix tests asserted that `~/.lando/config.yml` IS parsed for `userDataRoot`. They were inverted into coexistence assertions deliberately; that inversion is the intended behavior change, not a regression.
  - Deferred on purpose: renaming the dev/CI compiled artifact `core/dist/lando` and the `ci-platforms.ts` `binaryName` values. No acceptance criterion binds them — the criteria bind the npm bin, the installed executable, and retained release asset names — and touching them churns seven workflow generators plus their committed YAML.

## 2026-09-21 - US-619B1

Finished the Lando 4 identity story that the previous pass handed back.

`lando4 shellenv` now resolves its bin directory from the v4 install record and fails closed with a tagged `InstallRecordError` plus remediation when the record is corrupt, versioned forward, or no longer matches the executable on disk; with no record at all it falls back to the default bin directory. Both installers stopped hand-rolling a drifted copy of that snippet and now reprint the renderer output byte for byte, derived from the directory they actually installed into. Renaming the profile markers to `LANDO4` had left uninstall stripping the old `LANDO` marker, which after the rename is a Lando 3 shaped block: uninstall now removes only the v4 block and leaves a legacy block untouched. The engine record module is exported as `@lando/engine/install/record` so the subpath mirrors its file path.

Verification: gate:pr green (typecheck, lint, codegen:check, boundaries, guide-drift); lint:guides, check:guide-coverage, check:public-transcripts green; 297 spot-check tests across shellenv, both installers, uninstall (core and engine), fast-path, package-bin, scenario-context, install record, package seam, and paths, plus the 73-test setup suite including compiled/source parity, and the from-lando-3 guide. Manual CLI runs of `lando4 shellenv` covered record-backed resolution outside the user data root, digest drift, a symlinked executable, a corrupt record, and the `--format=json` failure envelope.

- **Learnings for future iterations:**
  - A user-visible string reproduced by more than one surface is not a partition boundary. The installer guidance, the fast-path canary, and the compiled-parity assertion all encode the shellenv snippet; a renderer change is a four-file change.
  - Renaming a shared marker is only half the work. Grep the stripper as well as the writer, or uninstall silently starts deleting the foreign block it was meant to protect.
  - `engine/test/package-seam.test.ts` requires the export key to mirror the source path exactly, so a nested module cannot take a flattened subpath.
  - Guide `expect={{ ... }}` props cannot contain a single quote; the parser rewrites every `'` to `"` before JSON parsing, and the failure surfaces as an unhelpful `JSON Parse error`.
