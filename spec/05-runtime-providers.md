# Lando v4: Runtime Provider API

> **Part 5 of 20** · [Index](./README.md)
> **Read next:** [06 Services](./06-services.md)

A `RuntimeProvider` turns a provider-neutral `AppPlan` into running service instances. The Lando-managed runtime is the default; system Docker and system Podman are bundled opt-in providers.

---

## 5. Runtime Provider API

### 5.1 Concept and terminology

| Term | Meaning |
|---|---|
| **Runtime provider** | Plugin implementing `RuntimeProvider`; this replaces the v3 “engine” concept. |
| **App plan** | Schema-validated, provider-neutral desired state for one app. |
| **Service instance** | Running or startable realization of one `ServicePlan`. |
| **Artifact** | Provider-specific runnable asset, such as an image, VM template, disk, or deployment manifest. |
| **Endpoint** | Service listener identified by protocol and port or socket. |
| **Route** | Host-facing HTTP/TLS mapping to a planned backend endpoint. |

### 5.2 Design principles

1. **Core never shells out to provider binaries.** Every provider operation goes through `RuntimeProvider`.
2. **Core never makes provider-native files the source of truth.** Providers MAY emit native files from a plan.
3. **Provider selection is explicit and cached.** App or global configuration overrides the bundled `lando` default; host-only commands and host tooling require no provider unless they operate on runtime resources. The CLI/default host-provider policy resolves setup's scoped override, then `LANDO_PROVIDER`, then config `defaultProviderId`, then `lando`. Embedding hosts follow §16.5: host configuration MAY outrank or exclude environment input. An app's Landofile provider MUST NOT change the host provider. Planner and registry MUST share the applicable override-aware resolution. Plan cache identity MUST include the host provider.
4. **Capabilities are validated before planning completes and before provider action.** Missing required behavior fails with a typed capability error.
5. **Provider-specific configuration is namespaced** under `providers.<id>`.
6. **Escape hatches are non-portable.** Supported Compose input remains shared input; provider extensions do not become portable semantics.
7. **Providers MAY use containers, VMs, remote execution, or hybrids.** The contract therefore uses `artifact` and `instance` terminology.
8. **The default provider owns its private runtime lifecycle.** It MUST use Lando-controlled binaries, configuration, storage, sockets, and machines and MUST NOT consume system Docker or Podman state.

### 5.3 The `RuntimeProvider` service

`RuntimeProvider` is an Effect service. Scoped methods MUST acquire external resources in `Scope`; interruption MUST reach the underlying operation and finalizers MUST reap owned resources.

Provider apply retains container creation, resource ownership, service-start/dependency graph scheduling, and partial-apply persistence. The engine supplies an invocation-scoped `ApplyOptions.executeReadinessAttempt` delegate for both service and host checks, bound to the actual plan, cancellation signal, and selected provider exec. Providers MUST invoke that delegate rather than choosing an independent attempt executor. Direct apply without it MAY execute service readiness, but MUST reject host readiness before resource mutation. The delegate transfers attempt execution only, not scheduling or ownership. Full engine scheduling remains deferred pending provider-neutral per-service lifecycle primitives and a reviewed partial-apply/cancellation contract (§6.7).

Only a provider with `ensureReady` may report `idle`; an unreadable or ambiguous observation is not evidence of absence. It MUST NOT launch or repair a runtime. `exec` MUST be a collector over `execStream`, not a second execution path. `execStream`, foreground `run`, data transfers, and other live operations are scope-bound. `logs` MUST always support the implicit console source when `serviceLogs` is declared; following declared file sources additionally requires `serviceLogSources` and follows §6.14.

Every Lando-created service container (user, global, scratch, and Compose-typed services, including selected rebuilds) MUST receive a creation-time read-only bind of the host's container-helper directory at `/run/lando/helper`. The mount participates in create-config identity (§5.3.2), so ordinary `lando start` recreates older containers missing it. Its source is the stable architecture directory, above content-addressed helper versions, and its target MUST remain stable across helper upgrades: publishing a new digest makes it visible to running containers without recreation. The resolved executable MUST be mode `0755` and accessible to non-root container users. Host-specific delivery paths MUST NOT become portable authored intent. Ephemeral data-plane helper containers are exempt.

Ordinary non-TTY `exec` and `execStream` MUST use exactly one engine exec on the warm path: the mounted helper's `exec-run --nonce <128-bit-random-hex> [--umask M] -- <argv>`, with stdin, stdout, and stderr attached and `Tty: false`. The helper MUST start the child in its own process group, become a child subreaper, and inherit stdout/stderr descriptors directly without proxying payload bytes. Exec stdin carries a bounded framed control protocol: `DATA(bytes)` forwards child stdin, `EOF` closes child stdin, and `SIGNAL(INT|TERM)` requests cancellation. Omitted stdin MUST send `EOF` immediately; logical `EOF` MUST leave the control channel open. Normal completion MUST use the child's real exit code, stop consuming control, and leave intentionally backgrounded descendants running without waiting for them. Launch failure MUST emit `lando: <prog>: command not found` and exit 127 for ENOENT, or `lando: <prog>: cannot execute` and exit 126 for EACCES/ENOEXEC.

On `SIGNAL`, the helper MUST forward the requested signal to the owned descendant tree, including descendants escaping with `setsid`, allow a bounded grace, escalate to SIGKILL, reap/join the tree, and exit `128 + signal`. Raw control-channel EOF before cancellation or normal child completion means host death or disconnect and MUST trigger the same termination and join. Providers MUST NOT interpret a daemon-namespace exec PID as a container-namespace signal target or signal unrelated processes. The host MUST send the signal frame and await the exec's own completion within one cleanup budget of at most six seconds, including helper grace and escalation. If writing fails or the budget expires, it MUST close the connection to trigger raw EOF and finally inspect the exec; an exec still observed running MUST produce a tagged cleanup failure with its cleanup role (§8.11.1). Cancellation remains Effect interruption and MUST NOT become a successful cancellation receipt. Existing provider failures retain their tags and remediation (§5.7).

If a SIGNAL write cannot complete within 250 ms, or the attach otherwise fails to join, the host MUST run at most one same-user control exec, `helper exec-signal --nonce <hex> INT|TERM`, within that same cleanup budget. It MUST match the exact helper path, `exec-run` role, and nonce in container-namespace `/proc` cmdline, require the same uid unless root, and signal only that pinned supervisor process, which performs its normal graceful forwarding, escalation, and join. No writable filesystem is required. A distinct not-found status is successful only after inspecting the payload exec as exited; a successful signal also requires bounded confirmation of payload completion.

The warm supervised path MUST use the same engine request set and count as plain exec (create, start, and completion inspection); it MUST NOT install helpers per invocation, create sessions, renew leases, or launch watch/control execs. The nonce-addressed control exec is reserved for the failed cancellation path above. Mount availability MUST be checked from existing container inspection or create-config evidence without another warm-path round trip. A missing mount MUST fail closed before payload launch with `ServiceExecError` and remediation to run `lando start`; unsupervised fallback is forbidden. The same inspection decides whether the target can run a command: a container that is absent, was created and never started, or has exited MUST fail before payload launch with `ServiceExecError` whose message says the service is not running, whose `details.containerState` names the observed state, and whose remediation is to run `lando start`.

TTY commands use the native terminal transport. `CommandSpec.raw: true` identifies internal operations that bypass both umask wrapping and process supervision, including readiness/healthcheck and umask probes, listener observation, and SSH/GPG agent preparation. Callers MUST NOT set it for user payloads or infer it from argv. These exemptions do not remove scoped transport cleanup. The managed Windows stdin path has the known supervision limitation in §5.8.1.

`ApplyOptions.onVolumeCreated` is an optional effectful callback receiving the same verified `VolumeCreationFact` reported in `ApplyResult.createdVolumes`. Providers MUST await it for each volume immediately after verified creation and before starting any service container. A callback failure MUST fail apply before service startup. Existing or adopted volumes MUST NOT trigger the callback; ownership labels alone are not creation evidence. Receipts already persisted survive a later apply failure, and the volumes they describe are retained with them.

#### 5.3.1 Teardown resolution and orphaned resources

All app kinds use one placement rule. Desired placement is the selected provider; realized placement comes from installed providers' applied plans matching the exact canonical root and app kind. Scratch plans carry `SCRATCH_EXTENSION_KEY` and MUST also match the scratch app id; user and global targets MUST exclude scratch plans. Kind/root matching is distinct from selecting a user app's current id: a user-app launch partitions matching same-root plans into the current app id and superseded ids. Same-provider superseded realizations follow the §7.4 rename rule. Claims on a different provider require explicit provider resolution and MUST NOT migrate automatically. Placement, applied-plan evidence, teardown evidence, orphan grouping where an applied plan disambiguates identity, and ownership cleanup MUST share the kind/root predicate. Colocated app kinds MUST NOT claim or remove each other's resources. Before start, rebuild, or restart mutates resources, a different realized provider MUST fail with `AppPlacementError` carrying `AppRef`, desired and realized provider ids, and working remediation commands. Observation and teardown MUST follow applied placement, not a changed default; legacy multiple same-provider user plans follow §7.4 read-only selection and teardown reconciliation, while different-provider claims remain ambiguous. Ownership inventories alone MUST NOT claim placement. `destroy --provider=<id> --yes` MUST restrict evidence and cleanup to that provider without reading another provider's inventory; multiple matching same-provider app names MUST reconcile during teardown as specified in §7.4. Plain destroy MUST retain named volumes. Every volume rule in this section is about named volumes: an anonymous volume shares its container's lifetime and is removed with it (§6.5).

A provider that reports `idle` (§5.3) runs no workload. `stop` against such a provider has no runtime work: it completes its host-side steps (routes, workers, sessions) without launching the runtime and reports `stopped` when the target has an applied plan, leaving stopped containers for the next start to reconcile. `destroy` needs a live runtime to inspect and remove containers and volumes. Its shared owner-preparation step invokes `ensureReady` when an owning provider reports `idle` or its status observation fails, including after a crash or an interrupted managed runtime. It then re-observes the provider and requires `running`; positive idle evidence is not a prerequisite to launching for destroy. A provider without `ensureReady` retains its original status failure. An `ensureReady` failure becomes the teardown failure. Observation and stop never invoke `ensureReady`; a failed status observation still fails stop.

`stop` and `destroy` callers resolve the app **root** from Landofile discovery, which succeeds on an invalid Landofile, and consult applied state and runtime evidence against that root before planning desired config:

1. No applied plan, no owned runtime resources, no nonempty cleanup inventory, and no unfinished accelerated-start journal at the root: the operation reports `outcome: "unchanged"`, takes no provider action, and exits successfully whatever the Landofile says. A nonempty inventory requires provider verification even when every recorded resource returns absent. The one exception is `destroy --purge`, which still removes the root's snapshots (§10.11.2), takes only the provider actions that removal needs, and reports `destroyed` when it removed any.
2. An applied plan exists: tear down from the applied plan. Landofile `events:` and `hostEvents` steps for that teardown come from the Landofile at the applied root at command time (§8.5.7); a Landofile that is missing, fails to load, or names another app or provider skips those steps with a notice. That tolerance is for hook sourcing only; the ownership and unfinished-accelerated-start checks below still fail closed.
3. No applied plan but owned runtime resources exist: tear them down as orphans of that root. Both operations remove orphan containers through `removeObservedService` by observed identity, never through provider state looked up by app id. When destroy's volume policy selects orphan volumes for removal, it uses `removeVolume` by observed identity. The desired plan is loaded only if teardown needs it; a desired-config failure at that point is reported as the tagged planner/landofile error.

Destroy plans before it executes. Identity, inventory, capability, journal, and file-sync checks are read-only and run before the `pre-destroy` bracket (§3.5); every mutation, and any validation that depends on quiescing retained writers, runs inside it. Owner preparation is infrastructure readiness, not an app mutation: destroy determines the full owner set from recorded evidence (applied plans, orphan groups, ownership inventory, unfinished journals, purged snapshots, superseded realizations, and the global app). One shared preparation step handles each distinct owner exactly once before any live read-only checks, including superseded file-sync inspection. Running owners require no admission; idle owners and owners with failed status observation are prepared and re-observed as described above. `destroy --root` and `apps:gc --prune` use the same preparation contract. Once prepared, live inventory is authoritative; an owner still idle at owned-resource cleanup remains a failure.

`stop` reports `stopped` or `unchanged`; `destroy` reports `destroyed` or `unchanged`. Every renderer and machine format MUST preserve that distinction. The operation result vocabulary is distinct from the provider's `DestroyOutcome` (`destroyed`, or `no-op` with reason `no-applied-plan`, §5.3): rule 1 returns `unchanged` without any provider call, an applied-plan teardown (rule 2) reports `destroyed`, and an orphan teardown (rule 3) derives its result from what it removed, `unchanged` when nothing was removed. A direct provider `no-op` MUST NOT be rendered as `destroyed`; it corresponds to `unchanged` unless the same operation removed other resources. Both operations stop and remove the selected containers, but `stop` retains the selected realization's applied plan and named volumes, while `destroy` clears applied state and follows its volume policy. The exception is `stop` against an `idle` provider: nothing is running, so it removes no containers and leaves container cleanup obligations pending for the next start or destroy. Legacy superseded realizations are retired under §7.4; when no recorded realization matches the current Landofile name, reconciliation MAY retire all recorded same-provider user realizations. An orphan teardown MUST report what it removed; a result that lists a service MUST mean that service was stopped and removed. Orphan volume removal under `destroy --volumes` MUST classify cache and data volumes exactly as planful bring-down does. A plain `destroy` leaves data stores, so rule 3 lets a later `destroy --volumes` remove them.

Selected global stop (§20.7) is the one teardown exception to rule 3: an otherwise valid selected orphan request (orphaned runtime resources or cleanup-only ownership hints, no applied plan) fails with `AppResolveError` before any mutation, because route ownership cannot be reconstructed without applied route definitions. Whole-global stop follows rule 3.

The orphan-teardown relaxation is scoped to teardown callers. `start` MUST reconcile resources retained from a failed attempt when their recorded ownership and observed identity validate against the desired plan (§6.7). Unknown or foreign resources MUST remain untouched and fail closed through the applicable app-resolution or provider-ownership error; convergence MUST NOT widen the shared evidence resolver's default or adopt resources without ownership proof. Whole-app user-app `start` also removes the service containers it owns for services its desired plan no longer names. Bare user-app `restart` and whole-app `rebuild` remove them in their halt, which destroys those containers before the following start, and each publishes the same notice for the services its halt removed. A halt observes before it acts only when the applied plan names a service the desired plan dropped. Candidates are this provider's observed containers that carry a native id, this app id, and the plan's canonical root, and name a service absent from the desired plan; role-labelled helpers are not service containers and keep their own cleanup owner. Every candidate is checked with the service-container ownership predicate below before anything is removed, and a candidate that fails it fails the start closed with nothing removed. Each owned candidate is removed through `removeObservedService` inside a `pre-service-stop`/`post-service-stop` pair, named volumes stay, and the complete desired plan is recorded. Removal stops at the first failure; a completed removal stays committed even when a later removal or the apply fails, and a retry rediscovers the rest from labels. One info notice names the services whose containers were removed and says their named volumes were kept. The whole-app result reports the removed names in `servicesRemoved`, present and possibly empty after the operation evaluated removals; a halt reports a service only when an observation taken before it proves the container existed, so a container that was already gone is never reported. Selected operations never sweep. The one exception is a selected `restart` or `rebuild` that first resumes an unfinished accelerated start: that resumed whole-app start removes what it finds and the operation reports those names in `servicesRemoved`, omitting the field when it removed nothing, while the selected phase itself still never sweeps. Global startup follows §20 and scratch startup §21.

The §10.11 `DataMover` uses native data-plane methods only when declared. Otherwise it MAY use the mount-aware ephemeral-run fallback; if `ephemeralMounts` is false and no native capability exists, planning or transfer fails with `CapabilityError`.

Before any provider `apply` mutates app containers, private networks, or volumes, the provider records the union of the previous successful attempt, prior failed attempts, and the attempt in progress. The record holds identities and digests only, plus the expected app, provider, root, and owner, and the actual physical name, including Lando Windows names. Shared networks are never owned. Applied plans are recorded on success only. `ResourceOwnership` (`appRoot`, `ownerKey`, `providerId`, `appIds`) is a summary hint. It is not physical existence, readiness, or seed evidence.

`RuntimeProviderContribution.resourceOwnership(ctx, root)` is a filesystem-only query and MUST NOT construct, initialize, or contact a runtime. It reads the provider-private `ctx.stateStore` `resource-ownership` namespace, keyed by canonical owner (§12.4.2). `RuntimeProviderRegistry.resourceOwnership(providerId, root)` is the optional per-provider form of the same query, with the same filesystem-only restriction.

`RuntimeProviderContribution.declaredCapabilities(platform, arch)` is optional. It returns the provider's capabilities for a host without IO and without constructing, initializing, or contacting a runtime, so it is a plain synchronous function rather than an Effect. `PluginRegistry.declaredProviderCapabilities(id, platform)` exposes it for offline config lint, which passes the resolved host platform (`PathsService.platform`), never a raw `process.platform`. A provider without it gets one lint warning that capability checks run at `lando start`.

`RuntimeProviderRegistry` MUST provide all three evidence members. Callers pass canonical roots; app-kind and identity matching follows the shared placement predicate above.

|---|---|---|

Ambiguous applied claims and mismatched attribution MUST fail with `AppResolveError`; provider inspection failures MUST propagate through `ProviderError`. The optional `app` selector MAY distinguish user realizations with distinct ids on one provider at the same root. It MUST NOT resolve conflicting provider claims or duplicate records with identical kind/id attribution. Missing registry members MUST NOT be replaced by empty or absent evidence.

Exact teardown queries every installed contribution's root inventory before any mutation, including an old applied app and a separate failed app. It validates ownership. An offline or corrupt nonempty hint fails with an actionable error and MUST NOT be treated as absent. Teardown evidence MAY be an applied plan, orphan observation plus ownership, or an ownership inventory alone (cleanup-only, no applied plan). Global teardown is the exception to the every-contribution inventory query: it consults only the realized global provider's inventory, or the host provider's when no applied global plan exists, through `RuntimeProviderRegistry.resourceOwnership`, and cleans up through that provider. It MUST NOT read or act on another provider's inventory.

Inventories are teardown evidence only, except that a successful apply retires the entries of app-owned authored networks it removes (§10.1). Non-teardown resolution (selected restart, applied-state resolution) serves a matching applied plan without reading any provider's inventory; it consults inventories only when no applied plan matches, and a nonempty hint then produces the existing orphan refusal (`AppResolveError`). Only teardown probes the availability and cleanup capability of inventory providers. The internal whole-app stop that restart and rebuild run does not perform ownership cleanup.

Whole-app `stop` and `destroy` combine verified cleanup outcomes. A network-only removal is not `unchanged`. An all-absent result stays `unchanged`. Verified absent or removed containers and private networks are retired from the inventory. Named volumes remain until the existing volume flags select them; a removed container's anonymous volumes go with it. Verification uses ownership labels, not trusted names, with one legacy exception for per-app bridges. Inventory cleanup applies the same service-container predicate as observed removal: a recorded container whose live labels contradict its recorded app, root, service, provider, owner, role, or scratch identity is refused rather than deleted. Observation projection applies the same predicate before a discovered container's app-root label may override a planned root, so an incoherent label set supplies no override.

| Observed resource | Teardown action |
|---|---|
| Service container with an observed native id whose app, canonical-root, and service labels equal its expected identity, whose provider, owner, and legacy `com.lando.app` labels are absent or agree with the acting provider, the root's owner key, and the app id, that carries no role label, and whose scratch markers are absent or `TRUE` with the app's own scratch id | Remove by observed native id. |
| Service container that lacks a required app, root, or service label, contradicts any label above, or carries a role label; or a planned-name or inventory inspection that returns no native id | Refuse that container with a tagged error naming it and the label (or missing id) that failed; it is never removed. No legacy exception. Teardown evidence collection refuses such a service observation that claims the target root before any mutation instead of treating it as absent. An observed service with no native id is `absent` and is not removed. Rows without a service label are not service observations; their own owner (for example stale data-helper cleanup) handles them. |
| Per-app bridge at the exact planned private network name with no labels at all | Legacy (created by an earlier build). Remove by observed native id during planful bring-down and ownership-inventory cleanup; a failed bring-up retains it like every other network. |
| Network with the expected ownership label set | Remove by observed native id. |
| Network with any nonempty label set that is not the expected ownership set (partial, another app, root, owner, or provider) | MUST refuse. |
| Shared network | Never removed. |

This inventory MUST NOT widen partial `provider.destroy`, selected rebuild, or global `-s`. Selected global orphan refusal (§20.7) is unchanged. Orphan lifecycle events are unchanged. A failed or interrupted start at any phase retains the selected realization's applied app, networks, routes, and volumes (§6.7); the ownership record is how the next start, stop, or destroy finds them. Explicit retirement of a superseded realization under §7.4 is a committed reconciliation step that a later launch failure does not undo; its named data volumes and ownership inventory remain. Removing the owned containers of services a whole-app user start no longer names (§5.3.1) is committed the same way. Neither path deletes named volumes unless the existing flags select them.

Prepared file-sync targets are not in this inventory. An unfinished accelerated-start journal (§10.6.3) is the ownership evidence for them: it names the attempt's provider, app, root, engine, target volumes, and sessions, and `prepareFileSyncTargets` re-verifies each target's ownership labels live before a resume touches it. The §12.4.2 manifest is consulted beside it only to reject a foreign provider or app; its absence is not a refusal. `stop` with an unfinished attempt runs the full plan stop from any phase (provider teardown that stops writers, then engine drain or session termination, then the owned cleanup above) and leaves the attempt unfinished for the next start. `destroy` disposes the attempt's sessions and targets from any phase, then clears the journal; a target with no session is disposed only when no app writer could have used it, so a post-apply-intent target with no matching session refuses until the session's synchronization history is restored in the engine and `lando start` finishes the attempt. Both fail closed when the journal's identity does not match the current app, provider, or engine; "from any phase" is subject to those ownership and data-preservation checks, not a guarantee in every resource state.

When the journal's app root no longer exists (`destroy --root`, `apps:gc --prune`), there is no project to sync back to and no Landofile to match, so the journal's own record is the evidence. The shared read-only inventory resolves each journal's recorded provider through the registry and reports whether its file-sync copies are removable, without launching a runtime. A provider declaring `fileSyncTargets: "prepared-volume"` cannot yet remove these copies through missing-root teardown. With recorded targets and `--volumes`, preflight MUST fail with `FileSyncStopError` before deleting anything, explain the limitation, and prescribe rerunning without `--volumes`. Without that flag, teardown removes everything else selected by its flags and keeps the copies and their ownership journal. For generic targets, teardown verifies the recorded provider, app, root, and engine, then terminates the recorded sessions the engine lists for that app (termination never deletes either endpoint). The sync targets may hold the only copy of the app's files, so they are data: without `--volumes` they and the journal that owns them stay, and the root keeps being reported; with `--volumes` each target whose ownership labels verify live is removed and the journal is removed after the last one. An unavailable engine, a mismatched identity, or a target that fails verification leaves the targets and the journal in place and fails that root with remediation.

Interrupted missing-root disposal retries automatically when a recorded target is already absent. A missing entry in the provider's projected volume inventory is not proof of native absence: a successful exact-name `locateVolume` observation must explicitly report `presence: absent`. The same observation runs again for every recorded target immediately before removal, because owned and orphan cleanup earlier in the teardown may already have deleted a listed target: a surviving listed target is removed only at its observed generation, and a target that was absent at preflight but present again keeps the journal and fails closed. A present target without matching ownership, an unknown presence observation, or any inventory or inspection failure keeps the journal and fails closed. Existing locator observations may omit `presence`; that omission never proves absence. No additional session coverage is required beyond a successful authoritative engine inventory and termination of its matching listed sessions: the deleted root cannot receive a synchronization flush, and `--volumes` explicitly discards the retained data.

#### 5.3.2 Create-config identity

Ordinary `start` and explicit `global:start` plan and build with the default cache policy (§6.13.3), then apply changed immutable container create configuration, keeping unchanged containers and named volumes; a recreated container's anonymous volumes are removed with it (§6.5). Bare `restart` stops and removes containers, then starts the app with the default cache policy (§6.15). `start` has no confirmation flag.

| Drift | Apply behavior |
|---|---|
| Image reference, digest, or build key, under the ordinary build flow | Recreate the affected container. |
| `command`, `entrypoint`, `init`, environment, `user`, working directory, mounts, storage, labels, preserved Compose knobs, or container `healthcheck` | Recreate the affected container. A change between absent and an explicit value, or between `true` and `false`, is drift; an unchanged value is not. |
| Missing opaque `dev.lando.create-config` label | One-time recreate. |
| A container with matching app, canonical app-root, and service labels, matching scratch markers, no role label, and no conflicting provider or owner label, under a name other than its planned container name (§10.1) | Ordinary apply and whole-app stop stop and remove it before creating anything, with its anonymous volumes; named volumes stay, and whole-app stop keeps its shutdown facts in the receipt. Selected restart never sweeps alternate names: it refuses as missing when the planned-name container is absent, and an alternate-named duplicate does not itself prevent restarting an existing planned-name container. Selected rebuild stops nothing for an absent container and converges the selected services. |
| Unchanged `${secret:...}` reference whose store value changed | Not a config-identity change. MUST NOT recreate for that reason alone. |
| Per-session credentials, allocations, and timestamps | Excluded from identity. |
| Host-proxy session (`dev.lando.host-proxy-session`) | Excluded from identity. A changed session recreates eligible services through the host-proxy session rule (§10.10.1), never as config drift, so selected restart is unaffected. |

The label value is `v4:` plus one SHA-256 digest of the desired create configuration, including the physical mount list (type, source or store, target, access, tmpfs options, and accelerated sync volume) but not role, exclude, or include metadata, including both authored artifact provenance and the realized artifact reference and digest, but not the realized ref's `origin` marker (§6.13.3), so marking a built image never recreates its container. It stores no raw values and no per-value hashes. The digest includes each bind's `sourceIdentity` when present, so a changed generated-certificate identity (§10.3) is create-config drift even when the source path is unchanged. Selected restart projects the current desired services onto ownership-matched applied artifacts before inspection and forbid-recreate apply, so an unchanged built service can restart without rebuilding or resolving creation secrets. Environment values enter the digest as their descriptors (§7.3.1): a literal string as its bytes, a `SecretRef` or `BoundText` as its reference identifiers, part order, and encodings, never as resolved SecretStore values. A literal `${secret:...}` string and a `SecretRef` to the same reference therefore have different identities. Literal env-file and YAML config, including a literal password, is desired configuration and is inside that single outer digest. The digest does not prevent dictionary inference and MUST NOT be described as proof that no secret was hashed.

Preserved runtime knobs enter create identity as canonical provider-neutral intent, independently of the engine dialect's request layout. This includes resource controls, GPU requests, and reserved device requests. Schema-declared inert `x-*` metadata MUST NOT enter create identity. `ServicePlan.pullPolicy` controls acquisition and is not itself container create configuration; changes to the acquired artifact remain subject to normal artifact identity.

Explicit `rebuild` requests artifact refresh subject to `ServicePlan.pullPolicy` and explicitly recreates containers (§6.15). It is not required to apply create-config drift.

A provider that realizes network names physically (the managed Windows machine) stamps the fingerprint computed from the physical plan. Its `inspect` presents the logical fingerprint only when the observed label exactly equals the physical expectation, so selected-restart preflight compares like with like. When physical and logical expectations differ, a physical mismatch withholds the fingerprint so it counts as config drift.

#### 5.3.3 Shutdown observations

Teardown reports what the daemon said about each container before removing it, never a verdict about how it stopped. `ServiceShutdownObservation` is an Effect Schema with inferred types: `appId`, `providerId`, `service`, optional exact `containerId` (the identity inspected, never a replacement found by name), optional `oomKilled` (the daemon's explicit OOM bit; omission means unknown, not `false`), and a discriminated `status`. `exited` carries an optional integer `exitCode`; a missing code is reported as unknown and is never read as `0`. `unknown` carries a `reason`: `container-absent`, `state-unavailable`, `not-exited`, or `inspect-failed`, and only `inspect-failed` carries a `diagnostic`, the canonical sanitized tagged-error JSON. The unknown arms reject an `exitCode`. A reported OOM bit is preserved even when the rest of the state is incomplete. No raw inspect body, environment, log bytes, native command, or unsanitized cause enters an observation.

Providers that observe do so on the exact owned container after a successful or already-stopped stop and before removal, within the existing operation timeout. A container that never started is not exit `0`. An inspection failure becomes `unknown` with reason `inspect-failed` and does not block an authorized removal; a stop or delete failure remains a failure with its original tag, cause, and remediation. `DestroyOutcome` and `ObservedServiceRemoval` carry `shutdownObservations` on success, and the engine forwards them unchanged onto `StopAppResult`, `DestroyAppResult`, observed orphan removal, and the selected global stop and destroy results, preserving `appId` attribution when service names repeat across apps. The field is optional at every layer: a provider without observation support omits it, and ownership-only cleanup that saw no container MUST NOT fabricate one.

There is no public graceful or forced boolean. Exit `137` alone does not prove a forced stop or an OOM kill, and exit `0` does not prove the application finished its own cleanup. Human output repeats the facts inline beside each service and raises a warning only for an explicit `oomKilled: true` or an inspection failure; machine output carries the schema-encoded observations.

Accelerated destroy MUST retain observations returned by `quiesceForFileSync` through synchronization flush, session and target disposal, and final provider cleanup into `DestroyAppResult`. This does not change the existing action order or failure channels. A later `container-absent` placeholder MUST NOT obscure earlier facts for the same app, provider, and service when its exact container id matches or is unavailable; observations for distinct exact container ids or different app/provider identities remain separate. Providers without observation support return an empty receipt rather than inventing facts.

#### 5.4.1 Agent-socket delivery (`agentSocket`, `openAgentSocketBridge`)

`openAgentSocketBridge(input)` takes `AgentSocketBridgeInput` (`appId`, `sessionId`, `kind: "ssh" | "gpg"`, an `upstream` that is a host Unix socket path or an authenticated host-loopback TCP endpoint, and `socketName`) and returns `AgentSocketBridgeResult`: either `bind-directory` naming a host directory the provider can bind, or `volume` naming a provider volume; in both cases the directory contains `socketName` once the bridge is live. The result is Scope-owned. Closing the scope tears down any guest listener, relay process, or volume and MUST reap them on interrupt. A failed or interrupted start MUST NOT close a bridge it has acquired and recorded; stop and destroy close it (§10.4). The provider MUST declare `agentSocket` only when its bridge works on the current host, so capability failure happens before planning rather than at apply.

| Host and provider | `delivery` | Realization |
|---|---|---|
| Linux native Podman or Docker Engine, including WSL rootless managed Podman | `bind-directory` | The app-owned relay directory is bind-mounted with `createHostPath: false`; the relay socket is created by the host worker and MUST be connectable by the actual non-root service user. |
| Podman machine on macOS and Windows, managed or user-owned | `guest-bridge` | The provider opens an SSH reverse forward into the machine using its machine SSH metadata, publishing a guest Unix socket in a machine-side directory that the machine bind-mounts into the service. The relay carries raw agent bytes and is separate from the §10.10 host-proxy protocol. Relay sockets are `0666` inside a per-user `0700` run directory. The Windows `guest-bridge` loopback TCP broker carries no token: other local accounts on that Windows host can reach it while the app runs, which is a documented trust-boundary limitation.

`bindMountPerformance: slow` permits acceleration through an eligible `FileSyncEngine` (§4.3). `appMount.accelerate: false`, global `defaultFileSyncEngine: passthrough`, or no eligible automatic candidate keeps ordinary binds; `native` never accelerates, though explicit engine choices still undergo host-policy validation; `none` rejects bind mounts. `sharedCrossAppNetwork` gates global-service contributions. Data-plane declarations select native behavior, documented generic fallback, or typed failure.

A provider MUST declare `fileSyncTargets: prepared-volume` only when its actual implementation supplies the required preparation and inspection lifecycle. The bundled `lando` provider declares it only on Windows when it manages the runtime, has applied-plan state, and has the API request hook needed to construct its preparation operations. An external socket MUST NOT gain this capability merely because the host is Windows. The acquired provider's capabilities and methods MUST agree before hooks, rotation, journaling, or target work. Capability, preparation, and ownership failures for a planned accelerated app fail with tagged errors and actionable remediation, never an ordinary-bind downgrade.

#### 5.5.2 Environment resolution and execution eligibility

`CurrentExecutableAppPlan` is `AppPlan` with `valueModel: 1` required. Before creating or recreating any container, a provider MUST decode the incoming plan as `CurrentExecutableAppPlan`; a plan without the marker fails with tagged `PlanReplanRequiredError` before any removal or resource allocation, regardless of what its strings look like. Observation, logs, stop, and teardown accept historical plans without the marker. Restart or reuse of an existing container never resolves creation values. A partial plan merge MUST NOT grant retained legacy services the incoming plan's marker. On successful apply, `recordedPlan ?? plan` is the incoming record; `ApplyOptions.recordedPlan` supplies it when it differs from the executed plan. With `ApplyOptions.complete: true` the incoming record is authoritative for the whole app and replaces the previous one; a complete record MUST NOT claim changes to services the operation did not apply. Otherwise the incoming record is merged with the previous one like any partial apply, whatever `reconcile` says; `reconcile` only forces recreation. A merge carries previous services absent from the incoming record, remaps each carried route reference to an equal route in the incoming route table and drops references with no equal route, and carries the previous stores those services mount unless the incoming record defines a store of the same name, and the previous file-sync sessions of those services and, when the incoming record defines a file-sync policy, their previous per-service entries in it. This keeps cleanup evidence for services whose containers are gone while the record stays self-consistent.

The applied-state envelope is version 6: the one-mount-list shape (§6.4) with canonical init intent, migrated hostname grammars, the exclusive SQLite target branch on `ServicePlan` (§10.7.1), and optional canonical `ServicePlan.pullPolicy`. Version 4 and version 5 records decode unchanged; absent historical pull policy remains absent rather than being inferred. Reading a version 1 envelope first migrates its `appMount`, `mounts`, `storage`, and Compose `tmpfs` knob into the one list. Both version 1 and version 2 records then migrate any `init` value under `extensions.compose`, in either persisted layout, into `ServicePlan.init`, including an explicit `false`, remove the extension entry, and keep the record's ownership identity. A malformed value makes the record unreadable without deleting it, and absence in a historical record stays unspecified rather than becoming `false`.

The version 3 to 4 step drops only `ServicePlan.hostAliases` entries whose string hostname fails `HostAliasName`; aliases take no part in ownership or teardown, and planning recomputes and validates them from the Landofile. Certificate CN and SANs pass through `certificateNameForHostname`: valid names stay, leftmost partial wildcards become the covering `*.` name, unmappable SANs are dropped, and SANs are deduplicated in order. An unmappable CN or a malformed alias or certificate field leaves the record unreadable, because replacing the CN would guess certificate identity and dropping the plan would discard certificate intent. All other fields, including ownership identity and v3 init intent, are unchanged; podman's aggregate layout migrates all members or none.

The tunnel registry uses envelope version 2. Version 1 allowed a `*.` prefix plus a 253-character suffix, beyond the 253-character `RouteHostname` limit. Migration drops each session whose string hostname no longer decodes, keeps every other session and field, and never invents a hostname; dropping is safe because sessions own no containers or volumes. Malformed entries and unknown versions fail instead of quarantining or emptying the registry.

A record that cannot be migrated without guessing, any undecodable record, and an aggregate record with any unconvertible member are unreadable. Every mutation (apply including reconcile, stop, restart, destroy, and teardown, even with a caller-supplied plan) reads applied state freshly and strictly and refuses unreadable state with `ProviderUnavailableError` naming the state file and the recovery: restore it, or move it aside and rerun destroy so ownership labels drive cleanup, accepting that unflushed accelerated changes may be lost. Protection is scoped: an unreadable per-app record protects only that app, and an unreadable aggregate record protects every app of that provider, so other apps, other providers, and commands run outside an app keep working. Observation reads tolerantly and reports unknown instead of failing; ownership-label and orphan cleanup skip and report the resources of protected apps rather than treating them as orphans. Historical plans whose environments are plain strings remain decodable as observed plans.

`ApplyOptions.resolveServiceEnvironment` is the only path from descriptors to bytes at the provider boundary. The engine's activation applier (§6.15) supplies it from a Scope-owned `EnvironmentValueResolver` session: each reference is read once per operation, every raw value, URI-encoded component, and secret-bearing composite is registered with the redactor before dispatch, and the resulting `Record<string, string>` reaches `CommandSpec.env` and container create requests only. Providers MUST call it only for a service they are about to create or recreate, before destructive replacement, and MUST NOT stringify or omit an unresolved descriptor. Resolved maps never enter applied state, caches, plans, or argv.

### 5.6 Provider extensions

Provider-specific intent MAY appear only under `providers.<id>`. Such intent is non-portable unless the extension defines a portable fallback, generated documentation and `lando config` MUST mark it non-portable, and the owning provider MUST validate it with Effect Schema and return `ProviderConfigError` on invalid input. Shared Compose keys are not provider extensions (§5.5.1).

### 5.7 Provider errors

| `_tag` | Failure |
|---|---|
| `ProviderUnavailableError` | Provider is unavailable on the host. |
| `ProviderCapabilityError` | Requested behavior is unsupported. |
| `ArtifactBuildError` | Artifact build failed. `BuildOrchestrator` adds the optional `service`, `transcriptPath`, and `outputTail` (§6.13.8). |
| `ServiceStartError` | Service lifecycle start failed. |
| `ServiceExecError` | Service command execution failed. |
| `ServiceNotFoundError` | Selected service does not exist. |
| `ProviderConfigError` | Provider extension configuration is invalid. |
| `ProviderInternalError` | Provider failed outside a more specific category. |
| `VolumeOperationError` | Volume locate, observe, adopt, coordinate, list, remove, snapshot, restore, or snapshot removal failed. |
| `ServiceCopyError` | Service file transfer failed. |
| `ArtifactTransferError` | Artifact export or import failed. |

Provider-owned errors MUST include `providerId`, `operation`, a user-facing `message`, a nonblank actionable `remediation`, redacted JSON `details` when present, and an optional original `cause`. `details`, and a capability error's `requiredValue` and `actualValue`, are typed as JSON values, so a non-JSON value fails at construction; values from untyped sources pass through a JSON-producing redaction first. A tagged `cause` is projected, redacted, into machine error output (§8.11); any other cause stays debug-only. Callers that return the provider error channel MUST pass an existing provider failure through with its own tag and remediation instead of relabeling it. A subsystem with its own published error channel (DataMover, URL scanner) MAY wrap the failure in its tagged error, but MUST keep it as `cause`, keep its remediation, and MUST NOT reclassify it as a different provider error; volume coordination, for example, reports `VolumeOperationError` only for an ownership conflict or a volume whose identity changed under it, and a runtime that cannot be reached stays `ProviderUnavailableError`. Volume observation keeps an unexpected HTTP status in the message without the response body and keeps a decode failure of volume metadata as `cause`. An unexpected HTTP status while creating, starting, waiting on, or inspecting an ephemeral `run` or `runStream` helper is `ProviderUnavailableError` with only `status` in `details`. Its message names the step and includes the engine's own reason, bounded and redacted in one pass with the live redaction profile plus every helper `env` value and the credentials inside URL-shaped values as authoritative tokens; when that redaction suppresses the reason, the message carries only the status. Helper credentials MUST travel in `env`, never argv. An invalid inspection or exit code is `ProviderInternalError` without the engine body or parser exception. A helper container Lando could not remove is reclaimed automatically: the first time a provider data plane starts a helper in a process, it removes this provider's helpers that are not running and finished more than 10 minutes ago, within a short deadline and without failing the user's operation, and volume removal that is blocked only by such helpers removes them and retries once. Cleanup remediation therefore never asks the user to remove a helper by hand. An ephemeral helper that exits nonzero and then cannot be removed fails with `ProviderInternalError` carrying `exitCode` and a bounded, redacted `stderrTail`, with the removal failure as a `cleanup` additional error. Lazy environment-resolution failures also travel through the provider error channel: `SecretStoreError` and `EnvironmentValueResolutionError` retain their own tagged shapes rather than being wrapped as provider outages. Messages and details MUST already be redacted with the owning runtime's live value set when an error is returned, so library callers see the same masking as CLI output.

The runtime provider registry MUST enforce redaction on failures from every Effect and Stream member, provider construction, and contribution callback, including applied-plan and resource-ownership reads. It MUST reconstruct canonical error classes with redacted `message`, deep-redacted `details`, `remediation`, and other exposed text fields while preserving tags, schema encoding, yieldability, and the original `cause`. Before canonical redaction, `details`, `requiredValue`, and `actualValue` pass through a bounded projection that never runs getters, `toJSON`, or proxy traps: it omits secret-bearing keys and undefined properties, replaces class instances, cycles, and over-limit values with `[redacted]`, and masks the whole field when its aggregate budget is exhausted or the redactor misbehaves. Every mapping preserves each failure reason and its annotations, so a cleanup failure merged into the cause stays visible. Shipped code maps failures with `mapFailures` and `mapStreamFailures` from `@lando/sdk/command-result`, never Effect's `mapError`, which keeps only the first failure (§8.11.1); `check:boundaries` enforces this, and a mapping that must hide a payload-bearing defect sanitizes it with `mapDefectCause` instead of dropping the reason. Data-plane members that wrap engine calls (snapshot, restore, volume list and removal, service copy, artifact transfer) pass canonical provider failures through and use their own category only for failures they detect themselves. Defects and interruption are unchanged. Providers MUST still redact errors at construction as defense in depth.

### 5.8 Bundled providers

Bundled providers MUST implement the complete `RuntimeProvider` contract; the known managed Windows exec limitation below remains tracked in #1888.

#### 5.8.1 Default: Lando-managed runtime (`@lando/provider-lando`)

The default provider uses Podman privately but presents the “Lando runtime” to users. It owns verified runtime bundles, private configuration and storage, its API endpoint, and managed macOS/Windows machines under Lando-controlled roots (§12.4). Production bundle entries MUST name immutable published assets with real checksums and sizes and MUST remain available for older binaries. Overrides MAY redirect development to another manifest or paired URL/checksum but MUST NOT disable verification. Resolution precedence is alternate manifest, paired URL/checksum, then bundled manifest; there is no channel-aware or runtime-fetched production manifest.

Status first observes the existing API. HTTP, protocol, permission, timeout, and unclassified failures MUST retain their failure; only a connection failure with `ENOENT` or `ECONNREFUSED` establishes endpoint absence and permits separate idle evidence. This applies to both provider status and minimal-bootstrap app discovery. A failed resource listing MUST NOT be hidden by a later absent endpoint. On macOS and Windows, read-only inspection of the managed machine reporting `stopped` supplies idle evidence after definitive endpoint absence. On Linux, the installed managed runtime uses a Lando-written, owner-only, atomically written shutdown receipt in provider-lando's confined plugin state: `{ generation, bootId, state: "admitted" | "stopped" }`, stored in a versioned StateBucket. Every admission, including setup, MUST invalidate prior idle evidence under the runtime launch lock before spawning the runtime, recording a fresh random generation and the current kernel boot id; a failed admission write MUST prevent launch. Host-maintainer teardown holds that same launch lock, reads the receipt generation before checking quiescence, and records `stopped` only after the API establishes quiescence, the service exits, and private pause teardown succeeds. Its generation compare and write MUST share the bucket's advisory lock with admission; a changed generation makes shutdown a no-op. After definitive endpoint absence, an installed bundle and no positive managed-process match, a readable receipt supplies idle evidence when it records `stopped` in the current boot or its boot id differs from the current boot id. A changed boot id proves no Lando admission since that boot. Missing, unreadable, or undecodable receipts and unreadable boot ids supply no evidence; `admitted` in the current boot remains `ProviderUnavailableError` and app runtime state remains `unknown`. Process matches MAY supply positive diagnostics only; process-scan absence and existing boot/PID-namespace ownership records do not establish quiescence. None of these observations may launch the runtime, and idle never authorizes resource pruning (§5.3).

The managed provider declares `serviceInit` and owns the init helper that realizes it (§6.2.1). On Linux the helper is a static `catatonit`, and it is a component of the runtime bundle recipe, not an independently installed tool. The bundle source manifest (`runtime-bundle-sources.json`) is the one authored pin: for x64 and arm64 it names the Debian package URL, digest, and size, the archive member, the extracted binary's digest, size, and ELF machine, the upstream source archive pin, and the verified license texts. The assembler extracts only that regular member, verifies the binary is a static ELF of the pinned architecture, and packs it as `bin/catatonit` with its notices under `licenses/catatonit`. Recipe version `0.1.8` is the first helper-bearing Linux payload. The committed published manifest (`runtime-bundle-versions.json`) keeps naming the real released `0.1.7` assets until the normal release workflow publishes and pins a helper-bearing bundle; no production pin is invented ahead of that release.

Installation verification treats the helper as part of the payload. For a helper-bearing version, a same-version installation counts as complete only when the runtime entrypoint, a verified helper (digest, static ELF, executable mode, owner-controlled regular file), and its notices are all present; otherwise the bundle is reinstalled from verified bytes. A helper-bearing installation whose helper or notices are still missing or damaged after that fails setup with remediation and MUST NOT fall back to a Debian download, because the bundle itself is the only source of its helper.

One bounded compatibility bridge exists for the transition. It applies only when the persisted installation marker is exactly the published `0.1.7` version. The bridge verifies an installed helper and reuses it offline; only when the binary itself is unusable does it download the same pinned Debian package, extract only the regular member, verify it, and publish it atomically as an owner-controlled executable under the private runtime bin path. License texts are fetched only when the notices are incomplete. A `.catatonit.identity` receipt recording the pin is written last and marks completion, so an interrupted bridge is redone, never trusted. A missing, unmarked, or any other installation marker fails with `lando setup` remediation rather than a guessed helper source. Retiring the bridge after publication and an explicit upgrade path is tracked in #1934.

Native init preparation belongs to creation. Setup and the operations that create or start a service with effective `init: true` (`apply`, and `start`, `restart`, or `resume` of such a service) prepare the helper and configuration under the runtime launch lock; a service whose `init` is absent or `false` never requires a helper download. Operations that read or tear down existing resources (status, logs, list, inspect, exec, environment reads, copies, volume discovery, service stop and suspend, destroy, observed removal, and file-sync inspection or disposal) use the already-running runtime as it is: they do not launch, repair, reconfigure, or download anything, and an unreachable endpoint is a tagged `ProviderUnavailableError`, never an empty or healthy answer. Preparation produces the desired configuration once and writes a file only when its content or mode differs, so repeated setup or start against a matching installation performs zero writes and no relaunch.

The provider points `[containers].init_path` in its private `containers.conf` at that canonical helper path rather than enabling a global init override. The runtime configuration revision is part of the owned daemon's launch identity, so an already-running Lando-owned daemon with an older revision is relaunched once with its live run root preserved; daemons Lando does not own are never relaunched. Managed macOS and Windows machines use the guest helper reached through the existing machine seams, verified with the guest's own `catatonit --version` when native init is prepared, and never a host path. Setup's smoke probe creates its probe container with init enabled. When the provider declares `deploy.resources`, `lando setup --smoke` also starts a container with `Memory`, `MemoryReservation`, `PidsLimit`, and `NanoCpus` and verifies that its `/sys/fs/cgroup/memory.max`, `pids.max`, `cpu.max`, and `memory.low` hold the requested values; a mismatch fails smoke with remediation.

Each data root's Linux runtime is isolated from every other data root and from system Podman run by the same user. One provider module owns how Lando invokes the managed Podman: its global storage, run-root, and config arguments, its child environment, and its private runtime directory. Every managed Podman process Lando starts, including the API service, uninstall cleanup, and `unshare`, uses all three. A Podman client that only talks to the running service's API in remote mode (`--remote --url` the managed socket) opens no storage, so it uses a minimal environment instead and never becomes a second storage user; repository tooling such as Linux runtime-bundle assembly uses that form.

- The child environment is an allowlist of host variables (home and user identity, locale, time zone, temporary directory, HTTP proxy, TLS trust files, and registry credential locations) plus Lando's overlay. Variables that redirect or reconfigure Podman (`CONTAINER_HOST`, `CONTAINER_CONNECTION`, `CONTAINERS_CONF_OVERRIDE`, storage overrides, and pause or user-namespace controls) MUST NOT reach it. Only the overlay is part of the launch identity and of the persisted launch record, so host variables never trigger a relaunch; the overlay's `PATH` keeps the host search path after the runtime bin directory, and launch matching compares only that managed prefix. macOS and Windows machine commands drop the same redirect variables but keep the host's machine configuration.
- `XDG_RUNTIME_DIR` is a private directory `lando-<16 hex digits of the SHA-256 of the canonical runtime directory>`, owner-only, under `/run/user/<uid>`, or under the session `XDG_RUNTIME_DIR` when `/run/user/<uid>` is not an owner-only directory owned by the user. With neither, setup fails closed with remediation. The directory sits under the session runtime base rather than under the data root, because Podman's rootless port helper binds Unix sockets below it by full path. `/run/user/<uid>` is normally a session tmpfs that reboot clears, as Podman expects; Lando checks a fallback base only for ownership and permissions, not its filesystem type or lifetime. Podman keeps its rootless pause process, user namespace, OCI runtime state, and network namespaces there. Podman storage created before this rule keeps the temporary directory recorded in its database; the pause process and user namespace are private regardless.
- The API socket path MUST fit the Unix socket path limit (107 bytes on Linux). Setup planning checks it before any download, the launch path checks it again, and doctor reports it as `managed-runtime-socket-path`. The failure names the byte count, the limit, and the longest data root that fits; it is never retried.
- Readiness observes the service process. A service that exits before its API answers fails immediately with the redacted tail of `runtime/run/service.log` and remediation naming that file, instead of waiting out the readiness budget.
- Containers started under one private runtime directory cannot be managed from another. Before a live owned daemon is replaced, its recorded launch directory is compared with the one the replacement would use. When they differ (or the record has none) and the daemon's API reports running or paused containers, or cannot list them, including because it no longer answers, the launch fails closed with remediation to run `lando poweroff`, naming how many containers are still running when the inventory was readable. A dead daemon is replaced without this check.
- On Linux the service gives containers their own cgroups by running in a delegated systemd user scope. A launch is eligible when the host's own `systemd-run` (an absolute host path, never the runtime-bin shim) and `/usr/bin/env` are executable, the user manager's `/run/user/<uid>/systemd/private` socket exists, the unified cgroup v2 hierarchy is mounted, and `user@<uid>.service` offers the `memory`, `pids`, and `cpu` controllers. These are a few stat and read calls; ordinary commands add no subprocess or polling. An eligible launch runs `systemd-run --user --scope --quiet --collect -p Delegate=yes [--expand-environment=no] --description=… -- /usr/bin/env XDG_RUNTIME_DIR=<private dir> <exact Podman argv>`. `--expand-environment=no` is passed when the host's systemd (254 or newer, read once at launch) supports it, so a `$` in a data-root path is never expanded. The launcher receives the managed child environment with `XDG_RUNTIME_DIR` set to `/run/user/<uid>`, so it reaches the user manager through `systemd/private`; `env` restores the private directory before Podman starts. Nothing in the launch receives a D-Bus address, Podman stays off the user's bus, and healthchecks keep `DISABLE_HC_SYSTEMD`. In scope mode `systemd-run` registers its own PID and then execs, so the launched PID, the PID file, the launch record, exit observation, and orphan matching all keep the Podman identity; ownership checks also recognize the launcher and `env` stages of that PID so a check made before the exec chain completes still sees the service. An ineligible host launches the service undelegated, as before.
- The runtime-bin `systemd-run` shim stays installed for Podman's descendants, whichever way the service launched: Netavark runs `systemd-run -q --scope --user` for aardvark-dns with the private `XDG_RUNTIME_DIR`, which has no manager socket, so the shim execs the command directly.
- Once the service answers its API, the launcher has exec'd into Podman, and the provider records the observed placement in the launch record as `containerCgroups`: `delegated` when the service's cgroup is owned by the user and offers `memory`, `pids`, and `cpu`, otherwise `shared`. A launch that selected the delegated scope but is observed `shared` is stopped and fails with a tagged error and remediation; it never falls back to a shared placement silently. A `systemd-run` failure surfaces through the early-exit path with the service log's stderr.
- A running owned service whose launch record is not `delegated` while the host is now eligible is relaunched by the next ensure only when its API lists no running or paused containers. The relaunch stops only the owned API process and keeps the private runtime directory, pause process, and namespaces. With containers running, the service is kept, the live capability withholds `deploy.resources`, and its remediation asks the user to run `lando poweroff` and start again. Containers created before the service moved into a delegated scope keep no cgroup of their own until they are recreated.
- Doctor's `managed-runtime-container-cgroups` check reports, for a running service, the placement it observes now and how many running containers share the service's cgroup instead of having their own; for an idle runtime it reports what the next launch will do and, when that launch cannot be delegated, the step that enables it.
- Stopping the service (`lando poweroff`, uninstall) terminates this data root's pause process only after the daemon has exited and the API listed no running, paused, or created containers, and after a best-effort reap of lingering exec helpers. Teardown uses the private directory recorded in the service's launch record, falling back to the current resolution, so a session whose runtime base changed still finds the pause. The pause is read from that directory's `pause.pid` and signaled only when it runs as the user, in a user namespace other than Lando's, with `_PODMAN_PAUSE=1` and that private directory as its `XDG_RUNTIME_DIR`. A pause belonging to another data root or to system Podman is never signaled. Purge also stops any pause its own cleanup started and removes the private directory.

Before it stops its runtime service, the provider makes a bounded, best-effort attempt to remove build-only containers left in its private storage. That attempt MUST NOT remove service containers, volumes, artifacts, or build cache, and its failure MUST NOT block the stop.

Podman-backed providers require Podman 6 or newer. Supported managed hosts are Apple Silicon macOS, Windows 11 or newer, and Linux with cgroups v2 and nftables; rootless networking uses Pasta with Netavark/Aardvark. Unsupported legacy stacks MUST fail closed with tagged remediation.

Intel macOS is unsupported by the managed provider. Setup, bundle resolution, runtime readiness, and status MUST fail closed with remediation naming `lando setup --provider=docker` or `LANDO_PROVIDER=docker`; the provider remains discoverable so dependent capability selection does not silently skip it.

On Windows, the Lando-owned machine exposes HTTP over the named pipe `\\.\pipe\podman-lando`. The provider MUST use named-pipe transport, MUST NOT invoke Unix-socket tooling, and MUST NOT probe the Linux managed-service socket.

Known limitation (#2149, related to #1888): managed Windows non-TTY exec with streamed stdin still uses `podman.exe` over the machine connection. Its routing MUST remain unchanged until native Windows tests establish stdin/EOF, exit status, and cancellation behavior. It does not yet supervise or join the container process tree on cancellation and therefore does not satisfy §5.3's owned-tree cancellation contract.

Podman’s published machine-OS update command spelling is unresolved; this specification does not normatively require one spelling.

`bindMountPerformance` is `native` on Linux and `slow` on supported macOS and Windows hosts. The provider is bundled and active by default, but distributions MAY omit it.

#### 5.8.2 Opt-in: system Docker (`@lando/provider-docker`)

The Docker provider targets Docker Engine or Docker Desktop and is selected by app or global provider configuration. It reports bind performance as `native` for Linux Engine and native WSL2 Engine with a WSL-resident app root, and `slow` for Docker Desktop on macOS or Windows. It declares `serviceInit` and realizes it through the engine's own init setting; Lando MUST NOT install, configure, or guess an init helper on a system Docker host.

#### 5.8.3 Opt-in: system Podman (`@lando/provider-podman`)

The Podman provider targets system Podman 6 or newer and is selected by app or global provider configuration. It follows the same supported-host and fail-closed legacy-stack rules as the managed provider. It reports bind performance as `native` on Linux and `slow` on supported macOS and Windows machine-backed installations. Additional providers MUST report this capability honestly. It declares `serviceInit` and relies on the system Podman installation's own init helper; Lando MUST NOT modify system `containers.conf` or install a helper there.

### 5.9 Multi-provider apps (deferred)

One provider is selected per app. Per-service provider data remains a non-portable extension hint. Multiple providers within one app, including their networking, route ownership, lifecycle ordering, failure handling, and capability negotiation, are deferred. Host-provider placement of the global app and cross-provider SSH delivery (§10.4) are not deferred. Cross-provider routing is unsupported: an enabled router with nonempty routes MUST fail planning when the app provider differs from the host provider (§10.2).
