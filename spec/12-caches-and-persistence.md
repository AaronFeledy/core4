## 12. Caches and Persistence

### 12.1 Cache catalog

The persisted app-plan key includes private implementation coordinates `{ name, source, realpath, identity }` for every selected non-bundled plugin with a path (§9.7), the resolved planning data name, and app kind (`user`, `scratch`, or `global`). The contribution graph captures plugin coordinates when it imports packages, including entryless packages, and carries them to planning outside the SDK registry contract. Planning MUST NOT walk plugin trees again. An unchanged implementation retains cache hits; editing any included source file or repointing the same name and version to another realpath invalidates the key. If the post-import identity differs from the pre-import observation, that invocation MUST skip persistent plan-cache writes. Help, version, and fresh cached-tooling paths MUST NOT perform the identity walk. Plugin coordinates are key inputs and do not change payload semantics; the private app-plan schema revision is 50.

`<userCacheRoot>` holds only regenerable caches, diagnostics, and operation-scoped temporary files (§7.5). Clearing it between operations MAY cost rebuild time or network access and MUST NOT lose ownership records, live-resource state, security floors such as the update-manifest replay floor (§17.6.1), or user data. Rows under `<userDataRoot>` are durable records listed here for their catalog identity.

Plugin command metadata has no persisted cache; it is projected from the plugin contribution graph on demand (§9.7). A retained MCP host keeps a generation's projections and catalog descriptors in memory, keyed by that generation (§10.14). The fresh-cache routing path validates known freshness metadata but MUST NOT parse Landofiles, resolve includes, import plugin modules, contact plugin sources, or initialize providers. On the CLI host, when app command-index metadata is missing, stale, or undecodable and the app source is already resolved, dispatch and help MUST rebuild that index once through the same operation as `app:cache:refresh` before continuing (§8.7), loaded lazily off the fresh-cache path. A failed rebuild reports its own tagged error and is retried on the next invocation. Host-proxy dispatch MUST NOT rebuild.

The embedded container helper (§17.3) uses `<userCacheRoot>/tool-downloads/container-helper/linux-<arch>/<sha256>/lando-container-helper`; resolving it requires no download. The architecture directory is the stable read-only bind source (§5.3), so it and the digest directory MUST be mode `0755` on POSIX, as must the executable. Cache reuse MUST repair older restrictive modes on those directories so non-root container users can traverse them. This permission rule covers public helper artifacts only and does not relax private cache roots, credentials, logs, or staging directories. Desired, global, scratch, and provider-applied plans retain logical mounts, not this host delivery path or the selected helper digest (§5.5).

### 12.2 Cache encoding

Router and tooling hot-path caches MUST use binary encoding. `Bun.serialize` is permitted for private cache shapes; public contract caches such as `AppPlan` use Effect Schema binary encoding. A cache MUST NOT mix encodings.

Every cache is versioned. Binary files carry a cache identity, schema/Lando version, and optional freshness hash; mismatch or partial-write detection invalidates and regenerates without surfacing a user error. Command caches retain all inputs needed to validate routing freshness.

Tooling caches MUST contain only expression ASTs and static redacted metadata. They MUST NOT contain dynamic shell-variable results, decrypted secrets, host output, provider connection state, or status/precondition results.

Execution observations are bounded in-memory metadata (§22.7), not replay journals. They do not change build-cache eligibility or permit caching resolved secrets and arbitrary Effect values.

### 12.3 Atomicity

`CacheService.writeAtomic` encodes before mutation, writes and syncs a sibling temporary file, then atomically renames it. In-process read/modify/write uses an Effect `Ref`. Crashes MUST leave either the prior complete cache or a regenerable invalid file, never a partial live value.

#### 12.4.1 Managed-file transaction lifecycle

Conversion and migration (§7.4.1, §8.2.1), and every declared translation materialization (§7.4.2), MUST use the private `@lando/managed-file` transaction coordinator with `ManagedFileService`, `FileSystem`, and `StateStore`. This includes explicit refresh, init, automatic lifecycle refresh, and both code-sync commands; commands, lifecycle handlers, and translators MUST NOT bypass it. It locks the canonical app root, rejects source/destination symlinks, and requires targets, backups, and stage parents to remain under that root. Only the journal under the state-store root is exempt.

Init acquisition and pure preview are not generated-file materialization. Init MUST place permitted source files and establish the final canonical root before committing generated fragments/Landofiles through this coordinator (§8.8.13). It MUST NOT create transaction or ownership records in an acquisition-cache root and relocate them later. Failures after source placement MUST retain truthful side-effect/recovery context rather than promise whole-init rollback.

Every existing regular input MUST have an immutable digest-named backup. Reuse requires exact digest, regular non-symlink type, and owner-safe mode. Stages are exclusive and same-directory. Existing nonsecret outputs preserve mode; new outputs are restrictive; secret outputs are owner-only. Raw bytes and secrets MUST NOT enter events, diagnostics, telemetry, transcripts, or journals (§3.5, §3.7).

For config datasets, every secret-bearing target, stage, backup, and snapshot MUST pass §10.12.7 before mutation: owner-only file access, owner-controlled repository parents without group/world write access, containment, gitignore coverage for each repository path, and export/support-bundle exclusion. Repository parents MAY be `0755`; Lando-owned secret-storage directories MUST remain private, with equivalent protections through Windows ACLs. Ignoring the target alone MUST NOT authorize a sibling stage or backup. An unsafe required backup MUST block the transaction, not be skipped or written publicly.

The journal state is `prepared` → `committing` → `committed` or `blocked`. Before mutation, a complete ordered before/after plan MUST be durably recorded. Commit rechecks digests around each rename and durably records completion before cleanup. Recovery derives applied operations from recorded before/after state, MUST preflight every path, and MUST NOT overwrite concurrent edits forward or backward. Conflicts preserve user files and mark `blocked`; cooperative locking is not filesystem-wide atomicity against noncooperative editors.

A crash before `prepared` MUST alter no target. Unjournaled stages MUST NOT be guessed or auto-deleted. Recovery and scoped cancellation remove only identity- and digest-verified owned stages. Committed journals are removed after cleanup; immutable backups remain. A transaction guard MUST run before native loading and start, recovering safely or refusing blocked state. The guard exposes two distinct entry points plus a pending-journal report: the recovering one, used by ordinary loads and start, and a read-only readiness one, used by candidate validation (§8.2.1), which recovers nothing and refuses `prepared`, `committing`, and `blocked` journals with a `pending-transaction` or `blocked` `ManagedFileTransactionError` whose text and remediation tell the user to run an ordinary load or resolve by hand. Which journal states permit a read is decided here, not by the Landofile loader. Dry-run reports recovery but MUST NOT lock for writing or mutate anything.

#### 12.4.2 Durable ownership manifest

This durable provider-private identity record lets stop, destroy, and a converging start finish when a failed or interrupted attempt left resources in place (§5.3.1, §6.7). It survives app-plan cache invalidation. Verified absent or removed containers and private networks are retired; named volume identities remain until the existing volume flags select their cleanup (anonymous volumes are never recorded, §6.5).

| Field | Contract |
|---|---|
| Namespace | `resource-ownership` on the provider-private `ctx.stateStore`, keyed by canonical owner. |
| Document | One JSON object per owner, version 1. |
| Mode | `0600`. |
| Lock | Advisory. |
| Corruption or version mismatch | Fail closed. Do not treat the hint as absent. |
| Payload | Container, private-network, and volume identities and digests only, with expected app, provider, root, and owner, and the actual physical name. No raw config, no per-value hashes, no resolved secret values. |

`ResourceOwnership` (`appRoot`, `ownerKey`, `providerId`, `appIds`) is the summary hint. `OwnedResourcesCleanupResult` (`servicesRemoved`, `networksRemoved`, `volumesRemoved`) is the verified cleanup result. `RuntimeProviderContribution.resourceOwnership(ctx, root)` reads this namespace from the filesystem and MUST NOT construct, initialize, or contact a runtime. The global app root's inventory is scoped to the realized global provider, or the host provider when no applied global plan exists (§5.3.1). Cleanup MUST verify ownership labels before mutation; recorded names alone are not ownership proof. A legacy unlabeled network entry is retired after its verified-by-id removal, or a 404 for that id, consistent with §5.3.1.

### 12.5 Hot-path read budgets

Warm router reads of core, app-command, and CWD-map indexes MUST complete in under 30 ms. Warm tooling reads of `app-plan` and compiled `ToolingProgram` MUST independently complete in under 30 ms. No provider contact, include resolution, expression parsing, or graph construction occurs on these paths. The perf-budget suite enforces both (§13.1), alongside the user-visible budgets in §2.1.

#### 12.5.1 Compiled hot-path decoders

Schema decoding on the CLI hot path uses ahead-of-time compiled decoders under the §2.5 policy: the schema stays the canonical contract, the CLI installs the compiled set, and embedding hosts keep the interpreter. This section fixes what the policy leaves to the cache layer: which schemas, where the module comes from, and how caches meet it.

- The compiled set is the fixed, ordered AST list in `core/src/cli/compiled-decoder-targets.ts`: `GlobalConfig`, `LandoRuntimeOptions`, `BunShellScriptFrontMatter`, the CLI command init and run events, the deliverable-event union, `LandofileShape`, and `AppPlan`. Install order and AST identity are the contract; the generated module MUST be regenerated after any change to a listed schema, to the list, or to the Effect version, and the target list MUST NOT import the generated module so generation works on a clean checkout.
- The `compiled-decoders` derived codegen entry (§17.2) emits the gitignored generated module and its declaration. `runCompiledCli` installs them before any decode; `makeLandoRuntime` and other library entries never install them.
- Compiled and interpreted decoding MUST agree on verdict, decoded value, and every issue path and message. The parity suite (§13.1) decodes the Landofile corpus in separate interpreted and compiled processes and fails on any difference.
- Membership is earned and kept under §2.5: end-to-end measurement on compiled binaries against the §2.1 hot-path budgets, recorded with the change that adds the schema. Compiled decoders optimize the hot path; they are never a second source of truth for validity.
- Binary hot-path caches (`core-command`, `app-command`) are V8-serialized behind header checks and perform no Schema decode, so they have nothing to compile. Effect Schema binary caches (`app-plan`, `global-app-plan`, `scratch-app-plan`) decode through the compiled `AppPlan` decoder when installed.

### 12.6 Disconnectable local-dev state

After successful materialization/build, resolved plugins and includes, provider metadata and artifacts, app-plan/tooling caches, and service information required for routine development MUST be local. `start`, `stop`, `restart`, `info`, `logs`, and cached tooling MUST work without network access when state is complete. `app:rebuild` and `meta:global:rebuild` refresh referenced artifacts with local fallback and a warning (§6.13.3); acquisition needs network only for referenced artifacts with no local copy. Build steps that download packages still need network access when they execute rather than reuse a cached build layer.

Missing managed dependencies fail with a tagged error naming the missing artifact and online repair command. Routine offline-capable commands MUST NOT silently retry the network. Telemetry and update checks are best-effort and MUST NOT invalidate caches or alter local-command exit status.

Automatic translation MUST use local snapshots and stored same-identity nonsecret metadata without API probes or TTL refresh (§7.4.2). Missing required metadata/output MUST block mutation with explicit refresh remediation. Explicit translation/code-sync metadata fetch failures MUST fail visibly, never use stale-success fallback or another environment's cache. Init populates required metadata before it reports success (§8.8.13), so first-start translation needs no vendor API call; this does not waive normal runtime/image/build dependency acquisition. Remote sync and tether require their declared connectivity and are not routine offline workflows.

### 12.7 State store

`CacheService` is the process-lifetime memo and raw atomic-cache service. `StateStore` is the level-`minimal` core Effect service for durable, schema-validated, versioned, atomic, optionally cross-process-locked files (§3.4). It is host/test-overridable but MUST NOT be a plugin contribution surface (§4.2).

#### 12.7.1 Buckets

`StateStore.open` accepts `StateBucketSpec` and returns `StateBucket`. Named contracts are `StateRoot`, `StateCodec`, `StateBucketSpec`, `StateBucket`, `StateMigrator`, and tagged `StateStoreError`. A bucket maps to exactly one contained file; opening resolves and validates the path without reading.

`StateRoot` selects user data/cache/config, an app root, or an explicit host path. A bucket rooted in the user cache root is a cache bucket: its spec MUST declare a `default`, its corruption policy MUST be `discard` or `quarantine`, and a version mismatch MUST discard, so a cleared or damaged cache reads as absent (§12.1). The SDK types enforce this, and `open` rejects a violating spec with `StateStoreError` for untyped callers. Durable records use any other root. `StateCodec` is `json`, `binary`, or a custom codec for a user-facing stable format. `StateBucketSpec` names root, optional namespace, single-segment key, Effect Schema, version, codec, lock policy, corruption/version policy, and optional default. `StateBucket` exposes `path`, `get`, `set`, `update`, `modify`, `remove`, and `exists`.

All mutations encode before atomic replace. Version mismatch either discards or runs `StateMigrator`. Corruption policy is quarantine, discard, or fail. Advisory locking serializes mutation across processes, is scope-acquired, and uses bounded stale-owner recovery. Resolved paths MUST remain under their root; traversal, absolute keys, and symlink escapes fail with `StateStoreError` reason `path`. Roots MUST come from §7.5.1. `StateStoreError` also distinguishes `io`, `decode`, `lock`, and `version` and carries operation, path, cause, and remediation.

Hot-path caches remain under their existing readers and MAY adopt `StateStore` only while preserving §12.5 budgets.

User-app mutation locks MUST be keyed by canonical root independently of app id, so a same-folder `name` change cannot bypass serialization (§7.4). Scratch and global mutation-lock keys retain app id plus canonical root.

App mutation locks left by dead commands MUST be reclaimed without a contention warning. Reclaim and vanished-file attempts retain the normal acquire deadline and retry delay; only an observed live holder triggers the wait message. A lock path that can never be reclaimed (a symbolic link, not a regular file, hard-linked, or owned by another user) fails at once with a `StateStoreError` whose remediation names the path and why it is unusable, never with a contention message.

Each process MUST own the mutation lease it uses. Nested canonical commands and SDK calls MAY reenter through the owning process's Effect context; another process MUST NOT borrow that lease through an inherited token or an ancestor PID. A recognized live ancestor or inherited-token owner MUST cause an immediate `StateStoreError` with reason `lock` and operation `nestedAppMutation`, with remediation to invoke the operation in process or run it separately after the owner finishes. Other processes acquire their own lease under the ordinary bounded wait. Once the earlier owner releases its lease or dies, a child MAY acquire a fresh lease normally. This contract applies to hook-launched CLI commands as well as unrelated callers.

#### 12.7.2 Reference consumers

The scratch registry uses an advisory, quarantining bucket; the include lockfile uses an app-root custom YAML codec in an unlocked bucket, and its writers re-read and merge under a host-wide `StateStore.withLock` operation lock so no lock file lands beside it; snapshot sidecars use owner/store-scoped, version-2 JSON buckets that migrate version 1 unchanged and fail on corruption or unsupported version mismatch, with per-snapshot removal locks; and the managed-file ledger uses an advisory, quarantining bucket. The provider resource-ownership manifest uses an advisory, fail-closed bucket in the provider-private `resource-ownership` namespace (§12.4.2). The accelerated-start journal uses an advisory, fail-closed, version-migrating bucket in the user-data `accelerated-starts` namespace (§10.6.3). Per-folder data identity uses an advisory, fail-closed, version-1 JSON bucket in the user-data `app-data-identity` namespace, one document per owner key (§7.4). The source store keeps its npm, git-ref, and lockfile-root index records as version-1 JSON buckets in the one user-cache `sources` namespace, distinguished by key prefix, so they land directly under `<userCacheRoot>/sources/` beside the entry directories (§12.8). These subsystems MUST NOT implement bespoke persistence primitives.

Detached host-proxy and agent-relay worker locks MUST live under the resolved user-data `operation-locks` namespace, outside disposable run directories. Their stable key combines worker kind with a SHA-256 digest of the absolute run-directory path. Ensure, replacement, shutdown, teardown, and root sweeping MUST use the same identity and injected private-file access and MUST NOT expire a live owner. Host-proxy root sweeping MUST acquire before inspecting or deleting worker state, including legacy and untrusted records, and MUST leave reserved agent-relay and tunnel directories to their owners. Release removes the individual lock file. Removing a worker run directory MUST NOT remove its operation lock; removing the user-data root also removes the operation-lock namespace.

#### 12.7.3 Plugins and embedding hosts

Plugins receive a `stateStore` factory pre-namespaced to `plugins/<plugin-id>/` under user data and MUST NOT access core or other-plugin state (§9.8). Embedding hosts MAY open explicitly isolated buckets (§16.5). `@lando/core/testing` supplies `TestStateStore`; `@lando/sdk/test` supplies `runStateStoreContract` and `StateStoreContractHarness`.

### 12.8 Source store

The source store is the one acquisition cache for every remote tree Lando fetches: Landofile git and npm includes (§7.7), recipe sources and `extends:` parents (§8.8.4), and npm plugin installs and updates (§9.6). It is owned by the private `@lando/source-acquisition` package, which derives its root from the directory of a user-cache `StateStore` bucket in namespace `sources`; callers supply no separate physical root. Consumers keep their own policy (lockfile pins, checksum prompts, plugin trust and install immutability) and MUST NOT fetch, verify, extract, or publish remote trees outside it.

#### 12.8.1 Layout and identity

Physical entries are content-identified: `git/<commit>/` for a full 40-hex commit and `archive/<sha256>/` for an archive keyed by the SHA-256 of its downloaded bytes. npm packages are archive entries whose tree holds the published `package/` directory. Each entry is `tree/` plus `entry.json` (`version: 1`, `format: 1`, `kind`, `id`, `treeDigest`, and display-safe `provenance`); an entry whose record is missing, undecodable, or inconsistent with its directory name is absent, never partially usable. Git initializes with an empty template, disables hooks, and checks out exactly the fetched commit with `core.autocrlf=false`, `core.eol=lf`, and `.git/info/attributes` overriding text, filter, ident, eol, and working-tree-encoding attributes. Committed bytes survive unchanged; `.git` is removed. Per-commit trees avoid a git spawn per file read during recipe copies; explicit GC bounds their storage instead of retaining a bare object store.

HTTP(S) git fetch and `ls-remote` share the HTTP client's resolved network trust: scheme-specific proxy or explicit direct connection after `NO_PROXY`, and a temporary owner-only CA bundle honoring custom PEMs, host trust, and Windows host roots. Cleanup removes the bundle after use; diagnostics redact proxy credentials. Undefined trust retains git's defaults. SSH and scp-style URLs retain SSH configuration without HTTP trust projection.

Three kinds of index record are user-cache `StateStore` buckets (§12.7.2), not entries. They share the single namespace `sources`, so each record is a file directly under `<userCacheRoot>/sources/` beside `git/`, `archive/`, and `.leases/`, and the record kind is carried by the key prefix: `npm-<sha256>` maps a registry plus `name@version` (credentials stripped, the whole coordinate hashed into the key) to the archive digest and the `integrity`/`shasum` it was verified against; `ref-<sha256>` maps a hashed `url#ref` to the last fetched commit; `root-<sha256>` records each `.lando.lock.yml` path whose include walk reached a remote source. `npm-<hash>` and `ref-<hash>` records are written only after their entry is published and verified, and a record that no longer matches a request is a miss, not a stale hit. `root-<hash>` records are registered before any acquisition: the first remote include of a walk registers the walk's lockfile path under the store lock, once per session, so the root is protected before the entries it will pin exist.

Every path under the store is containment-checked against the canonical store root, and symlinked entries, records, or trees are treated as absent.

#### 12.8.2 Integrity

- Git: identity is the commit. A full-SHA request or an exact-pin materialization MUST yield exactly that commit; a transport that returns anything else fails `fetch-failed`.
- npm: the registry MUST publish a usable `dist.integrity` or `dist.shasum`. The first SRI token of `dist.integrity` is verified when its algorithm is supported; when that first token is absent, malformed, or names an unsupported algorithm, the legacy sha1 `dist.shasum` is verified instead. A package with neither usable value fails `integrity-missing`; a mismatch against whichever value was checked fails `integrity-mismatch`. This policy applies to includes, recipes, and plugins alike. Tarball bytes MUST come from the authenticated registry client (§9.6), never a bare fetch of `dist.tarball`.
- Archive: the SHA-256 is always computed. A supplied digest MUST match before extraction (`checksum-mismatch`); with no digest the consumer's `onUnverified` policy runs with the computed digest (recipe init warns or confirms, §8.8.4).
- Extraction keeps the archive rules: path-traversal rejection, bounded gunzip, and links and devices skipped.

#### 12.8.3 Publication, immutability, and leases

Acquisition stages into a sibling `.staging-<pid>-<id>/` directory on the same filesystem, writes `entry.json` last, and renames the directory into place under the store-wide `StateStore.withLock` operation lock (§12.7). If a valid entry already exists, the staging copy is discarded; an invalid entry is renamed aside and replaced. A cross-device rename is a tagged `cache` failure, not a copy. Entries are immutable after publication. The only replacement of a valid entry is explicit repair: an online `app:includes:update` refetches authoritative bytes and, when the recomputed tree digest differs from the published tree, replaces the entry under the lock; a tampered or corrupted include entry is therefore repaired by that command rather than by deleting the cache by hand.

Every consumer works inside one scoped session. A session owns a lease file under `sources/.leases/` (`pid`, token, creation time, and the keys it has used) that is removed when the scope closes. The first open, hit, or publication of a key in a session registers it in the lease and touches `entry.json` (its mtime is the entry's last use) under the lock before the snapshot root is returned; later uses of the same key in that session are covered by the live lease and neither lock nor touch again. Snapshot roots are read-only by convention; consumers copy out what they persist (recipe init, plugin staging) or bind to the entry through lockfile pins (includes).

Operation failures are the private tagged `SourceAcquisitionError` (`invalid-locator`, `not-found`, `version-not-found`, `auth`, `fetch-failed`, `integrity-mismatch`, `integrity-missing`, `checksum-mismatch`, `extract-failed`, `offline-miss`, `cache`) with remediation. Consumers map it to `LandofileIncludeError`/`LandofileLockMismatchError`, `RecipeSourceError`, or `PluginPackageOperationError` so user-facing tags stay stable. Source coordinates in errors, records, and warnings are display-safe: URL userinfo, query, and fragment are stripped; identity keys hash the full value and never store it in plaintext.

#### 12.8.4 Offline behavior

- Opening a pinned or physical entry requires no network: a full commit SHA, a `--checksum` that matches a cached archive, an exact pin whose entry is warm, or an include lock lookup. Floating git refs resolve online (next bullet), and npm recipe and plugin acquisition always reads live registry metadata even when the archive is reused.
- A branch, tag, or default-branch git ref first resolves with `ls-remote`; a cached resolved commit skips fetch and updates its `ref-<hash>` record under the store lock. Annotated tags use the peeled commit; ambiguous short names fall through to fetch. Missing entries, unavailable resolution, and repair fetch the original ref name. A resolution failure falls through to fetch, whose existing non-authentication failure path may return the recorded cached commit when the consumer supplies a stale-fallback warning; includes never fall back (§8.8.4).
- An npm package is served from its `npm-<hash>` record in two ways. `materializeNpm` (and `acquireNpm`, used by recipe init, plugin install and update, and cold or repairing include loads) has already resolved the live packument and reuses the stored archive only when the record's registry, `name@version`, `integrity`, and `shasum` all match that packument; a different registry or republished metadata refetches and verifies again, and `repair` always refetches. `lookupNpm` (the pinned include path, which holds only `name@version` from the lockfile) contacts no registry: it prefers the record for the configured registry plus `name@version`; when that registry has no usable record, or the npm configuration naming it can't be read, it serves the most recently used archive recorded for the same `name@version` from any registry. The include's lock checksum still verifies the fragment, so an unreadable npm configuration never blocks a warm pinned load. With no candidate it returns a miss, or the registry-resolution failure when that failure triggered the search.
- `network: false` with a cold entry fails `offline-miss`; include `--no-network` semantics (§7.7.4, §8.2) are built on it and keep their messages and remediation.

#### 12.8.5 Garbage collection

`meta:sources:gc` (alias `sources:gc`, bootstrap `minimal`, §8.2) is the only path that removes entries. It reports by default and removes only with `--prune`; `--older-than=<days>` (finite non-negative integer, default 30) sets the age threshold measured from each valid entry's last use. An invalid physical entry (missing, undecodable, or inconsistent `entry.json`) is eligible regardless of age; lease and reachability protection below still apply to it. Nothing runs automatically.

Reachability is computed from the `root-<hash>` records: a `.lando.lock.yml` that still exists is read through the landofile lockfile codec, and every git commit it pins, and every archive reachable from an `npm-<hash>` record for a `name@version` it pins (any registry), is protected regardless of age. The report pass reads without the lock; on `--prune` every candidate is re-inventoried and reachability recomputed under the store lock immediately before its removal, and a candidate that stopped being eligible in between is reported `busy` (reason `touched-after-cutoff`). A missing lockfile retires its root record on prune unless any lease is live. An unreadable or undecodable lockfile, or a root record the store itself cannot decode, makes reachability incomplete: the run reports it and MUST withhold pruning of every git entry and every npm-indexed archive; only archives no npm record points at remain age-eligible, and an undecodable `npm-<hash>` record withholds every archive. Entries registered in a lease whose `pid` is alive are `busy` and are never removed; a lease file that cannot be read is reported `failed` and withholds every entry; leases of dead processes are deleted. `.staging-<pid>-*`, `.replaced-<pid>-*`, and `.gc-<pid>-*` directories are removed only when their owning pid is dead; a leftover with no parseable pid is removed only once older than the cutoff. Eligible entries are renamed aside under the lock and deleted outside it, so a concurrent reader sees a whole entry or none. On prune, `ref-<hash>` and `npm-<hash>` records whose entry is missing are removed (an `npm-<hash>` record whose archive is pinned stays, and one under incomplete reachability is withheld). The report (`SourceGcReportSchema`) carries `prune`, `olderThanDays`, `cutoff` (ISO), `reachability: "complete" | "incomplete"`, `roots` (lockfile path plus `ok` | `missing` | `unreadable` | `corrupt` and optional `detail`), `entries` (per git/archive entry: `id`, `bytes`, `lastUsedAt`, `valid`, `protected`, `leased`, `eligible`, `outcome`, `reason`, optional `npm` coordinates), `leftovers` (lease, index-record, staging/aside, and inventory-failure rows with the same outcome vocabulary and optional `pid`), and `totals` (`entries`, `bytes`, `eligible`, `eligibleBytes`, `removed`, `removedBytes`, `busy`, `withheld`, `failed`). Outcomes are `kept`, `removed`, `busy`, `withheld`, and `failed`. The CLI maps a report with any `failed` row to a nonzero exit carrying `DataTransferError` (operation `sourceCacheGc`) that lists each failed item and, on prune, the count removed before the failure; a `--older-than` value that is not a non-negative integer fails `MalformedCliFlagValueError` before the store is read.

There is no migration of pre-release `<userCacheRoot>/includes/` or `<userDataRoot>/recipe-cache/` directories; `meta:uninstall` removes both roots (§8.2).
